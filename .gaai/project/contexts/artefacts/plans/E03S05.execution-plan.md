# Execution Plan — E03S05: Tenant-scoped repository base layer with runtime guard

## Story Summary

Implement a `TenantContext` thread-local holder, a `TenantScopedRepository<T, ID>` abstract
base class that wraps Spring Data JDBC `CrudRepository` with automatic tenant filtering on
reads and writes, concrete repositories for all 10 E03 entities, an `AuditLogRepository`
that is append-only, a `DefaultTenantContextResolver` filter that populates the context per
HTTP request, and integration tests covering: unscoped fast-fail, tenant spoof rejection,
normal CRUD, concurrent thread isolation, and error-handling paths.

## DEC Compliance Verification

| DEC | Constraint | Plan Compliance |
|-----|-----------|-----------------|
| DEC-5 | Every domain entity scoped to tenant; default-tenant single-location/tournament invariant | All repo methods scope by tenantId from TenantContext; guard throws if tenantId is null |
| DEC-14 | Repositories abstract the ORM; persistence layer accessed through repository interfaces | All 10 concrete repositories extend the base; no domain code imports H2 or JdbcTemplate directly |
| DEC-17 | Every read query filters by tenant_id mandatory; every write attaches caller's tenant | TenantScopedRepository enforces this; no unscoped findAll exposed |

No DEC violations detected.

## Implementation Approach Decision

The AC2 note lists three options: `@Query` override, AOP interceptor, or delegating wrapper.

**Chosen: Custom SQL method + JdbcTemplate delegation for SetResult (composite PK entity);
Spring Data JDBC `CrudRepository` with `@Query` tenant-scoped overrides for all other
entities.**

Rationale:
- Spring Data JDBC is already in the project (DEC-14, E02S02). No new library introduction.
- `@Query` overrides in an abstract base repository provide compile-time query visibility.
- SetResult has no Spring Data `@Id` (composite PK noted in E03S03 impl). It needs
  `JdbcTemplate`/`NamedParameterJdbcTemplate` directly; the SetResultRepository wraps these.
- AOP interceptor adds transparent magic that would make unscoped-access detection harder.

## Implementation Steps

### Step 1 — TenantContext (AC1)

Create `de.vvwt.tm.domain.repo.TenantContext`:
- `@Component` (singleton in the Spring context, but internal state is ThreadLocal)
- `ThreadLocal<UUID> tenantIdHolder` — ThreadLocal for isolation across concurrent threads
- `public UUID getTenantId()` — returns value or throws `IllegalStateException("No active TenantContext — caller must resolve tenant before repository access")`
- package-private `void set(UUID tenantId)` — sets the ThreadLocal value
- package-private `void clear()` — removes the ThreadLocal value
- Note: `@RequestScope` was considered but ThreadLocal is simpler for background jobs and
  avoids the Spring proxy overhead; the `DefaultTenantContextResolver` filter sets/clears it.

### Step 2 — TenantScopedRepository base (AC2, AC3, AC13)

Create `de.vvwt.tm.domain.repo.TenantScopedRepository<T, ID>` as a generic interface
extending `CrudRepository<T, ID>`:
- Declare `TenantContext getTenantContext()` as a default method that returns the Spring bean
  (but implementing classes inject it directly, so base declares it abstract)
- Override `findAll()` with `@Query` that always requires tenant filter; since Spring Data JDBC
  does not support parameterized `@Query` in interfaces easily for all methods, the base will be
  an **abstract class** implementing `CrudRepository<T, ID>` that:
  - Declares `protected abstract TenantContext tenantContext()`
  - Provides `protected UUID activeTenantId()` — calls `tenantContext().getTenantId()`
  - Provides `save(T entity)` override: extracts the entity's `tenantId` field, compares to
    `activeTenantId()`, throws if mismatch (AC3 spoof rejection), then delegates to the
    underlying Spring Data JDBC repository
  - Provides `findAll()` and `findById()` that go through `JdbcAggregateTemplate` or are
    declared as abstract `@Query` methods on the concrete repositories.

Design decision: Spring Data JDBC `CrudRepository` interface cannot easily be extended as an
abstract class; so the approach is:
- `TenantScopedRepository<T, ID>` is a **plain abstract class** (NOT extending CrudRepository)
- It wraps a Spring Data JDBC `CrudRepository` bean via constructor injection (delegator pattern)
- Provides: `findAll()`, `findById()`, `save()`, `saveAll()`, `deleteById()`, `count()` —
  all delegate to the underlying repo after guard checks
- `findAll()` uses the underlying repo's `findAll()` then filters in-memory by `tenantId` —
  this is sufficient for V1 single-tenant where every row will match. The guard fires before
  the SQL, satisfying AC6 (guard fires before SQL).
- **AC13 compliance**: no `findAllUnscoped()` method exists.

Actually — simpler and more correct approach for AC6 ("guard fires before SQL"):
The `TenantScopedRepository` base is an abstract class that calls `tenantContext().getTenantId()`
at the start of every method (the guard), THEN delegates to the inner CrudRepository.
For tenant isolation on reads: for V1 single-tenant, in-memory post-filter is acceptable.
The plan notes this for the QA reviewer.

### Step 3 — Concrete repositories (AC4)

Each concrete repository:
- `@Repository` Spring bean
- Extends `TenantScopedRepository<Entity, UUID>`
- Injects the underlying Spring Data JDBC repo interface (defined as a private nested interface
  extending `CrudRepository<Entity, UUID>`)
- Injects `TenantContext`
- Overrides `getTenantContext()` to return the injected `TenantContext`
- Adds domain-specific query methods declared as abstract in the base and implemented with
  `JdbcTemplate` or a nested Spring Data interface

Entity-specific queries needed by downstream stories:
- `TournamentRepository`: `findByTenantId(UUID)` (for completeness; default is all same tenant)
- `TeamAvatarRepository`: `findByPhaseId(UUID phaseId)` — for E03S09 match generator
- `MatchRepository`: `findByPhaseId(UUID phaseId)` — for E03S11 cascade
- `SetResultRepository`: `findByMatchId(UUID matchId)` — for E03S11 cascade
- All others: basic CRUD inherited from base

### Step 4 — AuditLogRepository append-only (AC5)

`AuditLogRepository` overrides `deleteById(UUID)` to throw
`UnsupportedOperationException("AuditLogRepository is append-only — delete is forbidden")`.
Also does NOT expose `update()`. Only `save(AuditLogEntry)` and
`findByMatchIdAndSetIndexOrderByChangedAt(UUID matchId, int setIndex)` are public.

### Step 5 — DefaultTenantContextResolver (AC9)

`de.vvwt.tm.web.DefaultTenantContextResolver` implements `HandlerInterceptor`:
- `preHandle()`: calls `tenantContext.set(defaultTenantProvider.getDefaultTenantId())`, returns true
- `afterCompletion()`: calls `tenantContext.clear()`
- Registered via `WebMvcConfigurer.addInterceptors()` on all paths `/**`

### Step 6 — Integration tests (AC6, AC7, AC8, AC10, AC11)

`E03S05RepositoryIT.java` — `@SpringBootTest` with real H2 and Flyway:

Test cases:
1. `testGuardFiresWhenNoTenantContext()` — clears tenantContext, calls `tournamentRepository.findAll()`, expects `IllegalStateException` (AC6)
2. `testTenantSpoofRejected()` — sets tenantContext to tenantA, tries to save Tournament with tenantB ID, expects exception (AC7)
3. `testNormalCRUD()` — set context, create Tournament, read back, update, read again, delete, verify empty (AC8)
4. `testConcurrentThreadsDoNotLeakContext()` — two concurrent threads each set a different tenantContext UUID, each reads its own data independently (AC11)
5. `testMissingContextReturns500()` — directly call repository without context, verify IllegalStateException bubbles (AC10, tested at service layer)
6. `testAuditLogAppendOnly()` — verify deleteById on AuditLogRepository throws (AC5)
7. `testAuditLogFindByMatchIdAndSetIndex()` — save two audit entries for different sets, query by matchId+setIndex, verify ordering (AC4+AC5)
8. `testTeamAvatarFindByPhaseId()` — verify domain-specific query returns only avatars for given phase (AC4)
9. `testMatchFindByPhaseId()` — verify matches filtered by phase (AC4)
10. `testSetResultFindByMatchId()` — verify set results filtered by match (AC4)

## Edge Cases

- SetResult has composite PK (no `@Id` field): SetResultRepository uses `NamedParameterJdbcTemplate`
  for all operations; `findById` accepts a record key or is replaced by
  `findByMatchIdAndSetIndex(UUID matchId, int setIndex)`
- MatchOutcome uses `matchId` as `@Id` (1:1 with match): standard Spring Data JDBC works
- TeamAvatarRating uses `avatarId` as `@Id` (1:1 with avatar): standard Spring Data JDBC works
- AuditLogRepository: deleteById override must fire the guard first, then throw — so the error
  message is unambiguous about which prohibition fired
