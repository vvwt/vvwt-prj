## Design Notes (Delivery Decisions per Story Out-of-Scope §3)

The exact composition is a Delivery design decision:

- **`TeamSortCalculator.sortTeams` signature:** accepts `List<TeamAvatar> fromAvatars`, `Map<UUID, TeamAvatarRating> ratingsByAvatarId`, `int groupCount`. All three params are always supplied (ratings map is empty for unrated phases — not Optional). The caller (`DefaultPhaseTransitionService`) bulk-loads ratings via `findByPhaseId` and passes the map to the calculator.

- **`AbstractAssignmentProposalCalculator`:** abstract class providing:
  - `protected Map<UUID, TeamAvatarRating> bulkLoadRatings(UUID phaseId, TeamAvatarRatingRepository repo)` — calls `findByPhaseId`, returns map indexed by avatarId
  - Protected helpers for building `TeamAvatarProposal` with display fields (from `Team` lookup)
  
- **`TeamSortCalculatorRegistry.knownKeys()`** returns `Set<String>`; analogous to `Team2AvatarDistributorRegistry.knownKeys()`.

- **`DraftSection.validate(TeamSortCalculatorRegistry)`** overload: accepts registry as parameter. The existing no-arg `validate()` either calls the registry-aware overload with a null check (throws if null and sortType validation is needed) or is kept for non-sort-validation scenarios. Simplest: add a new `validate(TeamSortCalculatorRegistry sortRegistry)` method; `DefaultDraftService` calls it with the injected registry.

- **`DefaultPhaseTransitionService` changes:** constructor gains `TeamSortCalculatorRegistry sortRegistry` parameter; `computeProposals` method becomes a registry dispatch + passes ratings map loaded via `findByPhaseId`; the three private `computeTeamNumber/computePlacementGroup/computeGroupPlacement` methods are deleted (logic moves to implementations).
