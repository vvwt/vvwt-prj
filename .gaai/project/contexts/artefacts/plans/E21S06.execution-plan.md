# Execution Plan — E21S06: Device Aggregate + DeviceLimit + DeviceController + DeviceAdminController

## Q-7 Safety-Valve Assessment

13 classes is at the Q-7 upper edge. Assessment:
- 6 DTOs + 1 error-response DTO = 7 thin data-carrier classes (no significant logic)
- `Device` entity = straightforward field reconstruction
- `DeviceLimitConfig` = @ConfigurationProperties (trivial)
- `DeviceCrudRepository` = CrudRepository delegate interface (trivial)
- `DeviceRepository` = JdbcTemplate-based boundary-API repository (moderate complexity, well-understood from legacy)
- `DeviceService` = domain logic (PIN generation, DeviceLimit, configure, assign-location) — well-understood from legacy
- `DeviceController` = REST endpoints (register/status/list/assign) — moderate
- `DeviceAdminController` = location-assignment admin endpoints — moderate

**Verdict: No split needed.** All 13 classes are direct reconstructions of thoroughly understood legacy code. The service logic is documented in `DeviceService.java`. The story fits one Tier-2 delivery session.

## DeviceRepository Design Decision

Using **JdbcTemplate** directly (not extending TenantScopedRepository) for the new
`de.vvwt.tm.tournament.internal.DeviceRepository`, following the same pattern as
`TournamentRepository`. Rationale: Spring Data JDBC CrudRepository cannot map two entity classes
to the same table (`devices`) simultaneously — `de.vvwt.tm.domain.Device` (legacy) and
`de.vvwt.tm.tournament.Device` (new) would collide. JdbcTemplate avoids this entirely.
This is an established convention in the codebase (E21S02 pattern). No approach-evaluation needed.

## DeviceService Design — New vs. Legacy

The new `DeviceService` reconstructs ONLY the Device Limit enforcement capability
(AC-DEVICELIMIT-ENFORCEMENT) plus register/configure/assign-location as defined in E21S06 ACs.
The PIN-generation logic (complex) IS included — it is part of `register()`.
The legacy `DeviceService` methods `assignDevice`, `unassignDevice`, `getDeviceByToken`,
`getDeviceByPin`, `listAllDevices`, `clearAllDevices` are NOT reconstructed in this story — they
are covered by existing IT tests in `de.vvwt.tm.infrastructure.web` and the field-assignment
logic is a DeviceController concern already. The scope of E21S06 DeviceService is:
- `register(UUID tenantId, String deviceType)` — enforces DeviceLimitConfig cap BEFORE insert
- `configure(UUID deviceId, String deviceName, String configuration)` — for DISPLAY devices
- `assignLocation(UUID deviceId, UUID locationId)` — location assignment admin flow (DEC-24)
- `listDevices()` — list all devices for tenant
- `deleteDevice(UUID deviceId)` — delete device

## Risk Register

| Risk | Mitigation |
|---|---|
| Spring Data JDBC entity conflict (two entities on `devices` table) | Use JdbcTemplate for new DeviceRepository (TournamentRepository pattern) |
| DeviceAdminController admin-role security gap | AC-REST-IT-SEC-DeviceAdminController IT is the gate — explicit USER→403 test |
| Concurrent register race (DeviceLimit) | Document in impl-report; count-before-insert pattern; note non-transactional |
| PIN generation complexity | Copy from legacy DeviceService; no architectural change |
| Legacy `TenantContext` import ambiguity | Use `de.vvwt.tm.domain.repo.TenantContext` (matches legacy DeviceRepository pattern) |
