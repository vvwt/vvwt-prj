# Execution Plan — E05S07: Phase lifecycle — prepare + start + advance laps (REST + Svelte view)

## Story Summary

Expose the E03S12 4-step phase preparation flow through REST and Svelte:
- `POST /api/phases/{phaseId}/prepare` — runs steps 1–3 (generateMatches, optimizeSlots, assignReferees)
- `POST /api/phases/{phaseId}/start` — runs step 4 (startPhase, transitions PENDING → ACTIVE)
- `POST /api/phases/{phaseId}/advance-lap` — manual fallback lap advance (with force override + audit)
- `GET /api/phases/{phaseId}` — phase detail with status, lap number, match counts
- `GET /api/tournaments/{tournamentId}/phases` — list all phases ordered by sequence_number
- `GET /api/phases/{phaseId}/schedule` — match schedule organized by lap and field
- Svelte phase overview route: status badges, action buttons, schedule grid, lap tracking via WebSocket

## DEC Compliance

- **DEC-4 (V1 amendment)**: preparation calls `PhasePreparationService` in-process via `vvwt-worker-lib` —
  already implemented in E03S12. This plan merely exposes it via REST. No violation.
- **DEC-5**: all phase endpoints verify `phase.tournamentId → tournament.tenantId == activeTenantId()` (AC15).
  Tournament ACTIVE transition respects single-active-tournament invariant via `active_sentinel` schema column.
- **DEC-9**: schedule response uses TeamAvatar (phaseId, groupNumber, groupPosition) as identity — no UUID
  crossing the response boundary except as identifiers.
- **DEC-14**: audit_log for forced lap advance requires a `phase_audit_log` table (separate from the
  set-level `audit_log` — match_id FK is NOT NULL in V5 and cannot hold phase-level events without
  a migration to make it nullable, which would break existing append-only semantics).
  Decision: add `V9__e05s07_phase_lifecycle.sql` with a new `phase_audit_log` table.
- **DEC-17**: all new entities carry `tenant_id NOT NULL`.

## Implementation Steps

### Step 1 — DB Migration (V9)

File: `src/main/resources/db/migration/V9__e05s07_phase_lifecycle.sql`

- Create `phase_audit_log` table for phase-level governance actions (forced lap advance, etc.):
  - `id UUID NOT NULL PK`
  - `tenant_id UUID NOT NULL FK → tenants(id)`
  - `phase_id UUID NOT NULL FK → phase(id)`
  - `action VARCHAR NOT NULL` (e.g. `'FORCE_ADVANCE_LAP'`)
  - `lap_number INT NOT NULL`
  - `unfinished_match_count INT NOT NULL`
  - `actor_id VARCHAR NULL`
  - `changed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`
- Create index: `idx_phase_audit_log_phase_id ON phase_audit_log (phase_id, changed_at)`
- Create index: `idx_phase_audit_log_tenant_id ON phase_audit_log (tenant_id)`

### Step 4 — Domain: PhaseLifecycleService

File: `src/main/java/de/vvwt/tm/domain/PhaseLifecycleService.java`

Responsibilities:
- `prepare(UUID phaseId)` — calls `PhasePreparationService.generateMatches`, `optimizeSlots`, `assignReferees`
  in sequence (steps 1–3 only). Returns `PhasePreparationResult` record with step outcomes.
  Catches exceptions per-step, wraps in result object (step name + success/failure + message).
  Synchronous: V1 targets 9 teams / exhaustive mode (~seconds). HTTP client may use longer timeout if needed.
- `start(UUID phaseId)` — calls `PhasePreparationService.startPhase(phaseId)`.
  Also transitions tournament status from PLANNED → ACTIVE (DEC-5 single-active guard via schema).
- `advanceLap(UUID phaseId, boolean force, String actorId)` — manual lap advance:
  - Load phase, verify ACTIVE status (409 if not)
  - Count unfinished matches in current lap
  - If unfinished > 0 and !force → throw ConflictException (409) with count in message
  - If force: write `PhaseAuditLogEntry` (action=FORCE_ADVANCE_LAP, lapNumber=currentLap, unfinishedMatchCount)
  - Increment `phase.currentLapNumber` by 1, save phase
- `getPhase(UUID phaseId)` — load Phase, return with match counts (by state) and total lap count
  (derived from distinct lapNumber values on matches)
- `listPhases(UUID tournamentId)` — return all phases for tournament, ordered by sequenceNumber,
  each with status, currentLapNumber, match progress summary
- `getSchedule(UUID phaseId)` — return matches organized by (lapNumber, fieldNumber), with
  TeamAvatar descriptions for both teams and referee; resolve avatar/team descriptions from
  TeamAvatar + Team tables

### Step 6 — Controller: PhaseController

File: `src/main/java/de/vvwt/tm/infrastructure/web/PhaseController.java`

Endpoints:
- `POST /api/phases/{phaseId}/prepare` → `phaseLifecycleService.prepare(phaseId)` → 200 PhasePreparationResponse
- `GET  /api/phases/{phaseId}` → `phaseLifecycleService.getPhase(phaseId)` → 200 PhaseResponse
- `GET  /api/tournaments/{tournamentId}/phases` → `phaseLifecycleService.listPhases(tournamentId)` → 200 List<PhaseResponse>
- `POST /api/phases/{phaseId}/start` → `phaseLifecycleService.start(phaseId)` → 200 PhaseResponse
- `POST /api/phases/{phaseId}/advance-lap` → `phaseLifecycleService.advanceLap(phaseId, force, actorId)` → 200 PhaseResponse
- `GET  /api/phases/{phaseId}/schedule` → `phaseLifecycleService.getSchedule(phaseId)` → 200 PhaseScheduleResponse

Tenant scope (AC15): all endpoints resolve tenant via TenantContext (same as all other controllers —
repository calls enforce scope structurally; controller adds a `requireTenantScope(phase)` check
that throws `NoSuchElementException` if `phase.tournamentId → tournament.tenantId != activeTenantId()`).

### Step 8 — Team/Avatar description resolution

In `PhaseLifecycleService.getSchedule()`:
- Load matches for phase
- Load TeamAvatar for each memberAvatar1Id, memberAvatar2Id
- Load Team for refereeTeamId (if not null); use refereeDescription as fallback
- Build descriptions: `"Group {groupNumber} Pos {groupPosition}"` or similar (consistent with existing patterns)

### Step 9 — Tournament status transition (PLANNED → ACTIVE)

In `PhaseLifecycleService.start()`:
- After calling `PhasePreparationService.startPhase(phaseId)`:
  - Load tournament via phase.tournamentId
  - If status == "PLANNED", set status = "ACTIVE", save tournament
  - DEC-5 active_sentinel constraint fires on schema — if another ACTIVE tournament exists → constraint violation → 409

### Step 10 — Tournament COMPLETED transition (AC11)

In `PhaseLifecycleService` (or via event listener on `MatchResultChangedEvent`):
- When the last phase completes (Phase → COMPLETED), check if all phases in the tournament are COMPLETED
- If all COMPLETED: set tournament.status = "COMPLETED", save
- Implementation: add a `checkTournamentCompletion(UUID tournamentId)` helper called from the event listener
  registered in `DomainEventBridge` (already handles WebSocket events — add tournament completion logic there)

## Risk Register

| Risk | Mitigation |
|------|------------|
| PhasePreparationService already in E03S12 — PhaseLifecycleService wraps it cleanly | Delegate, don't duplicate |
| DEC-5 active_sentinel fires at DB level with unclear error message | Catch DataIntegrityViolationException in GlobalExceptionHandler → 409 |
| Tournament COMPLETED transition — race between last match and WebSocket event | Cascade service already fires event; DomainEventBridge handles post-ACTIVE logic |
| WebSocket lap tracking: re-subscribe on phase change | Use Svelte reactive subscriptions; re-sub on phaseId change |
| Forced advance lap: audit table append-only pattern must match existing AuditLogRepository style | PhaseAuditLogRepository overrides deleteById to throw |

## Rollback Boundary

- V9 migration is additive (new table only) — safe to roll back
- No existing data modified
