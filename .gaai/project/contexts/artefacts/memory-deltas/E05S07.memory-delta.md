# Memory Delta — E05S07

## New Patterns

### phase_audit_log table (separate from audit_log)

The project has two audit log tables:
- `audit_log` — match-level events (set result changes); `match_id UUID NOT NULL`
- `phase_audit_log` — phase governance events (force-advance-lap); no `match_id`

When adding phase-level governance events, a separate table was required because `audit_log.match_id` is NOT NULL and cannot store phase-level events without relaxing the constraint (which would break the existing append-only semantics). Both tables follow the append-only pattern (`deleteById` throws `UnsupportedOperationException`).

### Tournament lifecycle (complete state machine)

```
DRAFT → PLANNED (E05S06 applyDraft)
PLANNED → ACTIVE (E05S07 startPhase — first phase start)
ACTIVE → COMPLETED (E05S07 checkTournamentCompletion — all phases COMPLETED)
```

`checkTournamentCompletion()` is called from two paths:
1. `advanceLap()` — synchronous, same `@Transactional` context
2. `DomainEventBridge.onMatchResultChanged()` — `@TransactionalEventListener(AFTER_COMMIT)`, new transaction

### PhasePreparationResult pattern

Three-step pipeline result with skip propagation:
- If step N fails, steps N+1..3 are marked `success=false, message="skipped (previous step failed)"`
- Factory methods: `generateMatchesFailed`, `optimizeSlotsFailed`, `assignRefereesFailed`, `success`
- This pattern is reusable for other multi-step preparation workflows
