# Story: Fix — the scoring tablet surfaces a match from a non-active phase after a set result is submitted

## User Story

**As a** referee using the scoring tablet on a field,
**I want** the tablet to only ever show a match that belongs to the tournament's currently
active phase,
**so that** after I submit a set result I see the correct next match — or "no active match" —
with real team names, and never a not-yet-active match from a later phase.

---

## Context

Bug reported 2026-05-16 on a running tournament. On the field-2 scoring tablet
(`/score/field/2`), before submitting a set result the page correctly showed
"Mannschaft 03 vs. Mannschaft 06" with referee "Mannschaft 05". After the set result was
submitted, the page reloaded and showed two raw UUIDs in place of the team names, no referee,
and "Runde 1 — Satz 1" — an active match that, for a single-set match format, should not be
there.

This is a standalone bug-triage story (Brief D-8). It is filed under Epic E22 (the epic that
reconstructed the score-entry service) and is independent of the Epic E61 scoring-tablet
optimization; per Brief D-9 it lands before E61S02 (which modifies the same method).

---

## Root Cause Analysis

Discovery investigation (Brief O-1/O-2/O-3), narrowed but not implemented:

- `DefaultScoreEntryService.resolveActiveMatch()` resolves the match for a field via
  `MatchRepository.findByFieldNumberAndLapNumber(fieldNumber, lapNumber)`. That query — verified
  by code inspection — filters on field number and lap number only; it is **not scoped to the
  active phase**.
- Lap and field numbers restart per phase (DEC-56 / DEC-60 — L2 emits 1-based lap and field
  numbers per phase), so each `(fieldNumber, lapNumber)` coordinate exists once in **every**
  phase of the tournament.
- When the active-phase match on a field reaches a terminal state, the same query still returns
  a match at that coordinate from a **later, not-yet-active phase**; `resolveActiveMatch` picks
  the first non-terminal match it finds and surfaces that later-phase match.
- That later-phase match's `TeamAvatar`s carry `teamId = NULL` (DEC-59 — avatars are
  team-assigned only after the prior phase completes, via the operator-confirmation workflow),
  so `resolveTeamName()` falls through to returning the raw avatar UUID. The referee row also
  disappears because the later-phase match has no referee assigned — confirming the displayed
  match is a *different* match, not the just-submitted one re-served.

The null `teamId` of a not-yet-active-phase avatar is correct behaviour (DEC-59); the defect is
that the tablet surfaces a non-active-phase match at all.

## Acceptance Criteria

- [ ] AC1 (reproduction): Given a tournament with at least two phases, where phase 1 is ACTIVE
  and a later, not-yet-active phase has a match sharing the same field number and lap number as
  a phase-1 match; when the phase-1 match on that field reaches a terminal state; then the
  scoring tablet for that field does not display the later-phase match.
- [ ] AC2 (expected behaviour): the match resolved for a field by the scoring-tablet match API
  always belongs to the tournament's currently active phase; a match from a non-active phase is
  never surfaced, even when it shares the same `(fieldNumber, lapNumber)` coordinate.
- [ ] AC3 (error-handling): when the active-phase match on a field is terminal and no further
  non-terminal active-phase match exists for that field, the scoring tablet shows the existing
  "no active match" state — not a match from another phase.
- [ ] AC4 (error-handling): the active-phase match the scoring tablet displays shows real team
  names (team descriptions); a raw avatar UUID is never displayed in place of a team name for a
  correctly resolved active-phase match.
- [ ] AC5 (testing): the fix is covered by a regression test — authored failing-first per
  DEC-22 — that reproduces the AC1 scenario (a later-phase match at the same
  `(fieldNumber, lapNumber)` coordinate) and asserts that match resolution returns only the
  active-phase match.
- [ ] AC6 (governance — tenancy): match resolution remains scoped to the device-token-resolved
  tenant context (DEC-20).
- [ ] AC7 (governance): the existing test suite passes — `mvn verify` from the `vvwt-prj` root
  is BUILD SUCCESS (DEC-54, DEC-71).

> All acceptance criteria must be verifiable.

## Notes

Standalone bug-triage story (Brief D-8), filed under Epic E22. Per the Discovery Bug Triage
flow, Discovery has investigated and narrowed the root cause (see Root Cause Analysis) but does
not prescribe the fix — the acceptance criteria define expected behaviour (phase-scoped match
resolution); Delivery determines the implementation. Brief hypothesis H-1: the defect is
expected to reproduce only with a tournament of two or more phases — a single-phase tournament
has no other-phase match to surface; this was not inspected in-session (the live H2 tenant
database is held open by the running application) and is confirmed by the AC5 RED-first
reproduction. `resolveActiveMatch` reads `Phase.currentLapNumber`; DEC-65 governs that field's
semantics — the fix must preserve DEC-65-correct consumption. `mvn verify` is the build gate
per DEC-54 / DEC-71.
