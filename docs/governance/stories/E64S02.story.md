# Story: Info-Portal admin surface fully in German with configuration guidance

## User Story

**As a** tournament organizer,
**I want** the Info-Portal button and opt-in page to be entirely in German, and the page
to tell me how to set the Info-Portal up when it is not configured,
**so that** I can use and configure the feature without seeing raw keys or hitting a
dead-end.

---

## Context

The "Info-Portal" button on the tournaments page and the header of the Info-Portal opt-in
page (`InfoPortalOptIn.svelte`) display raw i18n keys — `tournaments.infoPortalButton`
and `infoPortal.title` — because those keys are absent from the `de.json` catalogue. With
`svelte-i18n`, a bare `$_(key)` lookup returns the key string itself when the key is
missing, so the raw key is what the operator sees. The rest of the opt-in page body
("Info-Portal nicht konfiguriert", "Bereits veröffentlicht", "Erneut versuchen", loading
and error text, button labels) is hardcoded German rather than i18n-externalized — it
displays correctly but is inconsistent with the app-wide catalogue convention.

The `infoPortal` and `tournaments` namespaces **already exist** as populated blocks in
`de.json`; the missing keys must be added **nested into** those existing blocks.

When the global Info-Portal connection is not configured, the backend reports status
`DISABLED` and the page shows "Info-Portal nicht konfiguriert" — correct behaviour, but a
dead-end: it gives the operator no idea how to configure the feature. The global
connection is set only in `application.yml` under the `info-portal:` block; there is no
admin UI for it, and per DEC-42 D6 none is intended (the connection is static
configuration). This story adds an actionable guidance hint to that state — not a config
UI.

---

## Acceptance Criteria

- [ ] AC1 (testing): TDD per DEC-22 — failing test(s) are authored before the production
  change. i18n-key presence and resolution are verified directly against the `de.json`
  catalogue and the rendering logic; mounting the Svelte component is **not** required
  (Svelte 5 component mounting is infeasible in the project's Vitest+jsdom environment —
  pre-existing gap, E58S05).
- [ ] AC2: the "Info-Portal" button on the tournaments page displays a German label
  resolved from a `tournaments.infoPortalButton` key, and the Info-Portal opt-in page
  header displays a German label resolved from an `infoPortal.title` key. Both keys are
  added **nested into the existing** `tournaments` and `infoPortal` namespaces in
  `de.json` — no duplicate top-level namespace block is created.
- [ ] AC3: every operator-facing German display string on the Info-Portal opt-in page
  (`InfoPortalOptIn.svelte`) — page title, status messages, loading and error text, and
  button labels — is rendered via i18n keys from the `de.json` catalogue. After this
  story the component contains no hardcoded German display string. The set of strings to
  externalize is the set found in the component at delivery time — the rule is "externalize
  all of them", not a fixed list.
- [ ] AC4: when the Info-Portal is not configured (backend status `DISABLED`), the opt-in
  page shows an actionable German guidance hint that names the `application.yml`
  `info-portal:` configuration block and the properties an operator must set — the
  `url`, `tenant-id`, and `location-id` keys nested under that `info-portal:` block. The
  hint must not state or imply that the connection can be configured from the UI (DEC-42
  D6 — the connection is static configuration; no admin config UI exists or is added).
- [ ] AC5 (governance): no rendered string on the button or the opt-in page falls back to
  a visible raw i18n key — every key resolves to real German text. Where a lookup needs a
  fallback it uses the canonical `$_(key, { default: … })` form; a bare `$_(key)` followed
  by a dead `?? 'literal'` (the current anti-pattern that produces the raw-key symptom on
  the button and the page title) is replaced, not retained. i18n lookups otherwise follow
  the project's existing `svelte-i18n` usage; the frontend stays Vite + Svelte +
  TypeScript, no SvelteKit (DEC-2).
- [ ] AC6 (governance): keys are added to the `de.json` catalogue only — `en.json` is out
  of scope (the app is German-first, `fallbackLocale='de'`). No pre-existing `de.json`
  entry used by another screen is changed. `mvn verify` is BUILD SUCCESS for `vvwt-tm-web`,
  including the frontend build via `frontend-maven-plugin` (DEC-54).

> All acceptance criteria must be verifiable.

## Out of Scope

- A runtime admin UI to set the global Info-Portal connection — it remains
  `application.yml` / environment-variable configuration (DEC-42 D6). This story adds a
  guidance hint only.
- Any change to the Info-Portal opt-in backend, its REST endpoints, or its status logic —
  the `DISABLED` / `NOT_REGISTERED` / `REGISTERED` / `ERROR` states are unchanged; only
  their German presentation changes.
- The `en.json` catalogue (German-first app, `fallbackLocale='de'`).
- Fixing the project's infeasible Svelte-5 / Vitest+jsdom component-mount test environment
  (pre-existing gap, E58S05).

---

## Dependencies

- None — the Info-Portal opt-in page, the button, and the `de.json` `infoPortal` /
  `tournaments` namespaces all already exist (Epics E38 and E62, `done`). Independently
  deliverable.
- DEC-42 — the governing decision: the Info-Portal global connection is static
  configuration; no per-instance config UI in the TM admin.

## Notes

The button label and the page title currently appear as raw keys because they are looked
up with a bare `$_(key)` form, which returns the key on a miss. The opt-in page body
strings appear correct only because they are hardcoded German literals. Both classes are
brought onto the catalogue. Delivery decides the testable seam; the ACs state the
behaviour, not a component-mount test, because mounting is infeasible in the project's
test environment (E58S05). The guidance-hint property names (`info-portal.url`,
`info-portal.tenant-id`, `info-portal.location-id`) match the commented-out `info-portal:`
block in `vvwt-tm-web/src/main/resources/application.yml`.
