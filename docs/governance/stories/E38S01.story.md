# Story E38S01: Bootstrap `vvwt-info-{dto,server,client}` modules under `vvwt-prj` parent + Maven Enforcer `bannedDependencies` rules + `vvwt-tm-web → vvwt-info-dto` dependency + self-host-default profile assertion

## User Story

**As a** Tournament Manager program maintainer,
**I want** the three `vvwt-info-*` Maven modules to exist as buildable submodules under the `vvwt-prj` parent POM, with build-time enforcement of the cross-subsystem dependency rules from DEC-42 D2 and the no-config-default-is-self-host profile guarantee from DEC-42 D3,
**so that** all subsequent E38 stories have a green-build foundation, and the security-by-default property of the deployment model is structurally verified at story closure.

---

## Context

DEC-42 establishes the Public Participant Info Service as the third subsystem within `vvwt-prj`, following the DEC-11 precedent (slot-opt as submodules; service boundary at artefact level, not repo level). DEC-42 D1 authorizes three Maven modules: `vvwt-info-dto` (pure Java contract), `vvwt-info-server` (Spring Boot 4 application), `vvwt-info-client` (Svelte+TS frontend). DEC-42 D2 establishes the only cross-subsystem dependency edge: `vvwt-tm-web` MAY depend on `vvwt-info-dto`. DEC-42 D3 mandates that out-of-box (no `spring.profiles.active`) = self-host profile (the drive-by-squatting mitigation).

This story bootstraps the module skeletons and wires (a) the DEC-42 D2 boundary as a build-time gate via Maven Enforcer `bannedDependencies` rules and (b) the DEC-42 D3 self-host-default property as a startup-time guarantee. No business logic. Subsequent stories (E38S02+) extend these skeletons.

## Acceptance Criteria

- [ ] **AC1 (testing)**: Each module contains a RED-first existence test that fails on a fresh checkout before module-skeleton code exists, then passes once the skeleton is in place. RED-state commit hash for each new production class cited in `impl-report.md` per DEC-22 Iron Law.
- [ ] **AC2 (testing)**: `mvn -pl vvwt-info-dto,vvwt-info-server,vvwt-info-client clean verify` from `vvwt-prj` root completes GREEN. Maven reactor builds `vvwt-info-dto` before `vvwt-info-server` (Java dep graph); `vvwt-info-client` participates in the reactor via `frontend-maven-plugin` (or equivalent OSS-compliant plugin per DEC-3) — npm install + npm run build are wired into the Maven `generate-resources` phase.
- [ ] **AC3 (testing)**: `mvn help:effective-pom -pl vvwt-info-dto,vvwt-info-server,vvwt-info-client` (output captured in `impl-report.md`) demonstrates inheritance of DEC-22 (TDD) + DEC-29 (compiler hygiene `failOnWarning=true`) + DEC-30 (Spotless + google-java-format AOSP) configuration blocks from the parent POM. No per-module override of these inherited blocks.
- [ ] **AC4 (governance)**: `vvwt-tm-web/pom.xml` adds a single new `<dependency>` on `vvwt-info-dto` (the DEC-42 D2-allowed cross-subsystem edge per Brief D-19). Verified by `mvn dependency:tree -pl vvwt-tm-web | grep vvwt-info` showing exactly that one dep.
- [ ] **AC5 (governance)**: Skill attestation — `impl-report.md` declares `skills_invoked` (the Delivery skills used) and `related_decs` matches this story's frontmatter. Governance propagation per DEC-23 + DEC-31: story file + `impl-report.md` + `qa-report.md` + memory-delta propagated into `vvwt-prj/docs/governance/` at story closure (single-commit per DEC-23; not §(c) two-commit, as this is forward-build per Epic Success Metrics).
- [ ] **AC6 (security)**: Maven Enforcer Plugin `bannedDependencies` rule wired in `vvwt-info-server/pom.xml` and `vvwt-info-client/pom.xml` (or via parent-POM-inherited reusable rule scoped to `vvwt-info-*` modules) banning compile-scope and runtime-scope dependencies on `vvwt-tm-*`, `vvwt-worker-*`, `vvwt-dispatcher`, `vvwt-slotopt-dispatcher`, `vvwt-standalone-worker`, `vvwt-benchmark`, and any `vvwt-slotopt-*` artifactId pattern. Rule violation MUST fail `mvn verify` with a clear Enforcer error.
- [ ] **AC7 (security)**: Symmetric Enforcer rule wired in `vvwt-tm-web/pom.xml` banning compile-scope/runtime-scope dependencies on `vvwt-info-server` and `vvwt-info-client` — only `vvwt-info-dto` is the DEC-42 D2 allowed cross-subsystem edge.
- [ ] **AC8 (security)**: **Default-profile-is-self-host startup assertion.** `vvwt-info-server` Spring Boot 4 application, started via `mvn spring-boot:run -pl vvwt-info-server` with NO `spring.profiles.active` setting (and no `SPRING_PROFILES_ACTIVE` env var), logs an INFO line at startup containing the phrase `active profile = self-host` (or the Spring profile resolution stamp confirming `self-host` is the only active profile). Verified by an integration test that captures the log output. When started with `spring.profiles.active=primary`, the same test verifies the log shows `primary` instead. This AC is the DEC-42 D3 drive-by-squatting-mitigation guarantee structurally enforced.
- [ ] **AC9 (security)**: **Durable Maven Enforcer negative-test IT** at `vvwt-info-server/src/test/java/de/vvwt/info/build/BannedDependenciesEnforcerIT.java` that programmatically invokes the Maven Enforcer plugin against a fixture pom (constructed in test-setup; fixture has a forbidden dep on `vvwt-tm-web`) and asserts: (a) Enforcer exit code = non-zero, (b) error message substring contains `bannedDependencies`. Test is PERMANENT (not removed before commit); it provides durable evidence the Enforcer rule fires for QA review and future regression.
- [ ] **AC10 (error-handling)**: `vvwt-info-server` Spring Boot 4 `@SpringBootApplication` class is the minimal bootable entry point. Both profiles boot cleanly: no-config (self-host) startup completes without errors; `spring.profiles.active=primary` startup also completes without errors. No DB tables, no endpoints — just bootable. Application starter set declared explicitly in pom: `spring-boot-starter-web`, `spring-boot-starter-data-jdbc`, `spring-boot-starter-validation`, `flyway-core`. PostgreSQL JDBC driver added as `runtime`-scope `<optional>true</optional>` dep activated by primary profile; H2 driver is the default-profile runtime dep.
- [ ] **AC11 (error-handling)**: `vvwt-info-client/package.json` + `vite.config.ts` exists with Svelte 5 + TypeScript 5 scaffold per DEC-2; `npm install && npm run build` produces a working static-asset bundle to `dist/`. SvelteKit explicitly absent — verified by `npm ls @sveltejs/kit` returning empty. Bundle relocation into `vvwt-info-server/src/main/resources/static/` is **out of this story's scope** (E38S08 owns that wiring; this story only verifies the bundle builds in isolation).

## Notes

- The Enforcer `bannedDependencies` rule pattern is the security-by-isolation control. Without it, a future Delivery agent could accidentally `import de.vvwt.tm.tournament.*` from `vvwt-info-server` and the build would still pass, breaking DEC-42 D2 silently. The rule converts the convention into a build-checked invariant.
- AC8's startup assertion is the drive-by-squatting-mitigation structural test for DEC-42 D3 — the no-config-default-is-self-host property cannot regress without the test failing.
- AC9's negative-test IT is permanent (not transient demo), providing durable Enforcer-fires evidence for QA review.
- `frontend-maven-plugin` (com.github.eirslett, Apache 2.0) is the recommended OSS choice for npm-into-Maven-lifecycle wiring; specific version pin is implementation choice within DEC-3 compliance.
- AC3's `mvn help:effective-pom` excerpt in `impl-report.md` provides verifiable evidence of parent-POM inheritance — replaces the previous tautological "auto-inherits" assertion.
