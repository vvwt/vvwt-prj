# Story: A scoring tablet advances to its field's next-round match automatically when the tournament advances

## User Story

**As a** referee whose match has finished,
**I want** the scoring tablet to move on to my field's next match when the tournament
advances to the next round,
**so that** I can keep scoring without having to reload the page.

---

## Context

After a set is submitted, the scoring-tablet field page looks up its field's match once. If
the field's current-round match is finished but the tournament has not yet advanced —
because other fields are still playing — the tablet shows "no active game on this field"
and never looks again.

Per the Discovery session of 2026-05-17 (Brief O-4), the field page has no polling and no
live subscription: a single match lookup runs on page load and once more shortly after a
submit. A field that finishes its round early therefore lands on a dead "no active game"
screen and stays there — even after the tournament advances and a new match for that field
exists — until the referee manually reloads. Rounds advance phase-global (all fields
together — Brief T-4); a field is correctly idle until the round advances, but it must then
follow.

---

## Acceptance Criteria

- [ ] AC1 (reproduction): Given a scoring tablet whose field has finished its current-round
  match while other fields are still playing, when the tournament later advances to the
  next round, then the tablet currently keeps showing "no active game on this field" and
  does not show the field's next-round match until a manual reload — this is the defect.
- [ ] AC2 (expected — auto-advance): After the fix, when the tournament advances to the
  next round, the scoring tablet shows its field's match for the new round automatically
  and promptly (within a few seconds), without a manual reload.
- [ ] AC3 (waiting state): While a field has finished its current-round match and the
  tournament has not yet advanced, the tablet shows an appropriate waiting/idle state for
  that field; it leaves that state automatically once the field's next-round match becomes
  available.
- [ ] AC4 (no regression): When a field has an active match the tablet shows it as before;
  submitting a set still works; the round model — phase-global advancement,
  `Phase.currentLapNumber` per DEC-65 — is unchanged.
- [ ] AC5 (error-handling / no-regression): A transient connectivity failure does not leave
  the tablet permanently stranded — once connectivity returns, the round-tracking mechanism
  this story introduces next runs and the tablet shows the correct current match for its
  field, with no manual reload. This story does not add an offline retry queue — that
  remains out of scope.
- [ ] AC6 (governance — DEC-19): The field page remains Mustache + inline vanilla ES5
  JavaScript only — no Svelte or other framework, no ES2015+ syntax, no bundler.
- [ ] AC7 (testing): First-party ES5 logic changed by the fix is authored test-first per
  DEC-22 to the extent the project's existing automated test surface for this Mustache +
  ES5 page supports it — that surface is rendered-HTML / template-structure inspection in
  the existing `ScoreFieldLayoutIT` / `ScoreFieldSwapIT` pattern, not runtime-JavaScript
  execution. The runtime behaviour — the tablet leaving the no-match/waiting state and
  showing the field's next-round match when the round advances — is, where not reachable by
  that automated surface, verified by the implementer and explicitly recorded in the
  impl-report, which states exactly what is automated and what is attested. Delivery may
  extend the test surface but is not required to.
- [ ] AC8 (governance — build gate): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS
  (DEC-54, DEC-71).

> All acceptance criteria must be verifiable.

## Notes

Per Brief O-4, the tablet resolves its match against the phase's current round with a
one-shot lookup and no live mechanism. AC2 states the observable WHAT — the tablet must
reflect the current round without a manual reload — and the mechanism (a poll, a live
subscription, or another approach within the DEC-19 Mustache + ES5 constraint) is
Delivery's. Per memory `feedback_ac_behavioural_what_not_test_how`, AC7 points at the
project's existing test surface for this Mustache + ES5 page rather than prescribing an
unsupported test mechanism. `mvn verify` is the build gate per DEC-54 / DEC-71.
