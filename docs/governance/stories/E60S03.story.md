# Story: Job finalization, cross-packet aggregation, and cache write at finalization

## User Story

**As an** operator of the slot-optimization service,
**I want** the dispatcher to detect when all of a job's packets are solved, compute the job's
global optimum, and complete the job,
**so that** a submitted job produces a correct, final, globally-optimal result — not a stale
`RECEIVED`/`DECOMPOSED` job and not one packet's partial sub-range answer.

---

## Context

The dispatcher never finalizes a job. `DefaultSubmitResultService` marks a packet
`RESULT_RECEIVED` but never touches the `JobRecord`, never detects "last packet of the job",
and never aggregates. `JobRecord.status` is written only once — to `RECEIVED` at intake — so
every job is perpetually `RECEIVED`. And the result cache is written **per packet**: for a
multi-packet job, every packet shares the job's structural fingerprint key, the cache is
INSERT-only, so the first packet to submit wins the slot and holds only *its* sub-range
optimum — a wrong global result, which also poisons the cache-hit short-circuit for any
later structurally-identical job.

`E37.slotopt-contract.md` §"Job Finalization" specifies the missing behaviour: when the last
packet of a job transitions to its terminal result state, the dispatcher computes the global
best across the job's packet results — lowest `bestScore` wins, ties broken by lowest
`bestRank`, deterministically.

This story implements that. When a job's last packet reaches `RESULT_RECEIVED`, finalization
reads the per-packet retention store (E60S02), computes the global optimum, transitions the
`JobRecord` `DECOMPOSED → COMPLETED`, and writes that **aggregated** optimum to the result
cache **once**. The per-packet cache write in `DefaultSubmitResultService` is removed — the
cache is written only at finalization, so it holds the correct global optimum.

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-LAST-PACKET-FINALIZES** — RED-first (DEC-22): when the last packet of a job
  reaches `RESULT_RECEIVED`, the job is finalized and its `JobRecord.status` transitions
  `DECOMPOSED → COMPLETED`.
- [ ] **AC-TEST-NOT-FINALIZED-BEFORE-LAST** — a job that still has any packet not in a
  terminal result state is **not** finalized: its status stays `DECOMPOSED` and no job
  optimum is written.
- [ ] **AC-TEST-AGGREGATION-GLOBAL-OPTIMUM** — finalization computes the job optimum as the
  packet result with the lowest `bestScore`; on a `bestScore` tie, the lowest `bestRank`
  wins. The test uses a multi-packet job in which the global optimum is **not** the
  first-submitted packet's result, proving cross-packet aggregation.
- [ ] **AC-TEST-AGGREGATION-DETERMINISTIC** — given the same set of packet results,
  finalization always yields the same `(bestRank, bestScore)`. The aggregation comparator is
  the total order `(bestScore, bestRank)` ascending — lowest `bestScore`, ties broken by
  lowest `bestRank`; because distinct packets cover distinct permutation-rank intervals an
  identical `bestRank` across two packets is not expected, and even that degenerate case
  resolves deterministically under the total order. Verified by submitting the same results
  in different orders and asserting an identical job optimum (`E37.slotopt-contract.md`
  §Job-Finalization determinism requirement).
- [ ] **AC-TEST-CACHE-HOLDS-AGGREGATED-OPTIMUM** — after finalization the result cache holds
  the **aggregated** job optimum (keyed by the job's structural fingerprint + game-mode);
  for a multi-packet job this is the global optimum, not any single packet's sub-range
  result.
- [ ] **AC-TEST-NO-PER-PACKET-CACHE-WRITE** — `submit-result` no longer writes to the result
  cache per packet; the per-packet `recordAcceptedResult` invocation is removed from
  `DefaultSubmitResultService`; the cache is written exactly once per job, at finalization.
- [ ] **AC-TEST-SUITE-GREEN** — `mvn verify` is BUILD SUCCESS for `vvwt-slotopt-dispatcher`
  (DEC-54); the existing E37/E40 suite remains GREEN.

### Governance

  code's conventions — the `RECEIVED`/`DECOMPOSED`/`COMPLETED` enum, the

### Error Handling

- [ ] **AC-ERR-FINALIZATION-DOES-NOT-BLOCK-RESULT-ACCEPT** — a failure in the finalization,
  aggregation, or cache-write path does **not** reject or roll back the valid worker result
  that triggered it: the packet's result acceptance, retention (E60S02), and `RESULT_RECEIVED`
  transition stand. A finalization failure is logged and degrades gracefully — the job is
  finalizable on a subsequent idempotent trigger — consistent with the existing
  audit-failure-absorption pattern (Session Brief Q-3).
- [ ] **AC-ERR-FINALIZATION-IDEMPOTENT** — finalization is idempotent: an already-`COMPLETED`
  job is not re-finalized, re-aggregated, or re-cached if a finalization trigger fires again
  for it.
- [ ] **AC-ERR-CACHE-WRITE-FAILURE-ABSORBED** — a result-cache write failure at finalization
  is absorbed (logged, not rethrown); the job still reaches `COMPLETED`. (The job optimum
  remains available via the job-status endpoint — E60S04 — even if the cache write failed.)
- [ ] **AC-ERR-LAST-PACKET-DEFINITION** — "last packet" is defined as: every packet of the
  job has reached the terminal `RESULT_RECEIVED` state. A packet that is `UNCLAIMED`
  (including a timed-out packet that the `PacketTimeoutSweeper` has reset to `UNCLAIMED` for
  reissue) or `CLAIMED` (claimed by a worker, result not yet submitted) is non-terminal and
  must not trigger premature finalization of a job whose work is not actually complete. (The
  `PacketRecord` status enum documents a `TIMEDOUT` value, but the delivered
  `PacketTimeoutSweeper` resets a timed-out packet directly to `UNCLAIMED` — `TIMEDOUT` is
  never written by production code; finalization keys off `RESULT_RECEIVED` vs. not.)

## Notes

A genuine open question for Delivery's confirm-audit (E60S01 AC-GOV-CONFIRM-AUDIT) and RED
tests: today the per-packet cache write is an INSERT-only call inside the `@Transactional`
`DefaultSubmitResultService.submit()`; for a multi-packet job the second packet's INSERT
collides on the job-fingerprint key and the duplicate-key exception is caught. Depending on
Spring/H2 transaction semantics this absorbed exception may already roll back that call's
`RESULT_RECEIVED` transition — i.e. the current multi-packet failure mode may be a *stuck
pipeline*, not merely a lossy cache. Either way, relocating the cache write to finalization
(this story) removes the per-packet duplicate-key write entirely and resolves it; Delivery's
RED tests should pin down the exact pre-change behaviour. Related Session Brief items: D-4,
D-5, O-4, O-6, H-1, T-3, S-3, S-4, Q-1, Q-2, Q-3.
