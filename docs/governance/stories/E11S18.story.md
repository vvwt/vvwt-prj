# Story E11S18: Fix — Timer END sound never plays for the final round of the tournament because the audio-fire gate suppresses the last ROUND's deactivate event when the schedule has no successor entry

## User Story

**As a** tournament organizer using the Timer SPA to signal round boundaries across the venue with audio,
**I want** the round-end sound to play when the FINAL round of the entire tournament ends, exactly as it plays at the end of every other round,
**so that** players and staff hear the same audible end-signal for the last round and are not left waiting for a cue that never comes — operator reported that every round's end-audio played correctly except the end-audio of the very last round of the whole tournament, which was silent.

---

## Context

Operator reported (2026-06-06): on the Timer/Audio page, all audio files played correctly except one — the END sound (Ende-Audio) for the **last round of the entire tournament** was never played. Every other round's end-sound fired normally; only the final round's end-sound was silent.

**This is a known, previously-deferred defect — not a new discovery.** E11S13's cycle-1 independent review flagged exactly this as a CRITICAL ("AC4 — tournament-end END_SOUND — structurally impossible because `countdownEngine.resolveActiveEvent` keeps `playingIndex` on the last entry while `activeEventIndex` becomes `-1`, so the `App.svelte` audio-fire gate is blocked"). E11S13 cycle-2 resolved this by **removing AC4 and deferring it** via explicit Out-of-Scope: "last-ROUND END_SOUND requires engine-level change — future Story." E11S15 and E11S17 both repeat "Last-ROUND END_SOUND at tournament end (E11S13 carryover)" in their Out-of-Scope. **This Story is that promised future Story.**

**Root cause (verified against HEAD):**

The Timer SPA fires schedule-event audio in `App.svelte` `onTick` (`vvwt-tm-web/src/main/ui-timer/src/App.svelte`). The fire is gated at line 475:

```ts
if (activeEventIndex !== lastFiredActiveIndex && activeEventIndex !== -1) {
  // deactivate previous playing entry → END_SOUND / PAUSE_MUSIC_STOP
  // activate just-started entry → START_SOUND / PAUSE_MUSIC_START
}
```

Each round's END sound is fired as the **deactivate** of the previous playing entry — i.e., the round-end sound for round K fires at the moment round K+1 (or the break after K) becomes active. This works for every round that has a successor entry.

The snapshot comes from `countdownEngine.resolveActiveEvent` (`vvwt-tm-web/src/main/ui-timer/src/lib/countdownEngine.ts`):

```ts
if (nextIndex === -1) {
  // All events are in the past — no future entry
  return { activeEventIndex: -1, secondsRemaining: 0, playingIndex };
}
```

When the schedule has no future entry (i.e., the last ROUND is playing or has just elapsed), `activeEventIndex` becomes `-1` while `playingIndex` still points at the last ROUND. The `&& activeEventIndex !== -1` guard on line 475 is then `false`, so the deactivate block never runs — **the last ROUND's END_SOUND is never fired**. There is no successor entry to trigger it, and the engine produces no event to drive it.

Each schedule entry already carries its own `endTime` on the wire (backend `DefaultTimerDataService` formats `entry.endTime()`; frontend `resolveEffectiveEndTime` parses it). So the last round's end instant is determinable client-side — **no backend change is implied**.

Why only the END fails and the last round's START + countdown still work (operator-confirmed): the last round's START is driven by the transition into it (the preceding entry's activate / the lap advance), and the countdown is driven independently. Only the **deactivate** (END) of the last entry is orphaned, because deactivate is wired to fire when the *next* entry activates and there is no next entry.

The tournament's closing `awardCeremony` phase has 0 matches and produces no ROUND entry (`mapTimelineToSchedule` skips `lapNumber == 0`). The target of this Story is the **last ROUND-type schedule entry across all phases**.

Discovery Session Brief `discovery-2026-06-06-timer-last-round-end-audio` (operator-validated 2026-06-06: scope = last-round END sound only; trigger = the last round's scheduled end, same basis as every other round; last-round START + countdown working and must not regress).

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach ("engine-level change") is Delivery's choice within the bounds set by the Brief.

### Last-round END audio correctness

- [ ] **AC1 — The final ROUND of the tournament plays its END sound when its scheduled round time elapses.** Given a tournament whose schedule ends with a ROUND entry that has no successor schedule entry, when the playing position reaches that last ROUND's scheduled end (its `endTime`), then the END sound (`audioEngine.play('END')`) fires exactly once — on the same trigger basis (scheduled round end) as every other round's END sound.
- [ ] **AC2 — Every non-final round's END sound continues to fire exactly once, unchanged.** The fix does not alter the existing behaviour where a round's END sound fires as the deactivate when its successor entry becomes active. No round's END sound is doubled, dropped, or shifted in time relative to the pre-fix behaviour for any round that has a successor entry.
- [ ] **AC3 — The last round's START sound and countdown are not regressed.** The last round's START sound still fires once when the round becomes active, and the countdown for the last round still displays and counts down correctly. (Operator confirmed these work today; the engine-level change for AC1 must preserve them.)
- [ ] **AC4 — Trailing non-ROUND entries do not produce an END sound, and the closing award-ceremony phase produces no spurious sound.** If the schedule's last meaningful entry is the last ROUND (no successor), only that ROUND's END fires. The `awardCeremony` / zero-lap closing phase (which produces no ROUND entry) does not cause any END / START / pause sound. A trailing break entry, if present, retains its existing audio semantics (REGULAR break → pause-music; ADDITIONAL break → none) per `getAudioEventOnActivate` / `getAudioEventOnDeactivate`.

### Error-handling (mandatory category)

- [ ] **AC5 — Idempotent / no double-fire at schedule completion.** Once the last ROUND's END sound has fired, subsequent `onTick` calls (the schedule remains in the "all events past" state, `activeEventIndex === -1`, `playingIndex` still on the last ROUND) do NOT re-fire the END sound. The END for the last round fires exactly once across the lifetime of the playing session, not once per tick after completion.
- [ ] **AC6 — Transport STOP / PAUSE / re-play interaction preserved.** If the operator presses STOP or PAUSE before or during the last round, the existing transport reset/early-return semantics are preserved (no END fired on STOP; on a subsequent re-play the init-suppress invariant still suppresses spurious audio on the first tick). The last-round END fire is subject to the same `transportState === 'PLAYING'` and `audioEngineJustStarted` guards as every other audio fire, so it cannot fire during a non-playing state or on the first tick after engine (re)start.
- [ ] **AC7 — WS-driven reload at tournament end does not double-fire or silence the last-round END.** If a WebSocket event (`LAP_ADVANCED` / `PHASE_CHANGED` / reconnect) triggers a silent reload at or near the last round, the E11S17 init-suppress invariant is preserved and the last-round END still fires exactly once when the last round's scheduled end is reached (and not a second time after a reload). No regression to E11S17.

## Notes

**Track:** `bug-triage`, priority **high** — a missing end-signal for the final round of a live tournament is a user-facing correctness defect on the venue's primary audible cue, and it is a long-standing known carryover.

**Root cause (verified, HEAD):**
- `App.svelte` `onTick` line 475 gate `activeEventIndex !== lastFiredActiveIndex && activeEventIndex !== -1` — the `&& activeEventIndex !== -1` term suppresses the deactivate (END_SOUND) block for the last ROUND.
- `countdownEngine.resolveActiveEvent` lines 200–202 — returns `activeEventIndex: -1` once `nextIndex === -1` (no future entry) while keeping `playingIndex` on the last ROUND.
- Each round's END is fired as the deactivate triggered by the *next* entry's activation; the last ROUND has no successor, so its END is never triggered.
- `resolveEffectiveEndTime` (countdownEngine.ts) + per-entry `endTime` already exist — the last round's end instant is available client-side.

**Why this needs an "engine-level change" (E11S13's deferral reason):** simply dropping the `&& activeEventIndex !== -1` guard is insufficient and risky — when `activeEventIndex` is `-1` there is no successor whose start time marks the round's end, so the fix must drive the last ROUND's END off the round's own end time (e.g., compare `currentNow` against the last playing ROUND's `resolveEffectiveEndTime`, fire END once when it elapses) and must fire it exactly once (AC5). Delivery chooses the precise mechanism (engine emits a terminal "schedule complete" signal carrying the just-ended `playingIndex`; or `onTick` detects `activeEventIndex === -1 && playingIndex` is a ROUND whose `endTime` has passed and fires END once via a one-shot guard) and attests it in the impl-report (AC11).

**Reproduction (operator-observed + analytic):** configure a tournament whose schedule ends with a ROUND (the normal case — the last competitive round before the award ceremony). Run the timer through to the end of the last round. Every prior round's END sound plays; the last round's END sound is silent. Expected after fix: the last round's END sound plays when its scheduled time elapses, identically to all prior rounds.
