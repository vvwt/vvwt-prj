# Story E37S05: identity package — KeyRegistration with algorithm discriminator + KeyRegistrationController + KeyRegistrationService + RegisterKeyRequest/Response + RoleConflictException (Q-1a TDD RED-first against spec)

## User Story

**As a** worker registering with the slot-optimization dispatcher (V1 with Ed25519; later with PQC-capable algorithms),
**I want** a KeyRegistry that accepts an algorithm discriminator alongside the public-key bytes (variable length per algorithm), a register-key HTTP endpoint that validates the algorithm against the dispatcher's SignatureVerifierRegistry, and a clear role-conflict response if I attempt to register an already-claimed worker_id with conflicting role,
**so that** V1 single-algorithm Ed25519 registration works as expected AND the schema + protocol shape are ready for future PQC algorithm additions without migration.

---

## Context

The identity package owns: KeyRegistration entity (with `algorithm` discriminator column + variable-length `public_key_bytes` VARBINARY(8192) per Brief C-19), KeyRegistrationController (HTTP `POST /api/register-key`), KeyRegistrationService (business logic + persistence), RegisterKeyRequest/Response DTOs, RoleConflictException, KeyRegistrationRepository (Spring Data JDBC).

This story is authored against E37S02 spec sections (a) auth flow per DEC-6, (b) dispatcher contract register-key endpoint, (d) algorithm-discriminator schema. No legacy inspection per Brief C-16.

Per Brief C-12: KeyRegistry stays single-row-per-worker (Option α from D-3 — locks out Option β at schema level).

Per Brief D-2 + D-6 + AC-D-6-DEC-AUTHORED (E37S04): the algorithm field on register-key is REQUIRED (not Optional). Backward-compat clause applies only to `supportedAlgorithms[]` on pull-packet, NOT to the algorithm field on register-key.

### Story-specific ACs

- [ ] **AC-KEY-REGISTRATION-ENTITY**: `de.vvwt.slotopt.dispatcher.identity.KeyRegistration` Spring Data JDBC POJO (NOT a record per DEC-35) with fields: `Long id`, `UUID workerId`, `String algorithm` (NOT NULL, VARCHAR 32), `byte[] publicKeyBytes` (variable, max 8192 per C-19), `String role` (NOT NULL — role values per E37S02 spec section (b); DEC-6 names "compute clients" and "Tournament Manager instances" as the two integration-point roles, which the spec section (b) operationalizes as concrete strings), `Instant registeredAt`. Schema migration (Flyway) creates `key_registration` table per DEC-26 (analogously applied to vvwt-slotopt-dispatcher; DEC-26 §Decision is textually scoped to vvwt-tm-web).
- [ ] **AC-KEY-REGISTRATION-REPOSITORY**: `de.vvwt.slotopt.dispatcher.identity.KeyRegistrationRepository extends CrudRepository<KeyRegistration, Long>` per DEC-35 Spring-Data carve-out. Custom finder: `Optional<KeyRegistration> findByWorkerId(UUID workerId)`.
- [ ] **AC-KEY-REGISTRATION-SERVICE**: `de.vvwt.slotopt.dispatcher.identity.KeyRegistrationService` interface + `de.vvwt.slotopt.dispatcher.identity.internal.DefaultKeyRegistrationService` impl per DEC-35. Method: `RegisterKeyResponse register(RegisterKeyRequest request)`. Behavior: (1) validate `algorithm` field against `SignatureVerifierRegistry.supportedAlgorithms()` — unknown algorithm → throw `IllegalArgumentException` mapped to HTTP 400; (2) validate publicKeyBytes length against verifier's declared key-length constraints (per E37S04 SignatureVerifier SPI contract — exact field/method shape authored at E37S04) — out-of-range → 400; (3) check workerId conflict — same workerId different role → throw `RoleConflictException` mapped to HTTP 409; same workerId same role same algorithm → idempotent (return existing); (4) persist new registration + return RegisterKeyResponse with workerId.
- [ ] **AC-REGISTER-KEY-CONTROLLER**: `de.vvwt.slotopt.dispatcher.identity.KeyRegistrationController` with `@PostMapping("/api/register-key")`. Accepts JSON `RegisterKeyRequest`. Returns JSON `RegisterKeyResponse` (HTTP 201 on new; 200 on idempotent re-register). Exception → `@ExceptionHandler` returning structured error JSON.
- [ ] **AC-REGISTER-KEY-REQUEST-RESPONSE**: `de.vvwt.slotopt.dispatcher.identity.RegisterKeyRequest` record `(UUID workerId, String role, String algorithm, byte[] publicKeyBytes)`. `RegisterKeyResponse` record `(UUID workerId, String role, String algorithm, Instant registeredAt)`. JSON serialization preserves these field names verbatim per E37S02 spec (b).
- [ ] **AC-ROLE-CONFLICT-EXCEPTION**: `de.vvwt.slotopt.dispatcher.identity.RoleConflictException extends RuntimeException` with `(UUID workerId, String existingRole, String requestedRole)` constructor. Authored RED-first.
- [ ] **AC-DEC26-COMPLIANT-DAO-IT**: `KeyRegistrationRepositoryIT` integration test follows DEC-26 three rules: (1) schema-from-migration via test-support utility; (2) independent persistence verifier (assertj-db direct JDBC reads, NOT the repository under test); (3) read/write decoupling. Tests cover: persist + retrieve roundtrip; findByWorkerId hit + miss; unique workerId constraint.
- [ ] **AC-MOCKMVC-CONTROLLER-TEST**: `KeyRegistrationControllerSliceTest` (`@WebMvcTest`) mocks the service interface (per DEC-36) and verifies HTTP layer: 201 on new, 200 on idempotent, 400 on unknown algorithm, 400 on out-of-range key length, 409 on RoleConflict. JSON request/response shapes match the spec verbatim.
- [ ] **AC-ALGORITHM-FIELD-REQUIRED**: Empty or missing `algorithm` field in request JSON → HTTP 400 with explicit error message. Per Brief: backward-compat clause (D-2) applies only to `supportedAlgorithms[]` on pull-packet, NOT to algorithm on register-key.

## Notes

- **C-12 lock**: schema is `key_registration(id, worker_id UNIQUE, algorithm, public_key_bytes, role, registered_at)` — single row per worker_id (no composite key with algorithm). Option β explicitly excluded.
- **C-19 sizing**: VARBINARY(8192) accommodates all known PQC algorithms' public keys.
- **DEC-26 enforcement**: `qa-review` skill verifies the three-rule pattern at PR-merge time.
- **Forward-use**: Future PQC algorithm addition requires only a new `SignatureVerifier` bean (no schema change here).
