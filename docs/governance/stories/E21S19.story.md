# Story E21S19: Fix — Restore `GET` + `PUT` mappings on `/api/tournaments/{id}/draft` lost during Modulith reconstruction; bundle the DEC-40 `DraftController` relocation (Q-1b whole-class) into self-contained scope after PR #90 (E22S08) was found stale on staging

## User Story

**As a** tournament organizer using the TM admin UI,
**I want** the Draft-configuration view at `/tournaments/{tournamentId}/draft` to load the saved draft on mount and to persist my edits when I press Save,
**so that** I can plan tournament phases without hitting `404 Not Found` on `GET /api/tournaments/{id}/draft` and without losing draft work between sessions.

---

## Context

On 2026-05-04 the user reported a `404 Not Found` for `GET /api/tournaments/{tournamentId}/draft` (concrete URL: `http://127.0.0.1:8080/api/tournaments/adcf956c-2879-4936-a149-a5126014d388/draft`). The Discovery Bug-Triage flow narrowed root cause to a **reconstruction-regression**:

- The frontend store `vvwt-tm-web/src/main/ui/src/stores/draftStore.ts` calls `GET /api/tournaments/${tournamentId}/draft` (line 87 — `getDraft`) and `PUT /api/tournaments/${tournamentId}/draft` (line 102 — `saveDraft`). These calls match the original E05S06 AC2/AC3 contract and the Svelte route `/tournaments/:tournamentId/draft` (`DraftConfig.svelte:57-78` calls `getDraft` once on mount and assigns `sections = config.sections.map(...)`).
- The current `DraftController` (on staging at `de.vvwt.tm.tournament.DraftController.java:65–122`) maps **only** `POST /preview` and `POST /apply` under `@RequestMapping("/api/tournaments/{tournamentId}/draft")`. There is no `@GetMapping("")` and no `@PutMapping("")` — Spring returns 404 for the GET/PUT calls.
- Verified via `git log --oneline staging -- vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/DraftController.java`: 4 commits — ec82a75 (E33S05), 9b4f8a7 (E33S04), 52730b6 (E21S13), 321fdac (E21S07). ## Reproduction Scenarios (Given / When / Then — RED-first per DEC-22)

### Scenario A — `GET` on tournament with persisted draft

**Given** a tournament `{tournamentId}` in `DRAFT` status with a non-empty `draft_json` value (i.e., a previous `PUT` has saved a draft with one or more sections),

**When** the client issues `GET /api/tournaments/{tournamentId}/draft` with a valid tenant context,

**Then** the response is `200 OK` with a `DraftResponse` body whose `sections` list contains the persisted sections (each with the `DraftSectionResponse` field set: `sectionNumber, sortType, groupCount, gameMode, lapBreakTimeMinutes, sectionBreakTimeMinutes, lapTimeMinutes, setQuantity, breaks`), bytewise round-trippable against the most recent `PUT` body.

**Current behavior (bug):** `404 Not Found` — no controller mapping exists.

### Scenario B — `GET` on tournament without a persisted draft

**Given** a tournament `{tournamentId}` in `DRAFT` status with an empty (`null` or absent) `draft_json` value,

**When** the client issues `GET /api/tournaments/{tournamentId}/draft`,

**Then** the response is `200 OK` with `DraftResponse` body `{ "sections": [] }`. Rationale: the frontend `DraftConfig.svelte:57-78` `onMount` assigns `sections = config.sections.map(...)` directly and would throw on a `404` body — empty-list-on-200 is the contract this Story chooses (consciously, not by restoration — see Notes below).

**Current behavior (bug):** `404 Not Found` — same root cause.

### Scenario C — `PUT` on `DRAFT`-status tournament

**Given** a tournament `{tournamentId}` in `DRAFT` status,

**When** the client issues `PUT /api/tournaments/{tournamentId}/draft` with a valid `DraftRequest` body (validated via `@Valid`),

**Then** the response is `200 OK` with a `DraftResponse` body echoing the persisted draft (same `sections` list, post-persistence read-shape). The `Tournament.draftJson` column is updated atomically.

**Current behavior (bug):** `404 Not Found`.

### Scenario D — `PUT` on non-`DRAFT`-status tournament

**Given** a tournament `{tournamentId}` whose status is `PLANNED`, `ACTIVE`, `COMPLETED`, or `CANCELLED`,

**When** the client issues `PUT /api/tournaments/{tournamentId}/draft` with any body,

**Then** the response is `409 Conflict` with a meaningful error message (e.g., *"Draft cannot be modified: tournament is in status {status}"*). The `Tournament.draftJson` column is **not** modified.

### Scenario E — `PUT` with malformed JSON

**Given** any tournament,

**When** the client issues `PUT /api/tournaments/{tournamentId}/draft` with a body that is not parseable as `DraftRequest`,

**Then** the response is `400 Bad Request` (reusing the existing `HttpMessageNotReadableException` handler pattern present in the current `DraftController.java:185-189`).

### Scenario F — Cross-tenant access

**Given** a tournament `{tournamentId}` belonging to tenant `A`, and an authenticated request bound to tenant context `B`,

**When** the client issues `GET` or `PUT` on `/api/tournaments/{tournamentId}/draft`,

**Then** the response is `404 Not Found` via the natural tenant-scoping mechanic — `TenantContext` binding at the repository layer (`DefaultTournamentRepository.java:20`) yields no row → `TournamentNotFoundException` (annotated `@ResponseStatus(HttpStatus.NOT_FOUND)` per `tournament/exceptions/TournamentNotFoundException.java:30`). No new auth code is added.

### Scenario G — `PUT` idempotency

**Given** a tournament `{tournamentId}` in `DRAFT` status,

**When** the client issues two consecutive `PUT /api/tournaments/{tournamentId}/draft` calls with **identical** request bodies,

**Then** the second call returns `200 OK` with a response body identical to the first call's response, AND the persisted `Tournament.draftJson` is identical to its post-first-call state. No exceptions, no spurious side effects.
