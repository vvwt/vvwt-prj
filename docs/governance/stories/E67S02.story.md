# Story: The certificate page presents the standard template as the active default and surfaces the path to generation

## User Story

**As a** tournament organizer who has not uploaded a custom certificate template,
**I want** the certificate page to make clear that the built-in standard template will be
used and to show me how to reach certificate generation,
**so that** I understand I can produce my teams' Urkunden without uploading anything, and I
am not left thinking an upload is required.

---

## Context

Clicking the "Urkunden" button on a tournament row opens the certificate page
(`/tournaments/:tournamentId/certificate-template`). Today, when no custom template is
uploaded, that page shows a "Keine Vorlage" empty-state (E12S05 AC2) — it reads as a
missing prerequisite, as if a template must be uploaded before anything can happen. The
path onward to certificate generation is a header-right "Urkunden erstellen" button that
only appears once the tournament is COMPLETED (E52S02). An organizer who arrives here sees
an upload form and concludes that uploading is mandatory.

With E67S01, that is no longer true: the built-in standard template is always available
and is used automatically when no custom template is uploaded. This story makes that
reality visible on the page. The empty-state should read as a positive default — the
standard template is active and will be used — rather than as an error or an unmet
prerequisite. The optional custom-template upload stays available for organizers who want
their own design. And the path to certificate generation should be discoverable from the
page, including, when the tournament is not yet completed, why generation is not yet
available.

This story does not re-route the "Urkunden" button and does not change the
COMPLETED-status gate on generation — generating certificates only after the tournament
is completed is correct. It changes what the certificate page communicates, not the
certificate flow's structure.

E67S02 depends on E67S01: the page may only state that the standard template will be used
once the backend actually renders it without an upload.

## Acceptance Criteria

- [ ] **AC1 [behavior]:** Given no custom certificate template is uploaded, when the
  organizer opens the certificate page, then the empty-state presents the built-in
  standard template as the active default — it conveys that certificates will be generated
  with the standard template — rather than framing the absence of an upload as an error or
  an unmet prerequisite.
- [ ] **AC2 [behavior]:** The optional custom-template upload affordance remains available
  on the page — uploading a custom template is still possible and is presented as
  optional, not required.
- [ ] **AC3 [behavior]:** From the certificate page, the path to certificate generation is
  discoverable. When the tournament is COMPLETED, the existing entry-point to the
  generation/download view (the "Urkunden erstellen" affordance delivered by E52S02) is
  clearly discoverable — this story ensures its discoverability; it does not add a new
  generation entry-point. When the tournament is not yet COMPLETED, the page conveys that
  certificate generation becomes available once the tournament is completed. The
  COMPLETED-status gate itself is unchanged.
- [ ] **AC4 [i18n]:** All new or changed UI copy is in German and sourced from the
  frontend i18n message bundle (`de.json`) — no hardcoded display strings — consistent
  with the existing certificate page i18n (E12S05 AC8).
- [ ] **AC5 [error-handling]:** The page's existing degraded states are preserved — a
  tournament or teams load failure still surfaces an actionable message, and loading
  states still display. The new standard-template messaging does not suppress or mask
  error or loading states.
- [ ] **AC6 [testing]:** The new empty-state messaging (AC1) and the
  generation-discoverability affordance (AC3) are asserted by the certificate page's
  automated test surface (`CertificateTemplate.test.ts`). Changes follow DEC-22 RED-first
  discipline for the changed behavior where the test environment supports it; the
  RED→GREEN cadence (or, where RED-first is infeasible for a given assertion, the reason)
  is recorded in the impl-report. `mvn verify` for `vvwt-tm-web` — which runs the frontend
  build and tests (DEC-54) — is BUILD SUCCESS after the change.
- [ ] **AC7 [governance]:** No new DEC is created; the change stays within the existing
  Vite + Svelte + TypeScript admin UI (DEC-2). `related_decs` cites the constraining DECs.
  This story depends on E67S01 — the standard-template messaging is only accurate once the
  backend fallback (E67S01) renders the standard template without an upload.

> All acceptance criteria must be verifiable. Vague criteria are invalid.

## Notes

- The story defines the behavioral outcome — a positive standard-template default state
  and a discoverable path to generation. Delivery chooses the exact UI (wording, placement,
