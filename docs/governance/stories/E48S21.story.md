# Story E48S21: Fix — Phase-1 Vorbereiten-flow does not generate matches (slots silently ignored, generateMatches never invoked)

## User Story

**As a** Tournament Organizer,
**I want** clicking "Vorbereiten" on Phase 1 — and confirming the proposed team-to-(group, position) distribution — to produce a phase that, once activated, displays the round-robin match grid on the operator's display devices,
**so that** I can run a tournament from Phase 1 without seeing an empty match grid after every Phase-1 activation.

---

## Context

After E48S17 (PR #210 merged 2026-05-07) and E48S18 (PR #211 merged 2026-05-07T20:17Z), the Phase-1 Vorbereiten flow is structurally incomplete: the operator's confirmation in the Vorbereiten UI persists the proposed team distribution to the new endpoint `POST /api/phases/{phaseId}/prepare`, but that endpoint — by E48S17 design — only flips phase status PENDING → PREPARED. It does NOT consume the slot payload and does NOT invoke match generation. The single production caller of `phasePreparationService.generateMatches(phaseId, gameMode)` is `DefaultPhaseTransitionService.commitTransition` at the legacy `/api/phases/{phaseId}/transition-commit` endpoint — which is no longer wired in by the Vorbereiten UI.

User-observable symptom (manual end-to-end test 2026-05-08): after clicking "Vorbereiten" → confirming → "Phase aktivieren", the phase enters status `ACTIVE` but the display SPA renders a phase-active layout with **zero matches** (`matchesData.matches.length == 0`). Reload does not change the outcome — the matches were never generated.

### Verified mechanism (Discovery investigation 2026-05-08)

- `vvwt-tm-web/src/main/ui/src/routes/PhasePreparation.svelte:22-28` (delivered by E48S18) sets `commitEndpoint = /api/phases/${phaseId}/prepare`.
- `vvwt-tm-web/src/main/ui/src/stores/phaseTransitionStore.ts` exports `commitTransition(phaseId, slots, commitEndpointOverride)` which posts a JSON-array of slot proposals to `commitEndpointOverride ?? /api/phases/{id}/transition-commit`. PhasePreparation routes the override to `/prepare`.
- `vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/DefaultPhaseLifecycleService.java:86-125` (`prepare()`) only flips status and publishes `PhaseStatusChangedEvent` — it does NOT read a request body, does NOT persist TeamAvatars from the slot payload, and does NOT call `generateMatches`.
- `vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/DefaultPhaseTransitionService.java:144-180` (`commitTransition()`) is the only production caller of `phasePreparationService.generateMatches(toPhaseId, gameMode)`. It is no longer reachable from the Phase-1 path.

The slot payload posted to `/prepare` is silently discarded — Spring's `@RequestBody` binding either ignores it (if the controller takes no body) or accepts it without acting on it (if the controller signature shadows it). Either way, no matches are generated.

### Scope posture

This is a **producer-side fix at the prepare-flow boundary** (per memory `feedback_discovery_cycle_resolution_scope_creep.md` — fix at the source, not via consumer tolerance). Discovery does NOT prescribe whether the fix wires `generateMatches` into the prepare endpoint, redirects the frontend to `/transition-commit`, or composes a new combined endpoint — that decision belongs to Delivery's investigation. The acceptance criteria define the observable outcome only.

## Acceptance Criteria

- [ ] **AC-TEST-PREPARE-FLOW-GENERATES-MATCHES-RED** (testing): RED-first integration test — given a tournament with `status=ACTIVE`, a Phase-1 phase with `status=PENDING` and `gameMode` set, a non-empty list of `TeamAvatarProposal` slots derived from `tournament.teams where participate=true`, when the operator-equivalent client invokes the same endpoint(s) the Vorbereiten UI invokes after confirmation (current state: `POST /api/phases/{phaseId}/prepare` with the slot JSON-array body), then after the response settles successfully (a) the phase status is `PREPARED`, (b) `TeamAvatar` records are persisted with structural identity `(phaseId, groupNumber, groupPosition)` per DEC-9, and (c) `match` records are persisted via `phasePreparationService.generateMatches` for the phase. Test fails under the current code path because (b) and (c) do not occur.
- [ ] **AC-TEST-PREPARE-FLOW-DEC9-IDENTITY-RED** (testing): RED-first or augmented to AC1 — verifies that the persisted `TeamAvatar` records have unique `(phaseId, groupNumber, groupPosition)` triples and that `teamId` references match the input slot payload's `teamId`. DEC-9 structural-identity invariant (TeamAvatar identity via `(phaseId, groupNumber, groupPosition)`, not UUID) is preserved.
- [ ] **AC-TEST-NON-PARTICIPATING-TEAMS-EXCLUDED-RED** (testing): RED-first — given the same fixture but with at least one team having `participate=false`, when the prepare flow completes, then no `TeamAvatar` and no `Match` references that team. Test fails before fix because no avatars or matches are generated at all.
- [ ] **AC-TEST-START-AFTER-PREPARE-MATCHES-VISIBLE-RED** (testing): RED-first end-to-end — given a successful prepare flow per AC1, when `POST /api/phases/{phaseId}/start` transitions PREPARED → ACTIVE, then `DefaultDisplayOverviewService.getMatches(deviceToken)` returns a non-empty `matches` array for at least one court. Anchors the user-visible outcome ("display shows the match grid").
- [ ] **AC-TEST-PHASE-2-PLUS-REGRESSION-GREEN** (testing): regression — for `sequenceNumber > 1` (Phase 2+) the existing `commitTransition` → `generateMatches` path remains functional and unchanged. Verify by exercising a Phase-2 prepare flow against the post-fix code and asserting matches are generated.
- [ ] **AC-TEST-PREPARE-IDEMPOTENT-ON-PREPARED-GREEN** (testing): regression — re-invoking the prepare flow on a phase already in `PREPARED` status either (a) is a no-op (no duplicate avatars, no duplicate matches) or (b) returns a documented operator-actionable conflict response. Either behavior is acceptable as long as it is deterministic and does not corrupt existing data. Delivery records the chosen semantics in the impl-report.
- [ ] **AC-IMPL-PREPARE-FLOW-PRODUCES-MATCHES**: after the Vorbereiten UI confirms the slot proposal, the resulting persisted state of the system MUST include (a) `Phase.status = PREPARED`, (b) `TeamAvatar` records for all participating teams with DEC-9 structural identity, (c) `Match` records generated via `phasePreparationService.generateMatches(phaseId, gameMode)`. The fix shape is at Delivery's discretion: candidates include (i) extending the prepare endpoint to consume the slot payload and invoke commitTransition+generateMatches inside the existing DEC-37 lock, (ii) routing the frontend to the existing `/transition-commit` endpoint and folding the status flip there, or (iii) composing a new combined endpoint. The chosen approach is documented in the impl-report. ANY shape that satisfies AC1–AC4 GREEN and AC5+AC6 GREEN is acceptable.
- [ ] **AC-IMPL-DEC-37-LOCK-PRESERVED**: whatever fix shape is chosen, the persistence of avatars + matches MUST execute under the per-tournament pessimistic DB row-lock (DEC-37 Clause B — `TournamentRepository.findByIdForUpdate(tournamentId)` as the first read in the transaction). No new transactional boundary may bypass the lock.
- [ ] **AC-IMPL-DEC-9-STRUCTURAL-IDENTITY-PRESERVED**: TeamAvatar identity is `(phaseId, groupNumber, groupPosition)` per DEC-9 — `teamId` is the source-data reference, not the identity key. The fix MUST NOT introduce UUID-based avatar identity at the optimizer-service or persistence boundary.
- [ ] **AC-ERROR-HANDLING-EMPTY-SLOTS-PAYLOAD** (error-handling): given an empty slot payload (zero teams), the prepare flow returns an operator-actionable HTTP 400 (or other documented client error) with a message naming the missing input. No partial persistence (no avatars without matches, no status flip without avatars). Vitest or controller IT verifies the rejection.
- [ ] **AC-ERROR-HANDLING-WRONG-PHASE-STATUS** (error-handling): given a phase already in `ACTIVE` or `COMPLETED` status, the prepare flow returns HTTP 409 `ConflictException` with an operator-actionable message naming the current status and the expected status. No silent re-execution. Mirrors E48S17 conflict-message contract.
- [ ] **AC-ERROR-HANDLING-NO-PARTIAL-PERSISTENCE** (error-handling): if `generateMatches` fails mid-flow (e.g., database error, slot-validation failure inside the match generator), the entire transaction rolls back. The phase remains in its pre-fix status; no orphan avatars persist. Verified by an integration test that injects a failure into a stub `MatchGenerator` strategy.
- [ ] **AC-SECURITY-PREPARE-AUTH-UNCHANGED** (security): the prepare endpoint(s) authentication and authorization posture remains unchanged from E48S17 — admin-only via Spring Security, no new device-token-based auth surface, no public-facing variant. Verified by a security IT that issues an unauthenticated request and expects 401/403.
