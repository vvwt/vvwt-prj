# Story E46S06: Schema-hygiene consolidation — fold E46S01 V2 i18n migrations into V1 baseline (`tenant/V1` + `tournament/V1`); V2 files deleted

## User Story

**As a** Tournament Manager developer reading the per-module Flyway layout,
**I want** the four E46S01 i18n columns (`tenants.language`, `tournament.organizer`, `tournament.language`, `team.language`) to live inline in `V1__initial_schema.sql` of their respective modules — not as a separate `V2__e46s01_certificate_default_template_i18n.sql` — so that the V1 baseline accurately reflects the architecturally-foundational scope (i18n was a foundational requirement of the rewrite, retroactively recognized by DEC-52),
**so that** the per-module Flyway layout matches the application's foundational schema as understood at the time of the rewrite, and the per-tenant Flyway log no longer emits a misleading "post-baseline V2 extension" entry for what is in fact baseline scope.

---

## Context

E46 introduced i18n to the certificate-rendering subsystem. E46S01 (PR #178, merged 2026-05-03) added two Flyway files extending the per-tenant H2 schema with four nullable columns:

- `db/migration/tenant/V2__e46s01_certificate_default_template_i18n.sql` — adds `tenants.language VARCHAR(8) NULL`.
- `db/migration/tournament/V2__e46s01_certificate_default_template_i18n.sql` — adds `tournament.organizer VARCHAR(255) NULL`, `tournament.language VARCHAR(8) NULL`, `team.language VARCHAR(8) NULL`.

DEC-52 (2026-05-04) retroactively reclassifies these files as part of the V1 baseline on the grounds that internationalization was a foundational requirement of the application rewrite. This story performs the mechanical consolidation: V2 columns folded into V1 inline; V2 files deleted; per-tenant H2 dev databases wiped before next boot.

The consolidation is authorized **only because DEC-25's no-prod-data condition still holds** at story-creation time (2026-05-04). If production data appears before merge, the story is cancelled per DEC-52 §"Bounded by DEC-25's no-prod-data condition".

**Why this story exists as a discrete unit (not retroactively merged into E46S01):** E46S01 has already merged on `staging` (2026-05-03). The consolidation cannot be retroactively backfilled into S01's commit without rewriting history on `staging` — explicitly forbidden by DEC-13. A new atomic commit on `staging` is the only valid path.

**Hard sequencing:** E46S01–S05 are all `done` and merged (E46S01 PR #178, E46S02 PR #180, E46S03 PR #181, E46S04 PR #182, E46S05 PR #179). No further dependency.

**No forward-binding scope.** DEC-52 explicitly disclaims a forward rule for future bounded contexts. This story does NOT establish, document, or imply a precedent for similar consolidations. Future contexts make their own V1-vs-V2 decisions in their own Discovery sessions.

## Out of Scope

- **Auth, certificate, infoportal modules.** They have only V1 (no V2 to consolidate). Verified
  pre-flight; no changes touch their migration files.
- **Code-layer i18n changes.** `LocaleResolver`, `MessageSource`, templates, assemblers from
  E46S02–S05 stay exactly as-is. This story is purely the schema consolidation.
- **Automated bootstrap-hook for DB-wipe.** Manual instruction in impl-report is the full extent
  of developer guidance per DEC-52 §"Dev environment impact". No code path attempts to detect or
  resolve a V1-checksum-mismatch automatically.
- **Retroactive amendment of E46S01–S05 impl-reports / qa-reports.** They remain point-in-time
  records of what was done at merge time; the consolidation is documented in E46S06 alone.
- **Forward-binding rule for future bounded contexts.** DEC-52 explicitly disclaims this. Future
  contexts decide V1 i18n inclusion per their own Discovery sessions.
- **Wave-2 broader schema audit.** Only the two known V2 files are touched.
- **Memory-hygiene fixes** — DEC-28 missing from `memory/index.md` and stale
  `decisions/_log.md` next-id pointer are flagged but out-of-scope; tracked as a separate
  Discovery follow-up.

## Notes

This story is bounded by DEC-25's no-prod-data condition (still satisfied per Brief H-1 at
story-creation time, 2026-05-04). If production data appears before merge, delivery STOPs and
Discovery is re-activated to re-evaluate via amendment per DEC-52 §"Production-data escape hatch
(inherited)".

**Why no consolidation-source comment in the V1 file:** The V1 file is the canonical SQL; it
does not need to encode "this column was previously in V2 and was folded in". That history lives
in `git log` for the V1 file itself plus in DEC-52's reclassification clause. The V1 file's
content is the authoritative current schema, no provenance prose embedded.

**Audit-trail rationale:** Pre-consolidation Flyway history on the existing dev DB
(`bbb25630-…`) is lost when the dev wipes — this is acceptable per DEC-52 §Audit trail. The
single dev DB holds no production data; the V2 history of E46S01 lives in `git log` of the
soon-to-be-deleted V2 files (preserved by `git`).

**Discovery Session Brief reference:** This story was authored from
`discovery-2026-05-04-flyway-v2-consolidation` — a Brief compiled from the 2026-05-04 Discovery
conversation that produced DEC-52. The Brief was human-validated; its mechanical-scope (α)
choice is reflected in DEC-52's "no forward-binding rule" clause.
