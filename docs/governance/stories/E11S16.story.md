# Story E11S16: Fix — Timer schedule renders 0-min REGULAR pauses because E11S14 baseline pre-population triggers recompute, and recompute cannot resolve `phaseNumber` on BREAK entries

## User Story

**As a** tournament organizer using the Timer SPA after E11S14 shipped,
**I want** the schedule table to render the wall-clock times that the backend computed from my persisted phase plan when I have not made any inline edits — i.e. the operator-configured `LAP-PAUSE = 5 min` value must be visible as 5-minute pause windows between consecutive rounds, not as 0-min markers,
**so that** I can rely on the displayed schedule for venue announcements and the countdown / audio behaviour stays correct.

---

## Context

After E11S14 (PR #371 merged 2026-05-29) shipped, operator reproduced this regression on 2026-05-29 and provided the empirical TimerDataResponse payload (see § Notes for the verbatim shape). The diagnosis is verifiable:

**Backend is correct.** The response payload carries per-phase config (`phase.config.lapBreakTimeMinutes = 5`) AND a `schedule` field whose REGULAR break entries already contain the correct 5-minute windows (`{ "breakType": "REGULAR", "startTime": "10:10", "endTime": "10:15", "type": "BREAK" }`, repeated through Phase 1 + Phase 2). The PHASE_BREAK SECTION_BREAK entries (`label: "PHASE_BREAK"`) also carry their correct 30-min windows from `sectionBreakTimeMinutes = 30`.

**Frontend recompute corrupts the schedule on fresh page load.**

1. E11S14 added `buildInitialBreakConfigFull(data)` in `App.svelte` (called from the initial-load and silent-reload handlers). It pre-populates `ephemeralBreakConfig` with entries for every backend ADDITIONAL BREAK row (SECTION_BREAK rows whose `label === 'PHASE_BREAK'`, and intra-phase Zusatzpausen) so that the inline `Dauer` and `Bezeichnung` inputs show operator-configured values without requiring an edit. This is per E11S14 AC4 / AC5.
2. With `ephemeralBreakConfig` non-empty, `hasEphemeralOverrides(ephemeralPhaseConfig, ephemeralBreakConfig)` returns `true` at `App.svelte:218`. This switches `effectiveSchedule()` from a passthrough of `timerData.schedule` to the FE-side `recomputeSchedule(...)` even though the operator has performed NO inline edits.
3. Inside `recomputeSchedule` (`timelineRecompute.ts`), for each entry the computed config is `cfg = entry.phaseNumber ? getEffectiveConfig(entry.phaseNumber) : getEffectiveConfig(0)`. **Backend BREAK entries do not carry a `phaseNumber` field** — only ROUND entries do (verified in the empirical payload). So for every REGULAR / ADDITIONAL break entry, `getEffectiveConfig(0)` is called.
4. `getEffectiveConfig(0)` checks `ephemeralPhaseConfig.get(0)` (no override; the operator hasn't edited phase 0 because there is no phase 0), then falls back to deriving from the schedule. The derivation filter `schedule.filter(e => e.type === 'ROUND' && e.phaseNumber === 0)` returns an empty list → `lapTimeMinutes` defaults to `15`. The break-filter (REGULAR breaks bracketed by ROUND entries of phase 0) also returns empty → **`lapBreakTimeMinutes` defaults to `0`**.
5. recomputeSchedule walks the schedule with `cursor` starting at the first entry's `startTime`. For each REGULAR BREAK row it advances `cursor` by `cfg.lapBreakTimeMinutes = 0`, producing 0-min pause windows AND shifting every subsequent ROUND entry one pause-window-worth earlier. The rendered schedule has Round 2 starting at the same wall-clock time the preceding Pause "starts" — exactly the operator's observation in `Bildschirmfoto_2026-05-29_10-10-44.png`.

**The fix is purely in the FE.** Backend is correct; backend DTO change is out of scope. Discovery's recommended path (operator-validated): introduce a distinction between **baseline pre-population** of `ephemeralBreakConfig` from backend values and **user-edits** that genuinely override backend values. Recompute fires only when at least one entry has been user-edited.

Discovery Session Brief `discovery-2026-05-29-timer-schedule-recompute-baseline-vs-edit` (compact diagnosis brief; operator-validated 2026-05-29 with empirical TimerDataResponse evidence). This Story is bug-triage, single-symptom, single-recommended-fix-direction.

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach is Delivery's choice within the bounds set by the Brief.

### Schedule rendering correctness

- [ ] **AC1 — Schedule renders backend-computed wall-clock times on fresh page load when no inline edits have been made.** Given a tournament whose backend `TimerDataResponse.schedule` contains REGULAR BREAK entries with `startTime`/`endTime` matching `phase.config.lapBreakTimeMinutes` (e.g. 5-minute pause windows for `lapBreakTimeMinutes = 5`), when the operator opens the Timer SPA and performs NO inline edit on any PhaseConfigRow input or break-row Dauer/Bezeichnung input, then the schedule table renders the same `startTime` and `endTime` values that the backend sent for every entry. ROUND entries advance by their backend-emitted `endTime` minus `startTime` (= operator-configured `lapTimeMinutes`); REGULAR BREAK entries advance by their backend-emitted `endTime` minus `startTime` (= operator-configured `lapBreakTimeMinutes`); SECTION_BREAK entries advance by their backend-emitted window (= operator-configured `sectionBreakTimeMinutes`).
- [ ] **AC2 — Schedule recompute fires only when at least one inline edit has been made by the operator (Discovery recommended path b).** The distinction between "baseline pre-population" of `ephemeralBreakConfig` from backend-delivered config (E11S14 AC4 / AC5) and "user-edit" of any inline input is observable at the recompute trigger: when only baseline pre-population is present and the operator has not yet edited any input, `recomputeSchedule` is NOT invoked and `effectiveSchedule()` returns the backend `timerData.schedule` verbatim. After the operator makes the first inline edit, recompute begins firing and the edited entry's value drives the recomputed times. Delivery picks the specific mechanism — e.g. (i) two separate state maps: one for baseline-display and one for user-edits, with `hasEphemeralOverrides` checking only the latter; OR (ii) a "dirty" flag per entry tracking whether the displayed value diverges from the backend baseline; OR (iii) an equivalent shape Delivery proposes with impl-report rationale. Discovery does not pre-judge the mechanism; the AC asserts the trigger semantics.
- [ ] **AC3 — Inline edits continue to work as introduced by E11S12 / E11S14.** When the operator manually edits a PhaseConfigRow input (LAP-ZEIT or LAP-PAUSE) or a break-row Dauer / Bezeichnung input, the schedule recomputes as specified by E11S12 D-11 (ephemeral, no `saveDraft` call) and E11S12 AC8 (live recompute on commit). The recomputed schedule reflects the operator's edit; page reload still reverts to backend-served values.
- [ ] **AC4 — PhaseConfigRow inputs continue to show backend-delivered values on initial render (E11S14 AC2 / AC3 carryover).** The LAP-ZEIT and LAP-PAUSE inputs display `phase.config.lapTimeMinutes` and `phase.config.lapBreakTimeMinutes` respectively on fresh page load, regardless of whether the recompute trigger semantic changes per AC2. The dedicated SECTION_BREAK row's `Dauer` input continues to display `phase.config.sectionBreakTimeMinutes` of the preceding phase (E11S14 AC4).
- [ ] **AC5 — INTRA_PHASE_BREAK row inputs continue to show backend-delivered values when the phase has DraftBreak entries (E11S14 AC5 carryover).** The `Dauer` and `Bezeichnung` inputs of each ADDITIONAL break row whose label is NOT `"PHASE_BREAK"` display the corresponding `phase.config.breaks[idx].durationMinutes` and `.label` (when present). If a tournament has no intra-phase breaks configured (operator's empirical payload: `phase.config.breaks: []`), no INTRA_PHASE_BREAK rows appear in the schedule and this AC is trivially satisfied.

Backend's REGULAR BREAK entries already have the correct 5-minute windows. The bug is solely on the FE side. Verbatim payload retained in operator's session message for Delivery's reference.

**Root cause (verified):**

- `App.svelte:218` `effectiveSchedule = $derived(() => { if (!hasEphemeralOverrides(...)) return timerData.schedule; return recomputeSchedule(...); })`. With baseline pre-population populating `ephemeralBreakConfig`, `hasEphemeralOverrides` returns true on fresh load.
- `App.svelte:281` and `:384`: `ephemeralBreakConfig = buildInitialBreakConfigFull(data);` — populated for SECTION_BREAK and INTRA_PHASE_BREAK entries from `phase.config.sectionBreakTimeMinutes` and `phase.config.breaks` respectively.
- `timelineRecompute.ts` `recomputeSchedule` line 155: `const cfg = entry.phaseNumber ? getEffectiveConfig(entry.phaseNumber) : getEffectiveConfig(0);` — BREAK entries lack `phaseNumber`, so `getEffectiveConfig(0)` is called.
- `getEffectiveConfig(0)`: `ephemeralPhaseConfig.get(0)` is undefined; derivation filters return empty lists; `lapBreakTimeMinutes` defaults to 0.
- recompute walks: ROUND advances by `lapTimeMinutes` (default 15 from line 96 for phase 0 — but if `entry.phaseNumber` is set on ROUND entries, this path uses the correct lookup); BREAK REGULAR advances by `lapBreakTimeMinutes = 0` → 0-min entries → cursor doesn't advance → subsequent ROUND starts at same wall-clock as preceding Pause.

Mathematically: for the operator's Phase 1 backend response, recompute produces:
- Round 1 backend `10:00-10:10` → recompute walks ROUND entry with `cfg.lapTimeMinutes` from `getEffectiveConfig(1)` = derived 10 (from backend first round delta) → recomputed `10:00-10:10`, cursor → 10:10.
- BREAK REGULAR → `getEffectiveConfig(0)` returns lapBreakTimeMinutes=0 → cursor stays at 10:10.
- Round 2 → ROUND `getEffectiveConfig(1)` → lapTimeMinutes=10 → recomputed `10:10-10:20`, cursor → 10:20.

Operator's screenshot showed Round 2 at 10:10 (not 10:15 as backend sent). The recompute produces `10:10-10:20`. Subsequent Round 3 should appear at 10:20 (after a 0-min Pause). This matches the operator's screenshot exactly.

**Recommended fix mechanism (Discovery recommendation; Delivery may pick (i)/(ii)/(iii) per AC2 / Brief operator-validated decision):**

Operator selected option (b) — Discovery recommends differentiating "baseline pre-population" from "user-edits". One concrete shape: introduce a second state map `userEditedBreakConfig: Map<entryIndex, EphemeralBreakConfig>` (or extend `EphemeralBreakConfig` with a `userEdited: boolean` flag, or maintain a separate "dirty" `Set<entryIndex>`) populated only on actual operator input. `hasEphemeralOverrides` checks the user-edit map, not the baseline. PhaseConfigRow and break-row inputs read the displayed value via the baseline map (E11S14 AC4 / AC5 preserved); inline-edit handlers write to the user-edit map and the recompute fires from there.

**Alternative implementation mechanisms (Delivery's choice — see AC2):**
- (i) Two separate maps as sketched above.
- (ii) A single `Map` with per-entry `{ value, userEdited: boolean }` shape.
- (iii) A "dirty-set" tracking which entries have been touched by the operator.

Discovery does not mandate. The AC asserts the trigger semantics: recompute fires only when the operator has edited at least one input.
