# Story: After a side-swap, each on-screen column fully represents one team — name, score, and +/- buttons

## User Story

**As a** referee scoring a match courtside on the tablet,
**I want** each on-screen column — team name, score value, and + / - buttons — to belong
entirely to the team physically on that side after a side-swap,
**so that** I always score the team in front of me and can never credit points to the
wrong team.

---

## Context

Epic E61 (E61S03) added the team-position swap to the scoring-tablet field page — a manual
control, an automatic switch each set, and a mid-set switch in a tiebreak. After a swap, the
team-name labels move, but the displayed score values and the + / - buttons stay with their
original positions.

Per the Discovery session of 2026-05-17 (Brief O-3), the result is a mismatched column: the
swapped column shows one team's name above the other team's score value and + / - buttons.
Points entered on a side then attach to the team that was originally there, not the team
now shown — the operator can unknowingly score the wrong team. The score-to-team data
binding is sound; the defect is in the on-screen rendering and the column's input routing.

---

## Acceptance Criteria

- [ ] AC1 (reproduction): Given a match on the tablet with a non-zero score, when the
  operator triggers a side-swap, then the on-screen column currently shows one team's name
  above the other team's score value and + / - buttons — this is the defect.
- [ ] AC2 (expected — the column fully follows the team): After the fix, following any
  side-swap — manual, the automatic per-set switch, or the tiebreak 8-point switch — each
  physical column consistently shows one team's name, that same team's current score, and
  + / - buttons that adjust that same team's score.
- [ ] AC3 (entry by position): Pressing + or - on a column always changes the score of the
  team currently shown in that column; editing a column's score input always changes the
  score of the team currently shown in that column.
- [ ] AC4 (data-integrity invariant): A side-swap never re-attributes points between teams.
  The swap is a presentation and input-orientation change only: in particular, the
  `team1Points` / `team2Points` values sent in the partial-score and set-submit requests
  always carry team 1's and team 2's own points respectively, in every swap state — a swap
  never changes which team a submitted or persisted score belongs to. After any sequence of
  swaps and score changes, the score the server holds for each team equals what the
  operator entered for that team.
- [ ] AC5 (edge cases / regression): With the score at 0:0 and with equal scores, a swap
  still produces a consistent column / team / score pairing; the automatic per-set and
  tiebreak switches still combine correctly with a manual swap (E61S03 behaviour
  preserved).
- [ ] AC6 (governance — DEC-19): The field page remains Mustache + inline vanilla ES5
  JavaScript only — no Svelte or other framework, no ES2015+ syntax, no bundler.
- [ ] AC7 (testing): First-party ES5 logic changed by the fix is authored test-first per
  DEC-22 to the extent the project's existing automated test surface for this Mustache +
  ES5 page supports it — that surface is rendered-HTML / template-structure inspection in
  the existing `ScoreFieldSwapIT` pattern, not runtime-JavaScript execution. The runtime
  swap behaviour — a column's name, displayed score, and + / - entry all belonging to one
  team (AC2, AC3) and the AC4 payload/data-integrity invariant — is, where not reachable by
  that automated surface, verified by the implementer and explicitly recorded in the
  impl-report, which states exactly what is automated and what is attested. Delivery may
  extend the test surface but is not required to.
- [ ] AC8 (governance — build gate): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS
  (DEC-54, DEC-71).

> All acceptance criteria must be verifiable.

## Out of Scope

- The swap triggers themselves — the manual control, the automatic per-set switch, and the
  tiebreak 8-point switch are E61S03 behaviour and are preserved, not redesigned.
- The field-page layout refinements (E65S06) and the swap-control placement.
- Propagating the orientation to the Display, Admin, or Timer SPAs — the swap is a
  tablet-local presentation concern.

## Notes

Per Brief O-3, E61S03's `applySwap` swaps only the name labels while the score inputs and
+ / - handlers stay bound to fixed positions. Per Brief D-4 the fix is stated as a
behavioural WHAT — each physical column fully and consistently represents one team for both
display and entry — and the implementation is Delivery's (e.g. re-rendering the column
contents on swap, or re-routing the column's handlers). AC4 is the hard invariant: the swap
must never re-attribute points. Per memory `feedback_ac_behavioural_what_not_test_how`, AC7
points at the project's existing test surface for this Mustache + ES5 page rather than
prescribing an unsupported test mechanism. `mvn verify` is the build gate per DEC-54 /
DEC-71.
