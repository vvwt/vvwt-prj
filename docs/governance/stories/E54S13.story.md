# Story E54S13: Refactor — extract `LapPermutationOptimizer` (single point of correctness for L3 brute-force) + add `ORDER BY` to `findByPhaseId` (determinism)

## User Story

**As a** maintainer of the slot-optimization pipeline,
**I want** the L3 exhaustive-lap-permutation brute-force algorithm to exist as a SINGLE implementation that every Leg (1, 2, 3) and every direct-invocation path delegates to,
**so that** future correctness improvements (or bug fixes like E54S12) propagate to ALL slot-opt code paths in one place — eliminating the structural risk of parallel implementations drifting into independent bugs.

**As a** test author / debugger inspecting `findByPhaseId` output,
**I want** the matches returned by `MatchRepository.findByPhaseId` to be in a deterministic, domain-natural order (lap_number then field_number, with NULL-lap matches at the end sorted by id),
**so that** L2 voting is reproducible across DB engines/configs AND post-L2 consumers (Mapper, Print, Display) get the schedule in natural ordering without redundant Java-side sorting.

---

## Context

### Bug surface (8 parallel sites identified by Discovery audit, 2026-05-11)

`RoutingSlotOptimizationClient.executeLeg1Inline` (Leg 1, `@Primary`), `DirectSlotOptimizationClient.optimize` (legacy direct path), and `DefaultCancelableInProcessSlotOptimizationService.optimize` (Leg 3 cancelable) implement structurally-identical brute-force lap-permutation algorithms across ~80-90 LOC each. After E54S12's fix in the Routing path, the THREE implementations diverge at 4 separate code positions, in 2 separate files (Direct + Cancelable), yielding 8 distinct bug-sites:

| Algorithm step | RoutingSlotOptimizationClient (correct post-E54S12) | DirectSlotOptimizationClient | DefaultCancelableInProcessSlotOptimizationService |
|---|---|---|---|
| `lapCount` derivation | `canonical.rowCount()` ✓ DEC-61 B | `rowCount / fieldCount` ✗ stale | `rowCount / fieldCount` ✗ stale |
| Scorer instantiation | `ScorerFactory.createScorerUnified(scorerConfig)` ✓ DEC-63 C | hardcoded `new VarietyScorer()` ✗ | hardcoded `new VarietyScorer()` ✗ |
| activeMatrix source | `denseIdsByRawRow` via helper ✓ E54S12 | `canonical.rows()` ✗ canonical-vs-original index-space mismatch | `canonical.rows()` ✗ same |
| rowSeq from π | `π` directly ✓ DEC-61 B (no expansion) | `pi[i/fc]*fc + i%fc` ✗ stale pre-DEC-61 expansion | `pi[i/fc]*fc + i%fc` ✗ same |

**Compound-bug observation**: in Direct + Cancelable, the stale `lapCount = rowCount/fieldCount` AND the stale rowSeq-expansion **mutually compensate for symmetric setups** (where `rowCount = lapCount × fieldCount`). Fixing either bug in isolation BREAKS the other. The two bugs are entangled. This makes a bug-by-bug fix risky; an extract-and-delegate refactor eliminates both bugs cleanly via one correct implementation.

**Latent-vs-active**: RoutingSlotOptimizationClient is `@Primary @Service` and handles all current production traffic. DirectSlotOptimizationClient and DefaultCancelableInProcessSlotOptimizationService are retained per docs for backward-compat / Leg-3 cancellable / IT-test direct-invocation paths. The bugs are LATENT today but would resurface if:
- Asymmetric phase configurations (e.g., 11T/2G/3F, matchCount=25, lapCount=10) reach Direct or Cancelable
- Leg 3 path activates (lapCount > `tm.slotopt.exhaustive-max-n=10`, e.g., 14+ teams)
- Tests target Direct/Cancelable directly with `tm.slotopt.scorer=balanced`

### Bug surface (1 additional site — determinism)

`DefaultMatchRepository.SELECT_BY_PHASE` is `"SELECT * FROM match WHERE phase_id=?"` with NO `ORDER BY`. H2 + PostgreSQL return rows in undefined order without ORDER BY → L2 voting tiebreak (stable-sort) depends on DB row-storage order → non-deterministic L2 output across runs/engines/versions. Violates DEC-49 D-3 (determinism mandate).

Investigation `2026-05-11-live-cluster-discrepancy.investigation.md` § H-δ marked this as PARTIALLY VERIFIED contributing factor.

### Why refactor-first (not bug-by-bug fix)

User-stated principle (2026-05-11): *"single point of failure zu vermeiden"*. Discovery confirms: extract-and-delegate is the architecturally-cleanest solution because:

1. **Structural elimination**: all 8 parallel bug-sites disappear because there's only ONE implementation to be correct.
2. **Future drift prevention**: when E54S12-equivalent bugs are found in the future, fixing them once propagates to all 3 clients.
3. **Test surface concentration**: the brute-force algorithm gets ONE thorough test suite (the extracted class's unit tests); each client only needs delegation-verification tests.
4. **Compound-bug avoidance**: bug-by-bug fix risks breaking the mutually-compensating lapCount + rowSeq-expansion entanglement; refactor sidesteps this by replacing both with the correct DEC-61-aligned single implementation.

## Root Cause Analysis

### Bug-class 1 — `lapCount = rowCount / fieldCount` (pre-DEC-61 stale derivation)

Two sites: `DirectSlotOptimizationClient:164` and `DefaultCancelableInProcessSlotOptimizationService:116`. Pre-DEC-61, Mapper produced one RawRow per match; rowCount = matchCount; lapCount = matchCount / fieldCount. Post-DEC-61 Clause B (E54S02 Mapper-refactor), Mapper produces one RawRow per lap; rowCount = lapCount directly. The stale division is incorrect for ANY setup but happens to coincide for symmetric cases (where rowCount = lapCount × fieldCount). For asymmetric setups (e.g., 11T/2G/3F: matchCount=25 vs lapCount=10), the division yields wrong values.

### Bug-class 2 — Hardcoded `new VarietyScorer()` (pre-DEC-63 stale scorer)

Two sites: `DirectSlotOptimizationClient:189` and `DefaultCancelableInProcessSlotOptimizationService:131`. Pre-DEC-63, only `VarietyScorer` existed. Post-DEC-63 Clause C, `BalancedVarietyScorer` is an opt-in alternative selected via `tm.slotopt.scorer`. The hardcoded instantiation ignores the config, so operators setting `tm.slotopt.scorer=balanced` get `VarietyScorer` on these paths instead.

### Bug-class 3 — `activeMatrix` built from `canonical.rows()` (E54S12-mirror)

Two sites: `DirectSlotOptimizationClient:190-191` and `DefaultCancelableInProcessSlotOptimizationService:132-133`. `canonical.rows()` is the lex-sorted form produced by `StructuralFingerprint.canonicalize()` Step 3. `LehmerCodec.rankToPermutation` and `SlotResultApplicator.applyResult` operate in original-lap-number space. Index-space mismatch → scorer finds optimum in canonical space but applicator applies it in original space → clustered output. Fixed in Routing by E54S12; latent in Direct + Cancelable.

### Bug-class 4 — `rowSeq = pi[i/fc]*fc + i%fc` expansion (pre-DEC-61 stale)

Two sites: `DirectSlotOptimizationClient:202-205` and `DefaultCancelableInProcessSlotOptimizationService:152-155`. Pre-DEC-61, this expanded a lap-permutation π into a row-permutation rowSeq when rows were matches (`rowCount = matchCount`). Post-DEC-61 Clause B, rows ARE laps already, so π directly IS the row sequence. The stale expansion is incorrect post-refactor. RoutingSlotOptimizationClient removed it; Direct + Cancelable still have it.

**Compound-bug entanglement (symmetric case only)**: bug-classes 1 + 4 mutually compensate ONLY for symmetric inputs where `rc = lc × fc`. Specifically: with `lapCount = rowCount/fc` (stale formula) producing `lc_stale = rc/fc`, and with `rowSeq[i] = pi[i/fc]*fc + i%fc` expansion producing length `rc` from `pi` of length `lc_stale = rc/fc`, the resulting rowSeq is a valid permutation of `[0, rc)` for symmetric input. Replacing `lc_stale` with the correct `lc = canonical.rowCount() = lapCount` post-DEC-61 would yield `pi` of length `lapCount = rowCount`, but the expansion `pi[i/fc]` for i up to rowCount would do `pi[0]*fc + 0, pi[0]*fc + 1, pi[0]*fc + 2, pi[1]*fc + 0, ...` — which would access pi at out-of-bounds indices AND produce duplicate values. For symmetric inputs the bugs are inseparable; both must change together.

**Asymmetric inputs (e.g., 11T/2G/3F: matchCount=25, lapCount=10) are NOT mutually compensating** — the stale `lc_stale = 25/3 = 8` is neither correct nor coincidentally aligned with bug-class 4; both bugs corrupt independently. Asymmetric inputs to Direct or Cancelable would either crash (IndexOutOfBoundsException via the stale rowSeq expansion) or silently produce structurally-wrong output (mis-applied permutations). E54S04's earlier OOB fix touched `SlotResultApplicator` but did NOT propagate to Direct/Cancelable's brute-force loops — those paths remain unsafe for asymmetric inputs. The extract-refactor eliminates this latent asymmetric-input bug along with the symmetric-input entanglement.

### Bug-class 5 — `findByPhaseId` undefined order

One site: `DefaultMatchRepository.SELECT_BY_PHASE:50`. No `ORDER BY` clause. Independent of bug-classes 1-4. Affects L2 voting determinism (stable-sort tiebreak depends on insertion order) and post-L2 consumer ordering (Mapper internally re-sorts but other consumers — Print, Display — rely on natural ordering).

### Why extract-refactor is the right answer

A bug-by-bug fix would need to address bug-classes 1+4 atomically in Direct AND Cancelable (4 code positions), plus bug-class 2 in both (2 positions), plus bug-class 3 in both (2 positions) — a total of 8 distinct edits across 2 files, requiring per-edit reasoning about the compound-bug entanglement. The risk of introducing a NEW bug during the bug-by-bug fix is significant.

An extract-refactor REPLACES all 8 bugs in one structural change: the new class IS correct (matches E54S12-fixed Routing); the 3 clients become thin wrappers; the parallel implementations cease to exist. The structural property "all 3 clients use the same algorithm" is now compiler-enforced.
