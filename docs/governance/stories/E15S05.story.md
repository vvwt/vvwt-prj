# Story E15S05: Flyway migration relocated from root V6 to db/migration/auth/V1; per-tenant application via E14 runner

## User Story

**As a** new tenant being onboarded,
**I want** the `admin_credentials` schema to live under the `auth` module's Flyway directory and be applied via the per-tenant runner from E14S04,
**so that** every tenant's DB gets the schema at creation time through the same mechanism every future context will use.

---

## Context

The legacy schema lives at `vvwt-prj/vvwt-tm-web/src/main/resources/db/migration/V6__e05s02_admin_credentials.sql`. Per DEC-20 / DEC-21, migrations must live under `db/migration/{context}/V1__*.sql` — so this story creates `db/migration/auth/V1__admin_credentials.sql` containing the exact same schema (unless a story AC identifies an improvement), and verifies the per-tenant Flyway runner from E14S04 applies it.

Per DEC-22 and the mission brief: the legacy `V1..V6` files are NOT deleted in this story. Deletion is the atomic responsibility of E15S07 cutover, which deletes both the new-path files' legacy counterparts AND ensures no dependency on the legacy path remains at runtime. During this story both locations coexist on disk; the runner from E14S04 applies only the new-path file (per E14S04 AC8, which proved legacy-root migrations are inert under the new runner).

## Acceptance Criteria

- [ ] AC1 (testing — test-first for migration application): Git history shows a failing integration test verifying the per-tenant Flyway runner applies `db/migration/auth/V1__admin_credentials.sql` to a fresh test tenant's DB before the migration file is added. The test initially fails because the migration does not exist; adding the migration file turns it green. Per DEC-22.

- [ ] AC2 (data-isolation — per-tenant application proof): An integration test creates two test tenants (via E14S02's registry), invokes the runner from E14S04 on each, and verifies each tenant's DB contains the `admin_credentials` table in exactly the expected shape. Neither tenant's table is visible from the other's DataSource.

- [ ] AC3 (governance — migration path compliance): The new migration file is at `vvwt-tm-web/src/main/resources/db/migration/auth/V1__admin_credentials.sql`. The version number is `V1` (per-module numbering restart — E14S04's runner applies per-module directories independently, per DEC-21). The schema matches the legacy `V6__e05s02_admin_credentials.sql` content byte-for-byte unless the Delivery plan documents a deliberate schema improvement with rationale.

- [ ] AC4 (governance — LEGACY V1..V6 NOT deleted in this story): `git diff` at this story's merge shows `vvwt-tm-web/src/main/resources/db/migration/V1__*.sql` through `V6__*.sql` UNCHANGED (no file deletions). Deletion is explicitly deferred to E15S07 per the mission brief and DEC-22 O-9. A deliberate check in the Delivery plan's verification steps confirms legacy files are still present.

- [ ] AC5 (error-handling — missing migration directory): If the runner is invoked and `db/migration/auth/` directory does not exist (e.g., a build-resource exclusion misconfiguration), the runner surfaces a clear error identifying the missing directory — it does not silently succeed with zero migrations applied. A test asserts this if the mechanism permits (e.g., pointing the runner at a controlled missing classpath location).

- [ ] AC6 (error-handling — schema conflict on existing tenant): If the runner is applied to a tenant whose DB was previously migrated with the legacy V6 schema (hypothetical — in Wave-1 reality, no production tenants exist), Flyway's standard behaviour applies: checksums are compared, duplicate-application is skipped. A test with a pre-loaded schema fixture confirms no destructive re-run.

- [ ] AC7 (testing — Modulith verify): `ApplicationModulesTest` remains green. The new migration directory's existence does not trigger any boundary issue.

- [ ] AC8 (governance — schema parity documentation): The Delivery plan contains a one-section schema-parity check: diff of legacy V6 SQL vs new auth/V1 SQL, documenting whether they are byte-identical or (if not) enumerating each deliberate change. No undocumented schema drift permitted.

- [ ] AC9 (security — credential-store contract preserved): The relocated migration preserves every security-relevant schema property of the legacy `admin_credentials` table: the hashed-password column type and width (no shorter column that would truncate a bcrypt hash), NOT NULL constraints on credential columns, the singleton_guard UNIQUE index preventing multiple admin rows, and any CHECK constraints. An explicit security-review paragraph in the Delivery plan attests that no schema change weakens the credential-store contract. If a deliberate schema improvement is made (per AC3), it must be security-reviewed and documented.

## Notes

The most common failure mode here is "copy-paste the legacy V6 into auth/V1 with a subtle whitespace or comment difference" — Flyway's checksum logic won't forgive this during future tenant cross-migration scenarios. AC8's schema-parity check is the safeguard.

The retention of legacy V1..V6 until E15S07 is not cosmetic — it is the point of the atomic cutover protocol. The system runs with both files present, but only the new one applied (AC4 of E14S04 proved the runner ignores legacy root). E15S07 performs the single deletion atomically.
