# Story E46S03: `DefaultCertificateAssembler` extension — `tom_organizer` data variable + 6 `tom_label_*` static-string variables (pre-rendered via `MessageSource`) + locale-aware date formatter + `tom_` prefix hard-cut on all 13 model variables + `DefaultCertificateTemplateService.VARIABLES` rewrite

## User Story

**As a** Tournament Manager template author (system-default OR custom upload),
**I want** the certificate render model to expose a single, namespaced contract — 7 data variables (`tom_placement, tom_team_name, tom_team_photo, tom_tournament_name, tom_date, tom_location, tom_organizer`) plus 6 pre-rendered i18n label variables (`tom_label_certificate, tom_label_place, tom_label_achieved_by, tom_label_team_photo, tom_label_generated_by, tom_label_on`), with the date formatted in the team's resolved locale and all label strings resolved at render time via Spring `MessageSource`,
**so that** the certificate renders with the V1 branded layout end-to-end without hardcoded German strings in the assembler, the public custom-upload contract (`/api/.../variables`) reflects the full 13-variable surface, and future language bundles can ship as additive `messages_<lang>.properties` resources without changing one line of Java.

## Context

Brief D-13 + D-16 + D-17 collectively reshape the certificate render model:

- **D-13 (i18n via pre-rendering, NOT lambdas):** `DefaultCertificateAssembler` resolves the 6 V1 label keys via `MessageSource.getMessage(key, args, locale)` AT RENDER TIME and binds them to the model under `tom_label_*` keys. The decision to pre-render (rather than expose a Mustache lambda) is final per Brief T-7. Resolver scope: per-page labels (the `_certificate_page.mustache` partial — `tom_label_place`, `tom_label_achieved_by`, `tom_label_team_photo`) use TEAM-LEVEL locale resolution; document-chrome strings (the wrapper template — `<title>`, `tom_label_generated_by`, `tom_label_certificate` if used at chrome level) use TOURNAMENT-LEVEL locale resolution. Story-author decides at delivery RED-first whether the chrome labels live on the team-level row map or are bound by the rendering controller before composing the wrapper.

- **D-16 (`VARIABLES` is the public contract — 13 entries, all PUBLIC):** `DefaultCertificateTemplateService.VARIABLES` (today: 6 entries at lines 78–88 — `placement, teamName, teamPhoto, tournamentName, date, location`) is rewritten to declare exactly 13 `tom_`-prefixed entries: 7 data + 6 labels. Label keys are public-stable; new labels arrive additively in future stories (Mustache `defaultValue("")` makes label additions non-breaking for older custom uploads — they just render an empty string for the new placeholder).

- **D-17 (variable-name prefix hard-cut, NO backward-compat layer):** All Mustache variables in the certificate-render model are renamed to lowercase snake_case with the `tom_` prefix. The `buildMustacheMap` helper (currently at `DefaultCertificateAssembler:314–325`) is rewritten to populate ONLY the prefixed names. Existing custom-upload templates that reference unprefixed names (`{{placement}}`, `{{teamName}}`, etc.) will render those placeholders as empty strings post-cutover — accepted residual risk per H-2 (audience presumed small, manual migration only).

- **D-8 (locale-aware date format — CERTIFICATE PATH ONLY):** The hardcoded `DATE_FORMATTER` constant at `DefaultCertificateAssembler:78–79` (`DateTimeFormatter.ofPattern("d. MMMM yyyy", Locale.GERMAN)`) is removed. The new per-call formatter is `DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(resolvedLocale)`, where `resolvedLocale` comes from the team-level resolver call. Non-certificate print surfaces (laufzettel, activity-schedule, timer view) stay V1 hardcoded German per S-18 — out of scope here.

### Date formatter: locale-aware, certificate path only (D-8 + S-18)

- [ ] **AC-DATE-FORMATTER-CONSTANT-REMOVED [governance]:** The `DATE_FORMATTER` static-final constant at `DefaultCertificateAssembler:78–79` is removed. The hardcoded `Locale.GERMAN` pattern no longer appears in this class.
- [ ] **AC-DATE-FORMATTER-LOCALE-AWARE [i18n]:** The `tom_date` value in the map is produced by `DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(resolvedLocale).format(localDate)`, where `resolvedLocale` is the team-level locale obtained via the `LocaleResolver` chain (E46S02). For the V1 German bundle the rendered string remains the long-form German date (e.g., `"15. April 2026"`) — verified by an explicit test against `Locale.GERMAN`.
- [ ] **AC-DATE-FORMATTER-NON-DE-PATH-SMOKE [i18n]:** A test invokes the assembler with a deliberately non-German `Locale` (e.g., `Locale.ENGLISH`) and asserts the produced `tom_date` string conforms to `FormatStyle.LONG` for that locale (e.g., `"April 15, 2026"`). This test demonstrates the locale-aware path is ACTUALLY used (not silently overridden) and that the E46S02 `setFallbackToSystemLocale(false)` wiring routes through correctly. The test does NOT require an English `messages_en.properties` bundle to exist (V1 ships only DE per E46 scope).
- [ ] **AC-DATE-FORMATTER-NON-CERTIFICATE-UNTOUCHED [governance]:** S03 commit must NOT modify date-formatting code in non-certificate print surfaces. Verified by `git diff ${baseSha}..HEAD --name-only` showing no edits under `vvwt-tm-web/src/main/java/de/vvwt/tm/print/`, `…/timer/`, or `…/laufzettel/` (or wherever the non-certificate print formatters live — story-author confirms exact paths at delivery via grep).

### i18n labels: pre-rendering via `MessageSource` (D-13)

- [ ] **AC-LABELS-RESOLVED-AT-RENDER-TIME [i18n]:** Each of the 6 `tom_label_*` map entries holds the value returned by `messageSource.getMessage(key, args, locale)` for the corresponding key (`tom.label.certificate`, `tom.label.place`, `tom.label.achieved_by`, `tom.label.team_photo`, `tom.label.generated_by`, `tom.label.on`) and the resolved locale. NO Mustache lambda is registered on the compiler. NO label string is hardcoded in Java.
- [ ] **AC-LABELS-PER-PAGE-USE-TEAM-LOCALE [i18n]:** Per-page labels (`tom_label_place`, `tom_label_achieved_by`, `tom_label_team_photo`) are resolved with the TEAM-LEVEL locale (per D-13). For a multi-team `print-all` rendering where teams have different `language` values, each team's row carries its own resolved label values.
- [ ] **AC-LABELS-CHROME-USE-TOURNAMENT-LOCALE [i18n]:** Document-chrome labels (`tom_label_generated_by`, `tom_label_certificate` — labels referenced by the wrapper `print.mustache` / `print-all.mustache` AND/OR the `<title>` element) are resolved with the TOURNAMENT-LEVEL locale (per D-13). The chrome labels are bound by the **assembler** (NOT by the rendering controller — Brief D-13 reads strictly: "DefaultCertificateAssembler resolves all static strings via MessageSource AT RENDER TIME"). The assembler exposes the chrome-bound label values at **root model scope** (NOT inside the per-team `singleCertificate` / `certificates` map), so the wrapper templates can reference `{{tom_label_certificate}}` outside any opened section and have it resolve. **Recommended pattern** (binding default unless story-author empirically chooses otherwise RED-first): all 6 label keys are placed at BOTH scopes (root for chrome-access AND inside the row map for per-page access), with chrome instances using tournament-level locale and per-page instances using team-level locale. This keeps the contract symmetric and avoids template-author surprises (E46S04's wrappers can reference any label key without scope-position concerns). Story-author records the final scope topology in `impl-report.md`.
- [ ] **AC-LABELS-V1-GERMAN-RESOLVED [i18n]:** When invoked with the V1 German locale chain (resolver returns `Locale.GERMAN`), all 6 label values match the canonical strings shipped in `messages.properties` (E46S02). The exact German strings are the source-of-truth in that file — this AC asserts the values come THROUGH the `MessageSource` indirection (verified by Mockito `verify(messageSource).getMessage(eq("tom.label.place"), …, eq(Locale.GERMAN))` at minimum on one canonical key, plus an integration test in `DefaultCertificateAssemblerTest` against the real Spring `MessageSource` bean for end-to-end confidence).
