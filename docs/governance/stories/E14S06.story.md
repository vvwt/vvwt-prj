# Story E14S06: Cross-tenant isolation @ApplicationModuleTest

## User Story

**As a** reviewer evaluating whether DB-per-Tenant isolation (DEC-20) genuinely holds,
**I want** an `@ApplicationModuleTest` that explicitly registers two tenants, writes differing data into each, and proves no query shape can cross the boundary,
**so that** the isolation claim is backed by an executable test that future changes cannot silently break.

---

## Context

DEC-20's strongest claim is that cross-tenant query leaks are impossible under DB-per-Tenant. Unit tests of individual components (the routing DataSource in E14S03, the runner in E14S04) exercise pieces of this claim; only an `@ApplicationModuleTest` wiring the full Modulith-managed `tenant` module and executing against real H2 files validates the claim end-to-end.

This story produces that test. It is a single test class (or small test suite) living under `vvwt-tm-web/src/test/java/de/vvwt/tm/tenant/` that uses Modulith's `@ApplicationModuleTest` annotation. It is the canonical reference test for cross-tenant isolation; future contexts' isolation tests follow this pattern.

Per DEC-22, the test itself is written test-first in the narrow sense: the test is committed in a failing state before any missing infrastructure is added to support it. In this story the supporting infrastructure from E14S01-S05 already exists, so the "red" phase may be shorter, but the discipline applies.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first and @ApplicationModuleTest): The isolation test class uses Modulith's `@ApplicationModuleTest` annotation to exercise only the `tenant` module's Spring context. Git history shows the test committed in a failing or red state first if any supporting test fixture is required (fixture commits precede the green test commit). Characterization tests are forbidden per DEC-22.

- [ ] AC2 (data-isolation — two-tenant two-row proof): The test registers tenant A and tenant B via `TenantRegistryPort`, binds `TenantContext` to A and writes a distinct marker row into a test table in A's DB, binds to B and writes a different marker row into B's DB, then asserts: reading A returns only A's row; reading B returns only B's row; neither can surface the other's row regardless of query shape (SELECT *, filtered selects, aggregates, native queries).

- [ ] AC3 (data-isolation — no-bleed via schema probe): The test inspects both tenants' DB files at the filesystem layer (or via a second connection to each) and confirms that tenant A's DB file does NOT contain tenant B's marker row and vice versa — isolation is physical, not just query-filtered.

- [ ] AC4 (error-handling — unbound-context query): The test includes a branch that executes a query with no `TenantContext` bound and asserts the typed exception from E14S01/S03 is raised. No silent default-tenant fallback.

- [ ] AC5 (error-handling — context switch mid-transaction): The test verifies that switching `TenantContext` mid-transaction (either explicitly rejecting this or cleanly tearing down the first transaction) produces defined behaviour per the E14S03 contract (nested-bind decision). Undefined/silent behaviour fails AC.

- [ ] AC6 (governance — Modulith surface compliance): The test uses `@ApplicationModuleTest` for `de.vvwt.tm.tenant` and does NOT import any `de.vvwt.tm.tenant.internal.*` type. All interaction goes through `tenant::api`. This proves a future consumer (E15's `auth`) can achieve the same result with the same surface.

- [ ] AC7 (testing — Modulith verify intact): `ApplicationModulesTest` from E13S01 still passes after this story lands. The new test is additive.

- [ ] AC8 (error-handling — cleanup on failure): The test cleans up its temp `${tm.data.dir}` regardless of pass/fail (using `@TempDir` semantics or equivalent) so repeated local runs do not accumulate stale tenant files. An explicit test verifies the temp-dir cleanup behaviour if using a custom teardown.

## Notes

This test is the `tenant` module's acceptance gate. If it cannot be made green without leaking context-switching complexity into consumers, that is a signal that the `tenant::api` from E14S01 needs revision — surface it before E14S07 cutover, not after.

The "schema probe" in AC3 is occasionally skipped in favour of "query-level filtering is enough". Do not skip it. DB-per-Tenant's entire value proposition is physical isolation; the probe is cheap and cements the claim.
