# Story E16S02: Test-DB isolation in `application-test.yml` — remove shared `testdb` JVM-lifetime state

## User Story

**As a** maintainer running `mvn verify` on `vvwt-tm-web` under Surefire's non-deterministic class ordering,
**I want** every `@SpringBootTest` using `@ActiveProfiles("test")` to receive a per-Spring-ApplicationContext-isolated H2 in-memory DataSource,
**so that** the class of ordering-dependent Flyway-collision flakiness — observed as `CrossTenantIsolationTest` erroring mid-E21S05 and self-masking after E21S07 — cannot reoccur when a future story adds another `@SpringBootTest` IT to the profile.

---

## Context

**Retrospective provenance.** During the E21S05 session (2026-04-20), four new integration tests (`MatchRepositoryIT`, `MatchOutcomeRepositoryIT`, `SetResultRepositoryIT`, `AuditLogRepositoryIT`) were added. An intermediate `mvn verify` run errored on `CrossTenantIsolationTest` with the same Flyway-collision stack previously seen on `GlobalExceptionHandlerTest`. The failure disappeared after E21S07 merged — not because of a code or test fix, but because Surefire's class order shifted. E21S05's final `qa-report.md` declared PASS (546 tests, 0 failures), correctly for its final run. The flake is real, the qa-report is honest, and the mechanism is deterministic-in-order but non-deterministic across orderings.

**Root cause.** `vvwt-tm-web/src/test/resources/application-test.yml` hard-codes
`jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE`. `DB_CLOSE_DELAY=-1` keeps the H2 in-memory DB alive for the JVM lifetime, and every `@SpringBootTest` loading this profile shares the same `testdb`. `DefaultTenantBootstrapRunner` (`@Order(1)`) and E15's `AdminCredentialsBootstrap` migrate schema (including `admin_credentials`) on every context load. When Surefire's class order places a context that hasn't seen `admin_credentials` before a context that now finds it pre-existing, Flyway/FK collisions surface. The fix is at the profile, not at each IT.

**Out-of-band evidence that the fix works** already lives in the codebase: `TenantContextTestSupport.java` (L146) and `TenantDaoTestSupport.java` (L88) both use UUID-suffixed H2 URLs and do not exhibit the ordering-dependency. The shared `testdb` in `application-test.yml` is the outlier pattern, not the project default.

**Why E16 as parent.** E16 codifies test-infrastructure governance under DEC-26. A YAML-level fix that makes the right test-DB isolation the default for every `@SpringBootTest` is precisely in E16's "right path = easiest path" Poka-Yoke spirit, even though the artefact is YAML rather than Java.

**Why the fix is narrow.** `@SpringBootTest`-profile-based ITs are the observed offender. The ~40 hard-coded per-suite H2 URLs (`jdbc:h2:mem:e05s04migdb`, …) are each used by a single IT class and have shown no cross-class collision in grep. Retrofitting them is deferred to a separate story if ever warranted — this story fixes the root of the observed flake class, nothing more.

**What this story does NOT change.** No production code. No changes to `TenantDaoTestSupport`, `TenantContextTestSupport`, `DefaultTenantBootstrapRunner`, `PerTenantFlywayRunner`, `AdminCredentialsBootstrap`. No new DEC, no new governance rule. No test is disabled, ignored, or deleted to absorb the fix. No Surefire ordering is forced.

## Notes

- **Mechanism choice is Delivery's to make within AC3's closed list.** The Session Brief intentionally does not pick one — all three are viable and each has different trade-offs (Spring-idiomatic, placeholder-style, Java-wired). Delivery picks the one that preserves Spring Test context-cache hit rates best (AC7) and documents the choice in `impl-report.md`.
- **The pre-fix-HEAD / post-fix-HEAD discipline matters.** Delivery records the pre-fix-HEAD commit SHA in `execution-plan.md` at story start, and references it in both `impl-report.md` and `qa-report.md` at story close. The test-count-superset requirement (AC12) hinges on this captured number — an absolute ("546") would go stale against ongoing merges to `staging`.
- **If the flake self-masked on current staging HEAD** (H-3 being the causal hypothesis), the pre-fix reproduction route (AC6 option 1) may be difficult. That is anticipated — AC6 explicitly provides the canary route (option 2) so Delivery is never blocked. The essential invariant is: either the original failure is reproduced, or a synthetic test exercising the same shared-state pathway is constructed RED-first; empty hand-waving is forbidden (AC11).
- **`spring.datasource.generate-unique-name=true` is likely the cheapest mechanism.** It is a documented Spring Boot property, it resolves uniqueness inside Spring Boot's own DataSource auto-config (not via text substitution → preserves context-cache key stability), and it requires a single YAML line change. Delivery may pick otherwise if it has strong grounds; the justification lives in `impl-report.md`.
- **The canary test, if route (2) is taken, is itself disposable.** It is a regression-guard probe, not a product feature. Delivery may either (a) keep it as a minimal permanent IT under `src/test/java` to prevent re-introduction of the shared-URL pattern, or (b) commit it as a temporary fixture that is removed after the GREEN commit proves the mechanism. Option (a) is recommended; option (b) is permitted only with explicit justification in `impl-report.md`. Either way, the RED commit precedes the GREEN commit in git history.
