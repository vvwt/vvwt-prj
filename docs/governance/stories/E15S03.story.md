# Story E15S03: AdminCredentialsBootstrap — reconstruction-in-place with TDD (orchestration)

## User Story

**As a** TM operator starting the application for the first time,
**I want** the admin credentials bootstrap to orchestrate generation → hashing → persistence with clear separation of concerns and deterministic first-start behaviour,
**so that** on first start a fresh admin password is generated, logged, and persisted, and on subsequent starts the existing hash is kept without regeneration.

---

## Context

The legacy `AdminCredentialsBootstrap` mixes three concerns (orchestration, persistence, password generation). E15S01 extracted generation; E15S02 extracted persistence. This story extracts the orchestrator itself: an `ApplicationRunner` under `de.vvwt.tm.auth.internal` that delegates to `PasswordGenerator` (E15S01) and `AdminCredentialsDao` (E15S02), plus Spring Security's `PasswordEncoder` for hashing.

The orchestrator has precise ordering requirements: it must run AFTER E14S05's default-tenant bootstrap (so the default tenant's DataSource is available) and declare this via `@Order(2)` (or the appropriate ordinal established in the Delivery plan). Per DEC-22 tests are first; orchestration tests mock the Dao and Generator (this is the one story where mocking IS appropriate — the SUT is orchestration, not the collaborators).

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows failing tests for `AdminCredentialsBootstrap` orchestration paths (first-start creates, subsequent-start no-op) committed BEFORE the implementation. Spot-check confirms red-then-green per DEC-22.

- [ ] AC2 (testing — orchestration unit tests with mocks): `AdminCredentialsBootstrapTest` uses mocked `AdminCredentialsDao` + mocked `PasswordGenerator` + a test `PasswordEncoder`. The mocking is justified: the SUT's only role is orchestration logic, which is fully decoupled from Dao/Generator internals (per the Epic Success Metrics).

- [ ] AC3 (security — first-start generates + logs plaintext + persists hash): A test verifies first-start branching: when the Dao's "find existing" returns empty, the orchestrator invokes the Generator, logs the plaintext password at INFO level (preserved behavior per the Epic scope), invokes the encoder, invokes the Dao insert with the hash. All four interactions are asserted in order.

- [ ] AC4 (error-handling — subsequent-boot behaviour preserved): On subsequent application starts (registry has existing admin credentials), the orchestrator does NOT regenerate a password — a test asserts Generator was NEVER called. The "set at first start — check startup log" INFO log line MUST be emitted at subsequent boots per the preserved observable behaviour of the legacy `AdminCredentialsBootstrap.java` (lines 126-131). If Delivery proposes to change this log line (e.g., for log hygiene), it MUST be escalated to the human — NOT silently downgraded.

- [ ] AC5 (error-handling — Dao insert race fallback): When the Dao's insert throws the concurrent-start race exception (per E15S02's AC3), the orchestrator re-queries via the Dao and uses the existing hash — does NOT regenerate or retry inserts. A test asserts this path executes without exception leakage.

- [ ] AC6 (error-handling — encoder failure): If the `PasswordEncoder` throws during hashing, the orchestrator surfaces the error and does NOT invoke the Dao insert — no half-written state. A test asserts this.

- [ ] AC7 (governance — @Order position): The `ApplicationRunner` declares `@Order(2)` (or the ordinal required to run after E14S05's default-tenant bootstrap, finalised in the Delivery plan and documented in Javadoc referencing the tenant bootstrap's ordinal). A Spring-context integration test verifies the ordering by observing bootstrap logs on a fresh-machine start.

- [ ] AC8 (testing — Modulith verify): `ApplicationModulesTest` remains green. The orchestrator lives under `de.vvwt.tm.auth.internal` and uses `tenant::api` only for its context-binding (if needed) — no `de.vvwt.tm.tenant.internal.*` imports.

- [ ] AC9 (governance — no legacy change): Legacy `AdminCredentialsBootstrap` untouched until E15S07. `git diff` shows only new files + tests.

## Notes

The orchestrator is the one place in E15 where mocks earn their keep. In S01/S02 mocks would be misuse. In S03 they are appropriate because the collaborators' behaviour is already verified against reality in their own tests; S03's job is solely to prove the orchestration wiring.

The "log plaintext at INFO" requirement is an inherited behaviour from E05S02 — it is a self-host deployment acceptable trade-off (operator sees the password once, stores it, plaintext lives only in stdout). If Delivery proposes to change this, it must be escalated — do not silently switch to "print once and erase" semantics.
