# Story E48S04: Match-Cancel-Lockdown — Bulk-Marking auf MatchState.CANCELED + Score-Service-Rejection-Guard

## User Story

**As a** Tournament Organizer who just cancelled an active tournament,
**I want** the system to automatically mark all unfinished matches as CANCELED and reject any further score submissions on those matches,
**so that** I have data integrity (tablets cannot keep writing scores into a cancelled tournament) without having to manually shut anything down.

---

## Context

Per Brief D-4 + O-15 / Cycle-1 F-1 Resolution: Cancel-Workflow markiert unfinished Matches via existing `MatchState.CANCELED(-10)` (kein neuer Enum-Wert; AC-ENUM-VALUES-STABLE per DEC-22/E21S05 erhalten). Diese Story erweitert die `cancel(tournamentId)`-Methode aus E48S03 um (1) Bulk-Marking aller unfinished Matches der betroffenen Tournament-Phasen auf CANCELED und (2) einen Guard im `DefaultScoreEntryService`, der Set-Result-Submissions auf CANCELED Matches mit HTTP 409 oder ähnlich ablehnt. Beide Operations laufen im selben Transactional row-lock wie der Status-Wechsel (DEC-37 Clause B), damit kein partial-state möglich ist.

`MatchState`-Werte: OPEN(0), ENABLED(10), INPROGRESS(30), ONCHECK(35) sind "unfinished". FINISHED_WINNER1(51) / FINISHED_WINNER2(52) / FINISHED_STANDOFF(50) bleiben unverändert (Audit-Erhalt). CANCELED(-10) ist Idempotent (re-cancel ist no-op).

## Acceptance Criteria

- [ ] **AC-TEST-MATCH-BULK-CANCEL-RED** (testing): RED-first IT-Test: gegeben Tournament mit Phasen + Matches in verschiedenen States (OPEN/ENABLED/INPROGRESS/ONCHECK/FINISHED_*); Aufruf `cancel(tournamentId)` setzt alle unfinished Matches (OPEN, ENABLED, INPROGRESS, ONCHECK) auf CANCELED; FINISHED_* Matches bleiben unverändert. Independent persistence verifier per assertj-db (DEC-26 Rule 2).
- [ ] **AC-IMPL-MATCH-BULK-CANCEL**: `cancel(tournamentId)` aus E48S03 wird erweitert (oder ein zusätzlicher Service `DefaultMatchLockdownService.cancelOpenMatchesByTournament(tournamentId)` wird aufgerufen): bulk-update der Matches mit `state ∈ {OPEN, ENABLED, INPROGRESS, ONCHECK}` auf `CANCELED(-10)`; im selben transactional Boundary wie der Status-Wechsel.
- [ ] **AC-IMPL-MATCH-CANCEL-IDEMPOTENT**: Re-cancel eines bereits CANCELED Tournaments wirft NICHT (E48S03 wirft `IllegalStateException` weil status bereits CANCELLED — der Match-Bulk-Update läuft daher gar nicht); aber: bulk-update SQL nutzt `WHERE state IN (0, 10, 30, 35)`, also auch idempotent wenn theoretisch der Code-Pfad nochmal liefe.
- [ ] **AC-TEST-SCORE-SERVICE-REJECT-CANCELED-RED** (testing): RED-first IT-Test: nach `cancel(tournamentId)` ein Set-Result-Submit auf einen jetzt-CANCELED Match wirft Exception (z.B. `IllegalStateException` oder `MatchCanceledException`) → Controller returnt HTTP 409 (Conflict).
- [ ] **AC-IMPL-SCORE-SERVICE-GUARD**: `DefaultScoreEntryService.submit(...)` (oder `DefaultScoringService.registerMatchResult` falls dort der natürliche Eintrittspunkt) prüft `match.state == CANCELED` und wirft Exception VOR jedem Schreib-Versuch. Lock-Order: kein Lock benötigt für reine State-Read-Prüfung (Match ist bereits final-state).
- [ ] **AC-TEST-FINISHED-MATCH-AUDIT-PRESERVED-RED** (testing): RED-first IT-Test: gegeben Tournament mit FINISHED_WINNER1 Match + Set-Results in DB; nach `cancel(tournamentId)` sind die Set-Results unverändert (assertj-db count + content verification per DEC-26).
- [ ] **AC-TEST-DEC-37-LOCK-MATCH-BULK-RED** (testing): RED-first concurrency IT-Test: zwei parallele Threads rufen `cancel(sameTournamentId)`; einer succeeds, der andere wirft `IllegalStateException`; Match-Bulk-Update läuft genau einmal. CascadeLockIT-Pattern.
- [ ] **AC-ERROR-HANDLING-CANCELED-MATCH-MESSAGE** (error-handling): die Score-Service-Rejection-Exception trägt operator-actionable Message ("Match {matchId} is CANCELED — score submission rejected. Tournament was cancelled at {timestamp}."); Controller mappt auf HTTP 409 mit JSON-Body.
- [ ] **AC-SECURITY-NO-NEW-ENDPOINTS-IN-THIS-STORY** (security): keine neuen REST-Endpoints — diese Story erweitert nur die existierende `cancel`-Endpoint-Methode aus E48S03 + den existierenden Score-Submit-Endpoint. Keine Security-Policy-Änderung.
- [ ] **AC-GOVERNANCE-NO-NEW-ENUM-VALUE** (governance): KEIN neuer `MatchState`-Enum-Wert (z.B. VOIDED) wird hinzugefügt; Story nutzt explizit das existierende `MatchState.CANCELED(-10)`. AC-ENUM-VALUES-STABLE (DEC-22/E21S05) bleibt erhalten.
- [ ] **AC-GOVERNANCE-NO-SCHEMA-CHANGE** (governance): keine V*-Migration in dieser Story — `match.state`-Spalte (Integer-codes) ist schon da; bulk-update ist reines DML, kein DDL.
- [ ] **AC-GOVERNANCE-DEC-26-DAO-RULES** (governance): bei jedem neuen DAO/IT-Test gelten DEC-26 + DEC-46 3-rules. Konkret für diese Story:
  - **Helper-Pflicht (Rule-3 enforcement):** Test-Fixtures, die `match` rows einfügen, MÜSSEN entweder den existierenden Helper `de.vvwt.tm.infrastructure.testsupport.TenantDaoTestSupport` (Pfad: `vvwt-prj/vvwt-tm-web/src/test/java/de/vvwt/tm/infrastructure/testsupport/TenantDaoTestSupport.java`) nutzen ODER alle FK-Targets (`tenant`, `tournament`, `phase`, `team_avatar`) in dieser Reihenfolge explizit vorher seedern. `match.member_avatar_1_id` / `match.member_avatar_2_id` sind NOT-NULL FK auf `team_avatar(id)` (constraint `FK_MATCH_MEMBER_AVATAR_1` / `FK_MATCH_MEMBER_AVATAR_2`); ein selbstgebauter `insertMatchDirectly`-Helper, der die FK-Targets nicht seedert, ist eine Verletzung dieser AC.
  - **Schema-aus-Migration (Rule-1 enforcement):** rohe JDBC-INSERT-Statements MÜSSEN die Spaltenliste 1:1 aus der zugehörigen V-Migration übernehmen und die Migration im Test-Code als Pfad-Kommentar zitieren (z.B. `// schema-source: vvwt-tm-web/src/main/resources/db/migration/tournament/V1__initial_schema.sql §set_result`). Spalten zu raten oder aus Trainingsdaten zu generieren ist verboten — Verletzung führt zu `BadSqlGrammar` und gilt als governance-fail.

## Known Pitfalls (cycle-1 attempt — 2026-05-06)

Erstes Delivery (PR #195, branch `story/E48S04`, commit `c41a59e`) wurde im post-exit-gate per DEC-47/DEC-51 als `failed` markiert — **nicht wegen Scope-Problem**, sondern wegen zwei spezifischen LLM-Hallucination-Mustern in den Test-Fixtures, die der nächste Delivery-Lauf vermeiden MUSS. Die ACs `AC-GOVERNANCE-DEC-26-DAO-RULES` und alle `AC-TEST-*` ACs schließen diese Pitfalls bereits ab; diese Sektion ist Anti-Hallucination-Hint-Injection für den nächsten Sub-Agent.

### Pitfall 1: `set_result`-Spaltenliste halluziniert

Cycle-1 schrieb `INSERT INTO set_result (match_id, set_index, team1_points, team2_points, set_state, actor_id, source_type, source_device_id) VALUES (?, ?, ?, ?, ?, ?, ?, ?)` → `BadSqlGrammar`.

**Tatsächliches `set_result`-Schema** aus `vvwt-tm-web/src/main/resources/db/migration/tournament/V1__initial_schema.sql`:

```sql
CREATE TABLE set_result (
    match_id            UUID          NOT NULL,
    set_index           INT           NOT NULL,
    phase_id            UUID          NOT NULL,        -- ← oft vergessen
    team1_points        INT           NOT NULL,
    team2_points        INT           NOT NULL,
    set_state           INT           NOT NULL,        -- OPEN(0), WINNER1(1), WINNER2(2), STANDOFF(3), CANCELED(-1)
    change_time         TIMESTAMP     NOT NULL  DEFAULT CURRENT_TIMESTAMP,
    created_at          TIMESTAMP     NOT NULL  DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (match_id, set_index),
    FOREIGN KEY (match_id) REFERENCES match (id),
    FOREIGN KEY (phase_id) REFERENCES phase (id)
);
```

Die Spalten `actor_id`, `source_type`, `source_device_id` **existieren nicht** im Schema (das sind Trainingsdaten-Halluzinationen aus anderen Audit-Pattern-Schemas). `phase_id` ist NOT NULL und wird beim INSERT oft vergessen.

### Pitfall 2: `match`-Insert ohne `team_avatar`-Seeding → FK-Violation

Cycle-1's selbstgebauter `insertMatchDirectly`-Helper rief direktes `INSERT INTO match (..., member_avatar_1_id, member_avatar_2_id, ...)` mit team_avatar UUIDs, die nicht vorher in `team_avatar` eingefügt wurden → `DataIntegrityViolationException FK_MATCH_MEMBER_AVATAR_1: PUBLIC.MATCH FOREIGN KEY(MEMBER_AVATAR_1_ID) REFERENCES PUBLIC.TEAM_AVATAR(ID)`.

**Korrekter Pfad**:
- **Option A (preferred):** `TenantDaoTestSupport`-Helper nutzen, der die transitive FK-Kette (Tenant → Tournament → Phase → TeamAvatar → Match) korrekt aufbaut.
- **Option B:** Manuelles Seeding in dieser Reihenfolge VOR dem `match`-Insert: `tenant → tournament → phase → team_avatar (×N) → match`.

### Validierungs-Empfehlung für Delivery (Pre-`mvn verify`)

Bevor `mvn verify` läuft, Test-Fixture-Spaltenlisten gegen die Migration prüfen:

```bash
grep -A 30 "CREATE TABLE set_result\|CREATE TABLE match\|CREATE TABLE team_avatar" \
  vvwt-tm-web/src/main/resources/db/migration/tournament/V1__initial_schema.sql
```

Alle `INSERT`-Spaltenlisten in neuen IT-Tests gegen diese Outputs spiegeln. Wenn Helfer-Klasse benutzt wird (Option A oben), entfällt der Manual-Check.
