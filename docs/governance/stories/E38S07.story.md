# Story E38S07: Phase 1 rate-limiting baseline — per-IP token-bucket + per-tournament-token reader concurrency limit + audit-log threshold breaches with split `signature_outcome`/`rejection_reason` (D-X5) + reverse-proxy trusted-proxies allowlist (default-empty, ignore-XFF) + abrupt-WS-close slot release

## User Story

**As a** primary-deployment operator (or self-host operator running publicly),
**I want** a baseline rate-limiting layer in front of the publisher and reader endpoints, with profile-tier defaults (looser self-host, tighter primary), per-IP token-bucket throttling, per-tournament-token reader concurrency caps, default-deny X-Forwarded-For handling, and threshold-breach audit-log writes with the split-enum schema,
**so that** an opportunistic flood from one client (whether QR-scan storm or malicious traffic) cannot degrade service for other tournaments or other operators, and source-IP can't be spoofed to bypass per-IP limits.

---

## Context

Brief D-25 + S-17 + Q-3 specify a Phase 1 rate-limiting baseline: per-IP request rate limit (token-bucket) + per-tournament-token reader concurrency limit + audit-log threshold breaches; profile-tier defaults; stronger postures (CDN, WAF, geo-rate-limiting) deferred Phase 2+. Brief Q-3 sets no quantitative SLO Phase 1.

This story wraps the publisher endpoints (E38S05) and reader endpoints (E38S06) in a rate-limiting middleware. Implementation library candidates per DEC-3 OSS: Resilience4j (`io.github.resilience4j:resilience4j-springboot3` or its SB4 successor), Bucket4j (`com.bucket4j:bucket4j-core`), or hand-rolled token-bucket using Spring's `Cache` abstraction + Caffeine backing. **All three are OSS-compliant per DEC-3**; library choice is implementation detail with story-AC neutral phrasing (per cycle-1 F-8 — Resilience4j is suggestion, not mandate).

CSRF / explicit CORS protection is Phase 2+ per Epic Out-of-Scope (signature verification covers POST authn from E38S04 onward; URL-as-bearer covers reader; SPA same-origin Phase 1).

- [ ] **AC1 (testing)**: **Every new production class** (cycle-1 F-4 fix — broader than "filter / interceptor"): rate-limit filter, source-IP extractor, token-bucket cache wrapper, slot-counter per-tournament-token, configuration-properties validator, 429-envelope mapper. Each has a RED-first test per DEC-22 Iron Law.
- [ ] **AC2 (testing)**: **Per-IP rate-limit IT under both profiles** (units pinned per cycle-1 F-7): rates expressed as **requests-per-minute** uniformly across AC2 + AC5. A single source IP issuing N+1 requests within the rate window (e.g., 600 req/min default for poll endpoints under self-host = 10 RPM averaging) — the (N+1)th request returns 429 Too Many Requests with `Retry-After` header. Test under self-host AND primary, with profile-specific defaults from AC5.
- [ ] **AC3 (testing)**: **Per-tournament-token concurrency IT**: open M+1 concurrent WS connections to `/api/v1/stream/{same_tournament_token}/{various_team_tokens}` (configurable; default 1000 per tournament) — the (M+1)th connection rejected at WS handshake with a clear error frame (envelope-wrapped `RegistrationRejected{reason: "RATE_LIMITED"}` per E38S02 contract). First M connections remain healthy.
- [ ] **AC4 (testing)**: **Threshold-breach audit-log IT** with full C-AUDIT-LOG-SCHEMA column set per Brief D-X5 split (cycle-1 F-9 fix): a 429 emits an `audit_log` row with **all required columns populated**: `request_id` (server-minted UUIDv4, NEVER null), `source_ip` (resolved per AC9), `timestamp_utc` (NEVER null), `signature_outcome="NA"` (rate-limit happens before signature verification), `rejection_reason="RATE_LIMITED"`, `http_status=429`, `tenant_id` / `tournament_id` (populated when extractable from URL, NULL otherwise), `request_path`. Schema columns from E38S03 AC4.
- [ ] **AC5 (governance)**: Spring `@ConfigurationProperties` keys with **profile-tier-default-load IT** (cycle-1 unit-mismatch fix — RPM uniformly):
  - `vvwt.info.rate-limit.per-ip.publisher-rpm` (default: 600 self-host, 300 primary — i.e., 10 / 5 RPS)
  - `vvwt.info.rate-limit.per-ip.reader-poll-rpm` (default: 1200 self-host, 600 primary — i.e., 20 / 10 RPS)
  - `vvwt.info.rate-limit.per-ip.reader-ws-rpm` (default: 300 self-host, 120 primary — i.e., 5 / 2 RPS for connection-attempt rate)
  - `vvwt.info.rate-limit.per-tournament-token.max-concurrent-ws` (default: 1000 self-host AND primary — bounds tournament-resource-exhaustion regardless of profile)
  Defaults documented in `application.yaml` (self-host) and `application-primary.yaml` (primary). IT verifies starting under default profile yields self-host defaults; starting with `spring.profiles.active=primary` yields primary defaults.
- [ ] **AC6 (governance)**: Skill attestation per Epic Success Metrics; DEC-23 / DEC-31 governance propagation. **DEC-23, DEC-31 in `related_decs`** (cycle-1 F-1 fix — citing in body requires frontmatter listing).
- [ ] **AC7 (governance)**: `audit_log` row emission via the established `AuditLogDao` from E38S03 (whose IT satisfies **DEC-26 three rules under DEC-46 multi-module scope-extension** — cycle-1 F-2 misapplication fix — this story does NOT re-implement DAO IT; it consumes the established DAO and emits rows with the split-enum from E38S03 AC4).
- [ ] **AC8 (security)**: **All transitive runtime dependencies** introduced by this story (rate-limit library, cache backing) are OSI-approved OSS per DEC-3 (cycle-1 F-3 fix — broaden to ANY transitive dep). Verified by `mvn dependency:tree -pl vvwt-info-server` review and `pom.xml` declarations.
- [ ] **AC9 (security)**: **Source-IP extraction with default-deny X-Forwarded-For** (cycle-1 F-5 fix — security default): config property `vvwt.info.trusted-proxies` (List<String> of trusted proxy IPs) defaults to **empty**. **Behavior when empty**: X-Forwarded-For header is IGNORED entirely; `request.getRemoteAddr()` is always used. Behavior when non-empty: if request comes from a trusted-proxy IP (CIDR match supported), the LEFTMOST IP in `X-Forwarded-For` is the source-IP; otherwise `getRemoteAddr()`. IT covers: (a) untrusted-source spoofs `X-Forwarded-For: 1.2.3.4` → source-IP for rate-limiting is the actual remote addr (NOT 1.2.3.4); (b) trusted-proxy injects header → leftmost IP is honored.
- [ ] **AC10 (security)**: **Combined-limits IT** (cycle-1 F-6 fix — replaces vacuous prose AC10): one attacker IP opens N concurrent WS connections to a single tournament. Test verifies: (a) per-IP rate limit triggers FIRST (since the connection-attempt rate exceeds `reader-ws-rpm` before the per-tournament concurrency limit M is reached), 429 envelope `scope: "PER_IP"`; (b) if attacker spreads across many IPs to bypass per-IP, the per-tournament concurrency cap kicks in at the M+1 connection, 429 envelope `scope: "PER_TOURNAMENT_TOKEN"`. Both scope values appear in the envelope; the FIRST limit hit determines the scope value.
- [ ] **AC11 (error-handling)**: 429 response shape consistent across publisher and reader endpoints: `Envelope<RateLimited{retry_after_seconds: int, scope: String}>` where `scope` ∈ {"PER_IP", "PER_TOURNAMENT_TOKEN"}. The `RateLimited` payload type is added to E38S02's sealed `ErrorResponse` hierarchy as part of the contract module — this story consumes the type but the type itself is owned by E38S02 (AC9 sealed `ErrorResponse` already includes `RateLimited`).
- [ ] **AC12 (error-handling)**: **Misconfiguration fail-fast at startup**: rate-limit values <= 0 or non-numeric in config produce a clear `ConfigurationPropertiesValidationException` (or equivalent Spring Boot 4 startup error). The server FAILS at startup rather than silently disabling rate-limiting.
- [ ] **AC13 (error-handling)**: **Abrupt-WS-close slot release IT** (cycle-1 F-11 promotion to AC): test opens a WS connection (incrementing per-tournament-token slot counter), then ABRUPTLY drops the TCP connection (force-close socket without WS close-frame). Verifies the server-side `WebSocketHandler.afterConnectionClosed` (or `@OnClose`) decrements the slot counter within a configurable timeout (default: 30s for half-open detection). A subsequent connection succeeds. Tests both clean-close path AND abrupt-close path — both release the slot.
- [ ] **AC14 (error-handling)**: Documentation in `vvwt-info-server/README.md` (or equivalent ops doc) describes the rate-limit knobs, recommended ranges, and how to tune for unusual tournament profiles (e.g., a tournament with 5000 expected concurrent participants exceeds the default 1000 per-tournament concurrency cap — operator must raise it).

## Notes

- Rate-limit library choice (Resilience4j vs Bucket4j vs hand-rolled) is implementation choice within DEC-3 OSS bounds — cycle-1 F-8 alternative consideration. AC text is library-neutral.
- Per-IP token-bucket implementation: a `Cache<String, Bucket>` keyed by source-IP, capacity + refill rate per profile. Caffeine (Apache 2.0, OSS per DEC-3) is the natural cache backing if not using Resilience4j's bundled cache. AC8 covers transitive OSS check.
- Per-tournament-token concurrency: `ConcurrentMap<TournamentToken, AtomicInteger>` slot counter incremented on WS-handshake, decremented on disconnect. The decrement-on-disconnect path MUST be reliable (Spring `WebSocketHandler.afterConnectionClosed` for clean close; idle-timeout sweep for abrupt close); AC13 covers both.
- Profile-tier rationale: self-host loose (single tournament; few hundred participants); primary tighter (untrusted internet traffic).
- AC4 audit-log split (per Brief D-X5): `signature_outcome="NA"` (rate-limit happens before signature verification path); `rejection_reason="RATE_LIMITED"` is the policy outcome. The `tenant_id` / `tournament_id` fields are nullable; populate when extractable from URL (publisher path includes them; poll path includes `tournament_token` only — server can lookup tournament_id from token if not too expensive).
- AC9 default-empty trusted-proxies is the security default: an attacker on the public internet sending a spoofed `X-Forwarded-For` cannot bypass per-IP limits unless the operator explicitly configures their reverse proxy as trusted. CIDR support: e.g., `vvwt.info.trusted-proxies: ["10.0.0.0/8", "192.168.1.5"]`.
- AC10's combined-limits semantic: per-IP and per-tournament-token are complementary — they bound different abuse vectors. Per-IP catches single-source flood; per-tournament catches resource-exhaustion-on-one-tournament. The `scope` enum lets clients (and admin observability) distinguish.
