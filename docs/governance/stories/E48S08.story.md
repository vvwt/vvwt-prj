# Story E48S08: Drag&Drop Phase-Transition Frontend — Svelte Route + Component + Integration

## User Story

**As a** Tournament Organizer who just completed a phase,
**I want** to see the proposed Team-zu-Gruppen-und-Platz-Zuordnung for the next phase, drag&drop teams to correct it, and confirm to commit the assignment,
**so that** I can fine-tune the next phase's structure before matches are generated, with the legacy "MappingSuggestion" UX restored.

---

## Context

Per Brief D-6 + O-16 + S-4: das Drag&Drop-Phase-Transition-UI ist die letzte fehlende UI-Komponente, um den vollen Tournament-Lifecycle ablauffähig zu machen. Diese Story liefert: eine neue Svelte-Route `/tournaments/:tournamentId/phases/:phaseId/transition` mit `<PhaseTransitionDragDrop />` Component; nutzt HTML5 Drag-and-Drop API (kein neues npm-Dependency, konform mit DEC-2 Geist); zeigt initiale Zuordnung aus E48S07 `GET /api/phases/:phaseId/transition-proposal`; Drag&Drop-Korrektur in einer Tabellen-Layout (Gruppen als Spalten, Plätze als Zeilen); Bestätigungs-Button persistiert via E48S07 `POST /api/phases/:phaseId/transition-commit`; nach Commit Navigation zu Phase-Übersicht (E48S05). Routing-Hook: nach E48S06 `complete(phaseId)` Erfolg navigiert UI auf `/tournaments/:id/phases/:nextPhaseId/transition` (außer wenn die abgeschlossene Phase die letzte war = Tournament wartet auf manuellen ACTIVE→COMPLETED via E48S03).

E47 Shell-Mechanism (sticky Header, back-arrow) wird konsumiert.

## Acceptance Criteria

- [ ] **AC-FRONTEND-TRANSITION-ROUTE** (i18n + url-routing): neue Svelte-Route `/tournaments/:tournamentId/phases/:phaseId/transition` registriert in App.svelte routes map; new component `PhaseTransition.svelte` in `src/routes/`; Page-Title via i18n.
- [ ] **AC-FRONTEND-LOAD-PROPOSAL**: bei Mount fetch GET `/api/phases/:phaseId/transition-proposal` und render initiale Zuordnung als Tabellen (Gruppen-Spalten × Position-Zeilen); jeder Team-Avatar ist draggable.
- [ ] **AC-FRONTEND-DRAGDROP-NATIVE**: HTML5 Drag-and-Drop API (`draggable=true`, `ondragstart/ondragover/ondrop` events) ohne npm-Library; Svelte-Action `use:draggable` und `use:dropzone` als hand-authored helpers oder inline.
- [ ] **AC-FRONTEND-SWAP-LOGIC**: drop on existing Team-Avatar → swap (Source und Target tauschen Position); drop on empty Slot (falls vorhanden) → move; Visual-Feedback (Highlight auf hover).
- [ ] **AC-FRONTEND-COMMIT-BUTTON** (i18n): Bestätigungs-Button "Übernehmen" / "Phase {N+1} starten"; klick → POST `/api/phases/:phaseId/transition-commit` mit aktueller Zuordnung im Body; bei Erfolg navigiert zu `/tournaments/:id/phases`; bei Fehler zeigt Error-Banner; i18n-Keys (`phaseTransition.commitButton`).
- [ ] **AC-FRONTEND-COMMIT-PAYLOAD-SHAPE** (governance): POST-Body kodiert die Zuordnung als Liste von Tupeln `{teamId, groupNumber, groupPosition}` — `groupNumber` und `groupPosition` identifizieren den Ziel-Slot in Phase N+1; `teamId` identifiziert das zu platzierende Team. Backend-DTO ist `TeamAvatarAssignment` aus E48S07 (`AC-IMPL-COMMIT-TRANSITION`-Body-Shape) — Delivery verifiziert exakte Field-Namen gegen den E48S07-Java-Record vor Frontend-Implementation. Note: DEC-9 strukturelle Identität `(phaseId, groupNumber, groupPosition)` governt die Optimizer-Service-Boundary (nicht diesen Commit-Pfad); die phaseId ist hier implizit aus der URL `:phaseId` und nicht im body.
- [ ] **AC-FRONTEND-CANCEL-BUTTON** (i18n): Abbrechen-Button (kein Commit, nur Navigation zurück); keine Persistierung; i18n-Key.
- [ ] **AC-FRONTEND-VITEST-DRAGDROP-RED** (testing): RED-first Vitest mit JSDOM. Wegen JSDOM's bekannter HTML5-DragEvent-Limitation (dataTransfer ist read-only / nicht propagiert) testet Delivery **Component-State-Mutations direkt** via Svelte-Runes-State-Zugriff oder Direct-Handler-Invocation (e.g., `component.handleDrop(sourceIndex, targetIndex)`), NICHT via `dispatchEvent(new DragEvent('drop'))`. Assertion: nach swap-handler ruft commit-Button mock-fetch mit aktualisiertem Body. (DEC-22 RED-first für neue Frontend-Code; Q-1a auch im TS).
- [ ] **AC-FRONTEND-VITEST-COMPLEMENTARY-COVERAGE-RED** (testing): RED-first Vitest-Tests für die übrigen production-Code-Pfade per DEC-22 Iron Law — (i) i18n-Keys (`phaseTransition.*` Keys existieren in `de.json`), (ii) Loading-State-Render (während fetch in-flight ist Spinner sichtbar), (iii) Error-Banner-Render (bei mock-fetch 4xx/5xx), (iv) Cancel-Button-Navigation (klick → navigation zu `/tournaments/:id/phases`, kein POST), (v) Route-Title via E47-Header-Mechanism. Pattern wie existing Tests (z.B. `Tournaments.test.ts`).
- [ ] **AC-FRONTEND-LOADING-AND-ERROR-STATES** (error-handling): während Backend-Fetch loading-Spinner; bei 4xx/5xx Error-Banner mit Message (i18n + Backend-Message-Anzeige).
- [ ] **AC-FRONTEND-ROUTING-HOOK** (url-routing): nach erfolgreicher `complete(phaseId)` (Phase-Lifecycle E48S06) UND wenn die abgeschlossene Phase NICHT die letzte ist, navigiert die UI automatisch zu `/tournaments/:id/phases/:nextPhaseId/transition`. Wenn die abgeschlossene Phase die letzte ist, navigiert zurück zur Phasen-Übersicht (E48S05). **Implementierungs-Ort: Frontend in PhaseList.svelte (E48S06-Button-Handler), kein Backend-Response-Shape-Change.** Frontend-Navigation-Logik ist die natürliche Verantwortung der UI; Backend bleibt agnostic gegenüber UI-Routing.
- [ ] **AC-FRONTEND-E47-HEADER**: Page-Title + Back-Button via E47 Shell-Mechanism.
- [ ] **AC-NO-NEW-NPM-DEPENDENCY** (governance): keine neuen npm-Pakete für Drag&Drop (z.B. `svelte-dnd-action`, `interactjs`, `dragula`); HTML5-Native + hand-authored Svelte-Action genügt.
- [ ] **AC-SECURITY-TRANSITION-CALLS-AUTH-VIA-EXISTING-INFRA** (security): Frontend nutzt existing fetch-helpers mit auth-credentials; keine eigene Auth-Logik in dieser Story; Backend-Auth (E48S07) ist die letzte Verteidigungslinie.
- [ ] **AC-GOVERNANCE-NO-BACKEND-CHANGES** (governance): diese Story modifiziert KEINEN Backend-Code; alle Endpoints kommen aus E48S07. File-Edits beschränkt auf `src/main/ui/src/**/*` + `App.svelte` route map + i18n files.
