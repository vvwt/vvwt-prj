# Story E51S11: L3 Refactor — SlotResultApplicator operates on L2-output (flat-index + rank-as-rowSequence-permutation)

## User Story

**As a** Tournament Operator,
**I want** the Slot-Optimization (L3) to optimize the Spielzeit-Verteilung over the schedule produced by L2 — without re-doing the round-assignment that L2 already computed,
**so that** L3 produces consistent results for any Spielart (not RoundRobin-only), aligns with the existing `VarietyScorer` rowSequence model, and respects the operator's `tournament.fieldCount` setting.

---

## Context

**Architecture (Brief D-1 + D-2 + Approach-Evaluation Option 3):** the existing `SlotResultApplicator` (`vvwt-tm-web/src/main/java/de/vvwt/tm/slotopt/SlotResultApplicator.java:92-153`) interprets the optimizer's `long rank` as an **avatar-permutation** + uses `buildCanonicalRoundSchedule` (circle-method, RoundRobin-specific) to derive `lapNumber` per match — and `assignedField = position-within-round` ignoring `fieldCount`. This is BOTH (a) RoundRobin-fixated and (b) inconsistent with `VarietyScorer.score(int[] rowSequence, CanonicalPhaseDef phaseDef)` (`vvwt-slotopt-worker-lib/.../VarietyScorer.java:85`) which ALREADY uses a row-permutation model.

**Refactor scope (Brief D-2 + D-7 + S-3):** SlotResultApplicator is rewritten to operate on L2-output:
- Optimizer's `rank` is interpreted as a **row-permutation** via `LehmerCodec.rankToPermutation(rank, lapCount)` — parameterized over `[0, lapCount!)` instead of `[0, rowCount!)` (Brief D-7). The result is a permutation π over `[0, lapCount-1]`.
- Per Brief D-7: the rowSequence is the concatenation `[π(0)*fc, π(0)*fc+1, ..., π(0)*fc+fc-1, π(1)*fc, ..., π(lapCount-1)*fc+fc-1]` where `fc = fieldCount`. **L3 search-space is restricted to lap-permutations only** (re-orderet whole laps; intra-lap row-positions stay).
- `SlotResultApplicator` writes for each row at index `i` in the rowSequence: `match.setLapNumber(i / fieldCount)` and `match.setFieldNumber(i % fieldCount)`. Since intra-lap positions are preserved by D-7's lap-permutation, `match.fieldNumber` is invariant under the permutation — only `lapNumber` changes.
- `buildCanonicalRoundSchedule` and the avatar-permutation-circle-method path are REMOVED from `SlotResultApplicator`.

**DEC-49 D-3 N-redefinition (Brief D-4):** N is now `lapCount` (not `rowCount/matchCount`). The `tm.slotopt.exhaustive-max-n=10` threshold is held against `lapCount` for routing-rule (Direct vs Dispatcher vs Cancelable). For 12 teams + 3 fields + 1 group: lapCount=22 → exceeds threshold → Leg 2/3.

**Per-group L3 invocation (NF-MED-1 from Tier-2 cycle-2):** L3 runs per group (each group's MappingResult passed to RoutingSlotOptimizationClient.optimize separately). lap-permutation search space is `[0, lapCount_g!)` per group g.

**`vvwt-worker-lib` ABI unchanged:** `CanonicalPhaseDef` record, `RawPhaseDef`, `RawRow`, `TransformResult`, `LehmerCodec` API all unchanged. Only the consumer (SlotResultApplicator) reinterprets the rank semantic and the n parameter.

**Refereeassigner-Korrektheits-Invariante (Brief O-21):** `match.refereeTeamId` is a Match-entity column persisted by `RefereeAssigner.assignReferees` (line 216-217). The lap-grouping at `RefereeAssigner.java:153-156` is transient. lap-permutation that preserves per-lap team-membership (D-7 invariant) preserves Schiri-Zuordnung. → L3 running AFTER assignReferees does NOT invalidate referee assignments.

This story is the L3 layer of the Layered Decomposition.

## Acceptance Criteria

- [ ] **AC-TEST-RANK-AS-LAP-PERMUTATION-RED** (testing): RED-first IT — given fieldCount=3, lapCount=4 (12 matches in 4 laps × 3 fields), L3's optimizer returns `rank=0` (identity); `SlotResultApplicator.applyResult` writes match-0 lap=0/field=0, match-1 lap=0/field=1, ..., match-11 lap=3/field=2. Identity-permutation = L2 baseline preserved. Test fails before fix because current applicator computes lap via circle-method on avatarCount.
- [ ] **AC-TEST-NON-IDENTITY-RANK-PERMUTES-LAPS-RED** (testing): RED-first IT — given lapCount=4 and `rank=1` (Lehmer-code for [0,1,3,2] or analogous), the resulting matches in the output have lap-values matching the lap-permutation (e.g., lap 0,1 stay; lap 2 ↔ 3 swapped); fieldNumber-values stay identical to L2. Test fails before fix.
- [ ] **AC-TEST-FIELD-INVARIANT-UNDER-LAP-PERMUTATION-RED** (testing): RED-first IT — for any rank, every match's `fieldNumber` after L3 equals its fieldNumber from L2-baseline. (D-7 invariant proof.) Test fails before fix because old applicator writes `fieldNumber = position-within-round` ignoring fieldCount.
- [ ] **AC-TEST-ROUND-CONFLICT-FREEDOM-AFTER-L3-RED** (testing): RED-first IT — for any rank, no team plays >1 match per lap after L3 (constraint preserved through the lap-permutation). Test asserts via SQL aggregation.
- [ ] **AC-TEST-DEC-49-N-EQUALS-LAPCOUNT-RED** (testing): RED-first IT — `RoutingSlotOptimizationClient.optimize(phaseId)` resolves N as `lapCount` (NOT `rowCount`). For 12 teams + 3 fields = lapCount=22 → routing rule selects Leg 2 or Leg 3 (exceeds `tm.slotopt.exhaustive-max-n=10`). Test fails before fix.
- [ ] **AC-TEST-EXHAUSTIVE-LEG-1-WHEN-LAPCOUNT-LE-THRESHOLD-RED** (testing): RED-first IT — for a small phase with lapCount=8 (e.g., 4 teams + 3 fields = 6 matches in 2 laps... etc.), routing rule selects Leg 1 (DirectSlotOptimizationClient exhaustive). Test fails before fix only if N-redefinition not applied.
- [ ] **AC-TEST-PER-GROUP-INVOKE-RED** (testing, NF-MED-1): RED-first IT — given a phase with 2 groups, RoutingSlotOptimizationClient invokes the optimizer separately per group (2 invocations). Each invocation's lapCount = lap count for THAT group only. Test fails before fix if current applicator runs once across all phase avatars.
- [ ] **AC-TEST-CANCELABLE-BEST-SO-FAR-ON-L2-DEFAULT-RED** (testing): RED-first IT — when `CancelableInProcessSlotOptimizationService` is cancelled before any rank is evaluated, the Best-So-Far applied is the L2-baseline (rank=0 / identity-permutation), NOT trivial-coordinates-from-FallbackSlotOptimizationClient. Per DEC-49 D-11a "trivial coordinates (lap 0, sequential field)" is a cancel-before-permutation fallback; L2's deterministic baseline is the new "trivial". Test fails before fix.
- [ ] **AC-TEST-OPTIMIZE-FALSE-SKIPS-L3-RED** (testing): RED-first IT — given `tournament.optimize=false`, L3 is NOT invoked after L2 completes. Matches retain L2's lap+field. `phase.last_job_state` stays `'idle'` (no slot-opt scheduled). DEC-55 D-5 amendment by DEC-56 (Story 12) supports this.
- [ ] **AC-TEST-VARIETY-SCORER-INTEGRATION-PRESERVED-RED** (testing): RED-first IT — `VarietyScorer.score(rowSequence, phaseDef)` continues to work (call signature unchanged); the rowSequence parameter is now interpreted as a flat-row-ordering matching L2's layout. Test verifies a known input gives expected score.
- [ ] **AC-IMPL-CIRCLE-METHOD-REMOVED** (governance): `SlotResultApplicator.buildCanonicalRoundSchedule` and the avatar-permutation-circle-method derivation REMOVED. `LehmerCodec.rankToPermutation(rank, n)` is invoked with `n = lapCount` (not `avatarCount`).

## Notes

- **Estimated LOC:** ~250-350 LOC + ~200 LOC tests. Surface: `SlotResultApplicator.java` (large refactor); `DirectSlotOptimizationClient.java` (N-resolution); `RoutingSlotOptimizationClient.java` (per-group iteration per NF-MED-1); `FallbackSlotOptimizationClient.java` (alignment with L2-baseline-as-Best-So-Far); tests.
- **Severity:** HIGH — required for L3 to function consistently in the new architecture; without this, L3 either bypasses L2 (current Bug-1.5 path) or is disabled.
- **Performance:** `LehmerCodec` operations are O(N) per rank; for lapCount up to ~30 (large tournaments), well within Direct-Leg exhaustive bounds when `exhaustive-max-n` is configured high. Default 10 sends most real phases to Leg 2/3.
- **`vvwt-worker-lib` cache stability (Brief O-19):** `StructuralFingerprint.CANONICALIZATION_VERSION = 1` unchanged; `CanonicalPhaseDef` byte serialization unchanged; distributed worker-cache results stay valid (Option 3 explicit benefit per Approach-Evaluation C15).
