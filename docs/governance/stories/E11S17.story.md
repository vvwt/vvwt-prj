# Story E11S17: Fix — Timer audio replays spuriously after WebSocket LAP_ADVANCED / PHASE_CHANGED / reconnect events because the audioEngineJustStarted invariant is not maintained across WS-driven state changes

## User Story

**As a** tournament organizer using the Timer SPA on a venue device whose browser intermittently triggers WebSocket reconnects (operator-confirmed on 32-bit Linux Chromium; suspected on any device that throttles WebSocket connections in background or fires reconnects on focus / visibility events),
**I want** schedule-event audio (round-start sound, round-end sound, pause-music start) to fire exactly once per real schedule transition,
**so that** the operator doesn't hear sounds replayed at random moments — operator reported on 2026-05-29 hearing the start-sound a second time about a minute after the genuine start, the pause-music re-starting after it had already ended, and the start-sound replaying ~6.5 minutes into round 8.

---

## Context

Operator reported intermittent spurious audio replays on a 32-bit Linux Chromium device. Three concrete instances on 2026-05-29:

1. Hallenzeit set inside the pause after round 3 (10:37). Pause music correctly skipped (E11S13 init-suppress in effect). Start-sound fired (correct — round 4 starts). About 1 minute into round 4, the start-sound fired AGAIN. Operator was interacting with the browser at this moment.
2. In the next pause, the pause-music fired a second time after its first playback had ended. The replay was cut off by the next round's start-sound (correct deactivate).
3. In round 8, ~6.5 minutes after the round started, the start-sound fired a second time. Operator was interacting with the browser at this moment.

Operator could not reproduce the symptom on another device. The affected device runs 32-bit Linux Chromium. Two of three instances coincided with operator browser interaction.

**Code-side audit identifies a clear bug source** (verified at `vvwt-tm-web/src/main/ui-timer/src/App.svelte`):

The audio-fire onTick at line 463 fires audio whenever `activeEventIndex !== lastFiredActiveIndex && activeEventIndex !== -1`. E11S10 introduced an init-suppress invariant via the `audioEngineJustStarted` flag: whenever `lastFiredActiveIndex` and `lastPlayingIndex` are reset to `-1` (the "uninitialized" sentinel), `audioEngineJustStarted` MUST also be set to `true` so the very next `onTick` records the current snapshot indices into `lastFiredActiveIndex` / `lastPlayingIndex` WITHOUT firing audio, then proceeds normally from the second tick.

**This invariant is broken in `handleWsLapAdvanced` (App.svelte:355-361):**

```ts
async function handleWsLapAdvanced(): Promise<void> {
    if (appState !== 'loaded') return;
    await loadTimerDataSilent();
    // Reset audio event tracking so events fire again from the new position
    lastFiredActiveIndex = -1;
    lastPlayingIndex = -1;
}
```

After WS LAP_ADVANCED:
1. `loadTimerDataSilent` reloads `timerData`; `snapshot.activeEventIndex` likely refers to a NEW upcoming event after the lap advance.
2. The handler resets `lastFiredActiveIndex = -1` and `lastPlayingIndex = -1` BUT does NOT set `audioEngineJustStarted = true`.
3. The next `onTick` (within 250 ms) skips the init-suppress branch at line 453 (`audioEngineJustStarted` is `false`), reaches the audio-fire gate at line 463: `activeEventIndex(new) !== lastFiredActiveIndex(-1) && activeEventIndex !== -1` → BOTH TRUE.
4. The deactivate side at line 466 is guarded by `lastPlayingIndex(-1) !== -1` → skipped (correct, but only by accident — see AC2 elaboration).
5. The activate side at line 482 reads `entry = effectiveSchedule()[playingIndex]`. If a ROUND is playing, fires `audioEngine.play('START')`. If a REGULAR-BREAK is playing, fires `audioEngine.play('PAUSE')`. **This is the spurious replay the operator hears.**

`handleWsReconnected` (App.svelte:383-388) and `handleWsPhaseChanged` (App.svelte:367-370) similarly call `loadTimerDataSilent` without re-establishing the init-suppress invariant. They do NOT reset the indices, but `loadTimerDataSilent` can shift `snapshot.activeEventIndex` (because `effectiveSchedule()` is recomputed on the fresh `timerData`). If the post-reload snapshot's `activeEventIndex` differs from the pre-reload `lastFiredActiveIndex`, the next `onTick` fires audio for the new `playingIndex` entry — a second spurious source.

The browser-interaction correlation hint is consistent with WebSocket reconnects firing on browser tab focus / visibility events — common when 32-bit Linux Chromium throttles WebSocket connections in background.

**Hypothesis on 32-bit Chromium specifics (UNVERIFIED — Delivery diagnostic):** The bug class identified above is environment-independent — any device that triggers WS reconnects more often would experience the symptom more often. The 32-bit Linux Chromium specificity may simply reflect that this device's tab-throttling behavior fires reconnects more aggressively. AC5 directs Delivery to confirm whether the WS-handler fix alone resolves the operator's symptom on the affected device, or whether an additional component (e.g., E11S15 audio-queue interaction with browser-specific `ended` event behavior) contributes.

Discovery Session Brief `discovery-2026-05-29-timer-ws-event-audio-replay` (compact diagnosis brief; operator-validated 2026-05-29 with three operator-reported instances + code-side root-cause walk).

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach is Delivery's choice within the bounds set by the Brief.

### Audio invariant correctness

- [ ] **AC1 — Schedule-event audio fires exactly once per real schedule transition.** A real schedule transition is a tick in which `snapshot.activeEventIndex` changes from one valid index to a DIFFERENT valid index AND the operator has not separately invoked transport state changes (PAUSE / STOP). A WS-driven `loadTimerDataSilent` that reloads the same conceptual schedule (no new lap advance, no phase change) does NOT count as a real schedule transition and MUST NOT fire audio.
- [ ] **AC2 — `audioEngineJustStarted` invariant maintained across all WS handler paths.** Whenever the audio-fire tracking state (`lastFiredActiveIndex`, `lastPlayingIndex`) is reset to `-1` (uninitialized sentinel), or whenever `loadTimerDataSilent` is invoked (because the post-reload `snapshot.activeEventIndex` may differ from the pre-reload value even without an explicit reset), the `audioEngineJustStarted` flag is set to `true` so the next `onTick` re-synchronises the indices without firing audio. Specifically `handleWsLapAdvanced`, `handleWsPhaseChanged`, `handleWsReconnected` (and the `loadTimerDataSilent` body they delegate to) MUST re-establish the invariant before the next tick. Delivery picks the specific call-site placement (set the flag inside `loadTimerDataSilent`, or in each handler after the await — either is acceptable provided the invariant holds for every WS-driven path).
- [ ] **AC3 — Browser focus / visibility / WS-reconnect events do NOT cause spurious audio.** When the browser tab regains focus, when the WebSocket disconnects and reconnects (triggered by browser background-throttle or any other transport-layer event), no audio fires for entries that have already been fired-and-tracked in the pre-event session state. The first tick after the reconnect re-synchronises the audio-fire tracking via AC2.
- [ ] **AC4 — Existing per-real-event audio behavior preserved.** On a real lap advance (WS LAP_ADVANCED that genuinely advances `currentLapNumber`), the audio for the newly-active ROUND or BREAK still fires once. On a real phase change (WS PHASE_CHANGED that genuinely transitions a phase), the audio for the newly-active entry still fires once. AC1's "real schedule transition" semantic is preserved.

### Diagnostic + 32-bit Chromium investigation

- [ ] **AC5 — Delivery confirms whether the WS-handler fix resolves the operator's symptom on the affected device.** After AC2 / AC3 land, Delivery (or operator-assisted Delivery investigation) confirms via empirical observation on the 32-bit Linux Chromium device whether the spurious audio replays disappear. Two outcomes are acceptable:
  - **(a)** the symptom is resolved by the WS-handler fix alone — impl-report attests "no further investigation needed; root cause was the WS-handler init-suppress invariant violation."
  - **(b)** residual symptoms persist (e.g., audio still replays at random intervals on browser interaction even without WS reconnects) — impl-report attests the residual class of symptom and escalates a follow-up Discovery for whatever component (e.g., E11S15 audio-queue `ended` event handling on 32-bit Chromium; HTMLAudioElement.play() promise-rejection retry on browser-specific timing) needs further investigation. The follow-up does NOT need to be implemented in this Story.
- [ ] **AC6 — E11S15 audio-queue compatibility preserved.** Whatever fix Delivery applies to AC2 / AC3 does NOT change `AudioEngine.play()` queue semantics, the `stopAll` / `stopPauseMusic` / `pauseAll` semantics, or the queue-drain on `ended` event. E11S15 is preserved unchanged. The fix lives in `App.svelte` `handleWs*` handlers and possibly in `loadTimerDataSilent`, NOT in `audioEngine.ts`.

### Error-handling (mandatory category)

- [ ] **AC7 — WS disconnect during audio playback.** When the WebSocket disconnects while an audio element is currently playing (currently-playing sound is in the middle of START / END / PAUSE_MUSIC), the playback continues uninterrupted (E11S05 AC4 carryover: local countdown continues, audio engine state unchanged on disconnect). On reconnect, AC3 ensures no spurious re-fire.
- [ ] **AC8 — Idempotent loadTimerDataSilent.** If `loadTimerDataSilent` is invoked multiple times in rapid succession (e.g., LAP_ADVANCED + reconnect arriving back-to-back), the audio-fire tracking re-synchronises correctly on each invocation. No accumulated index drift, no audio that should have fired silenced, no audio that should have stayed silent fired.
- [ ] **AC9 — STOP transport guards the fix.** When the operator presses transport STOP, the existing reset path (App.svelte:546-548 — `lastFiredActiveIndex = -1; lastPlayingIndex = -1; audioEngineJustStarted = false;`) is preserved. STOP does not need to re-set `audioEngineJustStarted = true` because the engine returns to STOPPED state and `onTick` early-returns; the invariant is naturally satisfied. Regression guard.

## Notes

**Track:** `bug-triage` MEDIUM. Operator-reported on one device; intermittent (3 instances over a day on 32-bit Linux Chromium); not a 100%-block but a correctness regression that may surface on any device that triggers WS reconnects in background.

**Root cause (verified, App.svelte HEAD post-E11S15 PR merged):**

- `handleWsLapAdvanced` at lines 355-361 resets `lastFiredActiveIndex = -1` and `lastPlayingIndex = -1` but does NOT set `audioEngineJustStarted = true`. The next `onTick` skips the init-suppress branch (line 453) and reaches the audio-fire gate at line 463: `activeEventIndex !== lastFiredActiveIndex(-1) && activeEventIndex !== -1` → fires audio for the current playingIndex entry — spurious replay.
- `handleWsReconnected` at lines 383-388 calls `loadTimerDataSilent` without resetting indices, but `loadTimerDataSilent` reloads `timerData` and `effectiveSchedule()` is recomputed. If the post-reload snapshot's `activeEventIndex` differs from the stale `lastFiredActiveIndex`, the next tick fires spurious audio.
- `handleWsPhaseChanged` at lines 367-370 has the same shape.
- Verified the invariant IS correctly maintained at:
  - App.svelte:283-285 (initial load via `handleClockSyncConfirm`): reset all three, including `audioEngineJustStarted = true`.
  - App.svelte:521-523 (`handlePlay` after PAUSE / STOP): reset all three.
  - App.svelte:454-457 (`onTick` init-suppress branch consumes the flag).

**Recommended fix shape (Discovery; Delivery may pick differently per AC2):**

One direct fix: inside `loadTimerDataSilent` (App.svelte:395-410), after `timerData = data;` and the ephemeral-state resets, add:
```ts
lastFiredActiveIndex = -1;
lastPlayingIndex = -1;
audioEngineJustStarted = true;
```
This re-establishes the invariant for EVERY caller of `loadTimerDataSilent` (handleWsLapAdvanced, handleWsPhaseChanged, handleWsReconnected). Delivery may instead place the invariant maintenance at each call site individually; AC2 asserts the behavioural outcome.

**Diagnostic note for 32-bit Linux Chromium hypothesis (AC5):** The bug class is environment-independent; the 32-bit Chromium specificity may reflect that this device's background-throttle / focus-driven reconnect cadence is more aggressive. After AC2 / AC3 land, Delivery confirms via empirical observation on the device. If residual symptoms persist (audio replays without WS-event correlation), the residual class is escalated as a follow-up Story (e.g., E11S15 queue `ended`-event timing on 32-bit Chromium; HTMLAudioElement.play() promise resolution semantics).
