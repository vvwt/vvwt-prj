# Story E53S04: Fix: PrintControllerIT post-E53-merge regression — restore mvn verify GREEN on staging (tearDown FK ordering + comment-leak-resilient assertions in 2 E53S03 tests + refereeing-row team-pair rendering)

## User Story

**As a** developer running `mvn clean install` (NetBeans Clean & Build) on `vvwt-tm-web` against staging HEAD,
**I want** the build to pass without test failures or errors in `PrintControllerIT`,
**so that** local Clean & Build is a trustworthy regression signal again and the CI gate (DEC-54 `mvn verify`) reflects merged-on-staging quality.

---

## Context

User reported on 2026-05-09 that NetBeans "Clean and Build" of `vvwt-tm-web` fails. Empirical reproduction on staging HEAD (`vvwt-prj` commit `36bf620`) confirmed: `mvn clean install` fails in failsafe phase with **5 Failures + 13 Errors + 4 Skipped** out of 631 tests — all in `de.vvwt.tm.web.PrintControllerIT`.

The three E53 stories (E53S01 Mustache→HTML comment refactor, E53S02 Laufzettel content semantics + ACTIVE-only filter, E53S03 print-index gate + /fotos fix + photo-schedule first-phase filter) are all `status: done` and merged on staging today (2026-05-09; PRs #237, #238, #239). Each PR passed `mvn verify` individually. The current failure is a **post-merge interaction regression on staging HEAD**, not a per-PR defect.

### Three coexisting defects (verified empirically 2026-05-09)

**Bug 1 — Test infrastructure: `tearDown` does not delete `activity_types` rows.**
`PrintControllerIT.java:96-105` deletes `match`, `team_avatar`, `phase`, `team`, `tournament`, `locations` but does NOT delete `activity_types`. New E53S03 photo-type tests (e.g. `seedTournamentWithPhotoActivityType()`) insert into `activity_types` with FK `FK_ACTIVITY_TYPES_TOURNAMENT` referencing `tournament(id)`. When the next test's `tearDown` runs `DELETE FROM tournament`, the FK blocks the delete with `DataIntegrityViolation`. This produces all 13 `tearDown:102` errors and corrupts test state for every test that runs after a photo-type test in the same JVM, manifesting as `EmptyResultDataAccess Incorrect result size: expected 1, actual 0` in subsequent setup helpers (e.g., `getTeamId:848` in `singleTeamSchedule_playingRow_containsVsOpponentContext`).

**Bug 2 — Test assertions in 2 E53S03 tests are too broad after E53S01's HTML-comment refactor.**
E53S01 replaced multi-line `{{!...}}` Mustache comments with HTML comments in `templates/print/index.mustache`. The HTML comment header at line 19 contains the literal text `URL to /activity-schedule/{photoTypeId}` and similar references for `/team-schedules`. These now appear in the rendered HTML body. Two E53S03 tests use body-substring matching that now hits the comment text instead of the actual `<a href>`:

- `printIndex_noPhotoActivityType_fotosLinkAbsent` (line 1093): asserts `not to contain "/activity-schedule/"` — matches the comment text.
- `printIndex_withPhotoActivityType_fotosLinkResolvesTo200` (line 971): URL extraction at lines 957-972 walks `body.indexOf("/activity-schedule/")` then `lastIndexOf("href=\"", actStart)`. The first `/activity-schedule/` occurrence is now in the comment header where there is no preceding `href="`, so `lastIndexOf` returns -1 → `+ 6` → `substring(5, ...)` produces a garbage substring like ` print/index.mustache — Tournament print index page (...)`. `URI.create(baseUrl + garbage)` throws `URISyntaxException: Illegal character in authority at index 22`.

A third assertion shape (`not to contain "/team-schedules"` in a different scenario) is affected by the same root cause if the comment-text contains `team-schedules`.

**Bug 3 — Refereeing-row teamA/teamB are not populated in the rendered Laufzettel output.**
`singleTeamSchedule_refereeingRow_containsBothMatchTeams` (line 344) — verified by isolated single-test run — fails identically with rendered output `Schiedsrichter:  vs ` (both team names empty). Expected: `Schiedsrichter: <Mannschaft 01> vs <Mannschaft 02>` (or equivalent). E53S02's Brief explicitly identified this case and prescribed a `LaufzettelRow` VO extension; either the extension was incomplete in E53S02's deliverable or a subsequent merge (E51S11 `SlotResultApplicator` refactor / E51S16 Modulith-cycle break + missing E51S11 ITs) regressed the data path between `RefereeAssigner` output and the rendered template. Discovery does not pre-judge which path is broken — Delivery investigates.

A cosmetic side-observation (`<thead>` skips time column when `hasTime=false` but `<tbody>` still emits an empty `<td class="laufzettel-col-time">`) is OUT-OF-SCOPE for this Story unless Delivery's investigation of Bug 3 reveals a shared root cause.

### Why ONE Story (not three)

- All symptoms surface in `PrintControllerIT` and block the same closure gate (`mvn verify` GREEN).
- Bug 1 corrupts test state — Bugs 2 and 3 cannot be reliably verified in isolation until Bug 1 is fixed first. Sequential dependency forces in-Story ordering.
- Per `discovery.agent.md` Bug Triage flow, Discovery defines WHAT to fix, not HOW; consolidating WHAT-statements that share a closure gate is more cost-effective than three serial Stories that each spin up Delivery overhead.

### Why a new Story (not amend E53S01/S02/S03)

- E53S01/S02/S03 are `status: done` and merged. The lifecycle does not permit `done → in_progress` (per base.rules.md § Backlog State Lifecycle).
- Bug-triage post-merge regression is its own scope and warrants its own provenance, RED-first commits, and qa-report.

## Acceptance Criteria

### Test Infrastructure (Bug 1)

- [ ] **AC-TEST-TEARDOWN-FK-ORDERING-RED**: A RED-first integration test (or seeding helper assertion) demonstrates that, given a test that inserts a row into `activity_types` and a subsequent `tearDown` invocation, the cleanup completes without `DataIntegrityViolation`. The test must initially FAIL on staging HEAD (proving RED), then PASS after the fix (proving GREEN). DEC-22 Iron Law applies — Delivery authors RED first.
- [ ] **AC-TEST-TEARDOWN-FK-COMPLETENESS**: After the fix, running the full `PrintControllerIT` test class (all `@Test` methods, in any JUnit-default order) completes with zero `DataIntegrityViolation` in any `@AfterEach` invocation.
- [ ] **AC-TEST-TEARDOWN-FK-FUTURE-PROOF**: The fix must not be a one-line "delete activity_types too" patch that reproduces the same defect-shape next time a new FK-bound table is added. Acceptable shapes include (Delivery's choice; non-exhaustive): (a) FK-aware ordered delete with a comment enumerating the FK chain referencing `tournament`; (b) helper utility that reads schema metadata; (c) `@Transactional`-rollback-based test isolation. Discovery does not prescribe shape.

### Test Assertions (Bug 2)

- [ ] **AC-TEST-ASSERTION-COMMENT-LEAK-RESILIENT-RED**: A RED-first test fixture demonstrates that assertions about the presence/absence of link URLs (`/activity-schedule/`, `/team-schedules`, `/fotos`) in the rendered HTML must NOT be matched by literal occurrences of those URL fragments inside HTML comments (`<!-- ... -->`). RED first on staging HEAD, GREEN after fix.
- [ ] **AC-TEST-ASSERTION-FOTOS-LINK-EXTRACTION**: After the fix, `printIndex_withPhotoActivityType_fotosLinkResolvesTo200` extracts the photo-link href from an actual `<a href>` element (not from any body substring) and the extracted URL successfully resolves to HTTP 200.
- [ ] **AC-TEST-ASSERTION-FOTOS-LINK-ABSENCE**: After the fix, `printIndex_noPhotoActivityType_fotosLinkAbsent` correctly asserts the absence of an actual `<a href>` link to `/activity-schedule/` (not the absence of the substring `/activity-schedule/` anywhere in the body).
- [ ] **AC-TEST-ASSERTION-TEAM-SCHEDULES-CONSISTENCY**: Any other PrintControllerIT assertion that today checks `body.contains("/team-schedules")` or `not to contain "/team-schedules"` must apply the same anchor-at-actual-link discipline. **Closure criterion:** Delivery's qa-report MUST enumerate every `body.contains(...)` / `body.toLowerCase().contains(...)` / `not to contain (...)` / `assertThat(body).contains(...)` assertion in `PrintControllerIT` against URL fragments (`/print/`, `/team-schedules`, `/activity-schedule/`, `/fotos`) and classify each as one of: (a) anchor-fixed by this Story, (b) verified already-anchored at actual rendered element pre-this-Story, or (c) confirmed N/A (asserts something other than a link). The qa-report list is the closure evidence — a one-line "I surveyed; no others found" is insufficient.

### Refereeing Row Content (Bug 3)

- [ ] **AC-CONTENT-REFEREEING-ROW-TEAM-PAIR-RED**: `singleTeamSchedule_refereeingRow_containsBothMatchTeams` is RED on staging HEAD (verified by Discovery 2026-05-09) — Delivery confirms RED reproduction before any code change, then makes it GREEN. Expected behaviour: when a Laufzettel row represents a refereeing assignment (the team this Laufzettel is for is the referee for a match between two OTHER teams), the rendered `Aktivität` cell contains BOTH match-team names (e.g., `Schiedsrichter: <TeamA> vs <TeamB>`), with non-empty `<TeamA>` and `<TeamB>`. **Trivial-pass guard:** the test seed MUST use two distinct deterministic team names (e.g., `TestTeamReferee-A` and `TestTeamReferee-B`); the assertion MUST verify both seeded names appear in the rendered cell text in the team-pair-context shape — not merely "non-empty". This prevents a fixture that hard-codes the literal names alongside a permissive renderer from passing the AC without proving the data path from `RefereeAssigner` → renderer is correctly wired.
- [ ] **AC-CONTENT-REFEREEING-ROW-NO-REGRESSION-PLAYING**: `singleTeamSchedule_playingRow_containsVsOpponentContext` (the sibling playing-row test that today errors due to Bug 1's cascade) becomes GREEN with no change to its assertion shape (the playing-row case is not in scope of behaviour change — only the refereeing-row case).
