# Story: Fix — certificate date renders in English/ROOT format on the jlink-produced production runtime despite `Locale.GERMAN`; add `jdk.localedata` to the `vvwt-tm-web` jlink module list

## User Story

**As a** tournament organizer on a German-locale tenant who runs the
production `tournament-manager` jlink fat-JAR distribution,
**I want** the certificate's date field to render in the German long form
("30. Mai 2026") as it already does on my developer machine running
`mvn`-launched TM,
**so that** I can print and hand out Urkunden without the date silently
falling back to the ROOT/English form ("2026 May 30") on the very runtime
artefact my participants receive.

---

## Context

The production deployment runs the jlink-bundled custom JRE produced by
`vvwt-tm-web/pom.xml` (per DEC-15: jlink fat-JAR is the primary V1
distribution). On that runtime the certificate date renders as `2026 May 30`
even though:
- the operator's OS region is set to German (GNOME Region & Language —
  Sprache: Deutsch / Formate: Deutschland);
- the per-tenant `tenants.language='de'` is set;
- the operator already pinned the HTML-row formatter to `Locale.GERMAN`
  directly in `DefaultCertificateAssembler.buildHtmlRows()`
  (`vvwt-tm-web/src/main/java/de/vvwt/tm/certificate/internal/DefaultCertificateAssembler.java:277`);
- the formatter is `DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG)
  .withLocale(locale)` (lines 487–489).

On the developer machine (Maven via NetBeans, full JDK 21) the same code
correctly renders `30. Mai 2026`. The symptom appears **only** on the
jlink-produced runtime. Setting `Locale.GERMAN` in Java has no effect on
that runtime because the JDK CLDR locale data simply is not present in the
linked image.

This story is `track: bug-triage` per the Discovery Bug-Triage Flow in
`.gaai/core/agents/discovery.agent.md`. Per DEC-67 Clause 1, the change
authors no first-party code — it is a pure build-descriptor-coordinate
change (`--add-modules` argument in the `exec-maven-plugin` jlink
invocation). DEC-22's Iron Law is not invoked; the verification surface is
DEC-67 Clause 2 (existing suite GREEN per DEC-54 + defect justification +
recommended GREEN-only regression guard).

---

## Root Cause Analysis

Single defect in `vvwt-prj/vvwt-tm-web/pom.xml:710` (the `<argument>` line
inside the `exec-maven-plugin` `create-runtime-image` execution that calls
`${java.home}/bin/jlink`):

```xml
<argument>java.base,java.compiler,java.desktop,java.instrument,java.net.http,java.prefs,java.rmi,java.scripting,java.security.jgss,java.sql.rowset,jdk.crypto.ec,jdk.jfr,jdk.management,jdk.net,jdk.unsupported</argument>
```

The module list does NOT include `jdk.localedata`.

**Upstream contract** — JDK 21 [`jdk.localedata`
module](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.localedata/module-summary.html):

> Provides locale data for locales other than US locale … The data
> includes CLDR data for non-US locales. Without this module, only the
> ROOT and en (US) locales are present.

**Empirical reproduction** (this Discovery session, JDK 21.0.11):

Same `T.java` (`LocalDate.of(2026,5,30).format(
DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(Locale.GERMAN))`)
executed against three runtimes:

| Runtime | Output |
|---|---|
| Full JDK 21.0.11 (`/usr/lib/jvm/.../java`) | `30. Mai 2026` |
| jlink image with current `pom.xml:710` module list (no `jdk.localedata`) | `2026 May 30` |
| Same jlink image + `jdk.localedata` added | `30. Mai 2026` |

The reviewer-proposed alternative — replacing the formatter with
`DateTimeFormatter.ofPattern("d. MMMM yyyy", Locale.GERMAN)` — was
empirically tested in the same harness and yields `30. May 2026` (English
month name) on a runtime without `jdk.localedata`: the `MMMM` symbol still
consults CLDR. Only a fully numeric pattern (`d. M. yyyy` → `30. 5. 2026`)
or a hand-rolled month-name array would avoid the CLDR dependency, both of
which (a) entail authoring first-party Java code (full DEC-22 RED-first
territory), (b) regress the `LocaleResolver` chain (DEC-5 multi-tenant —
each `tenant.language` would need its own hand-table), and (c) make
non-`de` tenant certificates wrong by a different mechanism.

A third alternative — adding a third-party CLDR-shim library
(e.g., `com.ibm.icu:icu4j`) as an independent CLDR provider — is also
rejected: (a) it introduces a runtime dependency that requires AGPL-3.0
compatibility verification per DEC-3 + DEC-75; (b) icu4j's JAR (≈14 MB)
is larger than the `jdk.localedata` module increment (≈10 MB) it would
replace; (c) the project's `DateTimeFormatter` calls would have to be
rewritten to consult the shim, regressing every locale-formatting call
site — a strictly larger change than the JDK-shipped solution; (d) the
JDK already ships the data, just not in our linked runtime. Adding a
library to compensate for an omitted JDK module is structurally
indirect. `jdk.localedata` remains the best-fit mechanism.

**Fix** — append `jdk.localedata` to the comma-separated module list on
`vvwt-tm-web/pom.xml:710` (the `<argument>` value following the
`<argument>--add-modules</argument>` line).

**Why it slipped past E02S05** — E02S05's `jdeps` analysis examined the
application's *compile-time* module dependencies. `jdk.localedata` is a
*run-time data* module the application does not statically import; it
contributes CLDR data the `DateTimeFormatter` consults via
`LocaleProviderAdapter`. `jdeps` does not surface that runtime dependency.

## Out of Scope

- **`DefaultCertificateAssembler.buildHtmlRows` Locale.GERMAN hardcode**
  — line 277 currently hardcodes `Locale teamLocale = Locale.GERMAN`
  for the HTML render path, while `buildSvgRows` uses the
  `LocaleResolver` chain. After this story's fix, HTML certificates will
  always be German regardless of tenant/tournament/team language, while
  SVG certificates correctly honour the chain. This inconsistency is a
  **separate** Java-code bug requiring DEC-22 RED-first treatment and is
  **out of scope** for this build-descriptor story. Tracked as a
  follow-up candidate; the operator surfaces it via a new
  `/gaai-discover` session if it becomes user-visible.
- **`DefaultCertificateAssembler.resolveLocaleForRow`** (currently
  always returns `Locale.GERMAN`, unused) — same domain as the previous
  item; cleanup deferred.
- **jlink launcher scripts** (`bin/tournament-manager`,
  `tournament-manager.bat`) — owned by DEC-68 + E55S15; not affected by
  the module-list change.
- **Docker secondary distribution** — DEC-15 secondary; the Dockerfile
  uses a full JDK base image and is not affected by the jlink module
  list; no change required there.
- **GraalVM native-image** — DEC-15 explicitly out of V1.
- **Any alternative date-format strategy** (hand-rolled month-name
  array, fully numeric pattern, JS-side formatting) — empirically
  evaluated in § Root Cause Analysis and rejected; not authored here.
- **Print-CSS layout bugs (Chromium content overflow + Firefox trailing
  empty page)** — separate bug-triage story E12S11; independent root
  causes, independent change surfaces.
- **`messages.properties` German label values** — already canonised by
  E46S03; not in scope.
