# Story E62S01: TM-domain → `TournamentSnapshot` builder + `de.vvwt.tm.infoportal` Modulith `allowedDependencies` expansion

## User Story

**As a** tournament operator whose tournament will be published to the Info-Portal,
**I want** the Tournament Manager to assemble a complete, correct snapshot of the
tournament's current state in the Info-Portal's contract format,
**so that** participants see accurate teams and schedule — and so that the publisher has
a snapshot to send on registration and on `409 FULL_RESYNC` recovery.

---

## Context

The TM-side publisher service (`InfoPortalPublisherService.postSnapshot(tournamentId,
snapshotJson)`) takes the snapshot as opaque JSON — there is **no TM-side builder** that
produces a `vvwt-info-dto.TournamentSnapshot` from TM domain data (verified: the TM has
zero `TeamEntry` / `TournamentSnapshot` construction sites; they are built only inside
`vvwt-info-server`). This story delivers that builder. It is the shared foundation for
E62S02 (initial snapshot on opt-in) and E62S03 (`409 FULL_RESYNC` resync).

The builder lives in the `de.vvwt.tm.infoportal` Modulith module, which today declares
`@ApplicationModule(allowedDependencies = {})` and therefore cannot read tournament data.
This story performs the boundary expansion the module's own `package-info.java`
anticipates: `allowedDependencies` becomes `{tournament, tournament::events}` per DEC-21
(`tournament::events` is declared as a separate `@NamedInterface` and needs its own entry
— the DEC-40 `tournament::exceptions` precedent; `tournament::events` is declared here so
E62S03's event listener has its edge ready).

The TM `Team` entity (`de.vvwt.tm.tournament.Team`) has `UUID id`, `int teamNumber`, and
`String description`; `vvwt-info-dto` `TeamEntry` is `record TeamEntry(String teamId,
String name, int number)`. `vvwt-info-dto`'s `ScheduleEntry` is a **polymorphic hierarchy**
(DEC-42 D1) — mapping TM schedule rows onto its discriminated subtypes is a delivery
decision point (AC3).

As the first story of the wiring epic, this story also re-confirms the existing publisher
service against current HEAD before the epic builds on it (AC9, Brief H-1).

This story authors no caller of the builder — E62S02 and E62S03 are the callers.

## Acceptance Criteria

- [ ] **AC1 (testing)**: Every new production class in this story (the snapshot-builder
  service and any helper) is authored RED-first per the DEC-22 Iron Law — a failing test
  precedes the implementation; the RED state is evidenced in `impl-report.md`.
- [ ] **AC2 (testing)**: Given a tournament with teams, the builder produces a
  `TournamentSnapshot` whose `teams` list maps each TM `Team` to a `TeamEntry` as
  `teamId = Team.id.toString()`, `number = Team.teamNumber`, `name = Team.description`.
  Verified by a test over a fixture tournament.
- [ ] **AC3 (testing)**: The builder populates the snapshot's `scheduleEntries` (the
  polymorphic `ScheduleEntry` subtypes — Match / SpecialAppointment / Pause) and the
  `tournamentEnded` flag per the `vvwt-info-dto.TournamentSnapshot` contract. The
  `TournamentSnapshot` contract carries `tournamentId`, `tenantId`, `sequenceNumber`,
  `scheduleEntries`, `teams`, `tournamentEnded` — it has **no finished-match-results
  field**; match scores/results are therefore not part of the snapshot (they flow only as
  `DomainEvent` deltas — E62S03 scope). The exact field set and the mapping of TM schedule
  rows onto the `ScheduleEntry` subtypes are re-confirmed against the live `vvwt-info-dto`
  snapshot DTOs at delivery HEAD — this story carries no hardcoded field inventory.
- [ ] **AC4 (error-handling)**: A tournament with no teams and/or an empty schedule yields
  a structurally valid `TournamentSnapshot` with empty collections — never a `null` field
  or a thrown exception.
- [ ] **AC5 (security)**: `TeamEntry.teamId` carries `Team.id.toString()` — the team UUID
  string the info-server uses as the input to its participant reader-token validation. A
  test pins the `teamId` string form so the published team identity stays consistent with
  the reader-token contract; the info-server's token-derivation algorithm itself is not
  re-implemented here (it lives in `vvwt-info-server`, out of scope per C-1).
- [ ] **AC6 (governance)**: `de.vvwt.tm.infoportal/package-info.java` `allowedDependencies`
  is expanded from `{}` to `{tournament, tournament::events}` (DEC-21);
  `ApplicationModules.verify()` passes (a declared edge that is not yet consumed by this
  story's builder — `tournament::events`, reserved for E62S03 — does not fail `verify()`);
  `mvn verify` invoked from the `vvwt-prj` root is BUILD SUCCESS (DEC-54).
- [ ] **AC7 (governance)**: The builder follows DEC-35 — a public service interface in the
  `de.vvwt.tm.infoportal` package, the implementation in `de.vvwt.tm.infoportal.internal`
  with the `Default*` naming canon. `vvwt-tm-web` depends only on `vvwt-info-dto` for the
  contract types (DEC-42 D2 — no `vvwt-info-server` dependency). If a new Repository/DAO
  read method is authored to reach team/schedule/result data, it follows DEC-26 + DEC-46
  (DAO-IT three rules) and DEC-69 (a production caller — the builder itself); reuse of an
  existing read method is preferred and audited for first.
- [ ] **AC8 (governance)**: Skill attestation per the Epic; governance artefacts
  propagated into `vvwt-prj/docs/governance/` per DEC-23 / DEC-31; committed to `staging`
  per DEC-13.
- [ ] **AC9 (governance)**: As the wiring epic's first story, re-confirm the existing
  publisher service `DefaultInfoPortalPublisherService` against current HEAD before the
  epic builds on it: its existing test suite runs green, and — where the `E38S10`
  qa-report is available in the working tree — its AC2/AC3/AC13 end-to-end verdict is
  read and recorded in `impl-report.md` (per Brief H-1, a green unit/integration suite
  alone is not equivalent to the end-to-end verdict). If this re-confirmation surfaces a
  genuine publisher-service defect, fixing it is an in-scope contingency under DEC-22

## Notes

- **Open question for delivery (Brief S-3 / reviewer N-1)**: the builder maps
  `TeamEntry.name ← Team.description` because the `Team` entity has no field literally
  named `name`. `description` is the entity's human-readable label. `TeamEntry.name` feeds
  an internet-public participant surface (DEC-42 D5). If, at delivery, `Team.description`
  is found to carry operator-internal label text rather than a participant-appropriate
  name, escalate to Discovery rather than publishing it verbatim.
- The `tournament::events` `allowedDependencies` entry is declared in this story even
  though this story's builder consumes only `tournament` root types — declaring it here
  means E62S03's event listener inherits a ready edge and `ApplicationModules.verify()`
  is exercised once for the full expansion. Spring Modulith `verify()` does not fail on a
  declared-but-not-yet-consumed dependency entry.
- `tournament::events` is a Spring Modulith `@NamedInterface` sub-package; a named
  interface needs its own `allowedDependencies` entry separate from the root `tournament`
  module (the DEC-40 `tournament::exceptions` precedent).
- The builder is reused by E62S02 (initial snapshot) and E62S03 (`409 FULL_RESYNC`
  resync) — it must be deterministic and side-effect-free (a pure read + map).
- The `vvwt-info-dto.TournamentSnapshot` contract carries no finished-match-results field;
  on a `409 FULL_RESYNC` the snapshot restores tournament structure (teams + schedule +
  tournament-ended) but not historical match scores — scores flow only as `DomainEvent`
  deltas, which are not replayed. This is a property of the E38 contract, not of this
  story; it is flagged as a possible E38 follow-up and is out of E62 scope.
