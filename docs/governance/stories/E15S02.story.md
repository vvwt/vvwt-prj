# Story E15S02: AdminCredentialsDao — reconstruction-in-place with TDD (H2 integration)

## User Story

**As a** maintainer of the `auth` context,
**I want** admin-credentials persistence isolated in a dedicated DAO with tests against a real H2 tenant DataSource,
**so that** orchestration code never sees SQL and concurrent-start race handling is verified against genuine database semantics.

---

## Context

The legacy `AdminCredentialsBootstrap` uses `JdbcTemplate` inline for SELECT-existing-or-INSERT-new logic, including a concurrent-start race-path where two JVM instances start simultaneously and both try to insert the first admin row. Under reconstruction-in-place (DEC-22), this persistence concern moves into its own `AdminCredentialsDao` class under `de.vvwt.tm.auth.internal`, tested against a real H2 DataSource obtained via the E14-delivered `TenantDataSourceResolver`.

Per DEC-22, the DAO is written test-first with real H2 integration — mocking `JdbcTemplate` would hide the race semantics and drop the test back to "we wrote what we thought it should do", undermining the Iron Law. Per DEC-20, the DAO operates against a tenant DataSource (obtained through the tenant context set up in the test), proving the `auth::tenant` dependency at the Dao layer.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows a failing integration test for `AdminCredentialsDao` (against H2) committed BEFORE the DAO implementation. Spot-check on each public method (`findExisting`, `insertNew`, or whatever names emerge) confirms red-then-green per DEC-22. Characterization tests are forbidden.

- [ ] AC2 (testing — real H2, no JdbcTemplate mock): The DAO's test suite uses a real H2 DataSource (in-memory or `@TempDir` file) via `TenantContext`/`TenantDataSourceResolver`. `JdbcTemplate` is NOT mocked. A test that mocks `JdbcTemplate` fails AC.

- [ ] AC3 (security — concurrent-start race path): A test explicitly exercises the race: two concurrent "insert first admin" attempts against the same empty table. One succeeds, the other catches the unique-constraint violation and re-queries. The final state is exactly one admin row; the concurrent re-querying path returns the existing row consistently. Per the Epic Success Metrics.

- [ ] AC4 (error-handling — transient DB failure): A test injects a transient JDBC failure (e.g., an H2 misconfiguration or a deliberately-corrupt schema state) and verifies the DAO surfaces a typed exception, does not silently retry indefinitely, and does not leave the tenant DB in a partially-written state.

- [ ] AC5 (error-handling — missing schema): If the DAO is invoked against a tenant whose DB has NOT had `db/migration/auth/V1__admin_credentials.sql` applied (E15S05 supplies this migration), the DAO fails fast with a message identifying the missing table — not a cryptic JDBC SQLException. A test asserts this.

- [ ] AC6 (security — hash storage contract): The DAO contract documents that it stores an already-hashed credential string (supplied by the caller — `AdminCredentialsBootstrap` in E15S03 uses Spring Security's `PasswordEncoder`). The DAO performs no hashing itself. A contract test confirms by passing a non-hash string and verifying the DAO stores it verbatim (without warning) — hashing is an orchestration concern.

- [ ] AC7 (governance — package placement): `AdminCredentialsDao` lives under `de.vvwt.tm.auth.internal`. No Spring-specific annotations beyond `@Repository` if Delivery chooses it; DAO does not expose itself via the root `de.vvwt.tm.auth` package.

- [ ] AC8 (testing — Modulith verify): `ApplicationModulesTest` remains green. If this story declares `@ApplicationModule` on `de.vvwt.tm.auth` (a Delivery choice; strictly `@ApplicationModule(allowedDependencies = {"tenant"})` is added in E15S06), the existing verify continues to pass.

- [ ] AC9 (governance — no legacy change): The legacy `de.vvwt.tm.auth.AdminCredentialsBootstrap` and any legacy persistence helpers are untouched. `git diff` shows only new files + tests under the new package. Legacy cutover is E15S07.

## Notes

AC3 — the concurrent-start race test — is the subtlest test in the whole E15 Pilot. Two strategies: (a) two explicit threads with a barrier, (b) a `@RepeatedTest` with carefully-sequenced operations. Either works; document the choice. The test should be deterministic, not flaky; if the implementation relies on H2's default isolation level behaviour, that too goes in the Dao's Javadoc.

AC5's "missing schema" test implicitly creates a sequencing dependency with E15S05 (Flyway migration creation). Delivery's execution plan must address the order: either E15S05 lands before E15S02's merge, or S02's test uses an inlined SQL fixture for schema setup as a scaffold, removed when S05 lands.
