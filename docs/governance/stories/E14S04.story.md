# Story E14S04: Per-tenant Flyway runner — tests first

## User Story

**As a** the `tenant` context responsible for onboarding a new tenant,
**I want** a Flyway runner that executes per-module migrations against the new tenant's H2 file in module-dependency order,
**so that** every tenant's DB is populated identically and new contexts (auth in E15, and future Wave-2 contexts) can ship their own `db/migration/{context}/V1__*.sql` without bootstrap changes.

---

## Context

DEC-20 specifies Flyway runs per tenant (not at application startup) using the per-module migration layout `src/main/resources/db/migration/{context}/V1__*.sql`, applied in Modulith's `ApplicationModule` dependency-tree order. DEC-21 provides `SpringModulithFlywayMigrationStrategy` to achieve the ordering.

This story implements the runner: given a tenant identifier, obtain its DataSource via `TenantDataSourceResolver`, invoke Flyway with the per-module location set, and verify success. The runner is invoked from E14S05 (default tenant bootstrap) and — in future Wave-2 work — from tenant lifecycle operations.

Per DEC-22 the runner is written test-first. Tests must exercise against real H2 files (not mocks) with test-only migration directories because Flyway's semantics (checksum validation, applied-migrations history table, idempotency) cannot be credibly tested against mocks.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows a failing test for the per-tenant Flyway runner's happy path before the runner class is introduced. Additional failing-test-first commits precede each error-path branch. Characterization tests are forbidden per DEC-22.

- [ ] AC2 (data-isolation — per-tenant application): A test creates two tenants (A, B), invokes the runner once per tenant with identical migrations, and asserts each tenant's H2 file contains the expected Flyway-managed schema AND that its `flyway_schema_history` table is local to that file. No shared history table across tenants.

- [ ] AC3 (governance — per-tenant runtime Flyway runner, NOT Modulith's boot-time strategy): The per-tenant Flyway runner is a custom component that consults `ApplicationModules.of(TournamentManagerApplication.class)` to derive the module dependency order at tenant-creation time, then invokes Flyway programmatically against the tenant-specific DataSource with `.locations(classpath:db/migration/{module1}, classpath:db/migration/{module2}, ...)` in dependency order. The runner does NOT use Spring Modulith's `SpringModulithFlywayMigrationStrategy` bean (that strategy is wired to boot-time auto-configuration and does not fit per-tenant runtime invocation). This distinction is documented in the class-level Javadoc of the runner and in the Delivery plan. Per DEC-21 semantics (module-dependency-ordered) are preserved; only the invocation mechanism differs.

- [ ] AC4 (error-handling — migration failure): A test with an intentionally broken migration (e.g., invalid SQL) asserts the runner surfaces the Flyway exception, does NOT partially commit, and leaves the tenant's `flyway_schema_history` consistent with the last successfully-applied migration. The tenant is NOT removed from the registry on migration failure — cleanup is a lifecycle concern, not a runner concern.

- [ ] AC5 (error-handling — re-run idempotency): Invoking the runner twice on an already-migrated tenant DB is a no-op (Flyway's default idempotency). A test confirms this: run, snapshot history, re-run, snapshot again, assert identical.

- [ ] AC6 (error-handling — unknown tenant): If the runner is invoked for an unregistered tenant identifier, it fails fast with a typed exception surfaced from `TenantDataSourceResolver` — it does not create a DB file on the fly.

- [ ] AC7 (governance — no post-hoc tenant::api widening): The runner consumes `TenantRegistryPort` and `TenantDataSourceResolver` EXACTLY as defined in E14S01. If the runner requires additional capability not covered by E14S01's interfaces, E14S01 is amended via a refine-scope pass (Discovery decision, adds AC + Javadoc to E14S01) — NOT introduced as an ad-hoc "facade" here. The Delivery plan attests "runner uses only E14S01-defined interfaces" with a method-by-method trace.

- [ ] AC8 (governance — migration directory convention): The runner's Flyway configuration explicitly uses `classpath:db/migration/{module}` per DEC-21. A deliberate test places a migration at the legacy root location `db/migration/V99__*.sql` and confirms the runner does NOT apply it (proves legacy-layout migrations are inert under the new runner). This is the precondition for E15S07's deletion of V1..V6.

## Notes

AC3's two-fake-module ordering test is the critical proof that Modulith's migration strategy is actually wired, not just depended on. Don't skip it in favour of a single-module happy-path test.

AC8 is subtle but important: the runner must NOT honour legacy-root `db/migration/V*.sql` files. If it did, E15S07 would need to keep V1..V6 around until every tenant had been re-migrated; by forcing the runner to per-module locations now, V1..V6 become dead files that E15S07 can safely delete.
