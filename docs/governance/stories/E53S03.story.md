# Story E53S03: Print-index ACTIVE-phase gate + /fotos route fix + photo-schedule first-phase filter (single-resolver helper shared between printIndex + activitySchedule)

## User Story

**As a** Tournament Operator using the print surface from the admin overview ("Druckdokumente"),
**I want** the print-index page to (1) hide both Laufzettel + Mannschaftsfoto-Zeitplan links with an operator-actionable message when no phase has the data-final ACTIVE status, (2) link the Mannschaftsfoto-Zeitplan to a non-404 photo-coordination output, and (3) when I follow that link, see only the single phase relevant for photo coordination,
**so that** I can reach correct print outputs for the live tournament without dead links and without multi-phase clutter, and I am guided to wait when the data is not yet finalized.

---

## Context

User-observable symptoms (Discovery 2026-05-08, screenshot 1 in session brief; user clarification 2026-05-09):

1. **Print-index links to a 404**: The print-index page (`/print/tournaments/{tid}`) renders a "Mannschaftsfoto-Zeitplan" link pointing to `/print/tournaments/{tid}/fotos`. PrintController has no `/fotos` endpoint — clicking the link returns HTTP 404.

2. **Multi-phase clutter on photo-schedule output (anticipated)**: User clarified (2026-05-09) that the photo-schedule output should show only ONE phase ("die erste Phase, in der Mannschaftsfotos koordiniert werden"). The FIRST_FREE_ROUND assignment underlying photo-coordination is per-phase (E08S04 ActivityAssignmentService); cross-phase photo-coordination does not match the actual algorithm.

3. **Operator confusion when no ACTIVE phase exists**: When all tournament phases are still in PENDING/PREPARED/ASSIGNED (e.g., a fresh tournament where the operator hasn't yet activated Phase 1), clicking either Laufzettel or Mannschaftsfoto-Zeitplan would produce technically-wrong round-order output (per O-13 — round-order changes via slot-optimization in `[PREPARED, optimize=true completion]` window). The print-index does NOT currently warn about this.

### Root cause (verified empirically 2026-05-09)

**(1) `/fotos` is a dead link**: PrintController.printIndex() at line 191:
```
model.addAttribute("fotosUrl", "/print/tournaments/" + tid + "/fotos");
```
Controller-comment line 190 says: "AC-URL-INDEX: fotosUrl — legacy behaviour preserved (dead link per legacy)". The Wave-2 reconstruction (E24S06) acknowledged the link is broken but kept the legacy URL. There is no `@GetMapping("/fotos")` in PrintController.

**(2) `/activity-schedule/{activityTypeId}` is the existing photo-schedule endpoint**: `PrintController.java:411` has `@GetMapping("/activity-schedule/{activityTypeId}")` which renders `print/activity-schedule.mustache`. The activity-schedule template at line 68 emits `{{teamNames}}` per round-row — exactly the photo-coordination output the user wants ("in welcher Runde, welche Mannschaften ihren ersten spielfreien Zeitabschnitt haben"). The FIRST_FREE_ROUND assigner (E08S04 ActivityAssignmentService) populates this content for the photo activity-type.

**(3) PrintController has no phase-status filter at any endpoint**: All four endpoints (`printIndex`, `singleTeamSchedule`, `allTeamSchedules`, `activitySchedule`) load phases via `findByTournamentId(tid)` and pass them unfiltered to assemblers. The print-index links to laufzettel and (broken) photo paths regardless of phase status — no operator-actionable indicator that the data may be wrong.

### Why ACTIVE-only gate (not ASSIGNED, not PREPARED)

Per O-13 Brief (user-stated 2026-05-09): the round-order within a phase changes via slot-optimization in the `[PREPARED-with-L2-RoundAssignment, optimize=true completion]` window. ACTIVE is the only state guaranteed post-optimization-final per DEC-55 D-6 activation guard.

Per O-14 Brief: Phase status ACTIVE is NOT the same as the phase chronologically starting. Chronological start = tournament-start-time + computed timing from round/break configuration. Gap between "Phase aktivieren" click and Round-1 chronological begin is typically hours, allowing operator pre-start print workflow.

Same data-correctness rationale that applies to E53S02 (laufzettel) applies here: photo-coordination (FIRST_FREE_ROUND assignment) depends on the round-order within a phase. ASSIGNED-stage output would also show wrong round-numbers for the photo schedule. The gate at print-index (defense-in-depth UX surface) and the content-filter at activitySchedule (data correctness) cooperate to ensure the operator never sees technically-wrong photo-schedule data.

### Why "first phase" for photo-schedule (not all phases)

User-stated 2026-05-09: "Bei den Mannschaftsfotos würde eigentlich nur die erste Phase Sinn machen, denn ich denke nicht, dass die Spielfrei-Ermittlung phasenübergreifend durchgeführt wird." Per E08S04 ActivityAssignmentService: FIRST_FREE_ROUND is a within-phase strategy (per-team, per-phase, find first free round). Photos are typically coordinated in the first phase of a tournament (the longest, opening phase). Cross-phase photo-scheduling is not how the algorithm works; emitting all phases would create a multi-phase output that the operator cannot meaningfully read.

### Three Control-Points (Defense-in-Depth)

This story implements two of the three control-points from Brief D-8:

- **Index-gate at print-index controller**: `printIndex()` checks for at-least-one-ACTIVE-phase; if none, hides both links + renders operator-actionable empty-state message.
- **Photo-schedule content-filter at activitySchedule controller**: when invoked for the photo activity-type, the controller filters the phases list to ONE phase (sequence_number=1 OR earliest-with-avatar-mapping — Delivery picks).

The third control-point (Laufzettel content-filter at singleTeamSchedule + allTeamSchedules) is in E53S02.

### Photo-activity-type-resolver helper

Both `printIndex()` (for fotosUrl resolution) and `activitySchedule()` (for first-phase filter trigger) need to identify which activity-type is the "photo" activity-type. Delivery extracts a single resolver helper to avoid divergence + double-test-coverage.

### Scope posture

This is a **producer-side fix at the PrintController layer + index template + i18n** (per memory `feedback_discovery_cycle_resolution_scope_creep.md`). Discovery does NOT prescribe:
- The shape of the `/fotos` URL fix (Brief T-3-E53S03 lists three: α printIndex resolves URL / β controller alias / γ HTTP 302 redirect).
- The mechanism for "photo activity-type" identification (lookup by name, by AssignmentRule=FIRST_FREE_ROUND, by config flag — but **NOT** by adding a new schema attribute, since BE schema changes are out-of-scope per Brief S-4).
- The mechanism for "first phase" resolution (Brief D-10: sequence_number=1 OR earliest-phase-with-avatar-mapping; mechanism (iii) "phase configured for activity-type" was REMOVED in cycle 4 because it implies schema affordance).
