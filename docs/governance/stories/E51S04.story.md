# Story E51S04: Slot-Opt FIFO-Queue serial pro Tournament — `SlotOptimizationJobRegistry` extension + slotopt-context invocation listener

## User Story

**As a** Tournament Operator,
**I want** the slot-optimization for Phase 2 to start automatically only after Phase 1's slot-optimization has finished (or been cancelled with Best-So-Far) — and never two phases of the same tournament optimizing in parallel,
**so that** my CPU is not overloaded by concurrent optimizers, the optimizer's results are deterministic per phase, and the order I declared in DraftConfig is honored at the slot-opt level.

---

## Context

DEC-55 D-3a mandates a serial-per-tournament FIFO queue for slot-optimization. The existing `SlotOptimizationJobRegistry` (introduced by E27S02) is single-handle-per-tournament: `ConcurrentHashMap<UUID, JobHandle>` keyed by `tournamentId`. This story extends it to FIFO semantics while preserving the existing cancel/status/Best-So-Far consumer API (DEC-49 D-11/D-11a/D-12 unchanged).

Two listeners + one new event close the cross-context loop established by E51S03:

1. `SlotOptJobScheduler` (in **tournament context**, `de.vvwt.tm.tournament.internal`) consumes `SlotOptJobScheduledEvent(tournamentId, phaseId)` (published by E51S03 match-gen-listener when `tournament.optimize=true`). It enqueues the phaseId to the per-tournament FIFO. If the FIFO was empty, it publishes `OptimizePhaseRequestedEvent(tournamentId, phaseId)` to drain the head element.
2. `SlotOptInvocationListener` (in **slotopt context**, `de.vvwt.tm.slotopt.internal`) consumes `OptimizePhaseRequestedEvent`, sets `phase.last_job_state='slot_opt_running'`, invokes `RoutingSlotOptimizationClient.optimize(phaseId)` synchronously within the listener thread, and on completion: flips `phase.optimized=true`, sets `phase.last_job_state='idle'`, publishes `SlotOptJobCompletedEvent(tournamentId, phaseId)`.
3. `SlotOptJobScheduler` (back in tournament context) ALSO consumes `SlotOptJobCompletedEvent` to drain the next FIFO entry (publish next `OptimizePhaseRequestedEvent` or stop if queue empty).

DEC-49 D-11 admin-cancel scope (per-tournament) is preserved: `SlotOptimizationCancelController` (E27S02) calls `SlotOptimizationJobRegistry.getHandle(tournamentId)` which still returns the head element (currently-running job) — the cancel flag flips, Best-So-Far is applied per DEC-49 D-11a, and the slotopt-listener catches the cancel-completion and publishes `SlotOptJobCompletedEvent` (cancel = completion from the queue's perspective). The next phase in the FIFO drains automatically.

`SlotOptimizationJobRegistry.getHandle(tournamentId)` (existing E27S02 consumer API used by `SlotOptimizationCancelController`) returns the FIFO head — backward-compatible. New API `getQueueDepth(tournamentId)` and `enqueue(tournamentId, phaseId)` are added.

## Acceptance Criteria

- [ ] **AC-TEST-FIFO-ENQUEUE-DRAIN-RED** (testing): RED-first IT — given two `SlotOptJobScheduledEvent` published in order (tournamentX, phase1) then (tournamentX, phase2), the FIFO drains in order: phase1 starts; phase1 completes; phase2 starts. Phase2 does NOT start before phase1 completes. Verified by capturing event order via `@RecordApplicationEvents`. Test fails before fix because today's registry is single-handle without queueing.
- [ ] **AC-TEST-FIFO-PER-TOURNAMENT-ISOLATION-RED** (testing): RED-first IT — given concurrent `SlotOptJobScheduledEvent` for tournamentX-phase1 and tournamentY-phase1, both start immediately (no cross-tournament serialization). Test fails before fix because the existing single-handle map blocks at the wrong level.
- [ ] **AC-TEST-CANCEL-MID-FIFO-CONTINUES-RED** (testing): RED-first IT — given a 3-phase tournament with FIFO depth 3, when the operator cancels phase1's slot-opt mid-run, phase1 completes with Best-So-Far per DEC-49 D-11a, `phase.optimized=true` flips, the FIFO drains to phase2 automatically, phase3 follows. Test fails before fix.
- [ ] **AC-TEST-PHASE-OPTIMIZED-FLIP-ON-SUCCESS-RED** (testing): RED-first IT — given a slot-opt-listener completes successfully, `phase.optimized=true` is persisted in the same TX as the lap/field column writes. Test fails before fix.
- [ ] **AC-TEST-PHASE-OPTIMIZED-FLIP-ON-CANCEL-RED** (testing): RED-first IT — given a slot-opt-listener catches the cancel signal (cancellation token observed during PacketSolver iteration), Best-So-Far is applied per DEC-49 D-11a (existing CancelableInProcessSlotOptimizationService behavior unchanged), AND `phase.optimized=true` is set in the same TX as the Best-So-Far application. Even cancel-immediate-pre-permutation (DEC-49 D-11a trivial coordinates) flips `phase.optimized=true`. Test fails before fix.
- [ ] **AC-TEST-CONCURRENT-CANCEL-DURING-DRAIN-RED** (testing): RED-first IT — given phase1 currently running and phase2 queued, an operator cancel on phase1 + a near-concurrent cancel on phase2 (which has not yet started — its handle does not exist in the registry yet) are handled correctly: phase1 is cancelled (Best-So-Far applied), phase2's cancel-attempt returns 409 per existing `SlotOptimizationCancelController` semantics (cancel for a phase that is not yet the head element). Test fails before fix.
- [ ] **AC-TEST-LAST-JOB-STATE-TRANSITIONS-RED** (testing): RED-first IT — `phase.last_job_state` transitions: `'idle'` → `'slot_opt_running'` (when invocation-listener starts) → `'idle'` (on success) OR `'cancelled'` (on cancel). Verified by capturing column values at each transition. Test fails before fix.
- [ ] **AC-TEST-MODULITH-EVENT-ONLY-CROSS-CONTEXT-GREEN** (testing): regression — Spring Modulith verification (`ApplicationModules.verify()`) passes after this story. No new compile-time edges between tournament and slotopt contexts. The `SlotOptInvocationListener` in slotopt context consumes `OptimizePhaseRequestedEvent` published by tournament context — events are not edges in Modulith.
- [ ] **AC-IMPL-FIFO-EXTENSION**: `SlotOptimizationJobRegistry` is extended with `Deque<PhaseId>` per `tournamentId`. `getHandle(tournamentId)` returns the head's `JobHandle` (backward-compatible). New methods: `enqueue(tournamentId, phaseId)`, `getQueueDepth(tournamentId)`, `peekQueue(tournamentId)`. Concurrency: `ConcurrentHashMap` of `Deque` with `synchronized` enqueue/dequeue at the deque level (ConcurrentLinkedDeque OR explicit synchronization — Delivery's choice).
- [ ] **AC-IMPL-EVENT-CLASSES-IN-TOURNAMENT-CONTEXT**: `OptimizePhaseRequestedEvent` and `SlotOptJobCompletedEvent` live in `de.vvwt.tm.tournament.events` (same package as E51S03 events). Both are immutable Java records carrying `(tournamentId, phaseId)`.
- [ ] **AC-IMPL-INVOCATION-LISTENER-IN-SLOTOPT-INTERNAL**: `SlotOptInvocationListener` lives in `de.vvwt.tm.slotopt.internal`. Annotated `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async` + `@Transactional` (DEC-37 Clause B per-tournament row-lock as first read).
- [ ] **AC-IMPL-SCHEDULER-IN-TOURNAMENT-INTERNAL**: `SlotOptJobScheduler` lives in `de.vvwt.tm.tournament.internal`. Two listener methods: `onJobScheduled(SlotOptJobScheduledEvent)` and `onJobCompleted(SlotOptJobCompletedEvent)`.
- [ ] **AC-IMPL-NO-MODULITH-CYCLE**: `de.vvwt.tm.tournament.package-info.java` does NOT declare `slotopt` as `allowedDependency`. Verified by source diff. Modulith verification passes.
- [ ] **AC-IMPL-DEC-49-CANCEL-CONTRACT-PRESERVED**: `SlotOptimizationCancelController` (E27S02) is NOT modified by this story. The cancel flow (POST /api/slotopt/tournaments/{tid}/cancel → `JobRegistry.getHandle(tid)` → `cancellationToken.cancel()` → CancelableInProcessSlotOptimizationService applies Best-So-Far) works as-is because `getHandle` returns the FIFO head.
- [ ] **AC-ERROR-HANDLING-LISTENER-EXCEPTION-NO-QUEUE-LOSS** (error-handling): if the slotopt-invocation-listener throws (network error during Leg-2 dispatch, internal error during Leg-3 cancelable-in-process, etc.), `phase.last_job_state='failed'` is persisted, the FIFO head is dequeued, and `SlotOptJobCompletedEvent` IS still published to drain the next entry. Failure of one phase does not block the queue.
- [ ] **AC-ERROR-HANDLING-EMPTY-QUEUE-NO-NPE** (error-handling): `SlotOptJobScheduler.onJobCompleted` checking the queue when it's empty MUST NOT throw NPE; it logs DEBUG and returns. Verified by IT.
- [ ] **AC-ERROR-HANDLING-CANCEL-ON-NON-HEAD-PHASE** (error-handling): cancel-attempt for a phase that is not currently the FIFO head (i.e., it's queued but not yet running) returns HTTP 409 from the cancel controller (existing E27S02 contract: "no active optimization for tournament" because `getHandle` returns the head, not the queued phase). Operator-actionable error message. The queued phase remains in the FIFO and runs when its turn comes.
- [ ] **AC-SECURITY-NO-NEW-AUTH-SURFACE** (security): no new endpoint, no auth posture change.
- [ ] **AC-SECURITY-NO-CROSS-TENANT-LEAKAGE** (security): per-tournament FIFO is keyed by `tournamentId`. Multi-tenant isolation (DEC-20 + DEC-5) is preserved at the tenant boundary by the existing per-tenant DataSource — within a tenant, tournaments are isolated by their `tournamentId` key. Verified by an IT exercising two tenants concurrently and asserting no FIFO entries cross.
