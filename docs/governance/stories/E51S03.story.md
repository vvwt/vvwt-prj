# Story E51S03: Background-Job-Pipeline foundation — `MatchGenJobScheduledEvent` + listener + Match-Gen invocation

## User Story

**As a** Tournament Operator,
**I want** Match-Generation to run automatically in the background after I click Apply on the DraftConfig — without me triggering anything else,
**so that** by the time I click "Phase aktivieren" on Phase 1 (or Phase 2+), the matches are already in the database and the display SPA renders the match grid immediately.

---

## Context

DEC-55 D-3 mandates a Spring `ApplicationEvent` + `@TransactionalEventListener` + `@Async` pipeline. After E51S02 persists structural avatars at apply-time, this story wires the next step: `apply()` publishes `MatchGenJobScheduledEvent(tournamentId, phaseId)` per phase; an async listener consumes the event, invokes `phasePreparationService.generateMatches(phaseId, gameMode)`, persists matches with `lapNumber=null, fieldNumber=null, refereeTeamId=null`, sets `phase.last_job_state='idle'` after success.

Slot-Opt enqueueing happens AFTER Match-Gen completes — but the slot-opt FIFO-queue extension itself is E51S04. This story stops at "match-gen-job runs to completion and sets `phase.last_job_state='idle'`". The slot-opt scheduler reacts to a NEW `SlotOptJobScheduledEvent` published BY this story when match-gen succeeds AND `tournament.optimize=true` — but the listener for that event arrives in E51S04. The S03 commit publishes the event into the void; S04 wires the listener.

**Modulith-cycle avoidance**: the existing `slotopt → tournament` allowedDependency edge (declared by E27S01) is preserved. This story does NOT add a `tournament → slotopt` edge. All cross-context communication traverses Spring `ApplicationEvent` — events do not count as compile-time edges in Modulith verification (DEC-21 § public-event-driven-cross-module pattern).

The Match-Gen-listener lives in tournament context (`de.vvwt.tm.tournament.internal`) — it consumes the event and invokes existing tournament services (`PhasePreparationService.generateMatches`). No cross-context call needed.

## Acceptance Criteria

- [ ] **AC-TEST-APPLY-PUBLISHES-MATCH-GEN-EVENT-RED** (testing): RED-first IT — given `DefaultDraftService.apply()` succeeds with N phases, exactly N `MatchGenJobScheduledEvent` events are published with `(tournamentId, phaseId)` per phase. Verified by `ApplicationEvents` test listener (Spring `@RecordApplicationEvents`). Test fails before fix because `apply()` does not publish events.
- [ ] **AC-TEST-MATCH-GEN-EVENT-FIRES-AFTER-COMMIT-RED** (testing): RED-first IT — given the apply transaction is rolled back (e.g., post-apply persistence error), the `MatchGenJobScheduledEvent` is NOT delivered to the listener. The listener uses `@TransactionalEventListener(phase = AFTER_COMMIT)` (the default) — verified by injecting a rollback and asserting zero match rows post-rollback. Test fails before fix because either (a) no event is published or (b) a wrong-phase listener fires on rollback.
- [ ] **AC-TEST-MATCH-GEN-LISTENER-INVOKES-GENERATE-MATCHES-RED** (testing): RED-first IT — given `MatchGenJobScheduledEvent(tournamentId, phaseId)` is published, the listener invokes `phasePreparationService.generateMatches(phaseId, gameMode)` exactly once and persists the resulting matches. Verified by `assertj-db` direct-JDBC count of `match` rows for the phase post-event. Test fails before fix because no listener exists.
- [ ] **AC-TEST-MATCHES-PERSISTED-WITH-NULL-COORDINATES-RED** (testing): RED-first IT — after match-gen-listener execution, all match rows for the phase have `lap_number IS NULL`, `field_number IS NULL`, `referee_team_id IS NULL`. Slot-Opt + Referee-Assignment have not yet run. Test fails before fix.
- [ ] **AC-TEST-PHASE-LAST-JOB-STATE-IDLE-AFTER-MATCH-GEN-RED** (testing): RED-first IT — after match-gen-listener completes successfully, `phase.last_job_state = 'idle'` for the phase. Test fails before fix because no listener writes the column.
- [ ] **AC-TEST-MATCH-GEN-FAILURE-SETS-FAILED-STATE-RED** (testing): RED-first IT — given `phasePreparationService.generateMatches` throws (injected via stub `MatchGenerator`), the listener sets `phase.last_job_state='failed'` and does NOT advance the lifecycle. The exception is logged at ERROR level. Test fails before fix.
- [ ] **AC-TEST-SLOT-OPT-EVENT-PUBLISHED-WHEN-OPTIMIZE-TRUE-RED** (testing): RED-first IT — given `tournament.optimize=true` and match-gen-listener succeeds, exactly one `SlotOptJobScheduledEvent(tournamentId, phaseId)` is published per phase. Verified by `@RecordApplicationEvents`. Test fails before fix.
- [ ] **AC-TEST-NO-SLOT-OPT-EVENT-WHEN-OPTIMIZE-FALSE-RED** (testing): RED-first IT — given `tournament.optimize=false`, NO `SlotOptJobScheduledEvent` is published; `phase.last_job_state` ends at `'idle'` after match-gen. Test fails before fix.
- [ ] **AC-TEST-PHASE-2-PLUS-MATCH-GEN-WITH-NULL-TEAM-IDS-RED** (testing): RED-first IT — given Phase 2+ avatars persisted with `teamId IS NULL` (per E51S02), the match-gen-listener invokes `generateMatches` and the `RoundRobinMatchGenerator` consumes `avatar.getId()` (DEC-9) without dereferencing `teamId`. Match rows persist with `member_avatar_X_id` populated to the (null-teamId) avatar's id. Test fails before fix because no match-gen ever runs for Phase 2+ in the new architecture.
- [ ] **AC-IMPL-EVENT-CLASSES-IN-TOURNAMENT-CONTEXT**: `MatchGenJobScheduledEvent` and `SlotOptJobScheduledEvent` live in `de.vvwt.tm.tournament.events` (the existing events package). Both are immutable record types (Java records) carrying `tournamentId, phaseId` (UUIDs).
- [ ] **AC-IMPL-LISTENER-IN-TOURNAMENT-INTERNAL**: `MatchGenJobListener` lives in `de.vvwt.tm.tournament.internal` (intra-context, calls `PhasePreparationService.generateMatches` via Spring DI). Annotated `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async` + `@Transactional` (new TX for the listener body — DEC-37 Clause B per-tournament row-lock acquired as first read).
- [ ] **AC-IMPL-MODULITH-NO-NEW-COMPILE-TIME-EDGE**: this story does NOT add a `tournament → slotopt` allowedDependency to `de.vvwt.tm.tournament.package-info.java`. Verified by inspecting the package-info source diff. The slotopt context's existing `slotopt → tournament` edge (E27S01) is unchanged. Cross-context communication (S04) flows via events.
- [ ] **AC-IMPL-ASYNC-EXECUTOR**: the `@Async` listener uses Spring's default `taskExecutor` bean OR a dedicated `MatchGenJobExecutor` bean (Delivery's choice — must be documented in impl-report). The choice does NOT introduce new external dependencies (DEC-3) and respects DEC-15 LAN-safe operation.
- [ ] **AC-ERROR-HANDLING-LISTENER-EXCEPTION-NO-SILENT-LOSS** (error-handling): a thrown exception inside the match-gen-listener is logged at ERROR level with `tournamentId + phaseId + stackTrace`, sets `phase.last_job_state='failed'`, and does NOT propagate to crash the executor thread (the `@Async` infrastructure swallows event-listener exceptions silently by default — Delivery configures an `AsyncUncaughtExceptionHandler` or equivalent to preserve the failure signal).
- [ ] **AC-ERROR-HANDLING-IDEMPOTENT-MATCH-GEN** (error-handling): re-publishing `MatchGenJobScheduledEvent` for the same phase (e.g., after restart-recovery in E51S07) MUST NOT duplicate match rows. Either (a) the listener checks `phase.last_job_state` and skips if already `'idle'`, or (b) `generateMatches` itself is idempotent (matches existing match rows are deleted+regenerated). Delivery picks one; the chosen semantics is documented in the impl-report.
- [ ] **AC-ERROR-HANDLING-NO-PARTIAL-PERSISTENCE** (error-handling): if `generateMatches` fails mid-flow (e.g., DB error, generator-validation failure), the listener's transaction rolls back. No partial match rows persist. `phase.last_job_state` is set to `'failed'` in a new (post-rollback) transaction or via a try/catch/separate-tx pattern — Delivery's choice; the chosen pattern documented in impl-report.
- [ ] **AC-SECURITY-NO-NEW-AUTH-SURFACE** (security): no new endpoint, no auth posture change. Event publication + listener are internal Spring infrastructure.
- [ ] **AC-GOVERNANCE-DEC-22-Q-1A-RED-FIRST** (governance): all 9 RED-first tests precede any production-code change. New code (event classes, listener, async wiring) is under DEC-22 Iron Law; §refactor-clause does NOT apply.
- [ ] **AC-GOVERNANCE-DEC-21-EVENTS-ONLY** (governance): the impl-report explicitly states the Modulith-cycle-avoidance choice (events-only) and cites DEC-55 D-3 + this AC's verification. Reviewer-cycle-2 finding F-1 (Modulith cycle) is the source of this AC.
- [ ] **AC-GOVERNANCE-DEC-37-LOCK-PRESERVED** (governance): the listener's transaction acquires the per-tournament pessimistic row-lock (`tournamentRepository.findByIdForUpdate(tournamentId)`) as the first read per DEC-37 Clause B. Verified by an IT that exercises concurrent listener invocations on the same tournament.
- [ ] **AC-GOVERNANCE-DEC-40-CONTROLLER-LAYER-UNTOUCHED** (governance): no new controller. Existing controllers unchanged. The pipeline is internal — DraftController → apply → event-publish → async-listener → tournament-internal services.

Listener-only ITs MAY use `@ApplicationModuleTest(...)` per DEC-38 Clause A (bounded-context module IT).
