# Story E16S03: Fix — per-tenant test DBs leak to `~/.vvwt-tm/`; extend `tm.data.dir` test-isolation to `PerTenantFlywayRunner`-bootstrapping ITs

## User Story

**As a** developer or daemon delivery agent running `mvn -pl vvwt-tm-web test`,
**I want** per-tenant H2 test databases to be isolated to an ephemeral path per test ApplicationContext (not persisted in `~/.vvwt-tm/`),
**so that** stale state from prior test runs (e.g., a `flyway_schema_history` row for a deleted migration) cannot cause `FlywayValidateException` failures in tests bootstrapping `PerTenantFlywayRunner`.

---

## Context

E16S02 (PR #66, 2026-04-20) fixed `spring.datasource.url` test-isolation in `vvwt-tm-web/src/test/resources/application-test.yml` by setting `spring.datasource.generate-unique-name=true`. That fix was explicitly bounded to the **main** Spring DataSource — its scope statement (`active.backlog.yaml:956`) reads *"root-cause fix on application-test.yml, no retrofit of ~40 hardcoded per-suite URLs"*. Per-tenant DBs were not in E16S02's scope.

The per-tenant DataSources resolved by `TenantFileRegistryDataSourceResolver.java:134` build a URL of the shape `jdbc:h2:file:${tm.data.dir}/tenants/{uuid}/db.mv.db` — file-based, persistent across JVM runs. `application-test.yml` does NOT override `tm.data.dir`, so per-tenant test DBs land at the production-default `~/.vvwt-tm/tenants/`. This file persists across test runs, branches, and worktrees, accumulating `flyway_schema_history` rows that may no longer correspond to migrations present in source.

Discovery investigation 2026-04-28 traced 3 currently-failing tests in `vvwt-tm-web` (`DomainEventBridgeTest$IntegrationTest.matchResultChangedEvent_receivedOnEventsTopic`, `WebSocketConfigTest.stompClient_connectsToWsEndpoint`, `WebSocketConfigTest.webSocketConfig_classPresent`) to a stale `~/.vvwt-tm/tenants/bbb25630-16c6-4332-9217-521472ad5ff2/db.mv.db` containing a `flyway_schema_history` row for V15 (`e12s04_certificate_template`, deleted from source by E23S07 under DEC-25 Big-Bang-Reset). The 3 failures reproduce on a clean clone of `staging` baseline `444bf58` without any feature-branch changes (verified during E38S09 escalation triage 2026-04-28).

In-codebase prior art for `tm.data.dir` test-override exists at `CrossTenantIsolationTest.java:76-78` (introduced by E14S06 per `tempDataDir = Files.createTempDirectory("tm-e14s06-isolation-")` suffix on line 51) — that pattern uses `@DynamicPropertySource` to inject a `Files.createTempDirectory` path. This pattern is currently applied to ONE IT class only; the 3 failing tests do NOT use it.

Most ITs in `vvwt-tm-web` use `@ApplicationModuleTest` (per DEC-44) and don't bootstrap `PerTenantFlywayRunner`, which explains why the 3-failure tip of the iceberg has remained a slow-burn issue rather than fully blocking the test suite.

This story is a **sibling** to E16S02 — same pattern family, complementary scope (per-tenant DB instead of main DB). Not a duplicate.

The result is robust to the developer NOT having manually cleaned `~/.vvwt-tm/`.

- [ ] **AC2 (testing — RED-before-GREEN regression witnesses)**: After the fix is applied, the 3 currently-failing tests (`DomainEventBridgeTest$IntegrationTest.matchResultChangedEvent_receivedOnEventsTopic`, `WebSocketConfigTest.stompClient_connectsToWsEndpoint`, `WebSocketConfigTest.webSocketConfig_classPresent`) pass with `Errors: 0`. RED-before-GREEN proof: git history on the fix branch shows these 3 tests failed on the parent commit (pre-fix state with phantom V15 row in `~/.vvwt-tm/`) and pass on the fix commit. **NO new IT class is created** — these 3 pre-existing full-context `@SpringBootTest` tests serve as the regression witnesses, avoiding the introduction of any new `@SpringBootTest`-in-bounded-context-module violation of DEC-38 Clause A canon. The pre-existing DEC-38 Clause A non-compliance of the 3 tests themselves is a separate technical-debt observation (recorded in `impl-report.md` per AC7) and out of this Story's scope. DEC-22 RED-first applies to production code; the fix itself touches only test-scope configuration (per AC3 closed list (i)–(iv)) — no new production code is authored, so DEC-22 RED-first is vacuously satisfied at the unit-test layer where it applies (per Brief T-4 / C-2).

- [ ] **AC3 (testing — closed list of fix mechanisms)**: The `impl-report.md` documents which mechanism from the closed list below was selected, and the rationale. Selection is Delivery's choice; the closed list is exhaustive at the test-config layer per Discovery Brief H-3:

## Notes

Bug-triage from E38S09 escalation investigation (Discovery 2026-04-28). Discovery investigation summary:

1. **Symptom:** 3 ApplicationContext failures (`DomainEventBridgeTest$IT`, `WebSocketConfigTest`×2) on `mvn -pl vvwt-tm-web test`. `Tests run: 1053, Failures: 0, Errors: 3, Skipped: 3`.
2. **Reproduction baseline:** failures reproduce on a clean clone of `staging` tip `444bf58` without any feature-branch changes — confirms pre-existing infrastructure debt, NOT a regression introduced by E38S09 or any recent Wave-2 story.
3. **Root cause:** `~/.vvwt-tm/tenants/bbb25630-16c6-4332-9217-521472ad5ff2/db.mv.db` carries a `flyway_schema_history` row at `installed_rank=14, version=15, description="e12s04 certificate template", success=TRUE`. V15 was deleted from source by E23S07 under DEC-25 Big-Bang-Reset (no production data). The stale row in the test-side `~/.vvwt-tm/` file causes Flyway validate to fail on per-tenant DB bootstrap.
4. **Why most tests pass:** Most ITs use `@ApplicationModuleTest` (DEC-44) and don't bootstrap `PerTenantFlywayRunner`. Only full-context `@SpringBootTest`(`classes = TournamentManagerApplication.class`) tests trigger the per-tenant runner.
5. **Net new test-regression delta from E38S09 = 0.** E38S09 added a V17 migration which compounds the validate error (`Detected resolved migration not applied to database: 17.`) but is not the cause; the V15 row is the underlying ghost.
6. **CI behavior:** likely passing because clean `$HOME` per CI build wipes the ghost (UNVERIFIED — H-1).
7. **Daemon worktree behavior:** worktrees share `$HOME`, so cross-worktree contamination is theoretically possible (UNVERIFIED — H-2). Empirical evidence S01–S08 of E38 merged successfully through the latent bug — no pause-of-E38 needed.
8. **Closed list of fix mechanisms (i)–(iv) authored in AC3** per E16S02 precedent. Delivery selects from the list; rationale documented in `impl-report.md`.
