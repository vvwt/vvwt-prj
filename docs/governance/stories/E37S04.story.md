# Story E37S04: Algorithm-agility DEC (D-6) + vvwt-slotopt-dispatcher module skeleton + crypto package (Q-1a TDD RED-first)

## User Story

**As a** dispatcher operator and a future-PQC-aware system architect,
**I want** the new D-6 DEC authored (algorithm-agility SPI + capability-advertisement protocol + algorithm-discriminator schema + dispatcher package layout convention), the new `vvwt-slotopt-dispatcher` Maven module created with Spring Boot scaffolding, and the crypto package (`SignatureVerifier` SPI + `SignatureVerifierRegistry` + V1 `DefaultEd25519Verifier` + supporting types `JcsCanonicalizer`, `InvalidSignatureException`) authored under Q-1a TDD RED-first against the E37S02 spec,
**so that** subsequent E37 stories have a working module skeleton + the foundational signature-verification SPI to build on, and the algorithm-agility architecture is documented as a formal DEC.

---

## Context

This is the first dispatcher-rebuild story. It establishes:
1. **D-6 DEC** — separate from D-6b (E37S01); authorizes the algorithm-agility SPI shape, the capability-advertisement wire protocol (with V1 backward-compat clause for `supportedAlgorithms[]` field per Brief D-2), the KeyRegistry algorithm-discriminator schema, and the package layout convention WITHIN vvwt-slotopt-dispatcher (interface in package root, `Default*` impl in `.internal` sub-package — fresh authorization per Brief C-8, NOT inheriting from DEC-35).
2. **vvwt-slotopt-dispatcher Maven module skeleton** — added to parent pom.xml; Spring Boot 4.0.5 application class; basic application.yml.
3. **crypto package** — `SignatureVerifier` interface (algorithmId/minPublicKeyBytes/maxPublicKeyBytes/verify), `SignatureVerifierRegistry` interface + DefaultSignatureVerifierRegistry, `Ed25519Verifier` interface (or simply concrete) + DefaultEd25519Verifier impl, `JcsCanonicalizer` (JSON canonicalization for verifying message bytes), `InvalidSignatureException`.

V1 ships exactly Ed25519. Future PQC verifiers register as additional Spring beans implementing SignatureVerifier without re-architecting.

This story is authored against E37S02 spec sections (a) shared concerns, (b) dispatcher contract crypto-related portions, (d) algorithm-agility extensions. NO legacy `vvwt-dispatcher` source inspection per Brief C-16.

Authored RED-first.
- [ ] **AC-SIGNATURE-VERIFIER-REGISTRY**: `de.vvwt.slotopt.dispatcher.crypto.SignatureVerifierRegistry` interface with `Optional<SignatureVerifier> lookup(String algorithmId);` and `Set<String> supportedAlgorithms();`. `de.vvwt.slotopt.dispatcher.crypto.internal.DefaultSignatureVerifierRegistry` impl auto-discovers all `SignatureVerifier` beans via Spring `@Component` scan. RED-first authored. Test asserts: lookup of registered algorithm returns Optional.of(...); lookup of unknown returns Optional.empty(); supportedAlgorithms() returns the algorithmId of every registered bean.
- [ ] **AC-DEFAULT-ED25519-VERIFIER**: `de.vvwt.slotopt.dispatcher.crypto.internal.DefaultEd25519Verifier implements SignatureVerifier`. Annotated `@Component`. `algorithmId()` returns `"Ed25519"`. `minPublicKeyBytes() = 32`, `maxPublicKeyBytes() = 32` (RFC 8032). `verify(...)` uses JDK 21 native `Signature.getInstance("Ed25519")` + `KeyFactory.getInstance("Ed25519")` per RFC 8032 + RFC 8410 SubjectPublicKeyInfo. RED-first authored. Tests cover: valid signature → true; invalid signature → false; wrong-length public key → InvalidSignatureException; valid known-vector test using RFC 8032 official test vectors (Spec-Anchored per DEC-41 §1(c)).
- [ ] **AC-INVALID-SIGNATURE-EXCEPTION**: `de.vvwt.slotopt.dispatcher.crypto.InvalidSignatureException extends RuntimeException` with `(String message)` and `(String message, Throwable cause)` constructors. Authored RED-first via test that asserts type + cause-chaining.
- [ ] **AC-JCS-CANONICALIZER**: `de.vvwt.slotopt.dispatcher.crypto.JcsCanonicalizer` class with method `byte[] canonicalize(JsonNode node)` (or equivalent) per RFC 8785 (JSON Canonicalization Scheme) for producing the deterministic byte form that workers sign. Authored RED-first; tests cover RFC 8785 canonical examples (Spec-Anchored citation).
- [ ] **AC-NO-NEW-NON-ED25519-VERIFIERS**: V1 ships exactly ONE SignatureVerifier impl. Verifiable via grep: only `DefaultEd25519Verifier` implements `SignatureVerifier`. Per Brief S-1.

## Notes

- **DEC ID** for D-6 is auto-assigned at execution time (next free DEC after D-6b's assignment in E37S01).
- **JcsCanonicalizer**: V1 implementation must match the canonical JSON form workers use to sign. Spec section (a) shared concerns must define this canonical form (RFC 8785 citation expected).
- **Per Brief Q-3**: `SignatureVerifierRegistry` design enables drop-in addition of future verifiers — adding `MlDsa65Verifier @Component` is the only change needed in a future story.
- **Per Brief T-4 boundary**: V1 wire-protocol additivity covers the Ed25519/ML-DSA-family case; future algorithms requiring context strings (FIPS 204 §5.2) WILL need wire-protocol extension.
- **Per Brief D-2 backward-compat**: D-6 DEC must explicitly state the `supportedAlgorithms[]` Optional + default-`["Ed25519"]` clause to enable existing standalone-worker (post-E37S01) to talk to new dispatcher.
