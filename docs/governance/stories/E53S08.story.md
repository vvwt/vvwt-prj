# Story E53S08: Fix: Team's first bye-round on Laufzettel must render as Mannschaftsfoto activity row (not "Frei") when a FIRST_FREE_ROUND ActivityType is configured

## User Story

**As a** Tournament Organizer using the printed Laufzettel as the source of truth for participating teams,
**I want** each team's first match-free round to be marked as the team's photo round (Mannschaftsfoto) instead of "Frei",
**so that** participants know when to be at the photo location and the photo schedule the operator distributes (Mannschaftsfoto-Zeitplan) is consistent with each team's individual Laufzettel.

---

## Context

User reported on 2026-05-10 that the Laufzettel currently shows "Frei" for any round in which a team has no playing or refereeing assignment. Per the user's intent: each team's **first** bye-round (in the ACTIVE phase) should be designated as the team's Mannschaftsfoto round and rendered as such on the Laufzettel — matching the data already produced by the Mannschaftsfoto-Zeitplan output (`/print/tournaments/{tid}/activity-schedule/{photoTypeId}`).

### Existing wiring (informational)

Per `DefaultLaufzettelAssembler.java:537-539`, when `ActivityAssignmentService.assignActivities(...)` returns an assignment for a team's lap, the assembler emits `LaufzettelRow.activity(lap, time, activityName)` instead of `LaufzettelRow.free(lap, time)`. The `FirstFreeRoundAssigner` (`de.vvwt.tm.tournament.activity.internal.FirstFreeRoundAssigner`) is the algorithm that populates assignments for `AssignmentRule.FIRST_FREE_ROUND` activity types. The wiring is therefore already correct in principle — Bug D's manifestation depends on whether (a) the `FIRST_FREE_ROUND` `ActivityType` is configured (resolved by E53S05), and (b) `ActivityAssignmentService` actually surfaces the assignment for the team's first bye-lap.

### Why this is a separate story (not bundled with E53S05)

While Bug A and Bug D share a configuration-layer prerequisite (a `FIRST_FREE_ROUND` `ActivityType` must exist), the symptoms surface at different layers:
- E53S05 (Bug A) → admin/CONFIG layer ⇒ link visibility on print-index
- E53S08 (Bug D) → ASSEMBLY-WIRING layer ⇒ Laufzettel cell semantics

Even after E53S05 closes, E53S08 may still fail if `ActivityAssignmentService` returns no assignment for a particular team-lap (e.g., due to a corner case in `FirstFreeRoundAssigner` or a data-flow break). E53S08 carries an explicit AC asserting end-to-end activity-row rendering for one configured tournament.

### Root principle (from Brief D-0)

Print is a downstream observer. Bug D's fix surface is the **ASSEMBLY-WIRING layer** — verify and (if needed) repair the data flow between `ActivityAssignmentService` output and `DefaultLaufzettelAssembler` consumption.

### Codebase entry points (informational only — Delivery picks the implementation shape)

- `DefaultLaufzettelAssembler.java:227-258` — phase-by-phase activity-assignment via `activityAssignmentService.assignActivities(...)`.
- `DefaultLaufzettelAssembler.java:537-539` — `LaufzettelRow.activity(...)` emission when assignment present.
- `de.vvwt.tm.tournament.activity.internal.FirstFreeRoundAssigner` — algorithm.
- `de.vvwt.tm.tournament.activity.ActivityAssignmentService` — orchestration.
- `print.laufzettel.label.free` (i18n: "Frei") — current label for unassigned rows.
- `tom.label.team_photo=Mannschaftsfoto` (i18n key in `messages.properties:212`).

### Reproduction & expected behavior

- [ ] **AC1 (testing — RED-first reproduction with explicit preconditions)**: Given a tournament fixture where (1) a `Mannschaftsfoto` `ActivityType` with `assignment_rule = FIRST_FREE_ROUND` is configured for the tournament, AND (2) at least one team has at least one bye-lap (a lap where the team is neither playing nor refereeing) within the ACTIVE phase, AND (3) `ActivityAssignmentService.assignActivities(...)` is invoked end-to-end, when the operator requests `/print/tournaments/{tid}/team-schedules/{teamId}` for that team, then the rendered HTML for the team's **first** bye-lap row contains the configured activity name (the Mannschaftsfoto label) AND the row is rendered as an ACTIVITY row (not a FREE row). RED before any production change.
- [ ] **AC2 (testing — first bye-round only)**: Given the same fixture, when a team has **multiple** bye-laps in the ACTIVE phase, then ONLY the first bye-lap (lowest `lapNumber`) is rendered as an ACTIVITY row carrying the Mannschaftsfoto label. Subsequent bye-laps for the same team continue to render as FREE rows. Regression test asserts both the activity-row at lap_min AND the free-row(s) at subsequent lap(s).
- [ ] **AC3 (testing — multi-team coverage)**: Given AC1's fixture with at least three teams that each have a bye-lap, when the operator requests team-schedules for each of the three teams, then each team's first bye-lap renders an activity row with the Mannschaftsfoto label. Verifies no team-specific assignment gap.

## Notes

### Severity (per Brief Q-5)

**HIGH** — Laufzettel cell semantics for a critical operator hint. Without this fix, teams see "Frei" on their photo round and have no indication from their individual Laufzettel that they should be at the photo location. The Mannschaftsfoto-Zeitplan output remains correct (E08S09 + E53S03), but operators who hand out Laufzettel rather than the consolidated photo-schedule lose the per-team signal.

### Sequencing constraint

E53S08 cannot pass acceptance until E53S05 closes — the AC1 fixture requires a configured `FIRST_FREE_ROUND` `ActivityType`. Daemon claim ordering should respect this dependency.

### Trade-off log (from Brief)

T-4 — INDEPENDENT story (not merged into E53S05) chosen. Each story has its own ACs and regression test. Sequencing is captured via `dependencies`, not via story merge.

### Investigation budget for Delivery

Delivery's Step-1 is to verify that Bug D's wiring path is intact: (a) given a configured `FIRST_FREE_ROUND` `ActivityType`, does `ActivityAssignmentService.assignActivities(...)` return an assignment for each team's first bye-lap? (b) Does `DefaultLaufzettelAssembler.java:537-539` correctly route the assignment into `LaufzettelRow.activity(...)`? If both YES, the only remaining gap is configuration (closed by E53S05) and AC1 will pass once a configured fixture is in place. If either is NO, that's Bug D's true root cause.
