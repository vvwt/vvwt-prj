# Story E54S12: Fix — L3 brute-force produces sub-optimal permutation for 12T/2G/3F despite iterating all 10! ranks

## User Story

**As a** tournament operator running a roundRobin phase with 2 groups of 6 teams on 3 fields,
**I want** the L3 slot-optimization output to actually achieve the minimum-variety score that is mathematically reachable from the L2 phase-global output (per the `VarietyScorer` cost function with default `tm.slotopt.scorer=mean`),
**so that** my teams experience the most-balanced active/idle pattern the algorithm can deliver — not a clustered output where some teams are idle for 5 consecutive rounds while others play 5 consecutive matches.

---

## Context

### Bug report (user empirical observation, 2026-05-11 live test)

User Live-Test 2026-05-11 (tournament `d00422b3-e1aa-4f9a-a6bc-526d1d...`, fresh staging build post-E54S07/S04/S09, optimize=true):

- Phase 1: 12 teams in 2 groups of 6, 3 fields, roundRobin gameMode (single phase containing both groups).
- Team 1 (M01, G1) Laufzettel: `Match-Foto-Frei-Frei-Frei-Match-Match-Match-Match-Frei` over 10 rounds.
- Both G1 teams active in laps {1, 6, 7, 8, 9}; G2 teams active in {2, 3, 4, 5, 10}. Disjoint per-group, MaxConsecutiveIdleLaps ≈ 4-5 per team.

### Root cause analysis (from investigation `2026-05-11-live-cluster-discrepancy.investigation.md`)

The voting-driven L2 and phase-global L3 are both wired correctly per DEC-61 and DEC-63 specifications:

- `DefaultRoundAssignmentService.assignRoundsAndFields(phaseId, 3)` implements DEC-61 Clause A voting-driven greedy slot-filling.
- `RoutingSlotOptimizationClient.optimize(phaseId)` for `lapCount=10` (≤ `tm.slotopt.exhaustive-max-n=10`) invokes `executeLeg1Inline`, which iterates `rank = 0 .. 10! - 1`, decodes each rank via `LehmerCodec.rankToPermutation(rank, lapCount)`, scores via `VarietyScorer.scoreWithMatrix` (default `tm.slotopt.scorer=mean`), and applies the lowest-score permutation via `SlotResultApplicator.applyResult(bestRank, fieldCount, phaseMapping)`.

Yet the production output is **sub-optimal vs analytical brute-force**:

| Source | Per-avatar product max | STDDEV | MEAN-score | MaxConsecutiveIdle |
|---|---|---|---|---|
| Analytical brute-force (circle-method L1 output, brute-force L3 in Python) | **1** | **0.00** | **1.0** | **1** |
| Production live (user observed) | clustered, consistent with **25** | — (high) | — (high) | **4-5** |
| Production IT (E54S09, nested-loop L1 fixture) | **25** | **5.85** | **17.0** | **5** |

For circle-method L1 insertion order (= production L1 `RoundRobinMatchGenerator.generatePairs`), the analytical optimum is `score=1.0` (all per-avatar products = 1, MaxIdle = 1, fully alternating G1/G2 pattern). The L3 brute-force exhaustive search MUST find this — yet production produces clustered output with MEAN-score ≈ 17.0.

### Candidate defective stages (UNVERIFIED — Delivery diagnoses)

Discovery does NOT pre-decide which stage is defective. Delivery's diagnostic walks the test through SIX candidates (expanded from the 4 initial candidates after Tier-2 review surfaced 2 additional candidates the investigation itself mentioned):

1. **`LehmerCodec.rankToPermutation(rank, lapCount)`** — must be bijective: for each `rank ∈ [0, 10!)`, must produce a distinct valid permutation of `[0, lapCount)`; iterating all ranks must enumerate all permutations exactly once.
2. **`VarietyScorer.scoreWithMatrix(rowSequence, rowCount, avatarCount, activeMatrix)`** — must correctly compute MEAN of per-avatar products of run-lengths for ANY valid `rowSequence`.
3. **`SlotResultApplicator.applyResult(bestRank, fieldCount, phaseMapping)`** — must correctly persist the picked permutation to DB `lap_number` values (1-based per DEC-60).
4. **`PhaseToRawPhaseDefMapper.map(phaseId)` `denseIdsByRawRow` / `activeMatrix` construction** — must correctly aggregate avatars-per-lap into the active-matrix consumed by the scorer.
5. **`ScorerFactory.createScorerUnified(scorerConfig)` wiring** — for `scorerConfig=mean` (default), must return a `Scorer` adapter that delegates to `VarietyScorer` per DEC-63 Clause A. Possible defect: default-resolution picks wrong scorer (e.g., `BalancedVarietyScorer` accidentally, or a stale identity).
6. **`RoutingSlotOptimizationClient.executeLeg1Inline` loop body** (file `slotopt/internal/RoutingSlotOptimizationClient.java:244-295`) — `bestRank`/`bestScore` tracking (initial values `0L` / `Double.MAX_VALUE`), comparator (`score < bestScore` strict-less), loop bound (`rank < totalPermutations`), and no early-termination. Possible defect: off-by-one in comparator, premature break, mis-initialized accumulators, or `long`-arithmetic edge case (10! = 3,628,800 fits long comfortably, but the iteration logic itself may have a defect).

The RED-first test below catches the defect; Delivery walks the six candidates to isolate the cause.

### Why this is a Bug-Triage track, not Architecture-Discovery

Symptom is empirically reproducible (E54S09 IT exhibits same defect). Root cause is bounded to 4 well-defined code paths. No architectural redesign needed. The defect is a SINGLE-STAGE divergence in an otherwise correct pipeline. Fits Bug-Triage flow per discovery.agent.md.

## Root Cause Analysis

(From investigation `2026-05-11-live-cluster-discrepancy.investigation.md` — full evidence, hypothesis verification table, simulation outputs, and side-by-side analytical-vs-empirical comparison.)

**Symptom**: `RoutingSlotOptimizationClient.executeLeg1Inline` iterates all `10! = 3,628,800` ranks for a 12T/2G/3F phase but the picked `bestRank` produces a permutation whose `VarietyScorer.scoreWithMatrix` value is 3-17× higher than the analytical brute-force minimum on the same L2 active-matrix input.

**Hypothesis-set after investigation (UNVERIFIED stages, narrowed to 6 candidates after Cycle-1 reviewer surfaced 2 additional candidates)**:
1. `LehmerCodec.rankToPermutation` — bijectivity / correctness across full rank range.
2. `VarietyScorer.scoreWithMatrix` — correctness for arbitrary `rowSequence`.
3. `SlotResultApplicator.applyResult` — correct persistence of the picked permutation.
4. `PhaseToRawPhaseDefMapper.map` `denseIdsByRawRow` / `activeMatrix` construction — correctness of active-set per lap.
5. `ScorerFactory.createScorerUnified` wiring / default-resolution.
6. `RoutingSlotOptimizationClient.executeLeg1Inline` loop body invariants (bestRank/bestScore tracking, comparator strict-less, loop bound, accumulator initialization).

**Diagnostic method (Delivery's responsibility)**:
- Step 1: Run the RED test from AC-TEST-L3-MATCHES-BRUTEFORCE-OPTIMUM-12T2G3F-RED. Confirm `prodScore != testBestScore` (RED).
- Step 2: Print the production `bestRank` and decode via `LehmerCodec`. Print the test's `testBestPermutation`. Compare structurally — same shape? same content? If `LehmerCodec` output deviates from test's permutation enumeration for the same logical pick → defect is in `LehmerCodec` (candidate 1).
- Step 3: Take the test's `testBestPermutation` and score it via `VarietyScorer.scoreWithMatrix` (production code). If score deviates from test's independent score-computation → defect is in `VarietyScorer.scoreWithMatrix` (candidate 2).
- Step 4: Take the production `bestRank`, apply via `SlotResultApplicator.applyResult`, then re-read DB and compute score; compare to production's `bestScore`. If deviates → defect is in `SlotResultApplicator` (candidate 3).
- Step 5: Print the `activeMatrix` built by Mapper; compare to test's independent active-matrix construction. If deviates → defect is in `Mapper.activeMatrix` (candidate 4).
- Step 6: Confirm `ScorerFactory.createScorerUnified("mean")` returns a `Scorer` whose `scoreWithMatrix` delegates to `VarietyScorer` (NOT `BalancedVarietyScorer`); add a unit test asserting the returned scorer type. If wrong scorer → defect is in `ScorerFactory` wiring (candidate 5).
- Step 7: Add instrumentation to `executeLeg1Inline` loop body to dump `(rank, score, bestRank, bestScore)` tuples; verify (a) `bestScore` decreases monotonically as expected, (b) `bestRank` updates whenever `score < bestScore`, (c) loop completes all `10!` iterations without early break. If any invariant violated → defect is in `executeLeg1Inline` loop body (candidate 6).

**Why this is reachable in single Delivery cycle**: The 6 candidates are all small, well-tested code units. Each per-candidate probe (Steps 2-7) takes ~10-20 minutes once the RED test is in place. Full candidate-walk fits within the 8-hour `AC-ERROR-DIAGNOSTIC-EXHAUSTED` escalation cap with substantial margin for the actual fix + threshold-recalibration of the E54S09 IT.
