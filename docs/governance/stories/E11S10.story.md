# Story E11S10: Fix — Timer audio-fire init-suppression, auto-PLAYING after Dialog confirm, and timeline math from operator-configured DraftConfig

## User Story

**As a** tournament organizer using the Timer SPA at a venue,
**I want** (a) the timer to run automatically after I confirm the Hallenuhr in the ClockSyncDialog (without forcing a separate PLAY click), (b) the countdown and the schedule table to use the lap durations, lap breaks, and inter-phase pauses I configured in the phase plan (not hardcoded defaults), and (c) audio events to fire only at the real schedule transitions (no false audio at the moment I open the page or press PLAY),
**so that** the timer behaves as I planned for the tournament — the right sound at the right time, no manual interventions required during play.

---

## Context

After E11S09 (math, AC4–AC8) shipped, the Timer SPA's Hallenuhr-Now display, visible countdown label, next-row highlight, and schedule-column-header are working correctly. Operator empirically reproduced three remaining correctness symptoms on 2026-05-28:

1. **Wrong audio fires immediately on PLAY click.** Test 1 — operator opens the page at Hallenuhr 09:58, lets the clock run to 10:00 (= Phase-1-Round-1 planned start; Hallenuhr-Now shows 10:00), no audio fires, then clicks PLAY → `PAUSE_MUSIC_START` fires immediately because `activeEventIndex` is the Pause entry (the entry AFTER Round 1, which is already playing). Test 2 — operator opens at 09:57, immediately clicks PLAY → `START_SOUND` fires immediately even though the countdown shows 3 minutes remaining. Root cause: `App.svelte` `onTick` initializes `lastFiredActiveIndex = -2`; first tick sees `activeEventIndex !== -2 && !== -1` and treats this as "a new event just activated", firing audio for the next-upcoming entry.

2. **Schedule timeline uses hardcoded default values.** Operator configured 10-minute lap duration for Phase 1; the schedule shows 15-minute slots. The phase-pause between Phase 1 and Phase 2 is zero (Phase 1 last round end → Phase 2 first round start has no break). Root cause: `DefaultTimerDataService.buildPhaseConfigs` uses `DEFAULT_LAP_TIME_MINUTES = 15` and `DEFAULT_LAP_BREAK_MINUTES = 5`, and passes `sectionBreakMinutes = 0` to `TimelineCalculationService.calculate`. The operator-configured values in `DraftConfig.sections[i].{lapTimeMinutes, lapBreakTimeMinutes, sectionBreakTimeMinutes, breaks}` (persisted in `tournament.draftJson`) are ignored.

3. **Countdown does not tick while transportState is STOPPED.** The Hallenuhr-Now display (E11S09 AC7, own interval) ticks; the countdown stays frozen until PLAY is clicked. Operator expects countdown and Hallenuhr to tick together so the time-until-next-event is visibly counting down while the operator waits before the tournament starts.

Discovery Session Brief `discovery-2026-05-28-timer-post-e11s09-bugs-and-ux-evolution` (Tier-2 cycle-2 with 3 escalated findings autonomously resolved en bloc per operator 2026-05-28; rubric_version 2026-03-30) drives the per-symptom DEC-22 routing.

Operator's structural decision: the Timer SPA's audio engine runs **automatically** from the moment the ClockSyncDialog is confirmed onward. The PLAY button remains available as a manual resume override after PAUSE/STOP. The countdown ticks only when the engine is in `PLAYING` — and since the engine is auto-`PLAYING` after Dialog confirm, the operator sees the countdown immediately. This single structural change dissolves Symptom 3 as a side-effect of fixing Symptom 1.

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach is Delivery's choice; this Story specifies the WHAT.

### Symptom 1 — Audio-fire correctness

- [ ] **AC1 — Audio engine runs automatically after Dialog confirm.** Confirming the ClockSyncDialog (either via the primary "Zeit bestätigen" button or via the Hallenuhr-time-entry path) sets the Timer's transport state to a "running" mode without requiring a separate click on the PLAY button. The PLAY / PAUSE / STOP buttons remain functional as manual override.
- [ ] **AC2 — First-tick audio init-suppression on engine start.** When the engine transitions from a non-running state (initial Dialog-confirm, or after PAUSE / STOP) into the running mode, the **first** tick observed after the transition MUST NOT fire any audio event, regardless of which schedule entry is the current `activeEventIndex` or `playingIndex`. The engine establishes its baseline by recording the current `activeEventIndex` and `playingIndex` without firing the corresponding activate / deactivate audio events.
- [ ] **AC3 — Documented edge case (operator-accepted).** When the running mode begins exactly at or within the millisecond resolution of an event boundary (e.g. Dialog confirmed at the second when Round 1's wall-clock time is reached), that boundary's audio is NOT fired. Subsequent boundaries fire normally. Operator's working pattern is to open the timer page with buffer time before the tournament start; this edge case is documented behaviour, not a regression.
- [ ] **AC4 — Subsequent event boundaries fire audio normally.** After the first-tick init-suppression, every subsequent observable change of `activeEventIndex` (i.e. a real event transition during the running tick stream) fires the corresponding audio event per the existing `getAudioEventOnActivate` / `getAudioEventOnDeactivate` classification (which is itself NOT changed by this Story — see AC16).

### Symptom 2 — Timeline math from operator-configured DraftConfig

- [ ] **AC5 — Lap duration in the timer schedule equals the operator-configured value.** For each phase, the wall-clock window allocated to every match round in the schedule equals the `lapTimeMinutes` value from the corresponding `DraftSection` in the tournament's persisted `DraftConfig` (`tournament.draftJson`). The hardcoded constant `DEFAULT_LAP_TIME_MINUTES` is no longer used as the source of the lap duration in the timer schedule path.
- [ ] **AC6 — Lap break in the timer schedule equals the operator-configured value.** For each phase, the wall-clock window allocated to a `LAP_BREAK` between two consecutive rounds equals the `lapBreakTimeMinutes` value from the corresponding `DraftSection`. The hardcoded constant `DEFAULT_LAP_BREAK_MINUTES` is no longer used as the source of the lap-break duration in the timer schedule path.
- [ ] **AC7 — Inter-phase pause (Phase-Pause) is included in the schedule.** Between two consecutive phases, a break entry of type `ADDITIONAL` (i.e. NO audio fires for it — `getAudioEventOnActivate` / `getAudioEventOnDeactivate` returns `NONE` per the existing E11S04 classification) is inserted in the timer schedule, whose duration equals the `sectionBreakTimeMinutes` value from the **preceding** phase's `DraftSection`. The wall-clock times of all subsequent schedule entries advance accordingly. The hardcoded `0` passed to `TimelineCalculationService.calculate` is replaced; this Story's behavioural requirement does not mandate one specific call shape — see § Notes.
- [ ] **AC8 — Intra-phase breaks (DraftSection.breaks) appear at their configured lap boundary with the configured duration.** Existing behaviour preserved; this AC is a regression guard for the operator-configured intra-phase break path that is presumed already in `DefaultTimerDataService` flow.

### Symptom 3 — Countdown ticks immediately after Dialog confirm

- [ ] **AC9 — Countdown ticks as soon as the Dialog is confirmed.** Because of AC1, the engine is in the running mode at the moment the operator sees the schedule. The visible countdown numerals tick down at one-second resolution from that moment, without any further operator interaction.

### Error-handling (mandatory category)

- [ ] **AC10 — Zero-offset regression guard.** When the operator confirms the Hallenuhr equal to the device clock (`Δ = 0`), the audio engine starts auto-running per AC1 and audio fires at the operator-configured wall-clock times via the standard device-time-equals-Hallenuhr path. No drift, no false-positive audio.
- [ ] **AC11 — DraftConfig load failure / absent draft.** When the tournament has no persisted `DraftConfig` (e.g. an older tournament that pre-dates the DraftConfig schema, or a fresh tournament with no draft saved yet) or the draft load fails, the timer page either (a) renders a clear operator-facing error consistent with E11S03's error states or (b) falls back to a documented, deterministic behaviour that does NOT silently substitute hardcoded `15` / `5` values. Delivery picks (a) or (b) and the choice is impl-report attested.
- [ ] **AC12 — Invalid DraftConfig values.** When the persisted `DraftConfig` contains values that fail `DraftSection` validation (e.g. `lapTimeMinutes <= 0` for a non-Siegerehrung phase), the timer page surfaces this via the same error path as AC11. The timer does NOT silently compute a schedule with invalid inputs.

Story AC asserts the behavioural outcome (AC5/AC6/AC7); Delivery picks (a) or (b) with rationale in impl-report.
