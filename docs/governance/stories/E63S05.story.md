# Story E63S05: TM embedded worker — operator controls + observability metrics

## User Story

**As a** Tournament Manager operator,
**I want** to pause, resume, and disable the embedded worker from the admin console and see
how it is doing,
**so that** I stay in control of the compute my server contributes — without restarting TM.

---

## Context

E63S03 builds the embedded-worker core (opt-in, OFF by default, governed by a config flag);
E63S04 makes it host-safe. This story gives the operator a live control and observability
surface so the worker can be managed at run time.

- **Controls.** Beyond the static boot-time config flag, the operator can pause, resume, and
  disable the embedded worker at run time — without restarting the TM host (the original
  Story E01S11 AC9). There is no run-time *enable*: enabling the worker is the boot-time
  config flag (E63S03); the run-time controls govern a worker that flag has enabled. The
  control surface is a REST endpoint plus admin-console UI, alongside the existing
  slot-optimization admin surface (`SlotOptimizationCancelController` lives at
  `de.vvwt.tm.web.slotopt.*`).
- **Observability.** The worker exposes metrics — packets completed, packets failed, and its
  current state (stopped / running / paused-by-host-activity / paused-by-operator / error) —
  so the operator can see whether it is contributing and why it is or is not.

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-CONTROL-PAUSE-RESUME-DISABLE** — RED-first (DEC-22): the control endpoint
  pauses, resumes, and disables the embedded worker; each operation moves the worker to the
  expected state, observable via the status surface. (Enabling the worker is the boot-time
  config flag, E63S03 — there is no run-time enable verb.)
- [ ] **AC-TEST-NO-HOST-RESTART** — pause and resume take effect without restarting the TM
  host process; a running TM transitions the worker live.
- [ ] **AC-TEST-METRICS-EXPOSED** — the worker exposes (per the original Story E01S11 AC10):
  two counters — `worker.packets.completed.total` and `worker.packets.failed.total` — and a
  worker-state value exposed as a **numeric gauge** with the canonical integer encoding
  `0 = stopped`, `1 = running`, `2 = paused-by-host-activity`, `3 = paused-by-operator`,
  `4 = error`. (Metric names / framework are the established TM observability stack; the
  gauge encoding is fixed so operator dashboards and alerts can rely on it.)
- [ ] **AC-TEST-WEB-IT** — the control controller's integration test runs under the DEC-44
  web-module IT framework (`@SpringBootTest(RANDOM_PORT, classes = TournamentManagerApplication.class)`
  with a per-IT `@Import({WebModuleTestConfig.class, <IT>.TestAdminCredentials.class})` — the
  DEC-44 2026-04-27 empirical refinement, required because the IT exercises the admin-
  authenticated control endpoints); the admin-UI control elements are covered by the SPA's
  test setup.
- [ ] **AC-TEST-SUITE-GREEN** — `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54).

### Governance

- [ ] **AC-GOV-CONTROLLER-PLACEMENT** — the worker-control REST controller follows DEC-40
  (controller placement; Clause B Pattern A — DTOs serialized directly); it is placed
  consistently with the existing `de.vvwt.tm.web.slotopt.*` admin surface.
- [ ] **AC-GOV-INTERFACE-MANDATE** — the new behaviour-bearing worker-control service gets an
  interface in the module root + a `Default*` implementation in `.internal` (DEC-58 / DEC-72
  / DEC-35 / DEC-36). The control REST controller itself is a `@RestController` and is
  therefore excluded from the interface mandate (DEC-58 Clause D / DEC-72 Clause D-ext). The
  interface-mandate build guard stays green.
- [ ] **AC-GOV-CONTROLS-COMPLEMENT-CONFIG-FLAG** — the run-time controls complement, and do
  not contradict, the E63S03 opt-in config flag: the flag is the boot-time enable; the
  run-time controls (pause / resume / disable) govern a worker the flag has enabled. There
  is no run-time enable verb — on a flag-disabled instance there is no worker to control and
  a control invocation returns the defined "worker not enabled" response
  (AC-ERR-CONTROL-ON-DISABLED-WORKER). The flag-vs-controls relationship is documented.
- [ ] **AC-GOV-RED-FIRST** — new first-party code is authored RED-first per DEC-22; the
  impl-report records RED-state evidence.
- [ ] **AC-GOV-BUILD-HYGIENE** — `mvn verify` exits zero (DEC-54); warning-free (DEC-29);
  Spotless / google-java-format (DEC-30); no production member exists solely for tests
  (DEC-70).
- [ ] **AC-GOV-COMMIT-FORMAT** — commit subjects use `chore(E63S05):` / `feat(E63S05):`
  prefixes per the close-story.sh contract.

### Error Handling

- [ ] **AC-ERR-CONTROL-ON-DISABLED-WORKER** — a pause / resume / disable control invoked when
  the worker is not in a controllable running/paused state — whether flag-disabled (OFF,
  never started) or run-time-disabled (stopped earlier this session) — returns a defined,
  informative response (e.g. a 409-class status), not an error 500 and not a misleading
  silent no-op. Bringing a run-time-disabled worker back is not a run-time operation: it
  requires a host restart with the config flag enabled — there is no run-time enable verb
  (AC-GOV-CONTROLS-COMPLEMENT-CONFIG-FLAG).
- [ ] **AC-ERR-METRICS-WHEN-DISABLED** — the metrics / status surface for a disabled worker
  reports a defined disabled/stopped state — it is never absent or an error.
- [ ] **AC-ERR-REDUNDANT-CONTROL-IDEMPOTENT** — a redundant control (pause an already-paused
  worker, resume a running not-paused worker) is idempotent — a defined no-op response, not
  a failure.
- [ ] **AC-ERR-CONTROL-INVOCATION-NON-BLOCKING** — invoking a control (pause / resume /
  disable) does not block or stall TM's request-handling threads or its primary duties
  (live scoring, the admin UI): the control operation signals the embedded worker thread
  and returns promptly — it does not synchronously join the worker thread or wait on an
  in-flight packet solve. This is Q-1 applied to the control surface itself (distinct from
  E63S04's steady-state host-protection).

### Security

- [ ] **AC-SEC-CONTROL-ENDPOINTS-ADMIN-AUTHENTICATED** — the worker-control endpoints require
  the same admin authentication as the rest of the TM admin console; there is no
  unauthenticated control surface for starting/stopping the worker.
- [ ] **AC-SEC-NO-KEY-MATERIAL-IN-SURFACE** — the control and metrics responses never expose
  the embedded worker's private key, key material, or any team UUID / PII (DEC-9).
