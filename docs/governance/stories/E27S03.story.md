# Story E27S03: Leg 2 — Dispatcher HTTP Client + Reachability Check + DEC-43 D3 Admin-Warning Surface

## User Story

**As a** Tournament Manager admin running a tournament with > 10 rounds and an internet-reachable dispatcher,
**I want** the slot-optimization to be offloaded to the dispatcher (distributed compute, faster results) when the dispatcher is reachable, falling back transparently to local in-process compute when not,
**so that** I get the best-available compute path automatically — distributed when possible, local when not — without manual switching.

---

## Context

E27S01 landed routing skeleton; E27S02 landed Leg 3 (cancelable in-process for N>threshold, no dispatcher). For N>threshold post-S02, ALL traffic uses Leg 3. This story lands **Leg 2**: when `tm.slotopt.dispatcher.url` is configured AND the dispatcher is reachable, the optimization is submitted via HTTP per DEC-11 boundary + DEC-43 wire format. When unreachable (or URL unset), the existing Leg 3 fallback (E27S02) applies.

This story unblocks **E01S10** (TM HTTP-submitter pattern, blocked since 2026-04-11 per DEC-11 § Impact: "blocked on the TM submodule(s) being bootstrapped").

DEC-43 D3 admin-warning surface (per Brief S-3a): when the dispatcher's registration response includes a non-null `deprecation_date` for the registered algorithm, TM publishes an `ApplicationEvent` consumed by an admin-UI banner endpoint. **V1 wire shape = single "Ed25519" with null deprecation_date → defensive code; never fires until Phase-2+** (when ML-DSA/SLH-DSA enter the registry). Implementation IN scope per DEC-43 D3 protocol-shape compliance.

Per DEC-11: TM imports `vvwt-slotopt-worker-lib` (types only) — NEVER imports `vvwt-slotopt-dispatcher`. Maven Enforcer rule (this story) makes the boundary build-checked.

## Acceptance Criteria

### NEW `SlotOptimizationDispatcherClient` (HTTP client per DEC-11 + DEC-43)

- [ ] **AC-DISPATCHER-CLIENT-AUTHORED [testing]:** A new public interface `de.vvwt.tm.slotopt.SlotOptimizationDispatcherClient` at module root (per DEC-35) + `de.vvwt.tm.slotopt.internal.DefaultSlotOptimizationDispatcherClient` impl, RED-first per DEC-22 Iron Law. Built on Spring Framework 6 `RestClient` (Spring Boot 4.0.5 default; per DEC-29/30 compiler-hygiene + Spotless). Methods sufficient to support Leg 2 routing — story-author chooses precise signatures, recommended set: `KeyRegistration register(...)`, `SubmittedJob submitJob(RawPhaseDef def)`, `Optional<JobResult> pollResult(JobId id)`. NO import of any class from `vvwt-slotopt-dispatcher` (DEC-11 boundary; verified by Maven Enforcer per AC-MAVEN-ENFORCER-RULE).

- [ ] **AC-REGISTER-KEY-WIRE-DEC43-D2 [security, testing]:** RED-first test asserts: `register(...)` POST `/api/register-key` includes `algorithm` field with value "Ed25519" (V1 = single algorithm per DEC-43 D4) per DEC-43 D2 wire schema. Public key bytes generated via `vvwt-slotopt-worker-lib`'s existing `WorkerKeyManager` per DEC-35 naming canon (interface), V1 default Ed25519 — NO new `WorkerKeyManager` impl authored by this story (reuses post-E37S01-rebuilt `vvwt-slotopt-worker-lib` instance).

- [ ] **AC-REGISTER-RESPONSE-PARSED-DEC43-D1 [security, testing]:** RED-first test asserts: registration response body is parsed for the algorithm-list per DEC-43 D1 wire schema (each entry: `algorithm_id`, `display_name`, `deprecation_date`, `parameters`). Response algorithm list is held in a `DispatcherRegistrationContext` (or analogue, story-author names) for downstream consumption by the DEC-43 D3 warning surface (AC-DEC43-D3-WARNING-EVENT). NO separate `GET /api/algorithms` poll endpoint is invoked — DEC-43 D1 mandates the algorithm list arrives WITH the registration response (per Brief F-4 correction).

- [ ] **AC-SUBMIT-JOB-WIRE-DEC9 [testing]:** RED-first test asserts: `submitJob(RawPhaseDef)` POST `/api/submit-job` payload contains the wire-format `{phaseId, rows: [[{group, pos}, ...]]}` per DEC-9 (no UUIDs; structural-tuple-only). Existing `PhaseToRawPhaseDefMapper` (untouched per Pattern C strict-additive) is used to construct the payload from TM domain.

- [ ] **AC-POLL-RESULT-WIRE-FORMAT [testing]:** RED-first test asserts: `pollResult(JobId)` GET `/api/job-status/{id}` parses status-response per E37S08 wire format (`status: RECEIVED | DECOMPOSED | COMPLETED | COMPLETED_FROM_CACHE`); on COMPLETED returns the result permutation; on RECEIVED/DECOMPOSED returns `Optional.empty()`. Polling cadence: story-author chooses (e.g., exponential backoff 1s → 30s, max 5 minutes) — Iron Law AC covers terminal-state contract, not the cadence specifics.

- [ ] **AC-ALGORITHM-MISMATCH-PROPAGATED [security, error-handling]:** RED-first test asserts: when `submitJob` or `pollResult` returns an algorithm-mismatch error (HTTP 400 per E37S09 server enforcement), the dispatcher client wraps it in a documented exception (e.g., `DispatcherAlgorithmMismatchException`) without leaking server-internal detail strings. Caller (RoutingSlotOptimizationClient) catches and falls through to Leg 3 (per AC-LEG-2-FALLS-THROUGH-ON-WIRE-ERROR).

### NEW `DispatcherReachabilityService`

- [ ] **AC-REACHABILITY-SERVICE-AUTHORED [testing, error-handling]:** A new public interface `de.vvwt.tm.slotopt.DispatcherReachabilityService` at module root + `de.vvwt.tm.slotopt.internal.DefaultDispatcherReachabilityService` impl, RED-first per DEC-22. Single method: `boolean isReachable()`. Mechanism (per Brief H-5 — story-author choice): HTTP `GET /actuator/health` OR `HEAD` on dispatcher base URL with short connect+read timeout (configurable via `tm.slotopt.dispatcher.reachability-timeout-ms`, default 2000). Returns `true` on HTTP 200 within timeout; `false` on any non-200, network error, or timeout.

- [ ] **AC-REACHABILITY-NULL-URL-RETURNS-FALSE [error-handling, testing]:** RED-first test asserts: when `tm.slotopt.dispatcher.url` is null (default), `isReachable()` returns `false` immediately without making any HTTP call. Routing falls through to Leg 3.

- [ ] **AC-REACHABILITY-TIMEOUT-OBSERVED [error-handling, testing]:** RED-first test asserts: when the configured URL points to a slow/unresponsive endpoint (e.g., a controlled fixture that delays beyond `reachability-timeout-ms`), `isReachable()` returns `false` within `reachability-timeout-ms + ε` (story-author chooses ε bound — e.g., 500ms — for non-flakiness).

### DEC-43 D3 admin-warning event publication (security per Brief S-3a)

- [ ] **AC-DEC43-D3-WARNING-EVENT [security, testing]:** RED-first test asserts: when `register(...)` response includes a `deprecation_date` that is non-null AND `Instant.now().isBefore(deprecation_date.plusDays(1).atStartOfDay(UTC).toInstant())` per DEC-48 boundary semantics (i.e., the algorithm is still acceptable for new registrations but flagged as deprecated), a Spring `ApplicationEvent` (e.g., `SlotOptimizationDeprecationWarningEvent`) is published containing `algorithmId`, `displayName`, `deprecationDate`, `recommendedMigrationTarget` (derived from non-deprecated subset of announced list, story-author chooses derivation). Test uses a stub registration response with non-null `deprecation_date`; verifies event published via `ApplicationEventPublisher` mock or `@RecordApplicationEvents` Spring test support. Event-publication satisfies DEC-43 D3 protocol-shape compliance ("clear admin warning ... exact warning channel is implementation-specific"); observable admin-UI rendering is a Phase-2+ companion concern when first non-null deprecation_date enters the registry (per AC-DEC43-D3-NO-ADMIN-UI-CONSUMER-IN-S03).

- [ ] **AC-DEC43-D3-WARNING-NEVER-FIRES-AT-V1 [security, governance]:** Documentation comment in `DefaultSlotOptimizationDispatcherClient` (or `DefaultDispatcherRegistrationHandler`, wherever the publication logic lives) explicitly cites: "V1 wire shape per DEC-43 D4 = 'Ed25519' with null deprecation_date → this branch never fires at V1; defensive code per DEC-43 D3 protocol-shape compliance." Per Brief S-3a + Epic Notes.

- [ ] **AC-DEC43-D3-NO-ADMIN-UI-CONSUMER-IN-S03 [governance]:** This story authors only the EVENT-PUBLICATION channel (AC-DEC43-D3-WARNING-EVENT). The admin-UI consumer (banner endpoint + Svelte banner component) is OUT of S03 scope. ### Routing extension in `RoutingSlotOptimizationClient`

- [ ] **AC-ROUTING-EXTENDED-LEG-2 [testing]:** `RoutingSlotOptimizationClient.optimize(phaseId)` is extended (RED-first per DEC-22): for N > `tm.slotopt.exhaustive-max-n`, call `DispatcherReachabilityService.isReachable()`. If `true` → invoke `SlotOptimizationDispatcherClient.submitJob(...)` + poll, return result; if `false` → fall through to existing Leg 3 (S02) `CancelableInProcessSlotOptimizationService`. RED-first tests cover both branches (reachable → Leg 2; unreachable → Leg 3) and the transparent fall-through.

- [ ] **AC-LEG-2-FALLS-THROUGH-ON-WIRE-ERROR [error-handling, testing]:** RED-first test asserts: when Leg 2 dispatcher submission fails post-reachability-check (e.g., dispatcher returns HTTP 500, network error mid-poll, algorithm-mismatch per AC-ALGORITHM-MISMATCH-PROPAGATED), the routing client logs the error with structured detail (algorithm id, wire-error code) AND falls through to Leg 3. The user observes a usable optimization result regardless of dispatcher-side errors. Per Brief T-3: offline-operability is first-class.

## Notes

**Spring `RestClient` vs `WebClient` vs `RestTemplate`:** Spring Boot 4.0.5 default is `RestClient` (synchronous, fluent; replaces `RestTemplate` semantically). `WebClient` (reactive) is alternative if story-author prefers async polling for `pollResult` cadence. Story-author choice; either is DEC-3 compliant (open-source, OSS Apache-2.0 licensed). NO use of legacy `RestTemplate` in new code (per DEC-3 minimal-dependency principle + Spring 6 modern-first guidance).

**DEC-43 D3 V1 effort justification (per Brief S-3a):** ~50 LOC for event publisher + ~1 IT scenario verifying publication on stub-registration-response-with-deprecation. V1 cost ≈ 1 hour Delivery work for protocol-shape compliance even if observable-fire-rate is zero. Alternative (defer to Phase-2+) was considered in Brief but rejected for DEC-43 D3 compliance discipline.

**Polling cadence story-author choice:** Recommended exponential backoff 1s → 5s → 10s → 30s with max wait 5 minutes (typical dispatcher response time per E37 design). If max-wait exceeded → fall through to Leg 3 (per AC-LEG-2-FALLS-THROUGH-ON-WIRE-ERROR analogue). Story-author may make max-wait configurable via `tm.slotopt.dispatcher.poll-max-wait-seconds` (default 300).

**`web/package-info.java` allowedDependencies awareness:** S02 added `"slotopt"` to web's allowedDependencies. S03 does NOT modify web/package-info.java (no new web-layer code in S03 — DEC-43 D3 admin-UI banner is OUT per AC-DEC43-D3-NO-ADMIN-UI-CONSUMER-IN-S03). If story-author judges that an admin-UI banner endpoint IS needed at S03, it would require a new web-layer controller (e.g., `de.vvwt.tm.web.slotopt.DeprecationWarningController`) — but this is OUT-of-scope per the AC.

**DEC-32 NOT invoked:** S03 does not perform mechanical FQN-rewrite on consumer code (no rename of any existing FQN). DEC-32 invocation count stays at 1 (E21S13 only).

**TDD provenance for Routing extension:** `RoutingSlotOptimizationClient` is post-DEC-22 code (authored at E27S01). §refactor-clause for the Leg-2 extension applies (Q-1b refactor on TDD-authored code) — but the Leg-2 logic is NEW behavior, so RED-first new tests are mandatory per Iron Law.
