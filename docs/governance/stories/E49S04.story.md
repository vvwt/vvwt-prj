# Story: Fix — registration & timer QR URLs show `127.0.0.1` instead of a LAN-reachable host

## User Story

**As a** tournament operator,
**I want** the registration-URL QR code (and the Timer-Link QR code) to encode the Tournament Manager's LAN address,
**so that** scoring tablets and timer displays — separate devices on the venue network — can actually open the URL by scanning the code.

---

## Context

**Symptom (verified by user screenshot 2026-05-15 14:47:25):** the admin "Registrierungs-URL" dialog shows `http://127.0.0.1:8080/score/register` and a QR code encoding that same URL. A tablet on the venue LAN that scans the QR code resolves `127.0.0.1` to *itself*, not to the Tournament Manager host — the registration page is unreachable from any device other than the host machine. The Tournament Manager is a self-hosted LAN application (DEC-15); the registration QR is useless unless it carries the host's LAN-reachable address.

**Root cause (verified):**

- `Devices.svelte` builds the registration URL purely client-side as `window.location.origin + '/score/register'` (used both for the QR code generation and for the URL text shown in the dialog).
- `window.location.origin` is whatever address the operator typed to open the admin UI. The operator opened the admin UI via `http://127.0.0.1:8080`, so `origin` is `http://127.0.0.1:8080` and the QR encodes `127.0.0.1`.
- There is **no backend involvement** in constructing this URL and **no configuration property** for a host / base-URL anywhere in the application today.
- `TimerLink.svelte` builds the Timer-Link URL the same way (from `window.location.origin`) — it has the identical latent bug. The human chose (2026-05-15) to fix both in this story.

**Why the fix cannot be purely client-side:** the operator's browser only knows the address the operator used (`127.0.0.1`). Only the server can know its own LAN network address(es). The server must determine a LAN-reachable host and make it available to the admin UI, which then builds the QR/URL from it.

**Chosen approach (human decision, 2026-05-15) — auto-detect with config override:**

- By default, the server detects its own LAN address — a site-local, non-loopback address — and the registration/timer URLs use it. This is zero-configuration for the common single-network-interface host.
- A configuration property (env var / `application.yml`) lets the operator override the detected value with an explicit host. This covers multi-homed hosts (Ethernet + Wi-Fi + Docker/VPN), where interface enumeration is order-non-deterministic and the auto-detected pick may be wrong, and the case where the operator wants a fixed address or hostname.

Rejected alternatives: *auto-detect only* — a wrong interface pick on a multi-homed host cannot be corrected by the operator; *config only* — forces every operator to know and type their LAN IP, defeating zero-configuration onboarding.

This is a Bug-Triage Story. Discovery defines the observable outcome (the registration and timer URLs are LAN-reachable, auto-detected by default and overridable by configuration). Delivery defines the mechanism — how the server detects the address, how the value reaches the Svelte admin UI, and the configuration-property name (see § Notes).

## Notes

**Mechanism guidance (Discovery is non-prescriptive; Delivery picks and records the choice + rationale in the qa-report):**

- *Server-side detection*: enumerate the host's own network interfaces (e.g. `java.net.NetworkInterface.getNetworkInterfaces()`), filter to up, non-loopback interfaces, and select a site-local IPv4 address. `InetAddress.isSiteLocalAddress()` / `isLoopbackAddress()` are the standard predicates. No external call is permitted (AC-SECURITY-LOCAL-ONLY-DETECTION).
- *How the value reaches the Svelte admin UI*: the operator's browser cannot determine the host — the server must supply it. Candidate mechanisms: a small backend endpoint returning the effective host (detected or overridden); injecting the value into the SPA bootstrap/config payload; or extending an existing config/info endpoint. Delivery chooses.
- *Configuration property*: a single override property (suggested name `tm.public-host`, final name Delivery's choice) read from env var / `application.yml`, consistent with the existing `TM_SERVER_PORT` pattern. When set, it wins over detection; when blank/invalid, detection is used (AC-ERROR-INVALID-OVERRIDE-FALLBACK).
- *URL composition*: the final URL = scheme + effective host + server port + path. The server port is already configurable (`TM_SERVER_PORT`); the effective host must combine with it. The displayed URL text and the QR payload must be identical (AC-REGISTRATION-URL-LAN-REACHABLE).

**Multi-NIC determinism (Brief T-1):** on a host with several site-local interfaces (Ethernet + Wi-Fi + Docker/VPN bridges), `NetworkInterface` enumeration order is platform-dependent and not guaranteed to surface the operator's intended LAN interface first. This is an accepted limitation of the auto-detect default — the configuration override is the deterministic remedy, and that is precisely why the hybrid approach was chosen over auto-detect-only.

**Reproduction (manual):**

1. Start the Tournament Manager and open the admin UI via `http://127.0.0.1:8080` (or `http://localhost:8080`).
2. Open the device-management view and trigger the "Registrierungs-URL" QR dialog.
3. Observe the URL `http://127.0.0.1:8080/score/register` and a QR code encoding it.
4. Scan the QR with a phone/tablet on the same LAN — it resolves `127.0.0.1` to the scanning device itself; the registration page does not load. ← bug.

**Test-harness candidates (Delivery's choice):** the host-detection logic is plain backend Java and is unit-testable directly (inject/stub the interface enumeration, or test the site-local/loopback predicate logic and the override-precedence logic). A `vvwt-tm-web` IT may exercise the endpoint/mechanism that surfaces the host to the frontend. The Svelte side may be covered by the existing frontend test setup. The RED test must fail on current production code (which always yields a loopback-derived URL when the admin UI is opened via loopback).

**Estimated LOC:** ~60–150 across a new backend host-detection component + configuration wiring, `Devices.svelte`, `TimerLink.svelte` (and possibly a shared frontend helper), `application.yml`, and test files.
