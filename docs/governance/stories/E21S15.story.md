# Story E21S15: Fix — E21S06 IT test fixtures (DeviceRepositoryIT FK-violation + DeviceAdminControllerIT 409-vs-200) via rebase of PR #59

## User Story

**As a** Wave-2 Track-3 maintainer relying on the Device aggregate
reconstructed in E21S06,
**I want** the two integration-test failures observed on PR #59 fixed via
targeted test-fixture corrections and a clean rebase onto current `staging`,
**so that** PR #59's 1373 lines of RED-GREEN-attested production code land
on `staging` without re-implementing the aggregate, and `mvn verify`
on the merged HEAD is GREEN across the full 546+ test suite.

## Context

E21S06 delivered 13 Device-aggregate classes on branch `story/E21S06`
(PR #59 `OPEN`, not merged) with commits `73e73ac` (RED tests) →
`c04a05f` (GREEN implementation) → `f5e6aea` (delivery artefacts).
DEC-22 RED-before-GREEN attestation is preserved by commit `73e73ac`.
Production code (entity, service, repository, controllers, DTOs,
config, exceptions, web error DTO) is correct by RED-GREEN gate —
not proven bug-free, but validated against its own RED suite.

Two real IT failures observed empirically by the human via
`mvn -pl vvwt-tm-web -am clean verify -B` (deterministic, not
intermittent):

1. **`DeviceRepositoryIT.findByLocationAndField_returnsPresentWhenAssigned`**
   fails with `FK_DEVICES_LOCATION: DEVICES FOREIGN KEY(LOCATION_ID)
   REFERENCES LOCATIONS(ID) — Referential integrity constraint violation`
   at `DeviceRepositoryIT.java:308`. Root cause: the private test helper
   `insertDeviceDirectlyWithLocation` inserts a `devices` row with
   `location_id = UUID.randomUUID()` without first inserting a matching
   parent row in `locations`. Single-test blast radius. Twin test
   `findByLocationAndField_returnsEmptyWhenNone` does not call the helper
   and is unaffected.

2. **`DeviceAdminControllerIT.adminPostLocation_setsLocationIdInDatabase`**
   fails with `expected: 200 OK, but was: 409 CONFLICT`. Code-inspected
   root cause (evidence-favoured hypothesis): the private test helper
   `insertLocationDirectly` has four defects — (i) table name `location`
   (singular) vs real `locations` (plural, V1), (ii) column `name` does
   not exist (real column is `display_name`), (iii) `ON CONFLICT DO NOTHING`
   is Postgres-only syntax (H2 rejects), (iv) `catch (Exception e) { /* best-effort */ }`
   silently swallows all three failures. Result: no `locations` row
   exists at test time; the subsequent admin `POST /api/tm/admin/devices/{id}/location/{lid}`
   triggers an FK violation on `devices.location_id` → mapped to HTTP 409
   by `GlobalExceptionHandler.handleDataIntegrityViolation` (line 165).

Additional code-inspected finding: the private helper
`DeviceRepositoryIT.insertTenantIfMissing` (line 311, called from
`@BeforeEach` line 99) inserts with columns `name` and `subdomain` —
neither exists in the V1 `tenants` schema (which has `display_name`,
`tenant_location_count`, `is_default`, `default_sentinel`, `created_at`).
Every invocation silently no-ops via its `catch (Exception ignored)`
block. The default tenant is actually provisioned by
`DefaultTenantBootstrapRunner` at `@SpringBootTest` context startup
(`INSERT INTO tenants (id, display_name, tenant_location_count, is_default, created_at) …`).
The binder method `TenantContextTestSupport.Binder.bindDefaultTenant()`
only binds an already-provisioned tenant to the current thread via
`TenantContext.bind(UUID)` — it does NOT provision. The helper is
therefore dead code today. It is `private`, with a single call site
(line 99) and the declaration (line 311); zero external references on
`staging`. Safe to remove.

Legacy-Device-Shadow ruled out as a bug source by empirical
bean-name audit: all new `tournament`-context beans are qualified
(`tmDeviceRepository`, `tmDeviceService`, `tmDeviceController`,
`tmDeviceAdminController`); `DeviceLimitConfig` prefix differs
(`vvwt.devices` legacy vs `vvwt.devices.tm` new). No bean-override
conflict possible.

Branch `story/E21S06` is 4 merged PRs behind `staging` (E21S05, E21S07,
E21S09, E21S11). Rebase onto current `staging` HEAD is required.

E21S06's backlog `status: failed` was triggered by a GAAI
`resolve-inner-repo-path` gate-wrapper-rollback bug (fixed in E17S08 /
E17S09), not by the two IT failures. The human authorised the
`failed → superseded` transition for E21S06 on 2026-04-20.

## Notes

**Governance provenance.** E21S06 was marked `failed` on 2026-04-20 due to a
GAAI `resolve-inner-repo-path` gate-wrapper-rollback bug (separately fixed
in E17S08 / E17S09), not because the aggregate implementation was broken.
The human authorised the `failed → superseded` transition on 2026-04-20
(Discovery session `discovery-2026-04-20-e21s06-rework-pfad-a`). This
Story is the narrow Pfad A rework — two test-fixture fixes plus a rebase
that preserves the DEC-22 RED attestation commit `73e73ac`.

**Failure #2 disambiguation is behaviour-gated.** `GlobalExceptionHandler`
maps two distinct exception classes to HTTP 409: `DataIntegrityViolationException`
at line 165 and `ConflictException` at line 197. Discovery's evidence-favoured
hypothesis (FK violation via broken `insertLocationDirectly`) points to the
first path. Because the observed failure log captured only the assertion
side (`expected: 200 OK, but was: 409 CONFLICT`) and not the server-side
stack trace, the fix is gated behind AC-FAILURE-2-EXCEPTION-CAPTURE +
AC-FAILURE-2-SCOPE-GATE. If the captured exception is the `ConflictException`
path or any other class, scope expansion is NOT authorised — escalate.

**`insertTenantIfMissing` removal, not repair.** The helper is private,
single-call-site, dead-code (bootstrap already provisions the default
tenant). Removal is strictly cheaper than repair and aligns with Q-2
(minimal diff) and Q-1 (no silent-catch-masking-as-fixture). Human verified
the no-external-references property on 2026-04-20.

**DEC-22 scope note.** The Iron Law applies to production-class
development (DEC-22: "Every class is developed strict TDD: failing test
written first"). Test-fixture corrections inside already-RED-GREEN-attested
integration tests do not constitute new class development — the Iron Law
does not re-apply to this fix. DEC-32 §e (line 137) confirms DEC-32 "Does
NOT apply to: any change in tests". The RED attestation for the aggregate
itself remains via AC-RED-COMMIT-PRESERVED.

**Rebase strategy rationale.** Force-push to PR #59 is preferred because
it preserves PR identity + CI history + review thread continuity.
Cherry-pick onto a fresh branch is the fallback only if force-push is
blocked. In both paths, preservation of commit `73e73ac` (by tree +
message, not necessarily by SHA) is load-bearing for DEC-22 attestation
and is the hard gate (AC-RED-COMMIT-PRESERVED, AC-BRANCH-STRATEGY).
