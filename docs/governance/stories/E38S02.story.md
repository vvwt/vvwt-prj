# Story E38S02: `vvwt-info-dto` contract — envelope (with `schemaVersion`), sealed `DomainEvent` + `ScheduleEntry` hierarchies, snapshot type, registration types, `AlgorithmDescriptor`, sealed error types

## User Story

**As a** Tournament Manager publisher (and future participant info-portal reader),
**I want** a stable, typed, versioned wire contract in the `vvwt-info-dto` module that captures every Phase 1 cross-subsystem message,
**so that** TM-side publisher code (E38S09) and info-server-side handlers (E38S04, E38S05, E38S06) both compile against the same contract and JSON serialization round-trips identically across both sides.

---

## Context

DEC-42 D2 designates `vvwt-info-dto` as the only allowed cross-subsystem dependency surface. Brief D-22 specifies the package layout (`de.vvwt.info.dto.{envelope, registration, snapshot, event, error}`) and that `ScheduleEntry` and `DomainEvent` are sealed/discriminated polymorphic types per Java 21 (DEC-10). Brief D-21 specifies the schema-versioning strategy. DEC-43 D1 specifies the `AlgorithmDescriptor` field shape.

The DTO module is a pure-Java contract artefact: NO Spring, NO JPA, NO Lombok (project pattern), NO bundled validator implementation. Java records are the immutable-shape default since Java 21. Jackson polymorphic discrimination is wired via sealed-type annotations. Bean Validation API constraints are declared at the field level; the validator IMPLEMENTATION lives in consuming modules (E38S04/S05/S07/S09), not in the DTO module.

## Acceptance Criteria

- [ ] **AC1 (testing)**: Every record type added to `vvwt-info-dto` has a RED-first JSON round-trip test (Jackson `ObjectMapper.writeValueAsString` then `readValue` produces an `equals`-identical instance). RED-state commit hash for each new record cited in `impl-report.md` per DEC-22 Iron Law.
- [ ] **AC2 (testing)**: Polymorphic discriminator dispatch test: `Match`, `SpecialAppointment`, `Pause` (sealed `ScheduleEntry` subtypes) deserialize from their respective discriminator-tagged JSON; an unknown discriminator value produces a Jackson `InvalidTypeIdException` (NOT silent fallback, NOT swallowed by `FAIL_ON_UNKNOWN_PROPERTIES=false` which is an orthogonal Jackson flag — discriminator handling and unknown-property handling are distinct code paths). Same shape for sealed `DomainEvent` (`ScoreUpdated`, `RoundCompleted`, `MatchResultFinalized`, `ScheduleAdded`, `ScheduleRemoved`).
- [ ] **AC3 (testing)**: Forward/backward compatibility test — a deserializer reading a payload that adds an unknown optional field deserializes successfully (Jackson `FAIL_ON_UNKNOWN_PROPERTIES=false`); a missing required field produces a Bean Validation failure with the field name in the error message.
- [ ] **AC4 (governance)**: Package layout exactly `de.vvwt.info.dto.{envelope, registration, snapshot, event, error}` per Brief D-22. No types in other packages. If `module-info.java` is added, it exports only these packages.
- [ ] **AC5 (governance)**: Maven version of `vvwt-info-dto` initialized at `1.0.0`; envelope `schemaVersion` field initialized at `"1.0"` (string form `MAJOR.MINOR`). The two are coupled at major-minor: any breaking change advances both; any additive minor change advances `schemaVersion` minor and Maven minor; PATCH (e.g., `1.0.1`) is wire-invisible — envelope `schemaVersion` continues to read `"1.0"` for any 1.0.x patch release.
- [ ] **AC6 (governance)**: Skill attestation per Epic Success Metrics; DEC-23 / DEC-31 governance propagation per the closure-time single-commit pattern.
- [ ] **AC7 (security)**: `AlgorithmDescriptor` record carries the DEC-43 D1 field shape: `algorithm_id` (String, required, `@NotBlank`), `display_name` (String, required, `@NotBlank`), `deprecation_date` (LocalDate or null, optional), `parameters` (Map<String, Object> or null, optional). Test: deserializing a payload with missing `algorithm_id` produces a Bean Validation error.
- [ ] **AC8 (security)**: `RegistrationRequest` includes `algorithm_id` (required), `public_key` (byte[] or base64-encoded String, required), and `signature` (NULLABLE — first registration is unsigned per Brief D-X4 (b) / DEC-43 D2 absence-of-signature carve-out; subsequent submissions sign per DEC-6 but the registration itself is unsigned). `RegistrationResponse` includes `tournament_token` (NULLABLE — populated by tournament-registration endpoint in E38S05, not by the tenant-registration endpoint in E38S04), `algorithm_warning` (optional `AlgorithmWarning` record with field shape only — `{algorithm_id, deprecation_date, days_remaining}`). **Population semantics for `algorithm_warning` are owned by E38S04** (server-side surfacing logic); this story defines only the field shape.
- [ ] **AC9 (error-handling)**: `ErrorResponse` is a sealed type. Phase 1 closed subtypes: `FullResyncRequired` (returned on 409 per Brief D-9), `RegistrationRejected` (with `reason` field of type **`String`** — open-string rather than closed-enum, per cycle-1 review F-2 — to allow E38S04 / E38S07 to define and extend reason codes without DTO contract revision), `SignatureInvalid`, `SequenceConflict`, `RateLimited` (with `retry_after_seconds: Integer`, `scope: String`).
- [ ] **AC10 (error-handling)**: `Envelope<T>` wraps every cross-subsystem payload: `{schemaVersion: String, payload: T}`. **All publish, snapshot, and reader stream messages are envelope-wrapped.** Snapshot responses are also envelope-wrapped (no "MAY embed" ambiguity). Test: deserializing a payload missing the `schemaVersion` field produces a Bean Validation error.
- [ ] **AC11 (governance)**: `vvwt-info-dto` POM has NO Spring, NO JPA, NO Lombok, NO Hibernate-Validator (or any validator IMPL) dependencies. Verified by `mvn dependency:tree -pl vvwt-info-dto` not listing `org.springframework.*`, `jakarta.persistence-api`, `org.projectlombok:lombok`, `org.hibernate.validator:hibernate-validator`. Runtime deps are exactly: `com.fasterxml.jackson.core:jackson-databind` + `jakarta.validation:jakarta.validation-api`. The validator IMPL is a consumer concern (E38S04 etc.) — Spring Boot 4 starter-validation pulls it in transitively in those modules.

## Notes

- Java records + sealed types (Java 17+, native to Java 21 per DEC-10) support exhaustive pattern matching on consumer side. The publisher (E38S05/E38S09) and reader (E38S06) can `switch` over `DomainEvent` or `ScheduleEntry` subtypes without a default branch when all subtypes are handled — a meaningful correctness guarantee.
- AC9's open-string `reason` field on `RegistrationRejected` is the cycle-1 F-2 fix: avoids hardcoding a Phase-2-changeable reason set into the DTO contract. E38S04, E38S07 etc. define and document their reason codes within their own scope; the DTO carries the string verbatim.
- AC8's nullable `signature` on `RegistrationRequest` is the cycle-1 F-9 fix: removes the smuggled proof-of-possession concern that was inferred when the field was non-nullable. First registration trusts the operator (Brief D-X4 b); subsequent operations sign per DEC-6.
- AC11 dep list is the cycle-1 F-4 fix: validator IMPL is a consumer concern, not a DTO concern. Pulling Hibernate-Validator into DTO would force every consumer (including TM, which has its own Spring-Boot-bundled validator) to inherit it transitively, risking version conflicts.
- Schema versioning rule (AC5): `schemaVersion = "MAJOR.MINOR"` (2-segment) and Maven version = `MAJOR.MINOR.PATCH` (3-segment). PATCH is wire-invisible. Convention enforced by review.
- Performance characteristic: large-snapshot serialization round-trip for a 100-team / 50-round / 1000-match tournament should complete in < 100ms on the reference machine. Soft target documented in `impl-report.md`; not a blocking AC.
