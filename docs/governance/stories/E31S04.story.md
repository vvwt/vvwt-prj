# Story E31S04: Atomic cutover — ScoreEntryService consumer refactor + delete legacy CascadeRecomputeService + ScoringCutoverIT

## User Story

**As a** maintainer of the post-E31 scoring-cascade baseline,
**I want** `de.vvwt.tm.infrastructure.score.ScoreEntryService`
refactored from injecting `de.vvwt.tm.domain.CascadeRecomputeService`
to injecting `de.vvwt.tm.scoring.ScoringService`, the legacy
`de.vvwt.tm.domain.CascadeRecomputeService` deleted in the same
commit, the `de.vvwt.tm.tournament.events.MatchResultChangedEvent`
emission point relocated from legacy to new (if not already handled
inside `DefaultScoringService` per E31S03), and a new
`ScoringCutoverIT` that verifies `DefaultScoringService` is the sole
active scoring-cascade implementation post-cutover,
**so that** the architectural-pivot baseline is complete: no consumer
in the codebase invokes legacy `CascadeRecomputeService`, no class
named `CascadeRecomputeService` exists in `de.vvwt.tm.domain`, and
all six Track-3 consumer contexts continue to compile against the
new `ScoringService` interface (or the unchanged tournament public
API where they did not consume scoring).

---

## Context

E31S04 is the climactic story of E31 — the atomic cutover commit
per DEC-21 § Atomic cutover protocol. All preceding E31 stories
(S01 tournament-side interface extraction; S02 scoring module
declaration; S03 `DefaultScoringService` reconstruction with lock)
built the new path while leaving the legacy path functional. This
story is the single commit on `staging` (per DEC-13) that:

1. **Refactors the only consumer of legacy
`CascadeRecomputeService`** — `ScoreEntryService` — to inject and
use `ScoringService` instead. Pure type-substitution refactor under
DEC-22 §Decision refactor clause and Brief Q-1b. No behavioral
change at the call site (the new `ScoringService.registerMatchResult(...)`
contract matches the legacy `CascadeRecomputeService.registerMatchResult(...)`
contract per E31S03 design).

2. **Deletes legacy `de.vvwt.tm.domain.CascadeRecomputeService`** and
any tournament.internal helper class that was used ONLY by it (must
be enumerated during the inventory pass at the start of this story).

3. **Verifies the cutover via `ScoringCutoverIT`** — a new
end-to-end IT that asserts `DefaultScoringService` is wired in the
Spring context as the active scoring-cascade implementation
(`ApplicationContext.getBeansOfType(ScoringService.class).size() == 1`)
and that an end-to-end submit-set-result flow through `ScoreEntryService`
produces the expected DB state (verified via assertj-db).

4. **Consumer type-substitution under DEC-22 §Decision refactor
clause (NOT DEC-32 invocation).** The substitution from
`de.vvwt.tm.domain.CascadeRecomputeService` (concrete class) to
`de.vvwt.tm.scoring.ScoringService` (interface) in `ScoreEntryService`
(the sole consumer per Brief H-1d's expected inventory finding)
is type-substitution-with-equivalent-contracts. Per Brief Cycle-1
reviewer F-S04-2 reclassification, this is DEC-22 §Decision
refactor-clause Q-1b territory — NOT DEC-32 mechanical-FQN-rewrite.
DEC-32's purpose is pure-textual relocation within an unchanged
TYPE (e.g., `de.vvwt.tm.X.Foo` → `de.vvwt.tm.Y.Foo` — same `Foo`).
E31S04 substitutes between DIFFERENT TYPES (concrete class →
interface) that share the cascade method signature by E31S03 design.
DEC-32 invocation count therefore REMAINS at #1 (E21S13) post-E31;
DEC-32 review-trigger fires only after a future genuinely-mechanical
FQN-rewrite invocation (likely E22 or E23 atomic cutover).

5. **Pre-commit inventory-validity grep per E21-Retrospective
Adjustment Proposals 1+2.** Before assembling the cutover commit,
Delivery runs a supplementary `grep -rn "de\.vvwt\.tm\.domain\.CascadeRecomputeService" src/main/java/`
to surface any consumer file added since E31S01 inventory. Any hit
that is NOT in the expected consumer set (`ScoreEntryService`
only per H-1d) is flagged for pre-enumeration authorization before
the cutover commit is assembled. This is a binding AC, not an
execution-plan note (per E21-Retro Adjustment Proposal 2 hard
lesson).

## Acceptance Criteria

### Atomicity (governance — DEC-13 + DEC-21)

- [ ] AC-ATOMICITY (governance — DEC-13 + DEC-21 § Atomic cutover):
  The cutover lands as ONE commit on `staging` (in `vvwt-prj`)
  that simultaneously:
  (a) refactors `ScoreEntryService` to inject and use
    `ScoringService` (interface from `de.vvwt.tm.scoring.*`);
  (b) deletes
    `vvwt-tm-web/src/main/java/de/vvwt/tm/domain/CascadeRecomputeService.java`;
  (c) deletes any tournament.internal helper file that was used
    ONLY by the legacy `CascadeRecomputeService` (enumerated in
    AC-CUTOVER-INVENTORY-DELETIONS below);
  (d) adds `ScoringCutoverIT` (new IT class) and any test-fixture
    updates necessary for the consumer refactor.
  `git show --stat <cutover-commit>` lists ALL of the above.
  No intermediate "delete-only" or "rewrite-only" commits exist.

### Pre-commit inventory validity (E21-Retrospective Adjustment Proposals 1 + 2)

- [ ] AC-CUTOVER-INVENTORY-CONSUMER-GREP (governance — error-
  handling): Before assembling the cutover commit, Delivery runs
  `grep -rn "de\.vvwt\.tm\.domain\.CascadeRecomputeService" vvwt-tm-web/src/`
  AND `grep -rn "import de\.vvwt\.tm\.domain\.CascadeRecomputeService"
  vvwt-tm-web/src/`. The resulting hit list is included in the
  story's impl-report as a table with columns `file`, `line`,
  `match-text`, `consumer-classification` (`expected` /
  `unenumerated`). Expected per H-1d: only `ScoreEntryService.java`
  and possibly its tests. Any `unenumerated` hit BLOCKS commit
  assembly and triggers escalation per Brief Q-6. The grep MUST be
  re-run immediately before commit assembly with no other changes
  intervening on staging — if `git fetch origin staging` shows
  staging has advanced between the inventory grep and the commit
  assembly, the grep MUST be re-run on the new staging head. The
  final grep output captured for the impl-report MUST correspond to
  the staging head SHA at commit-assembly time (the SHA is
  documented in the impl-report alongside the grep results).
- [ ] AC-CUTOVER-INVENTORY-DELETIONS (governance — error-handling):
  Before assembling the cutover commit, Delivery enumerates which
  tournament.internal helper classes were used ONLY by legacy
  `CascadeRecomputeService` (e.g., AuditLogEntry / AuditLogRepository
  if they were promoted to public API in E31S01 with the legacy as
  sole consumer; if they remain internal and have other consumers,
  they stay). The enumeration uses an inverse-call-graph procedure
  (documented in impl-report): for each candidate helper class H,
  run `grep -rn 'import.*\.H\b' vvwt-tm-web/src/main/java/ |
  grep -v 'CascadeRecomputeService.java' | grep -v 'H.java'`.
  If empty, H was used ONLY by `CascadeRecomputeService` and is
  deletable in this commit. If non-empty, H has other consumers and
  is PRESERVED. The output table (one row per candidate H, columns:
  `helper FQN`, `inverse-grep result`, `delete-decision`) lands in
  the impl-report. Files in the `delete=Y` set are deleted by the
  cutover commit; files in `delete=N` are PRESERVED untouched.

### Consumer refactor (Q-1b)

- [ ] AC-SCOREENTRY-CONSTRUCTOR (governance — DEC-35 + Q-1b):
  `ScoreEntryService` constructor parameter
  `CascadeRecomputeService cascadeRecomputeService` is replaced
  with `ScoringService scoringService` (or equivalent renamed
  field). All usages of `this.cascadeRecomputeService.registerMatchResult(...)`
  become `this.scoringService.registerMatchResult(...)`. No method
  signature changes on `ScoreEntryService` itself.
- [ ] AC-SCOREENTRY-TESTS-GREEN (testing — error-handling):
  Existing `ScoreEntryService` unit/integration tests remain GREEN
  after the consumer refactor. If any test referenced
  `CascadeRecomputeService` as a `@MockitoBean`, the mock target is
  changed to `ScoringService`; assertions are unchanged unless the
  legacy class's specific implementation behavior was being tested
  (in which case the test is moved or rewritten to target
  `DefaultScoringService` directly per same-package-white-box rule
  in DEC-36).

### Legacy deletion

- [ ] AC-DELETE-CASCADERECOMPUTESERVICE (governance — DEC-21
  + DEC-13): The file
  `vvwt-tm-web/src/main/java/de/vvwt/tm/domain/CascadeRecomputeService.java`
  is deleted in the cutover commit. Verifiable via `git show --name-status
  <cutover-commit> | grep "^D.*CascadeRecomputeService"`.
- [ ] AC-DELETE-LEGACY-HELPERS (governance): Any tournament.internal
  helper file enumerated by AC-CUTOVER-INVENTORY-DELETIONS is also
  deleted in the same commit.

### Consumer type-substitution (DEC-22 §Decision refactor clause, NOT DEC-32)

- [ ] AC-CONSUMER-REFACTOR-CLASSIFICATION (governance — DEC-22 +
  Brief Q-1b): The consumer-type-substitution in `ScoreEntryService`
  (`CascadeRecomputeService` concrete class field → `ScoringService`
  interface field) is classified as DEC-22 §Decision refactor-clause
  Type-Substitution per Brief Q-1b — NOT as DEC-32 mechanical
  FQN-rewrite. Rationale (Brief Cycle-1 reviewer F-S04-2): DEC-32
  governs PURE textual relocation within an unchanged TYPE (e.g.,
  `de.vvwt.tm.X.Foo` → `de.vvwt.tm.Y.Foo` — same `Foo` class,
  different package). E31S04's substitution moves between DIFFERENT
  TYPES (concrete `CascadeRecomputeService` class → `ScoringService`
  interface) that share method signatures by E31S03 design. This is
  type-substitution-with-equivalent-contracts, the textbook fit for
  Q-1b refactor classification. DEC-32 invocation count therefore
  REMAINS at #1 (E21S13) post-E31; the next DEC-32 invocation is
  expected at E22 or E23 atomic cutovers.
- [ ] AC-REFACTOR-MECHANICAL-PROOF (governance — DEC-22 refactor
  clause): The substitution diff produced by E31S04's commit is
  verifiable as PURELY MECHANICAL: only (a) one import line
  change, (b) one field-type declaration change, (c) one
  constructor-parameter-type declaration change, (d) zero
  call-site signature changes (the new `ScoringService.registerMatchResult(...)`
  matches the legacy `CascadeRecomputeService.registerMatchResult(...)`
  signature exactly per E31S03 AC-INTERFACE-EXISTS contract). Any
  observed non-mechanical change BLOCKS commit and triggers
  escalation per DEC-22 refactor-clause STOP discipline.
- [ ] AC-COVERAGE-DISCLOSURE (governance — error-handling): The
  impl-report documents the pre-cutover Jacoco line-coverage for
  `ScoreEntryService` and the new `DefaultScoringService` (the
  refactored consumer + the new bean it consumes). Per E21-Retro
  Appendix DEC-32 §(e) precedent for low-coverage disclosure: if
  ScoreEntryService coverage <70%, this is FLAGGED in the impl-
  report. Remediation: ≥1 net-new IT against `ScoreEntryService`
  exercising the post-refactor flow MUST land in the same E31S04
  commit (the `ScoringCutoverIT` per AC-SCORINGCUTOVERIT covers
  this requirement — it boots full-context and submits via
  `ScoreEntryService`). With ScoringCutoverIT in place, the <70%
  flag is acknowledged-and-mitigated.

### Cutover verification

- [ ] AC-SCORINGCUTOVERIT (testing — error-handling): The new
  `ScoringCutoverIT` exists at
  `vvwt-tm-web/src/test/java/de/vvwt/tm/scoring/internal/ScoringCutoverIT.java`
  (or equivalent path within scoring-module test scope). The IT:
  (a) Boots via `@SpringBootTest` (full-context required for
    end-to-end flow);
  (b) Asserts
    `applicationContext.getBeansOfType(ScoringService.class).size() == 1`
    and that the bean is an instance of
    `de.vvwt.tm.scoring.internal.DefaultScoringService`;
  (c) Submits a set-result via `ScoreEntryService`, verifies the
    expected post-cascade DB state via assertj-db (per DEC-26
    independent-verifier rule).
  (Note: the previous-cycle reflection-check sub-clause "no class
  named CascadeRecomputeService is loaded in the context" was
  removed as tautological — once the .java file is deleted per
  AC-DELETE-CASCADERECOMPUTESERVICE and `mvn verify` passes per
  AC-MVN-VERIFY-GREEN, no bytecode for the legacy class exists on
  the classpath. The compile-time + verify gates already provide
  this guarantee; runtime reflection check would be performative.)
- [ ] AC-EXISTING-SMOKE-ITS-GREEN (testing — error-handling):
  `TournamentCutoverSmokeIT`, `TournamentCrossContextSmokeIT`, and
  `CascadeLockIT` (from E31S03) all remain GREEN post-cutover.
  Any failure indicates the cutover is incomplete or breaks a
  consumer-context expectation.
- [ ] AC-MVN-VERIFY-GREEN (testing — error-handling): `mvn verify`
  runs green post-cutover. `ApplicationModules.of(...).verify()`
  green.

### Bean-uniqueness (governance — DEC-21 § Atomic cutover)

- [ ] AC-NO-DUPLICATE-SCORING-BEAN (governance — DEC-21): Post-
  cutover, exactly ONE `ScoringService` bean exists in the Spring
  ApplicationContext. The legacy `CascadeRecomputeService` bean
  no longer exists (because the class is deleted). No `@Primary`,
  `@Profile`, or `@ConditionalOn*` annotations remain on
  `DefaultScoringService` from any transitional state.

### Event publication continuity

- [ ] AC-EVENT-EMISSION-MIGRATED (testing — error-handling +
  governance): The `MatchResultChangedEvent` emission point that
  was in legacy `CascadeRecomputeService` (Step 12 per its Javadoc
  line 453-458) is verified-present in the new
  `DefaultScoringService.registerMatchResult(...)` post-cutover.
  Verification: read `DefaultScoringService` source post-cutover
  and confirm `eventPublisher.publishEvent(new MatchResultChangedEvent(...))`
  call exists at the equivalent point in the new cascade flow.
  If E31S03 absorbed the event-emission migration (most likely —
  the event is part of the cascade behavior that S03 reconstructs
  test-first), this AC is verifiable by reading post-S03 state. If
  E31S03 did NOT migrate the emission, this AC blocks E31S04
  cutover and triggers an S03 retro-amendment story before the
  cutover commit can land. End-to-end verification: existing
  `DomainEventBridge` listener (`@EventListener` per the bridge's
  Javadoc) MUST receive the event after a `ScoreEntryService.submit(...)`
  call — `ScoringCutoverIT` (per AC-SCORINGCUTOVERIT) covers this
  via its end-to-end flow with assertion on event-listener
  invocation (or via observable side-effect like WebSocket push,
  per the bridge's behavior).
