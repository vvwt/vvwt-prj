# Story: A newly registered scoring tablet appears on the admin Devices page live, without a manual reload

## User Story

**As an** operator managing scoring tablets,
**I want** a newly registered tablet to appear on the admin Devices page immediately,
**so that** I can assign it to a field without having to reload the page.

---

## Context

A scoring tablet registers itself via `/score/register`. The admin Devices page is meant to
update live: it holds a WebSocket subscription and reloads its device list when it receives
a device-registered notification. In practice a newly registered tablet does not appear on
an already-open Devices page until the operator manually reloads the browser.

Per the Discovery session of 2026-05-17 (Brief O-1), the live-update chain is wired except
for the producing end — the registration flow does not emit the notification the admin page
is waiting for. The fix closes that gap. Delivery re-confirms the exact gap at HEAD rather
than assuming a pre-supplied fix.

---

## Acceptance Criteria

- [ ] AC1 (reproduction): Given an operator has the admin Devices page open, when a scoring
  tablet completes registration via `/score/register`, then the new device currently does
  NOT appear in the Devices list until the page is manually reloaded — this is the defect.
- [ ] AC2 (expected — live update): After the fix, in that same scenario the newly
  registered device appears in the admin Devices list without any manual reload.
- [ ] AC3 (fresh audit): The registration-to-admin-notification path is re-examined at
  delivery HEAD; the specific gap that suppresses the live update is identified and closed
  so that completing a registration causes an open admin Devices page to refresh. No
  pre-supplied fix is assumed.
- [ ] AC4 (no regression): Device registration still persists the device correctly — unique
  device token, scoring-tablet PIN and name, `REGISTERED` status, tenant scoping, and a
  null location at registration per DEC-24 — and still returns its registration response;
  the live notification is purely additive.
- [ ] AC5 (error-handling): If publishing or delivering the live notification fails (e.g.
  a messaging-broker error), the device registration itself still succeeds and is
  unaffected; a registration completed while no admin client is connected simply finishes
  with no live update to deliver.
- [ ] AC6 (testing): The behaviour is covered by tests authored failing-first per DEC-22 —
  a completed registration produces the admin-facing device-registered notification — using
  the project's existing test surface for this area; any behaviour not reachable by that
  surface is verified and recorded in the impl-report.
- [ ] AC7 (governance — no test-only code): No production method, constructor, or field is
  introduced that exists solely to satisfy tests (DEC-70).
- [ ] AC8 (governance — build gate): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS
  (DEC-54, DEC-71).

> All acceptance criteria must be verifiable.

---

## Out of Scope

- The `Devices.svelte` admin-page logic itself — its WebSocket subscription and list-reload
  behaviour already work; this story only makes registration emit the notification.
- The `/score/register` page layout, the device-location-assignment workflow, and the
  device limit / PIN logic.

## Notes

Per Brief O-1, the event class, the admin-topic event bridge, and the admin page's
subscription all exist; the registration service simply does not publish the event. AC3 is
deliberately a fresh-audit criterion (per memory `feedback_no_precomputed_inventory_in_stories`
and `feedback_subagent_no_precomputed_findings`): the story carries the behavioural
requirement, not a baked-in "add a publish call" instruction — Delivery verifies the gap at
HEAD and chooses the implementation. DEC-40 governs where the publication and any event type
live (bounded-context module, not the controller). `mvn verify` is the build gate per
DEC-54 / DEC-71.
