# Story E53S05: Fix: Mannschaftsfoto-Zeitplan link missing on print-index for newly created tournaments — admin-UI Vorbelegung of FIRST_FREE_ROUND ActivityType analogous to Optimization

## User Story

**As a** Tournament Organizer creating a new tournament,
**I want** the Mannschaftsfoto activity-type to be pre-selected in the admin form by default,
**so that** the Mannschaftsfoto-Zeitplan link renders on the print-index page without manual configuration after tournament creation.

---

## Context

User reported on 2026-05-10 (screenshot `Bildschirmfoto_2026-05-10_18-48-16.png`) that the print-index page ("Druckdokumente") for a freshly created tournament shows only the "Spielplan (Laufzettel)" link — the "Mannschaftsfotos" / "Mannschaftsfoto-Zeitplan" link is absent.

### Pre-E53 vs post-E53 behavior

- **Pre-E53S03**: the print-index always rendered a `Mannschaftsfotos` `<li>` with an `href` to `/fotos` — but `/fotos` was a dead 404 endpoint. PrintController source comment from that era explicitly read "dead link per legacy".
- **E53S03 (merged)**: the print-index conditional now resolves `fotosUrl` to the working `/print/tournaments/{tid}/activity-schedule/{photoTypeId}` endpoint when an `ActivityType` with `assignment_rule = FIRST_FREE_ROUND` exists. When no such `ActivityType` is configured, `fotosUrl` is omitted and the `<li>` is hidden (per `print/index.mustache:46` `{{#fotosUrl}}…{{/fotosUrl}}`). This is correct UX for "no photo schedule available".

### Why this is a bug

Typical newly created tournaments do not include a `Mannschaftsfoto` `ActivityType`. There is no Flyway migration that seeds one (verified: `grep -rn FIRST_FREE_ROUND vvwt-tm-web/src/main/resources/db/migration/` returns 0 matches). Operators expect a Mannschaftsfoto-Zeitplan to be available out-of-the-box for ordinary tournaments — the same way the Optimization activity-type is pre-selected today (user-confirmed pattern: "Vorbelegung:true analog zur Optimierung").

### Root principle (from Brief D-0)

Print is a downstream observer; root cause for this defect lives in the **CONFIG layer** — typical tournaments lack the required `ActivityType`. The fix surface is the admin-side tournament-creation flow (this story is a bug-triage exception to E53 Epic's "admin-UI Svelte = E52 territory" carve-out, see Notes).

### Codebase entry points (informational only — Delivery picks the implementation shape)

- `PrintController.java:221-227` — `printIndex()` resolves photo activity-type via `AssignmentRule.FIRST_FREE_ROUND` + min `sortOrder`.
- `print/index.mustache:46` — `<li>` rendered conditionally on `fotosUrl`.
- `vvwt-tm-web/src/main/ui/src/routes/TournamentForm.svelte` — Svelte tournament-creation form (likely admin-UI fix locus, but Delivery may also touch BE seeding hooks).
- `de/vvwt/tm/tournament/activity/ActivityType.java` + `ActivityTypeService.java` — backend persistence + service layer.
