# Story E38S09: `vvwt-tm-web` publisher integration — `info-portal.url` config + Ed25519 keypair management with NO-PLAINTEXT-ON-DISK invariant (D-X7) + signed REST publisher service using RFC 8785 JCS canonical signature (D-X6) + tournament-registration via dedicated endpoint (D-X2 c) + per-tournament seq state in `info_portal_state` table + 409 FULL_RESYNC handling via snapshot-recovery (D-X8 c — no outbound queue) + algorithm-deprecation-warning Svelte UI surface in TM admin

## User Story

**As a** Tournament Manager (TM) operator who has enabled the public-info-portal feature,
**I want** my TM instance to register itself with the configured info-server URL using a generated Ed25519 keypair (never stored in plaintext on disk), then explicitly register each tournament via the dedicated tournament-registration endpoint to obtain `tournament_token` + `per_tournament_secret` for QR-code generation BEFORE the tournament starts, then push tournament events as signed REST POSTs (RFC 8785 JCS canonical signature) with transparent recovery from info-server restarts via snapshot rather than queueing,
**so that** participants reach the public-info-portal URL pre-tournament and see correct, current data without me managing uploads or reacting to silent server losses.

---

## Context

DEC-42 D2 specifies the only allowed cross-subsystem dependency edge: `vvwt-tm-web` MAY depend on `vvwt-info-dto`. Brief D-15 specifies global per-TM-instance config for `info-portal.url`. Brief D-16 specifies NO hardcoded primary URL default. Brief D-9 + D-X8 (c) specifies the publisher's resync flow on `409 FULL_RESYNC`: TM responds by posting current snapshot via `/snapshot` endpoint — **no outbound queue** (D-X8 c — TM is the source-of-truth, snapshot recovery covers state divergence; intermediate events during outage are accepted-as-lost-as-discrete-events, final state is preserved).

**Brief D-X2 (c) tournament-registration via dedicated endpoint** (per E38S05): TM calls `POST /api/v1/tournaments/{tenant}/{location}/{tournament-id}/register` AFTER successful tenant-registration to mint `tournament_token` + `per_tournament_secret`. TM then derives team URLs locally via `team_token = HMAC-SHA256(per_tournament_secret, team_uuid)` per Brief D-X3 (c1).

**Brief D-X4 (b) first registration unsigned** (operator-trust); subsequent operations signed per DEC-6.

**Brief D-X6 (a) RFC 8785 JCS** for signature payload — TM-side and server-side use the same library version pin (`io.github.erdtman:java-json-canonicalization`).

**Brief D-X7 (a) NO-PLAINTEXT-ON-DISK invariant**: TM-side private key MUST NOT be stored in plaintext at rest. Implementation may use AES-GCM encryption-at-rest (with a key wrapped by an OS keystore or operator-supplied passphrase) OR filesystem permissions `0600` ON A KEYFILE WHOSE BYTES ARE NOT THE RAW PRIVATE KEY (e.g., wrapped/encrypted form). The invariant is pinned; the scheme is implementation choice documented in `impl-report.md`.

**Brief D-X8 (c) NO outbound queue**: under sustained 5xx, TM logs failures + admin-UI alert + retries-with-backoff. When info-server returns, the next event's seq is ahead of `last_applied_seq` → 409 FULL_RESYNC → TM posts current snapshot.

The TM admin UI is **Svelte+TS per DEC-2** (corrects cycle-1 F-2 Vaadin reference); deprecation warnings surface via the existing TM admin notification component.

  - `info-portal.url` — required string; no default; missing config → publisher feature disabled (logged INFO at startup; admin UI shows feature-disabled state).

  - `info-portal.location-id` — required string per Brief D-2 (location-id always non-null in registration tuple).

- [ ] **AC7 (governance)**: Skill attestation per Epic Success Metrics; DEC-23 / DEC-31 governance propagation. **DEC-26 + DEC-46 DAO IT three-rule scope-extension** for the new TM-side `info_portal_state` table per AC12 — applied via either reusing TM's existing `TenantDaoTestSupport` (since TM is DEC-20 DB-per-Tenant, eligible per DEC-46 clause #2(a)) OR a TM-internal helper utility. - [ ] **AC8 (security)**: **Ed25519 keypair management with NO-PLAINTEXT-ON-DISK invariant** per Brief D-X7 (a): TM generates keypair on first-publish-attempt via `KeyPairGenerator.getInstance("Ed25519")` (JDK 21 native). Private key is stored either: (a) AES-GCM encrypted at rest with a wrap-key from OS keystore or operator-configured passphrase, OR (b) a filesystem keyfile at `0600` perms whose bytes are the WRAPPED form (NOT raw private key). **AC test**: an integration test asserts the on-disk representation does NOT contain the raw private-key bytes — read the on-disk bytes; assert they do NOT byte-equal the in-memory raw private-key bytes (within a configurable byte-window scan to defeat trivial obfuscation). Implementation scheme documented in `impl-report.md`.
- [ ] **AC9 (security)**: **Per-request signing with RFC 8785 JCS canonical bytes** (D-X6 a, matching E38S05 server-side): each publisher REST POST signs `JCS(envelope_body)` (using `io.github.erdtman:java-json-canonicalization`, **same library version pin as E38S05**); `X-Vvwt-Signature: <base64>` header set. IT test: corrupt body byte during transit (Spring `RestTemplate` interceptor injects bad-byte) → server returns 401. Plus: cross-implementation byte-stability via the shared fixture from E38S05 AC8 — TM-side signing of the same fixture produces byte-identical signed-bytes as the server-side verifier expects.
- [ ] **AC10 (security)**: **Algorithm-deprecation handling**: when registration response indicates active algorithm has `deprecation_date` set, AND the date is within `info-portal.deprecation-warning-threshold-days` (default 30), TM admin Svelte UI displays HIGH-severity warning. Beyond `deprecation_date`, registration would fail with 410 — TM publisher service stops attempting publishes and surfaces admin-actionable error per AC11.
- [ ] **AC11 (error-handling)**: **Comprehensive 4xx/5xx handling on publisher requests**:
  - 401 SignatureInvalid → log error; admin UI: "info-server signature mismatch — keypair may have changed; re-register manually" (Phase 2+ adds auto-re-registration).
  - 409 FULL_RESYNC → automatic snapshot post per AC3.
  - 403 RegistrationRejected → admin UI shows actionable diagnostic per `rejection_reason` (TENANT_LIMIT_EXCEEDED / KEY_MISMATCH / INVITATION_INVALID).
  - 410 ALGORITHM_DEPRECATED → admin UI: hard error; publisher stops; operator must rotate to non-deprecated algorithm (Phase 2+).
  - 429 RateLimited → exponential backoff + retry per `Retry-After` header; capped at 5 retries within 5-minute window before giving up and admin-UI alert.
  - 5xx → exponential backoff + retry indefinitely; admin-UI "publisher unhealthy" indicator after 5 consecutive failures within 5-minute window. **NO outbound queue**: events emitted during sustained 5xx are NOT buffered; once 5xx clears AND TM emits its next event normally, the seq mismatch triggers 409 FULL_RESYNC → snapshot recovery (AC3 path) per D-X8 (c).
- [ ] **AC12 (error-handling)**: **Per-tournament seq state persistence in TM-side `info_portal_state` table** (cycle-1 F-7 source clarification). Schema: `(tenant_id, location_id, tournament_id PK, last_published_seq BIGINT, tournament_token VARCHAR, per_tournament_secret BYTEA, last_published_at TIMESTAMP, registration_status VARCHAR)`. **Seq generation source**: monotonic per-`(tenant_id, location_id, tournament_id)` from TM's own event stream — TM assigns `seq` at TM-event-emit time (atomic `UPDATE info_portal_state SET last_published_seq = last_published_seq + 1 RETURNING last_published_seq`), THEN posts. **On 409 FULL_RESYNC**: TM does NOT reset seq to 1; TM posts the snapshot at the CURRENT `last_published_seq` value; server's `/snapshot` endpoint accepts the seq verbatim and sets info-server's `last_applied_seq = N`. Subsequent deltas continue at `seq = N+1`. The seq number is preserved across recovery, not reset.
- [ ] **AC13 (error-handling)**: **Idempotent publisher**: if TM attempts to re-publish a delta with `seq` already applied (e.g., TM-side network retry without local seq advance), the info-server's seq monotonicity check catches it (409 FULL_RESYNC). Test asserts retrying a successful publish does NOT advance TM's `last_published_seq` AND does NOT generate a duplicate delta on the info-server.

## Notes

- TM's `info_portal_state` table lives in TM's per-tenant DB (DEC-20 DB-per-Tenant unchanged). DEC-26 three rules apply via TM's existing `TenantDaoTestSupport` per DEC-46 clause #2(a).
- TM-side keypair: one keypair per TM instance is the simplest Phase 1 design. Storage location: TM-internal config table or filesystem keyfile per AC8.
- TM publisher service lifecycle: Spring `@Service` bean activated when `info-portal.url` is configured. Listens to TM's own internal domain events; converts to `vvwt-info-dto.DomainEvent` instances; posts.
- AC2 Testcontainers vs stub: cycle-1 F-2 fix — Testcontainers gives byte-equivalence to production; stubs risk contract drift. Real Spring Boot image used.
- AC9 cross-implementation byte-stability: the shared JCS fixture file from E38S05 AC8 is reused here; TM-side signing produces the SAME canonical bytes server-side verifier expects. Library version pin guarantees this.
- AC11 5xx exponential-backoff: standard pattern (initial 1s, ×2 with full-jitter, cap 60s, retry indefinitely). After 5 consecutive failures within 5-minute window → admin-UI indicator. NO max-retries on 5xx since the assumption is "operator will fix or shut down".
- AC12 seq generation source clarification (cycle-1 F-7): TM assigns `seq` BEFORE posting (atomic UPDATE-RETURNING). On 409 FULL_RESYNC, the seq is NOT reset to 1 — the snapshot post carries the current `last_published_seq`, and the info-server overwrites its `last_applied_seq` to that value. Continuity preserved across recovery.
- AC10 deprecation-warning threshold (default 30 days): tunable via `info-portal.deprecation-warning-threshold-days`. Operator with longer migration cycles can extend; tighter operators can shrink. The threshold determines UI prominence — DEC-43 D3 mandates the warning regardless of threshold.
- The AC4 Svelte admin UI integration: TM admin UI is Svelte+TS per DEC-2. The notification component reads from a TM-side REST endpoint exposing publisher status; Svelte store displays warnings. NO Vaadin (corrects cycle-1 F-2).
