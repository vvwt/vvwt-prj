# Story E14S03: AbstractRoutingDataSource wiring + TenantContext propagation — tests first

## User Story

**As a** data-accessing service (repositories, DAOs) anywhere in the TM backend,
**I want** my injected `DataSource` to transparently route to the current tenant's physical DB without me knowing anything about tenancy,
**so that** I can write plain Spring repository code against the standard `DataSource` abstraction and still get strict per-tenant isolation.

---

## Context

DEC-20 mandates `AbstractRoutingDataSource` keyed on `TenantContext.current()` as the connection-level isolation mechanism. Per-tenant `EntityManagerFactory` was explicitly rejected — all JPA metadata is shared; isolation is purely at the connection layer.

This story wires the routing DataSource and the `TenantContext` propagation that feeds it. `TenantContext` itself was specified as an interface in E14S01; this story provides the implementation — a `ThreadLocal`-backed holder with the proper lifecycle (bind on request entry or operation start, clear on exit) — plus the Spring `@Bean` definition for the routing DataSource.

Per DEC-22 tests are first. Tests here must exercise real routing behaviour: bind tenant A, execute a query, bind tenant B, execute another query, assert the underlying connection resolved to distinct targets.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows failing tests for `TenantContext` bind/clear semantics and for the routing DataSource lookup-key behaviour before their implementation commits. Spot-check on `TenantContext` and on `RoutingTenantDataSource` (or equivalent name) confirms red-then-green ordering.

- [ ] AC2 (data-isolation — routing proof): An integration test registers two test tenants (A, B) via `TenantRegistryPort`, binds `TenantContext` to A, writes a marker row, binds to B, writes a different marker row, then reads from both with the corresponding contexts and asserts each sees only its own row. Switching context without clearing does not leak connections across tenants.

- [ ] AC3 (error-handling — unbound propagation): When a query executes with no tenant bound, the routing DataSource surfaces the typed exception from `TenantContext.current()` defined in E14S01 — NOT a NullPointerException and NOT a fallback to a "default" DataSource. Test asserts the exception type.

- [ ] AC4 (error-handling — context leak): After a unit of work completes (successful or exception), `TenantContext.current()` returns to the unbound state. A test verifies this by executing a tenant-scoped operation that throws and asserting the next `current()` call raises the unbound exception (not the previously-bound tenant).

- [ ] AC5 (testing — Modulith verify): `ApplicationModulesTest` remains green. The routing DataSource bean is registered in `de.vvwt.tm.tenant.internal` and exposed only through Spring injection — no cross-module import of the routing class.

- [ ] AC6 (governance — internal placement): `RoutingTenantDataSource` (or equivalent), the `TenantContext` implementation, and any Spring configuration class live under `de.vvwt.tm.tenant.internal`. The root `de.vvwt.tm.tenant` package gains no new types.

- [ ] AC7 (governance — consume E14S01 nested-bind contract unchanged): The `TenantContext` implementation honours E14S01's AC-NESTED-BIND contract (re-entrant binding with outer-scope restoration on close). E14S03 does NOT re-open or refine this contract — it implements the interface as-specified in E14S01's Javadoc. A unit test exercises nested bind+close pairs (outer, inner, close inner, assert outer active, close outer, assert empty).

- [ ] AC8 (governance — no JPA EMF changes): No new `EntityManagerFactory` is introduced. The routing DataSource is wired into the existing `EntityManagerFactory` / `DataSource` chain per DEC-20's "shared JPA metadata, connection-level isolation" contract.

## Notes

`ThreadLocal`-based context propagation works for synchronous Spring code. If future async processing (e.g., scheduled jobs) crosses thread boundaries, propagation has to be solved per-usage site — that is not a Wave-1 concern. Document the limitation in Javadoc.

The test suite should prefer real H2 file DataSources under `@TempDir` over mocks — the isolation claim is only credible if exercised against actual JDBC connections.
