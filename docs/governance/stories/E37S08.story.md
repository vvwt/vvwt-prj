# Story E37S08: packet package — PacketDecomposerService + PacketRecord + PacketRepository + PacketTimeoutSweeper + PullPacketController/Service with supportedAlgorithms[] capability advertisement (Q-1a TDD RED-first against spec)

## User Story

**As a** worker polling the dispatcher for compute work,
**I want** to advertise my supported signature algorithms in the pull-packet request (or omit the field for V1 backward-compat default `["Ed25519"]`) and receive an unclaimed packet from a decomposed job,
**so that** the dispatcher can route packets that I am cryptographically capable of signing the result for, AND that orphaned-claim packets eventually get reissued to other workers via the timeout sweeper.

---

## Context

The packet package owns: PacketDecomposerService (decomposes a JobRecord into N PacketRecords), PacketRecord entity, PacketRepository, PacketTimeoutSweeper (background reissue job), PullPacketController (HTTP `POST /api/pull-packet`), PullPacketService, PullPacketRequest/Response DTOs (with `supportedAlgorithms[]` field).

Per Brief D-2 + D-6 backward-compat clause: `supportedAlgorithms[]` field on pull-packet is OPTIONAL in V1; missing field treated as `["Ed25519"]`. This permits existing standalone-worker (post-E37S01 import-rewrite, otherwise unchanged) to talk to new dispatcher.

Per Brief C-17: dispatcher remains algorithm-blind on packet allocation (algorithm choice is purely about result-authenticity downstream). For V1 with single Ed25519 algorithm, the `supportedAlgorithms[]` field is informational; future PQC-capable workers will use it to declare expanded capability sets.

This story is authored against E37S02 spec sections (a) shared, (b) dispatcher contract pull-packet + decomposition + timeout, (d) capability-advertisement protocol. No legacy inspection.

### Story-specific ACs

- [ ] **AC-PACKET-RECORD-ENTITY**: `de.vvwt.slotopt.dispatcher.packet.PacketRecord` Spring Data JDBC POJO with fields per spec (b): `Long id`, `UUID packetId` (UNIQUE), `UUID jobId` (FK), `String packetPayloadJson`, `String status` (`UNCLAIMED`, `CLAIMED`, `RESULT_RECEIVED`, `TIMEDOUT`), `UUID claimedByWorkerId` (nullable), `Instant claimedAt` (nullable), `Instant timeoutAt` (nullable).
- [ ] **AC-PACKET-REPOSITORY**: `de.vvwt.slotopt.dispatcher.packet.PacketRepository extends CrudRepository<PacketRecord, Long>`. Custom finders: `Optional<PacketRecord> findByPacketId(UUID)`, `List<PacketRecord> findByJobId(UUID)`, `List<PacketRecord> findByStatus(String)`.
- [ ] **AC-PACKET-DECOMPOSER-SERVICE**: `de.vvwt.slotopt.dispatcher.packet.PacketDecomposerService` interface + `DefaultPacketDecomposerService` impl per DEC-35. Method `List<PacketRecord> decompose(JobRecord job)`. Behavior: parse RawPhaseDef payload + worker-lib's PositionTuple/RawRow types, partition into packets per spec algorithm. RED-first.
- [ ] **AC-PULL-PACKET-DTOs**: `PullPacketRequest(UUID workerId, List<String> supportedAlgorithms)` — `supportedAlgorithms` field is Optional per Brief D-2; deserialization treats missing as `["Ed25519"]`. `PullPacketResponse(UUID packetId, UUID jobId, String packetPayloadJson, Instant timeoutAt)` — empty response (HTTP 204) when no unclaimed packets.
- [ ] **AC-CAPABILITY-FIELD-OPTIONAL** (per Brief D-2 backward-compat clause + D-6): missing or null `supportedAlgorithms` field in PullPacketRequest → service treats as `["Ed25519"]`. Empty array `[]` → HTTP 400 "supportedAlgorithms[] cannot be empty if provided". Test covers both cases.
- [ ] **AC-PULL-PACKET-SERVICE**: `de.vvwt.slotopt.dispatcher.packet.PullPacketService` interface + `DefaultPullPacketService` impl. Method `Optional<PacketRecord> claim(UUID workerId, Set<String> capabilities)`. Behavior: (1) verify workerId is registered (via KeyRegistrationService); (2) atomically claim one UNCLAIMED packet (UPDATE ... WHERE status='UNCLAIMED' LIMIT 1 idiom — DB row-level lock); (3) set claimedAt + timeoutAt (timeoutAt = now + spec-defined timeout). Capability set is informational at V1 (algorithm-blind allocation per Brief C-17). RED-first authored. Tests cover: claim returns next unclaimed; concurrent claim returns at most one packet per concurrent caller (use `PacketConcurrencyIntegrationTest` pattern).
- [ ] **AC-PULL-PACKET-CONTROLLER**: `de.vvwt.slotopt.dispatcher.packet.PullPacketController` `@PostMapping("/api/pull-packet")`. Accepts JSON `PullPacketRequest`. Returns JSON `PullPacketResponse` HTTP 200 OR HTTP 204 if no packets. Unknown workerId → HTTP code per E37S02 spec section (b) error matrix.
- [ ] **AC-PACKET-TIMEOUT-SWEEPER**: `de.vvwt.slotopt.dispatcher.packet.PacketTimeoutSweeper` Spring `@Scheduled` bean. Periodically scans for `status=CLAIMED AND timeoutAt < now` packets and reissues (set status back to UNCLAIMED + clear claimedByWorkerId + null timeoutAt). RED-first authored. Test uses Spring's `@SpyBean` or direct invocation — does not rely on @Scheduled timing.
- [ ] **AC-DEC26-COMPLIANT-DAO-ITs**: `PacketRepositoryIT` follows DEC-26 three-rule pattern.
- [ ] **AC-MOCKMVC-CONTROLLER-TEST**: `PullPacketControllerSliceTest` mocks PullPacketService; verifies all wire-format scenarios including capability field optionality.

## Notes

- **Per Brief C-17**: V1 is algorithm-blind on packet allocation. The `supportedAlgorithms[]` field is recorded but does not affect packet routing in V1. Future stories may filter packet-to-worker matching based on capabilities once heterogeneous worker fleets exist.
- **Per Brief D-2 backward-compat**: missing `supportedAlgorithms[]` → defaults to `["Ed25519"]`. This is the CRITICAL clause that lets the existing standalone-worker (post-E37S01) talk to the new dispatcher without forcing E38 closure as a blocker for E37.
- **Concurrency hazard**: atomic packet claim (UPDATE ... WHERE status='UNCLAIMED' LIMIT 1) requires DB-level concurrency safety. Test the concurrent-claim scenario with multiple parallel pulls.
