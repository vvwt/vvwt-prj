# Story E55S15 (Bug-Triage): Consolidate all Tournament Manager filesystem paths under a single configurable tm.data.dir root (DEC-68 operationalization)

## User Story

**As a** Tournament Manager operator,
**I want** all Tournament Manager data — databases, audit logs, audio, photos, certificate templates, slot-optimization keys, info-portal keys — to live under a single configurable data directory (`~/.tournament-manager` by default),
**so that** there is one directory to back up, one environment variable to set, and one location to document — instead of the current split across two unrelated roots (`~/.tournament-manager` and `~/.vvwt-tm`).

---

## Context

### Why this story exists

The Tournament Manager writes to the filesystem from **eight** independent configuration points split across **two** unrelated root directories. `tm.data.dir` (the `TmDataDirProperties` root for per-tenant H2 DBs + the tenant registry) is not set in `application.yml` at all — its Java-level default `${user.home}/.vvwt-tm` silently takes effect; the per-tournament audit log (E55S13) also defaults to `~/.vvwt-tm`; while the bootstrap DB, audio, photos, certificate-templates, slotopt-keys and info-portal-keys default under `~/.tournament-manager`. The split accrued feature-by-feature because no canon ever forced derivation from a single root.

Beyond the eight configuration points, the root literal is hardcoded a further three times in first-party Java (`TmDataDirProperties` field default, `AuditLogConfig` field default, `DatabaseDirectoryInitializer.resolveDatasourceUrl()` fallback), and the jlink launcher scripts hardcode `TM_DB_PATH`'s default. The full inventory was established by an in-Discovery grep audit (recorded in Brief O-1) — see § Nature of the change.

**DEC-68** (authored in the same Discovery cycle as this story) establishes the canon: a single `tm.data.dir` root, every path derives its default from `${tm.data.dir}`, and a "derive-don't-add" rule binds future path-needing features. This story operationalizes DEC-68.

### Discovery cycle provenance

Triggered 2026-05-15 when the operator observed the bootstrap DB at `~/.tournament-manager/db/tm` and asked whether it should sit under the data directory. Investigation surfaced that the real issue is the two-root split, not one path. The operator chose `~/.tournament-manager` as the consolidated root (self-descriptive name; minimal migration — only the per-tenant DBs and audit log, currently under `~/.vvwt-tm`, move; everything else is already under `~/.tournament-manager`).

### Nature of the change

The change has four parts (DEC-68 § Impact):

1. **`application.yml` rework** — introduce `tm.data.dir`; rewrite the seven per-purpose path defaults (datasource URL, audit-log, audio, photos, certificate-templates, slotopt worker-keys, info-portal keypair) to derive `${tm.data.dir}/...` via Spring property-placeholder nesting. The bound Java config beans `PhotoStorageConfig` / `AudioStorageConfig` carry no Java-level default literal — they read the resolved `data-dir` and need no code change.
2. **Two Java config-bean field defaults** — `TmDataDirProperties` (`~/.vvwt-tm` → `~/.tournament-manager`) and `AuditLogConfig` (`~/.vvwt-tm` → `~/.tournament-manager`). These are belt-and-suspenders fallbacks for an absent `application.yml`; left at `~/.vvwt-tm` they would silently re-create the two-root split.
3. **`DatabaseDirectoryInitializer.resolveDatasourceUrl()`** — an `EnvironmentPostProcessor` whose fallback branch (`:117-118`) hardcodes `~/.tournament-manager/db/tm`. Re-rooted to honour the single root.
4. **The jlink launcher scripts** (`tournament-manager`, `tournament-manager.bat`) — currently default `TM_DB_PATH` to `~/.tournament-manager/db/tm`; reworked to expose `TM_DATA_DIR` (the single root) as the operator override knob.

Parts 2 and 3 are first-party code → DEC-22 RED-first applies to them; `application.yml` and the launcher shell/batch scripts are configuration, not first-party code authoring.

Per DEC-25 §no-production-data: no data backfill. The operator deletes the old `~/.vvwt-tm` tree before rollout; fresh per-tenant DBs + audit-log directories are created under the unified root on next boot.

## Acceptance Criteria

### Implementation

- [ ] **AC-IMPL-DATA-DIR-ROOT-PROPERTY**: `application.yml` — introduce `tm.data.dir` as the explicit single root: `tm.data.dir: ${TM_DATA_DIR:${user.home}/.tournament-manager}`. This is the canonical root per DEC-68 clause 1.

- [ ] **AC-IMPL-DERIVE-ALL-PATHS**: `application.yml` — rewrite all **eight** per-purpose path defaults to derive from `${tm.data.dir}` (per DEC-68 clause 2), keeping each per-purpose override env var as the optional escape hatch (DEC-68 clause 3):
  - `spring.datasource.url` → `jdbc:h2:file:${TM_DB_PATH:${tm.data.dir}/db/tm};AUTO_SERVER=FALSE`
  - `tm.audit-log.data-dir` → `${TM_AUDIT_LOG_DATA_DIR:${tm.data.dir}}` — the audit-log layout is `<data-dir>/tenants/<tenant>/audit-log/...`, so `tm.audit-log.data-dir` resolves to `${tm.data.dir}` itself; it co-inhabits the same `tenants/<uuid>/` tree as the per-tenant DBs (DEC-68 clause 2)
  - `tm.audio.data-dir` → `${TM_AUDIO_DATA_DIR:${tm.data.dir}/audio}`
  - `tm.photos.data-dir` → `${TM_PHOTOS_DATA_DIR:${tm.data.dir}/photos}`
  - `tm.certificate-templates.data-dir` → `${TM_CERT_TEMPLATES_DATA_DIR:${tm.data.dir}/certificate-templates}`
  - slotopt dispatcher `worker-key-dir` → `${TM_SLOTOPT_WORKER_KEY_DIR:${tm.data.dir}/slotopt-keys}`
  - `info-portal.keypair-dir` (`application.yml:192`) → `${INFO_PORTAL_KEYPAIR_DIR:${tm.data.dir}/info-portal-keys}`
  Update the explanatory comments above each block to reflect the derived defaults + cite DEC-68.

- [ ] **AC-IMPL-TMDATADIRPROPERTIES-DEFAULT**: `TmDataDirProperties.java:44` — change the Java-level default field initializer from `${user.home}/.vvwt-tm` to `${user.home}/.tournament-manager`; update the class Javadoc (the "Default value" section + any `~/.vvwt-tm` mention) accordingly. This keeps the Java fallback consistent with the `application.yml` default.

- [ ] **AC-IMPL-AUDITLOGCONFIG-DEFAULT**: `AuditLogConfig.java:37` — change the Java-level default field initializer from `System.getProperty("user.home") + "/.vvwt-tm"` to `System.getProperty("user.home") + "/.tournament-manager"`; update the class Javadoc (the two `~/.vvwt-tm` mentions at lines 16-17 and 34). Without this fix, an absent `tm.audit-log.data-dir` property would silently re-root the audit log under `~/.vvwt-tm` — re-creating the two-root split DEC-68 eliminates.

- [ ] **AC-IMPL-DATABASEDIRECTORYINITIALIZER-REROOT**: `DatabaseDirectoryInitializer.resolveDatasourceUrl()` (`:104-119`) — the fallback branch at `:117-118` hardcodes `userHome + "/.tournament-manager/db/tm"`. Re-root it to honour the single root: when neither `spring.datasource.url` nor `TM_DB_PATH` is resolvable, derive the DB path from `TM_DATA_DIR` (read via `environment.getProperty("TM_DATA_DIR")`, default `${user.home}/.tournament-manager`) as `<root>/db/tm`. The `spring.datasource.url` and `TM_DB_PATH` priority branches (`:106-115`) are unchanged. Update the method Javadoc's priority list.

- [ ] **AC-IMPL-LAUNCHER-SCRIPTS**: The jlink launcher scripts `tournament-manager` (`:63`) and `tournament-manager.bat` (`:47`) currently default `TM_DB_PATH` to `~/.tournament-manager/db/tm`. Rework so the operator-facing override knob is `TM_DATA_DIR` (the single root): the script's DB-path computation derives from `${TM_DATA_DIR:-$HOME/.tournament-manager}/db/tm` while still honouring an explicit `TM_DB_PATH` if set. Update the script header comments + `src/main/assembly/README.txt:33` to document `TM_DATA_DIR` as the primary data-directory override.

- [ ] **AC-IMPL-HARDCODED-PATH-AUDIT-VERIFY**: The Discovery-time grep audit of `vvwt-tm-web/src/main` for `.vvwt-tm` / `.tournament-manager` / `user.home`-plus-path literals enumerated exactly these occurrences (Brief O-1):
  - **Re-rooted by this story:** the 8 `application.yml` path configs (AC-IMPL-DERIVE-ALL-PATHS); `TmDataDirProperties.java:44` + `AuditLogConfig.java:37` (Java field defaults `~/.vvwt-tm` — wrong root); `DatabaseDirectoryInitializer.java:118` (EnvironmentPostProcessor fallback); the two launcher scripts + `assembly/README.txt:33`.
  - **Deliberately left unchanged — already root-consistent (`~/.tournament-manager/...`):** `InfoPortalProperties.java:55` (Java field default `~/.tournament-manager/info-portal-keys`) and `SlotOptimizationDispatcherConfiguration.java:66` (the `@Value` annotation default `${tm.slotopt.dispatcher.worker-key-dir:${user.home}/.tournament-manager/slotopt-keys}` — a live code literal, NOT a comment; line 60 of the same file is the Javadoc comment). Both are Java-side belt-and-suspenders fallbacks; a `@Value` / field default cannot robustly nest-resolve `${tm.data.dir}` when `application.yml` is absent (since `tm.data.dir` itself comes from `application.yml`), so they must remain static literals — and being already under `~/.tournament-manager` they are canon-consistent. Only their `application.yml` entries (`:165`, `:192`) are re-rooted to derive (AC-IMPL-DERIVE-ALL-PATHS). See § Out of Scope.
  - **Comment-only mentions (no code literal):** `PhotoStorageConfig`, `AudioStorageConfig`, `InfoPortalConfig` Javadoc.
  Delivery RE-RUNS the grep after implementing all ACs and confirms: zero `.vvwt-tm` literals remain in `src/main`, and every `.tournament-manager` occurrence is either a derived `${tm.data.dir}` default, the `~/.tournament-manager` root literal itself, a Javadoc comment, or one of the two enumerated already-root-consistent Java defaults (`InfoPortalProperties.java:55`, `SlotOptimizationDispatcherConfiguration.java:66`). Any occurrence NOT in this enumerated inventory → AC-ERROR-HANDLING-UNANTICIPATED-PATH-LITERAL.

## Out of Scope

- **Data backfill / migration** — none. Per DEC-25 §no-production-data, the operator deletes the old `~/.vvwt-tm` tree before rollout; fresh directories are created under the unified root (Brief D-5).
- **Removal of the per-purpose override env vars** — `TM_DB_PATH`, `TM_AUDIT_LOG_DATA_DIR`, `TM_AUDIO_DATA_DIR`, `TM_PHOTOS_DATA_DIR`, `TM_CERT_TEMPLATES_DATA_DIR`, `TM_SLOTOPT_WORKER_KEY_DIR`, `INFO_PORTAL_KEYPAIR_DIR` are retained as escape hatches per DEC-68 clause 3 (Brief S-6).
- **Changing the on-disk sub-structure** — `tenants/{uuid}/`, `audio/{tournamentId}/`, `audit-log/{tournament-id}/` etc. layouts are unchanged; only the ROOT unifies (DEC-68 clause 5, Brief S-7).
- **The two already-root-consistent Java-side default literals** — `InfoPortalProperties.java:55` (Java field default `~/.tournament-manager/info-portal-keys`) and `SlotOptimizationDispatcherConfiguration.java:66` (the `@Value` annotation default `${tm.slotopt.dispatcher.worker-key-dir:${user.home}/.tournament-manager/slotopt-keys}`) are deliberately left unchanged. Both are already under the `~/.tournament-manager` root (canon-consistent), and a Java-side `@Value`/field default cannot robustly nest-resolve `${tm.data.dir}` as a fallback for an absent `application.yml` (when `application.yml` is absent, `tm.data.dir` is undefined too) — so they remain static literals. Only their `application.yml` entries (`info-portal.keypair-dir:192`, `tm.slotopt.dispatcher.worker-key-dir:165`) are re-rooted to derive (AC-IMPL-DERIVE-ALL-PATHS). This contrasts with `TmDataDirProperties`/`AuditLogConfig`, whose Java defaults ARE changed because their literal is `~/.vvwt-tm` — the wrong root.
- **DEC-14 / DEC-20 clause changes** — DEC-68 complements them; no clause of either is amended.
