# Story E48S02: Siegerehrung Backend — `SiegerehrungMatchGenerator` No-op Bean + `isLastPhase` Helper + draft_json Defensive Null-Handling

## User Story

**As a** Backend Service,
**I want** a registered no-op `MatchGenerator` for `gameMode=siegerehrung` plus a defensive helper to determine whether a given phase is the last phase of its tournament,
**so that** the Phase-Preparation pipeline does not throw when invoked for a Siegerehrung phase, and lifecycle code can derive `isLastPhase` reliably without a Phase-entity schema change.

---

## Context

Per Brief D-5 / D-10 / O-15 / C-14: `PhasePreparationService.generateMatches(phaseId, generatorKey)` (`PhasePreparationService.java:121-160`) ruft `matchGeneratorRegistry.get(generatorKey)` unconditional auf. Für gameMode=siegerehrung ist aktuell kein Bean registriert → würde fehlschlagen. Das Brief wählt Path (i) aus den drei O-15 Optionen: ein `SiegerehrungMatchGenerator` Spring-Bean, der `MatchGenerator` implementiert und `Collections.emptyList()` aus `generate(phase, avatars)` zurückgibt. Vorteil: minimal-invasiv, kein Code-Change in `generateMatches` oder Caller, registry-driven Dispatch funktioniert wie für jeden anderen Generator.

Per D-10 lebt gameMode in `tournament.draft_json` (kein Phase-Entity-Feld). C-14 verlangt defensive null/parse-error-Handling für jeden Service, der `isLastPhase`-Ableitung aus draft_json benötigt. Diese Story liefert `isLastPhase(phaseId)` als shared Helper-Methode (idempotent, defensive) — konsumiert in E48S06 (Phase-Lifecycle complete-Logik bei letzter Phase = trigger Tournament COMPLETED) und E48S07 (Drag&Drop-Transition: bei Siegerehrungs-Phase keine Match-Generierung).

## Notes

- `PhasePreparationService.generateMatches` Code-Anker bestätigt: Line 147 `MatchGenerator generator = matchGeneratorRegistry.get(generatorKey);` → registry-driven dispatch funktioniert mit jedem registrierten Bean. Path (i) ist daher minimal-invasiv: nur Bean-Registration, kein Service-Modification.
- **Trade-off Awareness (Path-(i) silent-success)**: das No-op-Generator-Bean returned `emptyList()` ohne Fehler-Signal. Falls ein Caller versehentlich `generateMatches(phaseId, "siegerehrung")` für eine non-siegerehrung-intendete Phase aufruft, wäre das ein silent-success (keine Matches generiert, keine Exception). Mitigation: Path (i) ist akzeptabel weil (a) gameMode kommt aus DraftSection.gameMode, der ist via E48S01-Whitelist auf {roundrobin, siegerehrung} bound; (b) das Apply-flow ist deterministic per draft_json — kein "versehentlicher" siegerehrung-Aufruf möglich. Path-(ii)/-(iii) hätten zusätzliche Fehler-Signal-Vorteile aber höhere Implementierungskosten + mehr Code-Surface; Path-(i) bleibt Best-Fit gegeben die existing whitelist-protected gameMode-Quelle.
- `isLastPhase` als Repository-Methode oder Helper-Service: Delivery wählt. Empfehlung: `PhaseRepository.findLastByTournamentId(UUID tournamentId)` + Helper `boolean isLastPhase(UUID phaseId)` der das nutzt. Pure Read, kein Lock.
- DEC-37 Clause B Lock NICHT erforderlich für diese Story — alle neuen Methoden sind read-only oder no-op-generators (kein Schreib-Cascade auf tournament/phase/match).
- Geschätzter LOC ~100-180 across ~6 files.
