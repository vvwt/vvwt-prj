# Story: Eliminate viewport-dependent certificate layout — convert all `cqh` units in `_certificate_styles.mustache` to mathematically-equivalent `cqw` units (Path A) and adopt the operator-tuned vertical-spacing values; deterministic photo-wrap geometry across browsers, viewports, and print rendering

## User Story

**As a** tournament organizer who renders Urkunden in the browser AND in
the print preview AND on the production jlink-deployed test system,
**I want** the certificate layout — particularly the team-photo area's
aspect ratio — to be **identical across all rendering contexts** (web at
any viewport height, Chromium print preview, Firefox print preview, the
final printed A4-landscape page),
**so that** when the operator uploads a team photo of the documented
aspect ratio (~2.18:1), the photo renders cropping-free in every
context, and team photos with closer-to-standard aspects (3:2, 4:3) crop
the same way everywhere instead of "more cropped in print than on
screen" or "different on every browser window size".

## Root Cause Analysis

Empirically isolated in Discovery via headless Chromium
(`chromium --headless --dump-dom`) on a stripped-down 1:1 reconstruction
of the cert layout — identical structure, identical class names,
identical CSS rules, but with the embedded base64 fonts stripped for
speed. `getBoundingClientRect()` of `.photo-wrap` captured to the page
title and harvested via `--dump-dom`.

**Verified root cause (Path A target):**

`_certificate_styles.mustache:44` declares
`.page { container-type: inline-size }`. Under CSS Containment, the
container-query-block-direction unit `cqh` only resolves against the
container when the container's `container-type` includes `size`; under
`inline-size`, `cqh` falls back to the small-viewport block size — i.e.,
the browser viewport height (web) OR the @page block size (print). The
following declarations all use `cqh`:

| Selector | Property | Value |
|---|---|---|
| `.page` (line 46) | `padding` (top + bottom) | `5cqh ... 4cqh` |
| `.hero` (line 83) | `margin-top` | `2cqh` |
| `.placement` (line 97) | `margin-top` | `1.6cqh` |
| `.photo-wrap` (line 115) | `margin-top` | `1.6cqh` |

Because the screen viewport differs across operator browser windows
(short laptop screens vs tall desktop monitors) and differs again
between screen and print, the absolute padding/margin values evaluate
differently in every context. The flex-stacked vertical sum of the
fixed-size siblings (header, divider, hero, placement, footer)
absorbs whatever vertical space the cqh values claim; whatever remains
is the height of `.photo-wrap` (which is `flex: 1 1 auto`). Different
cqh resolution → different leftover → different photo-wrap aspect
ratio → different `object-fit: cover` crop on the embedded `.photo`.

**Empirical photo-wrap aspect-ratio measurement (Discovery session,
2026-05-31), baseline (origin/staging at commit `3e024ff8`):**

| Mode | Viewport | photo-wrap (px) | AR |
|---|---|---|---|
| Web | 1280 × 600 | 1001 × 394 | 2.54 |
| Web | 1280 × 800 | 1001 × 383 | 2.61 |
| Web | 1280 × 1024 | 1001 × 371 | 2.69 |
| Web | 1280 × 1400 | 1001 × 352 | 2.84 |
| Web | 1280 × 1800 | 1001 × 331 | 3.02 |
| Print | A4 landscape @ 96dpi | 986 × 387 | 2.55 |

The web AR spans **2.54 – 3.02** depending on browser window height —
a 25% range from the same Mustache template — while print is constant
2.55. This is the divergence the operator observes.

**Verified fix (Path A — `cqh` → mathematically-equivalent `cqw`):**

`.page` has `aspect-ratio: 1684 / 1191` (line 40); height is therefore a
deterministic function of width: `height = width × 1191/1684 ≈ width ×
0.7074`. Therefore `1cqh = 0.7074 × 1cqw` is an algebraic identity
that holds for any container width.

Replacing every `cqh` literal in `_certificate_styles.mustache` with
its `0.7074×` cqw equivalent yields layout values that resolve
identically regardless of browser viewport height — `cqw` always
resolves against the container's inline-size (which is `inline-size`
under the existing `container-type`).

**Empirical confirmation post-Path-A (Discovery session, 2026-05-31),
applied to the operator-tuned values from this story's scope:**

| Mode | Viewport | photo-wrap (px) | AR |
|---|---|---|---|
| Web | 1280 × 600 | 1001 × 494 | **2.024** |
| Web | 1280 × 800 | 1001 × 494 | **2.024** |
| Web | 1280 × 1024 | 1001 × 494 | **2.024** |
| Web | 1280 × 1400 | 1001 × 494 | **2.024** |
| Web | 1280 × 1800 | 1001 × 494 | **2.024** |
| Print | A4 landscape @ 96dpi | 986 × 453 | **2.176** |

Web AR is now constant across the full operator-viewport range. A
residual ~7 % web/print AR divergence remains because the cert template
mixes cqw-based layout (now consistent) with absolute-pixel-sized fonts
(`font-size: 36px` lockup-row, `28px` URKUNDE label, `18px` of-row,
`13px` lbl, `10px` footer); the absolute font box takes a different
fraction of the page in web (`.page = 1180 × 834.5 px`) vs print
(`.page = 1122.5 × 793.7 px`). Closing that residual would require
converting fonts to `cqw` as well — explicitly **out of scope** for
this story (changing font sizing changes visible cert design, beyond
the operator's "match web to print" request).

**Operator-tuned vertical-spacing values (included in this story's
scope per Discovery decision 2026-05-31):**

The operator manually iterated cqh values on their local working copy
to make the cert content compact enough that the photo dominates the
visual real estate. The locked target values for this story are:

| Selector | Property | New cqh (operator target) | Path A cqw equivalent (Delivery emits this) |
|---|---|---|---|
| `.page` | `padding` top | `5cqh` (unchanged) | `3.537cqw` |
| `.page` | `padding` bottom | `4cqh` (unchanged) | `2.830cqw` |
| `.divider` | `margin-top` | `0.6cqh` (was `18px`) | `0.424cqw` |
| `.hero` | `margin-top` | `0.5cqh` (was `2cqh`) | `0.354cqw` |
| `.placement` | `margin-top` | `0.6cqh` (was `1.6cqh`) | `0.424cqw` |
| `.place-meta .row` | `margin-bottom` | `0.4cqh` (was `12px`) | `0.283cqw` |
| `.place-meta .of` | `transform: translateY(...)` | `0.8cqh` (was `0.3em`) | `translateY(0.566cqw)` |
| `.photo-wrap` | `margin-top` | `0.6cqh` (was `1.6cqh`) | `0.424cqw` |
| `.footer` | `margin-top` | `0.6cqh` (was `16px`) | `0.424cqw` |

Delivery emits the `cqw` column directly — the `cqh` column is the
operator's audit trail of how the value was derived, not a value that
should appear in the final shipped file. The `5cqh` and `4cqh`
top/bottom paddings on `.page` are NOT operator-tuned (kept at their
origin/staging values) but ARE included in the Path A conversion
because the cqh→cqw conversion is structural for the whole file.

**Authoritative team-photo aspect ratio for no-crop guarantee (post-fix):**
the print box AR `2.176 ≈ 11:5` is the canonical reference, since print
is the medium that produces the final cert and is deterministically fixed
(297 mm × 210 mm). Documented in the impl-report per AC4.

## Out of Scope

- **Font-size container-query conversion** — the residual ~7 % web/print
  AR divergence documented in § Root Cause Analysis comes from the
  absolute-pixel font sizes in `.lockup-row`, `.urkunde-badge .label`,
  `.place-meta .of`, `.place-meta .lbl`, `.footer`. Converting those to
  cqw would visibly resize the cert design — beyond the operator's
  "match web to print geometry" request. A follow-up Discovery may
  scope this if the operator finds the residual divergence visible.
- **`.page` aspect ratio refactor** — the `aspect-ratio: 1684 / 1191`
  declaration on `.page` (line 40) is preserved unchanged; the Path A
  conversion relies on it for the algebraic `1cqh = 0.7074 cqw`
  identity. Any future change to `.page`'s aspect ratio would
  invalidate the conversion factor.
- **`container-type` change** — the `container-type: inline-size` on
  `.page` (line 44) is preserved unchanged. Switching to
  `container-type: size` would make `cqh` resolve correctly without
  conversion, but would also enable size-direction queries, which the
  template does not use, and changes containment semantics in ways
  Discovery cannot scope without screen-render regression testing.
  Path A (cqw conversion) avoids that risk.
- **E12S10 jlink-jdk-localedata fix** — separate bug-triage story
  E12S10; independent root cause (production-only locale-data absence
  in the jlink image), independent change surface
  (`vvwt-tm-web/pom.xml` `--add-modules` argument).
- **E12S11 print-overflow fix** — already delivered (commit `3e024ff8`
  on staging); this story builds on the `@media print` block E12S11
  introduced and preserves it unchanged.
- **`DefaultCertificateAssembler` Java code** — including the HTML-row
  hardcode of `Locale.GERMAN` at `DefaultCertificateAssembler.java:277`
  (separate bug, deferred per E12S10 § Out of Scope) and any other
  Java-side change.
- **`CertificateRenderController` Java code** — endpoints, model
  population, override parameters, security pattern unchanged.
- **`messages.properties` label values** — the German tom.label.*
  values stay unchanged; the layout refactor is locale-text-neutral.
- **`LocaleResolver` chain** — unchanged.
- **SVG certificate path** — the SVG branch in
  `CertificateRenderController.singleCertificate` /
  `allCertificates` (per-template SVG byte-response / per-template ZIP
  archive) is unaffected; SVG certificates do not pass through this
  HTML template.
- **Browser-side print preferences** — DPI, paper colour, scaling
  override, header/footer toggle — operator-driven, not in the
  rendered HTML's scope.
- **Headless-Chromium CI integration test** — operator decision in
  Discovery session 2026-05-31 (reaffirmed from the E12S11 session):
  build-portability cost of adding chromium + its system deps to
  `mvn verify` outweighs the regression-guard benefit. The
  Mustache-render guard in AC2 plus the impl-report attestation in
  AC1/AC4 are the canon for this story (per memory
  `project_scoring_tablet_test_surface`).
- **Team-photo upload widget / helptext** — recording the
  ~2.18:1 AR in a user-facing helptext on the team-edit form is a
  separate UI story (E48 / E68 area); this story stops at impl-report
  documentation.
