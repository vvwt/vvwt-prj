# Story E11S09: Fix — Timer Hallenuhr-clock offset (display + audio trigger) + manual-mode orientation indicators

## User Story

**As a** tournament organizer operating the Timer SPA at a venue whose wall clock differs from the host device,
**I want** the Hallenuhr-clock setting to make countdown and audio events fire at the correct device-time equivalent of the planned Hallenuhr times, AND the timer page to show me at a glance what is upcoming, what time it is, and where the next event sits in the schedule,
**so that** rounds and breaks are signalled audibly at the right moment AND I can orient myself even before the first event has started.

---

## Context

Two operator-reported symptoms on `/timer/tournaments/{id}` (Timer SPA in `vvwt-tm-web/src/main/ui-timer/`):

**Symptom 1 — Hallenuhr setting produces wrong fire times.**
The ClockSyncDialog asks the operator to align the venue ("Hallenuhr") wall clock with the device clock. The intent is that schedule events fire when the venue clock reaches each event's planned time. The producer side (`DefaultTimerDataService.java:202` `tournament.getPlannedStartTime()`) emits schedule `startTime` values in the operator-planned **venue wall-clock domain**. The consumer side in the Timer SPA (`countdownEngine.ts`, `ScheduleRow.svelte`, `timerApi.applyClockOffset`) was authored with the inverse mental model — it treats the schedule's `startTime` as device-domain and adds `offset = venue − device` to it. Result with `offset > 0` (venue ahead of device): the schedule table column shows `venue + offset` (double-shifted nonsense — e.g. a 10:00 plan at +6h offset displays as 15:58/15:59), the countdown over-shoots by exactly the offset, and audio events fire late by the offset (~6 h late for the operator's reproduction). The schedule column header reuses the dialog prompt key `timer.clockSync.prompt` ("Aktuelle Gerätezeit:") as its header, compounding the confusion.

**Symptom 2 — Manual play has no orientation indicators.**
When the operator opens the timer page or presses PLAY before the first scheduled event has been reached, the RoundCounter renders `—` (because no event is "playing"), the large numeric countdown carries no visible label explaining what it counts down to (`timer.countdown.label` IS wired as an `aria-label` only — invisible), there is no permanently visible Hallenuhr-now reading on the page, and every non-active schedule row carries the uniform "Ausstehend" status badge with no differentiation of "next" vs "later". The operator is left looking at a number with no context.

Discovery Session Brief `discovery-2026-05-28-timer-hallenuhr-offset-and-manual-mode-orientation` (human-validated 2026-05-28; Review Sub-Agent Tier 2 cycle-2 PASS, rubric_version 2026-03-30) drives the per-symptom DEC-22 routing in this Story.

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach is Delivery's choice; this Story specifies the WHAT.

### Symptom 1 — Hallenuhr-clock offset correctness

- [ ] **AC1 — Audio trigger fires at the correct device-time equivalent.** Given a tournament whose first scheduled event is planned for `HH:MM` Hallenuhr-clock, and the operator has confirmed a Hallenuhr-clock offset of `Δ seconds` in the ClockSyncDialog (positive `Δ` = Hallenuhr ahead of device), when the device clock reaches the time equivalent to `HH:MM` in the venue domain (i.e., when `device + Δ` equals `HH:MM`), then the corresponding audio event (start sound, end sound, or pause music) fires within the engine's existing tick resolution. Holds for every event class the engine fires today (ROUND start/end + REGULAR-break start/end).
- [ ] **AC2 — Countdown reaches zero at the correct device-time equivalent.** Under the same setup as AC1, the visible countdown reaches `00:00` exactly when the device clock reaches the Hallenuhr-time-equivalent moment of the next scheduled event. The on-screen value at any earlier moment equals the wall-clock-domain remaining time (i.e., it counts down at real-time, one second per second, regardless of `Δ`).
- [ ] **AC3 — Schedule table displays planned Hallenuhr-clock times verbatim.** For every schedule entry whose backend `startTime` is set, the schedule table renders that `HH:MM` value verbatim in the Hallenuhr-clock domain, independent of `Δ`. The operator who reads the schedule sees the same Hallenuhr-clock times they planned in the admin, regardless of any device-vs-venue offset. (Edited / overridden times remain in the same Hallenuhr-clock display domain — the override semantic is unchanged.)
- [ ] **AC4 — Schedule-time column header reads as Hallenuhr-Zeit.** The column header above the schedule's time values reads in German as a Hallenuhr-clock label (e.g. "Hallenuhr-Zeit" or equivalent — Delivery chooses the literal value). The dialog-prompt key (`timer.clockSync.prompt`) is no longer reused as this column header; a dedicated i18n key is introduced for the column header per the project's frontend i18n convention.
- [ ] **AC5 — DTO JavaDoc clarifies wall-clock origin.** The JavaDoc on `TimerScheduleEntryResponse.startTime` and `.endTime` explicitly states that the values are the operator-planned venue wall-clock ("Hallenuhr") time, not a device-clock value. (One-line precision update to remove a documented ambiguity — see Brief D-1 side-finding.)

### Symptom 2 — Manual-mode orientation indicators (three indicators per Brief D-6)

- [ ] **AC6 — Visible label on the countdown.** A visible text element near the large countdown numerals identifies, in German, what the countdown is counting down toward (e.g. "Bis nächstes Ereignis" or equivalent). The existing `aria-label` continues to convey the same meaning to screen readers; visual sighted users now see the same orientation. Delivery may repurpose the existing `timer.countdown.label` key or introduce a sibling key — either is acceptable; duplication of the same key for both purposes is acceptable.
- [ ] **AC7 — Permanently visible Hallenuhr-clock now reading.** The timer page renders a permanently visible element showing the current Hallenuhr-clock time (= `device + Δ`), formatted at least to the minute. The element is driven by a timing mechanism that refreshes the displayed value at 1 Hz (a `setInterval(…, 1000)` or equivalent Svelte 5 `$state`-tick chain — the test mechanism for the AC is the **existence** of such a mechanism in the source per AC13, not a runtime-mount tick observation). The element remains visible across all transport states (STOPPED, PLAYING, PAUSED) and is not collapsed into the brand header strip.
- [ ] **AC8 — Next-upcoming schedule row visually distinguishable.** Among all schedule rows whose effective time is in the future, the row corresponding to the **earliest** future event is visually distinguishable both from the active/playing row (whose existing highlight is preserved) and from the later upcoming rows. The distinction is subtle (e.g. border accent, slight background tint) — not as dominant as the active-row highlight. When no row is currently playing (the operator's manual-mode case), the next-upcoming row carries this distinct visual treatment.

### Error-handling (mandatory category — edge cases & regression guards)

- [ ] **AC9 — Zero-offset regression guard.** When the operator confirms the device time as-is (`Δ = 0`), the schedule table, countdown, and audio events behave exactly as they did before this Story was implemented — no drift, no visible change for the zero-offset path. (Protects against the math fix degrading the common case.)
- [ ] **AC10 — Negative-offset symmetry.** When `Δ < 0` (device ahead of venue), the math is symmetric: the countdown reaches zero and audio fires when the device clock reaches `HH:MM + |Δ|` (i.e. later by `|Δ|` than the planned Hallenuhr time). The schedule table still displays the planned Hallenuhr `HH:MM` verbatim per AC3.
- [ ] **AC11 — Midnight wrap-around is preserved.** When the Hallenuhr-clock-domain math crosses midnight (next event's Hallenuhr time is numerically smaller than the current Hallenuhr time but logically in the next 24-hour period, or vice versa), the modulo-86400 normalisation existing in `applyClockOffset` / `nowSeconds` continues to produce a valid sub-24h countdown without negative values or `NaN`. Specific failure modes are not part of this Story's scope.

## Out of Scope

- **Post-tournament timer view.** When every phase of a tournament is COMPLETED, the Timer SPA today computes "all events upcoming" because none of the historical wall-clock times match today's wall-clock-now. A "Turnier beendet" placeholder is **not** part of this Story (Brief S-2, operator decision). Separate Story if confirmed needed in production.
- **ClockSyncDialog UX redesign.** The dialog's primary/secondary button layout, the "Hallenuhr-Zeit eingeben"-as-secondary-button-label ambiguity, and whether the dialog should default to direct venue-time entry instead of a two-step Adjust toggle are **not** part of this Story (Brief S-6, operator decision). Foreseeable risk acknowledged in the Brief: an operator who presses the blue primary "Zeit bestätigen" button without entering the venue time will keep `Δ = 0` and the *behavioural* bug appears to return ("schedule fires at device-clock time"). Separate UX Story if this recurs.
- **Other SPAs (Admin, Display, Score-Tablet) and their clock handling.** Untouched.
- **WebSocket sync (E11S05) / LAP-Advance lifecycle.** They consume the repaired snapshot; their logic is not touched.
- **Web Audio API initialisation / AudioEngine internals.** Untouched.
- **Backend changes beyond the AC5 one-line JavaDoc clarification.** `DefaultTimerDataService`, `TimelineCalculationService`, schedule-mapping logic, and any DAO / REST layer are out of scope.
