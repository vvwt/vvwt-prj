# Story E63S02: Leg-2 result round-trip — TM fetches and applies the dispatcher's computed optimum

## User Story

**As a** tournament organizer optimizing a large phase while the dispatcher is reachable,
**I want** the schedule the dispatcher computed to actually be applied to my phase,
**so that** Leg 2 produces an optimized phase instead of silently leaving it unoptimized.

---

## Context

`RoutingSlotOptimizationClient` routes a large phase to Leg 2 when the dispatcher is
reachable. `DefaultSlotOptimizationDispatcherClient.submitJob()` works — it submits the job.
But `pollResult()` polls the dispatcher's job-status endpoint and, when the job is reported
`COMPLETED` or `COMPLETED_FROM_CACHE`, returns `Optional.of(new int[0])` — an empty-array
**sentinel**, not the computed permutation. `RoutingSlotOptimizationClient.tryLeg2()` treats
that non-empty `Optional` as success, returns `true`, and **applies nothing** —
`SlotResultApplicator` is never called on the Leg-2 success path. A finished Leg-2 job
silently leaves the phase with its pre-optimization (L1+L2) assignment. A code comment in
`pollResult()` even claims "the dispatcher applies the permutation to the submit-job's
phaseId" — architecturally impossible: the dispatcher has no access to TM's per-tenant
database.

This story makes the Leg-2 success path functional: TM obtains the dispatcher's computed
job optimum and applies it to the phase's matches via `SlotResultApplicator` — the same
applicator Leg 1 and Leg 3 use. The Leg-2 wire-error / timeout fall-through to Leg 3 is
preserved unchanged; only the success path is fixed.

**Dependency on Epic E60.** E60 makes the dispatcher actually finalize jobs and exposes the
computed optimum (`finalResult`) on its job-status surface. The exact retrieval mechanism is
E60S04's delivered API — see the two hypotheses below. This story's ACs state the behaviour;
Delivery binds to E60's concrete API (this story is daemon-ordered after E60S04).

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-LEG2-RESULT-APPLIED** — RED-first (DEC-22): when a Leg-2 job the dispatcher
  has finalized is routed, the phase's matches reflect the dispatcher's computed optimum —
  `SlotResultApplicator` is invoked with the fetched result. The test fails on current
  `HEAD` (the phase is left unoptimized) and passes after the fix.
- [ ] **AC-TEST-POLLRESULT-RETURNS-REAL-RESULT** — `DefaultSlotOptimizationDispatcherClient`
  returns the dispatcher's actual computed result for a finalized job — never the empty-array
  sentinel. The result carries the data `SlotResultApplicator` needs (see AC-GOV-RANK).
- [ ] **AC-TEST-CACHE-COMPLETION-PATH** — a job the dispatcher reports as completed from its
  result cache (`COMPLETED_FROM_CACHE`) yields the applied optimum exactly as a freshly
  finalized job does — both completion routes are functional, neither returns the sentinel.
- [ ] **AC-TEST-LEG2-WIRE-ERROR-FALLS-THROUGH** — on a Leg-2 wire error, dispatcher-side
  error, or poll timeout, `tryLeg2()` still returns `false` and routing falls through to
  Leg 3 (the existing fallback behaviour is preserved — only the success path changes).
- [ ] **AC-TEST-SUITE-GREEN** — `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54);
  the existing E27 slotopt test suite remains GREEN.

### Governance

- [ ] **AC-GOV-E60-SURFACE-BINDING** — TM obtains the completed job's optimum from the
  dispatcher's E60-delivered job-result surface. The exact endpoint and payload shape
  (E60S04 leaves the cache-hit retrieval mechanism — inline payload vs a queryable
  `COMPLETED` job — a Delivery design choice) is bound at Delivery against E60's delivered
  API; the AC is the behavioural round-trip, not a fixed wire shape.
- [ ] **AC-GOV-RANK-SEMANTICS** — Delivery verifies that the rank the dispatcher emits for a
  finalized job is the lap-permutation rank `SlotResultApplicator.applyResult` consumes
  (`rank` ∈ `[0, lapCount!)`, N = lap count per DEC-56 / DEC-61). If the dispatcher's rank is
  packet-local or otherwise differently encoded, a rank-translation step is implemented as
  part of this story. The impl-report records the verified rank semantics.
- [ ] **AC-GOV-RECONSTRUCTION-CLASSIFICATION** — the changes to the E27-delivered
  `DefaultSlotOptimizationDispatcherClient.pollResult()` and `RoutingSlotOptimizationClient.tryLeg2()`
  follow reconstruction-in-place / DEC-22 §refactor-clause; the misleading "the dispatcher
  applies the permutation" comment is removed. The impl-report records the classification.
- [ ] **AC-GOV-DEC9-STRUCTURAL-ONLY** — the result fetch and apply carry only structural
  optimization data (a permutation rank / structural tuples); no team UUIDs, names, or other
  identity-bearing attributes cross the dispatcher boundary (DEC-9).
- [ ] **AC-GOV-NO-DISPATCHER-COMPILE-DEP** — the result fetch is HTTP only; no compile
  dependency on `vvwt-slotopt-dispatcher` is introduced (DEC-11); the Maven Enforcer ban
  stays.
- [ ] **AC-GOV-INTERFACE-MANDATE** — any new behaviour-bearing first-party Spring component
  obeys DEC-58 / DEC-72 / DEC-35 / DEC-36; the interface-mandate build guard stays green.
- [ ] **AC-GOV-RED-FIRST** — new first-party code is authored RED-first per DEC-22; the
  impl-report records RED-state evidence.
- [ ] **AC-GOV-BUILD-HYGIENE** — `mvn verify` exits zero (DEC-54); warning-free (DEC-29);
  Spotless / google-java-format (DEC-30); no production member exists solely for tests
  (DEC-70).
- [ ] **AC-GOV-COMMIT-FORMAT** — commit subjects use `chore(E63S02):` / `feat(E63S02):`
  prefixes per the close-story.sh contract.

### Error Handling

- [ ] **AC-ERR-RESULT-FETCH-FAILURE-FALLS-THROUGH** — if the result fetch fails (wire error,
  the dispatcher reports completed but the result is not retrievable), `tryLeg2()` returns
  `false` and routing falls through to Leg 3 — the operator still ends up with an optimized
  phase; the phase is never silently left unoptimized on a Leg-2 "success".
- [ ] **AC-ERR-EMPTY-PHASE-NO-OP** — an empty phase (no laps / no matches) is a no-op — the
  existing routing empty-phase guard is preserved.
- [ ] **AC-ERR-MALFORMED-RESULT-REJECTED** — a result payload from which the rank cannot be
  extracted is treated as a fetch failure (AC-ERR-RESULT-FETCH-FAILURE-FALLS-THROUGH), not
  applied as a corrupt optimum.

### Security

- [ ] **AC-SEC-NO-NEW-AUTH-SURFACE** — fetching the result introduces no new credential,
  authentication, or wire-protocol field beyond the existing E27 / DEC-43 dispatcher
  handshake; the DEC-43 algorithm-mismatch handling on the dispatcher interaction is
  unchanged. No dispatcher response field is trusted to carry identity-bearing data (DEC-9).
