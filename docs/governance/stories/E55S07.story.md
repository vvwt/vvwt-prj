## Acceptance Criteria

### M-1 Regression IT (phase.optimized silent regression)

- [ ] **AC-TEST-M-1-PHASE-OPTIMIZED-PERSISTENCE-RED** (testing): RED-first IT — set up a tournament with TWO phases requiring slot-opt (Phase 1: lapCount=10 — slow; Phase 2: lapCount=6 — fast, ~7ms slot-opt completion expected). Enqueue jobs for both phases via the orchestrator. Wait for both jobs to complete (`phase_lifecycle_job.status='COMPLETED'`). Assert post-state for BOTH phases: `phase.optimized=TRUE`, `phase.lastJobState='idle'`, all matches have `lap_number` + `field_number` non-null. The test MUST run 100 consecutive iterations and PASS GREEN on each (deterministic — not timing-sensitive). On the pre-E55-codebase baseline (E1 architecture), this same test FAILS at least once in 100 runs for Phase 2 (the fast-completion race). On the post-E55 codebase (E3 orchestrator), the test PASSES 100/100. Per Session Brief Q-6 M-1, the historical RED was reproduced 2026-05-11T22:06:47 — direct H2 read confirmed `phase.optimized=FALSE` in DB.

### M-2 Regression IT (phase.status ACTIVE→ASSIGNED regression)

- [ ] **AC-TEST-M-2-PHASE-STATUS-NO-REGRESSION-RED** (testing): RED-first IT — set up a tournament with Phase 1 in ASSIGNED status (via DEC-59 Clause C operator-confirmation); start Phase 1 (transitions to ACTIVE per E48S24); concurrently issue a Device.configure call (which historically triggered the regression observed 2026-05-11). Assert after configure completes: `phase.status='ACTIVE'` (unchanged); the regression to ASSIGNED does NOT occur. On E1 codebase, this test FAILS (regression observed); on E3 codebase, it PASSES.

### M-3 Regression IT (tournament.status ACTIVE→PLANNED regression)

- [ ] **AC-TEST-M-3-TOURNAMENT-STATUS-NO-REGRESSION-RED** (testing): RED-first IT — set up a tournament in PLANNED status with all phases PREPARED; start Phase 1 (auto-promotes tournament to ACTIVE per E48S24); concurrently trigger Spring listener cascade (e.g., simulate a Device.configure or other event that historically caused the M-3 regression). Assert after listener cascade: `tournament.status='ACTIVE'` (unchanged). On E1 codebase, this test FAILS (regression observed 2026-05-10/11); on E3 codebase, it PASSES.

### Restart-Recovery IT

- [ ] **AC-TEST-RESTART-RECOVERY-RED** (testing): RED-first IT — enqueue a job; orchestrator claims it (`status='RUNNING', claimed_by='jvm-1'`); simulate JVM restart by directly setting `claimed_by` to a fake-stale value (`'jvm-0-dead'`) and dropping the in-memory `WorkerRegistry` entry. Restart the orchestrator (via `WorkerRegistry.initOnStartup()` or equivalent — Delivery picks the hook). Assert post-recovery: the stale-claimed row is reset to `status='PENDING'` (or re-claimed by `'jvm-1'` directly — Delivery's contract), worker picks it up, job completes successfully. Verifies DEC-64 D-7 normal-loop recovery (no separate recovery service per DEC-64 supersession of DEC-55 D-8).
- [ ] **AC-TEST-RESTART-RECOVERY-CANCEL-RUNNING-RED** (testing): RED-first IT — claim a job; set `cancelled=TRUE`; simulate restart with stale `claimed_by`. On recovery, the orchestrator detects `cancelled=TRUE` AND `status='RUNNING'` AND fresh claim → dispatches to BSF-apply path (per E55S05 AC-TEST-CANCEL-PERSISTS-OVER-RESTART). Asserts post-state: `phase.optimized=TRUE`, `phase_lifecycle_job.status='COMPLETED'`, `cancelled=TRUE` retained.

### Combined IT — end-to-end happy-path on E3 architecture

- [ ] **AC-TEST-E2E-HAPPY-PATH-MULTI-TOURNAMENT-RED** (testing): RED-first IT — apply 2 tournaments concurrently, each with 3 phases (roundRobin / roundRobin / siegerehrung). Assert all 6 phases reach `status='PREPARED'`, optimized as expected (TRUE for roundRobin phases with optimize=TRUE; FALSE for siegerehrung phases per DEC-59 Clause F), all `phase_lifecycle_job` rows are `'COMPLETED'`. No deadlock observed. Total elapsed time < sum of sequential times (verifies parallelism per E55S03).
