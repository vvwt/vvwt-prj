# Story E23S07: Q-1a TDD-extract `CertificateTemplateRepository` interface + rename impl to `DefaultCertificateTemplateRepository` + author new DEC-26-compliant `CertificateTemplateRepositoryTest` (D-16)

## User Story

**As a** maintainer of the newly-relocated `de.vvwt.tm.certificate` module,
**I want** the concrete `CertificateTemplateRepository` class promoted to a
public port (interface) + `DefaultCertificateTemplateRepository` impl per
DEC-35 naming canon, plus a dedicated DEC-26-compliant DAO integration test
authored fresh via TDD RED-first,
**so that** the certificate module exposes a clean repository port per
DEC-35, the DAO boundary has generator/evaluator-separated tests per DEC-26
(closing the gap identified by Brief D-16 empirical grep: no such test
exists today), and subsequent certificate stories + Delivery work can rely
on a documented repository contract.

---

## Context

Per Brief v4 D-16 (empirically verified 2026-04-23 via
`find ... -name "CertificateTemplateRepository*Test*" -o -name "*CertificateTemplateRepository*IT*"`
returning zero results): no dedicated DAO test for
CertificateTemplateRepository exists today. Per DEC-26, DAO integration
tests MUST satisfy three rules (schema from production migration, assertj-db
verifier, direct-JDBC read-path fixtures) — the repository is currently
covered only transitively via `CertificateTemplateServiceImplTest`, which
is circular (DAO as its own evaluator).

Per Brief v4 D-9 Q-1a bucket: interface extraction from the concrete class
is Q-1a TDD RED-first under DEC-22 Iron Law (new Java type). Per DEC-35
§ "The interface MAY be a Spring Data Repository / CrudRepository interface
directly ... OR a separate hand-authored interface that wraps Spring Data
internally (port over adapter pattern)" — CertificateTemplateRepository is
a hand-authored `JdbcTemplate`-wrapping repo (not Spring Data), so the
interface is hand-authored per DEC-35 Item 2.

## Acceptance Criteria

- [ ] **AC-INTERFACE-EXTRACTED**: New public interface
  `de.vvwt.tm.certificate.CertificateTemplateRepository` with methods
  matching the existing concrete class's public API (CRUD-style operations
  on `CertificateTemplateMetadata`). Method signatures verbatim from the
  existing concrete class — Javadoc documents contract + cites DEC-35.
- [ ] **AC-IMPL-RENAMED**: Existing concrete class (relocated to
  `certificate.internal.*` in E23S06) renamed from
  `CertificateTemplateRepository` to `DefaultCertificateTemplateRepository`
  per DEC-35 naming canon. Implements the new interface.
- [ ] **AC-CONSUMER-REWIRE**: `DefaultCertificateTemplateService` (the
  impl in `certificate.internal.*`) constructor-injects the interface
  `CertificateTemplateRepository` instead of the concrete class.
  CertificateTemplateControllerIT / other consumers that type-reference
  the concrete class are updated to reference the interface (DEC-36
  cross-package rule).
- [ ] **AC-DAO-TEST-CREATED**: New file
  `src/test/java/de/vvwt/tm/certificate/internal/DefaultCertificateTemplateRepositoryIT.java`
  (or equivalent path per test-class convention). Tests the concrete impl
  via the `CertificateTemplateRepository` interface port.
- [ ] **AC-DEC-26-RULE-1**: DAO test loads schema from production
  migration via `ScriptUtils.executeSqlScript(Connection, Resource)`.
  Resource path is the new
  `classpath:db/migration/certificate/V1__*.sql` from E23S06. NO inline
  DDL strings in the test.
- [ ] **AC-DEC-26-RULE-2**: DAO test verifies database state after writes
  via `assertj-db` (`AssertDbConnection.table(...)` or equivalent), NOT
  by calling the DAO's own read methods. The DAO is never simultaneously
  subject and instrument of verification.
- [ ] **AC-DEC-26-RULE-3**: Read-path tests insert fixture data via direct
  JDBC (or `TenantDaoTestSupport.insertDirectly(...)`), NOT by calling
  the DAO's own write methods. Read-path and write-path tests are
  independent.
- [ ] **AC-DEC-26-TENANT-DAO-TEST-SUPPORT**: Test uses the `TenantDaoTestSupport`
  utility class (per DEC-26 § Enforcement) — `freshDataSource()` + `applyMigration()`
  + `assertDbOf()` + `insertDirectly()` — instead of ad-hoc wiring.
- [ ] **AC-TESTING-RED-FIRST**: TDD RED-first cycle per DEC-22 Iron Law.
  Test authored BEFORE interface + impl rename; first compilation / test
  run FAILS; interface + impl edits made; test GREEN. Commit history
  shows RED → GREEN.
- [ ] **AC-TESTING-DEC36**: Test in a different package than
  `DefaultCertificateTemplateRepository` (test is at public-facing
  `certificate.*` test package or `certificate.internal.*` test package;
  regardless, test type-references the `CertificateTemplateRepository`
  interface, not the concrete class) per DEC-36.
- [ ] **AC-TESTING-DEC41-OBSERVABLE-FORM**: Test assertions are
  observable-form per DEC-41: DB-state assertions (assertj-db) are
  external-spec-citation form (DDL schema from migration) + algebraic
  round-trip invariants (insert-then-find-via-direct-JDBC = input values
  preserved).
- [ ] **AC-ERROR-HANDLING-COVERED**: DAO test covers at minimum the
  exception paths documented by `CertificateTemplateServiceImpl`:
  storage errors (CertificateTemplateStorageException wrap path is at
  service layer not repo — verify; DAO-level errors likely DataAccessException).
  Test asserts exception is thrown + propagated when DB state is invalid
  (e.g., duplicate primary key if schema enforces it).
- [ ] **AC-MODULITH-VERIFY-GREEN**: `ApplicationModulesTest` GREEN.
- [ ] **AC-MVN-VERIFY-GREEN**: `mvn verify` GREEN on staging PR.
- [ ] **AC-GOVERNANCE-DEC-35-PATTERN**: Commit message cites DEC-35 Item 2
  (hand-authored interface wrapping JdbcTemplate) + DEC-26 rules 1-3 +
  Brief D-16.
- [ ] **AC-SECURITY-NA**: DAO layer has no authentication/authorization
  surface; tenant-scoping is via DEC-20 DataSource routing (external to
  DAO). No security-specific ACs in this story.
