# Story E22S09: TDD reconstruct 3 REST DTOs (records) in `web.internal.dto.*` + ScoreApiController in `web.*`

## User Story

**As a** maintainer of the post-E22 scoring REST surface,
**I want** three new Java record DTOs authored in
`de.vvwt.tm.web.internal.dto.*` (`MatchScoreResponse`,
`PartialScoreRequest`, `SetSubmitRequest`) and a new
`de.vvwt.tm.web.ScoreApiController` authored via strict RED-first
TDD against the `ScoreEntryService` public interface in
`de.vvwt.tm.scoring.*` (with jakarta-validation annotations, URL
mappings, and JSON wire format preserved byte-equivalent to the
legacy `de.vvwt.tm.infrastructure.score.*` surface),
**so that** the scoring-tablet and third-party REST clients can
migrate to the web-module endpoints without any observable wire
change, the Svelte admin-UI `/api/score/*` consumers continue to
function unchanged, and the legacy `infrastructure.score.*` REST
surface becomes safely deletable at the E22S11 atomic cutover.

---

## Context

E22S09 is one of two parallel RED-first TDD-reconstruction stories
for the scoring REST surface (companion: E22S10 — Mustache-backed
`ScoreController`). Per Brief v3 D-7, the three REST DTOs are
reconstructed as Java records (not classes) in
`de.vvwt.tm.web.internal.dto.*`. The package is web-internal per
DEC-35: the DTOs are a web-tier serialization concern and are not
intended as a public cross-module contract. Jackson wire-format
parity (JSON field names, URL paths, HTTP status codes, error
response shape) is a hard invariant per Brief Q-6 — the legacy and
reconstructed DTOs MUST produce byte-equivalent serialization for
identical input.

Per Brief D-12, entity-direct HTTP serialization is the default
post-E22; DTOs are justified here on (a) field omission (e.g.,
`tenantId` excluded from `MatchScoreResponse` wire format), (d)
field aliasing (Jackson `@JsonProperty` or `@JsonAlias` on record
components where legacy class names differ from record component
names), and the request-shape validation surface (PartialScoreRequest,
SetSubmitRequest carry `@Min`/`@Max`/`@NotBlank`/`@NotNull` jakarta-
validation annotations that must be preserved verbatim on the record
components).

`ScoreApiController` is authored as a `@RestController` with class-
level `@RequestMapping("/api/score")` per C-14 preserved URL map.
Three endpoints reconstructed byte-equivalent to legacy, calling
E22S06's public interface methods verbatim:
- `GET /match` — query params `field` (int) + `deviceToken` (String);
  invokes `scoreEntryService.getMatchForField(field, deviceToken)`
  returning `Optional<ScoreEntryResult>`; maps to 200 + body or 404.
- `POST /partial` — request body `PartialScoreInput` (scoring-public
  record delivered by E22S06; deviceToken carried inside body);
  invokes `scoreEntryService.handlePartialScore(request)` (void
  return); controller returns HTTP 204 No Content.
- `POST /submit` — request body `SetSubmitInput` (scoring-public
  record delivered by E22S06; deviceToken carried inside body);
  invokes `scoreEntryService.submitSetResult(request)` (void return);
  controller returns HTTP 204 No Content.

Each endpoint invokes the public interface
`de.vvwt.tm.scoring.ScoreEntryService` delivered by E22S06 — NOT
the `scoring.internal.DefaultScoreEntryService` implementation.

**Coordination verified with E22S06 (reviewer-flagged in cycle 1,
resolved in cycle 2):** E22S06 (post-refinement) delivers the
interface at authoring time with exact legacy method names:
`Optional<ScoreEntryResult> getMatchForField(int, String)`,
`void handlePartialScore(PartialScoreInput)`,
`void submitSetResult(SetSubmitInput)`. The 3 DTO records
(`PartialScoreInput`, `SetSubmitInput`, `ScoreEntryResult`) live in
`de.vvwt.tm.scoring.*` public root (Q-11 transitive-exposure — they
are parameter / return types of a public interface method). This
story consumes them directly at the controller — no scoping-boundary
DTO conversion layer required (DEC-40 Clause B entity-direct default
applies: scoring-public records ARE the Jackson wire format since
they carry the jakarta-validation annotations and the JSON field
shape E22S06 reconstructs from legacy).

A `MatchScoreResponse` web-internal DTO MAY be required if HTTP
wire-format parity with the legacy response body requires field
omission or aliasing (DEC-40 Clause B(a)/(d)); the story author
decides per AC-DTO-DECISION-JUSTIFIED below.

Per DEC-38, controller tests split two ways: the IT at
`@ApplicationModuleTest(module = "web", webEnvironment = RANDOM_PORT)`
covers end-to-end HTTP + Spring wiring; the slice test at
`@WebMvcTest(ScoreApiController.class)` covers
validation/error-response/security-negative paths with
`ScoreEntryService` mocked via `@MockitoBean`. Per DEC-36 cross-
package test typing rule, the mock target is the PUBLIC interface
`de.vvwt.tm.scoring.ScoreEntryService` (NOT the impl).

Per Brief Q-6, wire-format parity is asserted empirically: the IT
captures the response body as raw bytes and compares to a golden-
fixture JSON constant in the test class. The golden fixture is
derived from a pre-E22 legacy IT run (captured once at story
authoring and committed alongside the test). Any deviation blocks
story closure.

Legacy files (`de.vvwt.tm.infrastructure.score.ScoreApiController`,
`de.vvwt.tm.infrastructure.score.dto.*` three classes, and
`ScoreApiIT`) are UNTOUCHED this story — they continue to serve
requests until E22S11 atomic cutover.

### DTO decision + optional web-internal DTO (Q-1a TDD RED-first per DEC-22)

- [ ] AC-DTO-DECISION-JUSTIFIED (governance — DEC-40 Clause B):
  Per the refined DTO architecture (E22S06 provides scoring-public
  DTOs; they are consumed directly as Jackson wire format),
  web-internal DTOs are created ONLY when (a)/(b)/(c)/(d) of DEC-40
  Clause B applies. Story author decisions documented in impl-report:
  - **Request bodies** (`POST /partial`, `POST /submit`): The
    scoring-public `PartialScoreInput` + `SetSubmitInput` records ARE
    the Jackson wire format. No web-internal DTO required. Jakarta-
    validation annotations (`@Min`, `@Max`, `@NotBlank`, `@NotNull`)
    live on the scoring-public record components per E22S06's DTO-
    reconstruction ACs.
  - **Response body** (`GET /match`): If field-omission or aliasing
    is required (e.g., legacy `MatchScoreResponse` hides internal
    fields or uses different JSON field names than the scoring-
    public `ScoreEntryResult`), a web-internal `MatchScoreResponse`
    record is created at
    `de.vvwt.tm.web.internal.dto.MatchScoreResponse`. Otherwise the
    scoring-public `ScoreEntryResult` serves as the wire format
    directly. Story author cites the specific DEC-40 Clause B
    condition firing (or records "none — scoring-public record used
    directly").
  Legacy classes at `de.vvwt.tm.infrastructure.score.dto.*` remain
  UNTOUCHED (deleted in E22S11).
- [ ] AC-DTO-VALIDATION-BOUNDARY-VERIFIED (governance): Delivery
  greps scoring-public record files at pickup to confirm jakarta-
  validation annotations are present:
  ```
  grep -cE "@(Min|Max|NotBlank|NotNull|NotEmpty)" \
    vvwt-tm-web/src/main/java/de/vvwt/tm/scoring/PartialScoreInput.java \
    vvwt-tm-web/src/main/java/de/vvwt/tm/scoring/SetSubmitInput.java
  ```
  Each file MUST return >0. If missing, STOP and escalate for
  E22S06 amendment — do NOT re-declare validation annotations on a
  new web-internal DTO (the scoring-public record IS the validated
  wire contract).
- [ ] AC-JACKSON-WIRE-PARITY (testing — Q-6 hard invariant): For
  each endpoint, the IT captures the response body (or serialized
  request body for submits) as raw bytes and compares to a golden-
  fixture JSON constant derived from a pre-E22 legacy IT run,
  committed alongside the test at story authoring. If a web-
  internal DTO is introduced per AC-DTO-DECISION-JUSTIFIED, the
  parity assertion covers its Jackson output; otherwise the
  scoring-public record's output. Any divergence (field name, field
  order where pinned, field inclusion/omission) blocks story
  closure.
- [ ] AC-IF-WEB-DTO-RED-FIRST (testing — Q-1a, conditional):
  IF any web-internal DTO is authored per AC-DTO-DECISION-JUSTIFIED,

### Security

- [ ] AC-SECURITY-DEVICE-TOKEN (security — preserved from E22S06):
  Every endpoint validates the `deviceToken` (query-param for GET
  `/match`; body field on `PartialScoreInput` / `SetSubmitInput` for
  POST `/partial` + POST `/submit`) via E22S06's 3 public methods:
  `getMatchForField(fieldNumber, deviceToken)`,
  `handlePartialScore(request)`, `submitSetResult(request)` — which
  in turn invoke `DeviceRepository.findByToken(...)` per E22S06's
  AC-SECURITY-DEVICE-TOKEN. Invalid or absent token →
  `UnauthorizedException` → HTTP 401. Token valid but wrong field
  → `ForbiddenException` → HTTP 403. The slice test asserts both
  negative cases.
- [ ] AC-NO-ADMIN-AUTH-REGRESSION (security): The `/api/score/**`
  paths remain accessible without admin-session authentication per
  DEC-12 + existing SecurityConfig. The IT confirms: an
  unauthenticated client with a valid deviceToken receives 200
  (not 401 / not redirected to login).
