# Story E54S09: Replace `MaxConsecutiveIdleLaps` regression-IT with balance-metric IT (operationalizes DEC-63 Clause E)

## User Story

**As a** developer maintaining the slot-optimization regression-test suite,
**I want** the failing regression-IT `optimize_12T2G3F_idleTimeMetricImproved_maxIdleLapsLessThan5_E54S03` replaced by a new IT that asserts a balance-metric (variance / range / max-deviation of per-avatar idle-time products) below an empirically-grounded threshold,
**so that** the regression-suite tests the user's actual optimization objective (balance/variance-min) and not the misaligned MAX-MaxIdle metric that caused E54S03 to fail in the first place.

---

## Context

DEC-63 Clause E (2026-05-11) deprecates `MaxConsecutiveIdleLaps`-based regression-tests as misaligned with the user's stated balance-objective. The failing IT `optimize_12T2G3F_idleTimeMetricImproved_maxIdleLapsLessThan5_E54S03` in `LapOffsetCollapseRegressionIT.java:215-265` is the operational instance to replace.

This story is a **pure test-recalibration** (delivery_mode: source for test code only) — ZERO production-code change. The failing IT is removed (or renamed + recalibrated); a new balance-metric IT is added.

### Origin (Discovery follow-up forensik)

The failing IT was authored as part of E54S03 (Discovery 2026-05-10) with AC `MaxConsecutiveIdleLaps < 5`. The failure caused E54S03 to be marked `failed`. During Architecture-Discovery 2026-05-11 (E54S05), Discovery + user identified that:

1. The user's optimization objective is BALANCE / VARIANCE-MIN, not MAX-MIN (H-E confirmed).
2. The current voting + permutation algorithm IS domain-adequate (H-C rejected as defect by user; mixed laps are acceptable).
3. Empirical `MaxConsecutiveIdleLaps = 5` for 12T/2G/3F is NOT a defect — it just doesn't satisfy the wrong metric.

→ Replace the AC with a balance-metric IT.

### Balance-metric options (Delivery picks one + documents)

The new IT must use ONE of these balance-metrics:

- **STDDEV**: `STDDEV(per-avatar rating_i)` — standard statistical balance measure
- **RANGE**: `MAX(rating_i) - MIN(rating_i)` — simplest spread measure
- **MAX-DEVIATION**: `MAX(|rating_i - mean|)` — strictest balance constraint

Default Discovery recommendation: STDDEV (most mathematically aligned with the user's "nahe am Mittelwert" framing). Delivery may pick another and document rationale.

### Threshold `<X>` derivation

The exact threshold `<X>` is empirically grounded by Delivery:

1. Run the L1+L2+L3 pipeline on 12T/2G/3F at least 5 times (fresh runs).
2. Compute the chosen balance-metric for each run.
3. Pick `<X>` such that 4-5 out of 5 runs PASS (allow for narrow probabilistic margin).
4. Document the methodology + raw measurements in impl-report.

This is the same empirical-bound methodology that the prior (Bug-Triage Revision 1) version of E54S05 proposed — appropriate now that the metric itself is correct.

### Non-identity H-D verification (optional)

This story MAY add a focused unit-test in `SlotResultApplicatorTest` that verifies non-identity rank application for the 30-match / 10-lap case (closing the gap from H-D's partial-verification in Discovery's pre-flight). Optional; not required for the primary AC. If skipped, document the rationale in impl-report.

### Configuration awareness

When `BalancedVarietyScorer` (E54S07) ships, the test setup should ideally exercise both scorers (`tm.slotopt.scorer=mean` AND `tm.slotopt.scorer=balanced`). Both should pass the balance-metric AC (since either scorer produces balanced output, just with different aggregation). Delivery may parameterize the test on the scorer property.
