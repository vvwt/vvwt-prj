# Story E15S04: SecurityConfig + AdminCredentialsProvider — reconstruction-in-place with TDD

## User Story

**As a** consumer of Spring Security (the web layer authenticating HTTP requests),
**I want** `SecurityConfig` and its `AdminCredentialsProvider` wired in the new `auth` context with an integration test asserting request-time behaviour,
**so that** the security contract is testable end-to-end and the `auth` public API (`AdminCredentialsProvider`) is the single consumption point for other modules.

---

## Context

Per DEC-21, the root package `de.vvwt.tm.auth` exposes `AdminCredentialsProvider` as the sole public API (possibly with a refined signature vs legacy). All other `auth` types — including `SecurityConfig` — stay in `de.vvwt.tm.auth.internal`. `SecurityConfig` wires Spring Security's basic-auth chain, producing the beans the Spring Boot web layer consumes.

Per DEC-22, `SecurityConfig` is tested via an integration test against a real `SecurityFilterChain` (Spring's `MockMvc` or `WebTestClient`), asserting behaviour: valid credentials grant access; invalid credentials are rejected. Unit tests mocking `SecurityFilterChain` would not credibly prove the wiring; the Iron Law directs toward the real thing.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows failing integration tests for the SecurityFilterChain behaviour (valid creds accepted, invalid rejected) committed BEFORE the `SecurityConfig` / `AdminCredentialsProvider` implementations. Per DEC-22; characterization tests are forbidden.

- [ ] AC2 (security — valid credentials accepted): An integration test using `MockMvc` (or equivalent) sends a Basic-auth request with the admin username + a known plaintext password whose hash the test seeded via the Dao; the test asserts the request is accepted (HTTP 200 / non-401). The password is seeded through the real code path — no bypass of hashing.

- [ ] AC3 (security — invalid credentials rejected): An integration test sends a Basic-auth request with the admin username + a wrong password; the test asserts HTTP 401. A test with no credentials at all also asserts 401.

- [ ] AC4 (security — `AdminCredentialsProvider` is the only public API): `AdminCredentialsProvider` lives in root package `de.vvwt.tm.auth`. `SecurityConfig` lives in `de.vvwt.tm.auth.internal`. A deliberate spike demonstrates a test outside `de.vvwt.tm.auth.*` importing `SecurityConfig` directly would fail Modulith verify — the spike is documented in the Delivery plan and not committed.

- [ ] AC5 (error-handling — missing credentials table): If `SecurityConfig` starts up before `db/migration/auth/V1__*.sql` has been applied to the current tenant (e.g., a configuration error, or an integration-test misconfiguration), the filter chain's first request attempt surfaces a clear error — not a cryptic JDBC exception bubbling into an HTTP 500. An integration test asserts this.

- [ ] AC6 (security — session behaviour preserved): Spring Security session defaults (per the Epic's "session management unchanged") are retained. A test documents the session behaviour observed in the legacy code (stateful / stateless / short-timeout) and the new `SecurityConfig` matches it. If Delivery detects a deviation, escalate — do not silently change session semantics.

- [ ] AC7 (testing — Modulith verify): `ApplicationModulesTest` remains green. The new `SecurityConfig` + `AdminCredentialsProvider` work alongside the legacy classes (which remain live in their original package until E15S07 cutover).

- [ ] AC8 (governance — parallel-phase bean-collision avoidance without feature flags): During the parallel phase, `mvn -pl vvwt-tm-web verify` remains green. This proves Spring context loads successfully WITHOUT any `@Profile`, `@ConditionalOnProperty`, `@ConditionalOnBean`, `@ConditionalOnMissingBean`, or other `@Conditional*` annotation bridging old-and-new. The Delivery plan names the chosen mechanism (option A bean-rename OR option B deferred @Configuration — see Notes) and `git grep '@Profile\|@Conditional'` on the post-merge state shows NO new additions introduced by this story.

## Notes

Bean-collision risk during parallel phase is real — two `@Configuration` classes with `@Bean SecurityFilterChain` methods would collide at Spring context load. Per DEC-21 line 61 ("No feature flags. No @ConditionalOnProperty, no @Profile"), the ONLY permitted mitigation is a non-conditional mechanism. Two viable options remain:
- Option A: Rename the new `SecurityFilterChain` bean and add an explicit qualifier; the legacy chain keeps its default name. At cutover (E15S07), rename goes away and the new bean takes the default name.
- Option B: The new `SecurityConfig` class is NOT annotated with `@Configuration` during parallel phase (it exists in the package but is not picked up by component scan). At cutover, `@Configuration` is added in the same atomic commit that deletes the legacy class.
Delivery picks one and documents in the plan; AC8 enforces the chosen mechanism is verifiable at `mvn verify` time without feature flags.
