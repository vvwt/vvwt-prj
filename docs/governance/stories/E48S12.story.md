# Story E48S12: Wire TimelineCalculationService into DraftService.preview() — Activate DraftPreviewResult.timeline

## User Story

**As a** Tournament Organizer,
**I want** the Phasenplan-Vorschau to display the existing per-lap timeline table (with phase, lap, type, start–end times, and break labels) when I have set the tournament's start time,
**so that** I can see the detailed schedule of every match round and pause from one place — without having to wait for the print Laufzettel or the live Timer to be generated.

---

## Context

Per Brief D-9 / O-12 / O-13 (`discovery-2026-05-06-phasenplan-preview-fixes`): E21S11 (PR #62, merged 2026-04-20) shipped a complete `TimelineCalculationService` — the interface (`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/TimelineCalculationService.java:56-74`), the `DefaultTimelineCalculationService` implementation, and 5 supporting domain records (`PhaseConfig`, `PhaseBreakConfig`, `TimelineEntry`, `TimelineEntryType`, ...). Two production consumers actively use the engine: `DefaultLaufzettelAssembler` (Print module, line 260 `timelineCalculationService.calculate(...)`) and `DefaultActivityScheduleAssembler` (Print module, line 142) and `DefaultTimerDataService` (Timer module, line 204).

The third originally-planned consumer — the draft preview path — was never wired. `DefaultDraftService.preview():137-138` still hardcodes:

```java
// Timeline entries deferred to E21S11 (TimelineCalculationService)
return new DraftPreviewResult(previews, List.of());
```

The Javadoc comment promises a wiring that did not happen at E21S11 merge. `DraftTimelineEntryResponse.java:8-12` still says "future E21S11 timeline domain classes... E21S11's TimelineCalculationService **will** produce..." — pre-merge wording, never updated.

Frontend consequence: the `DraftConfig.svelte:512-536` timeline-table is conditionally rendered when `preview.timeline.length > 0`, but the condition is **never true** because the backend always returns an empty list. The user reports (2026-05-06) "Ich sehe aber keine Timeline und auch keine Details" — confirming the dead-code surface.

This story closes the spec-gap by mapping `DraftConfig` + `tournament.plannedStartTime` to the `TimelineCalculationService.calculate(...)` API and converting the returned `List<TimelineEntry>` to `List<DraftTimelineEntryResponse>` for the existing `DraftPreviewResult.timeline` slot. No frontend changes — the existing render-on-non-empty-list logic activates automatically.

**Impedance note for Delivery (Brief T-7):** `TimelineCalculationService.calculate(LocalTime startTime, List<PhaseConfig> phases, int sectionBreakMinutes)` accepts a SINGLE `sectionBreakMinutes` for ALL phase boundaries. `DraftSection` carries a per-section `sectionBreakTimeMinutes`. Resolution path is open — see AC-IMPL-IMPEDANCE-RESOLUTION below.

  - At least one `MATCH_ROUND` entry per non-Siegerehrung phase (count = totalLaps from S10 formula)
  - `INTRA_PHASE_BREAK` entries for each declared `DraftBreak`
  - `SECTION_BREAK` entries between consecutive phases (per impedance resolution, see AC-IMPL-IMPEDANCE-RESOLUTION)
  - First entry's `startTime` equals the tournament's `plannedStartTime` (HH:mm portion when LocalDateTime → LocalTime narrowing applies)

- [ ] **AC-IMPL-DRAFT-SERVICE-PREVIEW-WIRES-TIMELINE-SERVICE**: `DefaultDraftService.preview()` invokes `TimelineCalculationService.calculate(...)` to populate the `timeline` field of `DraftPreviewResult`.   - `lapBreakTimeMinutes` = `section.lapBreakTimeMinutes`

- [ ] **AC-IMPL-IMPEDANCE-RESOLUTION** (governance): The `int sectionBreakMinutes` parameter accepts a SINGLE value for all phase boundaries — but `DraftSection.sectionBreakTimeMinutes` is per-section. Delivery MUST resolve this via ONE of:
  - **(i)** Loop strategy — call `calculate()` once per phase pair with the from-phase's `sectionBreakTimeMinutes`, concatenating results. Requires careful handling of cumulative startTime offsets.
  - **(ii)** Extend `TimelineCalculationService.calculate(...)` signature to accept `List<Integer> sectionBreakMinutesPerBoundary` of size `phases.size() - 1`, with default-overload accepting a single int that broadcasts. Updates 3 existing consumers (`DefaultLaufzettelAssembler`, `DefaultActivityScheduleAssembler`, `DefaultTimerDataService`) to use the new signature.
  - **(iii)** Use `PhaseConfig.breaks` to encode a trailing `INTRA_PHASE_BREAK` mimicking the SECTION_BREAK semantics — semantic stretch, NOT recommended.
  - **ESCALATE** if Delivery cannot decide between (i) and (ii) — Discovery defers to a follow-up consult (Bug-Triage Q-1 "Story defines WHAT not HOW" applies; this AC is the explicit escalation path).
- [ ] **AC-IMPL-LOCAL-DATE-TIME-NARROWING**: `tournament.plannedStartTime` is a `LocalDateTime` (per backend Tournament entity); `TimelineCalculationService.calculate` accepts `LocalTime`. The Mapping uses `plannedStartTime.toLocalTime()`. Multi-day tournaments are NOT supported in this preview (timeline assumes single-day; documented limitation).
