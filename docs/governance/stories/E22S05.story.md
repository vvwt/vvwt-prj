# Story E22S05: TDD-reconstruct 2 registries (`scoring.*` public) + `TournamentRuleResolver` (`scoring.internal.*`)

## User Story

**As a** maintainer of the `de.vvwt.tm.scoring` Modulith module,
**I want** `ScoringRuleRegistry` and `SetValidationRuleRegistry`
reconstructed as `@Component` beans in the `de.vvwt.tm.scoring.*`
public root (cross-module callable), and `TournamentRuleResolver`
reconstructed as a `@Component` in `de.vvwt.tm.scoring.internal.*`
(not callable from outside the scoring module), all via RED-first TDD,
**so that** the 5 rule beans delivered by E22S04 can be resolved by
their persisted string IDs at cascade entry, the `web` module's
relocated `TournamentRulesController`/`ScoringRulesController` (E22S08)
can call `ScoringRuleRegistry.knownIds()` for the rules-listing
endpoint without reaching into `scoring.internal.*`, and
`TournamentRuleResolver` remains an implementation detail of scoring.

---

## Context

Per D-9 (Brief v3), the scoring module's public surface includes the
two registries (consumer: `web.ScoringRulesController` post-E22S08,
for the rules-listing endpoint); the `TournamentRuleResolver` stays
internal (consumer: only `DefaultScoringService` + `ScoreEntryService`,
both within the scoring module). This split enforces DEC-35 (module
public API discipline) while keeping the resolver — which embeds the
`(Tournament) → (rule, validator)` knowledge — hidden.

Classification: Q-1a TDD RED-first per C-2. Legacy templates at
`de.vvwt.tm.domain.rules.{ScoringRuleRegistry, SetValidationRuleRegistry,
TournamentRuleResolver}` remain in place unmodified through this story.

The dual-bean-boot pattern from E22S04 extends: if
`@ComponentScan` exclusion for `de.vvwt.tm.domain.rules.*` was set up
in E22S04, this story inherits that exclusion mechanism — no new
exclusion needed. The impl-report MUST verify the exclusion still
covers the 3 new bean names.

Consumer-graph:
- `ScoringRuleRegistry` — constructor takes a `Map<String, ScoringRule>`
  (Spring autowires all `ScoringRule` beans by qualifier name);
  methods `get(String id) → ScoringRule`, `knownIds() → Set<String>`.
- `SetValidationRuleRegistry` — constructor takes
  `Map<String, SetValidationRule>`; methods `get(String id) →
  SetValidationRule`, `getAll() → Map<String, SetValidationRule>`.
- `TournamentRuleResolver` — constructor takes both registries;
  method `resolve(Tournament) → (ScoringRule, SetValidationRule)`
  (returned as a small internal record/VO), throws `ValidationException`
  on unknown rule ID.

### Error-handling

- [ ] **AC-UNKNOWN-ID-VALIDATION**: `ScoringRuleRegistry.get(unknownId)`
  and `SetValidationRuleRegistry.get(unknownId)` throw
  `ValidationException` with a clear, user-actionable message
  (e.g., `"unknown scoring rule id: '<id>'"`). Behavior preserved
  from legacy. RED-first test required.
- [ ] **AC-NULL-GUARDS**: `registry.get(null)` throws
  `IllegalArgumentException`; `resolver.resolve(null)` throws
  `IllegalArgumentException`. RED-first test required.
- [ ] **AC-RESOLVER-CASCADE-ENTRY**: Resolver rejects tournaments
  referencing an unknown rule ID at cascade entry via
  `ValidationException` — this is the same rejection that
  `DefaultScoringService.registerMatchResult(...)` relies on for
  fail-fast behavior. Legacy behavior preserved.

### Security

- [ ] **AC-SECURITY-ID-VALIDATION**: The unknown-rule-ID rejection at
  cascade entry is the **security-relevant behavior** preserved in
  this story: without it, a tenant with a corrupted
  `tournament.scoring_rule_id` (database drift, manual DB edit, or
  stale Flyway baseline) could silently produce arbitrary cascade
  results. `AC-UNKNOWN-ID-VALIDATION` is the guard. No other authN/
  authZ surface is introduced — registries are read-only lookups and
  the resolver is a pure function. This AC satisfies the Q-9 security
  category **substantively** (not N-A).
