# Story E53S10: Fix — Laufzettel renders zero rows when ACTIVE-filter narrows phases to a single non-first phase (`PhaseConfig` positional-vs-`sequenceNumber` divergence in the `assembleWithTimeline` path)

## User Story

**As a** Tournament Organizer who has completed the group stage (Phase 1) and started the round-robin Zwischenrunde (Phase 2),
**I want** the printed Laufzettel (both the per-team and the Sammeldruck view) to show every Phase-2 round with opponent/court/referee/activity per team,
**so that** participants can find their next round and court without me reading out the spielplan manually.

---

## Context

A real tournament ("31. Frühjahrsturnier", 30.05.2026) entered the operationally normal state Phase 1 = COMPLETED, Phase 2 = ACTIVE with `tournament.plannedStartTime = 09:00`, 6 rounds, 10+ teams, and Phase-2 matches with lap+field assignment and TeamAvatar→Team resolution confirmed via Admin "Spiele anzeigen" (real team descriptions visible). Both Laufzettel endpoints — `GET /print/tournaments/{tid}/team-schedules` (Sammeldruck) and `GET /print/tournaments/{tid}/team-schedules/{teamId}` (per-team) — render the per-team `<section>` with team headers and the 4-column table shell (Runde | Zeit | Aktivität | Feld) but produce an **empty `<tbody>`** per team. The `print/laufzettel-no-matches` fallback is not rendered, so `PrintController.hasAnyMatches(phases)` returned `true`.

### Root-cause analysis (Discovery-converged via in-session code-read of HEAD `a1a4006a`)

`DefaultLaufzettelAssembler.buildPhaseConfigs` (vvwt-tm-web/src/main/java/de/vvwt/tm/print/internal/DefaultLaufzettelAssembler.java, lines 585–621) numbers `PhaseConfig.phaseNumber` **positionally** in the input list:

```java
int seqNumber = 1;
for (Phase phase : phases) {
    ...
    configs.add(new PhaseConfig(seqNumber, lapCount, lapTime, lapBreak, breakConfigs));
    seqNumber++;
}
```

`DefaultTimelineCalculationService.calculate` emits `TimelineEntry` instances with `phaseNumber == PhaseConfig.phaseNumber` (the positional value).

`DefaultLaufzettelAssembler.assembleWithTimeline` (lines 333–411) resolves each `TimelineEntry` back to a `Phase` via:

```java
Map<Integer, Phase> phaseBySeqNumber = new HashMap<>();
for (Phase phase : phases) {
    phaseBySeqNumber.put(phase.getSequenceNumber(), phase);  // line 350
}
...
Phase phase = phaseBySeqNumber.get(phaseNumber);              // line 357
if (phase == null) continue;                                  // line 358
```

— keyed on the **actual** `phase.getSequenceNumber()`.

Before E53S02 introduced the ACTIVE-filter at `PrintController.allTeamSchedules` (line 386–389) and `singleTeamSchedule`, `phases` always contained the full ordered phase list — positional and `sequenceNumber` aligned (1↔1, 2↔2, 3↔3). After the filter, when only Phase 2 remains in `phases` (because Phase 1 is COMPLETED), the two diverge: `PhaseConfig.phaseNumber == 1` (positional), `phase.getSequenceNumber() == 2`. `phaseBySeqNumber.get(1)` returns `null`, every `TimelineEntry` hits `continue`, and 0 rows are appended.

This is path-dependent on `hasTime == true`: `assembleWithoutTimeline` (lines 414–458) iterates `phases` directly and keys by `phase.getId()`, so the no-time branch is unaffected — but `plannedStartTime` is set on the operator's tournament.

### Scope discipline

Discovery investigated and CONVERGED to a single most-likely root cause via code-read + user-empirical confirmation. The Story's RED-first IT is the **symptom oracle** — Delivery is free to fix at either divergence site (PhaseConfig-side numbering OR `phaseBySeqNumber`-side keying), as long as the RED test passes GREEN. Discovery recommends the PhaseConfig-side shape per AC-IMPL-FIX-SHAPE-RATIONALE (Q-4 of the Session Brief: keeps `PhaseConfig.phaseNumber` semantically aligned with the domain `phase.sequenceNumber`; the alternative hides the asymmetry in the assembler's local map). Operator confirmed Shape (a).

### Fix shape (recommended)

Shape (a) per operator confirmation: in `DefaultLaufzettelAssembler.buildPhaseConfigs`, source the first `PhaseConfig` argument from `phase.getSequenceNumber()` instead of the incremental `seqNumber`. This keeps `PhaseConfig.phaseNumber` semantically aligned with the domain concept. Rough sketch:

```java
// before:
int seqNumber = 1;
for (Phase phase : phases) {
    ...
    configs.add(new PhaseConfig(seqNumber, lapCount, lapTime, lapBreak, breakConfigs));
    seqNumber++;
}
// after:
for (Phase phase : phases) {
    ...
    configs.add(new PhaseConfig(phase.getSequenceNumber(), lapCount, lapTime, lapBreak, breakConfigs));
}
```

This is a hint, not a prescription. Shape (b) (key `phaseBySeqNumber` positionally in `assembleWithTimeline`) is also acceptable per AC-GOV-FIX-SCOPE-MINIMAL — Delivery picks based on local code judgment.
