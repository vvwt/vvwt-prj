# Story E55S14 (Bug-Triage): H2 dependency-version upgrade 2.3.232 → 2.4.240 — re-do of escalated E55S12 under DEC-67 (dependency-version changes fall outside DEC-22 RED-first scope)

## User Story

**As a** Tournament Manager operator,
**I want** the H2 database engine upgraded from 2.3.232 to 2.4.240 — the version empirically verified to eliminate the M-2/M-3/M-5/Display-token-loss MVStore bug class — landed in the production deployment via a single dependency-version-coordinate change,
**so that** the silent data-loss bug class (Phase ACTIVE→PREPARED regression; Tournament ACTIVE→PLANNED regression; device-row loss; Display-token invalidation) is structurally addressed for tournament/phase/device data, complementing the audit-log file-isolation already delivered by E55S13.

---

## Context

### Why this story exists — DEC-67 corrects E55S12's category error

E55S12 attempted this exact upgrade and escalated as `failed`. The escalation reason was NOT a defect in the upgrade — it was a **governance category error**: E55S12's story imposed an AC requiring a deterministic RED-first IT (`H2VersionUpgradeRegressionProtectionIT`) proving the Heisenbug under H2 2.3.232 before the `pom.xml` bump could land. The IT ran GREEN at N=10 and N=30 under 2.3.232 — the M-2/M-3/M-5 Heisenbug requires concurrent multi-connection MVStore compaction and structurally cannot reproduce in a single-JVM in-process `@SpringBootTest` harness. The `pom.xml` bump was therefore never committed.

Discovery cycle (2026-05-15) determined that a dependency-version bump is not first-party-code authoring — it substitutes a vendor-released artefact. **DEC-67** amends DEC-22: dependency-version changes fall outside RED-first scope; verification is *existing-suite-green + defect-justification*, not a failing-test-first artefact. This is the same category as DEC-29's mechanical-fix carve-out (`conventions.md` § Compiler Hygiene). E55S14 is the first story authored under DEC-67.

E55S12 is NOT reopened — it stays `failed` as the historical record of the category error. E55S14 is the clean re-do.

### Empirical defect-justification (per DEC-67 clause 2)

| Run | Date | H2 Version | Logging | Bug |
|---|---|---|---|---|
| v4 | 2026-05-13 23:04 | 2.3.232 | minimal v4-class | OCCURRED |
| v5 | 2026-05-13 23:54 | 2.3.232 | v5-class | OCCURRED |
| v6 / Stair-0 | 2026-05-14 00:24 | 2.3.232 + WRITE_DELAY=0 | v5-class | OCCURRED |
| Stair-0b | 2026-05-14 ~01:30 | 2.4.240 | v5-class | DID NOT OCCUR |
| Stair-0b-min | 2026-05-14 ~01:50 | 2.4.240 | minimal v4-class | DID NOT OCCUR |

H2 2.4.240 changelog (https://www.h2database.com/html/changelog.html, release 2025-09-22) — two fixed Issues map directly to E55S11 hypotheses: **Issue #4247** "Compaction causes missing chunks and data loss" → H-B'(b2) MVStore compaction race; **Issue #4208** "Lost update when attempting to atomically increment a value using SELECT FOR UPDATE" → H-Z FOR-UPDATE + MVCC snapshot interaction.

**Residual risk** (honest framing per DEC-67 clause 2 — documented, proportionate): the fix-verification is n=2 operator-interactive runs, not statistically rigorous. Low-frequency residual recurrence cannot be empirically ruled out (E55S11 hypothesis H-G-(b) commit-flush no-op was not explicitly cited by the 2.4.240 fixes). Operator monitoring is the residual-risk control (AC-ERROR-HANDLING-RESIDUAL-RECURRENCE-MONITORING).

### Relationship to E55S13

E55S13 (audit-log file-isolation, `done`) is independent of this story. E55S13 protected the audit-log dimension regardless of H2 version. E55S14 addresses the remaining exposure: tournament/phase/device data under H2. Both are belt-and-suspenders for the same bug class on different data dimensions.

### DEC-67 classification (clause 3) — provisional, confirmed by `mvn verify`

This story is classified as a **pure version-coordinate change** — but the classification is **provisional until `AC-TEST-EXISTING-SUITE-GREEN` passes**. The basis for the provisional classification: E55S12's escalation observed (via operator-interactive runs under 2.4.240 + the H2 2.4.240 changelog) that the upgrade requires no source-level migration for this codebase's usage profile (file-mode embedded + standard JDBC; URL options `AUTO_SERVER`, `CASE_INSENSITIVE_IDENTIFIERS`, `MV_STORE`, `WRITE_DELAY`). This is a runtime + changelog observation — E55S12 escalated at the RED-first IT step *before* ever running `mvn verify` to BUILD SUCCESS under 2.4.240, so "no source migration" is not yet a compile/test-verified fact.

Under DEC-67 clause 1 + clause 3: while the change stays a pure version-coordinate change, DEC-22 RED-first does NOT apply. **If `mvn verify` reveals a forced first-party source edit (compile or test breakage under 2.4.240), the classification flips** — the coordinate change stays under DEC-67, the forced edit becomes DEC-22 RED-first territory — and the story escalates per AC-ERROR-HANDLING-MVN-VERIFY-FAILURE-ESCALATE for a new Discovery cycle to scope the edit. `AC-TEST-EXISTING-SUITE-GREEN` is the gate that confirms the pure-coordinate classification.

- [ ] **AC-IMPL-NO-OTHER-PRODUCTION-CHANGES**: Verify via `git diff` that the only production-side change is `pom.xml:70`. No first-party Java source, no `application.yml`, no Flyway migration changes. (The regression-guard IT per AC-TEST-GREEN-ONLY-REGRESSION-GUARD is test code, not production code.) If `mvn verify` reveals a compile-time or runtime API breakage forcing a source edit, escalate per AC-ERROR-HANDLING-MVN-VERIFY-FAILURE-ESCALATE — a forced source edit would re-classify part of the story under DEC-22 RED-first.

### Testing (mandatory category — Epic E55 declares)

- [ ] **AC-TEST-EXISTING-SUITE-GREEN**: `mvn verify` invoked from the `vvwt-prj` root (full reactor, full Maven lifecycle per DEC-54 — NOT a `-pl`-scoped partial reactor invocation) BUILD SUCCESS, exit-0, zero failures, under H2 2.4.240. This is the DEC-67 clause-2 **mandatory** verification gate — it proves the contract the first-party code depends on is preserved across the vendor-artefact substitution. All existing tests (post-E55S13 suite — note the `audit_log` table no longer exists after E55S13's atomic cutover) pass. This AC and AC-GOVERNANCE-DEC-54-MVN-VERIFY are the same `mvn verify` full-root invocation viewed from the testing vs governance category — a single BUILD SUCCESS satisfies both.

- [ ] **AC-TEST-GREEN-ONLY-REGRESSION-GUARD**: Author `H2VersionUpgradeRegressionProtectionIT` as a **GREEN-only regression guard** (per DEC-67 clause 2 *recommended*). NOT a RED-first artefact — it is authored against the post-upgrade (2.4.240) state and is GREEN from its first run; DEC-67 clause 1 establishes that RED-first does not apply to this dependency-version change. The IT programmatically runs the operator workflow (create tenant → create tournament → apply Phasenplan → assign teams → activate Phase 1 → register Display device → configure Display) for N cycles (default N=10, configurable via `tm.test.recurrence-protection-cycles`, ≤10 min runtime for N=10), and per cycle asserts the M-2/M-3/M-5 invariants: `phase[1].status == 'ACTIVE'` AND `tournament.status == 'ACTIVE'` AND `tournament.active_sentinel IS NOT NULL` AND `devices.count >= 1`. Annotation: `@SpringBootTest(classes = TournamentManagerApplication.class, webEnvironment = NONE)` — the IT spans the full multi-module operator workflow (not a bounded-context-module-scoped test), consistent with E55S12's accepted annotation precedent. The guard's diagnostic limitation is acknowledged: it catches a gross regression (e.g., an accidental H2 downgrade) but, being GREEN-only, does not reproduce the original Heisenbug.
