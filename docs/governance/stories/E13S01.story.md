# Story E13S01: Add Spring Modulith dependency + ApplicationModulesTest (baseline verify pass)

## User Story

**As a** TM maintainer preparing the project for bounded-context reconstruction,
**I want** Spring Modulith installed on `vvwt-tm-web` and a verify-phase test proving the current codebase satisfies its default module layout,
**so that** every subsequent context story can declare `@ApplicationModule` boundaries against a known-green baseline.

---

## Context

Before any context-level reconstruction (E14, E15) can proceed, the project must possess a mechanism to enforce module boundaries at test time. The TM backend today is 214 Java files with no module metadata; Modulith treats an unannotated codebase as one implicit module, so a verify-pass here means "the Modulith machinery runs and understands the project", not "boundaries are enforced yet".

This story is infrastructure-only. No bounded-context code moves, no package is reorganised, no legacy class is touched. Its only deliverables are: (a) a Maven dependency, (b) a single JUnit test file, (c) the test wired into `mvn verify`. Per DEC-21, the test cannot be `@Disabled` or ignored.

---

## Decision Points

- **Spring Modulith version selection:** 2.x line (targets Spring Boot 4.x) vs 1.4.x line (compatible with the SB 3.4.7 BOM fallback per DEC-10). Delivery picks based on the Spring Boot version active at story start; the choice + rationale is documented in AC2 and in the Delivery plan.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first, replayable red state): Git history shows two commits: (i) FIRST commit adds `ApplicationModulesTest` in a deliberately-red state (the test file references `TournamentManagerApplication` with `ApplicationModules.of(TournamentManagerApplication.class).verify()` when the intended scan is not yet valid — e.g., the annotation is missing or the target application class is stubbed); this commit MUST produce non-zero exit when `mvn -pl vvwt-tm-web test` is run at that commit hash. (ii) SECOND commit makes the test green (adds the full Modulith scanning target). Per DEC-22, reviewers can verify the red state by checking out commit (i) and running the test.

- [ ] AC2 (governance — dependency management): `spring-modulith-starter-core` and `spring-modulith-starter-jpa` are added to `vvwt-tm-web/pom.xml` with the version managed in `vvwt-prj/pom.xml` per DEC-10 C-1. The chosen Modulith line matches the current Spring Boot baseline (2.x line for SB 4.x; 1.4.x line for the SB 3.4.7 fallback period per DEC-10).

- [ ] AC3 (testing — baseline verify): `ApplicationModulesTest` exists under `vvwt-tm-web/src/test/java/de/vvwt/tm/` and executes `ApplicationModules.of(TournamentManagerApplication.class).verify()`. Running `mvn verify` from `vvwt-prj/` completes with the test green against the pre-reconstruction 214-file codebase.

- [ ] AC4 (governance — verify-phase wiring): The test runs in Maven's `verify` phase (not just `test` phase) so that module-boundary violations fail the same lifecycle stage that produces deployable artefacts. The test class is NOT `@Disabled`, `@Ignore`d, or tagged as excluded per DEC-21 C-8.

- [ ] AC5 (error-handling — persistent violation proof): A throwaway demonstration proves `ApplicationModulesTest` fails on a boundary violation. The sample output (the actual `verify()` failure stdout/stderr lines showing a rejected cross-module dependency) is persisted in the repository at `docs/modulith-verify-violation-sample.txt` (or equivalent path documented in the Delivery plan). The sample file is committed with E13S01 so that future reviewers can read the exact failure shape Modulith produces — this is NOT a trust-me attestation. The throwaway spike code itself is reverted before merge; only the sample output is retained.

- [ ] AC6 (governance — no behavioural code change): No existing production class under `de.vvwt.tm.*` is modified by this story. `git diff` at merge time shows only `pom.xml` changes, one new test file, and (optionally) a `package-info.java` at the application root if required by Modulith to locate the module scanner start.

- [ ] AC7 (error-handling — fail-closed signal): If Spring Modulith dependency resolution fails at build time (wrong version, BOM mismatch), `mvn verify` fails with an actionable error — not a silent skip of the ApplicationModulesTest. A Delivery run exercises this path during verification.

## Notes

The Modulith starter version must be selected deliberately: Spring Modulith 2.0.5 (stable at 2026-03-27) targets SB 4.x. If the project is still on the SB 3.4.7 BOM fallback per DEC-10 at the time of delivery, the 1.4.x line is the correct pick. The Delivery execution plan must document which line was chosen and why.

The violation-proof spike (AC5) is the only way to distinguish "verify() ran and found nothing to check" from "verify() is actually enforcing". Do not skip it.
