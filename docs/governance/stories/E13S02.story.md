# Story E13S02: Activate project-level TDD rules + document JMH carve-out

## User Story

**As a** Delivery Agent preparing to execute any Wave-1 story,
**I want** the TDD Iron Law loaded from `project/contexts/rules/tdd.rules.md` with the JMH carve-out documented explicitly,
**so that** every implementation session reads the same enforceable rule without re-deriving it from DEC-22.

---

## Context

DEC-22 activates TDD projektweit across all five `vvwt-prj` Maven modules, with `vvwt-benchmark` as the sole carve-out. Activation is mechanical: the framework ships the rule at `.gaai/core/contexts/rules/tdd.rules.md`; activation consists of inheriting or copying it into `.gaai/project/contexts/rules/tdd.rules.md` so the tool adapter loads it at session start.

Without this activation, the Delivery Agent may still honour TDD in spirit but has no project-level rule file to cite; enforcement drifts. The JMH carve-out, in particular, must be pinned down in writing so that future `vvwt-benchmark` stories do not trigger a false Iron-Law failure.

This story is a governance activation, not code. The deliverables are markdown rule files and a `patterns/conventions.md` Testing section update.

---

## Acceptance Criteria

- [ ] AC1 (governance — rule inheritance): `.gaai/project/contexts/rules/tdd.rules.md` exists, either as a copy of `.gaai/core/contexts/rules/tdd.rules.md` or a project-level override file that inherits and extends it. The file is loaded at Claude Code session start via the standard rule-loading mechanism.

- [ ] AC2 (governance — JMH carve-out): The project-level `tdd.rules.md` contains an explicit paragraph naming `vvwt-benchmark` as carved out from the Iron Law, with the rationale ("JMH measures, does not assert") and the fallback ("behavioural correctness of benchmarked code is covered in the hosting module").

- [ ] AC3 (governance — conventions update): `patterns/conventions.md` gains a "Testing" section that: (a) restates the Iron Law in one line, (b) names the JMH carve-out, (c) references Reconstruction-in-Place as the TM-Module migration strategy, (d) links to DEC-22.

- [ ] AC4 (testing — rule retrieval verification): A dry-run verification is documented in the Delivery execution plan showing that starting a new Delivery session loads the project-level TDD rule (e.g., via a skill that prints loaded rules, or via a spot check on one of the five modules). No silent load failure is tolerated.

- [ ] AC5 (error-handling — malformed rule file fail-closed): If `.gaai/project/contexts/rules/tdd.rules.md` is malformed at session start (invalid YAML frontmatter, missing mandatory fields, or unreadable), the tool-adapter logs a diagnostic at ERROR level and falls back to the core rule `.gaai/core/contexts/rules/tdd.rules.md` — the Iron Law MUST NOT silently degrade to "no TDD rule active". A Delivery run with a deliberately-malformed project rule (spike, not committed) verifies the fallback path during story delivery.

- [ ] AC6 (testing — JMH carve-out smoke): A minimal entry in `vvwt-benchmark/README.md` (or equivalent module doc) names the carve-out and references the project rule file. Delivery verifies the doc exists; no behavioural code change is required in `vvwt-benchmark`.

- [ ] AC7 (governance — effective-date note): The project-level `tdd.rules.md` explicitly states the effective date (story merge date) and scope ("all five `vvwt-prj` Maven modules except `vvwt-benchmark`"), matching DEC-22's activation contract.

- [ ] AC8 (governance — activation scope clarification): Activation is tool-adapter-based (the Claude Code / CLI adapter loads `project/contexts/rules/tdd.rules.md` at session start), making the TDD Iron Law session-global across any Maven module the Delivery Agent works on. NO per-module marker file is required — DEC-22's "active across all vvwt-prj modules" is satisfied by the adapter-load, not by per-module artefacts. The Delivery Agent's skill stack (which reads project rules) enforces per-module at execution time. This AC is non-codeable; verification is: the activation commit contains exactly the project-rules file + patterns/conventions update + (optionally) vvwt-benchmark/README.md carve-out note. No changes under `vvwt-worker-lib/`, `vvwt-dispatcher/`, `vvwt-standalone-worker/` are introduced by this story.

## Notes

The symlink-vs-copy choice is a Delivery decision: symlink preserves updates from the framework core, copy insulates the project from upstream drift. Either satisfies AC1 if loading works; document the choice.

The `patterns/conventions.md` Testing section is deliberately short — it is a pointer, not a restatement. Delivery Agents already read DEC-22 via the skill cross-reference step; the Testing section exists for fast context recall during implementation, not as an alternative source of truth.
