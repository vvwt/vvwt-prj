# Story E48S03: Tournament-Status-Transitions Service + Controller + UI (DRAFT→PLANNED→ACTIVE→COMPLETED, ACTIVE/PLANNED→CANCELLED)

## User Story

**As a** Tournament Organizer,
**I want** explicit buttons to advance my tournament's status (PLANNED machen, Aktivieren, Abschließen) and to cancel it, with confirmation prompts for irreversible actions,
**so that** I can drive my tournament's lifecycle from setup through to a clean end-state without auto-advances I didn't intend.

---

## Context

Per Brief D-2 / D-4 / D-8 / D-9 + O-2: `Tournament.java`-Lifecycle (DRAFT/PLANNED/ACTIVE/COMPLETED/CANCELLED) ist im Javadoc dokumentiert, aber im Code wird `tournament.setStatus(...)` nur einmal aufgerufen (`DefaultTournamentService.java:233` setzt "DRAFT" bei Anlegen). Es gibt keinen UI-Button und keinen Service, der den Status weiterschaltet. Diese Story liefert: `DefaultTournamentLifecycleService` mit den 4 Transition-Methoden, REST-Controller `TournamentLifecycleController` in `de.vvwt.tm.web` (DEC-40), entsprechende UI-Buttons in `Tournaments.svelte` mit Status-bedingter Sichtbarkeit (D-9: Cancel only PLANNED+ACTIVE), Confirmation-Dialogs für Cancel und COMPLETED (D-8). Per-tournament DB row-lock (DEC-37 Clause B / C-13) für jede Schreib-Operation. Match-Cancel-Lockdown bei `cancel(...)` ist NICHT in dieser Story enthalten — siehe E48S04.

## Acceptance Criteria

- [ ] **AC-TEST-LIFECYCLE-MARK-PLANNED-RED** (testing): RED-first IT-Test asserts `markPlanned(tournamentId)` setzt `tournament.status` von DRAFT auf PLANNED; wirft `IllegalStateException` wenn Status nicht DRAFT. Test ist RED vor jeder Service-Implementation.
- [ ] **AC-TEST-LIFECYCLE-ACTIVATE-RED** (testing): RED-first IT-Test: `activate(tournamentId)` setzt PLANNED → ACTIVE; wirft Exception wenn Status nicht PLANNED.
- [ ] **AC-TEST-LIFECYCLE-COMPLETE-RED** (testing): RED-first IT-Test: `complete(tournamentId)` setzt ACTIVE → COMPLETED; wirft Exception wenn Status nicht ACTIVE.
- [ ] **AC-TEST-LIFECYCLE-CANCEL-RED** (testing): RED-first IT-Test: `cancel(tournamentId)` setzt PLANNED→CANCELLED ODER ACTIVE→CANCELLED; wirft Exception wenn Status DRAFT/COMPLETED/CANCELLED.
- [ ] **AC-IMPL-LIFECYCLE-SERVICE**: `DefaultTournamentLifecycleService` in `de.vvwt.tm.tournament.internal` per DEC-35 (interface `TournamentLifecycleService` im public package); Methoden `markPlanned/activate/complete/cancel(UUID tournamentId)`; jede Methode akquiriert per-tournament row-lock via `TournamentRepository.findByIdForUpdate(tournamentId)` als ersten Read (DEC-37 Clause B / C-13).
- [ ] **AC-TEST-LIFECYCLE-LOCK-RED** (testing): RED-first concurrency IT-Test (CascadeLockIT-Pattern, E31S03 Referenz): zwei parallele Threads rufen `activate(tournamentId)` für dasselbe Tournament; nach beiden Calls hat das Tournament Status ACTIVE und genau eine Transition wurde durchgeführt (zweite throwt `IllegalStateException` weil Status bereits ACTIVE). DEC-37 Clause B verification.
- [ ] **AC-IMPL-LIFECYCLE-CONTROLLER**: `TournamentLifecycleController` in `de.vvwt.tm.web` per DEC-40; REST-Endpoints `POST /api/tournaments/:id/mark-planned`, `POST /api/tournaments/:id/activate`, `POST /api/tournaments/:id/complete`, `POST /api/tournaments/:id/cancel`; jede returns aktualisierten Tournament-DTO mit neuem Status.
- [ ] **AC-TEST-CONTROLLER-IT-PER-METHOD-GREEN** (testing): pro Endpoint mindestens 1 happy-path IT (`@SpringBootTest(RANDOM_PORT)`, DEC-44) + 1 security-negative IT (anonymous request → 401/403); DB-side Verification via assertj-db (DEC-26 Rule 2 controller-analogon).
- [ ] **AC-FRONTEND-LIFECYCLE-BUTTONS** (i18n + url-routing): `Tournaments.svelte` zeigt status-konditionale Buttons in der Action-Spalte:
  - DRAFT: "Phasenplan-Apply machen" (existing, no change), "PLANNED machen" (NEU)
  - PLANNED: "Aktivieren" (NEU), "Abbrechen" (NEU, mit Confirmation)
  - ACTIVE: "Abschließen" (NEU, mit Confirmation), "Abbrechen" (NEU, mit Confirmation)
  - COMPLETED: keine Lifecycle-Buttons (read-only)
  - CANCELLED: keine Lifecycle-Buttons (read-only)
  - Alle Button-Labels via i18n-Keys (`tournaments.lifecycle.markPlannedButton`, etc.).
- [ ] **AC-FRONTEND-CONFIRMATION-DIALOG** (i18n): Cancel-Button und COMPLETED-Button öffnen Confirmation-Dialog ("Wirklich abbrechen? Dies kann nicht rückgängig gemacht werden." / "Turnier endgültig abschließen?") via i18n-Keys; Dialog-Komponente kann existing oder neu (Story-Decision); Cancel/Bestätigen-Buttons.
- [ ] **AC-FRONTEND-VISIBILITY-RULES** (security): Cancel-Button NUR sichtbar in Status PLANNED + ACTIVE (D-9 / Brief); UI-Tests verifizieren.
- [ ] **AC-ERROR-HANDLING-INVALID-TRANSITION** (error-handling): Backend Exception bei Invalid-Transition (z.B. complete bei DRAFT) returnt HTTP 409 (Conflict) mit operator-actionable Message; Frontend zeigt Error-Banner via i18n.
- [ ] **AC-SECURITY-LIFECYCLE-AUTH** (security): alle 4 Lifecycle-Endpoints erfordern authenticated Admin per existierendem `SecurityConfig`; `.with(csrf())` für POST per DEC-26 controller-pattern (existing project convention); ITs verifizieren.
- [ ] **AC-GOVERNANCE-NO-DEC-AMENDMENT** (governance): keine DEC neu/geändert in dieser Story — DEC-37 Clause B + DEC-40 + DEC-22 werden konsumiert. C-13 Constraint-Anwendung ist Brief-derived, kein DEC-Schreibrecht für Discovery.
- [ ] **AC-NO-MATCH-CANCEL-IN-THIS-STORY** (governance): die `cancel(tournamentId)` Service-Methode in dieser Story ändert NUR `tournament.status`; Match-Bulk-CANCELED-Marking ist E48S04. Story-AC verbietet expliziten Match-Bulk-Update in dieser Story (klare Trennung).
