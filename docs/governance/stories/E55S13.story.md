# Story E55S13 (Bug-Triage): Tournament Manager `audit_log` File-Isolation — replace H2-backed `DefaultAuditLogRepository` with file-based `FileAuditLogRepository` (per-tournament JSONL append-only, async-after-commit) — belt-and-suspenders defense against H2 MVStore-class data-loss for the most-expensive-to-lose data dimension

## User Story

**As a** Tournament Manager operator,
**I want** the `audit_log` correction history persisted in plain-text JSONL files outside the H2 database, with one file per tournament, written asynchronously after the originating Spring transaction commits,
**so that** future H2 MVStore-class data-loss incidents (M-2/M-3/M-5/Display-token-loss bug class) cannot affect the audit trail (which represents correction history per DEC-14 §requirement (a) and is the most expensive data to lose silently); per-tournament physical separation also bounds the blast radius if a single audit file is ever corrupted.

---

## Context

### Discovery cycle-8 — file-isolation belt-and-suspenders defense

E55S11 audit (Stair-1 PASS) + E55S12 empirical Stair-0b verification under H2 2.4.240 established that the H2 MVStore-class data-loss bug-class is empirically eliminated by the 2.4.240 upgrade. E55S12 itself was escalated by Delivery as `failed` because the DEC-22 RED-first deterministic-IT could not be made to reproduce the Heisenbug under 2.3.232 in a single-JVM @SpringBootTest harness.

Discovery cycle-8 (2026-05-14) pivots from "find a deeper test" to "structurally protect the most-expensive-to-lose data dimension". The `audit_log` table is the natural carve-out target because (a) DEC-14 §requirement (a) names correction-traceability as its single-most-important durability obligation, (b) audit_log has no production read consumer outside tests (greppable claim: zero `auditLogRepository.find*` calls outside `AuditLogRepositoryIT`), (c) the JSONL append-only file pattern is naturally aligned with the append-only API invariant the codebase already enforces (`AuditLogRepository.deleteById` throws `UnsupportedOperationException`).

### Approach-Evaluation summary

Full evaluation at `.gaai/project/contexts/artefacts/evaluations/2026-05-14-tm-audit-log-file-isolation.approach-evaluation.md`. Three viable approaches compared against C1..C13 criteria:

- **Approach A — Plain JSONL append-only file** (`java.nio.channels.FileChannel + Jackson`, no new deps)
- Approach B — Logback `SiftingAppender` + JSON encoder — excluded (write-side framework, off-axis for per-tournament + lifecycle + read-back)
- Approach C — Chronicle Queue — excluded (overkill at TM scale ≤ 1.22 writes/sec, Windows hot-backup asymmetric, binary archive longevity risk, operator-tooling friction vs DEC-15 onboarding audience)

A vs C deep-dive: A wins or is equivalent on 10 of 11 evaluated dimensions (file-handle lifecycle, tournament-close, hot-backup-Windows, cold-archive longevity, process-kill recovery, FS-corruption recovery, random-access read, disk-after-archive, operator-forensic). C wins only on uncompressed disk density (unused at TM scale).

### Discovery Session Brief — human-validated

Brief was human-validated 2026-05-14 after cycle-2 of Review Sub-Agent Tier-2 (loop-limit reached; all findings resolved with user direction on F-A schema-drop posture). Key directional items:

- **D-2** Plain JSONL approach chosen
- **D-3** Per-tournament separation target
- **D-7** Lazy-open + JVM-shutdown lifecycle (NO seal ceremony, NO event-listener, NO `.closed` marker)
- **D-9** `TransactionSynchronization.afterCommit()` hook + asynchronous writer thread; rollback skips audit
- **D-10** per-write `force(true)` fsync (in writer thread, off request path)
- **D-11** File layout `<data-dir>/tenants/<tenant>/audit-log/<tournament-id>/audit.jsonl`
- **D-12** Cascade-delete-helper SQL for audit_log is REMOVED (no replacement); per-tournament audit-log directory becomes orphan after tournament-delete/reset (operator-driven cleanup acceptable)
- **C-12** Pre-rollout cleanup — operator deletes currently-deployed H2 file (per DEC-25 §no-production-data condition); no backfill of historical audit rows
- **T-9** D-9 `@AfterCommit` mechanism is structurally distinct from Epic-E55 silent-rollback bug-class — audit-append performs FILE IO only, opens NO inner Spring transaction, no inner DB-TX exists that could silent-fail

### Error-handling (mandatory category — Epic E55 declares)

- [ ] **AC-ERROR-HANDLING-WRITER-QUEUE-OVERFLOW**: Writer-thread bounded queue (capacity 1024). On `offer(...)` returning false (queue full): WARN log entry with format `[audit-log] queue-full tournament={} match={} setIndex={} — audit row DROPPED`. Audit-append is dropped (LOST entry, per Brief T-3 accepted failure mode). The `afterCommit` caller does NOT block (no `put(...)`, only `offer(...)`).

- [ ] **AC-ERROR-HANDLING-WRITER-IO-FAILURE**: Writer thread wraps `FileChannel.write` + `FileChannel.force` in `try/catch (IOException)`. On exception: WARN log entry with format `[audit-log] write-failed tournament={} match={} setIndex={} cause={}`. Writer thread continues running (does not terminate); subsequent appends for other rows are still attempted. Bug-class-T-9-guard: caught exception does NOT trigger any Spring transaction state.

- [ ] **AC-ERROR-HANDLING-JVM-SHUTDOWN-FLUSH**: `@PreDestroy` hook awaits up to 30 seconds for writer-thread queue drain. If timeout: WARN log entry `[audit-log] shutdown-timeout queue-depth={}`, `executor.shutdownNow()` invoked, remaining queue items LOST (acceptable per Brief T-3 failure-mode acknowledgment).

- [ ] **AC-ERROR-HANDLING-NULL-TOURNAMENTID-FAILS-FAST**: `Objects.requireNonNull(tournamentId, "tournamentId")` fires in BOTH (a) the all-args constructor (production-path: all 3 callers per O-2 use all-args) AND (b) the `setTournamentId(UUID)` setter (covers Spring Data JDBC reflective mutation path historically used by ROW_MAPPER — even though the legacy ROW_MAPPER is deleted at cutover, retaining the setter NPE guard is defensive). The no-arg constructor remains valid (existing `AuditLogEntryTest` calls it) but produces an entity with `tournamentId == null`; any subsequent `save(...)` MUST traverse a path that has set `tournamentId` to non-null (via `setTournamentId` which itself fails on null), so a null tournamentId cannot reach the file-write code. Tests of the no-arg-then-setter path verify the NPE-on-null-setter behavior — fail-fast, no defensive fallback (per Brief D-6 + Q-4 explicit > hidden).
