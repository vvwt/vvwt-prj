# Story E49S06 (Bug-Triage): Fix — admin Devices view "Zuweisen" inline assignment throws `TypeError: …trim is not a function`; the field-number input value is a number but is handled as a string

## User Story

**As a** tournament operator using the admin Device Management view (Geräteverwaltung),
**I want** the "Zuweisen" button in a device row to actually assign a scoring tablet (or display device) to a court field when I have entered the PIN and the field number,
**so that** I can bind a registered tablet to its court — the core E49 workflow — instead of clicking a button that silently does nothing.

---

## Context

The operator reported: in Geräteverwaltung, the PIN is now displayed on the physical scoring
tablet, but clicking "Zuweisen" in the device row after entering the PIN and the field number
produces **no reaction**. The browser console shows:

```
Uncaught (in promise) TypeError: K(...)[e.id]?.trim is not a function
    at ce (index-<hash>.js)
    at HTMLButtonElement.<anonymous> (index-<hash>.js)
```

The console error is the cause of the unresponsive button — not an unrelated symptom.

**Surface.** The inline-row assignment lives in
`vvwt-tm-web/src/main/ui/src/routes/Devices.svelte` (admin SPA, the E49S01 rewrite). Each
unassigned `SCORING_TABLET` row renders a PIN text input + a field-number `<input type="number">`
+ a "Zuweisen" button; each unassigned `DISPLAY` row renders the same field-number input + button
(no PIN input). Both buttons call the shared async handler `handleRowAssign(device)`.

**Why it surfaces now.** The inline-assign flow requires the operator to type the PIN displayed
on the physical tablet. The tablet only began actually displaying that PIN after **E49S03**
(`done` 2026-05-15) fixed a separate visibility defect on the tablet registration screen. Before
E49S03 the operator could not complete the flow far enough to reach `handleRowAssign`. With the
PIN now visible, operators reach the "type PIN + field + Zuweisen" step and hit a crash that has
been latent in the code since E49S01.

**Blast radius.** The defect lives in the shared `handleRowAssign` path, so it breaks the
"Zuweisen" action for **both** `SCORING_TABLET` and `DISPLAY` device rows — i.e. the entire
inline field-assignment workflow. The operator reported scoring tablets; the display-device row
is broken by the identical mechanism and is in scope for this fix (see Out of Scope for why
excluding it would be artificial). Severity is HIGH: this fully blocks the E49 success metric
("a scorekeeper holding a physical tablet can be assigned to a court in three keystrokes").

---

## Root Cause Analysis

- **Root cause.** The inline field-number input is
  `<input type="number" … bind:value={rowFieldInputs[device.id]}>`. Svelte's two-way binding
  (`bind:value`) on a **numeric** input coerces the bound value to the `number` type (or to
  `null`/`undefined` when the input is empty) — documented Svelte binding behaviour for
  `type="number"` inputs. Consequently `rowFieldInputs[device.id]` holds a `number` at runtime,
  even though `rowFieldInputs` is declared `Record<string, string>`.
- **The crash.** `handleRowAssign(device)` reads the field value as
  `const fieldStr = rowFieldInputs[device.id]?.trim() ?? '';` — calling the `String` method
  `.trim()` on what is actually a `number`. A `number` has no `.trim`; `(aNumber).trim` is
  `undefined`; invoking `undefined()` throws `TypeError: …trim is not a function`. The thrown
  error rejects the async `handleRowAssign` promise (surfaced as `Uncaught (in promise)`); the
  click handler aborts before `assignDevice` is ever called, so the "Zuweisen" button appears
  unresponsive.
- **Triggered by entering a value.** The crash requires the field input to actually hold a
  value: with a value present the binding yields a `number` and `.trim()` throws. An empty
  numeric input is expected to bind to a non-string nullish value on which `?.` short-circuits —
  falling through to the `parseInt('') → NaN` validation-error branch rather than crashing — but
  the exact empty-input behaviour is not load-bearing for this story: `AC-FIX-NO-CRASH` requires
  correctness across all three cases (value present, empty, non-numeric) independently. The
  reported scenario ("Pin und Feld eingetragen" — PIN and field entered) is the value-present
  case.
- **Why TypeScript did not catch it.** `rowFieldInputs` is typed `Record<string, string>`, so
  `?.trim()` type-checks against the declared `string` element type. The declared type and the
  runtime type produced by the numeric-input binding diverge; the type annotation masked the
  defect rather than preventing it.
- **PIN line is unaffected.** The PIN input on the same row is `<input type="text">`, so
  `rowPinInputs[device.id]` is a genuine `string` and the adjacent `rowPinInputs[device.id]?.trim()`
  call is safe. Only the field-number line is defective. For `DISPLAY` rows there is no PIN input
  at all, so `rowPinInputs[device.id]` is `undefined` and `?.` short-circuits harmlessly — the
  `DISPLAY` crash is likewise the field-number line.
- **Provenance.** The `rowFieldInputs` declaration, both `type="number"` field inputs, and the
  `handleRowAssign` `.trim()` call were all introduced together by commit `6d99b23`
  (E49S01, 2026-05-08), confirmed via `git blame`. The defect has existed since the inline-row
  assignment feature shipped — it is **not** a regression of a previously-working state and there
  is no earlier commit to revert to. The fix is a forward fix.

Discovery defines WHAT (clicking "Zuweisen" with a valid PIN and field number assigns the device;
invalid input yields an inline error; no uncaught exception on any input). Delivery picks HOW —
e.g. consuming the field value with the type the numeric input actually yields, correcting the
`rowFieldInputs` element type, changing the input control, or defensively normalizing the value.
This story does not prescribe the mechanism.

## Acceptance Criteria

### Reproduction

- [ ] **AC-REPRO**: Given the admin Devices view with at least one registered `SCORING_TABLET`
  in status `REGISTERED`, when a PIN and a field number are entered in that device's inline row
  and "Zuweisen" is clicked, then on the pre-fix code a `TypeError` whose message matches
  `…trim is not a function` is raised as an uncaught promise rejection, `assignDevice` is never
  invoked, and the device is not assigned. The impl-report records this confirmed pre-fix state.

### Fix

- [ ] **AC-FIX-SCORING-ASSIGN**: After the fix, given a registered `SCORING_TABLET` in status
  `REGISTERED`, when the operator enters the PIN displayed on the physical tablet and a valid
  field number (an integer ≥ 1) in the inline row and clicks "Zuweisen" (or presses Enter in the
  field input), then the device is assigned to that field via the assign endpoint, no exception
  is thrown, and on success the row no longer offers the inline assign controls and reflects the
  assigned state.
- [ ] **AC-FIX-DISPLAY-ASSIGN**: After the fix, given a `DISPLAY` device in status `REGISTERED`,
  when the operator enters a valid field number in its inline row and clicks "Zuweisen", then the
  device is assigned and the shared inline-assign action no longer throws. The shared action
  continues to tolerate the absence of a PIN input on `DISPLAY` rows exactly as before.
- [ ] **AC-FIX-NO-CRASH**: After the fix, the inline-assign action completes without any uncaught
  `TypeError` or unhandled promise rejection, regardless of whether the field input holds a
  numeric value, is empty, or holds non-numeric content. The field-number value produced by the
  inline `<input>` is consumed consistently with the type that input actually yields.
- [ ] **AC-FIX-ASSIGN-CONTRACT-PRESERVED**: The fix preserves the E49S01 assign contract — for a
  `SCORING_TABLET` the PIN typed in the row is sent to the assign endpoint as the
  proof-of-possession credential; for a `DISPLAY` device no PIN is sent. The fix changes neither
  the `assignDevice` request shape nor the PIN input control or its masking.

### Error-handling

- [ ] **AC-ERROR-INVALID-FIELD**: When the field input is empty or does not yield a usable field
  number ≥ 1, the inline row displays the existing localized validation error
  (`devices.assignError`) and no assign request is sent — without throwing an exception.
- [ ] **AC-ERROR-ASSIGN-FAILURE-MESSAGES**: The existing mapping of assign-endpoint failure
  responses to localized inline row messages is preserved and still reached — HTTP 403 →
  `devices.scoringTablet.pinMismatch`, 423 → `devices.scoringTablet.pinLocked`, 422 →
  `devices.scoringTablet.pinMissing`, other failures → `devices.assignError` — so a failed assign
  shows an actionable inline message rather than an uncaught error.
- [ ] **AC-ERROR-FIELD-CONFLICT-PRESERVED**: The field-conflict confirmation path (assigning to a
  field already occupied by another device → confirmation dialog → confirm → unassign the
  occupant → assign) continues to function and likewise completes without throwing.

### Testing

- [ ] **AC-TEST-REGRESSION-RED-FIRST**: A regression test exists that exercises the inline-row
  "Zuweisen" assign action with a field number entered. It is RED on the pre-fix code (it
  reproduces the `TypeError` / the failure to invoke the assign action) and GREEN after the fix
  (DEC-22 — the RED-first regression-guard obligation of a bug fix). The test exercises the
  assign action's actual handling of the field-input value — not a static source-text match. The
  harness form (component-render test, assign-action unit test, or equivalent) is a Delivery
  decision; co-located vitest alongside `Devices.svelte` (`Devices.test.ts`) is the existing
  pattern for this SPA.
- [ ] **AC-TEST-SUITE-GREEN**: After the fix, the full existing `vvwt-tm-web` admin-SPA test
  suite (the `src/main/ui` Vite root) passes, with no test disabled, skipped, `@skip`-ed, or
  weakened to achieve green.

### Build

- [ ] **AC-BUILD-MVN-VERIFY**: `mvn verify` invoked from the `vvwt-prj` root exits zero (BUILD
  SUCCESS) — the DEC-54 closure gate; the `vvwt-tm-web` frontend build and frontend tests run
  within it via the `frontend-maven-plugin` binding. This is the closure criterion.

### Security

- [ ] **AC-SECURITY-NO-NEW-SURFACE**: The fix introduces no new authentication, authorization, or
  network surface and makes no change to the `/api/devices/{id}/assign` endpoint or its
  request/response contract. The PIN continues to appear only in the assign request body for a
  `SCORING_TABLET`; it is not logged, echoed into the DOM, or persisted client-side.

### i18n

- [ ] **AC-I18N-NO-KEY-CHANGE**: The fix adds, removes, or renames no localization key. The
  inline-assign UI continues to use the existing keys (`devices.assignButton`,
  `devices.assignFieldPlaceholder`, `devices.assignFieldLabel`, `devices.assignError`,
  `devices.scoringTablet.*`), and every operator-facing string in the assign flow remains
  rendered through the i18n layer.

### Governance

- [ ] **AC-GOV-SCOPE-LOCKED**: The fix stays within the diagnosed scope — the inline-row
  field-assignment value handling in `Devices.svelte` (and, if needed, the `rowFieldInputs` type
  declaration). No unrelated refactor; no change to the other Devices view features (QR, clear
  all, rename, configure display device, remove, unassign, PIN-lock reset); no backend change; no
  DEC amendment.
- [ ] **AC-GOV-COMMIT-FORMAT**: Implementation commits use the project's conventional-commit
  story format scoped to `E49S06` (e.g. `fix(E49S06): …`) and name the bug being fixed. The fix
  lands as a single atomic commit.
- [ ] **AC-GOV-PROPAGATE**: At story close, governance artefacts are propagated per DEC-31.

## Out of Scope

- The `DISPLAY`-device row is **in** scope — it is broken by the identical mechanism in the
  shared `handleRowAssign` path. Excluding it would leave a known crash in place and split one
  root cause across two stories.
- Any redesign of the inline-assign UX (separate assign modal, keyboard flow, batch assignment,
  field-picker control). This story restores the existing E49S01 behaviour; it does not redesign it.
- The tablet-side registration / scoring screens (`score/register.mustache`, `score/field.mustache`,
  `vvwt-tablet.js`) — the DEC-19 tablet UI carve-out. The defect is entirely in the admin Svelte
  SPA; the tablet screens are untouched.
- The backend `DeviceController` / `DefaultDeviceService` / `/api/devices/{id}/assign` endpoint —
  the endpoint already receives `fieldNumber` as a parsed number and is not implicated.
- The PIN-display defects already fixed by E49S02 and E49S03, and the registration-URL defect
  fixed by E49S04 — all `done`.
- A broader audit of other `bind:value` numeric-input / declared-type mismatches elsewhere in the
  SPA. If Delivery notices adjacent instances it should report them, but fixing them is a
  separate hygiene initiative, not this story.

  shared `handleRowAssign` path. Fix risk is LOW — a small, localized frontend change in one

  (the fix must not disturb those surfaces).

  "Zuweisen" assigns the device, invalid input yields an inline error, nothing throws — and
  Delivery selects the mechanism under DEC-22 (RED-first).
