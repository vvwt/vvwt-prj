# Story E37S09: result package — SubmitResult* with algorithm field + JobStatusController + LateResult + ResultAudit* (Q-1a TDD RED-first against spec)

## User Story

**As a** worker submitting a signed packet result OR a Tournament Manager polling for job status,
**I want** to POST a signed result with an explicit `algorithm` field that the dispatcher uses to look up the verifier (per D-6 algorithm-agility) AND to GET aggregated job status / cache-resolved results,
**so that** the first-valid-result-wins mechanic per DEC-6 works algorithm-agnostically AND late results are logged-not-discarded for forensics.

---

## Context

The result package owns: SubmitResultController (HTTP `POST /api/submit-result`), SubmitResultService, SubmitResultRequest/Response DTOs (request carries `algorithm` field), JobStatusController + JobStatusResponse, LateResult entity + repository, ResultAuditEntry + ResultAuditRepository + ResultAuditService.

Per Brief C-18: first-valid-result-wins (DEC-6 mechanic) is algorithm-agnostic — first valid signed result wins regardless of which algorithm a worker uses. Per Brief C-17: algorithm choice is purely about result-authenticity.

This story is authored against E37S02 spec sections (a) shared, (b) dispatcher contract submit-result + job-status + late-result + result-audit, (d) algorithm field on submit-result. No legacy inspection.

### Story-specific ACs

- [ ] **AC-SUBMIT-RESULT-DTOs**: `SubmitResultRequest(UUID packetId, UUID workerId, String algorithm, byte[] signature, String resultPayloadJson)` (record). `SubmitResultResponse(boolean accepted, String reason)` for accepted-or-superseded distinction. `algorithm` field is REQUIRED (not Optional — D-2 backward-compat applies only to pull-packet supportedAlgorithms[], NOT to submit-result algorithm).
- [ ] **AC-SUBMIT-RESULT-SERVICE**: `de.vvwt.slotopt.dispatcher.result.SubmitResultService` interface + `DefaultSubmitResultService` impl. Method `SubmitResultResponse submit(SubmitResultRequest request)`. Behavior: (1) lookup `KeyRegistration.findByWorkerId(workerId)` — unknown → 401; (2) verify `algorithm` matches the registered algorithm — mismatch → 400 with explicit error; (3) lookup `SignatureVerifierRegistry.lookup(algorithm)` — unknown algorithm at runtime → 500 (server-misconfig); (4) canonicalize resultPayloadJson via JcsCanonicalizer; (5) verify signature via verifier; signature-invalid → 401; (6) check packet status via PacketRepository — first-valid wins per DEC-6: if status=RESULT_RECEIVED, persist a LateResult entry, return `accepted=false, reason="superseded"`; if status=CLAIMED, mark RESULT_RECEIVED + persist canonical result + ResultAuditEntry. Algorithm-agnostic per Brief C-18.
- [ ] **AC-SUBMIT-RESULT-CONTROLLER**: `de.vvwt.slotopt.dispatcher.result.SubmitResultController` `@PostMapping("/api/submit-result")`. JSON request → JSON response. HTTP codes per spec.
- [ ] **AC-LATE-RESULT-ENTITY**: `de.vvwt.slotopt.dispatcher.result.LateResult` Spring Data JDBC POJO with fields: `Long id`, `UUID packetId`, `UUID workerId`, `String algorithm`, `byte[] signature`, `String resultPayloadJson`, `Instant receivedAt`. Per DEC-6 first-valid-wins: late results logged, not discarded.
- [ ] **AC-LATE-RESULT-REPOSITORY**: `de.vvwt.slotopt.dispatcher.result.LateResultRepository extends CrudRepository<LateResult, Long>`.
- [ ] **AC-RESULT-AUDIT**: `de.vvwt.slotopt.dispatcher.result.ResultAuditEntry` entity (`Long id`, `UUID packetId`, `UUID workerId`, `String algorithm`, `String sourceIp`, `Instant receivedAt`, `String outcome` — `ACCEPTED`/`SUPERSEDED`/`SIGNATURE_INVALID`). `ResultAuditRepository`. `ResultAuditService` interface + Default impl per DEC-35.
- [ ] **AC-JOB-STATUS-CONTROLLER**: `de.vvwt.slotopt.dispatcher.result.JobStatusController` `@GetMapping("/api/job-status/{jobId}")` returns `JobStatusResponse(UUID jobId, String status, int totalPackets, int completedPackets, ...)` per spec.
- [ ] **AC-ALGORITHM-MISMATCH-REJECTED**: Test scenario — register worker with `algorithm="Ed25519"`; submit-result with `algorithm="ML-DSA-65"` for the same workerId → HTTP 400 with explicit "registered algorithm Ed25519 does not match submitted ML-DSA-65" error message. Prevents downgrade/upgrade attacks at submission time.
- [ ] **AC-FIRST-VALID-WINS**: Test scenario — concurrent submit-result calls for same packetId from two workers (both signature-valid): exactly one returns `accepted=true`, the other returns `accepted=false, reason="superseded"`; the superseded one persists as a LateResult entry; both produce ResultAuditEntry rows with appropriate `outcome` values.
- [ ] **AC-DEC26-COMPLIANT-DAO-ITs**: `LateResultRepositoryIT`, `ResultAuditRepositoryIT` follow DEC-26 three-rule pattern **applied analogously to vvwt-slotopt-dispatcher** (DEC-26 §Decision is textually scoped to vvwt-tm-web; the principle generalizes and is adopted here by analogy without invoking a DEC-26 scope-extension amendment).
- [ ] **AC-MOCKMVC-CONTROLLER-TESTS**: SliceTest for SubmitResultController + JobStatusController.

## Notes

- **DEC-6 first-valid-wins**: This is the canonical implementation site for DEC-6's first-valid-result-wins mechanic. Algorithm-agnostic per Brief C-18 — wins logic does not consider algorithm.
- **Algorithm-mismatch attack surface**: AC-ALGORITHM-MISMATCH-REJECTED defends against an attacker who tries to submit a result claiming a different algorithm than registered. The check is simple: registered algorithm must equal submitted algorithm. Future MaximumAlgorithmPolicy (Phase-4) adds further restrictions.
- **Cache integration**: writes flow through here; reads happen in E37S10. Coordination is via PacketRecord status + accepted-result persistence.
