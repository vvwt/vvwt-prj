# Story: Fix `build-image.sh` non-dry-run path so a single operator command produces a flashable FullPageOS image

## User Story

**As a** tournament operator,
**I want** `./build-image.sh --server-url=…` (with the documented prerequisites
installed) to clone FullPageOS 0.14.0, apply the vvwt-display overlay at the
correct CustomPiOS source-tree paths, and run the upstream `build_dist` to
completion,
**so that** preparing a venue display Pi remains the single-command workflow
that Epic E69 promises — without having to hand-execute the FullPageOS build
procedure step by step.

---

## Context

E69S01 (PR #357, merged 2026-05-25) shipped `build-image.sh` as the
single-command FullPageOS overlay wrapper. E69S02 (PR #358, merged 2026-05-25)
shipped the operator runbook describing the workflow. The bats test surface
authored for E69S01 covered the `--help`, tag-pin, and `--dry-run` paths
exhaustively (per E69S01 AC4 a–e). It did **not** cover the non-dry-run path
(lines 218–242 of `build-image.sh`), because a full FullPageOS image build is
not practical to run in CI (Docker + qemu + sudo + loop device + 20–60 minutes
of wall time, plus eventual Pi-side verification). E69S01's Brief F-6/F-7
resolution accepted this gap with the implicit assumption that the non-dry-run
path would be operator-attested at the first real image build.

The first real image build (2026-05-27, this story's reproduction trigger)
failed at the cp step — `cp: target '…/src/image/boot/': not found`. Empirical
investigation against FullPageOS 0.14.0 (
<https://github.com/guysoft/FullPageOS/tree/0.14.0>) and CustomPiOS master HEAD
identified **seven distinct defects** in the non-dry-run path, every one
statically verifiable against upstream files (no on-Pi observation required for
the diagnosis itself). The Discovery Session Brief
(`discovery-2026-05-27-pi-display-build-image-orchestrator-fix`, two Tier-2
review cycles, loop-limit reached → human-validated 2026-05-27) selected the
**Full-Build-Orchestrator** scope: fix every defect under one story so the
single-command workflow Epic E69 promises is restored, with operator-attestation
of the Docker-build phase the verification surface (per the E69S02 W-1/W-2/W-3
precedent).

The fix preserves `build-image.sh`'s **Wrapper identity** per E69S01's Brief —
the script clones FullPageOS and CustomPiOS, applies the overlay at the paths
the upstream `build_dist` actually expects, and delegates the chroot build to
`sudo bash -x src/build_dist`. No FullPageOS internals are forked, re-
implemented, or vendored.

This story is `track: bug-triage` per the Bug-Triage Flow in
`.gaai/core/agents/discovery.agent.md` — root cause is empirically established
and the fix is a script-level retrofit, not a feature expansion.

---

## Root Cause Analysis

Seven defects in the non-dry-run path (`build-image.sh:218-242`), all
empirically verified against FullPageOS 0.14.0 + CustomPiOS upstream:

1. **Wrong cp target directory** (`build-image.sh:232`).
   The script copies the overlay into `${WORK_DIR}/FullPageOS/src/image/boot/`,
   which does not exist in 0.14.0 — `src/image/` contains only a README ("Place
   zipped Raspbian image here"). CustomPiOS convention places module overlays
   at `src/modules/<module>/filesystem/boot/`; the FullPageOS module is
   `fullpageos`, so the correct target is
   `src/modules/fullpageos/filesystem/boot/`, which exists upstream and already
   contains `fullpageos.txt`, `fullpagedashboard.txt`, `splash.png`.

2. **Wrong build entrypoint** (`build-image.sh:238`).
   The script invokes `./build` at the FullPageOS clone root. No such file
   exists there in 0.14.0. The canonical invocation per FullPageOS README and
   `src/build_dist` is `cd src && sudo bash -x ./build_dist`.

3. **Missing CustomPiOS sibling clone**.
   FullPageOS's `build_dist` resolves `${CUSTOM_PI_OS_PATH}` from a file
   `src/custompios_path`, which CustomPiOS's `update-custompios-paths` writes
   when both repositories are checked out as siblings. The script clones only
   FullPageOS; without CustomPiOS as a sibling, `build_dist` cannot resolve
   `${CUSTOM_PI_OS_PATH}` and `source ${DIR}/custompios_path` fails.

4. **Missing `update-custompios-paths` step**.
   Even with both repositories cloned, the CustomPiOS-paths symlink patch
   (`../../CustomPiOS/src/update-custompios-paths`) must be invoked before
   `build_dist` to write `src/custompios_path`. The script does not invoke it.

5. **Missing Raspbian base-image download**.
   FullPageOS's `BASE_IMAGE_PATH=${DIST_PATH}/image` (CustomPiOS
   `src/modules/base/config:11`), and the build expects a Raspbian/Raspios `.zip`
   already present at that path before `build_dist` runs. The FullPageOS README
   prescribes `wget -c --trust-server-names
   'https://downloads.raspberrypi.org/raspios_lite_armhf_latest'` into
   `src/image/`. The script does not perform this download.

6. **Wrong output-path string**.
   `build-image.sh:241` reports the produced image at
   `${WORK_DIR}/FullPageOS/workspace/images/*.img`. CustomPiOS convention is
   `BASE_WORKSPACE=${DIST_PATH}/workspace` (`src/modules/base/config:48`) where
   `DIST_PATH` is the FullPageOS `src/` directory (`src/build_dist:3`). The
   actual output is therefore under `${WORK_DIR}/FullPageOS/src/workspace/`,
   not `${WORK_DIR}/FullPageOS/workspace/`. The README's "build/ subdirectory"
   reference (`pi-display/README.md:63-65`) is also incorrect.

7. **Doubled-firmware overlay path**.
   CustomPiOS `BASE_BOOT_MOUNT_PATH=boot/firmware` (`src/modules/base/config:52`)
   means `start_chroot_script:13` (`unpack /filesystem/boot
   /"${BASE_BOOT_MOUNT_PATH}"`) lays the overlay files down under
   `/boot/firmware/` on the final image. The script's `FIRMWARE_DIR` variable
   (`build-image.sh:188`) currently produces overlay at
   `${OUTPUT_DIR}/boot/firmware/vvwt-display/branding.conf`, which would
   unpack to `/boot/firmware/firmware/vvwt-display/branding.conf` on the
   final image — a doubled-firmware path. The correct overlay layout is
   `${OUTPUT_DIR}/boot/vvwt-display/branding.conf` so that the unpack lands at
   `/boot/firmware/vvwt-display/branding.conf` per the operator intent in the
   inline comment at `build-image.sh:200`. The `fullpageos.txt` placement is
   incidentally correct (`${OUTPUT_DIR}/boot/fullpageos.txt` →
   `/boot/firmware/fullpageos.txt`); the inline comments at lines 10 and 191
   that describe its final path as `/boot/fullpageos.txt` are off-by-one-segment
   and are corrected per AC8.

Cause of the gap reaching `staging`: the existing bats coverage (E69S01 AC4)
exercised only the dry-run path, which `exit 0`s at line 211 before any of
defects 1–7 execute. Defects 1, 2, 7 are statically verifiable against the
upstream source tree; defects 3, 4, 5, 6 are part of the upstream FullPageOS
build contract that the wrapper script did not encode. None required Docker,
qemu, or a Pi to diagnose — only the upstream source.

## Acceptance Criteria

- [ ] **AC1 [testing — reproduction scenario, Given/When/Then]:**
  **Given** a Linux host with the prerequisites listed in AC6 installed
  (Docker or `podman+podman-docker`, `qemu-user-static`, `git`, `wget`,
  `sudo`, ability to `sudo modprobe loop`) and an internet connection,
  **when** the operator runs from `vvwt-prj/pi-display/`:
  `sudo ./build-image.sh --server-url=https://tm.example.test/`,
  **then** the script completes with exit code 0 and a flashable `.img`
  file is present at `${WORK_DIR}/FullPageOS/src/workspace/` (per
  CustomPiOS `BASE_WORKSPACE=${DIST_PATH}/workspace` + FullPageOS
  `DIST_PATH=${FullPageOS}/src`). Against the pre-story script, the same
  invocation fails at the cp step
  (`cp: target '…/src/image/boot/': not found`). The reproduction-vs-fix
  evidence is recorded in the impl-report per AC7.

- [ ] **AC2 [testing — fixture-based bats coverage of corrected overlay-apply
  paths, no Docker invocation]:**
  The bats test suite under `vvwt-prj/pi-display/src/test/sh/` is extended
  with assertions that, against a checked-in mock FullPageOS-source-tree
  fixture under `vvwt-prj/pi-display/src/test/sh/fixtures/`, verify the
  overlay-apply logic places:
  (a) `fullpageos.txt` (containing the `--server-url` value when supplied)
      at the fixture's
      `src/modules/fullpageos/filesystem/boot/fullpageos.txt`;
  (b) `branding.conf` at the fixture's
      `src/modules/fullpageos/filesystem/boot/vvwt-display/branding.conf`
      (NOT under any `firmware/` sub-path — closes RCA #7).
  The fixture is the minimum stand-in for a FullPageOS 0.14.0 clone — only
  the directory structure that the overlay-apply step actually touches.
  Bats tests run within `mvn verify` without invoking `docker`/`podman`,
  without `sudo`, and without a live `git clone`. Each new assertion fails
  against the pre-story script and passes after the fix.

- [ ] **AC3 [error-handling — pre-flight checks extended for new
  FullPageOS-upstream prerequisites]:**
  The non-dry-run pre-flight check (currently at `build-image.sh:142-176`)
  is extended to verify presence of the command-existence-testable
  prerequisites that the FullPageOS 0.14.0 build pipeline now invokes via
  `build_dist`: at minimum `wget` (Raspbian-base-image download) and
  `sudo` (root-mode invocation). Each missing command produces a non-zero
  exit with an actionable English message that names the missing tool and
  points the operator at remediation (e.g.,
  `"sudo apt-get install wget"`). Bats assertions verify each error path.
  Runtime-dependent prerequisites (`modprobe loop` succeeds, CustomPiOS
  clone succeeds against an outage of github.com) are not pre-flight-
  testable and are covered by AC5's operator-attestation surface, not

  `boot/firmware/vvwt-display/branding.conf` per E69S01 AC4(c)) is updated
  to assert the corrected layout (`boot/vvwt-display/branding.conf` — no
  intermediate `firmware/` segment, per RCA #7). The updated assertion

  `sudo ./build-image.sh --server-url=…` per the upstream FullPageOS

  if the operator runs the script without sudo, it fails fast at the

  auto-elevate; this preserves principle-of-least-privilege and the
  operator's audit visibility into elevation." A bats assertion verifies
  the script source contains no `sudo` call against itself or any of
  its overlay-apply steps.

## Out of Scope

- **Full image build inside CI** — the Docker + qemu + sudo + loop + 20–
  60 min build envelope plus Pi-side verification cannot be productively
  expressed in `mvn verify`. Operator-attestation (AC5) is the
  verification surface for the Docker-build phase, per the E69S02 W-1
  through W-3 precedent.
- **`pi-display/README.md` Boot / Flash / Verify procedure content** —
  unchanged. Only the Prerequisites and a new Image-Build Attestation
  block are added (per AC5 + AC6).
- **FullPageOS tag bumps beyond 0.14.0** — separate stories per E69S01
  Brief D-9. Tag bumps each carry their own operator-runbook re-execution.
- **Pi-3 rendering performance, anonymous Pi-side identity,
  `wpa_supplicant.conf` plaintext posture** — Known Limitations per
  E69S02, unchanged.
- **Inline authoring of new systemd drop-ins, container-driver shims,
  or HTML fallback pages** if the operator-attestation later reveals an
  upstream FullPageOS / podman gap — escalated to a new story per the
  E69S01 Brief D-7-b precedent, never authored inside this story or
  this runbook.
- **Restructuring `build-image.sh` into a third "pre-Docker smoke-test"
  execution mode** — the bats fixture-based coverage in AC2 + AC4
  delivers the smoke-test value within the existing dry-run vs
  full-build distinction; a third execution mode is unnecessary
  structural complexity.
- **Server-side changes in `vvwt-tm-web`** — already shipped by Epic E07,
  out of scope of the entire Epic E69.
