# Story E48S24: Atomic tournament-status auto-promote — PLANNED→ACTIVE on first phase.start AND ACTIVE→COMPLETED on last phase.complete (forceComplete excluded; manual endpoints retained additive)

## User Story

**As a** Tournament Organizer,
**I want** the tournament to advance its lifecycle status automatically when I start the first phase (so the public display goes live without a separate "Activate Tournament" click) and when I complete the last phase via normal complete (so the certificate-creation workflow becomes available without a separate "Complete Tournament" click),
**so that** I cannot forget the explicit tournament-status transitions that today silently break the public display ("Kein aktives Turnier" while the tournament is logically running) and gate the post-tournament certificate workflow behind a redundant click.

---

## Context

This Story closes the operator-discoverability gap surfaced 2026-05-10 by user observation: after registering a display device the page showed "Kein aktives Turnier" and the connection indicator was red. Empirical investigation confirmed the chain is by-design — `DefaultDisplayOverviewService.resolveActiveOrPreviewPhase()` (`DefaultDisplayOverviewService.java:374-379`) requires a tournament with `status="ACTIVE"`; the `NoActivePhaseException` triggers a 404 with body `{"status":"NO_ACTIVE_PHASE"}` translated by `GlobalExceptionHandler.handleNoActivePhase` (`GlobalExceptionHandler.java:750-755`); the SPA classifies the 404 as `noPhase` and gates `wsConnect` on `phaseData.tenantId`, so the connection indicator stays disconnected (red). User had not invoked `POST /api/tournaments/{id}/activate` (E48S03 lifecycle) — the operator-forgetting case.

Tournament-status `ACTIVE` has three functional consumers beyond display: `cancel()` is allowed from PLANNED+ACTIVE (so already permissive); `complete()` requires ACTIVE (precondition unchanged); Timer accepts PLANNED|ACTIVE|COMPLETED (`DefaultTimerDataService.java:101-102`). Tournament-status `COMPLETED` has one operator-visible consumer beyond display: the "Urkunden erstellen" button in `CertificateTemplate.svelte` is gated on `tournament.status === 'COMPLETED'` (E52S02 — `CertificateTemplate.test.ts:79-87`).

Current code: `DefaultPhaseLifecycleService.start()` at line 340-396, `complete()` at line 408-445, `forceComplete()` at line 456-490 each acquire a per-tournament row-lock via `tournamentRepository.findByIdForUpdate(phase.getTournamentId())` (DEC-37 Clause B) at lines 347, 412, 460 respectively, but discard the returned `Tournament` (fire-and-forget for lock semantics only). Phase-status transitions do NOT check tournament-status — orthogonal lifecycles, this orthogonality IS the operator-discoverability gap. The existing `TournamentLifecycleSupport.isLastPhase(phaseId)` interface (`TournamentLifecycleSupport.java:34`) is DI-injectable and returns the last-phase predicate by max sequenceNumber.

The fix is atomic and additive (E48S22 atomic-side-effect-precedent — DRAFT→PLANNED is now a side-effect of `apply()`, no separate `mark-planned` button): `start()` captures the locked Tournament locally and conditionally promotes PLANNED→ACTIVE in the same `@Transactional` boundary BEFORE `eventPublisher.publishEvent`; `complete()` (only — not `forceComplete()`, per user decision: Notabschluss is escalation-pfad, operator may want to correct data before certificate workflow) symmetrically promotes ACTIVE→COMPLETED on last-phase complete. Manual endpoints (`POST /api/tournaments/{id}/activate`, `/complete`) and admin-UI buttons remain (additive — operators who DO use them keep their explicit pathway). Discoverability is a single `log.info("[E48S24] Auto-promoted tournament {} ...")` line per auto-promote site — neither manual `DefaultTournamentLifecycleService.activate/complete` nor this auto-promote writes `audit_log` rows or publishes `TournamentStatusChangedEvent`s (verified empirically — no asymmetry to introduce). No new public interface methods (DEC-58 Clause A does not fire — internal mutation of existing `DefaultPhaseLifecycleService` only).

Symmetry rationale (D-10 invariant per E48S01): the LAST phase always has `gameMode=siegerehrung` per the gameMode-Whitelist; under DEC-59 D-3 + Clause E the Siegerehrung phase has no matches (vacuous L1+L2). Therefore `phase.complete()` of the last phase IS the ceremonial tournament-completion gesture — no separate Tournament-Complete dialog/click adds semantic value. `forceComplete()` (Notabschluss / `MatchLockdownService` bulk-cancel) is the escalation pfad — operator chose Notabschluss deliberately, may need to correct data before reaching the certificate-creation workflow; tournament-completion remains explicit on this branch.

**Out-of-scope clarifications (separate Bug-Triage candidates):** ASSIGNED phase-status display-fallback (transient state, `DefaultDisplayOverviewService.isPendingOrPrepared` checks PENDING/PREPARED only — separate concern); phase-start/complete on CANCELLED/COMPLETED tournaments (residual orthogonal-lifecycle in non-PLANNED/non-ACTIVE branches — auto-promote NO-OPs in those branches per AC9 below, but existing phase transitions may still proceed); display-side gate removal (Option F was rejected — gate filters CANCELLED/COMPLETED stale-phase-leak per T-3 of Brief).

### Error-handling

- [ ] **AC-ERROR-TOURNAMENT-NOT-FOUND-DURING-AUTO-PROMOTE** (error-handling): if `findByIdForUpdate` returns `null` or throws (e.g., race with cascade-delete via E48S13 — extremely narrow given the lock is acquired BEFORE phase.setStatus, but possible if tournament was deleted between phase-load and lock-acquire on a different connection), the exception propagates unchanged to the existing `phase.start()`/`.complete()` exception handler — auto-promote does NOT introduce a new exception type, does NOT swallow, does NOT translate. Verified via test using a deliberate-throw fixture on the lock-acquire seam.

- [ ] **AC-ERROR-ISLASTPHASE-RACE-COVERAGE** (error-handling): `TournamentLifecycleSupport.isLastPhase(phaseId)` is invoked INSIDE the `@Transactional` boundary of `phase.complete()`, AFTER the per-tournament row-lock is held. Concurrent phase mutations (sequenceNumber re-shuffles, phase deletion via E48S13 reset-plan) cannot interleave between `isLastPhase` evaluation and `tournament.setStatus("COMPLETED")` because they would block on the same row-lock. Verified via concurrency IT (parallel `phase.complete` + concurrent `reset-plan` attempt — reset-plan rejects PLANNED-only precondition, but lock-serialization is verified). The `DefaultTournamentLifecycleSupport.java:100-107` defensive-true-on-empty-phases fallback cannot fire under D-1b because the phase being completed must exist (its `phase.status` was just transitioned to COMPLETED in the same TX).

- [ ] **AC-ERROR-NO-NEW-EXCEPTION-TYPES** (error-handling): no new `*Exception` class is introduced by this Story. All existing phase-lifecycle exceptions (`ConflictException` on invalid transitions, etc.) propagate unchanged. Auto-promote is a side-effect, not a precondition; it cannot block phase transitions that would otherwise succeed.

### Security

- [ ] **AC-SEC-TENANT-CONTEXT-PRESERVED** (security): auto-promote runs in the same `TenantContext` as the invoking `phase.start()` / `phase.complete()` call; the per-tenant `DataSource` routing per DEC-20 is preserved; `tournament.setStatus(...)` writes go to the calling tenant's H2 file. Verified via two-tenant IT (tenant-A `phase.start` does NOT auto-promote tenant-B's tournament, even if tenant-B has a similarly-shaped `PLANNED` tournament). DEC-5 multi-tenant isolation invariant preserved.

- [ ] **AC-SEC-AUTH-INHERITANCE** (security): the existing Spring Security authorization on `phase.start()` / `phase.complete()` callers (admin-only via `SecurityConfig.java:163` `/api/**` authenticated) is the sole authorization gate; auto-promote does NOT bypass any existing security check (it is a server-internal mutation occurring in an already-authorized request context). No new endpoint, no new authorization rule.
