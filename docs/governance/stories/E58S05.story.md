# Story: Data-driven, capability-filtered phase-plan generator selection

## User Story

**As a** tournament organizer,
**I want** the phase-plan and tournament pages to offer exactly the match generators the system actually supports, with the last phase offering only ceremony-capable generators,
**so that** I can never pick an unavailable or invalid generator, and the choices stay correct as generators are added or removed.

---

## Context

Today the phase-plan UI (`DraftConfig.svelte`) hardcodes the generator dropdown, and the tournament page
(`TournamentForm.svelte`) fetches a generator key list separately — there is no shared source and no
capability information. DEC-73 (D-5, D-8) makes generator selection data-driven from the registry: a REST
endpoint exposes the registered generators with their last-phase capability flag (`MatchGeneratorInfo`,
delivered by E58S01), a central TypeScript module loads the list once, and the phase plan filters generators
by phase position using the capability flag. This is the one deliberate observable change of Epic E58.

The current behaviour — the last phase is always a ceremony, and the award-ceremony generator is the only
last-phase-capable generator — is preserved; it simply becomes capability-driven instead of hardcoded.

---

## Acceptance Criteria

- [ ] AC1 (governance): a REST endpoint exposes the registered match generators as `MatchGeneratorInfo` records (generator key + last-phase capability flag) for the frontend; the controller resides in the `de.vvwt.tm.web` module per DEC-40. Per DEC-40 Clause B the response-shape choice is documented here with its reasoning: the projection the frontend needs is exactly the two components of the `de.vvwt.tm.tournament`-owned `MatchGeneratorInfo` record (`keyId`, `lastPhaseGenerator`) — no field omission, no aliasing, no aggregation — so projection equals wire shape and the endpoint serializes the record directly (Pattern A — bounded-context-owned query-shape record; a separate web-tier DTO would add a layer with no shape difference).
- [ ] AC2 (testing): a central TypeScript module loads the generator list and caches it; `DraftConfig.svelte` (phase plan) and `TournamentForm.svelte` (tournament page) both consume that shared module, and neither fetches the generator-list endpoint independently. Verified by (1) a behavioural test of the shared module — multiple calls to its generator-list accessor trigger exactly one endpoint fetch (the caching guarantee); and (2) confirmation that both components obtain the list via the shared module and contain no independent fetch of the generator-list endpoint. Full Svelte component-mount tests are NOT required for this AC — Svelte 5 component mounting is infeasible in the project's current Vitest + jsdom environment (a pre-existing limitation, out of E58 scope; see Notes).
- [ ] AC3 (testing): the phase-plan generator dropdown is populated from the registry data — no hardcoded generator list remains in the phase-plan frontend. Verified by a frontend test.
- [ ] AC4 (testing): the dropdown filters generators by the `isLastPhaseGenerator` capability flag — NOT by matching the generator key string — offering, for the **last** phase, only generators with `isLastPhaseGenerator == true`, and for every **other** phase only generators with `isLastPhaseGenerator == false`. Verified by a frontend test whose fixture includes a generator carrying a flag value independent of its key, so that a key-string-based filter would fail the test.
- [ ] AC5 (testing): the tournament-page match-generator selection uses the same central registry source; the tournament-page generator choice becomes the default generator for the phase plan. Verified by a frontend test.
- [ ] AC6 (governance): generator display labels in the dropdown are rendered via i18n keyed on the generator key; the registry key carries no human-readable label (DEC-73 Q-2). The frontend stays Vite + Svelte + TypeScript, no SvelteKit (DEC-2).
- [ ] AC7 (governance): the current single-phase / last-phase-is-ceremony behaviour is preserved — a single-phase tournament's sole phase is treated as the last phase and offers only last-phase-capable generators (operator decision, 2026-05-16).
- [ ] AC8 (testing): TDD per DEC-22 — the new endpoint and the frontend filtering logic each have a failing test authored before the implementation.
- [ ] AC9 (governance): `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54), including the frontend build via `frontend-maven-plugin`.

> All acceptance criteria must be verifiable.

## Notes

The deliberate observable change of Epic E58 (Brief D-8/D-9; not covered by the behaviour-preservation
hypothesis H-1). The `getGeneratorInfoList` registry accessor is delivered by E58S01; this story adds the REST
exposure and the frontend consumption. The "last phase = ceremony only" rule is the current behaviour made
capability-driven — it authorizes no new last-phase generator (DEC-73 D-5; the award-ceremony generator
remains the sole `isLastPhaseGenerator == true` generator).

**AC2 amendment (2026-05-16, post-delivery).** The first delivery of E58S05 reached `qa-review` cycle-2 FAIL
on AC2 only (ACs 1, 3–9 PASS). AC2's original verification clause — written during Discovery review cycle 2
— mandated mounting the phase-plan and tournament-page Svelte components in a frontend test. `qa-review`
established this is infeasible: Svelte 5 component mounting throws `lifecycle_function_unavailable` under the
project's current Vitest + jsdom test environment, and ~25 pre-existing component tests (MatchCorrection,
MatchOverview, …) already fail with the same error on `origin/staging`. This was a Discovery
over-specification — an AC must state the behavioural *what*, not prescribe an infeasible test *how*. AC2 is
amended (operator-approved 2026-05-16) to verify the load-once guarantee via a real store-level behavioural
test plus shared-module confirmation; component-mount tests are not required. The infeasible Vitest/jsdom
Svelte-5 component-test environment is a real pre-existing project gap but is out of E58 scope — a candidate
for a separate story. The cycle-1 E58S05 implementation already satisfies the amended AC2.
