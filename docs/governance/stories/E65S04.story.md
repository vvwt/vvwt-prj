# Story: The Display overview advances its current round automatically when the tournament advances

## User Story

**As a** spectator or operator watching the Display overview,
**I want** the Display to move its current-round indication forward automatically when the
tournament advances to the next round,
**so that** the Display always reflects the round actually being played.

---

## Context

When all matches of the current round are scored, the phase advances to the next round. The
Display overview highlights the round being played. Running a tournament on 2026-05-17 the
operator observed the Display staying on the previous round after the round had advanced —
while a scoring tablet correctly showed the new round.

Per the Discovery session of 2026-05-17 (Brief O-8, H-1), the round-advance event pipeline
is wired end to end: the scoring cascade emits a lap-advanced event, the event bridge
forwards it to the tenant display topic, and the Display SPA has a handler for it. So this
is a defect *inside* an existing pipeline, not a missing pipeline — but the exact point of
failure (the cascade's lap-advance condition, the event emission, or the Display's
re-render of the highlight) is not yet known. This is a bug-triage story: Delivery
investigates and pins the root cause.

---

## Acceptance Criteria

- [ ] AC1 (reproduction): Given a tournament where the matches of the current round are
  scored so that the phase advances to the next round, when this happens, then the Display
  overview currently does not move its current-round indication to the new round without a
  manual reload — this is the defect.
- [ ] AC2 (root-cause investigation): Delivery investigates the defect at delivery HEAD.
  Per Brief O-8 the round-advance event pipeline (scoring-cascade lap-advance → lap-advanced
  event → event bridge → tenant display topic) is already wired end to end and is presumed
  correct — it is confirmed, not re-derived. The primary suspect is the Display SPA's
  handling of the round-advance event — specifically whether it refreshes the data that
  drives the active-round indication. Delivery identifies the actual defect and records the
  root cause in the impl-report; the scoring cascade itself is touched only if the
  investigation proves the defect lies there (Epic Out of Scope).
- [ ] AC3 (expected behaviour): After the fix, when the tournament advances to the next
  round, the Display overview reflects the new current round automatically — without a
  manual reload.
- [ ] AC4 (no regression): Scoring, the confirmed-result Display update, and the round
  model itself — phase-global advancement, `Phase.currentLapNumber` as a 1-based running-lap
  index per DEC-65 — are unchanged; only the propagation/refresh defect is fixed.
- [ ] AC5 (error-handling / no-regression): The Display's existing resilience is preserved
  — if a live round-advance update is missed (e.g. a transient WebSocket drop), the Display
  still converges to the correct current round on its next refresh or reconnection, and the
  fix introduces no new failure mode.
- [ ] AC6 (testing — regression): A test authored failing-first per DEC-22 reproduces the
  round-not-advancing defect and passes after the fix; the existing test suite continues to
  pass. Behaviour not reachable by the project's existing test surface is verified and
  recorded in the impl-report.
- [ ] AC7 (governance — no test-only code): No production method, constructor, or field is
  introduced that exists solely to satisfy tests (DEC-70).
- [ ] AC8 (governance — build gate): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS
  (DEC-54, DEC-71).

> All acceptance criteria must be verifiable.

- The scoring-tablet round advance (E65S05) — a separate surface and story.
- The scoring cascade algorithm itself — the story may touch the cascade's lap-advance
  *condition* only if the bug-triage proves the defect lies there.

## Notes

Per Brief O-8 the round-advance pipeline already exists end to end, so this story is framed
as a bug-triage of a defect inside it (Brief H-1: UNVERIFIED root cause — a screenshot shows
a tablet correctly on the new round, so the lap advanced at least once). Per the Discovery
Bug Triage flow, AC1 is the reproduction scenario, AC2 narrows the root cause, AC3 states
the expected behaviour, and AC6 is the regression-test obligation — Delivery owns the
technical fix. DEC-65 fixes the round model as a non-negotiable boundary. The Display
overview is a Vite + Svelte SPA per DEC-2; any front-end change stays within that stack.
`mvn verify` is the build gate per DEC-54 / DEC-71.
