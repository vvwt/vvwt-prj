# Story E40S02: AlgorithmAnnouncementController + AlgorithmAnnouncementService exposing GET /api/algorithms returning DEC-43 D1 wire shape

## User Story

**As a** worker-side client (vvwt-slotopt-standalone-worker today via the E41 future rebuild; any DEC-43-aware client) preparing to register a public key with the dispatcher,
**I want** to query a `GET /api/algorithms` endpoint that returns the dispatcher's announced list of supported signature algorithms with their metadata (algorithm_id, display_name, deprecation_date, parameters) per DEC-43 D1,
**so that** I can choose an algorithm BEFORE generating my keypair (per DEC-43 D2 free-choice) and surface a deprecation warning to my admin if the chosen algorithm has a non-null deprecation_date (per DEC-43 D3 — admin-warning channel is client-implementation-specific, surfaced by E41 worker-side).

---

## Context

Per Brief D-2: endpoint shape is option (A) — separate `GET /api/algorithms` (REJECTED options B embedded-in-register-key, C both, D two-phase POST handshake; see Brief T-1 for steel-manned alternatives).

Per Brief D-3: metadata persistence is option (α) — Java-side @Component beans only; the AnnouncementService aggregates the announced list by iterating registered `SignatureVerifier` beans (E40S01-extended) and projecting their metadata methods to the wire shape.

Per Brief D-4: V1 announced list contains exactly one entry — Ed25519 with all fields populated per the DEC-43 D1 schema (`algorithm_id="Ed25519"`, `display_name="Ed25519"`, `deprecation_date=null`, `parameters=null`).

Per Brief S-4: package layout follows E37 D-6 fresh authorization — interface `AlgorithmAnnouncementService` in package root `de.vvwt.slotopt.dispatcher.crypto`; impl `DefaultAlgorithmAnnouncementService` in `.internal` sub-package; controller `AlgorithmAnnouncementController` in `de.vvwt.slotopt.dispatcher.crypto` (per E37 controller-in-context-package convention; dispatcher is not a Spring Modulith application so DEC-40 web-tier-as-module rule does not apply).

This story consumes E40S01's interface extension and runs in parallel with E40S03 (both depend on S01 only).

## Notes

- **Wire-format snake_case vs camelCase**: DEC-43 D1 schema uses snake_case (`algorithm_id`, `display_name`, `deprecation_date`). Jackson default with PROPERTY_NAMING_STRATEGY=SnakeCaseStrategy handles this OR explicit `@JsonProperty("algorithm_id")` per record component. Implementer choice at delivery time; both produce the required wire output.
- **Why a record, not a POJO**: `AnnouncedAlgorithm` is an immutable value object with no behavior. Java records are the canonical choice (per DEC-35 records-for-VOs convention; the records-as-entity-classes-forbidden clause does NOT apply here — this is a wire-payload VO, not a Spring Data JDBC entity).
- **Endpoint placement**: `de.vvwt.slotopt.dispatcher.crypto.AlgorithmAnnouncementController` lives alongside `KeyRegistrationController` etc. per E37 convention. Dispatcher is not a Spring Modulith application, so DEC-40 web-tier-as-module rule (which is `vvwt-tm-web` specific) does not apply.
- **Authentication note** (AC-NO-AUTH-REQUIRED): the announcement endpoint is intentionally public. Per DEC-43 D2 "client free choice from non-deprecated", the client must be able to discover the algorithm list BEFORE authenticating. SecurityConfig may need an explicit `permitAll()` rule for `/api/algorithms` if the dispatcher's default is `authenticated()` — implementer verifies at delivery time.
