# Story E46S05: Default-tenant re-branding + first-boot setup parameters in `DefaultTenantBootstrapRunner`

## User Story

**As a** Tournament Manager operator deploying a fresh on-prem (LAN) instance,
**I want** the bootstrapped default tenant to carry the product brand name (`"ToM Tournament Manager (LAN)"`) and the configured language (`"de"`) — both overridable via Spring properties at first boot —
**so that** I can brand the tenant correctly from day one without editing the registry file by hand and without waiting for the (still-out-of-scope) tenant edit UI, while existing local installations that already contain `"Default (LAN)"` keep their current name and are NOT silently re-branded.

---

## Context

Brief D-18 carves out a narrowly scoped UX fix for the most painful first-boot
gap exposed during the certificate / i18n discovery: the system today
bootstraps the default tenant with the literal constant
`"Default (LAN)"` (`DefaultTenantBootstrapRunner.DEFAULT_TENANT_DISPLAY_NAME`,
line 111 — empirically verified). That literal is visible to end users on the
new branded certificate (`tom_organizer` is snapshotted from
`tenant.displayName` at tournament INSERT — see E46S01) and on any future
admin surface. Until the edit-UI follow-up stories ship (Brief S-15 — out of
scope here), the only way to rebrand is to hand-edit
`${tm.data.dir}/tenant-registry.json` after first boot.

This story closes that gap with two Spring properties bound at first boot:

- `tm.bootstrap.default-tenant.display-name` (default: `"ToM Tournament Manager (LAN)"`)
- `tm.bootstrap.default-tenant.language` (default: `"de"`)

Both properties are evaluated **only** when the registry is empty (first boot).
On any subsequent boot the runner respects whatever name and language already
sit in `tenant-registry.json` — including legacy `"Default (LAN)"` entries
that pre-date this story (Brief backward-compat constraint). The existing
`findDefaultTenantRecord()` filter (line 665, currently matching by literal
`DEFAULT_TENANT_DISPLAY_NAME`) is the place where this re-bind logic must
shift: detection of "is the default tenant already registered?" must NOT
key on the new bootstrap-default literal alone, otherwise existing
`"Default (LAN)"` registries would be misclassified as empty and a duplicate
default tenant would be created on the next boot.

This story consumes the 3-arg `TenantRegistryPort.TenantRecord(UUID, String, String)`
shape and the `register(UUID, String, String)` overload that E46S01 introduces
(Brief D-14). The current 2-arg call (`registry.register(tenantId, displayName)`,
line 656) becomes a 3-arg call passing the resolved language.

DEC-22 RED-first applies: the existing `DefaultTenantBootstrapRunner` test
(`DefaultTenantBootstrapRunnerTest.java`, 665 lines, covers AC1–AC11 +
orphan-recovery) must be updated, plus new RED-first scenarios for
property-override on first boot, default-fallback when no property is set, and
backward-compat preservation of legacy `"Default (LAN)"` registries.

DEC-41 observable-form classification per surface: the bootstrap is a
boot-time bean lifecycle surface — observability is a combination of
registry-state assertions (the resulting `TenantRecord.displayName()` and
`.language()`) and the boundary of "first-boot vs subsequent-boot" decision
making. Tests assert observable registry state, not internal helper
invocations.

DEC-35 naming: properties live in a new `@ConfigurationProperties`-bound POJO
in `de.vvwt.tm.tenant.internal` (precedent: `TmDataDirProperties.java` in the
same package — empirically confirmed). `@Value` field-injection is also
acceptable (Brief: story specifies behavior, not the choice). Story-author
decides at delivery RED-first.

## Acceptance Criteria

### Property binding + defaults

- [ ] **AC-PROP-DISPLAY-NAME-DEFAULT [governance]:** A fresh boot with no
  override for `tm.bootstrap.default-tenant.display-name` registers the default
  tenant with `displayName = "ToM Tournament Manager (LAN)"`. Verifiable: after
  first-boot bootstrap completes against an empty `tenant-registry.json`, the
  resulting `TenantRecord.displayName()` equals exactly
  `"ToM Tournament Manager (LAN)"`.
- [ ] **AC-PROP-LANGUAGE-DEFAULT [i18n]:** A fresh boot with no override for
  `tm.bootstrap.default-tenant.language` registers the default tenant with
  `language = "de"` (system default per Brief C-15). Verifiable: after
  first-boot bootstrap completes against an empty `tenant-registry.json`, the
  resulting `TenantRecord.language()` equals exactly `"de"`.
- [ ] **AC-PROP-DISPLAY-NAME-OVERRIDE [governance]:** A fresh boot with
  `tm.bootstrap.default-tenant.display-name="My Club"` (provided via
  `application.yml`, env var, system property, or Spring test slice) registers
  the default tenant with `displayName = "My Club"`. Verifiable: after
  first-boot bootstrap completes, the resulting `TenantRecord.displayName()`
  equals exactly the configured override value.
- [ ] **AC-PROP-LANGUAGE-OVERRIDE [i18n]:** A fresh boot with
  `tm.bootstrap.default-tenant.language="en"` registers the default tenant
  with `language = "en"`. Verifiable: after first-boot bootstrap completes,
  the resulting `TenantRecord.language()` equals exactly the configured
  override value.
- [ ] **AC-LITERAL-DEFAULT-LAN-REMOVED [governance]:** The literal string
  `"Default (LAN)"` no longer appears as a hardcoded default-tenant name in
  the production source of `DefaultTenantBootstrapRunner`. Specifically:
  - The constant `DEFAULT_TENANT_DISPLAY_NAME = "Default (LAN)"` (currently
    line 111) is removed or replaced by a property-bound source.
  - The SQL literal `'Default (LAN)'` inside `INSERT_TENANT_SQL`
    (currently line 116, the main-DB upsert) is replaced by a parameterized
    bind whose value comes from the resolved bootstrap-default name.
  - Javadoc / log-message references to the literal `"Default (LAN)"` may
    remain as historical commentary but MUST NOT influence behavior.
  Verifiable by `grep -F '"Default (LAN)"' DefaultTenantBootstrapRunner.java`
  returning zero hits in active code paths (Javadoc / comments may be
  retained when explicitly marked as historical).

### First-boot-only evaluation

- [ ] **AC-FIRST-BOOT-ONLY-PROPERTY-EVALUATION [governance]:** The two
  properties are consulted ONLY when the registry is empty (no default tenant
  found). On subsequent boots — when the registry already contains the
  default tenant — the runner MUST NOT re-apply the property values to the
  existing record. Verifiable scenario: (1) first boot with default property
  values produces a `TenantRecord(uuid, "ToM Tournament Manager (LAN)", "de")`;
  (2) restart the application with the property overridden to
  `tm.bootstrap.default-tenant.display-name="Changed Name"`; (3) the registry
  record's `displayName()` after the second boot still equals
  `"ToM Tournament Manager (LAN)"` — the property change did NOT propagate to
  the persisted record.
- [ ] **AC-SUBSEQUENT-BOOT-NO-WRITE [governance]:** On a subsequent boot with
  a non-empty registry, the runner MUST NOT call
  `TenantRegistryPort.register(...)` for the default tenant. Verifiable by
  asserting that no register-side write path executes when
  `findAll()` already returns a default tenant entry. (The existing
  `firstStart_*` vs `subsequentStart_*` split in
  `DefaultTenantBootstrapRunnerTest` is the carrier surface.)

### Backward compatibility

- [ ] **AC-BACKWARD-COMPAT-LEGACY-DEFAULT-LAN-PRESERVED [governance]:** An
  existing `tenant-registry.json` containing a record with
  `displayName == "Default (LAN)"` (a pre-E46S05 installation) MUST be
  detected as the existing default tenant on subsequent boots — NOT
  re-bootstrapped, NOT renamed, NOT duplicated. Verifiable scenario: seed a
  registry file with one record `{uuid, "Default (LAN)", null}`, boot the
  application with default property values, and assert (a) the registry still
  contains exactly one record; (b) its `displayName()` is still
  `"Default (LAN)"`; (c) no second `"ToM Tournament Manager (LAN)"` record
  was created. The detection logic in
  `DefaultTenantBootstrapRunner.findDefaultTenantRecord()` (currently filters
  by `DEFAULT_TENANT_DISPLAY_NAME.equals(r.displayName())` at line 667) must
  be revised so that legacy `"Default (LAN)"` entries are recognized as the
  default tenant. The exact recognition strategy (e.g., "first record found
  is the default", "match a list of known historical names", or "match
  by `is_default` column / equivalent registry flag") is decided RED-first
  by delivery; story specifies the observable invariant only.
- [ ] **AC-BACKWARD-COMPAT-LEGACY-LANGUAGE-NULL-TOLERATED [i18n]:** A
  legacy `TenantRecord` with `language = null` (the convenience-constructor
  shape from E46S01 D-14) MUST be loaded without runtime error and MUST NOT
  trigger a re-write or migration of the registry by this runner.
  Language-resolution downstream (LocaleResolver chain — E46S02) is
  responsible for the null-fallback to system default; this runner does not
  back-fill `null` languages.

### Bootstrap writes language to per-tenant `tenants` table (architecture amendment Brief v5)

- [ ] **AC-REGISTER-VIA-PORT [governance]:** When the runner registers the default tenant
  on first boot, it invokes `TenantRegistryPort.register(...)` with the resolved
  displayName + language. The exact arity (2-arg with language passed via a separate
  channel, OR a 3-arg overload added by E46S05) is delivery's choice provided that:
  (i) `TenantRegistryPort.findAll().get(0).language()` returns the bound language per
      AC-PROP-LANGUAGE-DEFAULT / AC-PROP-LANGUAGE-OVERRIDE,
  (ii) the JSON registry persistence format is forward-compatible (legacy 2-field
       entries readable per AC-BACKWARD-COMPAT-LEGACY-LANGUAGE-NULL-TOLERATED),
  (iii) the `tenants.language` per-tenant DB column is also written per
        AC-INSERT-TENANTS-LANGUAGE-AT-BOOTSTRAP — both carriers consistent.
  *AMENDED 2026-05-04 (Discovery recovery session) — original AC required strict
  preservation of the 2-arg signature with no overload addition. This proved
  incompatible with AC-PROP-LANGUAGE-DEFAULT/OVERRIDE which require
  `TenantRecord.language()` to be observable from `findAll()`. Brief v5 architecture
  intent was honored (per-tenant table written per AC-INSERT-TENANTS-LANGUAGE-AT-BOOTSTRAP);
  this AC is widened to permit JSON to carry language as a cached duplicate so
  registry-level observables work without cross-storage joins.*

- [ ] **AC-INSERT-TENANTS-LANGUAGE-AT-BOOTSTRAP [governance][i18n]:** The runner's
  `INSERT_TENANT_SQL` (currently line 116) is extended to write the `language` column added by
  E46S01 (`tenants.language`). The INSERT statement is updated to include `language` in its
  column list AND the corresponding positional parameter. The bound value is the resolved
  language from `tm.bootstrap.default-tenant.language` (default `"de"`). Verified by:
  - reading the post-commit `INSERT_TENANT_SQL` constant — column list contains `language`;
  - the runner's INSERT call-site binds the property-resolved language;
  - the IT for AC-PROP-LANGUAGE-DEFAULT asserts via `assertj-db` that the per-tenant
    `tenants` row has `language = "de"` post-bootstrap;
  - the IT for AC-PROP-LANGUAGE-OVERRIDE asserts the `tenants.language` column reflects the
    overridden value.

- [ ] **AC-INSERT-TENANTS-DISPLAY-NAME-AT-BOOTSTRAP [governance]:** The runner's
  `INSERT_TENANT_SQL` is updated to bind the resolved displayName (from the property) to the
  `display_name` column instead of the previous hardcoded literal `'Default (LAN)'`. Verified
  by: post-commit reading the SQL string and observing it uses `?` (parameterised) instead of
  the hardcoded literal in the VALUES clause; the runner's INSERT call-site binds the
  property-resolved displayName; per-tenant `tenants` row's `display_name` reflects the
  property-bound value (matches the JSON-registry entry).

- [ ] **AC-CONCURRENT-BOOTSTRAP-RACE-PRESERVED [governance][testing]:** The existing
  `atomicRegisterIfAbsent`-based race protection (concurrent JVM-instance boot against the
  same `${tm.data.dir}/tenant-registry.json`) is PRESERVED end-to-end across the
  property-driven values. Two threads both passing the same default tenant-id concurrently
  with potentially different language values must result in: exactly one INSERT into the
  per-tenant `tenants` table, exactly one register-success in the JSON registry, AND no
  partial-write between the two carriers (i.e., NO state where the JSON registry has the
  tenant but the per-tenant `tenants` table is empty, OR vice versa). Verified by RED-first
  concurrent-boot test (two CompletableFutures invoking the bootstrap concurrently against
  the same `tm.data.dir`; assert exactly-one INSERT, exactly-one JSON entry, both consistent).
  Story-author chooses the exact concurrency mechanism RED-first (synchronized,
  optimistic-then-cleanup-on-loss, file-lock — delivery decides per existing
  `atomicRegisterIfAbsent` patterns; the contract is "atomic both-or-neither").

### Invalid display-name behavior (parity with language validation)

- [ ] **AC-DISPLAY-NAME-VALIDATION-FAIL-FAST-OR-FALLBACK [governance]:** Behavior on an invalid
  `tm.bootstrap.default-tenant.display-name` value (empty string, whitespace-only) is
  documented in the impl report and covered by an explicit test. The two acceptable strategies
  (parallel to AC-LANGUAGE-VALIDATION-FAIL-FAST-OR-FALLBACK below) are:
  (a) **fail-fast** — startup throws `IllegalArgumentException` with a message naming the
  offending property and the rejected value, OR
  (b) **default-fallback** — the runner logs WARN and falls back to
  `"ToM Tournament Manager (LAN)"`.
  Delivery picks ONE strategy RED-first; the choice is logged in `impl-report.md` with a
  one-sentence rationale. The validation MUST at minimum reject `null`, empty, and
  whitespace-only values. (Rationale: the existing `TenantRecord` canonical constructor only
  null-checks displayName, NOT empty/whitespace — without this AC, an operator setting
  `display-name=""` would create a tenant with `displayName=""`, which would break
  `findDefaultTenantRecord()` equality-based lookup on subsequent boots and cause re-bootstrap
  + duplicate-tenant attempts.) Same strategy chosen for both display-name AND language MUST
  be consistent (i.e., if language is fail-fast, display-name is fail-fast; if language is
  fallback, display-name is fallback).

### Invalid-language behavior (i18n fail-safe)

- [ ] **AC-LANGUAGE-VALIDATION-FAIL-FAST-OR-FALLBACK [i18n]:** Behavior on an
  invalid `tm.bootstrap.default-tenant.language` value (e.g., empty string,
  whitespace, an obviously non-ISO-639-1 token) is documented in the impl
  report and covered by an explicit test. The two acceptable strategies are:
  (a) **fail-fast** — startup throws `IllegalArgumentException` with a
  message naming the offending property and the rejected value, OR
  (b) **default-fallback** — the runner logs WARN and falls back to `"de"`
  (system default per Brief C-15). Delivery picks ONE strategy RED-first;
  the choice is logged in `impl-report.md` with a one-sentence rationale.
  The validation MUST at minimum reject `null`, empty, and whitespace-only
  values (the contract for "invalid"); deeper ISO-639-1 validation is NOT
  required (a free-form 2-letter token like `"xx"` is accepted — locale
  resolution is downstream's concern per E46S02).

## Out of Scope

- **Re-naming or migration of legacy `"Default (LAN)"` registries** — backward

  hand-edit the registry (or use a future migration story).

  `tenants.language` column addition (per Brief v5 amendment); this story only
  CONSUMES it (the bootstrap's INSERT_TENANT_SQL writes the property-bound language

- **`messages_<lang>.properties` resources beyond DE** — V1 ships only DE
  (Brief D-7); architecture is ready, additional bundles are separate
  stories.
- **Validation of ISO-639-1 conformance beyond null/empty/whitespace** —
  free-form 2-letter tokens are accepted; locale resolution and bundle
  fallback are E46S02's concerns.
- **`LocaleResolver` chain logic** — E46S02 owns the
  `team.language ?? tournament.language ?? tenant.language ?? "de"` chain.
  This story only PRODUCES `tenant.language` at first boot; it does not
  CONSUME it.
