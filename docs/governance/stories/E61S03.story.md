# Story: Scoring-tablet team-position swap — manual, automatic per-set, and tiebreak 8-point mid-set switch, consistent across reloads

## User Story

**As a** referee scoring a match courtside on the tablet,
**I want** the on-screen left/right positions of the two teams to match the physical court —
switching automatically each set, switching mid-set in a tiebreak when a team reaches 8, and
correctable by hand,
**so that** the score I enter on each side always belongs to the team actually on that side of
the court.

---

## Context

This is the third story of Epic E61. After the layout redesign (E61S01) and the match-API
extension (E61S02), the scoring-tablet field page can show the true current set and whether it
is a tiebreak. In real play the two teams change sides of the court between sets, and again
mid-set in the deciding (tiebreak) set; the referee needs the on-screen positions to follow,
and to be correctable when they drift from reality.

Per the Discovery session of 2026-05-16, the swap uses a relative-toggle model (Brief D-3): a
set change, the tiebreak 8-point switch, and a manual swap each flip the currently shown
orientation.

---

## Acceptance Criteria

- [ ] AC1 (manual swap): the field page provides a control that, when activated, swaps the
  on-screen left/right positions of the two teams.
- [ ] AC2 (automatic per-set): when the current set changes, the on-screen team positions
  switch automatically.
- [ ] AC3 (tiebreak mid-set): when the current set is a tiebreak and either team's current
  points are 8 or more, the tiebreak side-switch is applied to the on-screen orientation. This
  is a deterministic state recomputed from the current set, points, and tiebreak status — not a
  one-time edge event — so it is still correct after a page reload taken while a team's points
  are already at or above 8. (Within a set, points only increase, so the switch is observed
  once and then persists for the rest of the set.)
- [ ] AC4 (relative model): the position changes are relative — a set change, the tiebreak
  8-point switch, and a manual swap each flip the currently shown orientation; consequently a
  manual swap permanently shifts the subsequent per-set alternation, keeping the orientation
  aligned with the physical court.
- [ ] AC5 (score-team binding): a position swap never changes which team a score belongs to —
  points entered always attach to the team's identity, regardless of which side that team is
  currently shown on.
- [ ] AC6 (reload consistency): the on-screen orientation is consistent across a page reload —
  after a reload (which happens after every submit) the deterministic part of the orientation
  (the per-set alternation and the tiebreak 8-point switch) is recomputed from the current set,
  points, and tiebreak status, and combined with the persisted manual-swap state, so the same
  team is shown on the same side as before the reload — except where the submit itself
  legitimately changes the orientation (a set change, or crossing the tiebreak 8-point
  threshold), which must then be reflected.
- [ ] AC7 (error-handling): for a match format with no tiebreak / deciding set, the tiebreak
  8-point switch (AC3) does not occur; the automatic per-set switch (AC2) and the manual swap
  (AC1) still work.
- [ ] AC8 (i18n): any new user-facing label introduced (e.g. for the swap control) is sourced
  from a message key, consistent with the existing `score.field.*` keys.
- [ ] AC9 (governance): the field page remains Mustache + inline vanilla ES5 JavaScript only —
  no Svelte or other framework, no ES2015+ syntax, no bundler (DEC-19).
- [ ] AC10 (testing): the swap behaviour is covered by tests — authored failing-first for any
  first-party logic per DEC-22 — exercising the automatic per-set switch, the tiebreak 8-point
  switch and its absence for non-tiebreak formats, the manual swap, the score-team binding
  invariant (AC5), reload consistency (AC6), and — specifically — the tiebreak orientation
  being correct after a page reload performed while a team's current points are at or above 8.
  Behaviour not reachable by the project's existing test surface for this Mustache + ES5 page
  is verified and recorded in the impl-report.
- [ ] AC11 (governance): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS (DEC-54,
  DEC-71).

> All acceptance criteria must be verifiable.

## Notes

Per Brief O-8, the displayed orientation is the combination of a deterministic component — the
per-set alternation, recomputed from the API's true set index, and the tiebreak 8-point switch,
from the API's tiebreak signal plus the current points (true and reload-surviving once E61S02
lands) — and a path-dependent component, the manual-swap offset. The cross-reload-relevant
state (the manual-swap offset) is persisted on the tablet so that after a reload the
deterministic part is recomputed and combined with it; localStorage is permitted on this
surface by DEC-19. AC6 states the observable requirement (orientation consistent across
reload); how the state is stored is Delivery's. The swap is tablet-local presentation — no
server change and no change to other surfaces. The 8-point threshold is fixed (Brief S-6).
Per memory `feedback_ac_behavioural_what_not_test_how`, AC10 points at the project's existing
test surface for this Mustache + ES5 page rather than prescribing an unsupported test
mechanism. `mvn verify` is the build gate per DEC-54 / DEC-71.
