# Story E21S11: Timeline boundary-API (5 classes) — reconstruction-in-place with TDD

## User Story

**As a** consumer of tournament timeline data (future `print`, `timer`, and `scoring` contexts),
**I want** the five timeline classes reconstructed at `de.vvwt.tm.tournament.*` as a pure-stateless boundary-API with property-based tests,
**so that** downstream Track-3 reconstruction (E24 `print`, E26 `timer`) can depend on a stable `tournament::api` surface from day one, without re-targeting from `de.vvwt.tm.domain.timeline.*` mid-flight.

---

## Context

**D-2 resolution.** The five classes at `de.vvwt.tm.domain.timeline.*` were classified `uncertain` in E21S01 inventory (rows 334–338) because they are consumed by BOTH the `print` context (via `LaufzettelAssembler`) AND the `timer` context (via `TimerDataService`) — both legitimate owners. The E21S01 inventory deferred resolution to "E21S02..N discovery".

The resolution landed in Session Brief `discovery-2026-04-20-e21-full-refinement` D-2 (human decision K2=A, 2026-04-20): **all five classes are placed at `de.vvwt.tm.tournament.*` (public boundary-API)**. Rationale: timeline is a tournament-owned concept (it describes the tournament's temporal structure — phases, breaks, rounds); print and timer are DOWNSTREAM consumers. Placing timeline at the tournament boundary means print and timer depend on `tournament::api`, which matches the hub-first Approach C from the Wave-2 Program Map (D-10).

**The five classes** (all at public root `de.vvwt.tm.tournament.*` per D-2, NO `.internal.*` variants):

1. **`PhaseConfig`** (inventory row 335) — request value object carrying per-phase configuration (lap count, duration per phase).
2. **`PhaseBreakConfig`** (inventory row 334) — request value object carrying per-phase-break configuration (break type, duration).
3. **`TimelineCalculationService`** (inventory row 336) — stateless service computing the full tournament timeline from `PhaseConfig` + `PhaseBreakConfig` inputs. Consumed by print (Laufzettel timing) and timer (countdown schedule).
4. **`TimelineEntry`** (inventory row 337) — value object representing one timeline entry (start time, type, phase reference).
5. **`TimelineEntryType`** (inventory row 338) — enum for timeline entry type (ROUND_START, BREAK, etc.).

**Pure-stateless service contract.** `TimelineCalculationService` has no state. Per the legacy source (inventory row 336: "stateless service computing the full tournament timeline") and the D-2 rationale, the class takes `PhaseConfig` + `PhaseBreakConfig` inputs and returns a `List<TimelineEntry>`. No database access, no Spring-managed collaborators with state, no `@Transactional`. Spring-management is optional — Delivery decides and DOCUMENTS in the impl-report whether the class is `@Service`/`@Component` (Spring-managed singleton, useful if other tournament-internal code auto-wires it) or a plain POJO (simpler, avoids unnecessary Spring coupling in a value-pure service). See Notes.

**Property-based testing fit.** `TimelineCalculationService` is an ideal target for property-based tests (jqwik or parameterised): timeline construction has crisp invariants — monotone time ordering, correct start times, break insertions at the configured intervals, total duration equals sum-of-phases plus sum-of-breaks. These invariants should hold across arbitrary valid `(PhaseConfig, PhaseBreakConfig)` inputs, so property-based testing is strictly stronger than example-based here.

Per DEC-22 every class is test-first. Per DEC-30 (boundary-API discipline), public-package classes are tested via their runtime contracts — `TimelineCalculationService` is tested via its pure-function contract (input → output), NOT via a `@SpringBootTest` (because the class has no Spring-specific behaviour to integration-test; a pure-JUnit test is the correct integration level for a pure-stateless POJO).

## Acceptance Criteria

> Every AC below is testable by a command, a file-path check, or a pattern match. Vague criteria are invalid.

### Testing ACs (mandatory category: `testing`)

- [ ] **AC-TDD-PhaseConfig** / **AC-TDD-PhaseBreakConfig**: for each VO, git history shows a failing pure-JUnit test (constructor validation, equality, hashCode, immutability) committed BEFORE the implementation. Red-then-green per DEC-22. Characterization tests against the legacy classes are forbidden.

- [ ] **AC-TDD-TimelineEntry** / **AC-TDD-TimelineEntryType**: failing pure-JUnit tests committed BEFORE the implementation. For `TimelineEntry`, tests cover constructor + field accessors + equality. For `TimelineEntryType` (enum), tests cover `valueOf` + `values()` completeness (at minimum the types observed in the legacy enum — read legacy source to enumerate them, do NOT copy-paste the file).

- [ ] **AC-TDD-TimelineCalculationService-PROPERTY-BASED**: a failing property-based test suite (jqwik OR hand-rolled parameterised with ≥20 seeded cases) is committed BEFORE the implementation. The suite encodes at minimum these invariants:
    1. **Monotone time ordering**: for any `List<TimelineEntry> result`, `result.get(i).startTime <= result.get(i+1).startTime` for every valid `i`.
    2. **Total duration matches inputs**: `result.last.startTime + result.last.duration − result.first.startTime == sum(PhaseConfig.duration) + sum(PhaseBreakConfig.duration)`.
    3. **Break insertions match `PhaseBreakConfig`**: the count of `TimelineEntry` instances with `type == BREAK` equals the number of configured breaks.
    4. **Empty-input contract**: `TimelineCalculationService.compute(emptyPhaseConfig, emptyBreaks)` returns an empty `List` (or the documented degenerate value), not `null` and not an `IllegalStateException`.
  Each invariant asserted against ≥20 randomised inputs per run (jqwik default OR the hand-rolled equivalent).

- [ ] **AC-TIMELINE-PURE-JUNIT**: the `TimelineCalculationService` test class uses pure JUnit (no `@SpringBootTest`, no `@ApplicationModuleTest`). If Delivery chooses Spring-management for the class (see Notes), the Spring-wiring is verified via a separate small `@SpringBootTest` smoke test (one test method confirming the bean loads), but the invariant suite remains pure-JUnit. A property-based invariant test wrapped in `@SpringBootTest` fails this AC.

- [ ] **AC-LEGACY-OUTPUT-PARITY** (real-integration sanity): one parameterised test seeds a representative `(PhaseConfig, PhaseBreakConfig)` pair matching a legacy tournament fixture (same inputs the legacy `LaufzettelAssembler` consumed per inventory row 336) and asserts the new `TimelineCalculationService` produces a result with the same number of entries and the same total duration as the legacy service. Per DEC-22 this is NOT a characterization test (output is asserted against INDEPENDENT legacy-fixture expectations, not against a snapshot of the legacy class's output); it is a real-integration sanity check that the reconstruction preserves observable timeline semantics. If Delivery cannot identify a legacy fixture, STOP and escalate — silent drift in timeline computation is a scoring-correctness risk.

### Error-handling ACs (mandatory category: `error-handling`)

- [ ] **AC-VALIDATION-PHASECONFIG**: `PhaseConfig` constructor rejects invalid inputs with a typed exception and a clear message — at minimum: negative `lapCount`, negative `durationSeconds`, `null` required fields. Tests cover each rejection case.

- [ ] **AC-VALIDATION-PHASEBREAKCONFIG**: `PhaseBreakConfig` constructor rejects invalid inputs — negative duration, `null` break-type reference. Tests cover each rejection case.

- [ ] **AC-SERVICE-NULL-INPUT**: `TimelineCalculationService.compute(null, ...)` and `.compute(..., null)` throw a typed exception (e.g., `NullPointerException` via `Objects.requireNonNull` OR a domain exception from S09). Behaviour documented in Javadoc; test asserts it.

- [ ] **AC-SERVICE-INCONSISTENT-INPUT**: if `PhaseBreakConfig` references a phase index outside the bounds of the provided `List<PhaseConfig>`, `TimelineCalculationService.compute` throws a typed exception with a clear message — NOT an `IndexOutOfBoundsException`. Test asserts this.

## Notes

**For the Delivery Agent.**

- **Spring-wiring decision (AC-SPRING-WIRING-DECISION-DOC).** Two viable choices:
    - **Plain POJO** — simplest; constructors take nothing (stateless), consumers `new TimelineCalculationService().compute(...)`. Matches the "pure-function" semantic. Cleanest boundary-API for downstream contexts that want to call timeline math without Spring-coupling their tests.
    - **`@Service`-annotated** — Spring-managed singleton; consumers `@Autowired` it. Matches the existing `LaufzettelAssembler` usage pattern (inventory row 336 shows 4 importers via `LaufzettelAssembler → TimelineCalculationService` — the legacy is likely Spring-managed).
  Delivery picks one and documents with rationale. If unclear at refinement, the safer default is `@Service` (preserves legacy wiring semantics; downstream consumers can still call it directly via `new` if needed — `@Service` is a hint, not a restriction). Flag the choice in impl-report.

- **Read the legacy `TimelineCalculationService` source FIRST** to enumerate the `TimelineEntryType` enum values (AC-TDD-TimelineEntryType) and to identify representative inputs for AC-LEGACY-OUTPUT-PARITY. Class-read for inventory-resolution is allowed (same rule as E21S01 — read to resolve `uncertain`, do NOT copy-paste into the new file). Re-author under TDD.

- **Property-based testing library.** jqwik (https://jqwik.net) is the canonical Java property-based library and integrates with JUnit 5. If jqwik is not already on the test classpath, add it in a separate commit BEFORE the red-phase test commit (keeps the red-then-green sequence clean). If Delivery prefers hand-rolled parameterised tests with explicit seeds over adding a new dependency, that is acceptable PROVIDED ≥20 seeds per invariant.

- The five classes are tightly coupled (all five move together as a cohort). Natural commit sequence: (1) enum + VOs (`TimelineEntryType`, `PhaseConfig`, `PhaseBreakConfig`, `TimelineEntry`) in a first wave — pure-value, no Spring; (2) `TimelineCalculationService` in a second wave — consumes the four VOs. Within each wave, strict red-then-green per DEC-22.

**Scope-split hint (Q-7).** Five classes is a moderate scope — well within one Delivery session barring surprises. The most likely escalation trigger is AC-LEGACY-OUTPUT-PARITY failing to find a usable fixture (the legacy integration-test corpus may not expose timeline-computation inputs directly). If so, split: S11a = four VOs, S11b = `TimelineCalculationService` with a fixture-construction spike.
