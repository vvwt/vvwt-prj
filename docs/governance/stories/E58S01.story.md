# Story: MatchGenerator extensibility — stable key, last-phase capability, registry info list, GameMode enum removed

## User Story

**As a** tournament organizer,
**I want** every match generator to be addressable by one stable registry key and to declare whether it is a last-phase generator,
**so that** the phase plan can enumerate and offer the right generators per phase without a hardcoded, redundant enum.

---

## Context

`MatchGenerator` (`de.vvwt.tm.tournament`) already follows a registry+strategy shape — `MatchGeneratorRegistry`
dispatches by the `getBeanId()` string. But the `GameMode` enum (the type of `DraftSection.gameMode`) is a
second, redundant identity for the same thing, and the registry exposes no UI-facing description of the
registered generators. DEC-73 (D-1, D-4, D-5) makes the registry the single source of generator identity and
extends `MatchGenerator` with a last-phase capability predicate so the phase-plan UI (E58S05) can filter
generators per phase. This is the first story of Epic E58 and the foundation the other four build on.

`MatchGenerator` is layer L1 of the DEC-56 L1/L2/L3/L4 decomposition — its `generate()` match-generation
contract is unchanged by this story; only the L1 interface gains a key accessor and a capability predicate.

## Acceptance Criteria

- [ ] AC1 (governance): `MatchGenerator.getBeanId()` is renamed to `getKeyId()`; every implementation and every caller (production and test) uses `getKeyId()`; no `getBeanId` reference remains in `vvwt-tm-web` (fresh audit at delivery HEAD).
- [ ] AC2 (testing): `MatchGenerator` declares `boolean isLastPhaseGenerator()`; every `MatchGenerator` implementation present at delivery HEAD declares the correct value — the award-ceremony generator is the sole implementation returning `true` (per DEC-73 D-5 / Brief O-8), all others return `false`. Verified by a test authored failing-first per DEC-22 that enumerates the registered generators rather than assuming a fixed implementation count.
- [ ] AC3 (governance): a `MatchGeneratorInfo` record carrying the generator key and the `isLastPhaseGenerator` flag exists, as a public type in the `de.vvwt.tm.tournament` bounded-context root package per the DEC-35 layout (a value type that crosses the module boundary to `de.vvwt.tm.web`).
- [ ] AC4 (testing): the `MatchGeneratorRegistry` public interface (per AC7) declares `getGeneratorInfoList()` returning a `List<MatchGeneratorInfo>` for all registered generators; the implementation provides it. Verified by test.
- [ ] AC5 (governance): the `GameMode` enum is removed; `DraftSection.gameMode` is a String registry-key; no reference to `GameMode` remains in `vvwt-tm-web` (fresh audit at delivery HEAD).
- [ ] AC6 (governance): an unregistered `gameMode` key is rejected fail-fast in the `DraftConfig` / `DraftSection` validation path, which runs at both draft save and draft apply — given a draft whose `gameMode` is not a registered `MatchGenerator` key, when the draft is saved, and again when it is applied, then it is rejected with an operator-actionable error and no draft is persisted. The check is NOT deferred to deep-pipeline match-generation time (DEC-73 D-6). Verified by test.
- [ ] AC7 (governance): `MatchGeneratorRegistry` is addressable through a public interface per the DEC-58/DEC-72 interface mandate and the DEC-35 naming canon. Delivery verifies at HEAD whether E57S01 already extracted that interface: if so, this story extends it with `getGeneratorInfoList()` (AC4); if not, this story extracts the interface AND adds `getGeneratorInfoList()` to it. Either way the new accessor is declared on the public interface, not only on the implementation class. The E57S05 build-time interface-mandate guard passes.
- [ ] AC8 (testing): TDD per DEC-22 — all new behaviour (`isLastPhaseGenerator`, the registry info accessor, the `gameMode` validation) has a failing test authored before the production code. Delivery classifies the `getBeanId`→`getKeyId` rename per memory `feedback_dec22_refactor_phase_first.md` — Q-1b mechanical refactor only if a trustworthy TDD-authored test oracle already covers the renamed surface, otherwise Q-1a fresh RED-first — and records the classification in the impl-report.
- [ ] AC9 (governance): `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54); the `GameMode` removal leaves no compiler warnings or unused imports (DEC-29 / DEC-30).
- [ ] AC10 (governance): the DEC-59 Clause E/F siegerehrung lifecycle is behaviour-unchanged — the `gameMode` string value still drives the empty-match-list dispatch and the activation guard (the value remains `"siegerehrung"` until E58S04 renames it). Verified by the existing siegerehrung-lifecycle integration tests staying GREEN under `mvn verify`; if the `GameMode` removal forces an edit to that dispatch path, a fresh RED-first test re-specifies the unchanged behaviour (per DEC-22 — not a characterization test).

> All acceptance criteria must be verifiable.
