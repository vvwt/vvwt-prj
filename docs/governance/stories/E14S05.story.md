# Story E14S05: Default-tenant bootstrap on first start — tests first

## User Story

**As an** operator starting the TM application for the first time on a freshly-scaffolded machine,
**I want** the default tenant to be created automatically — with its H2 file, its Flyway-migrated schema, and its registry entry —
**so that** I can log in and use the application without a separate tenant-onboarding step, matching DEC-5's "1 Location, 1 aktives Tournament" local-default.

---

## Context

DEC-5 defines the default local-use configuration as single-location, single-active-tournament. DEC-20 reframes the default tenant as a regular tenant with a fixed (or bootstrap-generated) UUID, living in its own H2 file. DEC-17 (with its 2026-04-12 amendment) sketches the default-tenant identifier-generation approach; this story finalises whether a fixed UUID or a generated-and-persisted UUID is used.

The bootstrap is an `ApplicationRunner` with an ordered position: it must run AFTER Spring has wired the tenant infrastructure beans (registry, DataSource resolver, Flyway runner) but BEFORE the `auth` context's `AdminCredentialsBootstrap` (from E15) attempts to write credentials into the default tenant's DB. Ordering is governed by `@Order` on the runner.

Per DEC-22, the bootstrap is written test-first. Tests must cover: first-start (empty registry → create default tenant), subsequent-start (registered default tenant → skip creation), and error paths.

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows failing tests for (a) first-start default-tenant creation, (b) subsequent-start no-op detection, (c) failure during Flyway migration during bootstrap, before the bootstrap implementation commits. Spot-check confirms red-then-green ordering per DEC-22.

- [ ] AC2 (data-isolation — first-start behaviour): An integration test against a fresh `${tm.data.dir}` (`@TempDir`) verifies the bootstrap: creates the default tenant's H2 file at the DEC-20 path, runs the Flyway runner against it, registers the default tenant in the registry, and completes without errors. The resulting DB contains the expected Flyway-applied schema for the `tenant` module (and any other module declaring migrations at the time — but Wave-1 at this story's merge is `tenant`-only until E15S05).

- [ ] AC3 (data-isolation — subsequent-start behaviour): A second integration test starts with a `${tm.data.dir}` already containing the default tenant's registry entry and H2 file. The bootstrap runs but takes NO destructive action: no re-creation, no Flyway run that would reset history, no registry re-registration. The existing file and its content are intact after bootstrap.

- [ ] AC4 (data-isolation — default-tenant UUID per DEC-17 amendment): The default tenant's UUID is GENERATED at bootstrap time via `UUID.randomUUID()` and PERSISTED in the registry inside the same transaction as the bootstrap's first write (per DEC-17 2026-04-12 amendment — generated-and-persisted, NOT fixed). On subsequent application starts, the already-persisted UUID is read from the registry; no new generation. This is an operational requirement for cross-instance uniqueness against the Participant Info Service (PPIS) per DEC-17 context.

- [ ] AC5 (error-handling — bootstrap failure): If Flyway migration during the default-tenant creation fails, the bootstrap surfaces the error, does NOT leave a registry entry pointing to an incomplete DB, and the application startup fails fast with an actionable message. A test with an intentionally-broken test migration verifies this (the test migration is a fixture used only for this AC, not a permanent artefact).

- [ ] AC6 (error-handling — concurrent first starts): If two JVM instances start simultaneously against the same empty `${tm.data.dir}` (rare but possible in operator testing), the registry's concurrent-safe init from E14S02 prevents two conflicting default tenants from being registered. A test simulates this via explicit concurrent invocation of the bootstrap and asserts exactly one default tenant exists after both complete.

- [ ] AC7 (testing — Modulith verify): `ApplicationModulesTest` remains green. The `ApplicationRunner` class lives under `de.vvwt.tm.tenant.internal` and its `@Order` is documented in Javadoc so E15's AdminCredentialsBootstrap can reason about its relative ordering.

- [ ] AC8 (governance — no auth coupling): The bootstrap does NOT import or reference any `de.vvwt.tm.auth.*` type. Admin credentials are E15's concern; this story produces a tenant and registers it, nothing more. A negative import test or a manual `git grep` check is documented in the Delivery plan.

- [ ] AC-ORPHAN-RECOVERY (error-handling — partial-failure recovery on second start): If a prior start created a tenant directory (`${tm.data.dir}/tenants/{uuid}/`) but the registry entry was not persisted (crash between file creation and transaction commit), the bootstrap on the next start detects the orphan directory and either: (a) cleans it up and retries the full flow (if idempotent — preferred), OR (b) fails fast with an actionable error naming the orphan path and instructing the operator to remove it manually. The chosen recovery mode is documented in Javadoc of the bootstrap component. A test simulates the orphan state (create directory without registry entry) and asserts the detection + recovery behaviour.

- [ ] AC-PARALLEL-PHASE (governance — legacy DefaultTenantBootstrap coexistence during parallel phase): Per DEC-21 "no feature flags" + Brief trade-off T-2 ("staging deploy may briefly run with tests failing or with an inconsistent state — tolerated because no production deployment"), this story does NOT touch the legacy `de.vvwt.tm.tenant.DefaultTenantBootstrap` component. During the parallel phase (between this story's merge and E14S07's cutover commit), the staging branch may have two ApplicationRunner beans (legacy + new) that both attempt default-tenant-bootstrap with different persistence models — the staging deploy is accepted as paused/broken until cutover. The Delivery plan must acknowledge this explicitly. No `@Profile`, no `@ConditionalOnProperty`, no bean-exclusion is permitted (DEC-21). The resolution is E14S07's atomic cutover, not an interim guard.

## Notes

Per DEC-17's 2026-04-12 amendment, the default-tenant UUID is ALWAYS generated+persisted, never hardcoded. The earlier impulse toward "fixed UUID for local determinism" is superseded — PPIS cross-instance uniqueness is the load-bearing requirement.

Concurrent-first-start (AC6) is rare in production but common during operator testing ("start it, kill it, start it again"). Registry persistence from E14S02 gives the transactional substrate; this story's test exercises the bootstrap's correct use of it.
