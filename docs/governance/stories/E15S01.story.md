# Story E15S01: PasswordGenerator — reconstruction-in-place with TDD (pure Java)

## User Story

**As a** TM administrator whose credentials are generated on first start,
**I want** the password-generation logic isolated as a small, pure-Java, independently-tested component,
**so that** future changes to password length or alphabet can be made confidently and the component is reusable for any admin-credential scenario.

---

## Context

In the legacy code, `AdminCredentialsBootstrap` combines orchestration, JDBC persistence, and password generation in one class. Password generation — `SecureRandom` producing alphanumeric characters — is pure domain logic with zero Spring dependency. Isolating it is the first, smallest, lowest-risk application of reconstruction-in-place (DEC-22): a focused class, testable with pure JUnit, that validates the TDD pattern before E15S02 ventures into JDBC territory.

Per DEC-21, the new class lives at `de.vvwt.tm.auth.internal.PasswordGenerator` (implementation hidden from other modules). Per DEC-22, the class is written test-first: a failing test for the alphabet + length invariants precedes the implementation. Characterization tests against the legacy `AdminCredentialsBootstrap`'s generation behaviour are explicitly forbidden.

The legacy code remains live in its original location until E15S07 cutover — do not touch it in this story.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows a failing JUnit test for `PasswordGenerator` (exercising alphabet compliance and length invariants) committed BEFORE the `PasswordGenerator` implementation class commit. The test file path is `vvwt-tm-web/src/test/java/de/vvwt/tm/auth/internal/PasswordGeneratorTest.java` (or equivalent under the new auth package). Characterization tests are forbidden per DEC-22.

- [ ] AC2 (testing — property-based invariants): The test suite includes property-based tests (via jqwik or similar, or hand-rolled parameterised tests with multiple seeds) that confirm: generated passwords consist only of configured alphabet characters; length matches the configured length exactly; generation with distinct `SecureRandom` seeds produces distinct outputs (anti-determinism smoke); default length is 16 per the Epic scope.

- [ ] AC-ENTROPY-FLOOR (security — minimum 72-bit entropy): Generated passwords MUST provide at least 72 bits of entropy per the preserved E05S02 AC11 security floor: `log2(alphabet_size ^ length) ≥ 72`. At default parameters (62-char alphanumeric alphabet × 16 characters), this yields ~95.3 bits — well above the floor. A property-based test asserts this floor for any parameter combination the generator accepts (rejects configurations below the floor at construction time OR tests cover only above-floor configurations).

- [ ] AC3 (security — cryptographic source): `PasswordGenerator` takes a `SecureRandom` via constructor injection for testability (the production wiring uses a default `SecureRandom`). Tests explicitly cover: (a) a `SecureRandom` seeded for reproducibility produces expected outputs in a deterministic test, (b) the constructor rejects `null` with a typed exception.

- [ ] AC4 (error-handling — invalid configuration): Instantiating or invoking the generator with length < 1 is rejected with a typed exception and a clear message. Tests cover the boundary: length 0 rejected, length 1 accepted.

- [ ] AC5 (governance — package placement): `PasswordGenerator` lives under `de.vvwt.tm.auth.internal`. It is NOT placed in the root `de.vvwt.tm.auth` package (it is not part of the public API). No Spring annotations (`@Component`, `@Service`) are on the class — it is a plain POJO instantiated by the Spring configuration class in E15S04.

- [ ] AC6 (testing — no Spring): The test class uses pure JUnit (no `@SpringBootTest`, no `@ApplicationModuleTest`). This enforces the "pure Java" contract and keeps the test fast. A `@SpringBootTest` here fails AC.

- [ ] AC7 (governance — no legacy interaction): This story does NOT modify or delete the legacy `AdminCredentialsBootstrap`. `git diff` at merge shows only new files under the new `de.vvwt.tm.auth.*` paths plus tests. Legacy code is untouched; E15S07 removes it atomically.

## Notes

This story is deliberately the smallest first Pilot unit. If anything about the TDD + Modulith + reconstruction pattern is brittle, catching it here — on 30 lines of pure Java — is far cheaper than catching it in E15S03's orchestration tests.

Default alphabet choice (alphanumeric, no ambiguous characters like `0/O`/`l/I`?) is a small decision Delivery makes and documents in Javadoc — the Epic scope says "alphanumeric"; refine in the class's contract test.
