# Story E54S04: Fix — IndexOutOfBoundsException in L3 phase-global path for asymmetric 25-match phase (11T/2G/3F)

## User Story

**As a** tournament operator running a phase with asymmetric group sizes (e.g., 5+6 teams = 25 matches),
**I want** the L3 slot-optimization to complete without throwing `IndexOutOfBoundsException`,
**so that** the phase reaches PREPARED status and can be activated normally (Display SPA + Print Laufzettel render correctly).

---

## Context

This story is a **Bug-Triage spike** (per `discovery.agent.md` §Bug-Triage flow) targeting one of two failure modes that caused E54S03 to fail and prevented its delivery. E54S03 worktree (`/home/vvw/.worktrees/E54S03-inner-workspace`) has uncommitted production-code changes implementing DEC-61 Clause D (L3 phase-global invocation + SlotResultApplicator alignment) and two new regression-ITs.

### Observed failure (verbatim from `.gaai/project/contexts/backlog/.delivery-logs/E54S03.log` cycle 2 final mvn-verify):

```
[ERROR] Errors:

```

All three error sites are `slotOptimizationClient.optimize(phaseId)` invocations (line 198, 252, 300 of `AsymmetricBye11T2G3FRegressionIT.java`). The fixture setup is OK in cycle 2 (the cycle-1 `BadSqlGrammar` due to wrong column names `member_avatar1_id` was fixed). The exception originates in **production-code** under `vvwt-tm-web/src/main/java/de/vvwt/tm/slotopt/`.

### Reproduction scenario (Given/When/Then)

- **Given** a phase with 11 avatars in 2 groups (5 + 6 teams), `tournament.fieldCount = 3`, `tournament.optimize = true`, and 25 intra-group matches with `lap_number = NULL`, `field_number = NULL`;
- **When** `RoundAssignmentService.assignRoundsAndFields(phaseId, 3)` runs (L2 voting per DEC-61 Clause A) followed by `SlotOptimizationClient.optimize(phaseId)` (L3 phase-global per DEC-61 Clause D);
- **Then** the L3 invocation throws `IndexOutOfBoundsException: Index 25 out of bounds for length 25` somewhere inside `vvwt-tm-web/.../slotopt/` (likely in `RoutingSlotOptimizationClient.executeLeg1Inline` or `SlotResultApplicator.applyResult`).

### Root-cause investigation findings (Discovery — narrowing only, no fix proposed)

Discovery's narrowing of the OOB candidate sites:

- **`SlotResultApplicator.applyResult`**: post-E54S02, `lapCount = mapping.canonical().rowCount()` (= lapCount, not matchCount). But `matchOrder.size()` is still matchCount (= 25 for this phase). Any index arithmetic that conflated `lapCount` with `matchCount.size()` could overflow at index 25.
- **`RoutingSlotOptimizationClient.executeLeg1Inline`**: post-E54S03 uncommitted changes, the lap-perm-to-row-seq expansion is removed; `int[] rowSeq = LehmerCodec.rankToPermutation(rank, lapCount)` produces an array sized `lapCount` (not `rowCount = matchCount`). If a downstream caller still iterates by `matchOrder.size()` (= 25), accessing `rowSeq[25]` overflows.
- **`PhaseToRawPhaseDefMapper.map`** (post-E54S02): lap-rows aggregation — for asymmetric setup with `bye-slots`, lapCount may differ subtly; off-by-one in dense-id assignment plausible.

Discovery does **NOT** propose which line is the exact culprit; Delivery isolates via stack-trace.

### Expected behavior after fix

1. For 11T/2G/3F (25 matches), L2+L3 complete without exception.
2. All 25 matches have non-null `lap_number ∈ [1..lapCount]` and `field_number ∈ [1..3]` per DEC-60 D-1.
3. DB query `SELECT COUNT(*) FROM match WHERE phase_id = ? AND lap_number IS NULL` returns 0 post-L2+L3.
4. The 3 regression-ITs from E54S03 worktree (`AsymmetricBye11T2G3FRegressionIT.{optimize_11T2G3F_totalMatchCount25, displayOverviewMatches_allLaps, printLaufzettel_byeTeam}`) all PASS.
5. The 12T/2G/3F symmetric setup remains GREEN (no regression — E54S03 worktree's other ITs preserved).
