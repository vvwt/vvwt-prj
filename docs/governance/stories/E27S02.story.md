# Story E27S02: Leg 3 — Cancelable In-Process Timeout Compute + Admin-Cancel REST + Minimal UI

## User Story

**As a** Tournament Manager admin running a tournament with > 10 rounds,
**I want** the slot-optimization to begin computing locally even when no dispatcher is configured/reachable, with a clearly-visible status and a one-click cancel that returns the best permutation found so far,
**so that** I can complete a large tournament's optimization offline (per DEC-15 self-host LAN-local posture and gesamtkonzept §Offline-Strategie) without being blocked by dispatcher availability.

---

## Context

E27S01 landed the routing skeleton (Leg 1 only — N≤10 in-process via existing `DirectSlotOptimizationClient`). For N > `tm.slotopt.exhaustive-max-n` (default 10), the skeleton still throws `UnsupportedOperationException` via Direct's existing branch (`DirectSlotOptimizationClient.java:184-193`). This story lands **Leg 3**: a new in-process cancelable timeout compute path that (a) extends `RoutingSlotOptimizationClient` to route N>threshold to a NEW `CancelableInProcessSlotOptimizationService`, (b) tracks per-tournament jobs in an in-memory registry, (c) exposes a REST endpoint for admin-cancel + status, (d) provides a minimal Svelte cancel button + status badge in the admin UI.

Leg 2 (dispatcher HTTP) lands in E27S03; for N>threshold post-S02, ALL traffic uses Leg 3 (no Leg 2 yet — fully usable end-to-end without dispatcher).

Per Brief T-6: V1 accepts loss-on-restart for in-flight optimizations (in-memory job registry; no persistence). On TM restart mid-Leg-3, the in-flight compute is lost; admin re-triggers from the UI. Documented in operator docs at S04.

Per Brief D-3 + audit O-5: Leg 3 is **greenfield code** — `DirectSlotOptimizationClient`'s UOE-throwing branch confirms E04S04's timeout-mode substrate is missing on disk; this story authors it RED-first under DEC-22 Iron Law.

Per Brief D-3 Patch P4 + DEC-11 line 63 boundary: Leg 3 invokes `vvwt-slotopt-worker-lib`'s `PacketSolver` directly on TM-internal `RawPhaseDef` data — DEC-4 V1 amendment authorizes this path. DEC-11's "TM business logic does not invoke the worker in-process" prohibition applies to E01S11 packet-pull pattern only (worker as packet *consumer of dispatcher*), NOT to Leg 3.

## Acceptance Criteria

### NEW `CancelableInProcessSlotOptimizationService` (Leg 3 core)

- [ ] **AC-CANCELABLE-SERVICE-AUTHORED [testing]:** A new public interface `de.vvwt.tm.slotopt.CancelableInProcessSlotOptimizationService` is authored at module root (per DEC-35) with method signatures sufficient to support Leg 3 routing — story-author chooses concrete signatures (e.g., `OptimizationResult optimize(UUID phaseId, CancellationToken token)` + `void cancel(UUID tournamentId)`). - [ ] **AC-COOPERATIVE-CANCELLATION-TESTED [testing, error-handling]:** RED-first test asserts: when `cancel(tournamentId)` is invoked mid-computation, the in-progress computation terminates within a bounded time window (story-author chooses bound — e.g., "next inter-permutation check, ≤ 1 second observable wall-clock for a representative test fixture"). The test uses fixed seed/fixture data sufficient to take measurable wall-clock time without being flaky.

- [ ] **AC-BEST-SO-FAR-NON-NULL-AFTER-FIRST-PERMUTATION [error-handling, testing]:** RED-first test asserts: after at least ONE permutation has been evaluated, calling `cancel(tournamentId)` returns a non-null `OptimizationResult` containing the best permutation found so far (lowest variety score per existing `Variety` semantics from `vvwt-slotopt-worker-lib`). If `cancel(tournamentId)` is invoked BEFORE any permutation evaluated, the contract is story-author choice: either return a default/sequential assignment (analogous to existing `FallbackSlotOptimizationClient` pattern) or throw a documented exception (e.g., `NoOptimizationProgressException`). ## Notes

**Greenfield-ness of Leg 3 (per Brief F-1 + audit 2026-04-28):** E04S04 backlog status `done` does NOT reflect on-disk reality — `DirectSlotOptimizationClient.java:184-193` throws UOE for N>10 with explicit comment "E04S04 not yet implemented"; no `TimeoutBased*`/`BestSoFar*` class exists in repo. Leg 3 is authored fresh under DEC-22 Iron Law per this story; no repurpose path.

**Cooperative cancellation mechanism (story-author choice):** Options include (a) `volatile boolean` flag checked between permutations in `PacketSolver` invocation loop; (b) a custom `Iterable<Permutation>` wrapper with `Thread.interrupted()` checks; (c) Java 21 `StructuredTaskScope` for cooperative cancellation. Story-author picks per RED-first design — recommended (a) for simplicity (matches `vvwt-slotopt-worker-lib`'s existing single-thread-loop pattern) but (c) is acceptable if `StructuredTaskScope` integration adds value (e.g., supervised parallel exploration). Iron Law ACs cover the observable cancel-within-bounded-time invariant regardless of mechanism.

**Best-So-Far tracking pattern:** `DefaultCancelableInProcessSlotOptimizationService` maintains a private `AtomicReference<BestResult>` updated on each evaluated permutation if its variety score is strictly less than current best. On cancel: returns the current `BestResult.permutation` mapped via existing `SlotResultApplicator`. Threading: cancel may be invoked from a different thread than the compute thread; `AtomicReference` + cooperative-flag covers this without needing locks.

**Per-tournament isolation rationale (per Brief D-11):** Default-tenant single-active-tournament constraint (project context.md + DEC-17) means in practice only one tournament is active at a time on a default-tenant deployment. The per-tournament-key registry pattern is forward-compatible with multi-tenant cloud deployments where multiple tournaments may run concurrently.

**`web/package-info.java` allowedDependencies edit conflict awareness:** E27S02 modifies `web/package-info.java`. If E27S03 also modifies it (e.g., for additional slotopt sub-packages), Daemon serializes; standard rebase per E25/E26 precedent.

**Existing E03 N≤10 IT coverage (unchanged):** AC11 of E04S03 (existing IT covering full preparation flow Tournament → Phase → 6 TeamAvatars → optimizeSlots → verify lap/field) continues to pass post-S02 because RoutingSlotOptimizationClient routes N≤10 to Direct unchanged. No retrofit needed; if AC11's IT directly injected `DirectSlotOptimizationClient` (concrete), it continues to pass; if it injected `SlotOptimizationClient` (interface), it now goes through Routing → Direct (transparent).
