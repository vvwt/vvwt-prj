# Story E45S03: Java pre-Reset (tournament context) — drop redundant `tenant_id` WHERE predicates from tournament-package DAOs + drop `tenantId` parameters; preserve `tenant_id`-passing in INSERT/UPDATE temporarily until S05

## User Story

**As a** Tournament Manager developer preparing for the Wave-2 Big-Bang-Reset,
**I want** redundant `tenant_id` WHERE predicates and `tenantId` parameters removed from all tournament-package DAOs (DefaultMatchRepository, DefaultTeamRepository, DefaultPhaseRepository, DefaultTournamentRepository, DefaultDeviceRepository, MatchOutcomeRepository, SetResultRepository, TeamAvatarRatingRepository, DefaultAuditLogRepository, DefaultDraftService),
**so that** the production code is aligned with the post-Reset schema (DEC-39 D1 + DEC-50 drop the `tenant_id` columns) while the system remains functional during the S03→S05 window — INSERT/UPDATE keeps passing `tenant_id` so the still-NOT-NULL column is satisfied.

---

## Context

Brief O-6 empirically confirmed `tenant_id` appears as an active WHERE predicate
AND INSERT column across ~50+ touchpoints in tournament-package DAOs:

- `DefaultMatchRepository`: 8 SQL constants (SELECT_BY_ID, SELECT_ALL, SELECT_BY_PHASE,
  SELECT_BY_FIELD_LAP, INSERT, DELETE_BY_PHASE, DELETE_BY_ID, etc.) — all use
  `WHERE … AND tenant_id=?`.
- `DefaultTeamRepository`: SELECT_BY_ID, SELECT_BY_TOURNAMENT, DELETE_BY_ID — all
  carry tenant_id predicate.
- `DefaultDeviceRepository`: 11 SQL constants (INSERT, UPDATE, SELECT_BY_ID,
  SELECT_BY_PIN, SELECT_BY_FIELD, SELECT_BY_FIELD_NO_LOCATION, SELECT_ALL_BY_TENANT,
  COUNT_BY_TENANT, COUNT_BY_TENANT_DISPLAY, COUNT_BY_ID_AND_TENANT, etc.)
- `DefaultPhaseRepository`, `DefaultTournamentRepository`: similar pattern.
- `MatchOutcomeRepository`, `SetResultRepository`, `TeamAvatarRatingRepository`,
  `DefaultAuditLogRepository`: scoring-table DAOs (Option A puts these tables in
  `tournament/V1` per Brief T-7; their Java code stays in tournament package).
- `DefaultDraftService`: 3 INSERT call-sites with explicit `tenantId` parameter
  (lines 164, 210, 272 per `DefaultDraftService.java`).

Under DEC-20 DB-per-Tenant + AbstractRoutingDataSource, the WHERE-tenant_id
predicate is **observably redundant** — a per-tenant H2 file contains rows for
exactly one tenant by construction, so `WHERE tenant_id=?` filters nothing. But
the predicate-removal IS observably behavioral against any test that crosses
tenants (e.g., `CrossTenantIsolationTest`) — Brief H-4 verified that
tournament-DAO ITs use per-tenant routed DataSources via
`TenantContextTestSupport.bindDefaultTenant()`, so post-removal the same tests
continue to pass (each test runs in its own per-tenant H2 file).

**DEC-22 Iron Law applies.** Predicate-removal is behavioral. Per Brief T-4 + Q-3,
the per-surface classification (RED-first vs DEC-41 Spec-Anchored supplementary)
is decided at story-authoring with empirical evidence:

- If existing IT for a DAO method has a property-based / round-trip / external-
  spec-citation / named-algebraic-invariant test (DEC-41 Spec-Anchored): the test
  SURVIVES as supplementary regression safety; the predicate-removal is treated
  as DEC-22 §refactor-clause (NOT byte-equivalent — test guards behavioral
  invariance) and may proceed without fresh RED-first.
- If existing IT is Snapshot-Driven (DEC-41 §Forbidden-as-safety-net) or absent:
  fresh RED-first test authored against the new (predicate-removed) production
  code per DEC-22 Iron Law.

**INSERT/UPDATE retain `tenant_id`-passing temporarily** — column is NOT NULL
until S05 drops it. S06 removes the INSERT/UPDATE-side references after the
column is gone. This sequencing avoids a runtime-broken state between commits
(per Brief T-6 Alternative-Post + DEC-21 §Deploy-pause).

## Acceptance Criteria

### Predicate-removal scope (production code)

- [ ] **AC-WHERE-PREDICATE-REMOVED-MATCH [governance]:** `DefaultMatchRepository`'s SQL constants (SELECT_BY_ID, SELECT_ALL, SELECT_BY_PHASE, SELECT_BY_FIELD_LAP, DELETE_BY_PHASE, DELETE_BY_ID) drop the `AND tenant_id=?` clause from WHERE. Method signatures lose the trailing `UUID tenantId` parameter. Internal `tenantContext.current()` invocation removed where it was used solely to pass the parameter.
- [ ] **AC-WHERE-PREDICATE-REMOVED-TEAM [governance]:** `DefaultTeamRepository` SELECT_BY_ID, SELECT_BY_TOURNAMENT, DELETE_BY_ID — same pattern.
- [ ] **AC-WHERE-PREDICATE-REMOVED-PHASE [governance]:** `DefaultPhaseRepository` — same pattern.
- [ ] **AC-WHERE-PREDICATE-REMOVED-TOURNAMENT [governance]:** `DefaultTournamentRepository` — same pattern.
- [ ] **AC-WHERE-PREDICATE-REMOVED-DEVICE [governance]:** `DefaultDeviceRepository` — same pattern across all SELECT/COUNT/DELETE SQL constants. Note: device admin endpoints' `countByTenant`, `countDisplayByTenant`, `findAllByTenant` method NAMES retain "by tenant" terminology in S03 (semantic drift OK — they still return rows for the current tenant via per-tenant routing); rename to neutral names is a Wave-3 cleanup and out of S03 scope.
- [ ] **AC-WHERE-PREDICATE-REMOVED-MATCH-OUTCOME [governance]:** `MatchOutcomeRepository` — same pattern.
- [ ] **AC-WHERE-PREDICATE-REMOVED-SET-RESULT [governance]:** `SetResultRepository` — same pattern.
- [ ] **AC-WHERE-PREDICATE-REMOVED-TEAM-AVATAR-RATING [governance]:** `TeamAvatarRatingRepository` — same pattern.
- [ ] **AC-WHERE-PREDICATE-REMOVED-AUDIT-LOG [governance]:** `DefaultAuditLogRepository` — same pattern.
- [ ] **AC-DRAFT-SERVICE-PARAM-REMOVED [governance]:** `DefaultDraftService` 3 INSERT call-sites at lines 164, 210, 272 (per Brief audit) lose their explicit `null, // tenantId — set by repository` placeholder pattern; the underlying repository INSERT keeps `tenant_id`-passing per S03's INSERT-untouched policy. Net: the internal pass-through pattern simplifies, but the column is still written until S05.

### INSERT/UPDATE preservation (S03 must NOT touch INSERTs)

- [ ] **AC-INSERT-UPDATE-UNTOUCHED [error-handling]:** All `INSERT INTO …` and `UPDATE … SET …` SQL constants in the affected DAOs continue to write `tenant_id` values (column is still NOT NULL until S05). S03 commit must NOT remove `tenant_id` from any INSERT or UPDATE. Verified by `git diff ${baseSha}..HEAD --stat` showing INSERT/UPDATE statements either unchanged or limited to predicate-removal lines (i.e., the `WHERE … AND tenant_id=?` part within UPDATE is removed; the SET clause's `tenant_id` writes are preserved).
- [ ] **AC-INSERT-UPDATE-TENANTID-SOURCE-PRESERVED [error-handling]:** The INSERT/UPDATE-side `tenant_id` value source (`tenantContext.current()` call at INSERT/UPDATE call-site) is preserved in S03. If a method had `UUID tenantId = tenantContext.current()` used by both WHERE predicate (S03 removes) and INSERT (S03 preserves), the local variable stays — S03 only removes the WHERE binding, not the local variable.

### Test classification + RED-first vs Spec-Anchored

- [ ] **AC-DAO-TEST-CLASSIFICATION-AT-DELIVERY [testing]:** At story-authoring time, story-author classifies each affected DAO IT (`MatchRepositoryIT`, `TeamRepositoryIT`, `PhaseRepositoryIT`, `TournamentRepositoryIT`, `DeviceRepositoryIT`, `MatchOutcomeRepositoryIT`, `SetResultRepositoryIT`, `TeamAvatarRatingRepositoryIT`, `AuditLogRepositoryIT`, `DraftServiceIT`) per DEC-41 §observable-form criteria. Classification table stored in `impl-report.md`.
- [ ] **AC-SPEC-ANCHORED-PRESERVED [testing]:** For DAO ITs classified Spec-Anchored: tests survive as supplementary regression. DEC-22 §refactor-clause covers the predicate-removal change (existing test guards observable behavior; refactor preserves observability of "the right rows are returned for the current tenant context").
- [ ] **AC-SNAPSHOT-DRIVEN-RED-FIRST [testing]:** For DAO ITs classified Snapshot-Driven (or absent): fresh RED-first test authored under DEC-22 Iron Law BEFORE the predicate-removal in production code. RED-then-GREEN cadence visible in `impl-report.md` (e.g., separate sub-commits within the S03 single commit, or RED-first commit chained as a DEC-22 §refactor-clause-N/A note).
- [ ] **AC-CROSS-TENANT-ISOLATION-PRESERVED [testing]:** `CrossTenantIsolationTest` continues to pass post-S03. The cross-tenant isolation invariant (rows from tenant A do not leak to tenant B) is now enforced ENTIRELY by the per-tenant routing layer (DEC-20 AbstractRoutingDataSource); it is NO LONGER enforced by application-level WHERE-tenant_id predicates. The test verifies the routing layer does its job. If the test FAILs post-S03, that is signal that the routing layer has a bug — NOT that the predicate-removal was wrong.
- [ ] **AC-DEC-26-DEC-46-COMPLIANCE-RETAINED [testing]:** All affected DAO ITs continue to comply with DEC-26 + DEC-46 three rules (schema-from-migration via ScriptUtils, independent persistence verifier via assertj-db, read/write decoupling via direct JDBC). S03 does NOT alter the schema-source path (tests still load V1..V16 + V17 from root migration paths — the per-module path migration happens at S05/S06).
