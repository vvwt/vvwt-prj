# Story E46S01: Data foundation for certificate i18n + organizer — schema migrations for `tournament.organizer` + `tournament.language` + `team.language` + `tenants.language`, plus snapshot-at-INSERT logic for `tournament.organizer` from `tenants.display_name` (intra-DB)

## User Story

**As a** Tournament Manager developer preparing the E46 certificate i18n + organizer initiative,
**I want** the per-tenant H2 schema extended with four new nullable columns (`tenants.language`, `tournament.organizer`, `tournament.language`, `team.language`) plus the `tournament` INSERT path snapshotting the current tenant's `display_name` from the `tenants` table (intra-DB JDBC) into the new `tournament.organizer` column,
**so that** subsequent E46 stories (S02 locale-resolver, S03 assembler extension, S04 template adoption, S05 default-tenant re-branding) can read these fields as a stable contract without each story having to re-establish the data carriers.

---

## Context

E46 introduces three semantic concepts that have no carrier in the current per-tenant schema:

1. **Per-team / per-tournament / per-tenant `language`** — needed by the S02 `LocaleResolver` chain
   (`team.language ?? tournament.language ?? tenant.language ?? "de"`). All three surfaces must
   exist before the resolver can resolve them; this story creates the carriers, NOT the resolver
   (S02 owns the resolver impl).

2. **`tournament.organizer`** — captures the organizing club name on the certificate. Brief D-4
   mandates **snapshot-at-INSERT semantics**: at tournament creation time, the value is copied
   from the current per-tenant `tenants.display_name` value (read via JDBC against the
   bound per-tenant DataSource — same DataSource the INSERT uses) and persisted into the
   `organizer` column. The renderer reads the field directly thereafter; later edits to the
   tenant's display name do NOT propagate to existing tournament rows. The trade-off is
   documented in Brief T-3 (redundant in 99% of cases; user-directed for edit-flexibility on
   the V1+ follow-up edit-UI).

3. **`tenants.language`** — needed as the third fallback in the resolver chain. Brief v5 amendment
   (post cycle-1 review): the per-tenant schema has a `tenants` table inside each per-tenant H2
   file (`db/migration/tenant/V1__initial_schema.sql` lines 38–49) with a `display_name VARCHAR(255) NOT NULL`
   column. This is the **intra-DB carrier** for tenant identity within tenant context.
   `tenant-registry.json` (`TenantFileRegistry` line 81) is the **filesystem ROUTING carrier**
   (which per-tenant DBs to open). Per the architecture amendment confirmed by the human on
   2026-05-03, `tenant.language` lives **only** in the per-tenant `tenants` table (intra-DB
   column) — NOT in the JSON registry. `TenantRegistryPort.TenantRecord` stays at its current
   2-field shape `(UUID tenantId, String displayName)`; no extension.

**Brief v5 amendment summary** (closed in Discovery before backlog registration):
- D-4: snapshot source is `SELECT display_name FROM tenants WHERE id = ?` (intra-DB JDBC against
  the bound per-tenant DataSource) — NOT `TenantRegistryPort.lookup(...).displayName()`.
- D-5: language lives on 3 DB tables in the per-tenant H2 file (`tournament`, `team`, `tenants`);
  JSON registry (`tenant-registry.json`) is untouched.
- D-14: TenantRecord extension dropped — record stays 2-field; JSON registry stays unchanged.
- D-18 / S05: default-tenant bootstrap calls `TenantRegistryPort.register(UUID, String)` (existing
  2-arg overload) for the JSON entry AND separately INSERTs into the per-tenant `tenants` table
  (with `display_name` AND `language` from the bootstrap properties). No 3-arg `register` overload
  needed.
- O-15 corrected: tenant module **does** have a per-tenant Flyway pipeline; this story adds
  `db/migration/tenant/V2__e46s01_*.sql` to extend the `tenants` table.

**Why this story exists as a discrete unit (vs. inlined in S02–S05):** the data foundation must
land in one atomic commit so that downstream stories never see a half-applied schema (e.g., a
build with `tournament.organizer` present but `tournament.language` missing, or `tenants.language`
present but the snapshot path not wired). The snapshot-at-INSERT logic also belongs here, NOT in
S03 (assembler), because the assembler reads the `organizer` column directly at render time —
the column must already be populated for any tournament that exists when S03 is delivered.

**Hard sequencing constraint (Brief C-17):** this story depends on E45S06 done. E45S05 deletes
the 15 root `V*.sql` files and establishes the per-module Flyway layout under
`db/migration/{module}/Vn__*.sql`; E45S06 closes the DEC-21 §Deploy-pause and removes the last
INSERT/UPDATE-side `tenant_id` references and `Tournament.tenantId` field from production code.
Authoring the new migrations and snapshot logic before E45S06 done would either land them in the
soon-to-be-deleted root layer or against a still-present `tenant_id` column on the tournament
entity (which gets removed atomically by E45S06 — a moving target during S01 authoring).

**Verified module-edge alignment (Brief O-16):** `tournament/package-info.java:29` already
declares `@ApplicationModule(allowedDependencies = {"tenant"})`. The snapshot-at-INSERT logic
runs entirely intra-DB on the bound per-tenant DataSource — it does NOT call
`TenantRegistryPort.lookup(...)` from production code (the JSON registry is the routing carrier,
not the snapshot source). The cross-module FK from `tournament.location_id` to
`tenant/locations(id)` (established by `db/migration/tournament/V1__initial_schema.sql` lines
72–73) is part of the per-module Flyway dependency tree and is satisfied by tenant/V1 applying
before tournament/V1 — the new V2 migrations preserve this ordering.

**DEC-22 Iron Law:** delivery authors RED-first tests for every new behavioural surface
(snapshot-at-INSERT correctness, snapshot-at-INSERT does NOT trigger on UPDATE, snapshot
fail-fast when no tenants row exists). The schema-migration ACs are mechanical (column shape) and
do not require RED-first; the DAO IT verifies the migration produces the expected schema using
the DEC-26+DEC-46 helper-utility pattern.

**DEC-26 + DEC-46 DAO IT three rules:** the new DAO IT seeds the schema by applying both
`tenant/V1` AND `tournament/V1` AND the new `tenant/V2` AND `tournament/V2` (Rule 1 —
schema-from-production-migration), uses `assertj-db` to verify rows independently of the DAO under
test (Rule 2 — independent persistence verifier), and seeds fixtures via direct JDBC through the
per-module helper utility (`TenantDaoTestSupport.insertDirectly(...)`) — Rule 3, decoupled writes.
Crucially, the IT must seed **at least one `locations` row** (with the same UUID later used for
`tournament.location_id`) before the tournament INSERT, because `tournament.location_id` has a
NOT-NULL FK constraint to `tenant/locations(id)` (`db/migration/tournament/V1__initial_schema.sql`
line 72-73) — a tournament INSERT without a pre-existing locations row fails with FK-violation,
unrelated to the snapshot logic under test.

### Snapshot-at-INSERT logic for `tournament.organizer` (intra-DB JDBC source)

- [ ] **AC-INSERT-SNAPSHOT-FROM-TENANTS-DB [testing]:** When `DefaultTournamentRepository.save(...)`
      executes the INSERT branch (i.e., no row with the given id exists), it MUST populate the
      `tournament.organizer` column with the value of `display_name` from the bound per-tenant
      DataSource's `tenants` table — read via intra-DB JDBC (e.g., `SELECT display_name FROM
      tenants WHERE id = ?` bound to `TenantContext.current()`, OR equivalently
      `SELECT display_name FROM tenants` since the per-tenant invariant is exactly one row in
      that table). The query MUST run on the SAME DataSource the INSERT uses (no cross-module
      call, no `TenantRegistryPort.lookup(...)`). Verified by a fresh RED-first DAO IT that:
      (a) seeds a `locations` row directly via `TenantDaoTestSupport.insertDirectly(...)`;
      (b) seeds a `tenants` row via the same helper with `display_name = "Acme Sport Club"`;
      (c) invokes `repository.save(...)` on a fresh `Tournament` whose `id` is not present and
      whose `location_id` references the seeded location;
      (d) reads the persisted `tournament` row directly via assertj-db (NOT via the DAO under
      test, per DEC-26 Rule 2) and asserts the `organizer` column equals `"Acme Sport Club"`.

- [ ] **AC-DAO-IT-SEEDS-LOCATIONS-AND-TENANTS [testing][governance]:** The DAO IT MUST apply
      both per-module migrations (`tenant/V1` + `tenant/V2` + `tournament/V1` + `tournament/V2`)
      via the per-module helper utility (`TenantDaoTestSupport.applyMigration(...)` extended as
      necessary), AND seed at least one `locations` row AND at least one `tenants` row before
      any tournament INSERT. Without the locations seed, the tournament INSERT fails the
      `fk_tournament_location` FK constraint (`db/migration/tournament/V1__initial_schema.sql`
      lines 72-73); without the tenants seed, the snapshot SELECT returns empty and triggers
      AC-INSERT-MISSING-TENANTS-ROW-FAIL-FAST. The IT exercises the green path with both seeds
      present.

- [ ] **AC-INSERT-NO-DEFAULT-CLAUSE [governance]:** The tournament-V2 migration MUST NOT define
      a `DEFAULT` clause on `tournament.organizer`. The snapshot value is computed by application
      code at INSERT call-site, not by the database. (Rationale: the SELECT of `tenants.display_name`
      is application-layer logic, not a SQL-expressible default, and SQL DEFAULT clauses in H2
      cannot reference other tables.)

- [ ] **AC-UPDATE-DOES-NOT-RE-SNAPSHOT [testing]:** When `DefaultTournamentRepository.save(...)`
      executes the UPDATE branch (i.e., a row with the given id already exists), it MUST NOT
      modify the `organizer` column. Verified by a fresh RED-first DAO IT that:
      (a) inserts a tournament row directly with `organizer = "Original Club"` via the test
      helper-utility's `insertDirectly(...)` (DEC-26 Rule 3);
      (b) seeds the `tenants` table with a DIFFERENT `display_name` value (e.g.,
      `"Renamed Club"`);
      (c) invokes `repository.save(...)` on a `Tournament` whose `id` matches the seeded row
      (triggers UPDATE branch);
      (d) reads the row back via assertj-db and asserts `organizer` is still `"Original Club"`
      (NOT `"Renamed Club"` — i.e., the UPDATE did not re-snapshot). The corresponding
      `UPDATE_SQL` constant in `DefaultTournamentRepository` does NOT include `organizer=?` in
      its SET clause.

- [ ] **AC-INSERT-MISSING-TENANTS-ROW-FAIL-FAST [error-handling][testing]:** If the snapshot
      SELECT against the `tenants` table returns NO rows at INSERT time (invariant violation
      under DEC-5: every tenant has at least one tenants row in its per-tenant DB), the
      `save(...)` call MUST fail-fast with a typed runtime exception (e.g., `IllegalStateException`
      with a message naming the missing-tenants-row condition; story-author chooses the exact
      exception type RED-first per DEC-22) AND no tournament row may be persisted. The DAO IT
      verifies: (a) seed a `locations` row but NO `tenants` row (or delete the seeded `tenants`
      row); (b) invoke `repository.save(...)`; (c) assert the typed exception is thrown; (d)
      assert via assertj-db that the `tournament` table row count is unchanged.

### Locale-data integrity

- [ ] **AC-LANGUAGE-COLUMN-ACCEPTS-ISO-639-1 [i18n]:** The three `language` columns
      (`tenants.language`, `tournament.language`, `team.language`) accept ISO-639-1 strings

      2-character code; the extra capacity accommodates future BCP-47-style extensions like
      `"de-DE"` if a follow-up story widens the contract — V1 stores only ISO-639-1).

- [ ] **AC-LANGUAGE-COLUMN-NO-V1-VALIDATION [i18n]:** V1 does NOT enforce the ISO-639-1 format at
      the database, application, or repository layer. A row with `language = "qq"` (non-existent
      code) is accepted; the resolver in S02 treats it as an unknown locale and falls back to the
      default per the standard MessageSource resolution chain (Brief D-15). Validation is a
      potential follow-up story; this story does NOT add it.

- [ ] **AC-LANGUAGE-COLUMN-NULL-SEMANTICS [i18n][error-handling]:** `language = NULL` is a valid
      and expected value at all three carrier sites. NULL semantics: "fall through to the next
      surface in the resolver chain" (Brief D-6). This story does NOT change any production
      reader of these columns to treat NULL as an error; it merely creates the columns and
      documents the semantics.

## Notes

**Architecture amendment (Brief v5, post-cycle-1 review).** The original Brief v4 (D-5, D-14,
O-15) assumed the tenant module had no Flyway pipeline and that `tenant.language` would live in
the `tenant-registry.json` file. Cycle-1 review surfaced the empirical reality:
`db/migration/tenant/V1__initial_schema.sql` exists post-E45S05 with a `tenants` table that has
a `display_name VARCHAR(255) NOT NULL` column; the `tenant-registry.json` is the routing-layer
carrier (which DBs to open) and the per-tenant `tenants` table is the intra-DB carrier (one row
per per-tenant H2 file representing this tenant). Per the human-confirmed amendment on
2026-05-03:
- `tenant.language` lives in the per-tenant `tenants` table column added by this story (NOT in
  the JSON registry).
- The snapshot source for `tournament.organizer` is intra-DB JDBC against `tenants.display_name`
  (NOT a cross-module call to `TenantRegistryPort.lookup`).
- `TenantRegistryPort.TenantRecord` stays at the 2-field shape; no 3-arg `register` overload is
  added.
- The architecturally cleaner pattern (single carrier per DB context, no dual-carrier sync
  responsibility) was chosen.

**Sequencing against E45S06 (HIGH-3 fix).** This story is authored against the post-E45S06
baseline:
- `Tournament.tenantId` field has been removed (E45S06 AC-ENTITY-TENANT-ID-REMOVED).
- `DefaultTournamentRepository.INSERT_SQL` no longer references `tenant_id` (E45S06
  AC-INSERT-TENANT-ID-REMOVED-TOURNAMENT).
