# Story E15S06: @ApplicationModule(allowedDependencies = {"tenant"}) annotation + ApplicationModulesTest updated

## User Story

**As a** reviewer of the Pilot's Modulith compliance,
**I want** the new `auth` context declare its sole allowed dependency on `tenant` via `@ApplicationModule(allowedDependencies = {"tenant"})`, with the ApplicationModulesTest verifying boundaries are now meaningfully enforced,
**so that** any future change attempting to import from `de.vvwt.tm.tenant.internal.*` into `de.vvwt.tm.auth.*` fails `verify()` at build time.

---

## Context

Through E15S01–S05, the new `auth` code lives at `de.vvwt.tm.auth` + `de.vvwt.tm.auth.internal` with no Modulith annotation. This story makes the boundary real: a `package-info.java` on `de.vvwt.tm.auth` declares `@ApplicationModule(allowedDependencies = {"tenant"})`, and `ApplicationModulesTest` (from E13S01) now verifies this annotation against the new code.

Per DEC-21, this is the first real `@ApplicationModule` with a non-empty `allowedDependencies` in the codebase. `tenant` (annotated in E14S01) was a leaf module with `allowedDependencies = {}`. This story is the proof that dependency declaration + cross-module consumption work end-to-end.

Per DEC-22, a deliberate violation test is run as a spike (not committed) to confirm `verify()` actually catches boundary breaches — if this spike does not fail, the whole Modulith setup is broken.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first for annotation effect): Before the `@ApplicationModule(allowedDependencies = {"tenant"})` annotation is added, a deliberate-violation spike (uncommitted; documented in Delivery plan) proves that the current unannotated state ALLOWS an `auth.internal` file to import from anywhere — i.e., the annotation matters. Then the annotation is added, and the same violation now fails `verify()`. Git history shows the annotation's effect was proven before merge.

- [ ] AC2 (governance — annotation placement): `vvwt-tm-web/src/main/java/de/vvwt/tm/auth/package-info.java` contains `@org.springframework.modulith.ApplicationModule(allowedDependencies = {"tenant"})` (exact FQN or import as Delivery prefers). No other packages are annotated in this story.

- [ ] AC3 (testing — ApplicationModulesTest green with annotation): `ApplicationModulesTest` from E13S01 remains green with the annotation present and no boundary violations in the new `auth` code. `mvn verify` succeeds.

- [ ] AC4 (error-handling — legacy auth does NOT break verify): The legacy `de.vvwt.tm.auth.*` package (without the new annotation, contains the legacy `AdminCredentialsBootstrap` et al.) continues to work because Modulith treats annotated and unannotated packages coherently — the legacy classes live in the same root `de.vvwt.tm.auth` package as the new ones, so they fall under the same annotation. A Delivery-plan check confirms no legacy import violates the `{"tenant"}` constraint (in practice legacy `auth` uses `JdbcTemplate` directly via Spring, no `de.vvwt.tm.tenant.internal.*` imports). If an unexpected violation surfaces, escalate before merging.

- [ ] AC5 (security — deliberate violation spike): Delivery runs a pre-merge spike adding a throwaway import from `de.vvwt.tm.auth.internal.PasswordGenerator` attempting `import de.vvwt.tm.tenant.internal.SomeClass`; `ApplicationModulesTest` fails as expected. The spike is removed before merge and documented in the Delivery plan. This is the proof-of-enforcement moment for the whole Pilot.

- [ ] AC6 (testing — dependency consumption verified): A positive test confirms the new `auth` code DOES successfully import and use types from root package `de.vvwt.tm.tenant` (e.g., `TenantContext`, `TenantDataSourceResolver`). The `ApplicationModulesTest` does not object. This confirms `allowedDependencies = {"tenant"}` is neither too loose nor too tight.

- [ ] AC7 (governance — no other annotations added): This story does NOT annotate any other package (no `tournament`, `scoring`, etc.). `git diff` shows the one `package-info.java` addition plus any minor documentation updates. All other Wave-1 contexts remain Wave-2 scope.

## Notes

AC5 — the deliberate-violation spike — is the single most important test of the Modulith adoption's actual effectiveness in Wave 1. If it does not fail, the Modulith setup is broken, and E13S01's `ApplicationModulesTest` was never truly enforcing anything. Do not shortcut.

The legacy + new coexistence in the same root package (AC4) is the atypical coexistence under reconstruction-in-place: normally new code sits in a "staging name" package per DEC-21 recommendation. Delivery may have chosen to keep both in the same root with the new classes differentiated only by `internal/` sub-package; either choice works, but the Delivery plan must document which path was taken and confirm legacy classes do not violate `allowedDependencies`.
