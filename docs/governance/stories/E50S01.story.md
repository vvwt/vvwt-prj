# Story E50S01: Fix — Display SPA reactivity from `noPhase` state on tournament/phase activation

## User Story

**As a** Tournament Operator running a connected display device,
**I want** the display to transition from "kein Turnier aktiv" to the active overview within a few seconds after I activate a tournament and/or phase from the admin app — without me having to manually reload the display device's page,
**so that** I do not have to walk to every display station and refresh the browser at every status transition during a live tournament.

---

## Context

The display SPA's reactivity is structurally broken when the device starts up before the operator has activated a tournament or phase. The display's WebSocket connection is gated on a successful initial REST fetch — and the polling fallback is gated on WebSocket reconnect-attempt exhaustion. In the `noPhase` error state, neither path is reachable.

User-observable symptom (manual end-to-end test 2026-05-08): the display starts with "kein Turnier aktiv". The operator activates the tournament from the admin app (DRAFT → ACTIVE) — the display does not change. The operator activates a phase (PENDING → PREPARED → ACTIVE) — the display does not change. Only manually reloading the display device's page produces the expected layout (3-field grid with `Feld 1` / `Feld 2` / `Feld 3` headers).

### Verified mechanism (Discovery investigation 2026-05-08)

- `vvwt-tm-web/src/main/ui-display/src/App.svelte:293-303` — `wsConnect(token, phaseData.tenantId, …)` is invoked only inside `if (phaseData !== null && errorType === null)`. The WebSocket subscription is therefore tenant-scoped: it requires a `tenantId` field that is supplied by `fetchPhaseOverview()`. In the `noPhase` errorType, `phaseData` stays `null` and no WebSocket connection is ever established.
- `vvwt-tm-web/src/main/ui-display/src/App.svelte:215-241` — the polling fallback (`activatePollingFallback`) is invoked only via the `onFallback` callback that `wsConnect` triggers after the WebSocket reconnect-attempt budget (5×) is exhausted. In the `noPhase` state the WebSocket was never connected, so the fallback callback is never reached. The polling fallback that was designed to recover from WebSocket failures cannot recover the display from `noPhase`.
- `vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/events/` contains exactly four event classes (DeviceRegisteredEvent, LapAdvancedEvent, MatchResultChangedEvent, PhaseStatusChangedEvent) and `DomainEventBridge.java:67-207` has exactly four `@EventListener` methods. There is no `TournamentStatusChangedEvent` and no listener for it. The tournament DRAFT → ACTIVE transition is therefore never broadcast, even to display devices that are already subscribed.

### Scope posture

This is a producer-side fix at the display-SPA reactivity boundary. Discovery does NOT prescribe the fix shape. Three viable directions are listed in the Brief (H-2): (a) publish a `TournamentStatusChangedEvent` and let the display subscribe to a tenant-scoped topic resolved from the device token before any phase exists; (b) activate REST polling in the `noPhase` state independent of WebSocket health; (c) introduce a device-token-resolved "any-tenant-event" topic and connect the WebSocket on display mount before any phase exists. Delivery selects within the AC envelope.

## Acceptance Criteria

- [ ] **AC-TEST-DISPLAY-REACTS-TO-TOURNAMENT-ACTIVATION-RED** (testing): RED-first integration test (Vitest end-to-end against a stubbed REST + WebSocket backend, OR Playwright, OR equivalent) — given a display device that starts up while no tournament is `ACTIVE` (so the initial fetch returns the `noPhase` error), when the backend transitions a tournament to `ACTIVE` (state change visible to the test environment), then within a bounded latency budget (≤ 10 s wall-clock) the display SPA exits the `noPhase` error state and renders the overview layout — without any user-driven page reload during the test. Test fails before fix because no reactivity path exists from `noPhase`.
- [ ] **AC-TEST-DISPLAY-REACTS-TO-PHASE-ACTIVATION-RED** (testing): RED-first — same harness as AC1 but the trigger is a phase transition (PENDING → PREPARED → ACTIVE) on an already-ACTIVE tournament. Display starts in `noPhase` (e.g., tournament ACTIVE but phase still PENDING with zero scheduled matches → `resolveDisplayablePhase` throws `NoActivePhaseException`); when the phase transitions to ACTIVE, the display recovers within the same latency budget without a manual reload.
- [ ] **AC-TEST-DISPLAY-REACTIVITY-WS-CONNECTED-GREEN** (testing): regression — given a display device in the connected/active state (not `noPhase`), when phase status events fire, the existing E07S06 reactivity (refresh on PHASE_STATUS_CHANGED, MATCH_RESULT_CHANGED, LAP_ADVANCED) continues to behave as designed. Verifies the fix does not regress the already-working hot-path.
- [ ] **AC-TEST-DISPLAY-REACTIVITY-NO-DOUBLE-CONNECT** (testing): regression — when the display recovers from `noPhase` to the active overview, exactly one WebSocket connection is active (no leaked connection from a pre-recovery state, no double-subscription). If the fix shape uses polling, exactly one polling timer is active. Verified by counting active connections / timers in the test harness.
- [ ] **AC-IMPL-DISPLAY-REACTIVITY-FROM-NOPHASE**: after the operator activates the tournament and/or phase, the display SPA MUST transition from the `noPhase` error state to the active overview state within a bounded latency budget (the AC1/AC2 budget). The fix shape is at Delivery's discretion: candidates include (i) publish a `TournamentStatusChangedEvent` + add a device-token → tenantId resolution endpoint enabling pre-phase WebSocket subscription, (ii) activate REST polling in the `noPhase` state independent of WebSocket health, (iii) a device-token-resolved "any-tenant-event" topic. The chosen approach is documented in the impl-report. ANY shape that satisfies AC1, AC2, AC3, AC4 GREEN is acceptable.
- [ ] **AC-IMPL-LATENCY-BUDGET**: the latency from "operator clicks Aktivieren" to "display has rendered the active overview" is ≤ 10 s wall-clock under nominal LAN conditions. This budget covers the operator's perception of "near-immediate". Polling-based fixes MUST poll at an interval ≤ 5 s to satisfy this.
- [ ] **AC-IMPL-DEC-2-STACK**: the fix uses Vite + Svelte (no SvelteKit) + TypeScript per DEC-2. No new SPA framework, no new state-management library beyond what is already in use. Existing `@stomp/stompjs` + `sockjs-client` are reused if the fix uses WebSockets.
- [ ] **AC-IMPL-DEC-5-MULTI-TENANT**: the fix preserves DEC-5 multi-tenant isolation. If the fix shape introduces a pre-phase WebSocket subscription (option a or c), the topic MUST be tenant-scoped — the device must subscribe ONLY to events for its own tenant, resolved from the device token at handshake time per DEC-24. No cross-tenant leakage.
- [ ] **AC-IMPL-DEC-16-LAN-SAFE**: the fix preserves DEC-16 LAN-safe operation — no new external service dependency, no internet round-trip, no new public DNS lookup. WebSocket / polling endpoints remain relative to the serving host.
- [ ] **AC-ERROR-HANDLING-401-DURING-RECOVERY** (error-handling): if a recovery REST poll or WebSocket subscription returns 401 (device token revoked or expired), the display redirects to `/display/register` per existing `App.svelte:230-234` semantics. No silent loop, no infinite retry. Vitest verifies the redirect.
- [ ] **AC-ERROR-HANDLING-RECOVERY-FAILURE** (error-handling): if the recovery channel (WebSocket or polling) encounters a transient network error (5xx, timeout), the display continues to show the `noPhase` error panel with the existing retry button, AND the recovery channel keeps attempting at a backoff or fixed interval. The display does NOT silently appear stuck (no spinner forever). Vitest verifies the retry posture.
- [ ] **AC-SECURITY-DEVICE-TOKEN-AUTH-PRESERVED** (security): the fix MUST NOT introduce any new auth surface that bypasses the existing display device-token auth (DEC-24). Any new endpoint (e.g., a tenant-resolution-from-token endpoint, if the fix needs one) requires the device token in the request and returns 401 without it. Verified by a security IT.
- [ ] **AC-SECURITY-NO-CROSS-TENANT-LEAKAGE** (security): if the fix introduces any new event publication, the topic and the message body MUST be tenant-scoped or contain `tenantId` such that frontend filtering or topic isolation prevents a device on tenant A from receiving an event from tenant B. Verified by an IT that exercises two tenants concurrently.
- [ ] **AC-GOVERNANCE-DEC-22-RED-FIRST** (governance): all RED-first tests (AC1, AC2) precede any production-code change in commit history; commits show RED-subcommit before GREEN-subcommit per Iron Law. Memory `feedback_dec22_refactor_phase_first.md` applies — legacy code (App.svelte WebSocket gating, DomainEventBridge listeners, TournamentLifecycleService) requires Q-1a TDD RED-first; refactor-clause is NOT invoked.
- [ ] **AC-GOVERNANCE-DEC-44-OR-DEC-38-CONTROLLER-IT-FRAMEWORK** (governance): controller integration tests use the framework appropriate to the module they live in. **DEC-44 D1 (web-module)**: ITs in `de.vvwt.tm.web.*` use `@SpringBootTest(RANDOM_PORT, classes=TournamentManagerApplication.class) + @ActiveProfiles("test") + @Import({WebModuleTestConfig.class, ...})`. **DEC-38 Clause A (bounded-context module)**: ITs inside a bounded-context module (e.g. `de.vvwt.tm.display.*` or `de.vvwt.tm.tournament.*`) use `@ApplicationModuleTest(...)`.
