# Story E37S03: WorkerKeyManager + WorkerCapabilityProvider extension + D-4 hybrid keypair-mismatch mechanic in vvwt-slotopt-worker-lib (Q-1a TDD RED-first)

## User Story

**As a** worker (vvwt-slotopt-standalone-worker today; E38-rebuilt vvwt-slotopt-standalone-worker later) participating in the slot-optimization compute network,
**I want** the WorkerKeyManager interface to declare which signature algorithm I'm using (`algorithmId() → String`), a separate WorkerCapabilityProvider interface to advertise my supported algorithm set to the dispatcher (`supportedAlgorithms() → Set<String>`), and an automatic startup-time keypair-mismatch handling mechanic per Brief D-4 hybrid (i)+(iii),
**so that** the dispatcher can route packets correctly based on my advertised capabilities, future PQC-capable workers can declare ML-DSA support, and an operator changing the configured algorithm triggers a clean key-rotation OR a defensive refuse-to-start (preventing accidental dual-identity).

---

## Context

Per Brief O-6: WorkerKeyManager interface from E35S02 currently single-algorithm: `signResult(byte[]) → byte[]`, `getPublicKeyBytes() → byte[]`, `rotateKeypair() → KeyRotationResult`. E37 extends this by adding `algorithmId() → String` AND introducing a sibling interface WorkerCapabilityProvider for capability advertisement.

Per Brief D-4 (hybrid mechanic, user-confirmed):
- Keypair files carry algorithm suffix: `worker-Ed25519.key`, `worker-Ed25519.pub`
- At startup: worker looks for files matching the configured algorithm
- If files exist for OTHER algorithms only (none for configured) → log warning, delete old files, generate fresh keypair, re-register against dispatcher (new worker_id)
- If files exist for OTHER algorithms AND for the configured algorithm (mixed state) → REFUSE-TO-START with explicit ERROR; operator must manually clean up
- If files exist only for configured algorithm → normal startup, no rotation

Per Brief C-11: this discipline is V1 worker-implementation responsibility, not dispatcher-side enforceable. Heavy logic lives in `DefaultWorkerKeyManager` (vvwt-slotopt-worker-lib) per Brief S-5.

This story is authored against the E37S02 spec (section (a) shared concerns and (d) algorithm-agility extensions). No legacy `vvwt-dispatcher` source inspection per Brief C-16.

- [ ] **AC-D4-CLEAN-OTHER-ONLY-DETECTED**: Test scenario — startup with files present for algorithm X (e.g., `worker-OldAlgo.key/pub`) but configured for algorithm Y (e.g., `worker-Ed25519.key/pub` absent): WorkerKeyManager logs WARNING, deletes the OldAlgo files, generates fresh Ed25519 keypair, signals "new registration required" to caller. ## Notes

- **Risk**: D-4 mechanic introduces operational behaviour (auto-delete + refuse-to-start) that must be deployable correctly. RED tests must cover each of the three states (clean-other-only, mixed, configured-only).
- **Q-5 alignment**: refuse-to-start posture is "defensive fail-safe over silent recovery" — operator-friction preferred over silent key disposal.
- **Backward-compat**: V1 WorkerCapabilityProvider default impl returning `Set.of("Ed25519")` enables the dispatcher's V1 backward-compat fallback per D-2 (missing `supportedAlgorithms[]` field on pull-packet → dispatcher treats as `["Ed25519"]`).
- **Forward-use**: future PQC-capable workers will provide their own WorkerCapabilityProvider implementations returning multi-element sets (e.g., `Set.of("Ed25519", "ML-DSA-65")`).
