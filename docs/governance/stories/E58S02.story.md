# Story: Team-distribution registry — Team2AvatarDistributor strategy, DistributionMode enum removed

## User Story

**As a** tournament organizer,
**I want** the team-to-avatar distribution shapes to be selected through the same registry mechanism as match generators,
**so that** a new distribution shape can be added as a self-contained class without editing a core enum or branch.

---

## Context

Team-to-avatar distribution today has no registry: `DefaultPhaseTransitionService.computePhase1Proposals`
branches inline on the `DistributionMode` enum (`SEQUENTIAL` / `ROUND_ROBIN`) when computing the Phase-1
team-assignment proposal. DEC-73 (D-2, D-4) extracts this into a `Team2AvatarDistributor` strategy interface
plus a `Team2AvatarDistributorRegistry` — mirroring the match-generation registry — and removes the
`DistributionMode` enum so `DraftSection.distributionMode` is a registry string-key.

This story is behaviour-preserving for the DEC-59 operator-confirmation team-assignment workflow: the
distributor computes the same proposal it does today; `teamId` is still written only at operator confirmation.

---

## Acceptance Criteria

- [ ] AC1 (governance): a `Team2AvatarDistributor` strategy interface exists — a registry-key accessor plus a team-to-avatar-slot distribute operation — placed in the bounded-context public package per the DEC-35 layout.
- [ ] AC2 (governance): a `Team2AvatarDistributorRegistry` exists, dispatching by string key (analogous to `MatchGeneratorRegistry`); the registry and the strategy interface satisfy the DEC-58/DEC-72 interface mandate and the E57S04 build-time guard passes.
- [ ] AC3 (testing): two `Team2AvatarDistributor` implementations exist, one per current distribution shape (`sequential`, `round_robin`); each is registered under its key and resolvable from the registry. Verified by tests authored failing-first per DEC-22.
- [ ] AC4 (testing): the inline `DistributionMode` branching in `DefaultPhaseTransitionService.computePhase1Proposals` is replaced by registry dispatch; for both `sequential` and `round_robin`, the observable Phase-1 proposal output is identical to the current behaviour. The equivalence is verified by fresh RED-first tests that re-specify the proposal semantics — not by a characterization test (forbidden by DEC-22).
- [ ] AC5 (governance): the `DistributionMode` enum is removed; `DraftSection.distributionMode` is a String registry-key; no reference to `DistributionMode` remains in `vvwt-tm-web` (fresh audit at delivery HEAD).
- [ ] AC6 (governance): an unregistered `distributionMode` key is rejected fail-fast in the `DraftConfig` / `DraftSection` validation path — given a draft whose `distributionMode` is not a registered `Team2AvatarDistributor` key, when the draft is saved or applied, then it is rejected with an operator-actionable error. Verified by test.
- [ ] AC7 (testing): Delivery first verifies, at delivery HEAD, whether `TeamAvatarRepository` already exposes a batch (or loop-able single-row) save sufficient for persisting a list of avatars; if so it is used and no new method is added. If none suffices, `TeamAvatarRepository` gains a batch `save(List<TeamAvatar>)` write method. The batch save — added or reused — has a genuine production (non-test) callsite, the avatar-persistence path that persists the distributed avatars, and is not a test-only member (DEC-70). Persistence of distributed `TeamAvatar` instances happens outside the distributor; the batch save preserves the DEC-9 structural identity `(phaseId, groupNumber, groupPosition)`. Verified by a DAO integration test following the DEC-46 three rules: schema loaded from the production migration; written state verified independently via assertj-db; read-path fixtures inserted via direct JDBC, not via the DAO's own write methods.
- [ ] AC8 (testing): TDD per DEC-22 — every new class and method has a failing test authored before the production code.
- [ ] AC9 (governance): `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54); the `DistributionMode` removal leaves no compiler warnings or unused imports (DEC-29 / DEC-30).
- [ ] AC10 (governance): the DEC-59 operator-confirmation team-assignment workflow is behaviour-unchanged — no `teamId` is written by any `Team2AvatarDistributor` implementation or by the Phase-1 proposal-computation path; `teamId` is written only by the operator-confirmation handler. Verified by test.

> All acceptance criteria must be verifiable.
