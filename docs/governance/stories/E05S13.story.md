# Story E05S13: Tournament create — flip refereeAssignment default `false → true` for auto-seeded teams + UI add-row (in-app paths only)

## User Story

**As an** organizer setting up a new tournament,
**I want** every team that comes pre-populated at tournament create — and every team I add manually via the Teams grid — to default to "stellt Schiedsgericht" (refereeAssignment = true),
**so that** I don't have to flip the Schiedsrichter-checkbox on every team in the standard "Mannschaft = Schiedsgericht" tournament setup, and the most common manual-add case (external referee) only requires toggling the participate flag instead of two flags.

---

## Context

E05S12 (`POST /api/tm/tournaments` auto-seed of N empty team rows) deliberately set `participate=true, refereeAssignment=false, withoutAssessment=false` as the seed default (E05S12 AC-IMPL-DEFAULT-FLAGS, codified in `DefaultTournamentService.java:288` and `Teams.svelte:164`). The user has confirmed during Discovery 2026-05-11 that the `false` value for `refereeAssignment` was domain-incorrect: the standard volleyball-tournament rule is "Mannschaft = Schiedsgericht" — every participating team supplies a referee for matches in which it is not playing. The auto-seeded N teams are exactly those participating teams, so they should default to providing a referee.

The user explicitly chose to scope the flip to **two in-application paths** (Auto-Seed + UI Add-Row), with the REST DTO default and the DB column DEFAULT intentionally left at `false`. The asymmetry is documented and rationalized below.

This Story **supersedes the literal phrase `refereeAssignment=false`** in E05S12 AC-IMPL-DEFAULT-FLAGS for the seed-loop assertion only — no DEC amendment, no new DEC.

### Multi-path asymmetry catalogue (post-change state)

| # | Path | Default before | Default after | Scope |
|---|------|---------------|---------------|-------|
| P1 | Auto-seed at `POST /api/tm/tournaments` (`DefaultTournamentService.createTournament` line 288) | `false` (explicit setter) | **`true`** (explicit setter) | **IN** |
| P2 | UI manual "Mannschaft hinzufügen" (`Teams.svelte:164` `openAddRow`) | `false` (explicit object literal) | **`true`** (explicit object literal) | **IN** |
| P3 | REST `POST /api/.../teams` field omitted (`TeamCreateRequest.resolvedRefereeAssignment()` line 57) | `false` | `false` (UNCHANGED) | OUT |
| P4 | Java `new Team()` constructor with no setter (entity field initial value at `Team.java:59`) | `false` (JVM default) | `false` (UNCHANGED) | OUT |
| P5 | DB INSERT omitting `referee_assignment` column (`V1__initial_schema.sql:130`: `BOOLEAN NOT NULL DEFAULT FALSE`) | `false` | `false` (UNCHANGED) | OUT |

P3, P4, P5 stay at `false` by user decision. **P5 is never exercised by application code** — `DefaultTeamRepository.save()` (line 35) issues a parameterized INSERT that explicitly lists `referee_assignment` in the column list with the entity's value, so the DB DEFAULT clause functions only as belt-and-braces for hand-crafted SQL INSERTs.

### External-referee use-case (D-2 alignment with O-7 / O-10)

E05S12 backlog notes record: *"Es können mehr als diese Teams angelegt werden, wenn es z.B. externe Schiedsrichter gibt"*. External referees are typically `participate=false, refereeAssignment=true`. With the **new** UI defaults (`participate=true, refereeAssignment=true`), the operator now toggles only `participate=false` for an external referee — `refereeAssignment` is already correct. The new UI default reduces clicks for the most-cited manual-add case.

### Lost case (acknowledged, not regressed)

A manually-added team that is **neither participating nor a referee** (e.g., a placeholder for a withdrawn team) now requires toggling **both** `participate=false` AND `refereeAssignment=false` — one extra click vs. today. This is a minority case relative to the external-referee use-case and is accepted as a deliberate trade-off (Brief T-2).
