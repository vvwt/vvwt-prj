# Story E55S10 (Bug-Triage): M-2/M-3-regression + M-5 (Phase-2 match-deletion) + Display-token-loss bug class persists post-E55S09 — race condition above H2 layer (HikariCP / Spring TX / JVM memory model); empirically narrowed via TRACE_LEVEL_FILE=3 masks + AUTO_SERVER=TRUE does NOT fix; structural Diagnose via standard-SPI instrumentation (HikariCP MetricsTrackerFactory + Spring AOP on TransactionSynchronizationManager) — no new agent-attach tooling (BTrace/JFR-agent OUT OF SCOPE); H-1 stopgap (maximumPoolSize=1 per tenant) as stair-2 before T-1 PostgreSQL migration escalation; structural fix path may require DEC-15/DEC-20 amendment (PostgreSQL migration evaluated as T-clause)

## User Story

**As a** Tournament Manager operator,
**I want** the application's in-memory state and persistent DB state to remain consistent during a normal operator workflow (apply Phasenplan → team-zuordnung → Phase aktivieren → register Display → configure Display) such that previously-committed transitions (Phase ACTIVE, Tournament ACTIVE, Phase 2 matches present, Display device-row present) do not silently disappear,
**so that** the Display device, Print-URL, Phasenübersicht, and all REST-API consumers see a consistent, monotonically-progressing tournament state — instead of the current behavior where Phase 1 reverts ACTIVE→PREPARED, Phase 2 loses its 18 generated matches, Tournament reverts ACTIVE→PLANNED, and the Display SPA's device_token becomes invalid mid-session.

### Empirical hypothesis triage

| Config | Bug reproduces? | Hypothesis status |
|---|---|---|
| Default (AUTO_SERVER=FALSE, WRITE_DELAY=default-500ms) | YES | Baseline |
| `TRACE_LEVEL_FILE=3` (synchronous trace.db writes on every H2 internal op) | **NO** | TRACE serializes H2-internal I/O enough to mask the race; not a fix candidate (heavy I/O cost), but confirms race-condition diagnosis |
| `AUTO_SERVER=TRUE` (H2 internal TCP-server serializes all pool connections) | **YES** | H2-internal write-serialization is NOT sufficient → race is ABOVE H2's connection-handling layer |

**Conclusion**: race condition is **in the Java/Spring/HikariCP layer**, not in H2's MV-Store internal concurrency. The TRACE_LEVEL_FILE=3 masking happens because synchronous file I/O during every internal operation slows the race window past the application's typical timing.

### Candidate hypotheses (Java/Spring layer) — to be empirically narrowed by Delivery

**H-1 (HikariCP Pool Connection Reuse + Stale Visibility State)**: HikariCP returns a connection to the pool after `connection.commit()`. The next thread to check-out this connection sees its `Connection` state. If the JVM Memory Model (JMM) visibility guarantees don't hold across HikariCP's pool-return + pool-acquire boundary, a thread could observe a connection that's "logically committed" but where the committed data isn't yet visible to subsequent SELECTs. Unlikely with default HikariCP (which uses proper synchronization), but possible with specific concurrency patterns + H2's MVCC model.

**H-2 (Spring TransactionManager Nested-TX Boundary)**: The orchestrator's `@Transactional(REQUIRES_NEW)` creates a new TX from inside a HikariCP connection. If Spring's `DataSourceTransactionManager` mishandles the nested TX (e.g., suspends the outer TX but doesn't fully isolate the inner), commits on the inner could be invisible to subsequent reads on the outer-TX connection. Specifically: applyDraft's outer TX commits + schedules `afterCommit` drainNext → orchestrator's REQUIRES_NEW commits its writes → operator-driven HTTP threads reads → may not see orchestrator's commits if connection-pool-aliased.

**H-3 (Java Memory Model + Cached DataSource State)**: `TenantFileRegistryDataSourceResolver` caches per-tenant DataSources in `ConcurrentHashMap`. If a DataSource is recreated under specific conditions (e.g., due to error recovery), threads holding the cached reference might write to the OLD DataSource while reads go through the NEW one. The OLD DataSource's writes are then orphaned (the H2 file is shared but H2 has session-level visibility that doesn't sync across two DataSource pools targeting the same file with AUTO_SERVER=FALSE).

**H-4 (HikariCP `autoCommit` Default Disagreement)**: HikariCP default `autoCommit=true`. Spring's `@Transactional` sets `connection.setAutoCommit(false)` for the TX, then resets to `true` on TX end (via `DataSourceUtils.resetConnectionAfterTransaction`). If the reset doesn't fire (exception during commit), the connection stays at `autoCommit=false` and subsequent statements in OTHER threads (after pool-return) might enter implicit-transactions that never commit. **This is a known HikariCP/Spring failure mode under specific exception patterns.**

**H-5 (Spring Modulith Event Replay)**: Despite DEC-64 superseding the events-only pattern, `PhaseStatusChangedEvent` survives for STOMP UI broadcast (DEC-64 D-13). If Spring Modulith's `EventPublicationRegistry` persists undelivered events on shutdown OR a different lifecycle event triggers replay, a stale event handler might write back outdated phase state. Discovery cycle-3 listed this as H-E; static audit found no handler that mutates DB state from `PhaseStatusChangedEvent`, but the replay mechanism itself may have side effects.

**H-6 (H2 File-Mode Multi-DataSource Race despite AUTO_SERVER=TRUE)**: With AUTO_SERVER=TRUE, the first JVM-internal connection auto-starts a TCP server. Subsequent connections from the same JVM may use the file-mode connection OR the TCP-server-mediated connection inconsistently — depending on HikariCP pool order. If 2 connections from the same pool target the same file but one is direct-file and one is TCP-mediated, H2 might silently de-duplicate sessions in a way that loses data. Discovery considers this less likely but not eliminated by the AUTO_SERVER=TRUE empirical test.

### What Discovery cannot eliminate without further empirical work

Static audit + 3 reproductions narrowed the bug to "race in Java layer above H2 connection-handling". Further narrowing requires runtime instrumentation that Discovery cannot author from the diagnostic surface available in this session. Delivery is the right surface for the instrumentation work — using **standard JDK + Spring + HikariCP SPIs only** (no new agent-attach tooling like BTrace or JFR-agent which would require new project dependencies per cycle-1 Tier-2 finding F-6f) — because:
- It requires hot-deploying instrumentation into the running JVM during a live reproduction
- It requires correlation between bytecode-level operation traces and the H2 internal state
- It requires per-thread connection lifecycle tracing (HikariCP `LeakDetectionThreshold` + custom logging at acquire/release boundaries)
