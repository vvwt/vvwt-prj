# Story E31S03: DefaultScoringService TDD reconstruction with per-tournament DB-lock + CascadeLockIT RED-first

## User Story

**As a** maintainer of the new `de.vvwt.tm.scoring` Modulith module,
**I want** the `ScoringService` interface authored in
`de.vvwt.tm.scoring.ScoringService` (public) and a `DefaultScoringService`
implementation authored in
`de.vvwt.tm.scoring.internal.DefaultScoringService` via strict
TDD-first reconstruction (every public method preceded by a failing
test), with the per-tournament pessimistic DB row-lock
(`tournamentRepository.findByIdForUpdate(input.tournamentId())`)
acquired as the FIRST action of `registerMatchResult(...)`, and with
`CascadeLockIT` authored RED-first to prove that two parallel set-
result submissions for the same tournament execute serially without
lost-update on Phase auto-advance or TeamAvatarRating refresh,
**so that** the legacy `de.vvwt.tm.domain.CascadeRecomputeService`
becomes safely deletable in E31S04, and so that cross-court concurrent
score submissions can no longer cause silent lost updates.

---

## Context

E31S03 is the central reconstruction story of E31. Per Brief D-π S-6
and per the user's ESC-3 decision (Reconstruction-in-Place, NOT move
— DEC-22 §Decision Reconstruction-in-Place pattern), the legacy
`de.vvwt.tm.domain.CascadeRecomputeService` (596 LOC) is used ONLY as
a functional template; the new code is authored from scratch in the
new `de.vvwt.tm.scoring` Modulith module (declared in E31S02).

The 13-step cascade flow (per the legacy class's Javadoc lines 43-44)
is reconstructed step-by-step under DEC-22 Iron Law. Each public
method of `ScoringService` (initially: `registerMatchResult(SetResultInput)`;
additional methods may emerge during decomposition) is preceded by a
failing test that verifies its public contract. Internal helper
methods (e.g., `refreshAvatarRating`, the per-step cascade methods)
are exercised by the public-method tests; they may also have direct
unit tests at the discretion of the implementer per Brief Q-1a.

The lock acquisition (`tournamentRepository.findByIdForUpdate(...)`)
is the FIRST action in `registerMatchResult(...)` — before any other
read or write. Per Brief ESC-2=a, `CascadeLockIT` is authored
RED-first: the test goes RED before the lock-acquisition is added
(proving the lost-update race exists in the absence of the lock),
then goes GREEN once the lock-acquisition is added.

The full refresh of TeamAvatarRating (legacy class lines 524-608)
is reconstructed using the SAME "full-recompute, no incremental
delta" pattern (per the legacy class's Javadoc line 515 rationale) —
this pattern remains valid post-reconstruction because the lock
acquisition serializes cascades per-tournament, eliminating the
race that motivated the full-recompute pattern. The pattern is
preserved for correction-idempotence.

Per DEC-19, scoring-tablet UI consumers of `ScoringService` (via
`ScoreEntryService` and `ScoreApiController`) continue to use
synchronous HTTP requests; nothing in this story alters DEC-19's
Mustache + ES5 contract.

Per DEC-26 (DAO 3-rules), any new DAO test in this story adheres to
the three rules. Note: `DefaultScoringService` does NOT introduce
new DAOs — it consumes the existing tournament repositories
(per the interface refactor delivered by E31S01) and the existing
`AuditLogRepository` from `tournament.internal` (which becomes
accessible via the public-package interface `AuditLogRepository`
extracted in E31S01 if it appears in the smoke-IT call graph; if
not, the E31S03 implementation must call it through whatever public
interface E31S01 provided OR escalate the dependency gap to
Discovery for resolution before proceeding).

## Acceptance Criteria

### Interface authoring (Q-1a TEST-FIRST per DEC-22)

- [ ] AC-INTERFACE-EXISTS (governance — DEC-35): The interface
  `de.vvwt.tm.scoring.ScoringService` exists in the public scoring
  package. Method signatures match the public-method surface of
  legacy `CascadeRecomputeService` that consumers depend on. At a
  minimum: `void registerMatchResult(SetResultInput input)`.
  Additional public methods only if the legacy public surface
  required them.
- [ ] AC-IMPL-PACKAGE-INTERNAL (governance — DEC-35): The
  implementation class
  `de.vvwt.tm.scoring.internal.DefaultScoringService` exists in the
  internal sub-package. The class declares
  `implements ScoringService` and is annotated `@Service`. No
  `@Component` (use `@Service` for clarity per Spring idiom).
- [ ] AC-NO-DOMAIN-IMPORTS (governance — DEC-21 § Cross-module
  communication + DEC-35): `DefaultScoringService` does NOT import
  any `de.vvwt.tm.tournament.internal.*` type. Cross-module
  dependencies are routed through public-package interfaces only
  (per E31S01 extraction). If a needed dependency lives only in
  `tournament.internal.*` after E31S01, this is a dependency gap
  that MUST be escalated to Discovery — do NOT add a forbidden
  internal import to make the test pass.

### TDD reconstruction (Q-1a per DEC-22)

- [ ] AC-TDD-RegisterMatchResult-RED (testing — Q-1a TDD-first):
  Git history shows a failing unit/integration test for
  `DefaultScoringService.registerMatchResult(...)` committed BEFORE
  the implementation class commit. The test exercises at minimum:
  (a) a happy-path scenario (well-formed input → expected post-
  cascade state in tournament repos verified via assertj-db), (b)
  a failure scenario (invalid input → ValidationException). No
  characterization tests against legacy `CascadeRecomputeService`
  per DEC-22 prohibition.
- [ ] AC-TDD-EACH-CASCADE-STEP (testing): For each of the 13
  cascade steps from legacy `CascadeRecomputeService` Javadoc
  (Step 1 input validation → Step 13 return), the corresponding
  behavior in the new implementation is preceded by a failing
  test. The tests may be aggregated (one IT covering multiple
  steps via observable post-state) or per-step (more granular
  unit tests). Discretion to the implementer on aggregation, but
  coverage MUST be verifiable: the impl-report MUST include a
  coverage table mapping each of the 13 cascade steps → at least
  one test method (FQN) → at least one assertion in that method
  exercising that step's contribution. Steps without a coverage
  table entry block story closure.
- [ ] AC-DAO-3-RULES (testing — DEC-26): Any new test for a DAO
  call site within `DefaultScoringService` (none expected since
  scoring uses tournament-side DAOs, but if any emerge during
  implementation) adheres to DEC-26's three rules: schema from
  production migration, independent assertj-db verification,
  read/write decoupling. No DAO is both subject and instrument.

### Lock acquisition (Q-1a per DEC-22 — behavior-changing)

- [ ] AC-LOCK-FIRST-ACTION (governance — DEC-37 Clause B; verified
  at FINAL state of story): The FIRST action in
  `DefaultScoringService.registerMatchResult(...)` (after parameter
  null-check / input validation, but before any other repository
  read or write) is
  `tournamentRepository.findByIdForUpdate(input.tournamentId())`.
  The result is bound to a local variable and may be used downstream
  by the cascade (e.g., to validate that the tournament exists and
  belongs to the current tenant — replacing any earlier separate
  existence-check). Verification is at the FINAL committed state of
  this story; transient intermediate commits during the RED-first
  sequencing of `CascadeLockIT` (per AC-CASCADE-LOCK-IT-RED-FIRST
  below) MAY land a `DefaultScoringService.registerMatchResult`
  implementation WITHOUT the lock acquisition — this transient
  non-compliance is expected and is resolved by the lock-addition
  commit (the GREEN transition for `CascadeLockIT`). The story is
  considered AC-LOCK-FIRST-ACTION compliant only after both commits
  land.
- [ ] AC-CASCADE-LOCK-IT-RED-FIRST (testing — DEC-22 Iron Law,
  Brief ESC-2=a): Git history shows that `CascadeLockIT` was
  committed in a state that FAILED (proving the lost-update race
  exists without the lock) BEFORE the
  `tournamentRepository.findByIdForUpdate(...)` call was added to
  `DefaultScoringService.registerMatchResult(...)`. The transition
  from RED to GREEN is a SINGLE commit that adds the
  `findByIdForUpdate` call line. This ordering is verifiable in
  `git log -p` for the impl-report.
- [ ] AC-CASCADE-LOCK-IT-CONTRACT (testing): `CascadeLockIT`
  (likely at `vvwt-tm-web/src/test/java/de/vvwt/tm/scoring/internal/CascadeLockIT.java`)
  uses `@SpringBootTest` (full context required for parallel-thread
  test harness — annotation choice justified in test-class Javadoc
  per DEC-38 Clause C narrative) OR `@ApplicationModuleTest` if
  the harness can be expressed within scoring-module scope. The
  test:
  (a) Sets up a tournament with at least 1 phase containing 2
    matches; both matches are IN_PROGRESS; Team1 plays in both
    matches (to expose the TeamAvatarRating race);
  (b) Spawns two threads that submit set-result inputs concurrently
    (using `CountDownLatch` or `CyclicBarrier` to maximize overlap
    probability);
  (c) Asserts post-cascade DB state via assertj-db (per DEC-26
    independent-verifier rule):
    - Phase.currentLapNumber advanced correctly (auto-advance fired);
    - TeamAvatarRating for Team1 reflects BOTH match outcomes (not
      just one);
    - audit_log contains entries for both submissions in serialized
      order.
  (d) The test runs the harness 100 iterations to maximize race-
    exposure probability in the RED state (10 iterations is
    insufficient to consistently trip the lost-update race window;
    100 provides empirical confidence). If the RED-state test goes
    GREEN by chance on a particular run before the lock is added,
    the impl-report MUST document this and rerun until at least one
    RED commit demonstrably failed. Flakiness in the GREEN state
    (post-lock-addition) blocks story closure — the lock MUST
    deterministically serialize cascades.

### Spring DI wiring

- [ ] AC-SPRING-DI-WIRING (governance — testing): Spring's
  `ApplicationContext` resolves `ScoringService` to
  `DefaultScoringService` automatically (single `@Service` candidate
  for the interface; no `@Primary` or `@Qualifier` needed at this
  story's commit time because legacy `CascadeRecomputeService` is
  NOT removed yet — it is removed in E31S04). During the parallel-
  phase coexistence (E31S03 commit through E31S04 commit), both
  `de.vvwt.tm.domain.CascadeRecomputeService` and
  `de.vvwt.tm.scoring.internal.DefaultScoringService` exist as
  Spring beans. Consumers of `CascadeRecomputeService` continue to
  inject the legacy class until E31S04 refactors them. `ScoringService`
  has NO consumer yet (consumers are wired in E31S04). This is the
  expected coexistence state per DEC-22 Reconstruction-in-Place.
- [ ] AC-NO-PRIMARY-NO-PROFILE (governance — DEC-21 § Atomic cutover
  protocol): `DefaultScoringService` does NOT use `@Primary`,
  `@Profile`, or `@ConditionalOn*` annotations. Coexistence is via
  TYPE distinction (two different bean types — legacy concrete-class
  `de.vvwt.tm.domain.CascadeRecomputeService` is injected by its
  concrete type into existing consumers; new
  `de.vvwt.tm.scoring.internal.DefaultScoringService` is injected by
  its `ScoringService` interface type into NEW consumers introduced
  in E31S04 — different bean type signatures resolve independently).
  Cutover to the new bean as the sole scoring path happens in
  E31S04 by deleting the legacy class entirely.

## Notes

- Per Brief H-1c, this story's LOC budget is ~600-800 production
  + ~400-600 tests. The legacy `CascadeRecomputeService` is 596 LOC;
  the reconstructed `DefaultScoringService` is expected to be of
  similar magnitude (interface adds slight overhead; lock acquisition
  is one line; full-recompute pattern preserved). Significantly
  smaller (<500 production) suggests under-coverage; significantly
  larger (>1000 production) suggests scope drift.
- The "RED-first ordering" for `CascadeLockIT` (AC-CASCADE-LOCK-IT-RED-FIRST)
  is the most procedure-sensitive AC. Implementation order:
  (1) author `CascadeLockIT` (full test code);
  (2) commit (test FAILS — RED, because `findByIdForUpdate` line is
  not yet present);
  (3) add the `findByIdForUpdate` call as a single one-line edit;
  (4) commit (test PASSES — GREEN).
  Both commits land before story closure. Impl-report cites the
  two commit SHAs as evidence of the RED-first ordering per Brief
  ESC-2=a.
- `AuditLogRepository` (currently at `tournament.internal`) is a
  dependency challenge: cascade audit-logging needs to write to it,
  but consuming `tournament.internal` from `scoring` violates DEC-21.
  Resolution paths (decided at E31S01 inventory time, not here):
  (a) `AuditLogRepository` is in E31S01's interface-extraction
  scope → it becomes a public interface accessible to scoring;
  (b) `AuditLogRepository` is NOT exposed publicly → scoring needs
  its own audit-log mechanism (out of E31 scope) OR tournament
  exposes a `record-audit` service method on a public interface that
  scoring calls. If E31S01 inventory does not produce a viable path,
  E31S03 escalates to Discovery before authoring.
- Per DEC-19, the scoring-tablet flows that consume scoring (via
  `ScoreEntryService` calling the new `ScoringService` post-E31S04)
  remain Mustache + ES5. This story does NOT change DEC-19's
  contract.
