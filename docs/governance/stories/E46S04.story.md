# Story E46S04: System-default certificate template adoption — replace `print.mustache` + `print-all.mustache` with a two-partial topology (`_certificate_styles` + `_certificate_page`), embed Plus Jakarta Sans Bold 700 + ExtraBold 800 as literal Base64 WOFF2 in the styles partial, ship `PlusJakartaSans-OFL.txt` at `META-INF/licenses/`, and translate the German handoff template placeholders to the canonical `tom_`-prefixed English convention with i18n labels bound by the assembler

## User Story

**As a** VVWT Tournament Manager operator running a fresh installation with no per-tenant uploaded certificate template,
**I want** the system-default certificate render endpoint (`GET /certificate/tournaments/{tid}/print/{teamId}` and `/print`) to produce the polished, branded VVW Tournament Manager Urkunde layout — Plus Jakarta Sans typography, hex watermark, organizer line, hero title, placement badge, team-photo block, and "generated by ToM" footer — composed from a self-contained two-partial topology that requires no internet access at render time and ships a SIL OFL 1.1 license file alongside the embedded fonts,
**so that** participants receive the production-quality certificate visual immediately on first install without operators uploading a custom template, and so that the certificate-template subsystem becomes maintainable as a clean styles-partial / page-partial pair (single source of truth for layout + styling + fonts) on top of which V1 i18n labels (per E46S03's `tom_label_*` model variables) and a future custom-upload three-piece extraction (deferred per S-22) can compose without re-touching the system-default path.

## Context

The current system-default certificate templates `vvwt-tm-web/src/main/resources/templates/certificate/print.mustache` (single page) and `print-all.mustache` (N pages with `{{> print-page-break}}`) ship a minimalist Arial double-border layout with hardcoded German strings (`Platz`, `Mannschaftsfoto`) and unprefixed Mustache variables (`{{placement}}`, `{{teamName}}`, `{{tournamentName}}`, `{{date}}`, `{{location}}`, `{{teamPhoto}}`, `{{hasPhoto}}`). They do not reflect the VVW Tournament Manager brand and contain no carrier for i18n labels.

A polished, brand-aligned, self-contained Mustache template ships as upstream source-of-truth at `vvwt-prj/handoff/certificate-template/urkunde.mustache.html` (229 lines): hex-shield watermark, lockup row with embedded T·M hex SVG, "Tournament Manager" badge, glow-backed `URKUNDE` label, hero title with subtitle, placement section (`{{platz}}.` numeric + `PLATZ`/`erreicht von` labels + accent + team name), photo-wrap with stamp, footer (`{{veranstaltungsort}}` `am` `{{datum}}` and "generated by ToM"), and an embedded Plus Jakarta Sans 700 + 800 (`@font-face` with `{{font_700_base64}}` / `{{font_800_base64}}` placeholder data-URI sources). The handoff `README.md` (`vvwt-prj/handoff/certificate-template/README.md`) documents the SIL OFL 1.1 status of the fonts and the layout's intent (self-contained, ~850 KB per HTML at 1600 px JPEG q85, A4 landscape).

This story performs four coordinated edits, in line with E46 epic scope item S04 and the Discovery Session Brief decisions D-1, D-3, D-9, D-10, D-11, D-12, D-13, D-17:

1. **Two-partial split (D-3, D-5).** The handoff template body is split into two new Mustache partials inside `vvwt-tm-web/src/main/resources/templates/certificate/`: `_certificate_styles.mustache` carries the `<style>` block (license attribution comment, two `@font-face` declarations, `:root` design tokens, layout CSS rules, `@media print` rules) and `_certificate_page.mustache` carries the body markup of one certificate tile (the `<div class="page">…</div>` block including watermark SVG, header lockup, divider, hero, placement, photo-wrap with stamp, footer). The wrappers `print.mustache` (1 page) and `print-all.mustache` (N pages with the existing `{{> print-page-break}}` partial preserved) are rewritten to be minimal: `<!doctype html><html lang="…"><head><meta><title><include _certificate_styles></head><body><stage><include _certificate_page (×1 or ×N)></body></html>`. The two-partial topology is the single source of truth for layout + styling on the system-default path; future custom uploads remain whole-document in V1 (T-13 deferred S-22).

2. **Literal Base64 WOFF2 fonts inline (D-9, Q-1, T-4).** Plus Jakarta Sans Bold 700 (`vvwt-prj/handoff/certificate-template/PlusJakartaSans-Bold.woff2`, ~30 KB binary) and ExtraBold 800 (`PlusJakartaSans-ExtraBold.woff2`) are Base64-encoded one-shot at story-authoring time and pasted as literal data-URI bytes inside `_certificate_styles.mustache`'s two `@font-face` declarations. The handoff template's `{{font_700_base64}}` / `{{font_800_base64}}` Mustache placeholders are REMOVED — there is NO runtime font-variable handling in the assembler model and the custom-upload variable contract (`DefaultCertificateTemplateService.VARIABLES`) is NOT extended with font variables. The trade-off (T-4): the styles partial grows from ~3 KB to ~80–90 KB but the rendered output is fully self-contained — opening the rendered HTML in an offline browser renders Plus Jakarta Sans correctly with no external font fetch (DEC-15 + DEC-16 offline self-host mandate satisfied). The handoff folder remains the upstream source-of-truth for the WOFF2 font bytes (D-12); future font updates re-substitute from the same source one-shot.

3. **OFL.txt license file shipping (D-11, C-13).** The SIL Open Font License 1.1 text from the upstream Plus Jakarta Sans repository (https://github.com/tokotype/PlusJakartaSans/blob/master/OFL.txt) is committed as a new resource file at `vvwt-tm-web/src/main/resources/META-INF/licenses/PlusJakartaSans-OFL.txt`. Spring Boot's resource-packaging convention places this at `BOOT-INF/classes/META-INF/licenses/PlusJakartaSans-OFL.txt` inside the built JAR. The license attribution comment block already present in the handoff template's `<style>` (`Plus Jakarta Sans — embedded as base64 WOFF2 / SIL Open Font License 1.1 — https://github.com/tokotype/PlusJakartaSans / Two weights only: 700 (Bold) + 800 (ExtraBold)`) is preserved verbatim during the split into `_certificate_styles.mustache`. The Reserved Font Name `Plus Jakarta Sans` is used unmodified — TM ships the upstream font bytes without alteration.

4. **Handoff template translation — German placeholders → `tom_`-prefixed English (D-10, D-13, D-17, O-12).** Per the variable mapping established in the Brief (Additional Context table):

   | Handoff German placeholder | Replaced by |
   |---|---|
   | `{{turnier_name}}` | `{{tom_tournament_name}}` |
   | `{{verein}}` | `{{tom_organizer}}` |
   | `{{platz}}` | `{{tom_placement}}` |
   | `{{mannschaft}}` | `{{tom_team_name}}` |
   | `{{veranstaltungsort}}` | `{{tom_location}}` |
   | `{{datum}}` | `{{tom_date}}` |
   | `{{foto_base64}}` (data-URI fragment, embedded inside `src="data:image/jpeg;base64,…"`) | `{{tom_team_photo}}` (the COMPLETE `src` value — full URL for HTML path per `buildPhotoUrl`, full data-URI for SVG path; the literal `data:image/jpeg;base64,` prefix in the handoff `<img src=…>` MUST BE REMOVED during translation per AC-PHOTO-IMG-SRC-PREFIX-REMOVED) |
   | `{{font_700_base64}}`, `{{font_800_base64}}` | REMOVED — bytes pasted literally inline (D-9) |

   Static German strings inside the handoff template body become Mustache variables bound by the E46S03 assembler from `MessageSource` (D-13 pre-rendered `tom_label_*` carriers — assembler-side ownership in E46S03; this story uses them inside the partials):
   - `URKUNDE` → `{{tom_label_certificate}}` (inside `.urkunde-badge .label`)
   - `PLATZ` → `{{tom_label_place}}` (inside `.place-meta .lbl`)
   - `erreicht von` → `{{tom_label_achieved_by}}` (inside `.place-meta .of`)
   - `Mannschaftsfoto` → `{{tom_label_team_photo}}` (inside `<img …alt="…">`)
   - `am` → `{{tom_label_on}}` (inside footer text)
   - `generated by` → `{{tom_label_generated_by}}` (inside footer text — the literal `T<o>M` mark stays as inline markup, only the prose word "generated by" is i18n-bound)

   The handoff wrapper's `<title>{{turnier_name}} · {{platz}}. Platz · {{mannschaft}}</title>` becomes — for the single-page wrapper — `<title>{{tom_label_certificate}}</title>` (or a wrapper-decided shape using only available `tom_*` variables); the `print-all.mustache` wrapper title uses tournament-level locale per D-13 chrome scope (e.g., `<title>{{tom_label_certificate}}</title>` or a tournament-level shape). Story-author exact title shape recorded under the wrapper-specific AC below; the requirement is no German remains and no per-team variable is referenced in the `print-all.mustache` `<title>` (where multiple teams render in one document).

   Following E46S03's contract, ALL Mustache variables in the certificate model are `tom_`-prefixed (D-17 / DEC-26-style hard-cut); no unprefixed variable name remains anywhere in either partial after this story.

**Sequencing constraint (C-17).** This story declares hard dependencies on:
- **E45S06** done (Wave-2 Big-Bang-Reset cleanup — ensures the templates resource path is in the post-Reset layout and avoids churn against still-present `tenant_id` plumbing).
- **E46S03** done (the assembler binds the `tom_*` data variables and the `tom_label_*` label variables that this story's partials reference; without E46S03 the partials would render to empty placeholders for every `tom_label_*` use site).

**Test-mechanism note (DEC-22).** Existing certificate render IT (`CertificateRenderControllerIT`) and slice test (`CertificateRenderControllerSliceTest`) cover the `view().name("certificate/print")` and `model().attributeExists("singleCertificate")` invariants and the 400/500 error branches with a custom uploaded template. They do NOT today exercise the system-default partial composition (no model-key shape assertions for `tom_*` keys, no JAR-resource assertions for OFL.txt, no offline-renderability assertion). DEC-22 §RED-first applies per surface: this story authors fresh RED-first surfaces for (a) the system-default render path producing a document that contains the embedded Base64 font bytes, the `tom_label_*`-substituted strings, and references no external font URLs; (b) the JAR build containing the OFL.txt resource at the canonical path; (c) the partial composition (both wrappers include both partials and the `print-all` wrapper iterates `_certificate_page` per `certificates`-list entry). The exact test mechanism is named in the AC below; story-author leaves the choice between extending `CertificateRenderControllerIT` vs. adding a dedicated `SystemDefaultCertificateTemplateIT` to delivery, with the constraint that the test must observe `text/html` rendered output through Spring Mustache view-resolution — not a mere file-existence test on the partial files (which would not exercise the `{{>}}` partial-include resolution path).

## Notes

- **Mustache partial-include path verification (empirical).** The existing `templates/certificate/print-all.mustache` (line 66) resolves `{{> print-page-break}}` to `templates/print-page-break.mustache` (top-level). The new partials live at `templates/certificate/_certificate_*.mustache` (one level deeper). Spring Boot's Mustache view-resolution looks up partials relative to the `prefix` (default `classpath:/templates/`) using the partial name plus the `suffix` (default `.mustache`). Therefore the path-prefixed include form `{{> certificate/_certificate_styles}}` resolves to `classpath:/templates/certificate/_certificate_styles.mustache`. Delivery should verify this empirically (extend slice test or run `print.mustache` view through a smoke test) before committing the wrappers — if the path-prefix form does not resolve under the active jmustache + Spring Mustache binding, fallback options are: (a) move the partials up one level to `templates/_certificate_styles.mustache` and `templates/_certificate_page.mustache` (matching `print-page-break.mustache`'s placement) — but this dilutes the certificate-namespace boundary; (b) configure `spring.mustache.prefix=classpath:/templates/certificate/` in a profile-scoped property (not chosen — this would break the existing `{{> print-page-break}}` lookup). Story-author preference: keep the partials inside `templates/certificate/` and use the path-prefixed include form, with the empirical verification step on delivery.

- **Underscore-prefix convention for partials.** The leading underscore in `_certificate_styles.mustache` and `_certificate_page.mustache` follows the widespread Mustache/Rails-style convention that "files starting with `_` are partials, not standalone views." This is decorative documentation — Mustache itself does not enforce it. The convention is chosen to make the certificate folder self-documenting (an operator browsing `templates/certificate/` immediately sees `_certificate_*` are partials and `print*.mustache` are full views). The existing `print-page-break.mustache` (no leading underscore) is preserved as-is — it predates this convention and renaming it is a Wave-3 cleanup out of S04 scope.

- **Base64 substitution mechanism.** Delivery encodes the two `*.woff2` source files (`PlusJakartaSans-Bold.woff2`, `PlusJakartaSans-ExtraBold.woff2`) via `base64` (BSD/GNU coreutils `base64` command, or Java `Base64.getEncoder().encodeToString(Files.readAllBytes(path))`) and pastes the resulting strings literally into the two `@font-face` `src: url(data:font/woff2;base64,…)` declarations in `_certificate_styles.mustache`. This is a one-shot operation at delivery time. The handoff `fonts.base64.json` helper file is NOT separately adopted (per O-13) — the two `*.woff2` source files are the authoritative input. If a future story refreshes the fonts (e.g., to a new Plus Jakarta Sans release), the same one-shot encode-and-paste mechanism re-applies.
