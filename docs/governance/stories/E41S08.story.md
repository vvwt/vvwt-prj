# Story E41S08: Fix — `HappyPathIT.happyPath_runtimeObservabilityEvents_emitted` intermittently times out (30 s) under `mvn verify` parallel load (`vvwt-slotopt-standalone-worker`)

## User Story

**As a** developer running `mvn verify` on `vvwt-prj`,
**I want** `vvwt-slotopt-standalone-worker`'s `HappyPathIT` integration test to pass
deterministically regardless of machine load,
**so that** an unrelated story's QA gate is not failed by a flaky test in a module it
never touched (per DEC-71 a non-zero `mvn verify` is an unconditional QA FAIL).

---

## Context

`HappyPathIT.happyPath_runtimeObservabilityEvents_emitted` in `vvwt-slotopt-standalone-worker`
(IT suite delivered by E41S06) **intermittently fails** under `mvn verify` parallel load:
the test hits its 30 s worker-thread `join` timeout, collects an **empty** runtime-event
list, and the assertion `Runtime events must include packet_pulled, packet_processed,
result_submitted, worker_stopped` fails.

This is a **pre-existing, load-dependent flake** — it is unrelated to any feature story.
It surfaced as the attempt-2 blocker of story **E62S01**, which touches only `vvwt-tm-web`:
because DEC-71 makes any non-zero `mvn verify` an unconditional QA FAIL, this flake can
fail the QA gate of any story whose `mvn verify` run happens to trip it. It is the second
distinct flake found in this module's WireMock IT suite — the first (timezone-fragile
algorithm-deprecation tests) was fixed by **E41S07** (`done`); this story is the same
class of test-infrastructure bug-triage, for a different test and a different mechanism.

The fix is expected to be **test-infrastructure-only** — the production standalone-worker
code is correct; the defect is in the test's readiness-wait logic.

---

## Root Cause Analysis

Established empirically by the E62S01 Delivery investigation (2026-05-17), verified against
`origin/staging` with no E62S01 changes present:

- `HappyPathIT` launches the worker via a helper, `launchWithStopAfterNextIteration()`,
  which uses a fixed **`Thread.sleep(500)`** to "allow the worker to start" before it
  sends `requestShutdown()`.
- Under full `mvn verify` parallel load (all reactor modules building/testing
  concurrently), 500 ms is **insufficient** for the worker subprocess to start and begin a
  packet cycle. `requestShutdown()` therefore arrives **before** the worker emits
  `packet_pulled`.
- The worker stops early; the test's `workerThread.join(30_000)` then waits the **full
  30 s timeout**, collects an empty runtime-event list, and the
  `happyPath_runtimeObservabilityEvents_emitted` assertion fails.
- Verified pre-existing: `mvn -pl vvwt-slotopt-standalone-worker verify` reproduces the
  failure on `origin/staging` under load; the test **passes when run in isolation / under
  low CPU load** (≈3 s). This is a genuine load-sensitive timing race, latent since the
  E41S06 IT suite shipped.

The root cause is the **fixed-duration `Thread.sleep` used as a readiness gate** — a
timing assumption that does not hold under `mvn verify` parallel load.

## Acceptance Criteria

- [ ] **AC1 (testing — reproduction)**: The current flake is documented and reproduced.
  *Given* `mvn verify` runs the `vvwt-slotopt-standalone-worker` IT suite under parallel
  reactor load, *when* `HappyPathIT.happyPath_runtimeObservabilityEvents_emitted` runs,
  *then* it intermittently hits the 30 s worker `join` timeout and fails on an empty
  runtime-event list. `impl-report.md` records the reproduction.
- [ ] **AC2 (testing — expected behaviour)**: After the fix,
  `HappyPathIT.happyPath_runtimeObservabilityEvents_emitted` observes the full runtime
  event sequence (`packet_pulled`, `packet_processed`, `result_submitted`,
  `worker_stopped`) and **passes deterministically regardless of `mvn verify` parallel
  load**. The fixed `Thread.sleep`-based readiness gate in
  `launchWithStopAfterNextIteration()` is replaced with a **deterministic readiness
  signal** — the worker is shut down only after it is genuinely ready (e.g. has begun /
  completed a packet cycle). The concrete readiness mechanism (poll for an observed
  lifecycle event, await a latch, etc.) is a Delivery implementation choice.
- [ ] **AC3 (testing — regression)**: The test is demonstrated stable — `mvn verify` for
  `vvwt-slotopt-standalone-worker` is run repeatedly under load and
  `HappyPathIT.happyPath_runtimeObservabilityEvents_emitted` passes every run.
  `HappyPathIT`'s assertion coverage (the runtime-event-sequence assertions) is **not
  weakened, disabled, `@Disabled`-tagged, or deleted** — the fix makes the readiness wait
  deterministic, it does not relax what the test verifies.
- [ ] **AC4 (error-handling)**: If the worker genuinely fails to start (a real defect, not
  a slow start), the test **fails fast with a diagnostic message** that names the missing
  readiness condition — it no longer degrades to a silent 30 s `join` timeout plus an
  opaque empty-list assertion failure.
- [ ] **AC5 (testing — module suite green)**: The full `vvwt-slotopt-standalone-worker` IT
  suite passes; `mvn verify` invoked from the `vvwt-prj` root is BUILD SUCCESS (DEC-54).
  No other test in the module is weakened to achieve this.
- [ ] **AC6 (governance)**: The change is test-infrastructure-only — no production
  `vvwt-slotopt-standalone-worker` code is modified (the production worker is correct;
  AC-IMPL-NO-PRODUCTION-CHANGE). Compiler hygiene + Spotless apply to the touched test
  files (DEC-29 / DEC-30). Skill attestation; governance artefacts propagated into
  `vvwt-prj/docs/governance/` per DEC-23 / DEC-31; committed to `staging` per DEC-13.

> All acceptance criteria are verifiable by the test run, the build, and the
> `impl-report.md` / `qa-report.md` content.

## Out of Scope

- A broader audit / hardening of the entire `vvwt-slotopt-standalone-worker` WireMock IT
  suite — this story is the targeted fix for the `HappyPathIT` timing race
  (`launchWithStopAfterNextIteration()`). If the same fixed-`Thread.sleep`-as-readiness
  helper is shared by other tests in `HappyPathIT`, fixing the helper fixes them too —
  that is in scope as a consequence; a suite-wide audit of unrelated tests is not.
- Any change to production `vvwt-slotopt-standalone-worker` code.
- The timezone-fragile algorithm-deprecation flake — already fixed by E41S07 (`done`).
- Re-delivery of E62S01 — once this story is `done` and `mvn verify` is green on
  `staging`, E62S01 is reset `escalated → refined` and re-delivered (separate operator
  action; E62S01 carries `depends_on: [E41S08]`).

## Notes

- Same bug-triage class as **E41S07** (the timezone-fragile flake in the same module) —
  `vvwt-slotopt-standalone-worker`'s E41S06 WireMock IT suite has now shown two distinct
  load/timing-sensitive flakes. If a third surfaces, a broader IT-suite-hardening story
  (the rejected "broader" option of the 2026-05-17 triage) should be reconsidered.
- The fix target is the readiness gate, not the worker: the production worker emits its
  lifecycle events correctly when given time to run; the test must *wait for* readiness
  rather than *assume* it after a fixed 500 ms.
- Verification of an intermittent flake requires repeated runs under load (AC3) — a single
  green run is insufficient evidence (per `feedback_mvn_verify_intermittent_rebase_first`).
