# Story: Operationalize DEC-74 — the operator match-correction path advances `Phase.currentLapNumber` forward-only, guarded to the lap in play

## User Story

**As a** tournament operator who records match results through the "Match-Korrektur" correction page,
**I want** the current round to advance to the next round once every match of the round being played is finished,
**so that** the Phasenübersicht "Runde" column shows the round actually in play — regardless of whether results were entered via the Score-Tablet or the correction page.

---

## Context

E56S01 operationalized DEC-65: `Phase.currentLapNumber` is a **1-based running-lap index** ("the lap currently being played"), initialized to `1` at the ASSIGNED→ACTIVE transition and advanced one lap at a time by the scoring cascade (`DefaultScoringService`) when every match of a lap becomes terminal.

The admin match-correction page routes through **`DefaultMatchCorrectionService`** — a peer service to `DefaultScoringService` that runs a simplified result-recording cascade and **deliberately omits the lap-advance step**. Its class javadoc, its `correctMatchSets` method javadoc, and an inline comment block all assert "correction MUST NOT touch / NEVER modifies `phase.currentLapNumber`"; E56S01 added the acceptance criterion `AC-GOVERNANCE-MATCHCORRECTION-STAYS-NON-MUTATING` codifying the service as a non-mutating consumer.

Operator-observed 2026-05-16: the Score-Tablet is not yet operationally used, so **every** match result is recorded through the correction page. Because that path never advances the counter, `Phase.currentLapNumber` stays frozen at its init value of `1` for the whole tournament — the Phasenübersicht "Runde" column (`PhaseList.svelte`, which displays `phase.currentLapNumber` directly) never advances past `1`.

**DEC-74** (this Discovery session, 2026-05-16) amends DEC-65 to make the lap-advance **path-independent**: the correction / Nacherfassung path must advance the running-lap counter — **forward-only, guarded to the lap currently in play**. This story operationalizes DEC-74. DEC-74 is the locked WHAT; Discovery defines the corrected observable behavior, Delivery picks the HOW.

DEC-74 D-6 explicitly **supersedes** the E48S25 "must not touch" javadoc and the E56S01 `AC-GOVERNANCE-MATCHCORRECTION-STAYS-NON-MUTATING` constraint — this story therefore reverses a prior shipped interpretation, under DEC-74's authority.

## Acceptance Criteria

### Testing (DEC-22 Iron Law — fresh Q-1a RED-first; DEC-44 web-module IT framework; DEC-54 `mvn verify` gate)

- [ ] **AC-TEST-CORRECTION-ADVANCES-CURRENT-LAP-RED**: A RED-first test exercises an ACTIVE phase with `lapCount ≥ 2` and `currentLapNumber == K` for a non-last lap `K` (`1 ≤ K < lapCount`), where lap `K` contains **at least two matches**; through `DefaultMatchCorrectionService` it corrects the matches of lap `K` one at a time and asserts **both**: (i) after all-but-the-last match of lap `K` is terminal, `phase.currentLapNumber` is still `K` (the advance does not fire early — only on the last match of the lap); (ii) after the **last** match of lap `K` is terminal, `phase.currentLapNumber == K + 1`. The test MUST fail on current HEAD (the correction path omits the advance entirely) and pass after the fix; the RED commit precedes the GREEN commit in `git log`.
- [ ] **AC-TEST-CORRECTION-LAST-LAP-SENTINEL-RED**: A RED-first test brings every match of the **last** lap (`lapNumber == lapCount`) to terminal via the correction path and asserts **both** (i) `phase.currentLapNumber == 0` (sentinel) post-correction and (ii) `phase.status` remains `ACTIVE` — no `COMPLETED` transition. MUST fail on current HEAD. (DEC-74 D-4; DEC-65 D-3/D-7.)
- [ ] **AC-TEST-CORRECTION-NON-CURRENT-LAP-NO-CHANGE-GREEN**: A regression-guard test corrects a match in an already-completed **earlier** lap (`lapNumber < currentLapNumber`), keeping all matches of that lap terminal, and asserts `phase.currentLapNumber` is **unchanged** — no backward regression. This test is GREEN on current HEAD (HEAD's correction path never advances the counter at all) and MUST stay GREEN after the fix; it guards against a guard implementation that over-fires on a non-current lap. (DEC-74 D-2/D-3.)
- [ ] **AC-TEST-CORRECTION-FUTURE-LAP-NO-CHANGE-GREEN**: A regression-guard test corrects matches in a lap **ahead of** the one in play (`lapNumber > currentLapNumber`), bringing every match of that future lap to a terminal state, and asserts `phase.currentLapNumber` is **unchanged** — completing a not-yet-current lap does not pull the counter forward. This test is GREEN on current HEAD and MUST stay GREEN after the fix; it guards against a guard implementation that over-fires on a future lap — the symmetric forward case of the DEC-74 D-3 accepted limitation, and the failure mode that made Option C unacceptable. (DEC-74 D-2/D-3.)
- [ ] **AC-TEST-CORRECTION-INCOMPLETE-LAP-NO-CHANGE**: A test asserts that a correction which does **not** bring every match of the lap in play to a terminal state leaves `phase.currentLapNumber` unchanged.
- [ ] **AC-TEST-CANCELED-CORRECTION-NO-CHANGE**: A test asserts that a correction of a `CANCELED` match (the audit-only branch) does not change `phase.currentLapNumber`. The impl-report additionally addresses the all-`CANCELED`-lap edge case (a lap whose every match is `CANCELED`): an audit-only correction records no result and never reaches the advance guard, so the counter is not advanced — accepted-inert. (DEC-74 D-5.)
- [ ] **AC-TEST-SCORING-CASCADE-LAP-ADVANCE-UNCHANGED-GREEN**: Regression — the `DefaultScoringService` lap-advance behavior (the Score-Tablet path) is not modified; its existing lap-advance / sentinel tests remain GREEN.
- [ ] **AC-TEST-CORRECTION-ADVANCE-IT**: An integration test covering the correction REST endpoint asserts the counter advances end-to-end when a lap is completed via correction. If a web-module integration test is the level chosen, it uses the canonical DEC-44 framework (`@SpringBootTest(RANDOM_PORT, classes = TournamentManagerApplication.class)`).

### Governance (DEC-74 fidelity; consumer audit; doc rewrite; DEC-22/29/30/37/44/54/58/72; commit format)

- [ ] **AC-GOVERNANCE-DEC-74-FAITHFUL**: The implemented behavior matches DEC-74 D-1…D-5 exactly — the correction path advances `currentLapNumber` **only** when the corrected match's `lapNumber` is non-null AND equals the phase's current `currentLapNumber` AND every match of the phase with that `lapNumber` is terminal; on a fire it advances to `lapNumber + 1`, or to sentinel `0` if `lapNumber == lapCount`; it never moves the counter backward and never advances from a non-current lap. No clause of DEC-74 is reinterpreted, narrowed, or extended.
- [ ] **AC-GOVERNANCE-ALL-TERMINAL-PREDICATE-MIRRORS-SCORING**: The "every match of that lap is terminal" check uses the **same match set and the same terminal-state predicate** as the `DefaultScoringService` `allTerminalInLap` check (all matches of the phase carrying that `lapNumber`; the existing terminal-state set) — verified and evidenced in the impl-report. The audit confirms no lap-advance path is missed and that this story modifies only the correction-service advance. ### Error Handling

- [ ] **AC-ERROR-NULL-LAPNUMBER**: A correction of a match whose `lapNumber` is `null` (slot-optimization not yet run for that match) does not advance the counter and does not raise an error — the guard's clause (a) (non-null `lapNumber`) short-circuits.
- [ ] **AC-ERROR-OPERATOR-CORRECTION-WINDOW**: After the last lap is finalized — `currentLapNumber == 0`, `status` still `ACTIVE` — a subsequent correction of a last-lap match still succeeds, does **not** advance `currentLapNumber` off `0` (the guard's clause (b) cannot match: a match's `lapNumber` is never `0`), and does **not** auto-complete the phase. (DEC-65 D-7 operator-correction window preserved.)
- [ ] **AC-ERROR-NO-BACKWARD-REGRESSION**: A correction is never able to move `currentLapNumber` backward — covered by AC-TEST-CORRECTION-NON-CURRENT-LAP-NO-CHANGE; the impl-report records that the guard structurally precludes a backward write.

### Security

- [ ] **AC-SECURITY-NO-NEW-SURFACE**: Internal phase-aggregate semantic change — no new REST endpoint, no new WebSocket topic or event type, no new authentication or device-token handling. The existing `POST` correction endpoint contract is unchanged.

- **Adding `LapAdvancedEvent`** to the correction path (DEC-74 D-7) — out of scope.
- **Schema migration** — `current_lap_number` stays an `int` column (DEC-25 no-prod-data).
