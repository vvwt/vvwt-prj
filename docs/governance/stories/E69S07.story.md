# Story: Pin CustomPiOS clone to tag 1.5.0 with full E69S01-AC3-symmetric CLI surface so FullPageOS chroot finds Bookworm-armhf libconfig9

## User Story

**As a** tournament operator,
**I want** `./build-image.sh` to clone CustomPiOS at the specific tag
(1.5.0) that FullPageOS 0.14.0 was integrated against — and to refuse
any other tag without explicit `--override-customos-tag-confirmation`
authorisation, mirroring the existing FullPageOS tag-pin pattern,
**so that** the FullPageOS chroot's GPU-acceleration apt-install block
(`xcompmgr libgl1-mesa-dri mesa-utils compton libconfig9`) resolves
against Raspbian Bookworm armhf's actual package set — instead of
failing on CustomPiOS devel HEAD's `libconfig11` which Bookworm armhf
does NOT ship.

sequential Escalation-Clause-driven defect discovery:

|---|---|---|
| E69S03 | 7 defects in non-dry-run path | merged |
| E69S04 | update-custompios-paths argument | merged |

| E69S06 | RaspiOS image URL pin (Bookworm 2025-05-13) | refined |
| **E69S07** | **CustomPiOS clone tag pin (1.5.0)** | this story |

The 2026-05-28 operator-attest log (post-E69S04+E69S05+E69S06 merge)
reached the FullPageOS chroot GPU-acceleration phase and failed at:

```
+ apt-get -y --force-yes install xcompmgr libgl1-mesa-dri mesa-utils compton libconfig11
E: Unable to locate package libconfig11
build failed, unmounting image...
```

Root cause is empirically established. The offending command lives in
CustomPiOS `src/modules/gui/start_chroot_script:24`. The wrapper script
currently clones CustomPiOS unpinned (`git clone --depth 1
${CUSTOMPIOS_REPO} ${WORK_DIR}/CustomPiOS`) → defaults to `devel`
branch HEAD. Devel HEAD ships `libconfig11`; tag `1.5.0` (latest CustomPiOS
release, 2024-10-25) ships `libconfig9`. Raspbian Bookworm armhf has
`libconfig9` (verified at `http://raspbian.raspberrypi.org/raspbian/dists/bookworm/main/binary-armhf/Packages.gz`) but NOT
`libconfig11`. Pinning CustomPiOS to 1.5.0 closes the immediate
chromium-build defect AND addresses the unpinned-clone staleness vector
flagged in E69S05 Brief NEW-D.

The pin pattern is the **full E69S01-AC3-symmetric** structure: a
constant + a mutable variable + a `--custompios-tag=TAG` operator-
override flag + a `--override-customos-tag-confirmation` guard +
runtime validation that refuses unconfirmed tag mismatches. This
mirrors the existing FullPageOS pattern (PINNED_TAG / FULLPAGEOS_TAG /
`--fullpageos-tag` / `--override-tag-confirmation`) verbatim. The
partial-symmetric path (constant + override-confirmation flag only,
without a `--custompios-tag` flag) would produce either dead-code
validation or an empty governance-only flag — both rejected at Brief
Cycle-2 NEW-1 in favour of full symmetry.

This story is `track: bug-triage` per the Discovery Bug-Triage Flow in
`.gaai/core/agents/discovery.agent.md`. Like E69S04/S05/S06, it is a
single-defect retrofit on the wrapper — not a feature expansion. The
CLI surface addition (`--custompios-tag` + `--override-customos-tag-
confirmation`) is part of the single defect's symmetric-pin pattern,
not a separate feature.

## Root Cause Analysis

Single defect: `vvwt-prj/pi-display/build-image.sh` clones CustomPiOS
without a tag pin, defaulting to remote HEAD (`devel` branch). Devel
HEAD has diverged from tag 1.5.0 in the `gui` module's apt-install
package list, breaking the build on Raspbian Bookworm armhf.

**Upstream contract** — CustomPiOS `src/modules/gui/start_chroot_script:24`
gates a GPU-acceleration apt-install block under
`GUI_INCLUDE_ACCELERATION=yes` (default). The package list differs by
tag/branch:

| Source | Package list | Raspbian Bookworm armhf? |
|---|---|---|
| `tag 1.5.0` (2024-10-25) | `xcompmgr libgl1-mesa-dri mesa-utils compton libconfig9` | All available ✓ |
| `devel HEAD` (2026-05-28) | `xcompmgr libgl1-mesa-dri mesa-utils compton libconfig11` | `libconfig11` MISSING ✗ |

Raspbian Bookworm armhf ships `libconfig9` (libconfig 1.5.x series) but
not `libconfig11` (libconfig 1.7.x series). The transition happens in
Trixie+. Empirically verified at review time via
`http://raspbian.raspberrypi.org/raspbian/dists/bookworm/main/binary-armhf/Packages.gz`.

The next package in the conditional block (`rpi-chromium-mods`) IS
available at `archive.raspberrypi.org/debian/dists/bookworm/main/binary-armhf` — so once `libconfig9` resolves, the rest of the
conditional clears.

**Wrapper's failure mode** — `build-image.sh` clones CustomPiOS with no
`--branch` argument, defaulting to remote HEAD = `devel` branch. The
build then runs the devel chroot script with the libconfig11 reference,
which Bookworm armhf cannot satisfy. `apt-get install` fails with
"Unable to locate package libconfig11". Per `set -euo pipefail`
(`build-image.sh:87`), the script aborts.

**CustomPiOS releases** — Verified via
`github.com/guysoft/CustomPiOS/releases` at review time: tag `1.5.0`
published 2024-10-25, previous `1.4.0` published 2020-11-04 (~4-year
cadence, irregular like FullPageOS — per E69S02 Known Limitations §2).
No newer tag exists. Tag-bump-beyond-1.5.0 path foreclosed until
upstream cuts a release.

**Why tag 1.5.0 is the correct pin** — Three reasons, ordered
empirical-first:

1. **[Empirical, correctness-critical]** CustomPiOS 1.5.0 installs
   `libconfig9` which Raspbian Bookworm armhf HAS; devel HEAD installs
   `libconfig11` which it does NOT. Pin closes the defect.
2. **[Context, governance-relevant]** 1.5.0 is the latest CustomPiOS
   release tag. Symmetric to E69S01's choice of FullPageOS-latest-tag
   at integration time.
3. **[Supporting inference, NOT independently verified]** FullPageOS
   0.14.0 was tagged 2025-07-14 — after CustomPiOS 1.5.0 (2024-10-25)
   and before any later CustomPiOS tag (none exist) — so 1.5.0 is
   the most plausible version FullPageOS 0.14.0 was integrated
   against. Reason 1 alone justifies the pin; reason 3 is
   corroborative.

**CustomPiOS 1.5.0 structural compatibility** — Verified at review time:

- `src/update-custompios-paths` (the symlink-helper E69S04 fixed):
  IDENTICAL contract to devel HEAD (DEST=$PWD with optional $1
  override, writes ${DEST}/custompios_path). E69S04's argument fix
  continues to apply.
- `src/execution_order.py` (CustomPiOS build entry point): at
  top-level in 1.5.0 (not in `custompios_core/` subdir as in devel).
  Imports ONLY `argparse` + `os` (stdlib). NO `import git`, NO
  `import yaml`. → E69S05's Python-deps pre-flight check is **a
  blocking false prerequisite** at 1.5.0 (1.5.0 doesn't need
  GitPython or PyYAML at all). Resolution per AC8 below: update the
  pre-flight error message text + README Note to state the
  precautionary basis explicitly.
- Modular structure (`src/modules/{base,gui,...}`): preserved in
  1.5.0; same execution_order pattern.
