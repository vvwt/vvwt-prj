# Story E40S03: DefaultKeyRegistrationService deprecation-date enforcement per DEC-43 D2/D3 with HTTP 410 Gone path

## User Story

**As a** dispatcher operator preparing for future Phase-2+ algorithm deprecation (e.g., when ML-DSA replaces Ed25519),
**I want** the existing `KeyRegistrationService` to enforce `deprecation_date` semantics per DEC-43 D2/D3 — server-clock authoritative; new registrations using a deprecated-after-deadline algorithm rejected with HTTP 410 Gone; pre-existing registrations using a now-deprecated algorithm continue to verify (no force-rotation),
**so that** when Phase-2+ deprecation activates, operator-controlled tempo for migration is enforceable at the dispatcher boundary without breaking active compute jobs from already-registered workers.

---

## Context

Per Brief D-6: KeyRegistrationService deprecation-date enforcement per DEC-43 D2/D3:
- Server-clock authoritative (per DEC-43 § Boundary semantics).
- `deprecation_date` interpreted as UTC end-of-day: a new registration submitted at any instant `≥ deprecation_date.atTime(23:59:59Z)` is rejected.
- Rejection HTTP code: 410 Gone with explicit error body identifying the deprecated algorithm + its deprecation date.
- Pre-existing registrations (rows in `key_registration` table with the now-deprecated algorithm) continue to VERIFY at submit-result time per DEC-43 D3 — no force-rotation. The verify path in `SubmitResultService` (E37-shipped) is NOT touched by this story.

Per Brief C-17: V1 universal `deprecation_date = null` means the HTTP 410 path is **defensive code that never fires in V1 operation**. Activation comes when Phase-2+ deprecates Ed25519 in favor of a newer algorithm. The story authors and tests the path anyway to lock the DEC-43 D2/D3 contract at compile-time.

Per Brief S-5: Pre-existing E37 `KeyRegistrationService` is touched ONLY at the deprecation-date enforcement boundary — new check + new HTTP 410 path before existing logic; existing logic preserved byte-equivalent. NOT a refactor (DEC-22 §refactor-clause not invoked); ADDITIVE new code requiring fresh Q-1a TDD RED-first per DEC-22 Iron Law.

This story consumes E40S01's interface extension (`SignatureVerifier.deprecationDate()`) and runs in parallel with E40S02 (both depend on S01 only). E40S03 does NOT consume E40S02's announcement endpoint — the deprecation check operates directly via `SignatureVerifierRegistry.lookup(algorithmId).deprecationDate()`.

- [ ] **AC-DEPRECATED-ALGORITHM-EXCEPTION**: New exception class `de.vvwt.slotopt.dispatcher.identity.DeprecatedAlgorithmException extends RuntimeException` with constructor `(String algorithmId, LocalDate deprecationDate)`. Message format: `"Algorithm '" + algorithmId + "' deprecated as of " + deprecationDate + " (UTC end-of-day); new registrations rejected per DEC-43 D3."` Authored RED-first via test asserting message format + accessor methods.
- [ ] **AC-CLOCK-INJECTION**: `DefaultKeyRegistrationService` constructor extended to inject a `java.time.Clock` bean (`@Autowired Clock clock`). Spring config provides a `@Bean Clock systemUtcClock() { return Clock.systemUTC(); }` in the dispatcher's main `@Configuration` class (or appropriate config). Tests use a fixed `Clock.fixed(...)` to deterministically assert deadline-crossing behavior. Per Brief D-6 / DEC-43 § Boundary semantics: server clock authoritative; clock-skew tolerance NOT prescribed (no implicit grace-window).
- [ ] **AC-DEPRECATION-CHECK-BEFORE-EXISTING-LOGIC**: `DefaultKeyRegistrationService.register(...)` gains a new check at the START of the method (before existing algorithm-validation / public-key-length / role-conflict / persistence logic): after `SignatureVerifierRegistry.lookup(algorithmId)` succeeds, if the verifier's `deprecationDate()` is non-null AND `clock.instant().isAfter(deprecationDate.atTime(LocalTime.MAX).atZone(ZoneOffset.UTC).toInstant())`, throw `DeprecatedAlgorithmException`. Otherwise proceed with existing logic verbatim.
- [ ] **AC-EXISTING-LOGIC-PRESERVED**: Existing `KeyRegistrationService` logic (algorithm validation against `SignatureVerifierRegistry.supportedAlgorithms()`, public-key-length validation against verifier min/max, role-conflict detection, persistence, idempotent re-register on (workerId, role, algorithm) match) preserved byte-equivalent. Verifiable via `git diff` showing only ADDITIVE new code (the deprecation check + clock injection wiring); existing-logic test suite from E37 continues to pass without modification.
- [ ] **AC-CONTROLLER-410-GONE-PATH**: `KeyRegistrationController` (E37-shipped) gains a new `@ExceptionHandler(DeprecatedAlgorithmException.class)` returning `ResponseEntity.status(HttpStatus.GONE).body(Map.of("error", ex.getMessage()))`. Existing exception handlers (`IllegalArgumentException` → 400, `RoleConflictException` → 409) preserved unchanged. RED-first authored via `@WebMvcTest` MockMvc slice that mocks the service throwing the exception and asserts HTTP 410 + JSON error body.
- [ ] **AC-PRE-EXISTING-REGISTRATIONS-CONTINUE-VERIFYING**: Per DEC-43 D3 explicit rule. Verifiable: integration test pre-populates a `KeyRegistration` row with `algorithm = "Ed25519"`, then sets `Ed25519Verifier`'s `deprecationDate()` to a past date (via test config), then calls submit-result with a signature from that pre-existing key — submit-result accepts the signature and returns 200 / accepted=true (no 410, no rejection). The `SubmitResultService` verify path is NOT touched — only the new-registration path enforces deprecation.
- [ ] **AC-DEPRECATION-AT-EXACT-DEADLINE**: Test asserts boundary semantics per DEC-43: a new registration submitted at exactly `deprecation_date.atTime(23:59:59Z)` (or any later instant) is rejected; a registration submitted at `deprecation_date.atTime(23:59:58Z)` (one second earlier) is accepted. Fixed `Clock` controls the test instant.
- [ ] **AC-V1-NULL-DEPRECATION-NOOP**: With Ed25519 `deprecationDate()` returning null (V1 default per E40S01), every registration path bypasses the new check entirely. Verifiable via test asserting V1-shipped integration test suite from E37S05 continues to pass without modification (no false-410 returns).

## Notes

- **Defensive code at V1**: per Brief C-17, this entire story's enforcement path is dormant in V1 operation (Ed25519 has `deprecationDate=null` universally). The path is authored, tested, and shipped to lock the DEC-43 D2/D3 contract at compile-time so Phase-2+ activation is a code-only operator change (set `DefaultEd25519Verifier.deprecationDate()` to a future date) — no DEC amendment, no wire-protocol change, no controller modification.
- **Why throw + ExceptionHandler vs. return-error pattern**: the existing E37-shipped `KeyRegistrationController` uses the throw + `@ExceptionHandler` pattern for `IllegalArgumentException` (→ 400) and `RoleConflictException` (→ 409). This story extends the SAME pattern with `DeprecatedAlgorithmException` (→ 410) for consistency. No new architectural pattern introduced.
- **Clock injection vs. `Instant.now()`**: testability requires deterministic clock. `java.time.Clock` is the standard JDK abstraction; Spring's `@Bean Clock systemUtcClock()` is a one-line config addition. Tests inject `Clock.fixed(...)`. No new library dependency.
- **HTTP 410 Gone vs. 403 / 400**: per DEC-43 D3 verbatim "the server returns a registration error (HTTP 410 Gone or equivalent application-level error) for any new registration request using a deprecated algorithm". 410 Gone semantically signals "this resource (the algorithm) is no longer available" — appropriate for deprecation. 400 Bad Request is reserved for client-format errors (unknown algorithm, bad key length); 409 Conflict is reserved for role conflict. The error matrix stays clean.
