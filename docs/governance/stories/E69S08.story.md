# Story: Switch CustomPiOS pin from tag 1.5.0 to devel-HEAD commit (27ff1d3…) for /sys-bind-mount fix + add libconfig11→libconfig9 sed-patch

## User Story

**As a** tournament operator,
**I want** `./build-image.sh` to clone CustomPiOS at a specific
devel-HEAD commit sha that contains the `/sys`-bind-mount fix in
`common.sh:mount_image`, and to map `libconfig11` back to `libconfig9`
in the cloned `gui/start_chroot_script` via a build-time sed-patch
(verbatim reversal of upstream commit c298127 for Raspbian Bookworm
armhf compatibility),
**so that** the FullPageOS chroot's `initramfs-tools` postinstall step
runs `mkinitramfs` successfully (with sysfs available for kernel-module
dependency resolution) and the subsequent `apt-get install
chromium-browser dependencies` resolves `libconfig9` from Raspbian
Bookworm armhf — clearing two consecutive blockers that no single
CustomPiOS release tag can resolve simultaneously.

## Context

E69S08 is the sixth bug-triage retrofit under Epic E69, continuing the
sequential Escalation-Clause-driven defect discovery. After E69S07
(CustomPiOS tag 1.5.0 pin) merged 2026-05-28, the next live operator-
attest reached the FullPageOS chroot `initramfs-tools` postinstall
phase and failed with:

```
mkinitramfs: MODULES dep requires mounted sysfs on /sys
update-initramfs: failed for /boot/initrd.img-6.12.25+rpt-rpi-v8 with 1.
dpkg: error processing package initramfs-tools (--configure): installed
initramfs-tools package post-installation script subprocess returned
error exit status 1
build failed, unmounting image...
```

Root cause is empirically established. CustomPiOS 1.5.0 (E69S07's
pin) `common.sh` `mount_image` function bind-mounts /dev, /dev/pts,
/proc but NOT /sys. Bookworm's `initramfs-tools` default `MODULES=dep`
(or Raspberry-Pi-OS override) queries `/sys` for kernel-module
dependency resolution. Without /sys mounted, `mkinitramfs` aborts and
the dpkg postinstall fails.

The fix is upstream commit `7e484b3` (2024-12-14, "Mount proc and sys
as read-only"), which added the missing `/sys` bind-mount. This commit
is AFTER tag 1.5.0 (2024-10-25). No subsequent CustomPiOS release tag
exists with this fix — the only tagged release is 1.5.0. A later
upstream commit `c298127` (2025-12-15, "Upgrade libconfig9 to
libgonfig11 for Debian Trixie") changed the GPU-acceleration package
name in `gui/start_chroot_script` from `libconfig9` to `libconfig11`,
which Raspbian Bookworm armhf does NOT have.

Per user choice 2026-05-28 (Path C of the Discovery analysis), the
resolution is:
1. Switch the CustomPiOS pin from tag 1.5.0 to a specific devel-HEAD
   commit sha (`27ff1d372294d51ac186fb1ac17ac6221bac6833`,
   snapshot 2026-05-22 14:47 UTC) — which has the /sys-bind-mount fix.
2. Add a build-time sed-patch mapping `libconfig11` back to
   `libconfig9` in the cloned `gui/start_chroot_script` — a verbatim
   reversal of upstream commit c298127's package-name change.

E69S07's CLI scaffolding (`PINNED_CUSTOMPIOS_TAG` constant,
`--custompios-tag` flag, `--override-customos-tag-confirmation` flag,
string-equality validation block) is REUSED — only the pin VALUE and
the clone MECHANISM change. Two existing E69S07 bats assertions
(AC2(a) `1\.5\.0` literal and AC2(f) `--branch.*CUSTOMPIOS_TAG`
pattern) require in-place updates within E69S08's amendment scope
because the production changes would otherwise turn them RED and break
`mvn verify` (DEC-54).

This is the FIRST commit-sha pin in the E69 chain — all previous pins
were release tags (FullPageOS 0.14.0 per E69S01; CustomPiOS 1.5.0 per
E69S07; RaspiOS 2025-05-13-bookworm-armhf-lite per E69S06). The
commit-sha pin is an explicit one-time deviation from E69S01 AC3
tag-pin-enforcement semantics, justified by the absence of any release
tag that satisfies both correctness requirements simultaneously. A
sha-to-tag-return obligation (D-7 below) tracks the eventual return to
tag-pin semantics when CustomPiOS cuts a release >= 1.6.0 with both
fixes.

This story is `track: bug-triage` per the Discovery Bug-Triage Flow.

## Root Cause Analysis

Single-defect: CustomPiOS 1.5.0 `common.sh` `mount_image` lacks `/sys`
bind-mount. Bookworm `initramfs-tools` postinstall requires sysfs in
chroot. Build aborts.

**Upstream contract** — verified at review time:

| Source | `common.sh` /sys bind-mount? | `gui/start_chroot_script` libconfig version |
|---|---|---|
| Tag 1.5.0 (2024-10-25; E69S07 pin) | ✗ NO | `libconfig9` ✓ |
| Commit `7e484b3` (2024-12-14) | ✓ ADDED | `libconfig9` ✓ |
| Commit `c298127` (2025-12-15) | ✓ | `libconfig11` ✗ |
| Devel HEAD `27ff1d3…` (2026-05-22) | ✓ (line 209-214) | `libconfig11` ✗ (line 24) |

No release tag has BOTH /sys-mount AND libconfig9 simultaneously.

**Wrapper's failure mode at E69S07's 1.5.0 pin** — `common.sh:205-209`
bind-mounts only /dev, /dev/pts, /proc. When the chroot runs
`apt-get install initramfs-tools` (pulled in transitively by GUI
acceleration packages or other dependencies), the postinstall
`update-initramfs` invokes `mkinitramfs`, which queries `/sys` per the
Bookworm `MODULES=dep` default. Without /sys mounted in chroot,
`mkinitramfs` exits non-zero, dpkg reports postinstall failure, and
the CustomPiOS chroot loop aborts via `set -euo pipefail` propagation.

**Why Path C (commit-sha pin + libconfig sed-patch) chosen over Path
A (1.5.0 + /sys-mount sed-patch backport)** — per user choice
2026-05-28. Both paths are 1-patch solutions; Path C transitively
picks up specific verified fixes between 1.5.0 and `27ff1d3…` (most
notably the /sys-bind-mount commit `7e484b3`), at the cost of
introducing the libconfig sed-patch.
