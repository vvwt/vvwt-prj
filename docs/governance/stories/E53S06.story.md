# Story E53S06: Fix: Laufzettel renders only 4 rounds for an ACTIVE Phase containing 30 roundRobin matches on 3 fields — round-assignment compresses lapNumber distribution upstream of print

## User Story

**As a** Tournament Organizer printing Laufzettel for participating teams,
**I want** the printed Laufzettel to list every round the team plays in the ACTIVE phase,
**so that** participants receive a complete schedule without gaps and the printed artefact matches the matches the operator scheduled.

---

## Context

User reported on 2026-05-10 (screenshot `Bildschirmfoto_2026-05-10_18-49-15.png`) that the Laufzettel page renders only **4 rounds per team** for a tournament with 12 teams in 2 groups (6+6) on 3 fields, roundRobin spielmodus. The Phasen-Übersicht admin UI confirms (screenshot `Bildschirmfoto_2026-05-10_19-14-41.png`) that Phase 1 is `Aktiv`, `roundRobin`, with `0 / 30` matches scheduled.

### Verifiable expected behavior

For 30 matches on 3 fields, the natural distribution is 30 / 3 = **10 distinct lap numbers** in Phase 1 (the only ACTIVE phase). The per-team Laufzettel must therefore render at least 10 round rows for that phase.

### Pre-history (informational)

Pre-E51 the system ignored phase configuration and always assumed roundRobin in a single group of 12 teams (66 matches → 22 rounds). User mental model still ran on that pre-E51 expectation. Post-E51 the phase configuration is honored: Phase 1 alone produces 30 matches → 10 rounds. The verifiable lower bound for THIS story is therefore **≥10 rounds for Phase 1**, not 22.

### Pre-E53 vs post-E53 narrowing

Pre-E53S02 the Laufzettel rendered 10 rows (correct given honoring phase config but compressed if upstream assignment had a defect). Post-E53S02's ACTIVE-only phase filter narrowed the symptom: only Phase 1 reaches the assembler. The current rendering of **4** rows means `max(Match.lapNumber)` in Phase 1 data is 4 — not 10.

### Root principle (from Brief D-0)

Print is a downstream observer; root cause for this defect lives in the **DATA layer** — `Match.lapNumber` distribution is wrong, not the print rendering. The fix surface is upstream of `DefaultLaufzettelAssembler`. Print-layer patches that would mask the upstream defect are forbidden.

### Codebase entry points (informational only — Delivery picks the implementation shape)

- `DefaultLaufzettelAssembler.java:178-181` — derives `maxLap = max(Match.lapNumber)` across phase's matches.
- `DefaultLaufzettelAssembler.java:439` — iterates `for (lap = 1; lap <= maxLap; lap++)` per phase.
- `PrintController.java:274-277` and `:361-363` — ACTIVE-only phase filter (E53S02). PRESERVED.
- Round-robin match generator + slot-optimization (root-cause search bounded to these by Brief O-12; specific FQN unknown to Discovery).
- Slot-opt threshold: `tm.slotopt.exhaustive-max-n=10` (memory `[Slot-Opt threshold N = rounds]`) — N=10 is at the threshold; Delivery verifies whether this interacts with the compression.
