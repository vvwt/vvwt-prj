# Story E18S01: Activate compiler-hygiene gate — `-Xlint:all,-serial` + `failOnWarning=true` + cleanup of ~36 mechanical warnings

## User Story

**As a** maintainer of the multi-agent-authored `vvwt-prj` codebase,
**I want** `mvn verify` to fail on any javac hygiene warning except the deferred serial-keyset,
**so that** future PRs cannot introduce silent warnings and the existing 85-warning backlog is closed to ~36 mechanical fixes now (serial-category ~49 fixes deferred to a future governance amendment).

---

## Context

Discovery 2026-04-19 ran an empirical audit. `mvn test-compile` with `<compilerArgs><arg>-Xlint:all</arg></compilerArgs>` injected into the parent POM and reverted immediately returned 85 warnings across 4 modules (`vvwt-worker-lib`, `vvwt-dispatcher`, `vvwt-standalone-worker`, `vvwt-tm-web`; `vvwt-benchmark` produced zero warnings at measurement time). Distribution: ~49 serial-keyset + ~36 mechanical (`unchecked` 4, `cast` + redundant cast 6, `deprecated` 2, `this-escape` 2, `non-transient` 1, plus any `-Xlint:all` keys outside those individually observed).

DEC-29 specifies the exact parent POM configuration (`-Xlint:all,-serial` + `failOnWarning=true`) and the scope (deferring serial-keyset). This story implements DEC-29: (a) apply the configuration, (b) fix the emergent mechanical warnings, (c) document in `patterns/conventions.md`, (d) confirm clean build across all 5 modules, (e) verify forward enforcement is live via a probe.

Per DEC-22 TDD Iron Law: mechanical warning fixes (adding `@SuppressWarnings`, narrowing a generic, removing a deprecated call, adding a missing `@Override`) are modifications of existing code paths or annotation additions, not new production-code additions. No new failing test is required per iron-law interpretation. However, the full test suite MUST remain green post-fix — any failure indicates a regression introduced by the fix, which is a quality defect.

## Acceptance Criteria

- [ ] **AC1 (governance — DEC-29 configuration):** Parent POM `de.vvwt:vvwt-prj` `pluginManagement/maven-compiler-plugin` is updated to match DEC-29 § Decision #1 exactly — `<failOnWarning>true</failOnWarning>` is a top-level element inside `<configuration>` (NOT inside `<compilerArgs>`); `<compilerArgs>` contains `<arg>-Xlint:all</arg>` followed by `<arg>-Xlint:-serial</arg>` in that order. No per-module override introduced. The `release` element remains as before.

- [ ] **AC2 (build — clean compile across all 5 modules):** After activation and after all warning fixes, `mvn clean test-compile` run from `vvwt-prj/` produces zero javac `[WARNING]` lines across all 5 modules. Measurement (both German and English locale): `mvn clean test-compile 2>&1 | grep -E '\[WARNING\] .*\.java:\['` returns zero lines. Surefire/resources/plugin `[WARNING]` messages unrelated to Java source files are acceptable.

- [ ] **AC3 (build — failOnWarning is live):** Introduce a deliberate probe — e.g., an unused local variable or an `@Override` annotation on a non-override method — in a test file under `vvwt-worker-lib/src/test/java/`. `mvn compile` (or `mvn test-compile`) MUST terminate with `BUILD FAILURE`, not merely emit a warning. Revert the probe. Evidence: inline terminal transcript in the impl-report, OR a `story/E18S01-probe` branch or reverted probe-then-revert commit pair.

- [ ] **AC4 (governance — no serial-keyset fixes):** The diff between `staging` pre- and post-merge shows no new `serialVersionUID` field additions, no new `transient` modifiers on existing Serializable-class fields, no new `@SuppressWarnings("serial")` annotations. Serial cleanup is deferred per DEC-29 § Decision #4. If a suppression-free fix is genuinely required (e.g., removing a `Serializable` from a class that was never meant to implement it), escalate to Discovery for a DEC-29 amendment — do NOT silently add serial-keyset artefacts.

- [ ] **AC5 (testing — existing suite green per DEC-22):** All existing tests across the 5 modules pass after fixes. Evidence: `mvn verify` green on fresh checkout of `staging` after merge. No test is added, removed, or altered in this story except where a warning fix requires a mechanical test-code change (e.g., `@SuppressWarnings("unchecked")` on a test method). Such test-code changes MUST NOT alter assertion semantics — impl-report lists each test file touched with a one-line reason.

- [ ] **AC6 (governance — documentation):** `patterns/conventions.md` gains a new top-level section titled "Code Quality" (if absent) with a subsection "Compiler Hygiene" that: (a) names the active configuration (`-Xlint:all,-serial` + `failOnWarning=true`); (b) points to DEC-29; (c) explains that serial-keyset lints are deferred until a future DEC settles the exception-serialization contract; (d) specifies that any new module inherits the configuration from the parent POM — no per-module override.

- [ ] **AC7 (governance — JMH carve-out evaluation per DEC-29 § Decision #2):** After activation, `mvn clean test-compile` on `vvwt-benchmark` is inspected for JMH-generated-code warnings (sources under `target/generated-sources/`). If zero warnings, the impl-report states "vvwt-benchmark produces zero warnings under `-Xlint:all,-serial` — no carve-out required." If any warnings appear, the impl-report names the specific warnings, proposes either a surgical suppression (annotation on the generated wrapper) or an amendment to DEC-29 carving out `vvwt-benchmark` explicitly, and escalates to Discovery before merging. Silent suppression is forbidden.

## Out of Scope

- Serial-keyset fixes (deferred per DEC-29 via `-Xlint:-serial`).
- Unused-import removal (DEC-30 / Story E18S02 territory).
- Spotless, Checkstyle, PMD, Error Prone activation.
- Per-module POM overrides — all configuration lives in parent POM per DEC-10 inheritance.
- CI pipeline wiring (DEC-21/DEC-22 no-CI fallback).
- Behavioural changes in any warned-about code path — fixes are mechanical (annotations, narrowings, removals), not refactorings. If a warning surfaces what looks like a real defect, the fix is a separate Story/Bug-Triage, not inline scope creep.

## Notes

- The ~36 mechanical fix count is a heuristic-measured estimate from Discovery. Authoritative count comes from Delivery's first `mvn test-compile` after activation. Acceptable variance ±20%. If >100 mechanical warnings surface, Delivery halts and escalates to Discovery — heuristic underestimated and scope requires re-validation.
- **Fix patterns per category:**
  - `unchecked` (4) — typically `@SuppressWarnings("unchecked")` with a single-line rationale comment; occasionally a narrowing of generic types is feasible.
  - `cast` / redundant cast (6) — delete the redundant cast, or `@SuppressWarnings("cast")` with rationale when the cast is intentional for documentation purposes.
  - `deprecated` (2) — inspect each: if a non-deprecated replacement exists, swap; if the deprecation note advises "do not replace yet", suppress with rationale.
  - `this-escape` (2) — constructor self-reference issues (e.g., `WorkerKeyManager` ~line 102 invoking subclass-init-sensitive code). Fix options: extract to `@SuppressWarnings("this-escape")` with Javadoc explaining the accepted risk, OR refactor the constructor to avoid the self-reference. Mechanical choice per-class.
  - `non-transient instance field` (1) — serial-adjacent. `-Xlint:-serial` should suppress this; if it surfaces, mark the field `transient` only if transient semantics are correct; otherwise escalate (do not silently switch to `@SuppressWarnings`).
- Expected fix approach per warning is mechanical and localized. If a warning triggers design debate, Delivery escalates rather than guessing.
- Forward-enforcement probe (AC3) can be any deliberate trigger — choose the smallest/most-local warning that reliably produces `BUILD FAILURE`. An unused local variable is recommended.
