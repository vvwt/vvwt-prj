# Story E54S07: Add `BalancedVarietyScorer` variance-aware cost function in vvwt-slotopt-worker-lib (operationalizes DEC-63)

## User Story

**As a** developer maintaining the slot-optimization pipeline,
**I want** the worker-lib to offer a variance-aware cost function (`BalancedVarietyScorer`) as an alternative to the existing `VarietyScorer` (MEAN-of-products legacy port),
**so that** the cost function is mathematically aligned with the user's stated balance-objective (*"die Reihenfolge zu finden, in der die spielfreien Zeiten für alle Mannschaften am ausgeglichensten sind (nahe am Mittelwert)"*), and the project can opt-in to the variance-aware behavior via configuration without breaking backward-compatibility with the existing scorer.

---

## Context

DEC-63 (2026-05-11, this Discovery cycle) operationalizes by this story. The full architectural rationale + approach-evaluation is at `.gaai/project/contexts/artefacts/evaluations/2026-05-11-l3-variety-score-bound-investigation.approach-evaluation.md`.

User-confirmed framing 2026-05-11: *"Der bessere Algorithmus sollte aber trotzdem verwendet werden"* — variance-aware cost is theoretically aligned with the balance-objective. In practice the existing `VarietyScorer` produces similar outputs due to structural avatar-coupling, BUT the cleaner algorithm should be implemented.

### Architectural placement

- Worker-lib path: `vvwt-slotopt-worker-lib/src/main/java/de/vvwt/slotopt/worker/score/`
- Existing: `VarietyScorer.java` (legacy port; MEAN-of-products; DEC-61 Clause F preserved unchanged)
- New: `BalancedVarietyScorer.java` (variance-of-products; DEC-63 Clause B contract)
- Per DEC-63 Clause B: per-avatar computation IDENTICAL to existing scorer (same active-matrix walk, same product accumulation); only the aggregation differs.

### Cost function specification (per DEC-63 Clause B)

**Existing `VarietyScorer`:**
```
totalScore = SUM(per-avatar product-of-run-lengths)
score      = totalScore / avatarCount    // = MEAN of products
```

**New `BalancedVarietyScorer`** (one of these formulations — Delivery picks the canonical one and documents in impl-report):
```
mean       = SUM(rating_i) / avatarCount
variance   = SUM((rating_i - mean)^2) / avatarCount
score      = variance                    // pure variance
```
OR:
```
score      = α × mean + β × variance     // weighted (α=1, β=10 strongly penalizes imbalance)
```
OR:
```
score      = MAX(rating_i) - MIN(rating_i)   // range (simpler)
```

The choice between these three formulations is a Delivery-time decision. Pure variance (option 1) is the cleanest and most aligned with the user's stated objective. The α=1/β=10 weighted form (option 2) is most flexible. Range (option 3) is the simplest but coarsest. **Default Discovery recommendation: option 1 (pure variance)** — but Delivery may justify another choice with empirical evidence.

### Configuration selection (per DEC-63 Clause C)

Spring `@Value("${tm.slotopt.scorer:mean}")` resolved at PacketSolver invocation site (or wherever the scorer is instantiated). Valid values:
- `mean` (default): use `VarietyScorer` (existing, legacy port).
- `balanced`: use new `BalancedVarietyScorer`.
- Invalid: log WARN + fall back to `mean`.

### Determinism preservation

Both scorers MUST produce bit-identical outputs for identical inputs (DEC-49 D-3 determinism requirement). New scorer uses the same primitive-arithmetic patterns as existing (double accumulation, no platform-dependent functions).

### Tie-break preserved

E01S03 PacketSolver tie-break-by-lowest-rank policy is preserved by new scorer (same caller-side handling).

## Notes

Estimated LOC: ~100-200 new production lines (`BalancedVarietyScorer.java` + minor invocation-site change) + ~150 test lines (7 new tests + existing-tests-symmetry-checks). NO modification of existing scorer.

The configuration property pattern (`tm.slotopt.scorer={mean|balanced}`) follows the existing project precedent (`tm.slotopt.fallback.field-count`, `tm.slotopt.exhaustive-max-n`).

The variance formulation chosen by Delivery should be documented in impl-report with rationale. Discovery's default recommendation is pure variance (`SUM((rating_i - mean)^2) / avatarCount`) for maximal mathematical alignment with user's stated objective. Range (`MAX-MIN`) is simpler but coarser. Weighted (`α × mean + β × variance`) gives flexibility for future tuning.

This story is a **theoretical improvement**, NOT a critical bug-fix. The existing `VarietyScorer` continues to work; the new `BalancedVarietyScorer` is opt-in. Production deployments may flip the config when ready.
