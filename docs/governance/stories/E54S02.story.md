# Story E54S02: PhaseToRawPhaseDefMapper RawRow=Lap refactor + cascading consumer updates

## User Story

**As a** developer maintaining the slot-optimization pipeline,
**I want** `PhaseToRawPhaseDefMapper` to produce one `RawRow` per lap (with the union of active avatars in that lap), matching the DEC-56 D-3 literal text `rows.size() = lapCount`,
**so that** `VarietyScorer` measures lap-variety (the correct cost function per the user's domain), `RoutingSlotOptimizationClient`'s lap-perm-to-row-seq expansion workaround can be removed, and the slot-opt pipeline is structurally aligned with its governing DEC.

---

## Context

DEC-61 Clause B (this story's operationalization target) clarifies that DEC-56 D-3's literal text `"lapCount = RawPhaseDef.rows.size()"` becomes code-conform only post-Mapper-refactor. The current `PhaseToRawPhaseDefMapper.map` (lines 127-167) builds one `RawRow` per match with exactly 2 `PositionTuple`s — making `rows.size() = matchCount`, not `lapCount`. The implementation works today only because `RoutingSlotOptimizationClient.executeLeg1Inline:299-305` expands the lap-permutation `π` to a row-sequence via the formula `rowSeq[i] = pi[i / fieldCount] * fieldCount + i % fieldCount` before passing to `VarietyScorer.scoreWithMatrix` — a workaround for the mismatched mapper output.

Refactoring the Mapper to RawRow=Lap aligns three things at once:
- `RawPhaseDef.rows.size() = lapCount` (DEC-56 D-3 literal text becomes structurally true)
- `VarietyScorer`'s active-matrix becomes `[lapCount][avatarCount]` — measures lap-variety (correct cost function: per-avatar idle-vs-active across lap sequence, matching the user's "spielfreie Zeiten" domain semantic)
- `RoutingSlotOptimizationClient:299-305` expansion becomes redundant — π directly is the row-permutation passed to `scoreWithMatrix`; that block of code is removed

DEC-61 Clause D mandates this consumer-side cleanup; this story executes it.

`vvwt-slotopt-worker-lib` core (`VarietyScorer`, `LehmerCodec`, `PacketSolver`, `RawPhaseDef`, `RawRow`, `CanonicalPhaseDef`, `StructuralFingerprint`) is textually unchanged per DEC-61 Clause F. The Mapper-refactor changes the CONSUMER side only.

L3 invocation shape (per-group `mapGroup` loop → phase-global `map`) is E54S03's scope, not this story's; however, `PhaseToRawPhaseDefMapper.mapGroup` (lines 222-323) becomes dead code post-E54S03 and is DELETED in E54S03 (not here, to keep this story focused on Mapper-output-shape).

The L2 voting-driven slot-filling from E54S01 produces match rows with 1-based `lapNumber` per DEC-60. The Mapper consumes those Match rows and aggregates by `lap_number` — produces lap-rows ordered ascending by `lap_number ∈ [1..lapCount]`.

Reviewer cycle-2 CRIT-1 concern (Mapper refactor unnecessary because `RoutingSlotOptimizationClient:299-305` expansion bridges the semantic gap) is user-overridden per DEC-61 § Reviewer-cycle disclosure: the expansion is the workaround being removed, not the canonical bridge.

## Acceptance Criteria

### Testing (DEC-22 RED-first; DEC-54 mvn verify gate)

- [ ] **AC-TEST-MAPPER-ROWS-EQUALS-LAPCOUNT-RED**: New unit test on `PhaseToRawPhaseDefMapper.map` (or sibling `PhaseToRawPhaseDefMapperTest`) asserts that for a phase with 30 matches across 10 distinct `lap_number` values, the returned `RawPhaseDef.rows.size() == 10` (NOT 30). Fixture builds Match rows with `lap_number ∈ [1..10]`, 3 matches per lap. RED before GREEN.

- [ ] **AC-TEST-MAPPER-ROW-POSITIONS-UNION-RED**: New unit test asserts that for any lap-row produced by the Mapper, `RawRow.positions` is the union of `PositionTuple`s of all matches in that lap (size between 2 and `2 * fieldCount`, depending on actual match count in the lap). For a lap with 3 matches and 6 distinct avatars (typical 3-field non-overlapping), `positions.size() == 6`. RED before GREEN.

- [ ] **AC-TEST-MAPPER-ROW-ORDER-ASCENDING-LAP-RED**: New unit test asserts that the Mapper's `RawPhaseDef.rows` are ordered by ascending `lap_number`. For a fixture with input matches in shuffled `lap_number` order, the output rows have `rows[0]` corresponding to `lap_number = 1`, `rows[1]` to `lap_number = 2`, etc. RED before GREEN.

- [ ] **AC-TEST-MAPPER-NULL-LAP-NUMBER-THROWS-RED**: New unit test asserts that if any input Match has `lap_number = null` at Mapper invocation time, the Mapper throws `IllegalStateException` with a message naming the offending match ID. Mapper is contractually post-L2; pre-L2 invocation is a programmer error. RED before GREEN.

- [ ] **AC-TEST-ROUTING-EXPANSION-REMOVED-RED**: New unit/IT asserts that `RoutingSlotOptimizationClient.executeLeg1Inline` (or its private helper) does NOT contain the expansion expression `pi[i / fieldCount] * fieldCount + i % fieldCount` for the post-Mapper-refactor code path. Verified by either: (a) `git diff --unified=0` of `RoutingSlotOptimizationClient.java` shows the expansion block deleted; OR (b) a new contract-test asserts that `rowSeq` passed to `VarietyScorer.scoreWithMatrix` has `length == lapCount` (not `length == matchCount`) for a 30-match / 10-lap input fixture. RED before GREEN.

- [ ] **AC-TEST-SLOTRESULTAPPLICATOR-LAPCOUNT-DIRECT-RED**: New unit test asserts that `SlotResultApplicator.applyResult` derives `lapCount` from `mapping.canonical().rowCount()` directly (NOT from `rowCount / fieldCount`). Verified by either: (a) `git diff` of `SlotResultApplicator.java` shows line 115 replaced with `int lapCount = mapping.canonical().rowCount();` (or equivalent); OR (b) a new unit test with a contrived input where `rowCount / fieldCount != mapping.rowCount()` (post-Mapper-refactor `rowCount == lapCount`, so they happen to be equal — use a test that verifies the actual derivation expression in source via reflection-free contract assertion). RED before GREEN.

- [ ] **AC-TEST-DISPATCHER-WIRE-FORMAT-COMPAT-GREEN**: Existing or new IT exercises the Leg-2 dispatcher path with a 12T/2G/3F mapping post-Mapper-refactor; verifies that `DispatcherClient` / `DefaultSlotOptimizationDispatcherClient` correctly serialize the new lap-row `RawPhaseDef` and that the dispatcher's response is correctly applied by `SlotResultApplicator`. If no live dispatcher is available in the IT setup, a mock-based test verifies the JSON wire-format of the request body matches the worker-lib's `RawPhaseDef` record schema. GREEN expected (worker-lib record schema is unchanged; only consumer-side population changed).

- [ ] **AC-TEST-EMPTY-LAP-LIST-EDGE-RED**: New unit test asserts that if the Mapper is invoked on a phase with zero matches (edge case: post-L2 ran but produced no Match-Rows, e.g., siegerehrung gameMode per DEC-59), the Mapper throws `IllegalStateException` per existing line 110-115 contract (preserved). RED if the throw message changes; GREEN if the existing throw is preserved.
