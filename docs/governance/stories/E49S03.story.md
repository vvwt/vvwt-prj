# Story: Fix — scoring-tablet UI elements never become visible (`vvwtShow` cannot override a stylesheet `display:none`)

## User Story

**As a** tournament operator (and the scorekeeper who uses the tablet during play),
**I want** the scoring tablet to actually display the elements its JavaScript reveals — the PIN block on `/score/register`, and the match / no-match / queue / confirm-dialog / error panels on `/score/field/{n}`,
**so that** I can read the PIN off the tablet to bind it to a court, and the scorekeeper can see the live match panel, the waiting state, and any error during play.

---

## Context

E49S01 (PR #213, merged 2026-05-08) introduced the **out-of-band PIN**: the device PIN is shown ONLY on the registering tablet, and is the proof-of-possession token an admin types to bind the tablet to a court. E49S02 (PR #277, merged 2026-05-14) extended `GET /api/devices/status` to return the PIN on revisit.

**Symptom (verified by user screenshots 2026-05-15 14:46:57 and 15:30:01):** `/score/register` shows the heading "Scoring Tablet" and the status line "Warte auf Zuweisung…" but **no PIN is ever displayed** — no PIN box, no PIN-instruction text, no device name, no retry button. The operator cannot type a PIN they cannot see, so the inline-row field-assignment flow in `Devices.svelte` is blocked. Reproduced by the user on multiple browsers, including a freshly-used browser, and on the physical tablet — i.e. it is deterministic and environment-independent, not a per-device or per-build artefact.

**Root cause (verified — empirical):**

- `vvwt-tablet.js:316–318` — the shared ES5 helper `vvwtShow(el)` is implemented as `el.style.display = ''`.
- Setting `style.display` to the empty string removes the *inline* `display` declaration only. The element's `display` then resolves from the author stylesheet cascade. If a stylesheet rule sets `display:none` on that element, the computed value **stays `none`** — the element is NOT revealed.
- `register.mustache:58–62` hides `#pin-block` via a **stylesheet rule** (`#pin-block { display: none; }`); the `<div id="pin-block">` element carries no inline style. Therefore `vvwtShow(elPinBlock)` — called inside `showPinAndPoll()` (`register.mustache:337`) — cannot reveal it. The PIN value *is* written into the block (`vvwtSetText(elPinValue, pin)` sets `textContent`, which is display-independent), but the block remains `display:none`.
- This was confirmed empirically in-session with a headless-Chromium reproduction: a div hidden by a stylesheet `display:none` rule has computed `display:none` after `vvwtShow()`; a div hidden by an inline `style="display:none"` has computed `display:block` after `vvwtShow()`.
- The PIN backend data path is correct end-to-end — verified by live `curl` against the running app: `POST /api/devices/register` returns `pin`, and `GET /api/devices/status?token=…` returns `pin` (E49S02). The bug is purely client-side presentation; **no backend change is needed.**
- This is why E49S02 did not resolve the user-visible symptom ("immer noch keine PIN"): E49S02 fixed the PIN *data* on the revisit path, but the PIN *block* was invisible regardless of the data path.

**The same defect affects the scoring page `field.mustache`.** Its `#match-panel`, `#no-match-panel`, `#queue-status`, `#confirm-dialog`, and `#error-banner` are all hidden by stylesheet rules and revealed via `vvwtShow` (call sites: `#confirm-dialog` l.544, `#queue-status` l.630, `#error-banner` l.645, `#no-match-panel` l.686 and l.700, `#match-panel` l.745 — six call sites for five elements, as `#no-match-panel` is revealed from two). They therefore also cannot appear — the live scoring page is latently broken. It has not surfaced as a user report only because the user is blocked at registration and has never reached `/score/field/{n}`. The human confirmed (2026-05-15) that this story should fix the scoring page in the same change, since it is the identical shared-utility root cause.

|---|---|---|---|

That path is correct and is out of scope. `field.mustache`'s `#error-banner` is additionally revealed via `vvwtShow` inside `showError()` — that path IS defective and IS in scope.

This is a Bug-Triage Story. Discovery defines the observable outcome (every element the tablet JS reveals via `vvwtShow` must actually become visible, at its correct display type, without regressing currently-correct call sites). Delivery defines the mechanism (see § Notes — Fix Mechanism Candidates).

## Notes

**Fix Mechanism Candidates (Discovery enumerates non-prescriptively; Delivery picks ONE and records the choice + rationale in the qa-report):**

- **M-A — Class-based visibility**: replace the `display:none` stylesheet rules (and the inline `style="display:none"` on `#referee-row`) with a shared CSS class (e.g. `.is-hidden { display: none; }`); change `vvwtShow`/`vvwtHide` to remove/add that class. Each element then falls back to its natural/intended `display` when shown. Robust against the cascade problem; touches every hide site.
- **M-B — Restore intended display value**: change `vvwtShow` to set an explicit `display` value, while preserving each element's intended type (e.g. read a `data-display` attribute, or default to `''` only for inline-hidden elements and a real value otherwise). Must not hard-code `block` for elements that need `flex`/`inline-block`.
- **M-C — Convert hides to inline**: change the *hiding* mechanism so every element `vvwtShow` must reveal is hidden by an inline `style="display:none"` instead of a stylesheet rule (then the existing `vvwtShow` works unchanged). Smallest change to `vvwt-tablet.js`, but spreads inline styles across two templates.
- **M-D** — any other mechanism that satisfies all ACs.

Whichever mechanism is chosen, **all `vvwtShow` call sites in the inventory table above must be verified** — both the currently-defective and the currently-correct ones.

**Test-harness candidates (Delivery's choice — DEC-19 forbids a JS bundler/framework on this surface, so a vitest-style harness is not available for the tablet pages):**

- A Java web-module IT using **HtmlUnit** (a headless browser with CSS-cascade + `getComputedStyle` support) that loads the rendered Mustache page, drives the inline JS, and asserts computed `display`.
- A headless-browser integration test (the in-session reproduction used headless Chromium successfully).
- A structural assertion if Delivery can express the property without a browser (lower fidelity — must still genuinely fail RED).

The constraint from Discovery: the RED test must *actually exercise the visibility behaviour* (computed display / rendered visibility), not merely the source text — and it must fail on current production code. If Delivery concludes that no RED-first test can faithfully exercise computed visibility within the project's tooling, STOP and escalate to Discovery rather than weakening the test.

**Reproduction (manual):**

1. Open `/score/register` in any browser. The page registers a tablet; `POST /api/devices/register` returns a valid `pin` (confirmed via `curl`).
2. Observe: status line shows "Warte auf Zuweisung…" but no PIN box, no PIN-instruction text, no device name appear. ← bug.
3. Repeat in a different / fresh browser and on the physical tablet — identical result (deterministic).

**Empirical root-cause artefact:** an in-session headless-Chromium test rendered two divs — one hidden by a stylesheet `display:none` rule, one by an inline `style="display:none"` — and ran the exact `vvwtShow` body (`el.style.display = ''`) on each. Result: the stylesheet-hidden div had computed `display:none` (NOT revealed); the inline-hidden div had computed `display:block` (revealed). This is the deductive + empirical basis for the root cause.

**H-1 (UNVERIFIED, not load-bearing):** the `vvwtShow` defect implies the tablet PIN and the `field.mustache` panels have likely been invisible since these pages first shipped — no environment ever displayed them. Confirming this would need git-archaeology of when the hide-mechanism became a stylesheet rule and/or when `vvwtShow` became `display=''`; it does not affect the fix.
