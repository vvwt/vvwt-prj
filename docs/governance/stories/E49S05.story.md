# Story E49S05 (Bug-Triage): Fix — DefaultLanHostDetector's test-only constructor seam breaks the vvwt-tm-web Spring application context; consolidate to a single production constructor (regression from E49S04)

## User Story

**As a** developer maintaining `vvwt-prj` — and the GAAI Delivery pipeline that gates every story on `mvn verify`,
**I want** `DefaultLanHostDetector` to have a single production constructor with no test-only seam, so the `vvwt-tm-web` Spring application context loads,
**so that** `mvn verify` exits zero again (DEC-54) and the codebase contains no production constructor that exists only to serve tests.

---

## Context

E49S04 (PR #285, merged 2026-05-14, commit `b9df966`) added a new `@Service`,
`de.vvwt.tm.tournament.internal.DefaultLanHostDetector`, to resolve the LAN host for registration
and timer QR URLs. The class declares **two constructors**:

- `public DefaultLanHostDetector(TmPublicHostProperties properties)` — production path; delegates to the second constructor with a method reference to the real interface enumeration.
- `DefaultLanHostDetector(TmPublicHostProperties properties, Supplier<List<InetAddress>> addressSupplier)` — **package-private, documented in the source as the *"Testing constructor"* / *"Secondary constructor for testing"***. It exists only so unit tests can inject a deterministic fake address list.

Two defects flow from this:

1. **Production code that exists only for tests.** The 2-arg constructor (and the `Supplier<List<InetAddress>>` it feeds) is production code whose sole reason to exist is unit-test injection. Production never needs a substitutable address supplier — it always uses the real `NetworkInterface` enumeration. This is the anti-pattern DEC-69 named the *converse of the Iron Law*: DEC-22's Iron Law governs authoring order (no production code without a failing test first); its converse — production code must not exist solely to serve tests — was made explicit by DEC-69, but only for Repository/DAO read methods. DEC-69's letter does not yet cover constructors. The operator mandated, in this Discovery session, that the same principle applies here: tests must exercise production code, and the test-only constructor must go.

2. **Spring cannot instantiate the bean.** Spring performs implicit single-constructor injection only when a bean declares exactly one constructor. With two constructors and **neither annotated `@Autowired`**, Spring cannot pick a candidate, falls back to a no-argument constructor — which does not exist — and bean creation fails:

```
org.springframework.beans.factory.BeanCreationException: Error creating bean with name
'defaultLanHostDetector' ... Failed to instantiate [DefaultLanHostDetector]:
No default constructor found
```

Because `DefaultLanHostDetector` is a component-scanned singleton `@Service`, this aborts the
**entire `TournamentManagerApplication` Spring context**. Every test that boots that context fails
on `Failed to load ApplicationContext`.

Defect 2 is a *symptom* of defect 1: the second constructor exists only because of the test-only
seam. Removing the seam removes the ambiguity.

**Empirical reproduction (2026-05-15, `staging` HEAD `07e3ebe`):** `mvn verify` →
`BUILD FAILURE`, exit 1, `Tests run: 1429, Failures: 0, Errors: 20, Skipped: 3`. All 20 errors
share the identical `Caused by` above, across 4 `@SpringBootTest` classes:

| Test class | Errors |
|---|---|
| `de.vvwt.tm.certificate.LocaleResolverContractTest` | 13 |
| `de.vvwt.tm.certificate.MessageSourceFallbackTest` | 4 |
| `de.vvwt.tm.tournament.internal.web.WebSocketConfigTest` | 2 |
| `de.vvwt.tm.tournament.internal.web.DomainEventBridgeTest$IntegrationTest` | 1 |

## Root Cause Analysis

- **Root cause:** E49S04 introduced a **test-only constructor** in `DefaultLanHostDetector` — a production-code seam (the package-private 2-arg constructor + its `Supplier<List<InetAddress>>` parameter) created solely for unit-test injection. The test-only seam is what gives the class a second constructor; with two constructors and no `@Autowired` marker, Spring Boot 4.0.5's constructor resolution attempts the non-existent default constructor and fails. Removing the seam is mandated by the operator's explicit decision in this Discovery session — that the fix must eliminate any production constructor or function existing solely to serve tests — with DEC-69 as the closest existing precedent (DEC-69 formalised this converse-of-the-Iron-Law principle for Repository/DAO read methods; constructors are not yet in its letter).
- **Originating change:** `DefaultLanHostDetector.java` is a 100%-addition new file introduced by commit `b9df966` (E49S04) — confirmed via `git log --diff-filter=A`. The bean did not exist before E49S04; therefore the 20 context-load errors did not exist before E49S04. This is a **regression introduced by E49S04** — not a pre-existing failure.
- **Why it shipped:** E49S04's qa-report classified the 20 errors as "pre-existing failures confirmed on `origin/staging`" on the basis of a `git stash` probe. `DefaultLanHostDetector.java` was a committed file on the story branch, so `git stash` never reverted it; the probe could not observe a true pre-E49S04 baseline. The story passed QA under DEC-54's "pre-existing failures only" allowance with a regression mislabelled as pre-existing. (Hardening the `qa-review` classification method is **out of scope** here — see Notes.)
- **Blast radius:** every `mvn verify` on `staging` exits non-zero. Because DEC-54 makes `mvn verify` exit-zero the closure gate for every story, the entire Delivery pipeline is blocked. E18S04 escalated on exactly this failure (2026-05-15).
- **Why a minimal `@Autowired` patch is rejected — and the cost accepted:** annotating the 1-arg constructor `@Autowired` is the smaller, lower-risk fix — one line, smallest blast radius, and it would unblock `mvn verify` (and therefore E18S04 and every pipeline story) fastest. But it leaves the test-only 2-arg constructor in production code, fixing only the symptom. The operator explicitly mandated that the fix must not merely make the build pass — it must remove the test-only seam. The structural fix is therefore chosen, and its costs are accepted: a larger diff than a one-line patch; a test rewrite (mitigated by `AC-TEST-DETERMINISTIC-COVERAGE-RETAINED`); the possible introduction of a new component-scanned bean — itself new context-load surface (mitigated by `AC-TEST-REGRESSION-GUARD` + `AC-BUILD-MVN-VERIFY`); and a marginally later pipeline unblock than the one-liner.

## Acceptance Criteria

### Reproduction

- [ ] **AC-REPRO**: Given `staging` at or after commit `b9df966`, when `mvn verify` is invoked from the `vvwt-prj` root, then the build fails (exit 1) with ≥1 test error whose root `Caused by` is a `BeanCreationException` for bean `defaultLanHostDetector` reporting `No default constructor found`. The impl-report records this confirmed pre-fix state.

### Fix

- [ ] **AC-FIX-NO-TEST-ONLY-SEAM**: After the fix, no constructor, method, or field on `DefaultLanHostDetector` exists solely to serve tests — in particular the package-private 2-arg "testing constructor" (`DefaultLanHostDetector(TmPublicHostProperties, Supplier<List<InetAddress>>)`) is gone. The unit tests drive `DefaultLanHostDetector` through its single production constructor; where a test needs deterministic control of the address list, that control is obtained by substituting a collaborator that production itself genuinely depends on — not a seam (constructor parameter, overridable method, or field) introduced only for tests. The HOW is a Delivery decision; one illustrative shape is extracting the local-address enumeration into a production collaborator (interface + implementation) injected through the production constructor — and if that collaborator is a self-created Spring `@Service`/`@Component`, DEC-58 requires it to carry a bounded-context interface (`{Foo}` interface + `Default{Foo}` impl naming canon).
- [ ] **AC-FIX-SINGLE-PRODUCTION-CONSTRUCTOR**: After the fix, `DefaultLanHostDetector` declares **exactly one constructor**, and every parameter it takes is a collaborator that Spring wires in production.
- [ ] **AC-FIX-CONTEXT-LOADS**: The `TournamentManagerApplication` Spring context loads successfully and Spring instantiates the `DefaultLanHostDetector` bean. With a single production constructor, Spring's implicit single-constructor injection applies and the multi-constructor `No default constructor found` failure no longer occurs.
- [ ] **AC-FIX-NO-BEHAVIOUR-CHANGE**: `detectHost()`'s observable resolution behaviour is unchanged — config-override precedence, first site-local non-loopback selection, `localhost` fallback, and the production use of real local-interface enumeration all behave exactly as E49S04 intended. The change is structural (removing the test-only seam), not behavioural.

### Testing

- [ ] **AC-TEST-EXERCISES-PRODUCTION-CODE**: The unit tests for `DefaultLanHostDetector`'s address-selection logic instantiate and exercise the class through its single production constructor and production collaborators only. No test instantiates `DefaultLanHostDetector` via a test-only constructor. Deterministic control of the address list under test is achieved by substituting the production collaborator (e.g. a mock/fake of its production interface), not by a production constructor that exists for tests.
- [ ] **AC-TEST-DETERMINISTIC-COVERAGE-RETAINED**: The deterministic coverage of the address-selection branches established by E49S04 — config-override precedence, site-local preference over a public address, multi-interface determinism, loopback-only fallback — remains present and GREEN after the restructuring. No branch of `detectHost()` loses coverage.
- [ ] **AC-TEST-REGRESSION-GUARD**: A regression test exists that is RED before the fix and GREEN after, verifying the Spring application context can instantiate the `LanHostDetector` / `DefaultLanHostDetector` bean (DEC-22 — the regression-guard obligation of a bug fix). Whether this is a new minimal context-load test or a designated existing test is a Delivery decision; a new context-booting test follows the DEC-44 web-module IT canon (`@SpringBootTest(classes = TournamentManagerApplication.class)`).
- [ ] **AC-TEST-SUITE-GREEN**: After the fix, the full existing `vvwt-tm-web` test suite passes — in particular the 20 previously-erroring tests across the 4 classes named in Context are GREEN — with no test disabled, skipped, `@Disabled`, or weakened to achieve green.

### Build

- [ ] **AC-BUILD-MVN-VERIFY**: `mvn verify` invoked from the `vvwt-prj` root exits zero (BUILD SUCCESS) — the DEC-54 closure gate. This is the closure criterion.
- [ ] **AC-BUILD-DEC-29-CLEAN**: `mvn verify` produces no new javac hygiene warning — `failOnWarning=true` (DEC-29) stays satisfied (e.g. no unused import or unused field introduced by the restructuring).
- [ ] **AC-BUILD-DEC-30-CLEAN**: `mvn spotless:check` stays green (DEC-30) — the fix leaves no formatting drift.

### Error-handling

- [ ] **AC-ERROR-FALLBACK-PRESERVED**: `DefaultLanHostDetector`'s degraded-path behaviour is untouched — the no-site-local-interface `localhost` fallback and its WARN log (E49S04 `AC-ERROR-NO-LAN-INTERFACE-FALLBACK`) behave exactly as before. The restructuring introduces no new failure mode; failures the production collaborator may encounter while enumerating interfaces are handled the same way E49S04's `enumerateLocalAddresses()` handled them.

### Security

- [ ] **AC-SECURITY-LOCAL-ONLY-PRESERVED**: The fix introduces no outbound network call and no new external dependency. The DEC-15 / DEC-16 zero-internet, local-only detection guarantee E49S04 established (`AC-SECURITY-LOCAL-ONLY-DETECTION`) is preserved — address enumeration still reads only local network interfaces. (A new in-process production collaborator bean for that enumeration is permitted; a new network or external surface is not.)

### i18n

- [ ] **AC-I18N-NO-CODE-CHANGE**: The fix touches no localization surface — no user-facing string, message key, resource bundle, or locale-resolution logic is added or modified. The i18n test classes among the 20 (`LocaleResolverContractTest`, `MessageSourceFallbackTest`) return to GREEN purely because the application context loads again, with zero i18n code change.

### Governance

- [ ] **AC-GOV-SCOPE-LOCKED**: The fix stays within the diagnosed scope — `DefaultLanHostDetector`, its test-only seam, and the production collaborator extracted from it. No unrelated refactor, no change to other `@Service` classes, no change to `detectHost()` resolution logic, no DEC amendment.
- [ ] **AC-GOV-ATOMIC-COMMIT**: The fix (seam removal + collaborator extraction + test rewrite + regression test) lands in a single atomic commit.
- [ ] **AC-GOV-COMMIT-FORMAT**: Implementation commits use the project's conventional-commit story format scoped to `E49S05` (e.g. `fix(E49S05): ...`) and name the regression being fixed.
