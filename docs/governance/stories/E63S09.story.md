# Story E63S09: Fix — DispatcherProcessLauncher discards the dispatcher subprocess output, leaving SlotOptE2EIT dispatcher-startup failures undiagnosable

## User Story

**As a** developer running the Tournament Manager reactor build,
**I want** a failed `SlotOptE2EIT` dispatcher-startup to tell me *why* the dispatcher
subprocess died,
**so that** I can diagnose it from the build output alone, without manually re-launching the
dispatcher JAR.

---

## Context

`SlotOptE2EIT` (authored by E63S08) starts the `vvwt-slotopt-dispatcher` fat JAR as an
external OS subprocess via `DispatcherProcessLauncher` — the no-compile-dependency design
required by DEC-11. When that subprocess fails to start, the test reports only:

```
AssertionError: DispatcherProcessLauncher: dispatcher process died before becoming ready (port=N)
```

`DispatcherProcessLauncher` launches the subprocess with
`pb.redirectOutput(ProcessBuilder.Redirect.DISCARD)` — the dispatcher's own stdout and
stderr (merged via `redirectErrorStream(true)`) are **thrown away**. So when the dispatcher
crashes during startup, the actual cause — the Spring bean-creation stack trace printed by
the subprocess — is gone. The operator can only recover it by manually re-launching the JAR
with the same arguments and capturing the output by hand.

This was triggered on 2026-05-17 by a `mvn verify` failure on `vvwt-tm-web`. Diagnosing that
single failure required manually reproducing the subprocess launch to discover the real
cause. The launcher's two readiness-failure branches — *process died* and *readiness
timeout* — are both equally opaque, and will be opaque again for every future cause
(port race, OOM, configuration drift, a stale JAR).

This story fixes the **diagnosability defect** in the test infrastructure. It does not change
any production code and does not change the dispatcher.

---

## Root Cause Analysis

Investigation (Discovery, 2026-05-17 — root cause established, not implemented):

- **The reported `mvn verify` failure itself was not a code defect.** `SlotOptE2EIT` ran
  against a stale `vvwt-slotopt-dispatcher` fat JAR built before E63S08's H2-`runtime`-scope
  fix landed. The stale JAR lacked the H2 driver, so the dispatcher subprocess crashed on
  startup with `Cannot load driver class: org.h2.Driver`. A clean reactor build rebuilds the
  dispatcher with H2 and the test passes — empirically confirmed; the dispatcher `pom.xml` on
  staging is correct. **No production fix is needed for that failure** — it is a stale-build
  artifact, resolved by a clean reactor build.

- **The defect this story fixes** is what made that one-line diagnosis cost an hour:
  `DispatcherProcessLauncher` discards the dispatcher subprocess's stdout/stderr
  (`Redirect.DISCARD`). When the subprocess dies, the test failure carries the launcher's own
  generic message but none of the subprocess's error output. The genuine cause is reproducible
  only by manually re-launching the JAR — there is no automated diagnostic path.

**Reproduction scenario (the diagnosability defect):**
- **Given** a `vvwt-slotopt-dispatcher` fat JAR that fails during startup for any reason,
- **When** `SlotOptE2EIT` runs and `DispatcherProcessLauncher.start()` launches that JAR,
- **Then** the test fails with only `dispatcher process died before becoming ready (port=N)`
  and no trace of the subprocess's own error output — the cause is invisible in the build
  output and recoverable only by a manual re-launch.

**Expected behaviour after the fix:** the same failure surfaces the dispatcher subprocess's
captured output as part of the failure, so the cause is identifiable from the build output
alone. Delivery determines the implementation.

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-DEATH-FAILURE-CARRIES-OUTPUT** — when `DispatcherProcessLauncher` reports
  that the dispatcher subprocess died before becoming ready, the failure surfaced to the
  test (its message, or its surfaced cause) includes the dispatcher subprocess's captured
  stdout+stderr — sufficient to identify the startup-failure cause (e.g. a bean-creation
  stack trace) from the build output alone, with no manual re-launch required. An automated
  test exercises this failure path; the mechanism for producing a non-ready subprocess is
  Delivery's choice.
- [ ] **AC-TEST-REACTOR-SUITE-GREEN** — `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` with
  the reactor building `vvwt-slotopt-dispatcher` fresh; `SlotOptE2EIT` and
  `SlotOptLeg3FallbackIT` pass; no pre-existing test regressed (DEC-54).

### Governance

- [ ] **AC-GOV-NO-DISPATCHER-COMPILE-DEP** — the change introduces no compile-time
  dependency from `vvwt-tm-web` on `vvwt-slotopt-dispatcher` (DEC-11); subprocess output
  capture uses only `ProcessBuilder` / filesystem mechanisms, never an imported dispatcher
  class.
- [ ] **AC-GOV-TEST-INFRA-SCOPE** — the change is confined to test-infrastructure code under
  `vvwt-tm-web/src/test/`; no production code in any module and no dispatcher code is
  modified. Delivery classifies the change per DEC-22 test classification and authors the
  AC-TEST-DEATH-FAILURE-CARRIES-OUTPUT coverage accordingly.
- [ ] **AC-GOV-BUILD-HYGIENE** — `mvn verify` exits zero (DEC-54); the build is warning-free
  (DEC-29); Spotless / google-java-format clean (DEC-30); no production member exists solely
  for tests (DEC-70).

### Error Handling

- [ ] **AC-ERR-TIMEOUT-CASE-ALSO-DIAGNOSTIC** — the readiness-*timeout* failure path
  (subprocess alive but never returning HTTP 2xx on the readiness probe within the timeout)
  likewise surfaces the captured subprocess output, so a hung or slow startup is as
  diagnosable as an outright crash. Both readiness-failure branches carry the diagnostic.
- [ ] **AC-ERR-CAPTURE-NEVER-HANGS-LAUNCHER** — capturing the subprocess output never causes
  the launcher itself to hang: a dispatcher that emits a large volume of output must not
  block on a full OS pipe buffer, and a healthy dispatcher must still be detected as ready
  and stopped cleanly in the success path.

### Security

- [ ] **AC-SEC-NO-SECRET-LEAK-VIA-CAPTURE** — surfacing the subprocess output does not widen
  the secret-exposure surface: the launcher does not raise the dispatcher's log verbosity
  above the levels it already sets (`root=WARN`, `de.vvwt=INFO`), so no additional credential
  or Ed25519 key material is drawn into the captured stream; the captured output is surfaced
  only into the test/build failure output for the duration of the test run — not written to
  any new persistent or shared location.

## Out of Scope

- A staleness / freshness check for the resolved dispatcher fat JAR (e.g. detecting an
  H2-less or out-of-date JAR up front and failing with a "run a reactor build" message) —
  explicitly deferred by the operator on 2026-05-17.
- Any change to the dispatcher `pom.xml` H2 scope — it is already correct on staging; the
  reported `mvn verify` failure was a stale-build artifact, not a code defect.
- Any production-code change, in `vvwt-tm-web` or any other module.
- The `Surefire is going to kill self fork JVM ... 30 seconds after System.exit(0)` symptom
  observed in the same build — a separate lingering-non-daemon-thread shutdown concern, not
  addressed here.
