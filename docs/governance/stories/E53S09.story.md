# Story: 1-based fieldNumber migration — L2 + Slot-Opt + Fallback emit 1-based; revert E53S07 read-side +1; Display SPA / Score-Tablet natural-aligned (operationalizes DEC-60)

## User Story

**As a** tournament operator using the public Display screen, the printed Laufzettel, and the score-tablet at venue,
**I want** the system to use 1-based field numbering end-to-end (matching physical signage convention "Feld 1, 2, 3" and consistent with the existing 1-based lapNumber convention established by E53S06),
**so that** (1) the Display SPA renders exactly K columns "Feld 1..K" for K configured fields (no ghost "Feld 0" column), (2) the score-tablet can resolve the active match for a given field (currently silent-broken: 1-based URL fieldNumber queried against 0-based DB column returns empty), (3) the score-tablet device-field equality check passes for legitimate scoring (currently throws ForbiddenException because device.assignedField=1 ≠ match.fieldNumber=0), and (4) a single coherent storage convention exists across L2 + Slot-Opt + DB + downstream consumers.

---

## Context

vvwt-tm-web has had an inconsistent field-number indexing convention since the L2/L3 layered decomposition (DEC-55 + DEC-56) was implemented:

- **L2 `DefaultRoundAssignmentService.java:200-203`** writes `fieldNumber` 0-based (`fieldIdx` loop counter starting at 0).
- **L3 `SlotResultApplicator.java:135`** writes `fieldNumber` 0-based (`outputField = i % fieldCount`), inconsistent with the immediately-adjacent line 134 `setLapNumber(outputLapIndex + 1)` which is 1-based per E53S06.
- **Fallback `FallbackSlotOptimizationClient.java:95`** writes `fieldNumber` 0-based (`idx % fieldCount`).
- **Class comment `SlotResultApplicator.java:34`** explicitly documents the asymmetry: *"E53S06 fix — lap numbers start at 1), `match.setFieldNumber(i % fc)`."* — the inconsistency is a known, documented artefact of E53S06's lap-only migration scope.
- **DB column `match.field_number`** (`db/migration/tournament/V1__initial_schema.sql:188`) — `INT NULL`, no CHECK constraint enforcing the index base.
- **Downstream consumers**:
  - `DefaultDisplayOverviewService.java:251` passes through 0-based `m.getFieldNumber()` to `DisplayMatchesResponse.MatchEntry` → SPA shows "Feld 0/1/2/3" for 3-field tournaments (Bug 1, T1 from prior Discovery cycle).
  - `DefaultScoreEntryService.java:285` compares 0-based `match.getFieldNumber()` with 1-based `device.getAssignedField()` → ForbiddenException on legitimate scoring once L2 has assigned a fieldNumber (Bug 3).
  - `DefaultScoreEntryService.java:424` queries `findByFieldNumberAndLapNumber(fieldNumber, lap)` with 1-based URL parameter against 0-based DB → returns empty list → operator scoring fails silently (Bug 2 — production bug, unverified-in-production-yet because score-tablet end-to-end is rarely exercised).
  - `DefaultLaufzettelAssembler.java:522/529` applied a read-side `+1` conversion (E53S07 PR #250 merged 2026-05-10T21:07:15) as interim print-output fix.
- **`Device.assignedField`** is 1-based (`Devices.svelte:765 <input type="number" min="1">` operator-input convention "Feldnummer", physical-signage-aligned + `DefaultDeviceService.java:334` direct passthrough write + `DefaultDeviceRepository.java:244-245` direct DB-bind read).
- **Score-tablet client** (`templates/score/field.mustache:367` + `:679`) constructs `/api/score/match?field=' + FIELD_NUMBER + '&token=...'` with 1-based `FIELD_NUMBER`.
- **5+ Javadoc contracts** (`DefaultScoreEntryService.java:163`, `ScoreEntryResult.java:33`, `DeviceRepository.java:60`, plus inferred others) declare 1-based as the public API contract.

**Predecessor analyses**:
- E53S06 (PR #248 merged 2026-05-10T20:48:13) is the direct precedent for a write-side L2+L3 1-based migration — same pattern, same skill-pattern (`outputLapIndex` 0-based intermediate + `+1` at `setLapNumber`), without DEC amendment.
- E53S07 (PR #250 merged 2026-05-10T21:07:15) chose Approach B (read-side scatter) for the print output, leaving the Display SPA + Score-Tablet bugs explicitly handed-off to Discovery in its impl-report blast-radius analysis.
- Discovery 2026-05-10 cycle authored `evaluations/2026-05-10-field-number-indexing-strategy.approach-evaluation.md` (3 approaches A/B/C); user chose Approach A (write-side L2 1-based) with no schema-data-migration; user authorized DEC-60 (delta-amendment to DEC-56 D-1) to formalize the convention. Brief `discovery-2026-05-10-field-number-indexing-strategy` Tier-2 reviewer cycle 2 PASS; user-validated 2026-05-10.

This Story operationalizes DEC-60 D-1 (1-based-from-L2 convention) by completing the symmetric pattern E53S06 established for lapNumber.
