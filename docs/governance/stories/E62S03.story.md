# Story E62S03: Live delta publication — TM tournament events → Info-Portal, with `409 FULL_RESYNC` snapshot recovery

## User Story

**As a** participant following a tournament that has been published to the Info-Portal,
**I want** my team's Info-Portal page to update as the tournament progresses,
**so that** I see current schedule and results without the operator re-publishing
anything by hand.

---

## Context

Once a tournament is opted in and registered (E62S02), the TM must keep the info-server
current by pushing **deltas** as the tournament progresses. The TM already has a
tournament-context domain-event system: the events in `de.vvwt.tm.tournament.events` (a
Spring Modulith `@NamedInterface("events")` sub-package) — `MatchResultChangedEvent`,
`PhaseStatusChangedEvent`, `LapAdvancedEvent`, `DeviceRegisteredEvent`. This story
subscribes the `de.vvwt.tm.infoportal` module to the participant-relevant events and
publishes each as a `vvwt-info-dto.DomainEvent` delta via
`InfoPortalPublisherService.publishDelta(...)`.

The publisher's `409 FULL_RESYNC` contract (Brief S-4; DEC-42 §Impact — the info-server
returns `409 Conflict {required: "FULL_RESYNC"}` on out-of-order arrival): when the
info-server has lost state, a publish returns `409`; the TM recovers by posting a fresh
full snapshot (built by E62S01's builder) — there is no outbound queue.

Publication must be **best-effort and asynchronous**: a failing or unreachable info-server
must never block or break the operator's core tournament workflow. The event listener is
therefore an async / after-commit listener — the tournament-event path must carry no
synchronous hard dependency on the info-server.

## Acceptance Criteria

- [ ] **AC1 (testing)**: Every new production class is authored RED-first per the DEC-22
  Iron Law; the RED state is evidenced in `impl-report.md`.
- [ ] **AC2 (testing)**: For an opted-in tournament, a participant-relevant
  tournament-progress domain event from the `de.vvwt.tm.tournament.events` event set
  results in `publishDelta(...)` being invoked with the corresponding
  `vvwt-info-dto.DomainEvent`. Verified per mapped event type. The TM-event →
  `DomainEvent` mapping — including which events are participant-relevant — is derived
  from the live `vvwt-info-dto.DomainEvent` contract and the TM event set at delivery
  HEAD; this story carries no hardcoded mapping table.
- [ ] **AC3 (testing)**: Negative cases produce no publish call, verified by tests —
  (a) any event for a tournament that is **not** opted in; (b) an event on an opted-in
  tournament that is **not** participant-relevant (a TM-internal event with no
  participant-facing meaning maps to no delta). The participant-relevant in/out partition
  of the event set is determined at delivery HEAD and recorded in `impl-report.md`.
- [ ] **AC4 (error-handling)**: On a `409 FULL_RESYNC` response to a delta publish, the
  wiring posts a fresh full snapshot (via the E62S01 builder) and publication resumes —
  verified by a test that drives a `409` and asserts the snapshot resync. The resync
  outcome (recovery succeeded / still failing) is reflected in the publication-state
  surface (`PublisherStatus`).
- [ ] **AC5 (error-handling)**: Publication is best-effort and asynchronous — the event
  listener runs async / after-commit, so a failing or unreachable info-server during
  delta publication never blocks or breaks the TM tournament workflow. A test asserts the
  tournament-event path completes normally when the publisher fails; failures surface via
  `PublisherStatus`, not as an exception propagated into tournament processing.
- [ ] **AC6 (security)**: Delta publication uses the publisher service's existing signed
  path (DEC-6 / DEC-43) — this story invokes `publishDelta(...)`; it does not bypass or
  re-implement signing.
- [ ] **AC7 (governance)**: The event listener consumes the `de.vvwt.tm.tournament.events`
  events via the `tournament::events` `allowedDependencies` edge. That edge is declared by
  E62S01; this story verifies the edge is present at delivery HEAD and, if E62S01's
  delivery scoped it otherwise, declares it itself — so this story's
  `ApplicationModules.verify()`-green outcome is not silently contingent on another
  story. The listener is an async / after-commit listener (per AC5 / no synchronous
  info-server dependency). `ApplicationModules.verify()` passes; `mvn verify` from the
  `vvwt-prj` root is BUILD SUCCESS (DEC-54).
- [ ] **AC8 (governance)**: Skill attestation per the Epic; governance artefacts
  propagated into `vvwt-prj/docs/governance/` per DEC-23 / DEC-31; committed to `staging`
  per DEC-13.

## Notes

- The exact TM-event → `vvwt-info-dto.DomainEvent` mapping and the participant-relevant
  in/out partition are derived at delivery HEAD from the live `DomainEvent` contract.
  `DeviceRegisteredEvent` is a TM-internal concern with no participant-facing meaning and
  is the expected example of an opted-in event that maps to no delta (AC3 b) — but the
  in/out set is re-audited against the live contract; the story carries no precomputed
  mapping.
- The async listener mechanism (e.g. `@ApplicationModuleListener`, or
  `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`) is a Delivery/Planning choice;
  the story pins only the behavioural requirement that the tournament-event path carries
  no synchronous hard dependency on the info-server (Brief Q-4).
- `409 FULL_RESYNC` resync posts the snapshot at the current sequence number — the
  sequence is not reset (E38 / E38S09 AC12 semantics).
