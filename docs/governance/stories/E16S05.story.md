# Story E16S05: Fix — Tournament Manager test runs accumulate per-context temp directories in the system temp directory, exhausting host disk

## User Story

**As a** developer running the Tournament Manager reactor build (and the delivery daemon,
which runs `mvn verify` once per story),
**I want** a test run to leave no temp artefacts behind in the shared OS temp directory,
**so that** repeated builds do not slowly exhaust the host's `/tmp` filesystem and cause
unrelated stories to fail or escalate on disk-exhaustion errors.

---

## Context

`E16S03` (PR #150, done) stopped per-tenant test databases leaking into `~/.vvwt-tm/` by
giving every test its own isolated data root. The mechanism is the test-profile config in
`vvwt-tm-web/src/test/resources/application-test.yml`:

```yaml
tm:
  data:
    dir: ${java.io.tmpdir}/vvwt-tm-test-${random.uuid}
```

The isolation works — but it has an unbounded side effect. `${random.uuid}` resolves to a
fresh value for every Spring test context, so every context creates a brand-new
`/tmp/vvwt-tm-test-<uuid>/` directory. **Nothing ever deletes those directories.** A single
`mvn verify` of `vvwt-tm-web` (169 `@SpringBootTest`-profile test files, with Spring
context-caching producing many distinct contexts) leaves hundreds of them; embedded-Tomcat
base/docbase directories (`tomcat.*`, `tomcat-docbase.*`, which also resolve under
`java.io.tmpdir`) add hundreds more. Because the delivery daemon runs `mvn verify` once per
story, the OS temp directory grows without bound.

On 2026-05-17 this exhausted the host disk: `/tmp` reached 100 %, and story **E63S09**
escalated when its `mvn verify` failed with H2 I/O errors that the QA report misattributed to
pre-existing code defects (see memory `feedback_disk_exhaustion_fails_mvn_verify`). The
escalation was purely environmental — a clean baseline built green once disk was freed. This
story removes the recurring cause so the disk cannot be exhausted again by ordinary builds.

This is a test-infrastructure fix in the E16 (Test Infrastructure Governance) family — the
direct successor to E16S02 (test-DB isolation) and E16S03 (`tm.data.dir` test-isolation). It
changes no production code.

---

## Root Cause Analysis

Investigation (Discovery, 2026-05-17 — root cause established empirically, not implemented):

- **Why the directories are created.** `application-test.yml` sets `tm.data.dir` to
  `${java.io.tmpdir}/vvwt-tm-test-${random.uuid}`. `${random.uuid}` is re-evaluated per
  Spring `ApplicationContext`, so each cached context gets a distinct directory under the
  OS temp root. The Tournament Manager application creates that directory at startup as its
  tenant data root (`tenant-registry.json` + `tenants/`).

- **Why they are never deleted.** `tm.data.dir` is an *application* property — the
  application's own data root — not a JUnit-managed `@TempDir`. JUnit's temp-directory
  cleanup never sees it. The application itself must not delete its data root on shutdown
  (in production that would destroy live tenant data). So the directory simply outlives the
  test JVM. The same applies to embedded Tomcat's `tomcat.*` / `tomcat-docbase.*` working
  directories, which Tomcat also places under `java.io.tmpdir`.

- **Why it accumulates without bound.** Each `mvn verify` run repeats this; the delivery
  daemon runs `mvn verify` once per delivered story; the directories from every past run
  remain. The OS temp directory (`/tmp`, a fixed-size tmpfs on the build host) therefore
  fills monotonically. Empirically on 2026-05-17 the host's `/tmp` held thousands of orphan
  `vvwt-tm-test-*` directories totalling ~1.9 GB.

**Reproduction scenario:**
- **Given** the Tournament Manager reactor on `staging`,
- **When** `mvn verify` runs the `vvwt-tm-web` test suite, and the run is repeated (as the
  delivery daemon does for every story),
- **Then** each run leaves orphan `vvwt-tm-test-*` (and embedded-Tomcat `tomcat.*` /
  `tomcat-docbase.*`) directories in the shared OS temp directory that are never removed —
  repeated runs accumulate them without bound until the host temp filesystem is exhausted.

**Expected behaviour after the fix:** test runs place all test-created temporary artefacts
under the Maven module build directory, not the shared OS temp directory. `mvn clean` (and
the daemon's worktree teardown) remove them. Repeated `mvn verify` runs accumulate nothing
in the OS temp directory. The implementation mechanism is Delivery's to determine.

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-TEMP-BUILD-SCOPED** — Tournament Manager test runs place every test-created
  temporary artefact — the `tm.data.dir` per-context tenant tree, and the temp working
  directories of any test-spawned embedded server or forked JVM (embedded-Tomcat
  base/docbase, etc.) — under the Maven module build directory (`target/`), not under the
  shared OS temp directory (the default `java.io.tmpdir`, e.g. `/tmp`). A repeated
  `mvn verify` therefore creates nothing in the OS temp directory and accumulates nothing
  there across runs.
- [ ] **AC-TEST-REGRESSION-GUARD** — an automated, deterministic test guards the fixed
  behaviour: it fails on the pre-fix configuration and passes after the fix. It asserts that
  the temp root resolved by the test profile (the `tm.data.dir` resolution at minimum) lies
  under the module build directory and not under the OS default temp directory. Delivery
  determines the test's location and mechanism and classifies it per DEC-22.
- [ ] **AC-TEST-REACTOR-SUITE-GREEN** — `mvn verify` is BUILD SUCCESS for the full reactor;
  `mvn clean` removes the test temp artefacts (they reside under `target/`); no pre-existing
  test regresses (DEC-54 / DEC-71).

### Governance

- [ ] **AC-GOV-PROD-CANON-UNTOUCHED** — the fix is test-scoped only. The production
  `tm.data.dir` default and the DEC-68 filesystem-path canon are not altered: no change to
  `application.yml` or to any production Java path-default code. Changes are confined to test
  resources, build descriptors (POM), and test code. The fix relocates only where *test*
  JVMs put temporary files; production filesystem behaviour is unchanged.
- [ ] **AC-GOV-TDD-CLASSIFICATION** — Delivery classifies the change per DEC-22 (and its
  amendment DEC-67, which places build-descriptor / build-configuration changes outside the
  RED-first Iron Law): the fix authors build-descriptor configuration and/or test-profile
  configuration plus the AC-TEST-REGRESSION-GUARD test — no first-party production code — so
  it is not a production-feature change requiring RED-first production code; the regression
  guard is authored per that classification (RED on the pre-fix configuration, GREEN after).
- [ ] **AC-GOV-BUILD-HYGIENE** — `mvn verify` exits zero (DEC-54 / DEC-71); the build is
  warning-free (DEC-29); Spotless / google-java-format and the SPDX license header are clean
  on any new or modified Java file (DEC-30 / DEC-76); no production member exists solely for
  tests (DEC-70).

## Out of Scope

- **The one-time removal of temp directories already accumulated in `/tmp`** from past test
  runs — that is an operational host-cleanup action, not part of this code fix.
- **An operational `/tmp` sweep hook** in the delivery daemon or `close-story.sh` — the
  operator chose the root-cause fix (option A) over an operational mitigation on
  2026-05-17; the sweep-hook option is explicitly not pursued by this story.
- **The recurring `close-story.sh` worktree-cleanup leak** — a separate delivery-environment
  hygiene defect (silently-failing `git worktree remove`) flagged during the E63S09 triage;
  it is in the GAAI framework, not in `vvwt-prj`, and is a distinct triage.
- **Any production-code change**, in `vvwt-tm-web` or any other module.

## Notes

Discovery 2026-05-17 — Bug-Triage Story, parent epic **E16** (Test Infrastructure
Governance; successor to E16S02 test-DB isolation and E16S03 `tm.data.dir` test-isolation).
No Session Brief — single-session triage; the root cause was established empirically
in-session by inspecting the live host (`/tmp` holding ~9.5k orphan `vvwt-tm-test-*`
directories, ~1.9 GB) and tracing the prefix to `application-test.yml:42`. Surfaced while
triaging the E63S09 escalation, whose `mvn verify` failure was caused by the resulting host
disk exhaustion (memory `feedback_disk_exhaustion_fails_mvn_verify`).

Implementation guidance (NOT acceptance criteria — Delivery owns the mechanism): the obvious
single lever is to point the test JVMs' `java.io.tmpdir` at a build-directory-scoped path
(e.g. `${project.build.directory}/...`) via the parent POM's `maven-surefire-plugin` /
`maven-failsafe-plugin` `systemPropertyVariables` — Discovery verified those `pluginManagement`
entries currently carry no `<configuration>`, so the addition is clean. Because
`application-test.yml` resolves `${java.io.tmpdir}` directly, redirecting that one property
relocates `vvwt-tm-test-*`, the embedded-Tomcat directories, and Mockito/Surefire fork temp
all at once. Whether to set it parent-POM-wide or per module, via `systemPropertyVariables`
or `argLine`, and whether `application-test.yml` itself should additionally be retargeted,
is Delivery's decision; Discovery confirmed only that the approach is feasible and
collision-free on current `staging`.
