# Story: Fix — PIN not displayed on `/score/register` when device.status == REGISTERED (E49S01 follow-up)

## User Story

**As a** tournament operator,
**I want** the scoring-tablet registration page (`/score/register`) to display a usable PIN whenever the tablet is in REGISTERED status (i.e., not yet bound to a field),
**so that** I can complete the inline-row field-assignment flow (PIN + field-number + click "Feld zuweisen" in Devices.svelte) regardless of whether the tablet's browser was previously connected to this Tournament Manager.

---

## Context

E49S01 (PR #213, merged 2026-05-08) introduced the **out-of-band PIN flow**: the device PIN is shown ONLY on the registering tablet (out-of-band channel) and is the proof-of-possession token an admin must type to bind the tablet to a court. The PIN was removed from the admin device-list response (E49S01 D-13 "list-PIN-omission server-side") and from any other admin-visible surface.

**Symptom (verified by user screenshot 2026-05-13 23:06:47):** On a tablet whose browser holds a device-token in localStorage/cookie from a prior registration, opening `/score/register` shows the status text "Wird zugewiesen…" indefinitely with **no PIN visible**. The operator cannot type a PIN they cannot see, so the inline-row field-assignment flow is blocked. E49's success metric ("scorekeeper assigned to a court in three keystrokes") is unreachable for the common revisit case.

**Root cause (verified):**

- `register.mustache:524–533` (`init()`): if `localStorage` / cookie holds a `vvwt_device_token`, the page calls `validateExistingToken(token)` instead of `registerDevice()`.
- `register.mustache:463–508` (`validateExistingToken()`): on `GET /api/devices/status` success with `data.status` != "ASSIGNED", calls `startPolling(token)` — **never displays the PIN**.
- `register.mustache:484–491` contains an explicit inline NOTE acknowledging the gap: *"The server does not return the PIN on status checks. We do not have the PIN to display here without re-registering."*
- `DeviceStatusResponse.java` fields = `{status, assignedField, registeredAt, deviceName, configuration}` — **no `pin` field**. Verified.
- The device row's PIN value persists in the DB (E07S01 V8 migration column; DEC-24 §E "PIN per-device lifetime-stable until removal") — the data is present, only the surfacing channel is missing.

**Operational trigger** (Brief O-9): the bug fires whenever an admin clicks "Zuweisung aufheben" (`PUT /api/devices/{id}/unassign`) in Devices.svelte to reassign a tablet to a different field. The unassign transitions the device row back to `status = REGISTERED` with PIN preserved; the operator then walks to the tablet to reassign it, but `/score/register` cannot surface the PIN.

**Status semantics (clarified):**

- `REGISTERED` (`Device.java:40`) — device has a token, not currently bound to a field. Reached after `POST /register` (fresh) or `PUT /unassign`.
- `ASSIGNED` (`Device.java:43`) — device is bound to a field. Existing redirect to `/score/field/{n}` is unchanged.
- `DISCONNECTED` (`Device.java:46`) — **never SET in production main code** (verified by project-wide grep — only read in `DeviceTokenHandshakeInterceptor`; only set in test fixtures). Treated as dead-code-reachable; out-of-scope to specify.

This is a Bug-Triage Story. Discovery defines the observable outcome (PIN visible when `status == REGISTERED`); Delivery defines the mechanism (extend `/status` payload with PIN, add new tablet-only endpoint, client-side PIN cache at registration, or other — see Notes).

The exact assertion shape is mechanism-dependent and is Delivery's responsibility (see § Notes — Mechanism Candidates).

- [ ] **AC-TEST-PIN-STABLE-PER-REVISIT-GREEN**: A test asserts that the PIN shown on a revisit equals the PIN that was assigned to the device row at registration (DEC-24 §E PIN lifetime-stable preserved). No PIN rotation on revisit. If Delivery uses a client-side PIN cache, the cached value MUST match the device's server-side `pin` column.

- [ ] **AC-TEST-PIN-NOT-EXPOSED-WITHOUT-DEVICE-TOKEN-RED**: A test asserts that the PIN value is NOT readable by callers that do not present a valid device-token bound to the device whose PIN is requested. - [ ] **AC-TEST-FRESH-REGISTRATION-PIN-VISIBLE-PRESERVED-GREEN**: Regression-guard — a fresh tablet (no localStorage token) opening `/score/register` still receives a PIN from `POST /api/devices/register` and the PIN is displayed (existing E06S04 AC2 behavior unchanged).

- [ ] **AC-TEST-ASSIGNED-REDIRECT-PRESERVED-GREEN**: Regression-guard — a tablet whose token resolves to `status = ASSIGNED` is redirected to `/score/field/{assignedField}` per existing E06S04 AC5 behavior (no PIN exposed at any point in this path).

- [ ] **AC-TEST-INVALID-TOKEN-CLEAR-AND-REREGISTER-PRESERVED-GREEN**: Regression-guard — a tablet whose token returns 404 from `GET /api/devices/status` (e.g., device was "Entfernt"/`DELETE`d server-side) clears localStorage + cookie and performs a fresh `POST /register`, showing the new PIN (existing E06S04 AC6 behavior unchanged).

- [ ] **AC-TEST-LIST-PIN-OMISSION-PRESERVED-GREEN**: Regression-guard — `GET /api/devices/list` response (admin-session caller) MUST NOT contain `pin` for any device (E49S01 D-13 preserved). Verified by JSON-payload assertion on the list endpoint with at least one REGISTERED SCORING_TABLET fixture.

- [ ] **AC-TEST-LOGS-NO-PIN-LEAK-GREEN**: Regression-guard via logback list-appender IT (consistent with E49S01 AC10) — any new PIN-surfacing code path MUST NOT emit the PIN value into server logs, audit logs, error responses, or response headers. ## Notes

**Mechanism Candidates (Discovery enumerates non-prescriptively; Delivery picks ONE — Brief D-4):**

- **M-A**: Extend `/api/devices/status` response with a `pin` field, returned only when the caller authenticates via the device's own device-token (i.e., the token in the query string belongs to the device whose status is queried). Admin-session callers continue to call a different endpoint (`/list`) which remains PIN-free. Requires `DeviceStatusResponse.java` schema change.
- **M-B**: Add a new tablet-only endpoint, e.g., `GET /api/devices/pin?token={token}`, returning only the PIN (or 404 if token invalid, 410 if device is ASSIGNED — Delivery's call on the not-applicable-status response code). Smaller surface than M-A; orthogonal to `/status`.
- **M-C**: Client-side PIN cache — `register.mustache` stores `pin` alongside `vvwt_device_token` in localStorage/cookie at initial registration time (line 444 `storeToken(data.deviceToken)` extended to also store PIN). On revisit, `validateExistingToken` reads PIN from the same storage. NO server changes. Cache invalidation on `clearToken()` is mandatory (AC-ERROR-CACHED-PIN-INVALIDATION applies). Trade-off: PIN value lives in the tablet's persistent storage — acceptable because the tablet is the legitimate holder of the device-token and the PIN is bound to that tablet by design (E49S01 threat model).
- **M-D**: Any other mechanism Delivery proposes that satisfies all ACs and does not require DEC-24 amendment.

Each option has different security and IT-shape implications. Discovery does not pre-select to avoid over-constraining Delivery. Delivery's qa-report MUST cite which mechanism was chosen and why (1–2 sentences).

**Reproduction (manual)**:

1. Open `/score/register` in a fresh browser (no localStorage token). PIN displays (current behavior — correct).
2. Without assigning the device, close the browser tab.
3. Re-open `/score/register` in the same browser. PIN is **not** displayed; status reads "Wird zugewiesen…" indefinitely. ← bug.

Alternative reproduction via admin path:

1. Register a tablet (PIN displays).
2. Admin assigns the device to a field via Devices.svelte (tablet redirects to `/score/field/{n}`).
3. Admin clicks "Zuweisung aufheben" (`PUT /unassign`) on the device row.
4. Walk to the tablet, open `/score/register`. Status: "Wird zugewiesen…", no PIN. ← bug.

**Inline-code NOTE (`register.mustache:484–491`)** documents the known-but-unresolved gap from E49S01:

> *"NOTE: The server does not return the PIN on status checks. We do not have the PIN to display here without re-registering. Show the waiting message and start polling with the existing token."*

This is cited for traceability per Brief Q-3 — no blame, just evidence that the gap was visible at E49S01 close.

**H-1 (UNVERIFIED, likelihood LOW)** — user's "zum 1. Mal" observation in the conversation may indicate a second bug variant (fresh-tablet `POST /register` returning no PIN). Screenshot evidence (status = MSG_WAITING without error banner) is inconsistent with this code path — if `/register` returned no `pin`, `register.mustache:440` would set `MSG_ERROR_REG` and show the error banner, not "Wird zugewiesen…". Delivery's `AC-TEST-FRESH-REGISTRATION-PIN-VISIBLE-PRESERVED-GREEN` regression test catches the alternate variant if it exists. If that regression test fails on the unmodified production code, STOP and escalate to Discovery before proceeding — this Story does not cover that variant.
