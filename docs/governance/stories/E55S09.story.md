# Story E55S09 (Bug-Triage; cycle-4 refinement post-escalation): structural fix for H-B stale-entity-save in `OrchestratorStepAExecutor` + `DefaultJobDrainService` + H-F restart-recovery tenant-binding gap in `DefaultWorkerRegistry.initOnStartup()` — replace full-entity `phaseRepository.save(phase)` with column-scoped `updateLastJobState` writes per DEC-64 intent; RED-first ITs structurally simulate the stale-save pattern (no interactive browser reproduce required)

## User Story

**As a** Tournament Manager operator,
**I want** the orchestrator's `last_job_state` writes to NOT overwrite my concurrent operator-driven phase transitions (Team-Zuordnung, Phase aktivieren) with stale `status` values,
**so that** the structural elimination promised by E55 Saga-Orchestrator pivot (DEC-64) is actually structurally honored — by removing the producer's capability to write whole-entity state, not by symptom-patching observed regressions.

### Delivery's static-analysis findings (preserved from execution-plan)

**H-B structurally CONFIRMED at TWO call sites:**

1. **`OrchestratorStepAExecutor.executeStepA()` lines 144-150** (identified by Discovery cycle-3 audit):
   ```java
   Phase phase = phaseRepository.findById(phaseId).orElseThrow(...);
   phase.setLastJobState(stepADoneState);
   phaseRepository.save(phase);
   ```

2. **`DefaultJobDrainService.writeMatchGenRunning()` lines 152-160** (NEW site identified by Delivery static analysis):
   ```java
   Phase phase = phaseRepository.findById(...).orElseThrow(...);
   phase.setLastJobState(MATCH_GEN_RUNNING);
   phaseRepository.save(phase);
   ```

Both sites invoke `phaseRepository.save(phase)` which delegates to `DefaultPhaseRepository.UPDATE_SQL`:
```sql
UPDATE phase SET description=?, status=?, current_lap_number=?, optimized=?, last_job_state=? WHERE id=?
```

The UPDATE writes ALL mutable fields, including `status` and `optimized`. **No Spring Data change-tracking** — every save is a full-entity overwrite. If the entity is read with a stale `status` (e.g., `status='PREPARED'` after step-A's own `transition(PREPARED, "match-gen-done")` write), and operator-driven transitions to ASSIGNED → ACTIVE have occurred subsequently, the save() at line 150 / 159 overwrites the operator's ACTIVE with the stale PREPARED. This is the H-B stale-entity-save pattern.

The static-analysis confirmation is sufficient to author the structural fix without empirical producer-identification, because the structural fix is independent of which trigger fires (H-B is the mechanism, the trigger is downstream of the mechanism's existence).

**H-F structurally CONFIRMED — restart-recovery silently disabled in production:**

*Contradiction-acknowledgment per cycle-4 cycle-2 review F-7:* the production code comment at `DefaultWorkerRegistry.java:174-176` asserts *"In production, a tenant is always bound by the routing DataSource infrastructure before any DB call"*, which directly contradicts Delivery's static-analysis claim that no tenant is bound at `@PostConstruct`. The contradiction may indicate either (a) the code-comment is stale and Delivery is right (H-F is real), OR (b) the code-comment is right and there IS some tenant-binding mechanism at @PostConstruct that Delivery missed. AC-TEST-H-F-INITONSTARTUP-RUNS-FOR-REGISTERED-TENANTS-RED must FIRST verify Delivery's claim empirically on the pre-fix codebase (e.g., add a probe log statement before `jobRepository.handleCorruptRunningRows()` and confirm whether tenant is bound or unbound at that point in production startup). If the code-comment is right and tenant IS bound at @PostConstruct, then H-F does not exist as Delivery described — Discovery must re-refine.

`DefaultWorkerRegistry.initOnStartup()` runs at `@PostConstruct` time. Per Delivery's static analysis, at @PostConstruct execution **no tenant context is bound** (the `TenantContextResolver` HandlerInterceptor only binds on per-request entry, not at app-init). The method is wrapped in try-catch (`DefaultWorkerRegistry.java:177-186`):

```java
try {
    String currentJvmId = resolveCurrentJvmId();
    initOnStartup(currentJvmId);
} catch (Exception e) {
    LOG.warn(
        "[phaselifecycle] initOnStartup skipped during @PostConstruct: {} — "
        + "recovery will not run (expected in test contexts without"
        + " a bound tenant; E55S07, DEC-64 D-7)",
        e.getMessage());
}
```

When `initOnStartup(currentJvmId)` calls `jobRepository.handleCorruptRunningRows()` or `jobRepository.resetStaleRunningJobs(currentJvmId)` or `jobRepository.findTournamentsWithNonCompletedJobs()`, the fail-fast `RoutingTenantDataSource.determineCurrentLookupKey()` (line 109-111) throws `IllegalStateException` because no tenant is bound. The exception is swallowed by the outer try-catch with a WARN log. **Recovery never runs in production for any tenant.** DEC-64 D-7's restart-recovery guarantee is structurally void.

This is a SEPARATE structural bug from H-B but compounds the M-2/M-3 reproduce path: any app-crash or operator-restart between phase-orchestrator-pipeline-completion and operator-activation breaks the recovery contract.

**M-5 (Phase 2 PREPARED→PENDING + 18 matches DELETED + optimized=TRUE→FALSE) — producer NOT identified by static analysis:**

Static analysis ruled out: `cascadeDeleteStructuralData` (private; only called from `resetPlan()` requiring PLANNED tournament — not applicable post-activation, AND `deleteTournament()` requiring non-ACTIVE), `draftService.apply()` (requires DRAFT tournament — not applicable), `DefaultDeviceService.configure()` (only touches device fields). The M-5 signature (match-deletion + phase-status→PENDING + last_job_state→NULL combined) matches `cascadeDeleteStructuralData + draft.apply re-creation` but no guarded code path can trigger this post-activation. **M-5 producer remains unidentified by static analysis** and is **explicitly deferred** to a follow-up Bug-Triage Story (E55S10, to be authored if M-5 persists after the H-B + H-F structural fix lands).

## Acceptance Criteria

### Structural fix (Governance + implementation)

- [ ] **AC-FIX-H-B-PHASE-REPOSITORY-UPDATE-LAST-JOB-STATE-METHOD** (governance): Author new method `Phase updateLastJobState(UUID phaseId, String lastJobState)` on the public `PhaseRepository` interface (`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/PhaseRepository.java`), per DEC-58 universal-interface-mandate. Implementation in `DefaultPhaseRepository` (`.internal` per DEC-35) executes column-scoped SQL: `UPDATE phase SET last_job_state = ? WHERE id = ?`. Method returns the updated phase entity (fresh read after UPDATE) OR throws if the phase no longer exists. DOES NOT TOUCH any other phase column — specifically NOT `status`, NOT `optimized`, NOT `current_lap_number`, NOT `description`.

- [ ] **AC-FIX-H-B-ORCHESTRATOR-STEP-A-COLUMN-SCOPED** (governance; DEFENSE-IN-DEPTH per cycle-4 cycle-2 review F-11): Eliminate the full-entity-save semantics at `vvwt-tm-web/src/main/java/de/vvwt/tm/phaselifecycle/internal/OrchestratorStepAExecutor.java:150`. The implementation MAY use the new `phaseRepository.updateLastJobState(phaseId, stepADoneState)` method (preferred for code-symmetry with the `DefaultJobDrainService` fix) OR an equivalent column-scoped mechanism that writes only `last_job_state` without touching other phase fields. Eliminate the intermediate `findById` + `setLastJobState` calls (lines 144-149) — they are no longer needed for the column-scoped write. The orchestrator's `transition(PREPARED, "match-gen-done")` call at line 134 remains unchanged (it is the canonical status writer per DEC-55 D-4 and is ALLOWED-graph-guarded). Note: this call-site is STRUCTURALLY PROTECTED from H-B by the preceding transition-guard, so this AC is DEFENSE-IN-DEPTH (eliminating the latent producer surface even though no reachable trigger currently exercises it). Reviewer-verified per cycle-4 cycle-2 substance check #11. Skipping this AC would leave a latent risk if the transition-guard upstream is ever weakened.

- [ ] **AC-FIX-H-B-JOB-DRAIN-SERVICE-COLUMN-SCOPED** (governance; PRIMARY H-B fix per cycle-4 cycle-2 verification — this is the only call-site where H-B is reachable, since `writeMatchGenRunning` has no pre-save transition-guard): Eliminate the full-entity-save semantics at `vvwt-tm-web/src/main/java/de/vvwt/tm/phaselifecycle/internal/DefaultJobDrainService.java:160` (within `writeMatchGenRunning()` at lines 152-160). The implementation MAY use the new column-scoped `updateLastJobState` method (preferred for symmetry) OR an equivalent mechanism that writes only `last_job_state`. Eliminate the intermediate `findById` + `setLastJobState` lines.

- [ ] **AC-FIX-H-B-NO-OTHER-FULL-ENTITY-SAVE-SITES** (governance): Audit all `phaseRepository.save(phase)` call sites in the phaselifecycle module — verify no remaining sites perform full-entity-save for the purpose of writing only `last_job_state` or only `optimized`. Each remaining `save(phase)` MUST be intentional (i.e., the call site genuinely modifies multiple fields and accepts the multi-field write semantics). Document the audit in qa-report with a per-call-site verdict.

- [ ] **AC-FIX-H-B-NO-PATCH-FOR-SYMPTOM** (governance): Forbidden: do NOT add a "guard against backward status transition" check in `DefaultPhaseRepository.save()` or `Phase.setStatus()` or any wide-cast guard. Such a guard is a symptom-patch and violates DEC-64 intent + `feedback_discovery_cycle_resolution_scope_creep.md` (trace failure to producer first; don't band-aid). The column-scoped UPDATE method is the SINGLE sanctioned structural fix for H-B.

- [ ] **AC-FIX-H-F-INITONSTARTUP-TENANT-BINDING** (governance): Fix the silent-skip behavior in `DefaultWorkerRegistry.initOnStartup()` (called from `@PostConstruct` at line 163-187). Two acceptable structural fixes:
  - **Option (i) — Per-tenant binding inside initOnStartup**: enumerate registered tenants via `TenantRegistry` (or equivalent), bind tenant context per-tenant, call `jobRepository.handleCorruptRunningRows()` + `jobRepository.resetStaleRunningJobs()` + `jobRepository.findTournamentsWithNonCompletedJobs()` per bound tenant, unbind tenant in finally block.
  - **Option (ii) — Move recovery to per-tenant lifecycle hook**: move the initOnStartup call out of `@PostConstruct` into a per-tenant-DataSource-initialization-complete hook in `DefaultTenantBootstrapRunner` (which already runs at `@Order(1)` ApplicationRunner with tenant binding established). The `@PostConstruct` only starts the idle-poller; recovery fires per-tenant when that tenant's DataSource is first registered.
  Implementer chooses (i) or (ii) based on minimal-blast-radius; document choice in impl-report. Either way, the `catch (Exception e)` block at line 180-185 MUST be removed or replaced — silently swallowing `IllegalStateException` is the bug; an actual IllegalStateException post-fix means a real recovery failure that warrants escalation, not WARN-log-and-skip.
