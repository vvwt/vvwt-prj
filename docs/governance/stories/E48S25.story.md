# Story E48S25: Operator Match Score Correction + Nacherfassung — REST + Admin SPA (active-phase-only; DEC-65 D-7 correction-window; audit-only for CANCELED)

## User Story

**As a** Tournament Organizer (Admin),
**I want** to correct entered match scores and enter missing sets (Nacherfassung) for matches in the currently-active phase via the Admin SPA,
**so that** typos or gaps in tablet-entered data can be fixed within the operator-correction-window (DEC-65 §D-7) without database-level intervention; corrections cascade to ratings + standings + WebSocket push for FINISHED-state changes, or are recorded audit-only for CANCELED matches, preserving tournament-protocol integrity.

### Functional Scope (V1)

| Match-state | Phase-state ACTIVE | Behavior |
|---|---|---|
| `OPEN(0)`, `ENABLED(10)` | ACTIVE | Nacherfassung: admin enters all sets → match transitions to `FINISHED_*` → single transactional cascade-recompute per match. |
| `FINISHED_WINNER1(51)`, `FINISHED_WINNER2(52)`, `FINISHED_STANDOFF(50)` | ACTIVE | Korrektur: admin modifies existing set values → cascade-recompute (ratings + standings + WS push) per submit. |
| `CANCELED(-10)` | ACTIVE | Audit-only: `audit_log` row written with proposed score; `match.state` stays CANCELED; NO cascade, NO WS push, NO ratings/standings change. |
| `INPROGRESS(30)`, `ONCHECK(35)` | ACTIVE | **Forbidden** in V1 — HTTP 409 (avoid race with live Score-Tablet writes). |
| any | non-ACTIVE (PENDING / PREPARED / ASSIGNED / COMPLETED) | **Forbidden** in V1 — HTTP 409 (active-phase-only constraint per DEC-65 §D-7 correction-window). |

Tournament-status guard is **derivative**: only `tournament.status = ACTIVE` can host an ACTIVE phase. PLANNED / COMPLETED / CANCELLED / DRAFT tournaments have no ACTIVE phase → correction effectively forbidden (defense-in-depth HTTP 409 on the rare race where state changes mid-request).

### DEC-65 Operator-Correction-Window Alignment

DEC-65 (2026-05-12, active) explicitly preserves the operator-correction-window structurally: after the last lap of a phase finalizes, `phase.currentLapNumber` writes sentinel-0 in-place, `phase.status` remains ACTIVE until operator manually clicks "Phase abschließen" (verb-encoded `transition(phaseId, COMPLETED, ·)`). This story's active-phase-only constraint **operates within that window**: corrections are allowed as long as the phase is ACTIVE; once operator transitions to COMPLETED, corrections are locked out (S-9 Re-Open territory). DEC-65 operationalization is DEFERRED post-Epic-E55 (per DEC-65 §D-8) — independent of this story; this story's code MUST NOT touch `phase.currentLapNumber` (preserves both pre- and post-DEC-65-operationalization paths).

### Operational Workflow

1. Operator opens Admin SPA → navigates to Phase view of the ACTIVE phase.
2. Each match row shows "Korrigieren" link (only when phase ACTIVE + match.state ∉ {INPROGRESS, ONCHECK}).
3. Click → navigate to correction route → load match detail (REST GET) → display current sets + recent audit-log entries.
4. Edit a set value (or enter all sets for OPEN/ENABLED Nacherfassung) → optional reason free-text.
5. Click "Submit" → confirmation dialog with pre-vs-post values (Brief Q-6 deliberate-action UX).
6. Confirm → REST POST/PUT → backend acquires DEC-37 Clause B lock (FINISHED-state path) OR skips lock (CANCELED audit-only) → cascade-recompute or audit-only write → audit_log row → WS push (if cascade) → 200 OK + updated match detail.
7. Operator returns to Phase view; standings update via existing WS subscription.

After operator clicks "Phase abschließen" → phase transitions COMPLETED → "Korrigieren" links are disabled / endpoints return HTTP 409 per AC-ERR-PHASE-NOT-ACTIVE-409.
