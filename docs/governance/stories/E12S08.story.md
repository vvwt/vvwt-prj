# Story: Fix — team photo upload fails with bare "HTTP 413"; raise the photo size limit to 25 MB (env-configurable)

## User Story

**As a** tournament organizer uploading team photos in the admin console,
**I want** photos taken with a phone or camera to upload without being rejected, and to get a
clear, readable message if a photo really is too large,
**so that** I can populate every team's photo without manually shrinking images or guessing
what a bare "HTTP 413" means.

---

## Context

On the **Mannschaftsfotos** page (`/admin/#/tournaments/{id}/photos`, route `TeamPhotos.svelte`),
uploading a team photo fails: the row shows the bare text **"HTTP 413"** in red and no photo is
stored. Reported 2026-05-17 with a screenshot — the organizer was at the start of populating team
photos ("0 von 12 Mannschaften haben ein Foto").

Two problems combine here:

1. **The size limit is too low for real photos.** The team-photo feature caps uploads well below
   the size of typical phone/camera images, so normal photos are rejected.
2. **The rejection is unreadable.** Instead of a sentence telling the organizer what went wrong
   and what to do, the page shows a raw HTTP status code. This violates E12S03 AC7 (upload errors
   must be shown inline and be actionable) and AC8 (all messages via the i18n layer).

The product decision (Discovery session 2026-05-17, human-validated): **raise the limit to 25 MB**
and make it **adjustable via an environment variable** so it can be tuned later without a code
change — and fix the error message so an over-limit photo produces a clear, translated, inline
message. Client-side image downscaling was considered and rejected (it would breach E12's explicit
"no image resizing/cropping" boundary).

---

## Root Cause Analysis

Investigation of `vvwt-tm-web` (Discovery, code-read only — the precise fix is Delivery's):

- The upload passes through **two stacked size limits**:
  1. **Spring's global multipart limit** — `spring.servlet.multipart.max-file-size` /
     `max-request-size` in `application.yml`, currently **10 MB** (the config block is even
     labelled "audio file upload", bound to `TM_AUDIO_MAX_FILE_SIZE`).
  2. **The photo-domain limit** — `tm.photos.max-size-bytes` (`PhotoStorageConfig`), default
     **5 MB**. It is not set in `application.yml`; the Java default applies.
- A photo **larger than 10 MB** is rejected by Spring *before* the controller runs →
  `MaxUploadSizeExceededException` → **HTTP 413**. A photo **5–10 MB** reaches the controller →
  `PhotoSizeException` → **HTTP 400**. So a 413 means the uploaded photo exceeds 10 MB.
- Therefore raising **only** the photo-domain limit would not fix the symptom — the 10 MB Spring
  cap would still produce 413. The effective limit a photo must clear is the *lower* of the two.
- `GlobalExceptionHandler.handleMaxUploadSizeExceeded` maps the exception to 413 but with the
  **audio** i18n key (`error.audio.tooLarge`) and a generic English string — a *photo* upload
  surfaces an *audio* error.
- The frontend (`photoStore.ts` `uploadPhoto`) shows `body.message` from the JSON error response,
  and falls back to the literal `HTTP {status}` when no usable message is present — which is what
  the organizer sees.
- No backlog story and no automated test currently cover the photo over-limit / 413 path.
- Awareness note for Delivery (not a hard AC): for uploads *far* above the limit, the embedded
  Tomcat `maxSwallowSize` can reset the connection before the error body is read; keeping the
  multipart cap from being the photo path's gatekeeper avoids this for in-range photos.

Discovery defines the expected behaviour; how the two limits are layered and where the
photo-specific message is produced is Delivery's decision.

## Acceptance Criteria

- [ ] **AC1 (testing — reproduction):** Delivery first confirms the baseline — Given a team photo
  file larger than 10 MB, When it is uploaded via the Mannschaftsfotos page, Then the upload fails
  and the row shows a bare "HTTP 413". The reproduction and its result are recorded in the
  impl-report.
- [ ] **AC2 (error-handling):** After the fix, Given a team photo at or below the configured photo
  size limit (default **25 MB**), When the organizer uploads it, Then the upload succeeds and the
  photo is stored — the photo is not rejected by any intermediate size cap (neither the multipart
  layer nor the photo-domain check rejects an in-limit photo).
- [ ] **AC3 (error-handling):** Given a team photo that exceeds the configured photo size limit,
  When it is uploaded, Then it is rejected with a photo-specific error response — **not** a bare
  HTTP status code and **not** an audio-domain message. This holds regardless of which internal
  layer enforces the limit.
- [ ] **AC4 (i18n):** The over-limit error message reaches the organizer through the application's
  i18n layer (svelte-i18n, consistent with E12S03 AC8) — for the German UI it appears in German —
  states the maximum allowed photo size, and is shown inline near the team's upload control per
  E12S03 AC7 (not a bare status code, not a console error, not a dialog).
- [ ] **AC5 (configuration):** The photo size limit is adjustable via an **environment variable**
  with no code change required; its default is **25 MB**; the variable is named consistently with
  the `TM_*` upload-config override convention already used in `application.yml` (cf. the existing
  `TM_AUDIO_MAX_FILE_SIZE` audio-upload override). Setting the variable changes the effective limit
  for both successful uploads (AC2) and rejection (AC3).
- [ ] **AC6 (security):** The upload endpoint remains admin-authenticated via Spring Security
  `/api/**`. Raising the limit and changing the error handling does not alter authentication or
  authorization for upload, retrieve, or delete.
- [ ] **AC7 (testing — regression):** An automated regression test covers both directions — (a) a
  photo at/under the configured limit uploads successfully, and (b) a photo above the configured
  limit produces the photo-specific error response — so the 413 regression cannot silently return.
  Existing upload / retrieve / delete behaviour and JPEG/PNG format validation are unchanged, the
  rest of the `vvwt-tm-web` test suite stays green, and `mvn verify` from the `vvwt-prj` root is
  BUILD SUCCESS.

> All acceptance criteria must be verifiable.

---

## Out of Scope

- **Client-side image downscaling / resizing / cropping** — explicitly excluded by Epic E12
  ("photos are used as uploaded"); the chosen strategy is to raise the limit, not to shrink images.
- **Changing the audio or certificate-template upload limits** beyond any incidental shared-config
  change strictly needed to let an in-limit photo through.
- **Connection-reset behaviour for uploads far above the limit** (Tomcat `maxSwallowSize`) — noted
  in Root Cause Analysis for Delivery awareness; not a hard acceptance criterion.
- **Re-architecting the global multipart configuration** or per-endpoint multipart resolvers.
