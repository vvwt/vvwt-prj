# Story E11S15: Timer audio playback queue — serialize coinciding sounds via FIFO drain on HTMLAudioElement `ended`

## User Story

**As a** tournament organizer using the Timer SPA during a live tournament,
**I want** coinciding audio cues at the same schedule boundary (the round-end sound and the pause-start music both fire at the moment Phase-1-Round-1 ends) to play **one after the other** instead of overlapping,
**so that** the chosen sounds remain individually recognizable to participants and we avoid the muddy overlap that, depending on the chosen sound files, can produce unwanted side effects.

---

## Context

After E11S13 shipped the audio activate-fire fix (using `playingIndex` instead of `activeEventIndex`), the Timer SPA now plays the correct sound for each event boundary. Operator verified this on 2026-05-29 and reported a new observation: at the Runde-end ↔ Pause-start boundary, the END_SOUND (deactivate of the finishing ROUND) and PAUSE_MUSIC_START (activate of the starting REGULAR-BREAK) both fire on the same `onTick` invocation. Both `audioEngine.play(...)` calls execute back-to-back on the same JavaScript event-loop turn and the sounds play simultaneously. While mathematically correct, this overlap is operationally suboptimal: depending on which audio files the operator uploaded, the sounds can fight, mask one another, or produce unintended artifacts.

Operator's request (Discovery Session Brief `discovery-2026-05-29-timer-audio-playback-queue`, Tier-2 cycle-2 PASS, rubric_version 2026-03-30):

- Serialize audio playback. When two `play()` calls would coincide on the same tick, play the first to completion before starting the second.
- Stop commands remain immediate (Pause-Music must end as soon as the round starts — operator can't tolerate Start-Sound being delayed by pending Pause-Music).
- Plain FIFO queue — no staleness pruning. If a queued sound's schedule position has passed by the time its turn comes, it still plays. For typical operator audio choices (END 5–10 s, pauses minutes) this scenario is operationally non-existent; extreme edge cases (long END_SOUND + very short pause) remain plain-FIFO per operator-accepted decision.

Operator clarifications during cycle-1 review:
- **stopPauseMusic also prunes queued PAUSE entries.** When `audioEngine.stopPauseMusic()` is called (deactivate of a REGULAR-BREAK), any queued PAUSE-category entries that have not yet started are removed from the queue. START / END queued entries remain. This prevents the "END finishes after pause-end → queued PAUSE-MUSIC-START fires AFTER its STOP" bug-shape.
- **Transport-Pause retains the queue.** When the operator presses the transport PAUSE button, the currently-playing sound pauses but the queue is unchanged. When the operator presses transport PLAY again, the paused sound resumes (where the engine method is invoked) and the queue continues to drain on its `ended` event. Only `stopAll()` clears the queue — consistent with the plain-FIFO operator decision.

The fix lives entirely inside `AudioEngine`. The `App.svelte` `onTick` call sites are unchanged (per Brief Q-1, D-4) — only the internal behavior of `AudioEngine.play(category)` changes from synchronous-immediate-fire to queue-aware.

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach is Delivery's choice within the bounds set by the Brief.

### Queue behavior

- [ ] **AC1 — `play(category)` plays immediately when nothing else is playing.** When `AudioEngine.play(category)` is called and no audio element in the engine is currently playing, the targeted element begins playback immediately (the existing pre-Story behavior for the single-sound case is preserved).
- [ ] **AC2 — `play(category)` queues when another sound is playing.** When `AudioEngine.play(category)` is called and any audio element in the engine is currently playing, the requested category is appended to an internal FIFO queue and does not begin playback yet.
- [ ] **AC3 — Queue drains on the playing element's `ended` event.** When the currently-playing audio element's HTMLAudioElement `ended` DOM event fires, the engine pops the head of the queue and plays the popped category. If the queue is empty at `ended`, nothing is played (the engine returns to idle).
- [ ] **AC4 — Drain is recursive.** The popped sound's own `ended` event drains the next queued entry. Multiple queued entries play in FIFO order until the queue is empty.

### Stop / pause semantics

- [ ] **AC5 — `stopAll()` clears the entire queue and stops the currently-playing element.** After `stopAll()`, no audio is playing AND no queued entries remain. A subsequent `play(category)` call plays immediately per AC1.
- [ ] **AC6 — `stopPauseMusic()` removes queued PAUSE-category entries and stops in-progress PAUSE playback.** Calling `stopPauseMusic()` while PAUSE is currently playing stops it; queued PAUSE-category entries (if any) are also removed from the queue. Queued START or END entries are NOT removed and continue to be drained per AC3 / AC4 once the currently-playing element finishes (or immediately, if PAUSE was the playing element and no other element is in progress).
- [ ] **AC7 — `pauseAll()` pauses the currently-playing element; the queue is unchanged.** Calling `pauseAll()` pauses (does not stop) the currently-playing element. Queue contents are unchanged. The `ended` event does NOT fire on a paused element, so the drain is naturally suspended.
- [ ] **AC8 — `resumeAll()`, where invoked, resumes the paused element; queue drain naturally continues on the `ended` event.** When `resumeAll()` is called on a paused-but-not-stopped engine, the paused element resumes from its current playback position. When it eventually fires `ended`, the queue drains per AC3 / AC4. (Note: `App.svelte` transport `handlePlay` does not currently invoke `resumeAll()` — this AC defines engine-level behavior; consumer call sites are unchanged per Q-1 / D-4.)

### Call-site invariance

- [ ] **AC9 — `App.svelte` `onTick`, `handlePause`, `handlePlay`, `handleStop` are unchanged.** The producer-side call sites in `App.svelte` for `audioEngine.play(...)`, `audioEngine.pauseAll()`, `audioEngine.stopAll()`, and `audioEngine.stopPauseMusic()` are not modified by this Story. Only the internal behavior of `AudioEngine` changes.
- [ ] **AC10 — No new AudioEngine method names introduced.** No method named `playQueued`, `playImmediate`, `enqueue`, `drainQueue`, or equivalent is added to the public surface. `play()` semantics extend transparently. (Internal private state and helper methods are Delivery's choice and may use any naming.)

### Error-handling (mandatory category)

- [ ] **AC11 — Queue drain proceeds when an HTMLAudioElement `ended` event fails to fire.** When the currently-playing element encounters an audio-decode or source-not-found error (the element fires an `error` event instead of `ended`), the engine treats this as an "ended" signal for queue-drain purposes: the queue's next entry is drained per AC3 (or the engine returns to idle if the queue is empty). This ensures a single broken audio file does not freeze the queue.
- [ ] **AC12 — `stopPauseMusic()` on an empty queue is a no-op.** If `stopPauseMusic()` is called when no PAUSE is currently playing and no PAUSE is queued, the call is a safe no-op. No exception, no state change, no audio side-effect.
- [ ] **AC13 — Queue depth is not externally bounded.** This Story does not impose a queue-depth limit. If Delivery identifies a concrete failure mode during implementation (e.g., extreme operator skip-spam producing memory pressure or browser audio-element exhaustion), Delivery MAY add a reasonable safeguard with rationale attested in the impl-report. Discovery does not pre-judge.

**Implementation pointer (informational, NOT prescriptive — Brief D-1 / D-2 / Q-3 / Q-4):**
- Add private state to `AudioEngine` tracking (a) the currently-playing `HTMLAudioElement | null` and (b) a FIFO queue of `AudioCategory` entries.
- In `play(category)`: if state.currentlyPlaying === null, set currentlyPlaying = el, register `ended` and `error` listeners (the latter per AC11), play the element; else push to queue.
- The `ended` (or `error`, per AC11) listener clears state.currentlyPlaying and, if the queue is non-empty, shifts the head and recursively plays it (effectively a single-step drain that recurses via the next `ended` event).
- `stopAll()`: clear queue, stop currently-playing element, clear state.currentlyPlaying.
- `stopPauseMusic()`: if currentlyPlaying corresponds to PAUSE category, stop it and clear state.currentlyPlaying (then drain next per the standard path); ALSO filter the queue to remove PAUSE-category entries (per AC6).
- `pauseAll()`: pause currently-playing element (does not clear state.currentlyPlaying); queue unchanged. The paused element does not fire `ended`, so the drain is naturally suspended.
- `resumeAll()`: resume currently-playing element (paused, not stopped). On `ended`, drain proceeds per normal.

**Q-3 polling guard:** `ended` event is the natural drain trigger; do NOT introduce a `setInterval` / `setTimeout` polling loop to peek at currentTime / duration. This keeps the engine event-driven and avoids stale-poll timing windows.

**Q-4 silent-stop guard:** `stopAll()` clears the queue WITHOUT firing any audio events for queued items. No "play-then-immediately-stop" intermediate state is permitted.

**Test harness reality:** `audioEngine.test.ts` uses HTMLAudioElement mocks injected via the engine's `createElement` factory (E11S04 test harness). Queue behavior is testable via mock `ended` event dispatch + assertion on which element's `play()` was called next. Source-inspection per `AppBranding.test.ts` precedent is the fallback for any AC not directly observable via the mock-injection path.
