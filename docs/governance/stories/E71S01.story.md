# Story E71S01: Crop team photo to the target aspect ratio and downscale before saving

## User Story

**As an** operator preparing team photos for certificates,
**I want** to crop a team photo to the correct aspect ratio (with a suggested crop I can adjust) and have it automatically downscaled before it is saved,
**so that** I no longer crop and resize photos by hand in an external image editor.

---

## Context

Today a team photo is stored exactly as uploaded — there is no cropping or downscaling in the
app (`de.vvwt.tm.photo`). This story adds an in-browser crop+downscale step to the existing
Team-Photos screen for a single image, reusing the existing upload endpoint and storage
(per reuse-search: HIT on upload/endpoint/storage/size-config; NO-HIT on client-side
crop/resize → built with the browser Canvas API). It is the foundation the other E71 stories
build on. Best-shot selection (E71S03) and the per-template ratio override (E71S02) are
separate stories; here the crop uses a single **global default** target ratio.

Target aspect ratio and downscale size are operator-tunable without a rebuild: the global
default aspect ratio is **11:5** and the default downscale long-edge is **2200px**, both
server-configured and overridable via environment variable (mirroring the existing
`TM_PHOTOS_*` ENV-override pattern; DEC-68 Clause 3 escape-hatch). 2200px keeps the operator's
proven print quality (~214 dpi at near-full A4-landscape width); do not silently downgrade it.

The certificate render is unchanged (`object-fit: cover` stays); the chosen ratio is the
operator's declared intended display ratio, not a code-guaranteed pixel-faithful render.

---

## Acceptance Criteria

- [ ] **AC1 (crop suggestion + manual adjust):** Given a selected team photo on the Team-Photos
  screen, when the operator enters the crop step, then a crop rectangle is pre-suggested
  (face/subject-aware) at the configured target aspect ratio, and the operator can move/resize
  it while the rectangle stays **locked to that aspect ratio**.
- [ ] **AC2 (downscale + save via existing endpoint):** Given an accepted crop, when the operator
  saves, then the image is cropped to the rectangle and downscaled so its **longest edge does
  not exceed the configured max long-edge** (default 2200px; smaller images are not upscaled),
  and the single resulting JPEG/PNG is stored via the existing `POST /api/photo/.../teams/{teamId}`
  endpoint (no new storage path; `${tm.data.dir}/photos` layout unchanged).
- [ ] **AC3 (server-configurable, ENV-overridable defaults):** Given no overrides, the target
  aspect ratio defaults to **11:5** and the max long-edge to **2200px**; given the corresponding
  environment variables are set, the crop step uses the overridden values. The values are
  resolved server-side and consumed by the crop UI (no value hardcoded only in the frontend).
- [ ] **AC4 (testing — deterministic logic RED-first; runtime attested):** Deterministic logic —
  aspect-ratio parsing/normalization, crop-rectangle geometry for a given ratio, and long-edge
  downscale arithmetic — is covered by RED-first automated unit tests (DEC-22). Runtime
  canvas crop/resize pixel output (no automated browser oracle) is verified by the `impl-report`
  and MUST NOT be claimed as automated coverage (DEC-22 test-surface honesty). `mvn verify` is
  BUILD SUCCESS (DEC-54).
- [ ] **AC5 (error-handling / degraded states):** Given an unsupported file type or an over-limit
  file, the existing format/size validation still applies and the operator sees the existing
  localized error (no regression). Given an image **smaller** than the target crop in some
  dimension, the operator is still able to produce a valid crop (no crash; the crop is
  constrained to the available pixels) and the result is not upscaled beyond its native size.
- [ ] **AC6 (i18n):** All new/changed UI text (crop controls, save/cancel, any crop-related
  error or hint) is provided through the frontend i18n layer with German-first entries per the
  existing TM convention — no hardcoded user-facing strings.
