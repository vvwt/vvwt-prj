# Story: Certificate render endpoints fall back to the built-in standard template when no template is uploaded

## User Story

**As a** tournament organizer running a tournament for which I have not uploaded a
certificate template,
**I want** the certificate render endpoints to produce the built-in branded standard
certificate,
**so that** I can generate and print/download my teams' Urkunden without first having to
upload a template.

---

## Context

The application ships a complete, branded system-default certificate template — E46S04
built `_certificate_styles.mustache` + `_certificate_page.mustache` with embedded Plus
Jakarta Sans fonts, a hex watermark, and i18n `tom_label_*` labels. The HTML render branch
of `CertificateRenderController` already renders it through the `certificate/print` /
`certificate/print-all` Spring views.

But the template is unreachable. `CertificateRenderController` gates **both** endpoints —
`GET /certificate/tournaments/{tid}/print/{teamId}` and `GET /certificate/tournaments/{tid}/print`
— on `certificateTemplateService.retrieveFile(tid).isEmpty()`, returning HTTP 400 ("Keine
Urkunden-Vorlage hochgeladen…") **before** the SVG-vs-HTML format branch. With no uploaded
template, the organizer can never reach the standard certificate.

This is the unmet half of E46S04: its stated goal was a production-quality certificate
"immediately on first install without operators uploading a custom template," and Epic
E46's Success Metrics claimed a fresh tournament renders the branded layout "without any
per-tenant template upload." E46S04's changes touched only the Mustache view templates —
its git history shows the controller was never modified, so the 400 gate survived and that
success metric was false at E46 close. E67S01 closes the gate: when no template is
uploaded, the endpoints render the system-default certificate instead of failing.

The human chose an **automatic fallback** (no explicit "use standard template" action).
An uploaded SVG template still overrides the default with its own content. An uploaded
HTML template's content is already ignored by the renderer today (it only ever served as
the gate token); after this story it produces the same system-default render as the
no-template path — making the two paths behaviorally identical, which is acceptable and in
scope. Whether an uploaded HTML template's *content* should drive the render is a separate
custom-template concern and is out of scope.

## Acceptance Criteria

- [ ] **AC1 [behavior]:** Given a tournament with valid game results (a final phase and
  computed placements) and **no** per-tournament certificate template uploaded, when
  `GET /certificate/tournaments/{tid}/print/{teamId}` is requested, then the response is
  HTTP 200 and renders the system-default branded HTML certificate for that team. It MUST
  NOT return HTTP 400.
- [ ] **AC2 [behavior]:** Given the same no-template precondition, when
  `GET /certificate/tournaments/{tid}/print` is requested, then the response is HTTP 200
  and renders the system-default branded HTML certificate document covering all teams.
- [ ] **AC3 [behavior]:** Given a tournament with an uploaded **SVG** template, the
  existing SVG render behavior is unchanged — `/print/{teamId}` returns the rendered SVG as
  an attachment and `/print` returns the SVG ZIP archive. The fallback applies only when no
  template is uploaded.
- [ ] **AC4 [behavior]:** Given a tournament with an uploaded **HTML** template, both
  endpoints render the system-default branded HTML certificate — the same output as the
  no-template path. This story introduces no new behavioral distinction between "no
  template uploaded" and "HTML template uploaded"; using an uploaded HTML template's
  content is explicitly out of scope.
- [ ] **AC5 [error-handling]:** Given a tournament that has no final phase, no game
  results, or no computed placements, both endpoints still return HTTP 400 with the
  existing actionable plain-text message about missing results. The no-template 400 branch
  is the **only** 400 branch removed; the no-results 400 branches are preserved unchanged.
- [ ] **AC6 [governance]:** The no-template 400 code path is removed from
  `CertificateRenderController`, including its inline German error string. The story author
  audits, by reference search at delivery time, whether any message-bundle key (for example
  `print.certificate.error.noTemplate`) or other resource is left referenced only by the
  removed path; every key or resource thereby orphaned is removed in the same change. Do
  not assume the orphan set — verify it.
- [ ] **AC7 [testing]:** The behavior change is authored RED-first per DEC-22 — the tests
  for AC1 and AC2 (no-template → HTTP 200 system-default render) fail against the
  pre-story codebase and pass after the change. The RED→GREEN cadence is recorded in the
  impl-report.
- [ ] **AC8 [testing]:** The existing `CertificateRenderControllerSliceTest` no-template
  case (currently asserting no-template → HTTP 400) is updated atomically to the new
  contract — the no-template case asserts the HTTP 200 system-default render path. A slice
  case for a still-400 branch (no game results) is retained so the 400 error path stays
  covered.
- [ ] **AC9 [i18n]:** The system-default certificate produced via the fallback carries its
  display labels through the `tom_label_*` model variables resolved via Spring
  `MessageSource` (E46S03), exactly as the existing HTML render path does. No hardcoded
  display strings are introduced — the fallback reuses the existing HTML render path.
- [ ] **AC10 [governance]:** The change is confined to the `CertificateRenderController`
  primary adapter (DEC-40) — no new service, registry, or DAO. No new DEC is created. The
  rendered standard certificate remains self-contained and offline-capable (embedded
  fonts, no external fetch) per DEC-16, inherited unchanged from the E46S04 render path.
- [ ] **AC11 [testing]:** `mvn verify` for `vvwt-tm-web` is BUILD SUCCESS after the change
  (DEC-54) — no regression to the SVG render path, the no-results 400 branches, or other
  certificate tests.

> All acceptance criteria must be verifiable. Vague criteria are invalid.

## Out of Scope

- Making an uploaded HTML template's content drive the render (the renderer ignores HTML
  template content today; that is a separate custom-template concern).
- An SVG system-default template — the system-default is HTML; no SVG default is added.
- Any change to the system-default template's visual design or the E46S04 Mustache
  partials.
- The COMPLETED-status gate on certificate generation.
- Any frontend change (covered by E67S02).

## Notes

- The fallback is automatic (human decision): no per-tournament template uploaded → render
  the system-default certificate. No explicit "use standard template" action exists.
- Behaviorally, after this story, "no template uploaded" and "HTML template uploaded"
  produce the identical system-default render. This is intended (see Context / AC4).
- The render path for the no-template case is the existing HTML render path
  (`certificate/print` / `certificate/print-all` views + the certificate model). The story
  defines the behavioral outcome (HTTP 200, system-default certificate); Delivery chooses
  how the controller selects that path when `retrieveFile` is empty.
