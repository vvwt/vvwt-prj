# Story E70S06: Fix — maven-pmd-plugin baseline lookup fails when `mvn` is invoked from a vvwt-prj submodule

## User Story

**As an** operator running `mvn` from a submodule directory (e.g., from `vvwt-tm-web/` via NetBeans / IDE / shell),
**I want** the build to succeed without `Cannot load file …/pmd-baseline.xml` errors from `maven-pmd-plugin`,
**so that** per-submodule `mvn` invocations remain a viable local dev loop after the E70 Layer-C build gates were activated.

---

## Context

E70S01 (PR #382, merged 2026-05-31T10:49Z) and E70S03 (PR #383, merged 2026-05-31T11:41Z) activated PMD CPD + PMD complexity gates by adding `<plugin>` declarations to `vvwt-prj/pom.xml` whose `<configuration>` references reactor-root files via `${maven.multiModuleProjectDirectory}/…` properties. The activation is correct at the reactor root; the build property does not resolve to the reactor root when `mvn` is invoked from a submodule, because `vvwt-prj/` carries no `.mvn/` marker directory (Maven's standard signalling mechanism for reactor-root discovery from subdirectories). Without the marker, `${maven.multiModuleProjectDirectory}` falls back to the working directory of the `mvn` invocation. The user-reported failure (2026-05-31, `mvn clean install` from `vvwt-tm-web/`):

```
Failed to execute goal org.apache.maven.plugins:maven-pmd-plugin:3.28.0:cpd
(cpd) on project vvwt-tm-web: Failed to determine whether report can be
generated: Error loading exclusions: Cannot load file
/home/vvw/NetBeansProjects/vvwt-prj/vvwt-tm-web/pmd-baseline.xml
```

The daemon and the `qa-review` `mvn verify` gate (DEC-54 / DEC-71) saw GREEN because both invoke `mvn` from the reactor root — the defect is a CI-vs-local-loop asymmetry, not a verdict-integrity gap.

Per DEC-78 Clause C, the corrective build-config edit (pom.xml change or `.mvn/` marker-directory creation) routes via the DEC-67 non-authoring carve-out under DEC-78's broader reading (build-descriptor coordinates without first-party Java code). The RED-first regression fixture (first-party test code) routes via DEC-22.

Per DEC-79, the corrective work is confined to the vvwt-prj working tree — no `~/.m2/settings.xml` edit, no host-PATH mutation, no Maven-wrapper bootstrap that fetches binaries from the network.

## Notes

**Fix-mechanism closed list (Delivery chooses; Discovery does not prescribe — per Bug-Triage Flow §"WHAT not HOW"):**

- **(a)** Add `.mvn/` marker directory at `vvwt-prj/` (Maven-conventional reactor-root signalling); `${maven.multiModuleProjectDirectory}` then resolves to `vvwt-prj/` from any subdirectory. Systemic — fixes every present and future property of this form.
- **(b)** Replace the affected `${maven.multiModuleProjectDirectory}/…` property values with reactor-root-relative paths resolved at the parent POM via an alternative mechanism (e.g., a parent-POM-level `<properties>` definition derived from a basedir-traversal). Surgical — fixes only the audited properties; H-2 latent for future additions.
- **(c)** Use `${session.executionRootDirectory}` and codify a "Maven must be invoked from the reactor root" mandate in `README.md` + `nbactions.xml`. Depends on operator discipline — least robust against IDE actions.
- **(d)** Any other mechanism whose footprint is limited to the vvwt-prj working tree (per DEC-79) and that satisfies AC2–AC6.

Delivery selects, justifies the choice in `impl-report.md`, and documents the trade-off the choice makes (per-property surgical vs. systemic).

**Reproduction (informational — Delivery re-verifies in the RED phase per AC4):**

```
# At the unfixed staging HEAD:
cd vvwt-prj/vvwt-tm-web && mvn pmd:check
→ BUILD FAILURE: "Cannot load file …/vvwt-tm-web/pmd-baseline.xml"

# From the reactor root (currently GREEN — must remain GREEN per AC5):
cd vvwt-prj && mvn verify
→ BUILD SUCCESS
```

**Asymmetric-error preference at the fixture (DEC-47 Clause F / DEC-71)**: a missing, unparseable, or ambiguous Maven output produces fixture FAIL — never silent PASS. This protects the gate against future regression introduced by output-format drift.

**Latent-class disclosure (H-2, deferred to follow-up Discovery if it recurs)**: D-3 (b) and (c) fixes are surgical and leave a latent defect class — any future `${maven.multiModuleProjectDirectory}/…` property addition could re-introduce the same failure mode. D-3 (a) is systemic. The choice + its blast radius are documented in `impl-report.md` per AC1.
