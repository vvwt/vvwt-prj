# Story E14S07: Atomic cutover commit — delete legacy `de.vvwt.tm.tenant.*`, wire new beans

## User Story

**As a** reviewer of the Wave-1 programme,
**I want** the legacy `de.vvwt.tm.tenant.*` code replaced by the new `tenant` context in a single atomic commit with no feature flags,
**so that** the staging branch never carries two competing tenant implementations and DEC-21's atomic-cutover protocol is exercised for the first time on a real context.

---

## Context

E14S01–S06 built the new `de.vvwt.tm.tenant` (root) + `.internal` layout in parallel with the existing legacy `de.vvwt.tm.tenant.*` package (which today contains the prior E02S04 default-tenant-bootstrap work). Under DEC-21's atomic cutover protocol, that parallel phase ends here: one commit deletes the legacy code, promotes the new beans as the only implementations, and must leave `mvn verify` green.

Per DEC-21 explicitly: no feature flags, no `@ConditionalOnProperty`, no `@Profile("new"|"old")`. The discipline is the point of the exercise — E14S07 is the first real rehearsal of the protocol that E15S07 will repeat on the `auth` context with legacy Flyway deletion added.

Legacy Flyway migrations (`V1..V6` under root `db/migration/`) are NOT deleted in this story. That deletion belongs to E15S07 per DEC-22 O-9 (single legacy-migration-clearance commit tied to the auth cutover).

---

## Acceptance Criteria

- [ ] AC1 (governance — atomic single-commit discipline): The cutover lands as ONE commit on `staging` that: (a) deletes the legacy `de.vvwt.tm.tenant.*` package contents (all files under the old package path in `vvwt-tm-web/src/main/java/de/vvwt/tm/tenant/` that predate E14's reconstruction work), (b) promotes the new `de.vvwt.tm.tenant` + `.internal` layout to its final package path (if a staging name was used during reconstruction), (c) updates any Spring wiring / bean references to point at the new classes. Git log at merge shows the single commit; no intermediate "parallel phase" commit carrying both old and new bean definitions. Per DEC-21.

- [ ] AC2 (governance — no feature flags): `git grep` across the cutover commit shows no new `@ConditionalOnProperty`, `@Profile("new")`, `@Profile("old")`, or similar conditional wiring added to bridge the transition. An explicit search is documented in the Delivery plan per DEC-21's no-feature-flags constraint.

- [ ] AC3 (governance — legacy Flyway untouched): `V1..V6` under root `db/migration/` remain intact. This story does NOT delete them — E15S07 is the authorised deletion point per DEC-22 O-9. `git diff` for this commit shows zero changes under `vvwt-tm-web/src/main/resources/db/migration/V*.sql`.

- [ ] AC4 (testing — full verify green after cutover): Post-cutover, `mvn verify` from `vvwt-prj/` is green: `ApplicationModulesTest`, the cross-tenant isolation `@ApplicationModuleTest` from E14S06, all pre-existing TM-module tests, and every other module's tests. No test skipped, no `@Disabled`.

- [ ] AC5 (data-isolation — end-to-end on clean machine): A fresh-machine smoke run (simulated via `@TempDir`-backed integration test) starts the application, observes the default-tenant bootstrap from E14S05, and confirms a write-then-read cycle works against the default tenant's DB. No references to legacy `de.vvwt.tm.tenant.*` classes survive in the runtime bean graph — a bean-registry assertion or a negative-import test documents this.

- [ ] AC6 (error-handling — no legacy-symbol drift): After cutover, a source-level search (`git grep 'de.vvwt.tm.tenant.{legacy-class-names}'` with the pre-cutover class names list enumerated in the Delivery plan) returns zero hits across the entire `vvwt-prj` project. No straggler import statements survive.

- [ ] AC-LEGACY-ENUM (governance — legacy class enumeration inline): The cutover commit deletes at minimum these known legacy files under `vvwt-prj/vvwt-tm-web/src/main/java/de/vvwt/tm/tenant/`: `DefaultTenantProvider.java`, `DefaultTenantBootstrap.java`. If the Delivery agent finds additional legacy files in the same package at cutover time (e.g., helper classes not visible at Discovery time), they are enumerated in the Delivery plan and deleted in the same commit. The AC is: `find vvwt-prj/vvwt-tm-web/src/main/java/de/vvwt/tm/tenant -type f -name '*.java'` after the cutover commit returns ONLY new-package files — zero legacy files remain.

- [ ] AC7 (testing — Modulith verify): `ApplicationModulesTest` is green with `de.vvwt.tm.tenant` declaring `@ApplicationModule(allowedDependencies = {})` and no other module yet importing from it (the first consumer, `auth`, arrives in E15).

- [ ] AC8 (governance — rollback readiness): Per DEC-21, deploy-pause between the "last parallel-phase commit" and this cutover commit is accepted as a brief inconsistent state. The Delivery plan documents the explicit rollback procedure if cutover verify fails post-merge (revert the commit; returns the repo to the last-good parallel-phase state). Procedure exists but is not expected to be exercised.

## Notes

The pre-cutover checklist Delivery should run through in the execution plan: (1) new module's `@ApplicationModuleTest` green, (2) `ApplicationModulesTest` green, (3) full `mvn verify` green on the parallel-phase branch, (4) every consumer of any legacy `tenant` type has been identified and re-targeted. Skipping step (4) is the most common cutover failure mode.

The "pre-cutover legacy class name enumeration" for AC6 is Delivery's responsibility — the exact legacy files under `de.vvwt.tm.tenant/` today depend on what E02S04 produced and what any interim work may have added. Enumerate at plan time.
