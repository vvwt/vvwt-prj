# Story E16S06: Fix — cold `mvn clean verify` fails: InfoPortalPublisherIT needs vvwt-info-server's fat JAR, but vvwt-info-server builds after vvwt-tm-web in the reactor

## User Story

**As a** developer or CI pipeline running a clean full build of the `vvwt-prj` reactor,
**I want** `mvn clean verify` from the reactor root to complete BUILD SUCCESS with
`InfoPortalPublisherIT` executed,
**so that** a clean build is not broken by a reactor module-ordering gap and the InfoPortal
publisher end-to-end coverage runs on every clean build instead of failing deterministically.

---

## Context

`InfoPortalPublisherIT` (`vvwt-tm-web`, package `de.vvwt.tm.infoportal`) is the
Testcontainers end-to-end integration test for the Tournament Manager InfoPortal publisher.
It launches a real `vvwt-info-server` instance from that module's repackaged Spring Boot
fat-JAR (`vvwt-info-server/target/*-exec.jar`) and resolves the JAR path at **static
initialization time** — the test's `@Container` static field is initialized by a helper
that lists `vvwt-info-server/target` for the `-exec.jar`.

On a cold `mvn clean verify` from the reactor root the JAR does not exist when that static
initializer runs, because `vvwt-info-server` builds **after** `vvwt-tm-web` in the reactor.
The build aborts with a class-initialization error and BUILD FAILURE. A warm `mvn verify`
(no `clean`, JAR present from a prior build) passes — which is why the defect is latent.

The defect is **pre-existing and independent of E16S05** — reproduced with E16S05 reverted.
It was flagged for triage in the E16S05 `memory-delta` (§3, "latent build-ordering quirk in
InfoPortalPublisherIT"). This is a test-infrastructure fix in the E16 (Test Infrastructure
Governance) family, alongside the bug-triage fixes E16S02, E16S03, E16S04 and E16S05. It
changes no production code.

---

## Root Cause Analysis

Investigation (Discovery, 2026-05-17 — root cause structurally verified in-session and
empirically reproduced by the operator; not implemented):

- **Why the JAR is missing on a cold build.** The Maven reactor builds modules in
  topological dependency order; for modules with no dependency edge between them, the
  reactor falls back to the declaration order of the `<modules>` block in the parent
  `pom.xml`. In that block `vvwt-tm-web` is declared **before** the `vvwt-info-dto` /
  `vvwt-info-server` / `vvwt-info-client` module set. `InfoPortalPublisherIT` needs
  `vvwt-info-server`'s repackaged fat-JAR, but `vvwt-info-server` is built later in the
  reactor — so on a `clean` build its `target/` has no `-exec.jar` when `vvwt-tm-web`'s
  `integration-test` phase runs.

- **Why no dependency edge fixes the order.** Maven would reorder the reactor if
  `vvwt-tm-web` declared a dependency on `vvwt-info-server`. It does not, and it must not:
  **DEC-42 D2** forbids `vvwt-tm-*` depending on `vvwt-info-server` (only the
  `vvwt-tm-web → vvwt-info-dto` edge is permitted), and a `maven-enforcer-plugin`
  `bannedDependencies` rule in `vvwt-tm-web/pom.xml` actively bans it. With no edge, the
  declaration order is the only ordering signal — and it is wrong for this test.

- **Why the JAR-resolution helper cannot compensate.** The test resolves the JAR from the
  filesystem precisely to avoid a compile-time Maven dependency (DEC-42 D2). When the JAR
  is absent the helper throws — and because the resolution runs inside a static field
  initializer, the failure surfaces as a class-initialization error that aborts the test
  class and the reactor build.

- **Stale documentation.** The test's class-level Javadoc and its JAR-resolution helper
  Javadoc assert — incorrectly — that the reactor builds `vvwt-info-server` before
  `vvwt-tm-web`'s integration-test phase "because `vvwt-tm-web` depends on `vvwt-info-dto`
  which is in the same reactor". The `vvwt-info-dto` dependency does not pull
  `vvwt-info-server` forward; `vvwt-info-dto` and `vvwt-info-server` are distinct modules.
  The asserted invariant is false and is the reason the fragility went unnoticed.

**Reproduction scenario:**
- **Given** the `vvwt-prj` reactor on `staging` in a clean state — no prior build output, so
  `vvwt-info-server/target` contains no `*-exec.jar`,
- **When** `mvn clean verify` runs from the reactor root,
- **Then** `vvwt-tm-web`'s `integration-test` phase initializes `InfoPortalPublisherIT`,
  whose static JAR resolution fails because `vvwt-info-server` has not yet been built — the
  test class aborts with a class-initialization error and the reactor build ends in
  BUILD FAILURE. (A subsequent `mvn verify` without `clean` passes, because the fat-JAR
  produced by the failed run's later `vvwt-info-server` build — or any prior build — is
  still present.)

**Expected behaviour after the fix:** on a cold `mvn clean verify` from the reactor root,
`vvwt-info-server`'s repackaged fat-JAR is present before `vvwt-tm-web`'s `integration-test`
phase runs; `InfoPortalPublisherIT`'s three tests execute and the reactor build completes
BUILD SUCCESS. This is achieved without introducing any Maven dependency from `vvwt-tm-web`
on `vvwt-info-server` (DEC-42 D2) and without making the test skip when the JAR is absent.
The implementation mechanism is Delivery's to determine (see Notes for the indicated lever).

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-COLD-CLEAN-VERIFY-GREEN** — from a clean state in which
  `vvwt-info-server/target` holds no `*-exec.jar`, a single `mvn clean verify` invoked from
  the reactor root completes BUILD SUCCESS, and `InfoPortalPublisherIT`'s three tests are
  **executed** — run and reported as run in the failsafe results, not skipped and not
  aborted by a class-initialization error. (This is the reproduction scenario inverted; the
  failure is deterministic, so this cold-build run is itself the regression guard — it
  fails on the pre-fix reactor and passes after the fix.)
- [ ] **AC-TEST-REACTOR-SUITE-GREEN** — `mvn verify` for the full reactor is BUILD SUCCESS
  both cold (after `clean`) and warm (without `clean`); no pre-existing test in any reactor
  module regresses (DEC-54 / DEC-71).

### Governance

- [ ] **AC-GOV-NO-DEP-EDGE** — the fix introduces no Maven `<dependency>`, of any scope
  (`compile`, `provided`, `runtime`, `test`), from `vvwt-tm-web` on `vvwt-info-server` or
  `vvwt-info-client`. DEC-42 D2 and the existing `vvwt-tm-web/pom.xml`
  `maven-enforcer-plugin` `bannedDependencies` rule remain intact — the Enforcer check
  stays green in `mvn verify`.
- [ ] **AC-GOV-NO-SILENT-SKIP** — `InfoPortalPublisherIT` is not converted into a
  conditional skip (JUnit `Assumptions` or any equivalent) for the absent-JAR case. The
  test's E38S10 AC5 design ("the tests never skip silently") and the project's
  false-FAIL-over-false-PASS preference (DEC-71 / DEC-54) are preserved: the three publisher
  tests run on every cold `mvn clean verify`, never silently absent from a passing build.
- [ ] **AC-GOV-JAVADOC-CORRECTED** — `InfoPortalPublisherIT`'s class-level Javadoc and its
  JAR-resolution helper Javadoc no longer assert the false claim that the reactor builds
  `vvwt-info-server` before `vvwt-tm-web`'s integration-test phase because of the
  `vvwt-info-dto` dependency. The Javadoc instead states the actual ordering invariant the
  fix relies on (and that DEC-42 D2 precludes enforcing it via a Maven dependency edge).
- [ ] **AC-GOV-TDD-CLASSIFICATION-AND-HYGIENE** — Delivery classifies the change per DEC-22
  and its amendment DEC-67: the fix authors build-descriptor configuration (the reactor
  `<modules>` ordering in the parent `pom.xml`) and a documentation correction (the IT
  Javadoc) — no first-party production code — so it is outside the RED-first Iron Law;
  verification is the canonical full-lifecycle `mvn verify` BUILD SUCCESS gate (DEC-54 /
  DEC-71), with the deterministic cold-build reproduction (AC-TEST-COLD-CLEAN-VERIFY-GREEN)
  as the pass/fail evidence. The build remains warning-free (DEC-29); Spotless /
  google-java-format and the SPDX licence header are clean on any modified file
  (DEC-30 / DEC-76).

## Out of Scope

- **Any change to `InfoPortalPublisherIT`'s test logic, assertions, tenant/keypair fixtures,
  or Testcontainers setup**, beyond the Javadoc correction in AC-GOV-JAVADOC-CORRECTED. The
  three publisher tests are correct; only their runnability on a cold reactor build is
  broken.
- **Any change to `vvwt-info-server`, `vvwt-info-dto`, `vvwt-info-client`**, or to the
  Tournament Manager InfoPortal publisher service.
- **A machine-checked guard against re-introduction of the wrong reactor order** (an
  ArchUnit-style or Enforcer reactor-order rule). This story delivers the minimal ordering
  fix; a structural recurrence guard, if wanted, is a separate decision.
- **Reactor or CI restructuring** — splitting Testcontainers integration tests into a
  dedicated module, introducing build profiles, or changing how the daemon invokes Maven.
- **Adding a Maven `<dependency>` of any scope to force the build order** — precluded by
  DEC-42 D2 and the `bannedDependencies` Enforcer rule.

## Notes

Discovery 2026-05-17 — Bug-Triage Story, parent epic **E16** (Test Infrastructure
Governance; same family as the bug-triage fixes E16S02–E16S05). No Session Brief —
single-session triage: the root cause was verified structurally in-session (reactor
`<modules>` declaration order; absence of and DEC-42-D2 prohibition on a
`vvwt-tm-web → vvwt-info-server` dependency edge; the `bannedDependencies` Enforcer rule;
the static-initializer JAR resolution in `InfoPortalPublisherIT`; the false Javadoc
invariant) and was empirically reproduced by the operator (cold `mvn clean verify` fails,
warm `mvn verify` passes), independent of E16S05 (reproduced with E16S05 reverted).

**Fix direction chosen by the operator on 2026-05-17:** correct the reactor build order so
`vvwt-info-server`'s fat-JAR is built before `vvwt-tm-web`'s integration-test phase. Two
alternatives were considered and rejected:

- **Make `InfoPortalPublisherIT` skip gracefully when the JAR is absent** — rejected: a
  skip converts a deterministic false-FAIL (the cold build fails loudly) into a
  deterministic false-PASS (the cold build succeeds while the three publisher tests
  silently do not run), which contradicts the test's E38S10 AC5 "never skip silently"
  design and inverts the project's false-FAIL-over-false-PASS preference (DEC-71 / DEC-54).
- **Declare `vvwt-info-server`'s fat-JAR as a `test`-scope Maven artifact dependency of
  `vvwt-tm-web`** — the idiomatic Maven way to force both JAR availability and reactor
  ordering. Rejected outright: any `vvwt-tm-web → vvwt-info-server` dependency edge, of any
  scope, is banned by DEC-42 D2 and by the `bannedDependencies` Enforcer rule. The reactor
  `<modules>` ordering is the only DEC-42-D2-compliant lever.

**Accepted cost of the chosen direction:** the fix makes a cross-module build-time ordering
invariant (the `vvwt-info-*` modules built before `vvwt-tm-web`) depend on the textual order
of the parent-POM `<modules>` list, with no machine-checked guard against a future innocent
reordering reintroducing the break. That exposure is accepted for this minimal fix — a
structural recurrence guard (an Enforcer / ArchUnit reactor-order rule) is explicitly
deferred (see Out of Scope). Residual risk is low: `SlotOptE2EIT` already depends on the
same reactor-ordering property, so a regressive reorder would break two tests, not one,
raising the chance of detection.

**Implementation guidance (NOT acceptance criteria — Delivery owns the mechanism):** the
indicated lever is to move the `vvwt-info-dto` / `vvwt-info-server` / `vvwt-info-client`
`<module>` entries ahead of `vvwt-tm-web` in the parent `pom.xml` `<modules>` block. Maven
uses `<modules>` declaration order as the reactor tiebreaker for modules with no dependency
edge, and DEC-42 D2 precludes such an edge. Discovery verified: (a) no reverse edge exists —
none of `vvwt-info-dto` / `vvwt-info-server` / `vvwt-info-client` depends on `vvwt-tm-web`
(the only references are `bannedDependencies` exclusions) — so the reorder is safe; and
(b) `vvwt-tm-web` already depends on `vvwt-info-dto`, so placing the info-module set ahead
of `vvwt-tm-web` makes the declared order consistent with the dependency-driven build order
Maven already computes. Precedent: the slot-opt end-to-end test `SlotOptE2EIT` already
relies on this same reactor-ordering property — `vvwt-slotopt-dispatcher` is declared
before `vvwt-tm-web` so its fat-JAR exists when that test runs. Whether to additionally
make the JAR-resolution helper fail with a clearer diagnostic is at Delivery's discretion
and is not required by any AC.
