# Story E38S05: Tournament-registration endpoint (D-X2 (c)) + signed publisher endpoints — `POST /api/v1/tournaments/.../register` (mints `tournament_token` + `per_tournament_secret` BEFORE first snapshot, enabling early QR-code generation) + `POST /api/v1/publish/.../{events}` + `POST /api/v1/publish/.../snapshot` with RFC 8785 JCS canonical signature, per-tournament monotonic seq, 409 FULL_RESYNC, atomic supersede semantics, on-demand default-tenant location creation

## User Story

**As a** Tournament Manager instance with a registered Ed25519 key,
**I want** to register a new tournament via a dedicated signed endpoint that mints `tournament_token` + `per_tournament_secret` immediately (without requiring a first snapshot), so the operator can print QR codes BEFORE the tournament starts; then push delta domain events as signed REST POSTs with per-tournament sequence monotonicity and atomic supersede, plus a clear 409 FULL_RESYNC + dedicated `/snapshot` recovery path,
**so that** participants reach the per-team URL pre-tournament and see continuously-updated timeline that survives info-server restarts.

---

## Context

DEC-42 D2 mandates the publisher protocol shape; Brief D-7..D-9 specifies HTTPS REST + domain events + 409 FULL_RESYNC + dedicated `/snapshot` endpoint + per-tournament monotonic seq owned by TM. **Brief D-X2 (c) decision: tournament-registration is a DEDICATED endpoint** (not first-snapshot upsert) — mints tokens immediately so QR codes can be generated pre-tournament. Brief C-B1c specifies one active tournament per `(tenant_id, location_id)`; new tournament-registration discards prior tournament data via the supersede mechanic. Brief D-2 (post-F20 fix) specifies on-demand location creation under default tenant on self-host.

**Brief D-X3 (c1) HMAC-derived team tokens**: this story mints `per_tournament_secret` (32 bytes, cryptographically random) at tournament-registration; returns it to TM in the response. TM derives team URLs locally via `team_token = HMAC-SHA256(per_tournament_secret, team_uuid)`. The reader (E38S06) validates URLs by recomputing HMAC from the stored secret. No per-team-token storage; server stores only the secret.

**Brief D-X6 (a) RFC 8785 JCS** for canonical signature payload: this story uses the `io.github.erdtman:java-json-canonicalization` library (Apache 2.0, OSS per DEC-3) to produce byte-stable JCS-canonical bytes for signing. Both this story (server-side verification) and E38S09 (TM-side signing) MUST agree on JCS bytes byte-for-byte.

This story consumes the `SignatureVerifier` interface from E38S04 (the F6 ownership) on every signed request: `verify(jcsCanonicalBytes, signature, tenant.public_key)` per DEC-6 + DEC-43 D2.

## Acceptance Criteria

- [ ] **AC1 (testing)**: Every endpoint, service method, and seq-validation method has a RED-first test per DEC-22 Iron Law.
- [ ] **AC2 (testing)**: **Tournament-registration IT** (the D-X2 (c) endpoint): signed `POST /api/v1/tournaments/{tenant}/{location}/{tournament-id}/register` with body `Envelope<TournamentRegistrationRequest{team_uuids: List<UUID>}>` returns 200 with `Envelope<TournamentRegistrationResponse{tournament_token: String, per_tournament_secret: byte[], schemaVersion: String}>`. Server creates `tournament` row, generates random 256-bit `tournament_token` (Base64URL-encoded) + 256-bit `per_tournament_secret` (BYTEA), persists. Subsequent re-registration of same `(tenant, location, tournament-id)` triple is the supersede path (AC4).
- [ ] **AC3 (testing)**: **Publisher delta IT** — happy path: signed `POST /api/v1/publish/{tenant}/{location}/{tournament}` with `Envelope<DomainEvent>` and `seq=last_applied_seq+1` → 200; the delta is persisted to `tournament_delta`; `last_applied_seq` advances; the corresponding state mutation is applied to `tournament.state`.
- [ ] **AC4 (testing)**: **Out-of-order seq IT**: signed POST with `seq != last_applied_seq+1` → 409 with `Envelope<FullResyncRequired{required: "FULL_RESYNC", last_applied_seq: <N>, tournament_token: <existing-or-null>}>`. Test variants: `seq < last_applied_seq+1` (replay), `seq > last_applied_seq+1` (skip), `seq=0` (server has no record of this tournament — same 409 FULL_RESYNC; client is expected to call tournament-registration first per AC2).
- [ ] **AC5 (testing)**: **Snapshot resync IT**: post a 409, then signed `POST /api/v1/publish/{tenant}/{location}/{tournament}/snapshot` with `Envelope<{seq, snapshot: FullTournamentState}>` → 200; server clears prior `tournament_delta` history for that tournament, applies the snapshot to `tournament.state`, sets `last_applied_seq=N`. Subsequent delta posts with `seq=N+1` succeed.
- [ ] **AC6 (testing)**: **Supersede atomicity IT** (cycle-1 F-4 promotion to AC): a tournament-registration POST for an EXISTING `(tenant_id, location_id)` triggers atomic supersede in a SINGLE database transaction: (1) prior `tournament` row gets `superseded_at = now()`; (2) prior `tournament_delta` rows are deleted; (3) NEW `tournament` row created with fresh `tournament_token` + fresh `per_tournament_secret` + new `tournament_id`; (4) `audit_log` row inserted. Test simulates rollback after step (1) (e.g., via `@Sql` script or test-helper that throws between transactional steps) → verifies system state is FULLY rolled back: prior tournament still active, no new row, no audit log entry. The 24h grace window for the superseded `tournament` row is preserved per E38S06.
- [ ] **AC7 (governance)**: Endpoints exposed at exactly:
  - `POST /api/v1/tournaments/{tenant_id}/{location_id}/{tournament_id}/register` — body `Envelope<TournamentRegistrationRequest>` + signature header — returns 200 + `Envelope<TournamentRegistrationResponse>` (with tokens).
  - `POST /api/v1/publish/{tenant_id}/{location_id}/{tournament_id}` — body `Envelope<DomainEvent>` + signature — 200 / 409 / 413 / 401.
  - `POST /api/v1/publish/{tenant_id}/{location_id}/{tournament_id}/snapshot` — body `Envelope<FullTournamentState>` + signature — 200 / 4xx.
- [ ] **AC8 (governance)**: **RFC 8785 JCS canonical signature payload** per Brief D-X6 (a). Library: `io.github.erdtman:java-json-canonicalization` (Apache 2.0, OSS-compliant per DEC-3). Signature header: `X-Vvwt-Signature: <base64-encoded signature>`. The `payload` to sign is `JCS(envelope_body)` as bytes (NOT the request body bytes verbatim — they may include whitespace etc.). **Cross-implementation byte-stability AC**: a fixture file `vvwt-info-server/src/test/resources/jcs-fixtures/sample-publish-payload.json` + its signed canonical bytes (signed by an external tool e.g. `jcs` CLI) is verified by the server's verifier — confirms TM-side and server-side produce byte-identical JCS bytes. Test verifies that any byte-level modification to the body invalidates the signature.
- [ ] **AC9 (governance)**: Skill attestation per Epic Success Metrics. **DEC-26 DAO IT three-rule scope-extension via DEC-46** (cycle-1 F-7 fix): all DAO IT touches in this story (`tournament_delta`, `tournament`, `audit_log` access) use `InfoDaoTestSupport` from E38S03 (per DEC-46 clause #2(b)) — schema-from-Flyway, assertj-db verifier, read/write decoupling. AC enumerates per-DAO compliance: (a) `TournamentDeltaDaoIT` satisfies Rule 1+2+3, (b) `TournamentDaoIT` satisfies Rule 1+2+3, (c) `AuditLogDaoIT` satisfies Rule 1+2+3 (all already from E38S03; this story consumes them).
- [ ] **AC10 (security)**: **Per-request signature verification** (DEC-6 + DEC-43 D2): invalid signature → 401 with `Envelope<SignatureInvalid>` regardless of request body validity. Audit-log row written with `signature_outcome=INVALID`, `rejection_reason=null` (signature is the cryptographic outcome; the request never reached policy checks).
- [ ] **AC11 (security)**: **Single-key guarantee** (cycle-1 F-6 naming-fix from "single-writer"): a publish or tournament-registration request signed with a key OTHER than the registered key for `(tenant_id)` is rejected with 401 (signature verification fails using the registered public key). The single-writer property at the SOURCE (one TM holding the private key) is operator-internal — protocol layer enforces single-KEY only; concurrent same-key writes from misconfigured operator setups surface as seq-mismatch 409 (AC4).
- [ ] **AC12 (security)**: **On-demand location creation under default tenant** per Brief D-2 (the only AC10-cycle-1 surviving sub-clause; primary-profile location-limit is E38S04 territory): first publish or tournament-registration for `(default_tenant_id, NEW_location_id, ...)` on self-host implicitly creates the location entry under the default tenant. Verified by IT: registering a new tournament under the default tenant with a previously-unseen `location_id` succeeds; the `tenant.is_default=true` row's location-list grows on-demand (modeled within the `tournament` row's `location_id` column — the `tenant` table has no separate `locations` array since `is_default=true` implies unbounded per Brief C-B1b).
- [ ] **AC13 (error-handling)**: **Audit-log every accepted AND rejected request** per DEC-6 + Brief C-AUDIT-LOG-SCHEMA, with the **split-column schema** (per Brief D-X5):
  - `signature_outcome` ∈ {VALID, INVALID, NA} (NA reserved for unsigned paths — none in this story; all operations are signed).
  - `rejection_reason` ∈ {SEQ_MISMATCH, TOURNAMENT_NOT_FOUND, MALFORMED, PAYLOAD_TOO_LARGE, INTERNAL_ERROR, null (when accepted)} for this story's scope. Audit row written even on 5xx (durability via dual-transactional-unit or write-ahead audit buffer; IT covers via deliberate-throw fixture).
- [ ] **AC14 (error-handling)**: Body-size cap on publish requests: configurable `vvwt.info.publish.max-delta-bytes` (default 1 MB) and `vvwt.info.publish.max-snapshot-bytes` (default 16 MB — matches `tournament.state` upper bound from E38S03 AC11). Oversize requests → 413 Payload Too Large with `Envelope<RegistrationRejected{reason: "PAYLOAD_TOO_LARGE"}>` (reusing the reason-string DTO; ad-hoc semantics OK per E38S02 open-string `reason`). Audit row written. **Asymmetric default rationale**: snapshot is strictly larger than a delta (carries full state + envelope + metadata); 16:1 ratio reflects empirical estimates for a 100-team / 50-round tournament's snapshot size — Phase 2+ may tune from observed traffic.
- [ ] **AC15 (error-handling)**: Malformed `DomainEvent` discriminator (unknown event type per E38S02 sealed-type AC2) → 400 with `Envelope<RegistrationRejected{reason: "MALFORMED"}>`. Polymorphic discrimination per E38S02 sealed-type contract.

## Notes

- **D-X2 (c) tournament-registration endpoint** is the load-bearing AC2 for the human-pinned property "URL must be available BEFORE first snapshot publication so QR codes can be generated as early as possible". The tournament-registration response carries `tournament_token` + `per_tournament_secret`; TM derives `team_token = HMAC(per_tournament_secret, team_uuid)` for each known team and distributes URLs to the organizer.
- **D-X3 (c1) HMAC-derivation**: server stores ONLY `per_tournament_secret` on the `tournament` row (no per-team-token storage). Reader validation in E38S06 recomputes HMAC for each team_uuid in the current `tournament.state` team list and constant-time-compares with the URL's team_token.
- **D-X6 (a) RFC 8785 JCS**: chosen over project-internal canonicalization spec because it's a published industry standard with mature Java OSS implementation. Both server (this story) and TM (E38S09) use the same library version pin to guarantee byte-identity.
- **Single-key vs single-writer naming** (cycle-1 F-6 fix): the protocol enforces single-KEY-per-tenant via DEC-42 D3 first-key-wins binding. "Single-writer" is the operator-aspirational property (one TM holding the private key); the protocol cannot detect shared-key misconfiguration. Audit-log source-IP analysis (Phase 2+) is the operator-forensic mitigation.
- AC6's atomicity test pattern: standard Spring `@Transactional` with `@Rollback` + a deliberate-throw fixture; alternative pattern uses `TransactionTemplate.executeWithoutResult` with a forced exception; either passes.
- AC8 fixture file: shipped in test resources; signed-bytes recorded as base64 next to the fixture JSON; verifier IT loads both and asserts verifier returns true. Cross-tool byte-stability is the property under test.
