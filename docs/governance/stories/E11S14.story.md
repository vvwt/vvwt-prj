# Story E11S14: Fix — TimerDataResponse carries operator-configured per-phase values + drop duplicate phase-pause input + distinct labels for Phasen-Pause and Zusatzpause

## User Story

**As a** tournament organizer using the Timer SPA's inline phase-config and break-edit features (E11S12),
**I want** the lap-time, lap-break, and phase-pause input fields to show the values I configured in the phase plan (not "0"), the dedicated Phasen-Pause schedule row to show its 30-minute duration in its own input field, only ONE place to edit the phase-pause (not two), and the schedule to clearly distinguish the inter-phase Phasen-Pause from intra-phase Zusatzpause entries by label,
**so that** I can verify my phase plan at a glance without context-switching, adjust values inline against meaningful defaults, and read the schedule without ambiguity about which kind of break sits between which rounds.

---

## Context

After E11S12 shipped the inline-controls + ephemeral phase-config edit, operator empirically observed three usability defects on 2026-05-28:

**Symptom 1 — PhaseConfigRow inputs default to 0.** `App.svelte:698` `getInitialPhaseConfig` returns `{ lapTimeMinutes, lapBreakTimeMinutes: 0, sectionBreakTimeMinutes: 0 }`. Only `lapTimeMinutes` is derived (from the first ROUND entry's start-end delta); the break fields are hardcoded to zero. The PhaseConfigRow's `LAP-PAUSE` and `PHASEN-PAUSE` inputs show "0" instead of the operator-configured `DraftSection.lapBreakTimeMinutes` and `DraftSection.sectionBreakTimeMinutes`. The dedicated Phasen-Pause schedule row's inline-edit `Dauer` input is also empty (same root cause — backend does not carry the operator-configured value for that break entry to the FE).

**Symptom 2 — Duplicate phase-pause input.** The same `sectionBreakTimeMinutes` value is exposed in TWO places: (a) PhaseConfigRow's `PHASEN-PAUSE` numeric input above Round 1 of the phase, AND (b) the dedicated SECTION_BREAK schedule row (rendered as a "Pause" entry) at the END of the phase with its own `Dauer` inline-edit. Operator decision: remove the input from PhaseConfigRow entirely (input + prop + caller binding); keep the edit only on the dedicated schedule row (which sits at the visual location of the actual break in the timeline).

**Symptom 3 — Phasen-Pause and Zusatzpause not distinguishable in the schedule.** Both `TimelineEntryType.INTRA_PHASE_BREAK` and `TimelineEntryType.SECTION_BREAK` are mapped to `TimerBreakType.ADDITIONAL` on the wire by `DefaultTimerDataService.mapTimelineToSchedule`. The FE renders both with the generic "Pause" label or `entry.label` if set. The inter-phase Phasen-Pause and the intra-phase Zusatzpause look identical in the schedule. Operator wants Phasen-Pause clearly labeled "Phasen-Pause", and Zusatzpause labeled with the configured `DraftBreak.label` or — if empty / null — fall back to "Zusatzpause".

Operator's data-source decision: backend extends `TimerDataResponse` with a per-phase config sub-DTO carrying `lapTimeMinutes`, `lapBreakTimeMinutes`, `sectionBreakTimeMinutes`, and the intra-phase `breaks` list (each with `durationMinutes` + `label`). Backend distinguishes SECTION_BREAK from INTRA_PHASE_BREAK on the wire by reusing the existing `label` slot — sends a stable, non-i18n key string (Delivery picks the literal, e.g. `"PHASE_BREAK"`) for SECTION_BREAK; INTRA_PHASE_BREAK continues to send `DraftBreak.label`. FE switches on the stable key vs `label`-or-fallback "Zusatzpause".

Discovery Session Brief `discovery-2026-05-28-timer-post-e11s10-s12-bugs` (Tier-2 cycle-2 PASS, rubric_version 2026-03-30; operator-validated 2026-05-28) drives the scope.

This Story ships **after** Story E11S13 (Brief D-8 / T-6 — E11S13 is strictly subtractive in `ScheduleRow.svelte`; this Story layers Phasen-Pause / Zusatzpause label rendering atop the cleaned-up component).

## Acceptance Criteria

> All acceptance criteria are observable behaviour. Implementation approach (backend DTO shape, FE state wiring) is Delivery's choice within the bounds set by the Brief.

### Symptom 1 — Per-phase config values reach the FE inputs

- [ ] **AC1 — TimerDataResponse carries per-phase config.** The backend `TimerDataResponse` (or equivalent existing wrapper) is extended with a per-phase config sub-structure that, for each phase in the tournament's persisted `DraftConfig`, carries: `lapTimeMinutes`, `lapBreakTimeMinutes`, `sectionBreakTimeMinutes`, and the intra-phase `breaks` list (each with `durationMinutes` and `label`). The wire shape is Delivery's choice (e.g. a `TimerPhaseConfigResponse` sub-record extending `TimerPhaseResponse`, or a separate parallel list keyed by `phaseNumber` — Delivery picks).
- [ ] **AC2 — PhaseConfigRow LAP-PAUSE input pre-populates from backend value.** The `LAP-PAUSE (MIN)` input in PhaseConfigRow renders the operator-configured `DraftSection.lapBreakTimeMinutes` value for that phase on initial page load (read from AC1's per-phase config). The previous behaviour of hardcoding `lapBreakTimeMinutes: 0` in `getInitialPhaseConfig` is removed.
- [ ] **AC3 — PhaseConfigRow LAP-ZEIT input remains operator-configured.** The `LAP-ZEIT (MIN)` input continues to render the operator-configured `DraftSection.lapTimeMinutes` for that phase (this is now read from AC1's per-phase config, not derived from the schedule's first ROUND start-end delta). The delta-derivation fallback path is removed if AC1's value is reliably present (Delivery's choice — if Delivery retains the delta fallback as a defensive backstop, the impl-report attests this).
- [ ] **AC4 — Dedicated SECTION_BREAK schedule row's `Dauer` input pre-populates.** The inline-edit `Dauer` input on the dedicated Phasen-Pause schedule row (the SECTION_BREAK entry between two phases) renders the operator-configured `DraftSection.sectionBreakTimeMinutes` of the **preceding** phase on initial page load. Empty / unset behaviour from before this Story is replaced.
- [ ] **AC5 — Dedicated INTRA_PHASE_BREAK schedule row's `Dauer` + `Bezeichnung` inputs pre-populate.** The inline-edit `Dauer` and `Bezeichnung` inputs on each intra-phase break (INTRA_PHASE_BREAK / Zusatzpause) schedule row render the operator-configured `DraftBreak.durationMinutes` and `DraftBreak.label` (read from AC1's per-phase config `breaks` list).

### Symptom 2 — Drop duplicate phase-pause input

- [ ] **AC6 — `sectionBreakTimeMinutes` prop is removed from `PhaseConfigRow.svelte`.** The component no longer accepts `sectionBreakTimeMinutes` as a prop.
- [ ] **AC7 — `PHASEN-PAUSE (MIN)` input is removed from `PhaseConfigRow.svelte`.** The component no longer renders the input element or its label.
- [ ] **AC8 — `App.svelte` `<PhaseConfigRow ... sectionBreakTimeMinutes={...} />` call-site is updated.** The caller no longer passes `sectionBreakTimeMinutes` to `PhaseConfigRow`. Any consumer that derived this value for the PhaseConfigRow (e.g. in `getInitialPhaseConfig`) is updated to no longer expose it via the PhaseConfigRow path. The value continues to be available for the dedicated SECTION_BREAK schedule row per AC4.

### Symptom 3 — Distinguish Phasen-Pause from Zusatzpause in the schedule

- [ ] **AC9 — Backend distinguishes SECTION_BREAK from INTRA_PHASE_BREAK on the wire via the `label` slot.** `DefaultTimerDataService.mapTimelineToSchedule` populates the `label` field of a SECTION_BREAK `TimerScheduleEntryResponse` with a stable, non-i18n key string (Delivery picks the literal — e.g. `"PHASE_BREAK"`); INTRA_PHASE_BREAK continues to populate `label` with `DraftBreak.label` (which may be null or empty). The `breakType` field remains `ADDITIONAL` for both. (Alternative path — adding a dedicated discriminator field on the wire — is acceptable if Delivery provides rationale in the impl-report overcoming the no-schema-change simplicity of label-reuse.)
- [ ] **AC10 — FE renders "Phasen-Pause" for SECTION_BREAK entries.** When a schedule row's `label` matches the stable SECTION_BREAK key from AC9, the FE renders the i18n-localized "Phasen-Pause" label (new i18n key added to `de.json` per project frontend convention).
- [ ] **AC11 — FE renders the operator-configured break label for INTRA_PHASE_BREAK entries.** When a schedule row is `breakType=ADDITIONAL` AND its `label` is NOT the SECTION_BREAK key, the FE renders `label` if it is non-empty AND non-null; otherwise it falls back to the i18n-localized "Zusatzpause" label (new i18n key added if not already present).
- [ ] **AC12 — Audio events remain silent for both SECTION_BREAK and INTRA_PHASE_BREAK rows.** Both kinds continue to be `breakType=ADDITIONAL`, so the existing `getAudioEventOnActivate` / `getAudioEventOnDeactivate` classification (preserved per E11S13 AC3 carryover) returns NONE for both. No audio fires for either.

### Error-handling (mandatory category)

- [ ] **AC13 — FE behavior when the per-phase config sub-block is absent on the response.** When a `TimerDataResponse` arrives without the per-phase config block (e.g. serialization drift, older backend during a rolling deploy, or a phase row that lacks an entry in the new structure for any reason), the FE renders the page with a documented, deterministic fallback. Delivery picks: (a) render input fields blank with a non-blocking inline note that values could not be loaded; OR (b) hide the PhaseConfigRow entirely for that phase. The choice is impl-report attested. The FE does NOT silently substitute hardcoded `15` / `0` values.
- [ ] **AC14 — FE behavior when `DraftBreak.label` is null or empty.** Per AC11, the FE falls back to the "Zusatzpause" i18n label. The inline `Bezeichnung` input shows an empty string (no fallback text inside the input — only the rendered schedule-row label uses the fallback).
- [ ] **AC15 — Partial / older DraftConfig where per-phase config fields are unavailable.** This AC covers the case where `DraftConfig` deserialization SUCCEEDS but does NOT yield per-phase config fields for every phase (e.g. older serialized DraftConfig schema, the `sections` list is shorter than the phase count, or a section is missing one of the four target fields). The no-persisted-DraftConfig path is already covered upstream by E11S10 AC11 / `NoScheduleConfiguredException` (the FE never receives a TimerDataResponse in that case — an error response triggers the existing E11S03 error states). For the partial-DraftConfig case THIS AC covers, `DefaultTimerDataService` either (a) omits the per-phase config sub-block for the affected phase only (FE then triggers AC13 fallback for that phase) OR (b) populates the per-phase config sub-block with placeholder default values for the affected phase. Delivery picks (a) or (b); the choice is impl-report attested. Either way the FE does not silently substitute hardcoded values that mis-represent operator intent.
