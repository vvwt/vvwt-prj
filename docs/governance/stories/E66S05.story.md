# Story: The match-correction page identifies each side by team number and name

## User Story

**As a** tournament organizer correcting a match result,
**I want** each side of the match identified by its team number and name,
**so that** I enter the corrected scores against the right team without ambiguity.

---

## Context

The match-correction ("Match-Korrektur") page labels the two score columns "Team 1 Punkte"
and "Team 2 Punkte" — generic placeholders that never name the actual teams. The operator
sees only a Match-ID and "Team 1 / Team 2", which is not enough to be sure the right match
is being corrected. The match-list data the page already consumes carries the resolved
team names (`team1Name` / `team2Name`); the page simply does not render them. The team
**number** is held on the `Team` entity.

The Discovery Session Brief records this as Q-2 — match identity must be unambiguous; show
the number and the name.

---

## Acceptance Criteria

- [ ] AC1 (testing): TDD per DEC-22 — a failing test is authored before the production
  change, proven RED, then GREEN.
- [ ] AC2: on the match-correction page, each side is identified as
  "Nr. {teamNumber} — {teamName}" instead of the generic "Team 1" / "Team 2" — in the
  score-input column headers.
- [ ] AC3: the same "Nr. {teamNumber} — {teamName}" identification appears in the
  correction confirmation dialog, so the operator confirms against named teams.
- [ ] AC4 (governance): when a side's slot has a team assigned, the page shows that team's
  number and name (both are available — the name from the match data the page already
  receives, the number resolved from the team, the payload extended minimally if it does
  not already carry the number — see AC5). When a side's slot has no team assigned at all,
  the label degrades gracefully to a clear fallback — never "undefined", never a blank
  header, never a runtime error.
- [ ] AC5 (governance): the team number and name are sourced from the match data the
  backend provides for this page — extended minimally if the team number is not already
  carried so that the number is reliably available for every match the page can correct;
  no `teamId` UUID is rendered in the DOM (DEC-9). The frontend stays Vite + Svelte +
  TypeScript, no SvelteKit (DEC-2); any operator-facing string this story introduces
  resolves through `de.json` via the project's canonical fallback-aware i18n pattern
  (`$_(key, { default })`). `mvn verify` is BUILD SUCCESS for `vvwt-tm-web`, including the
  frontend build (DEC-54).

> All acceptance criteria must be verifiable.

---

## Out of Scope

- The "Match-ID" line on the page — it is unchanged.
- Any change to the correction logic itself (set scores, the correction submission, the
  audit trail) — this story changes only how the two teams are labelled.
- Other pages that show matches (the Display overview, the match overview).

---

## Dependencies

- None — independently deliverable. The match-list data already carries the resolved team
  names; the team number is available on the `Team` entity.
- DEC-9 — structural identity; a `teamId` UUID must never reach the DOM.

---

## Notes

Acceptance criteria state behaviour, not a test mechanism — no Svelte-5 component mount is
required (component mounting is infeasible in the project's Vitest+jsdom environment, a
pre-existing gap documented by E58S05). Delivery decides whether the team number is already
on the page's data payload or the payload needs a minimal extension to carry it, and the
exact header layout; the labels appear in the score-input column headers and the
confirmation dialog — the two places the page presents the teams.
