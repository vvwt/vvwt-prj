# Story: Tournament-form generator selection + German labels on all dropdowns; phase-plan non-last-phase game-mode pre-fill

## User Story

**As a** tournament organizer,
**I want** the tournament form to offer only valid (non-last-phase) match generators with readable German labels on every dropdown, and the phase plan to open with every non-last phase's game mode already pre-filled,
**so that** I can configure a tournament and its phase plan without blank dropdowns, raw key strings, or the ability to pick a generator that is only valid for the last phase.

---

## Context

This is a bug-triage follow-up to **E58S05** ("Data-driven, capability-filtered phase-plan generator
selection", PR #303, merged 2026-05-16) — the story that operationalized DEC-73 D-5's capability-driven
generator selection. An operator reported four defects (2026-05-16):

1. In the phase plan (`DraftConfig.svelte`), the game mode ("Spielmodus") of every non-last phase
   should be pre-filled from the tournament's chosen default — the non-last phase dropdowns instead
   render blank.
2. The tournament's chosen default generator is currently `awardCeremony` — a generator valid only
   for the **last** phase.
3. The tournament form (`TournamentForm.svelte`) should offer only generators **not** intended for the
   last phase, and pre-select the first available one.
4. The tournament form shows raw string keys / IDs in its dropdowns instead of German labels.

**Root cause.** E58S05 applied the `isLastPhaseGenerator` capability filter only to the phase-plan
dropdown (`DraftConfig.svelte`); the tournament-form dropdown (`TournamentForm.svelte`) was left
unfiltered — it iterates all generators, defaults to `generators[0]`, and renders the raw `keyId`.
Because the tournament's stored default can therefore become `awardCeremony` (a last-phase generator),
the phase plan — which pre-fills new phases from that tournament default and then filters non-last
dropdowns to non-last generators only — renders those dropdowns blank (the default is filtered out).
Symptom 1 is thus downstream of symptoms 2/3. Separately, phases **loaded from a persisted draft** are
never normalized at all — only newly-added phases receive any default, and only the last phase has a
load-time invariant-enforcer (`enforceLastSectionAwardCeremony`).

E58S05's own acceptance criteria under-specified the tournament-form side (AC5 required only a shared
registry source and "becomes the phase-plan default" — not capability filtering or i18n labels), so
Delivery built exactly what was specified. This is a Discovery scoping gap, closed here.

The fix is **frontend-only**. The registry, `MatchGeneratorInfo`, the `GET /api/match-generators`
endpoint, and the shared `generatorStore.ts` already carry the `isLastPhaseGenerator` flag (E58S01 /
E58S05) — no backend, REST, or store-contract change is needed.

The operator additionally asked for German labels on the tournament form's other three option
dropdowns — match format ("Spielmodus"), scoring rule ("Wertungsregel"), set-validation rule
("Satzregel"). Those dropdowns pre-date E58 (original tournament form, E05-era); their missing-label
defect is pre-existing and bundled here because it is the identical defect pattern on the same form.

## Acceptance Criteria

- [ ] AC1 (testing): The tournament-form match-generator dropdown offers only non-last-phase
  generators — generators whose `isLastPhaseGenerator` capability flag is `false`. A last-phase-only
  generator (e.g. `awardCeremony`) never appears as an option on the tournament form. Filtering is by
  the capability flag, NOT by matching the generator key string (DEC-73 D-5 / C-1). Verified by a
  frontend test whose fixture includes a generator carrying a flag value independent of its key, so
  that a key-string-based filter would fail the test.
- [ ] AC2 (testing): The tournament-form's default match-generator selection is the first
  non-last-phase generator in the registry list — not the first generator overall. Verified by a
  frontend test with a fixture whose first registry entry is a last-phase generator.
- [ ] AC3 (testing): On the phase plan, every non-last phase whose game mode is not a valid
  non-last-phase generator (blank, or a last-phase generator key) is set to the tournament's chosen
  non-last default; a non-last phase that already holds a valid non-last-phase generator is left
  unchanged (an operator's explicit per-phase choice is preserved). This normalization is applied
  whenever the phase list is loaded or structurally changed — initial load of a persisted draft,
  adding a phase, removing a phase, and reload after a phase-plan reset. A single-phase plan has no
  non-last phase, so the normalization is a no-op for it. The behaviour is verified per AC5 — at the
  pure-function / module level, for the blank-game-mode case, the last-phase-generator-key case, and
  the valid-non-last-generator case (asserted unchanged); the normalization is invoked at every
  phase-list entry point listed above.
- [ ] AC4 (testing): The non-last-phase normalization (AC3) runs on the post-mutation phase list,
  after the existing last-phase enforcer has set the last phase. Consequently, when a phase is added
  and the previously-last phase becomes non-last while still holding the last-phase (award-ceremony)
  generator, that phase's game mode is normalized to the non-last default. Verified by a frontend
  test that adds a phase and asserts the demoted phase's game mode is the non-last default.
- [ ] AC5 (testing): TDD per DEC-22 — each new or changed unit of frontend logic (the tournament-form
  capability filter and default selection; the non-last-phase normalization) has a failing test
  authored before its implementation. The non-last-phase normalization is implemented as a pure,
  separately-testable function so DEC-22 (RED-first) and the test-environment limitation (C-6) are
  jointly satisfiable; behaviour is verified at the pure-function / module level, not via Svelte
  component mounting (infeasible in the project's Vitest + jsdom environment — E58S05 AC2 finding).
- [ ] AC6 (governance): All four option dropdowns on the tournament form — match generator, match
  format, scoring rule, set-validation rule — render each option's visible text via an i18n label.
  No tournament-form dropdown renders a raw registry key, enum name, or rule ID.
- [ ] AC7 (governance): A German i18n label value exists for every option value of those four
  dropdowns, in `de.json`. (`de.json` is the project's fallback locale — `i18n.ts` sets
  `FALLBACK_LOCALE = 'de'`; `en.json` is an intentionally partial override-only overlay and is NOT
  required to carry these keys — consistent with the existing generator labels, which today live
  only in `de.json`. `en.json` stays unchanged.) The operator-supplied German labels, keyed by the
  exact registry value each dropdown emits, are:

  | Value (registry key) | Dropdown | German label |
  |---|---|---|
  | `roundRobin` | match generator | Jeder gegen Jeden |
  | `awardCeremony` | match generator | Siegerehrung |
  | `BEST_OF_1` | match format | 1 Gewinnsatz |
  | `BEST_OF_3` | match format | 2 Gewinnsätze |
  | `BEST_OF_5` | match format | 3 Gewinnsätze |
  | `BEST_OF_7` | match format | 4 Gewinnsätze |
  | `FIXED_2_SETS` | match format | Genau 2 Sätze |
  | `setPoints` | scoring rule | Satzgewinn |
  | `threePoint` | scoring rule | Drei-Punkte-Wertung |
  | `twoPoint` | scoring rule | Zwei-Punkte-Wertung |
  | `standardVolleyball` | set-validation rule | Standard-Volleyball |
  | `timeBounded` | set-validation rule | Zeitbegrenzter Satz |

  The scoring-rule and set-validation-rule keys are the registry bean IDs the API actually emits
  (`ScoringRule.getBeanId()` and the Spring `@Component` bean name) — verified against `staging`
  HEAD; the `ScoringRulesController` Javadoc example block carries stale strings
  (`threePointMatch` / `twoPointMatch` / `timeBoundedSet`) that the executable code does not produce.
  The `roundRobin` label is corrected from the current placeholder value "RoundRobin" to "Jeder
  gegen Jeden" (a translation correction — not a DEC-73 D-7 violation: D-7 preserves the German
  display value across the `siegerehrung`→`awardCeremony` key rename, it does not freeze an
  inaccurate placeholder). `awardCeremony` stays "Siegerehrung". Delivery freshly audits the
  registered option values at delivery HEAD (scoring/set-validation rule IDs from the registries,
  match formats from the `MatchFormat` enum names, generators from the generator registry); if a
  registered value has no entry in this table, Delivery STOPS and escalates — no silently invented
  label.
- [ ] AC8 (governance): All four dropdowns' option-value label keys live under one neutral,
  page-agnostic i18n namespace, with a per-dropdown sub-key group (match generator, match format,
  scoring rule, set-validation rule). The namespace is NOT page-scoped — not under `draftConfig.*`
  (phase plan) or `tournamentForm.*` (tournament form). The generator-label sub-group is the one the
  phase plan also consumes: the existing `draftConfig.gameMode.*` generator labels are moved into it
  and `DraftConfig.svelte`'s existing reference is re-pointed as part of this story; the match-format
  / scoring-rule / set-validation-rule sub-groups are net-new keys (none exist today). The generator
  label display **values** are unchanged by the key relocation (DEC-73 D-7) — the only generator
  value change is the `roundRobin` correction in AC7.
- [ ] AC9 (governance): The capability filter is extended from the phase-plan UI (DEC-73 D-5) to the
  tournament-form generator surface — a faithful application of D-5's intent, closing an E58S05
  operationalization gap; no DEC is amended. The change stays Vite + Svelte + TypeScript, no
  SvelteKit (DEC-2). No backend, REST endpoint, or `generatorStore.ts` contract change is made, and
  no persisted `matchGeneratorId` or `draft_json` value is migrated (DEC-25 no-production-data).
- [ ] AC10 (governance): `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54), including the
  frontend build via `frontend-maven-plugin`.
- [ ] AC11 (error-handling): The non-last default is resolved defensively — it is the tournament's
  chosen generator when that is a valid non-last-phase generator, otherwise the first non-last-phase
  generator. If no non-last-phase generator is registered at all, the tournament-form dropdown and
  the phase-plan non-last dropdowns degrade gracefully: no crash, no invalid key written, the game
  mode left blank. Verified by a frontend test with a fixture in which every registered generator is
  a last-phase generator.
- [ ] AC12 (security): Option text on all four tournament-form dropdowns is rendered as plain text
  through the i18n / Svelte templating layer (Svelte auto-escaping); generator keys and rule IDs
  obtained from the API are never rendered as raw/unescaped HTML. No new user- or API-controlled
  value reaches the DOM unescaped.

## Out of Scope

- Adding, removing, or renaming any match generator, match format, scoring rule, or set-validation
  rule — the dropdowns reflect exactly the registered set.
- The registry, `MatchGeneratorInfo`, `getGeneratorInfoList()`, the `GET /api/match-generators`
  endpoint, and `generatorStore.ts` — delivered by E58S01 / E58S05; consumed unchanged.
- Any backend / REST / persistence change; any data migration of a stored `matchGeneratorId` or
  `draft_json` value (DEC-25 no-production-data — the defensive resolution in AC11 makes the UI
  correct without one).
- The phase-plan last-phase rule and its enforcer (`enforceLastSectionAwardCeremony`) — already
  correct; unchanged.
- The Svelte-5 component-mount test-environment limitation (E58S05 AC2 amendment) — a pre-existing
  project gap, not addressed here.
- The DEC-59 operator-confirmation team-assignment workflow and the `gameMode`-string lifecycle
  dispatch — untouched (DEC-73 D-5 keeps `isLastPhaseGenerator` and the `gameMode` string value as
  two distinct, non-unified discriminators).

## Notes

- **Provenance is mixed but the defect class is one.** The generator-selection defects (symptoms
  1–3, and the generator label) are E58S05 regressions/gaps; the missing German labels on the match
  format / scoring rule / set-validation rule dropdowns are a pre-existing E05-era gap. They are
  bundled into one story because they are the identical "raw value rendered, no i18n label" pattern
  on the same form and the operator reported them together (2026-05-16).
- **Root-cause analysis** is in the Context section: the tournament form was never capability-
  filtered, its default is the unfiltered first generator, and it renders raw keys; the phase plan
  has no load-time normalization for non-last phases. Discovery investigated the code at `staging`
  HEAD — `TournamentForm.svelte` (unfiltered `{#each generators}`, `generators[0]` default, raw
  `{gen.keyId}`), `DraftConfig.svelte` (`addSection` pre-fills new phases only; loaded sections kept
  verbatim; `enforceLastSectionAwardCeremony` last-phase-only), `generatorFilter.ts` (the existing
  `filterNonLastPhaseGenerators` / `filterLastPhaseGenerators` pure functions to reuse).
- **Determinism caveat.** Today exactly two generators are registered (`roundRobin` non-last,
  `awardCeremony` last), so "the first non-last-phase generator" resolves to `roundRobin` by
  cardinality. If a second non-last generator is ever registered, the "first" becomes dependent on
  the registry list order — revisit AC2/AC11 then.
- **i18n target.** The new and relocated label keys land in `de.json` only — `de` is the project's
  i18n fallback locale (`i18n.ts` `FALLBACK_LOCALE = 'de'`) and `en.json` is a small partial
  override-only overlay; the existing generator labels are already `de.json`-only, so the new keys
  follow the same pattern. The scoring-rule / set-validation-rule registry keys (`setPoints`,
  `threePoint`, `twoPoint`, `standardVolleyball`, `timeBounded`) were verified against `staging` HEAD
  — do NOT trust the stale `ScoringRulesController` Javadoc example block, which lists
  `threePointMatch` / `twoPointMatch` / `timeBoundedSet` (strings the executable code never emits).
- The daemon may deliver concurrently; the next-available story ID and any ID-collision guard were
  verified against `staging` HEAD at authoring time (2026-05-16) — no `E58S06` artefact or backlog
  entry existed.
- Validation gates: `validate-artefacts` (format) and the Review Sub-Agent (independent review) run
  as isolated sub-agents before backlog registration.
