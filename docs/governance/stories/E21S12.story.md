# Story E21S12: `@ApplicationModule(allowedDependencies = {"tenant"})` on tournament + substantive bytecode boundary-spike

## User Story

**As a** reviewer of the Wave-2 Track-3 Modulith-compliance state,
**I want** the new `tournament` context declare its sole allowed dependency on `tenant` via `@ApplicationModule(allowedDependencies = {"tenant"})`, with `ApplicationModulesTest` verifying boundaries are **substantively** enforced via a bytecode-retained foreign-type reference (not just an unused import),
**so that** any future change attempting to import from `de.vvwt.tm.scoring.internal.*` (or any other non-allowed module) into `de.vvwt.tm.tournament.*` fails `ApplicationModules.verify()` at build time, and the E15 Pilot lesson (unused imports are discarded pre-bytecode — import-only spikes pass vacuously) is encoded as a test pattern from the start of Track-3.

---

## Context

Through E21S02–S11, the new `tournament` code lives at `de.vvwt.tm.tournament.*` (public API) + `de.vvwt.tm.tournament.internal.*` (implementation) with no Modulith annotation. Tournament currently compiles alongside legacy `de.vvwt.tm.domain.*` and legacy `de.vvwt.tm.infrastructure.web.*` under the default unannotated-package behaviour. This story makes the boundary real: `vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/package-info.java` declares `@ApplicationModule(allowedDependencies = {"tenant"})`, and `ApplicationModulesTest` (from E13S01) now verifies this annotation against the new tournament code.

Per Session Brief `discovery-2026-04-20-e21-full-refinement` **D-5**, tournament's final `allowedDependencies` list is exactly `{"tenant"}` — tournament persists data per-tenant via the Wave-1 routing DataSource and depends on nothing else. Six downstream contexts (`scoring`, `certificate`, `print`, `display`, `timer`, `slotopt-integration`) consume tournament's `::api` surface, but tournament does NOT consume them — the dependency is one-way by design.

Per DEC-21, this story continues the substantive-annotation pattern established in E15S06 (`auth` → `{"tenant"}`). Per Session Brief **C-14** + E15 retrospective §1 ("What Went Well — Modulith `ApplicationModules.verify()` enforced boundaries exactly as designed"), the critical lesson from the Pilot is: **the Java compiler discards unused imports before bytecode is emitted**, so a violation spike using only an unused `import` statement silently passes `verify()`. The spike MUST reference the foreign type in bytecode — via class literal (`X.class`), field type (`X field;`), or method parameter/return type (`void m(X arg)`) — so the reference survives compilation and Modulith's classpath analyzer detects it.

This story is NOT the atomic cutover — E21S13 deletes legacy. At S12 commit time, legacy `de.vvwt.tm.domain.*` and `de.vvwt.tm.infrastructure.web.*` still exist unannotated; S12's concern is ONLY the new tournament package getting its `@ApplicationModule` and the boundary-spike test encoding C-14's bytecode-retention lesson.

### C-14 — substantive bytecode-retained violation spike (the Pilot lesson encoded)

- [ ] AC-C14-BYTECODE-SPIKE-SUBSTANTIVE (testing — C-14 + E15 retrospective §1): A test class at `vvwt-tm-web/src/test/java/de/vvwt/tm/tournament/ApplicationModuleBoundaryEnforcementSpikeTest.java` (or equivalent path inside `de.vvwt.tm.tournament.*` test code) demonstrates that the `@ApplicationModule(allowedDependencies = {"tenant"})` annotation is substantively enforced. Protocol:
  1. The spike temporarily adds a **bytecode-retained** reference from tournament test code to a type in a non-allowed module — concrete candidate: `de.vvwt.tm.scoring.internal.ScoreEntryService` (still at legacy path `de.vvwt.tm.infrastructure.score.ScoreEntryService` until S13 — use whichever FQN exists on disk; the reference must target a type that is genuinely not in `tenant` and not in `tournament`).
  2. The reference MUST be in bytecode. Acceptable forms: class literal `ScoreEntryService.class`, field declaration `private ScoreEntryService svc;`, method parameter `void m(ScoreEntryService s) {}`, or method return type `ScoreEntryService r() { return null; }`. An `import` line alone is NOT acceptable — the Java compiler discards unused imports (E15 retrospective §1).
  3. With this reference in place, `ApplicationModules.of(TournamentManagerApplication.class).verify()` MUST fail with a dependency-violation error that names `tournament` → the non-allowed target.
  4. Once failure is observed, the spike reverts: the foreign-type reference is removed, the test returns to green. A short Javadoc block on the spike test class documents: (a) the exact FQN that was referenced, (b) the exact form of the bytecode reference used, (c) the verify-failure message observed, (d) the date of the verification run.
  5. The spike test may remain in the codebase as `@Disabled("Re-enable to re-verify Modulith bytecode-enforcement; see Javadoc")` to preserve the pattern for future boundary re-verifications without running in every build. Alternative: spike is fully reverted and the verification is recorded in the Delivery impl-report only. Either is acceptable; the Javadoc / impl-report record is mandatory.
- [ ] AC-SPIKE-JAVADOC-RETRO-LINK (governance): The spike test's Javadoc cites `E15-pilot-retrospective.md §1` and `Session Brief C-14` as the rationale for the bytecode-retention requirement. This is traceability for the next reviewer — the "why" of the test is not obvious from its code alone.

## Notes

**AC-C14-BYTECODE-SPIKE-SUBSTANTIVE is the single most important test of this story's value.** If the spike passes `verify()` with a foreign-type reference in bytecode, the whole Modulith setup is broken on tournament — just as E15S06's violation spike was the proof-of-enforcement moment for the Pilot. Do not shortcut. Delivery MUST observe the failure, record the failure message in the Javadoc / impl-report, and only then revert to green.

**Forbidden shortcut pattern:** writing the spike with only `import de.vvwt.tm.scoring.internal.ScoreEntryService;` at the top of the test class, observing it passes `verify()`, and concluding "the test works". This is exactly the E15 Pilot-lesson trap. The import is not in bytecode after `javac` strips it. The spike MUST exercise class-literal, field-type, method-parameter, or method-return bytecode retention.

**Cross-module naming note:** At S12 commit time, the violation-target type still lives at its legacy FQN (e.g., `de.vvwt.tm.infrastructure.score.ScoreEntryService`) because S13 has not yet rewritten. The spike uses whichever FQN exists on disk at execution time. After S13's cutover, a future re-enable of the spike test will use the post-rewrite FQN (`de.vvwt.tm.scoring.internal.ScoreEntryService` if scoring's own epic has placed it there). This evolution is acceptable — the spike is about enforcement mechanism, not a specific FQN.

**The annotation does NOT enforce anything against legacy `de.vvwt.tm.domain.*`:** the legacy package is unannotated; Modulith treats it as an implicit or default module and does not flag it as a dependency of tournament (tournament does not import from it after S02–S11). If a stray legacy import into the new tournament code surfaces from S12's verify, that is a bug in S02–S11 and must be escalated — not resolved silently in S12.
