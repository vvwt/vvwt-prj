# Story: Fix — PrintControllerIT intermittently fails to start its Spring/Flyway ApplicationContext

## User Story

**As a** GAAI operator relying on `mvn verify` as the delivery QA gate,
**I want** `PrintControllerIT` to start its integration-test context reliably,
**so that** `mvn verify` is deterministically green and a story is not failed by an
intermittent test-infrastructure failure unrelated to its change.

---

## Context

`PrintControllerIT` (`vvwt-tm-web`, `@SpringBootTest(RANDOM_PORT,
classes=TournamentManagerApplication.class)`, integration tests for `PrintController`)
intermittently fails to start its Spring/Flyway ApplicationContext, producing ~22
whole-class errors (the IT class errors at context-load rather than running its tests).
The failure is documented across multiple stories' qa-reports (E24S02, E51S16, E51S17,
E53S03, E53S05) — E53S03's qa-report calls it "confirmed pre-existing on staging baseline."

Under DEC-71 a non-zero `mvn verify` is an unconditional QA FAIL with no "pre-existing"
carve-out — so while this failure persists it can fail any story's QA (it contributed to
E59S02 being marked `failed`). This bug-triage story makes the IT context-start reliable.

---

## Root Cause Analysis

Investigation so far: `PrintControllerIT` boots the full `TournamentManagerApplication`
context (per DEC-44's web-module IT model). The failure is an intermittent
ApplicationContext **startup** failure (~22 errors — the whole IT class fails to load its
context), not an assertion failure. It is intermittent — the E59S02 delivery log records a
second `mvn verify` run not reproducing the failure set. It recurs across the qa-reports
listed in Context. It is the same test-infrastructure family as E16S02 (shared in-memory
test DB + per-tenant Flyway producing ordering-dependent flakiness) and E16S03 (per-tenant
test-DB isolation) — both `done` — so it is plausibly a residual instance the E16S02 /
E16S03 fixes did not cover, or a distinct race in the same Flyway / context-startup area.
The exact race and the precise fix are for Delivery to confirm — Discovery deliberately
does not pre-compute the mechanism or copy the ~22 error FQNs.

## Acceptance Criteria

- [ ] AC1 (testing): Delivery first reproduces the failure — Given the `vvwt-tm-web` test
  suite is run, When `PrintControllerIT`'s ApplicationContext starts, Then the intermittent
  startup failure is observed. If it cannot be reproduced in the delivery environment after
  a documented diagnostic effort (intermittent failures need not reproduce on demand),
  Delivery records that and proceeds on the qa-report evidence cited in Context. The
  reproduction approach and result are recorded in the impl-report.
- [ ] AC2 (governance): expected behaviour after the fix — `PrintControllerIT`'s
  Spring/Flyway ApplicationContext starts reliably; the IT runs its tests instead of
  erroring at context-load; the intermittent startup failure no longer occurs.
- [ ] AC3 (testing): because the failure is intermittent, a single green run is
  insufficient evidence — Delivery verifies the fix by repeated runs (the IT's context
  starts cleanly across multiple consecutive IT / `mvn verify` executions) and records the
  verification in the impl-report.
- [ ] AC4 (governance): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS (DEC-54 /
  DEC-71) — `PrintControllerIT` no longer contributes a non-zero `mvn verify` exit.
- [ ] AC5 (governance): the fix is confined to test infrastructure / IT setup —
  `PrintController` production behaviour is unchanged, and once its context starts
  `PrintControllerIT`'s existing assertions still hold (the IT's coverage is not weakened,
  disabled, or deleted to make the build pass).
- [ ] AC6 (testing): no other integration test regresses — the rest of the `vvwt-tm-web`
  IT suite stays green under `mvn verify`.

> All acceptance criteria must be verifiable.

qa-reports E24S02 / E51S16 / E51S17 / E53S03 / E53S05. The fix targets test infrastructure

authors no first-party production code. Per memory

repeated-run verification — AC3 carries that. Per DEC-13, delivered on `staging`; AI never
pushes to `vvwt-prj/main`. Discovery defines the expected behaviour (a reliably-starting
context); the precise Flyway / context-startup fix is Delivery's.
