# Story E21S21: Fix Vorschau/Apply 400 — Frontend sends body for `previewDraft` + `applyDraft`; remove `handlePreview` auto-save workaround; load `participatingTeamCount` from `Tournament.getTeamCount()`

## User Story

**As a** tournament organizer using the Tournament Manager Admin SPA,
**I want** the "Vorschau" button on the Draft configuration page to display a meaningful preview reflecting my current draft sections and the planned team count, without auto-persisting my edits,
**so that** I can iterate on the draft configuration (try out section changes, see the resulting match math) and explicitly Save only when I am satisfied — restoring the legacy "create → preview → save-when-good" UX.

---

## Context

User-reported defect 2026-05-05: clicking "Vorschau" on `/tournaments/{id}/draft` returns HTTP 400. Discovery investigation surfaced **three causally-related defects** that are fixed atomically in this Story:

### Bug 1a — Frontend posts no body, backend requires `@RequestBody @Valid`

`draftStore.ts:123-126` and `:144-147` POST to `/api/tournaments/${id}/draft/preview` and `/draft/apply` with `method: 'POST'` only — no `Content-Type` header, no JSON body. Backend `DraftController.previewDraft` and `applyDraft` (DraftController.java:155-157, 181-183) declare `@RequestBody @Valid DraftRequest request`, where `DraftRequest` has `@NotNull @Valid List<DraftSectionRequest> sections` (DraftRequest.java:17). Spring rejects the empty body via `HttpMessageNotReadableException` → 400 (DraftController.java:59 Javadoc).

**Provenance**: frontend authored no-body at cb4c3b1 (E08S05, 2026-04-15), valid at the time against the legacy `de.vvwt.tm.infrastructure.web.DraftController` (no `@RequestBody`). The body-required contract became live at the frontend's URL at the E21S13 atomic cutover (8a4ce11, 2026-04-21). Defect surfaced at E21S13; latent ~14 days.

### Bug 1c — `handlePreview` auto-saves before previewing (UX-incorrect; was Bug-1a workaround)

`DraftConfig.svelte:223` calls `await saveDraft(tournamentId, { sections })` before `previewDraft(tournamentId)`. The line-221 source comment documents the workaround intent verbatim: `// Save first so server has the latest config`. Path A obsoletes the workaround AND restores the user's recalled UX intent ("create draft → view preview → save only if acceptable"). A separate Save-Button at line 398 (`handleSave` at lines 201-212) provides the explicit save UX, so removing the auto-save does not strand the user.

### Bug 1b — `participatingTeamCount=0` hardcoded in `previewDraft`

`DraftController.previewDraft:160-162` calls `draftService.preview(config, 0)` with hardcoded zero. TODO comment on the same line acknowledges the defect: `// participatingTeamCount=0 during preview — section math uses provided groupCount; (future: load from tournament repository; for now DraftService computes with 0)`. `DefaultDraftService.computePreview:331-356` consumes the count to compute `teamsPerGroup`, `matchesPerGroup`, `totalLaps`, `totalMatches`, `estimatedTimeMinutes`. With count=0, all values collapse to 0 — preview is functionally meaningless.

**Source**: `Tournament.getTeamCount()` (Tournament.java:325-327, planned-participating count from tournament setup) — NOT `Team::isParticipate` filter (which `apply` uses). Rationale (user direction 2026-05-05): there can be more `Team` rows than participating teams (e.g., external referees marked `isParticipate=false`); the planned `Tournament.teamCount` is the correct source for preview math.

## Reproduction Scenarios (Given / When / Then)

### Bug 1a — Vorschau-Button → 400

```
GIVEN a tournament in DRAFT status with id 02376d90-f8bf-424c-881e-5468e9d3b938
  AND a saved or in-memory draft with at least one section
 WHEN the user clicks the "Vorschau" button in the Draft configuration page
 THEN today: the network request POST /api/tournaments/{id}/draft/preview is sent
       without body and without Content-Type header
   AND the backend responds 400 Bad Request (HttpMessageNotReadableException)
   AND the UI shows previewError without a usable preview
 EXPECTED post-fix: the network request includes Content-Type: application/json
       and JSON body { sections: [...] }
   AND the backend responds 200 OK with DraftPreviewResponse
   AND the UI renders the preview table with non-zero math (cf. Bug 1b)
```

### Bug 1c — handlePreview unintentionally persists edits

```
GIVEN a tournament in DRAFT status with persisted sections P
  AND the user has unsaved local edits L (L != P)
 WHEN the user clicks "Vorschau"
 THEN today: handlePreview calls saveDraft({ sections: L }) which OVERWRITES P
       with L on the server, then calls previewDraft (which returns 400 today)
   AND if the user then closes the page without explicit Save, the persisted
       state is L (not P) — UX-incorrect per user's recalled intent
 EXPECTED post-fix: handlePreview does NOT call saveDraft; only calls
       previewDraft({ sections: L }) which returns the preview based on L;
       persisted state remains P until the user explicitly clicks Save
```

### Bug 1b — Vorschau math is meaningless with 0 teams

```
GIVEN a tournament with Tournament.teamCount = 8 and groupCount = 4
  AND a saved draft with one section (sortType=team_number, groupCount=4)
 WHEN the user clicks "Vorschau" (hypothetically with Bug 1a fixed)
 THEN today: backend calls draftService.preview(config, 0)
   AND DraftPreviewSection returns teamsPerGroup=0, matchesPerGroup=0,
       totalLaps=0, totalMatches=0, estimatedTimeMinutes ≈ break-time-sums
   AND the UI shows a structurally empty preview
 EXPECTED post-fix: backend loads Tournament.getTeamCount() = 8 and calls
       draftService.preview(config, 8)
   AND DraftPreviewSection returns teamsPerGroup=2, matchesPerGroup=1,
       totalLaps=1, totalMatches=4, estimatedTimeMinutes computed correctly
   AND the UI shows a meaningful preview
```

### Anti-fooling: getTeamCount, NOT Team::isParticipate filter

```
GIVEN a tournament with Tournament.teamCount = 4
  AND in the team table for this tournament:
       4 Team rows with isParticipate = true
       2 Team rows with isParticipate = false (external referees)
 WHEN the preview is computed
 THEN the participatingTeamCount source is Tournament.getTeamCount() = 4
       (NOT teamRepository.findByTournamentId(...).filter(isParticipate).count() = 4
        — this happens to coincide here, so the test fixture must be
        constructed to disambiguate)
 ANTI-FOOLING FIXTURE: Tournament.teamCount = 8, but only 6 Team rows with
       isParticipate=true exist (e.g., user planned 8 but has only entered 6
       so far). Expected: preview uses 8, NOT 6. This rules out the wrong
       source.
```

### Implementation choice for backend count load

Per Brief O-15, two viable implementations:
- **(i) Service signature refactor** — add overload `preview(UUID tournamentId, DraftConfig config)` to `DraftService` interface; `DefaultDraftService` impl loads tournament internally. Ripple: 1 interface + 1 impl + 1 controller + 3 test callers = 6 files.
- **(ii) Controller-side count load** [CHOSEN per AC-IMPL-BE-CONTROLLER-LOAD-TEAMCOUNT] — `DraftController` injects `TournamentRepository`, loads tournament, calls `getTeamCount()`, passes via existing `draftService.preview(config, count)` signature. Ripple: 1 controller + 1 new dependency = 2 production files. Service stays pure-compute. Smaller blast radius, easier IT.

Delivery may consult the Story author if (i) is preferred for symmetry with `apply`'s tournament-loading pattern, but (ii) is the steered choice. The AC explicitly forbids the `Team::isParticipate` filter pattern regardless of (i)/(ii).
