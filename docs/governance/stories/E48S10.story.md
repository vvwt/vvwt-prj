# Story E48S10: Field-Count-Aware Lap Formula in computePreview

## User Story

**As a** Tournament Organizer,
**I want** the Phasenplan-Vorschau to display the realistic number of "Runden" based on my tournament's available number of fields,
**so that** the estimated tournament duration reflects actual scheduling constraints and I can plan logistics accurately.

---

## Context

Per Brief D-5 / O-6 / O-7 / O-8 (`discovery-2026-05-06-phasenplan-preview-fixes`): `DefaultDraftService.computePreview` (`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/DefaultDraftService.java:334-359`) currently computes `totalLaps = teamsPerGroup - 1` (per-group RR rounds) — ignoring the tournament's `field_count` column. User defines a "Runde" as a time-slot where each team plays at most 1 match, bounded by available fields. Concrete: for 30 matches on 3 fields → 10 rounds expected; current formula returns 5 (= teamsPerGroup-1 for 6-team groups).

`tournaments.field_count INT NOT NULL DEFAULT 1` already exists since V1 (`vvwt-tm-web/src/main/resources/db/migration/tournament/V1__initial_schema.sql:70`); the input is wired in `TournamentForm.svelte:43,210`; the value is loaded via existing `TournamentRepository`. The fix threads `tournament.fieldCount` from `DraftController` through `DraftService.preview()` (pattern parallels E21S21 AC-IMPL-BE-CONTROLLER-LOAD-TEAMCOUNT) and replaces the lap formula with a field-aware + team-conflict-aware variant.

Per Brief T-6: preview is intentionally a **lower-bound for laps** (upper-bound for time) — the real slot-optimizer may achieve fewer laps via smarter scheduling; preview's role is conservative planning, not exact scheduler simulation. `tm.slotopt.fallback.field-count` (Spring property) and `FallbackSlotOptimizationClient` are SEPARATE concerns and remain unchanged (Brief S-4).

- [ ] **AC-IMPL-COMPUTE-PREVIEW-FIELD-AWARE-FORMULA**: `computePreview` computes:
  ```
  teamConflictPerLap = floor(teamsPerGroup / 2) * groupCount
  effectivePerLap    = max(1, min(teamConflictPerLap, fieldCount))
  totalLaps          = totalMatches == 0 ? 0 : ceil(totalMatches / effectivePerLap)
  ```
  Edge cases: totalMatches=0 → totalLaps=0 (no compute); fieldCount ≤ 0 → clamped to 1 by `max(1, ...)`.
  **Source mapping for inputs (Reviewer F-B clarification):** `teamsPerGroup` = `participatingTeamCount / section.getGroupCount()` (existing line 336 of `DefaultDraftService.java`); `groupCount` = `section.getGroupCount()` (existing line 335); `totalMatches` = `groupCount * matchesPerGroup` (existing line 339); `fieldCount` = NEW parameter to `computePreview(DraftSection, int teamCount, int fieldCount)` — Delivery extends the per-section helper signature alongside the public `preview(...)` signature change. NO re-derivation from `DraftConfig.phases().size()` or any other source.

  - **Sufficiency:** `totalLaps * effectivePerLap >= totalMatches` for all generated inputs
  - **Tightness:** `(totalLaps - 1) * effectivePerLap < totalMatches` whenever `totalLaps > 0`
  - **Definition:** `effectivePerLap = max(1, min(floor(teamsPerGroup/2) * groupCount, fieldCount))`
  - Generators: `teamsPerGroup ∈ [1, 24]`, `groupCount ∈ [1, 8]`, `fieldCount ∈ [1, 20]` (Q-jqwik default ≥ 100 trials).
