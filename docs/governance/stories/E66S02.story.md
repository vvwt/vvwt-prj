# Story: The phase-transition page lets the operator change the team-sort and the group-distribution

## User Story

**As a** tournament organizer,
**I want** to change the team-sort and the group-distribution directly on the phase-transition page,
**so that** I can correct a setting I entered wrongly in the phase plan and immediately see the corrected assignment proposal.

---

## Context

The phase-transition ("Phasenwechsel" / Mannschaftsübernahme) page is today entirely
read-only with respect to how teams are sorted and distributed — both values come from the
tournament's `draft_json` and the only way to change them after the plan has been applied
is the destructive `resetPlan` (the draft is otherwise locked once the tournament leaves
`DRAFT` status — `DraftService.saveDraft` rejects a non-`DRAFT` tournament). The operator
needs to correct a `sortType` / `distributionMode` value that was wrong at plan creation,
at the moment the assignment matters.

DEC-77 D-5 makes the phase-transition page a deliberate, narrowly-scoped post-apply edit
surface for exactly these two fields. This story adds the controls; E66S01 (the decoupled
`computeProposals`) is the engine they drive. This is the first code path that writes a
`DraftSection` after apply — so its write target and its non-disruption of the rest of the
tournament are pinned by behavioural acceptance criteria below, not assumed.

---

## Acceptance Criteria

- [ ] AC1 (testing): TDD per DEC-22 — a failing test is authored before the production
  change, proven RED, then GREEN.
- [ ] AC2: the phase-transition page shows two operator controls — a team-sort selector
  and a group-distribution selector — each offering the registered keys (the three sort
  keys, the two distribution keys). For an initial (no-predecessor) transition the sort
  selector is fixed at `team_number` and not changeable; the distribution selector is
  always active.
- [ ] AC3: changing either control re-computes and re-displays the assignment proposal —
  both the "Bisherige Zuordnung" pane and the "Neue Zuordnung" grid reflect the new value.
- [ ] AC4: the chosen `sortType` / `distributionMode` persist into the `DraftSection` of
  **the phase currently being transitioned** — the target phase, which is in `PREPARED`
  with teams not yet assigned — and into no other section. After a page reload the page
  shows the operator's chosen values, not the original phase-plan values.
- [ ] AC5 (governance): an unknown / unregistered `sortType` or `distributionMode` value
  is rejected at the moment of the persist, before any proposal recompute — the registered
  strategy keys are the only accepted values. The check fires on this post-apply write
  path itself (this path does not pass through `DraftService.saveDraft`, where the
  DEC-73 D-6 membership check normally fires); it is the same membership rule applied at
  this new write site.
- [ ] AC6 (testing): the persist is invalidation-neutral, verified behaviourally — given
  matches have already been generated for the target `PREPARED` phase, when the operator
  changes `sortType` or `distributionMode`, then the target phase's generated matches are
  unchanged, the target phase's status stays `PREPARED`, and no other phase's status or
  data changes. Only the target phase's team-assignment proposal is re-computed. `teamId`
  is still written into avatars only by the operator-confirmation ("Übernehmen") handler
  (DEC-59 Clause C) — the sort/distribution edit writes no `teamId`.
- [ ] AC7: the sort / distribution controls are offered only while the transition has not
  yet been committed (the target phase is `PREPARED` and teams are not yet assigned); once
  the assignment is committed (`ASSIGNED`) they are not editable.
- [ ] AC8 (governance): the frontend stays Vite + Svelte + TypeScript, no SvelteKit
  (DEC-2); every operator-facing string the controls introduce resolves through `de.json`
  via the project's canonical fallback-aware i18n pattern (`$_(key, { default })`); no
  `teamId` UUID is rendered in the DOM (DEC-9). `mvn verify` is BUILD SUCCESS for
  `vvwt-tm-web`, including the frontend build (DEC-54).

> All acceptance criteria must be verifiable.

---

## Out of Scope

- The decoupled `computeProposals` engine itself — delivered by E66S01.
- Showing the points / sets / balls ranking basis in the left pane — that is E66S03.
- Editing any other part of the phase plan / draft after apply — only `sortType` and
  `distributionMode` of the phase being transitioned are made editable (DEC-77 D-5).
- Re-sorting or re-assigning a phase after its assignment is committed (`ASSIGNED`).

---

## Dependencies

- **E66S01** — the decoupled, unified `computeProposals` the controls drive. Hard
  prerequisite.
- DEC-77 D-5 — the governing decision for the editable post-apply surface.
- DEC-59 — `DraftSection.distributionMode` is the source of truth for the assignment
  shape; the persist writes that source of truth; `teamId` is written only at operator
  confirmation.
- DEC-73 D-6 — the registry-membership check whose rule AC5 applies at the new write site.

---

## Notes

Delivery decides where the recompute-on-change is triggered and how the persist reaches the
target phase's `DraftSection` (the proposal endpoint already resolves the `DraftSection`);
the ACs state the behaviour. The invalidation-neutrality (AC6) is structurally plausible
because `sortType` / `distributionMode` feed only the team→avatar-slot proposal — generated
matches reference avatar slots, not teams (DEC-9 / DEC-56) — but AC6 makes it an observed
before/after invariant, not an assumption.
