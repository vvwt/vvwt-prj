# Story: Fix — certificate generation falsely reports "no game results" for a completed tournament; placement must come from the Siegerehrung phase's TeamAvatar group positions

## User Story

**As a** tournament organizer whose tournament is fully completed — all phases played,
including the final Siegerehrung (award-ceremony) phase,
**I want** certificate generation to produce my teams' Urkunden with each team's correct
final placement,
**so that** I can print and hand out the certificates instead of being blocked by a false
"no game results" error.

---

## Context

A fully completed tournament (31. Frühjahrsturnier, `ad21bf32-7ef8-40e8-9e78-81b3ba9f7872`
— status Abgeschlossen; Phase 1 round-robin 30/30, Phase 2 round-robin 18/18, Phase 3
Siegerehrung 0/0) cannot produce certificates: `GET /certificate/tournaments/{tid}/print`
returns HTTP 400 "Es sind keine Spielergebnisse vorhanden. Bitte spielen Sie zuerst die
Spiele." — even though every game has been played.

The certificate placement is computed from the wrong source. The final placement for each
team is recorded on the Siegerehrung phase's TeamAvatars as their **group position**, but
the certificate code computes placement from match ratings — and the Siegerehrung phase has
no matches.

Domain facts confirmed by the operator (2026-05-17):
- Each team's final placement is the `groupPosition` of its TeamAvatar in the Siegerehrung
  (award-ceremony) phase.
- The Siegerehrung phase has a **single group** — `groupPosition` 1..N corresponds directly
  to places 1..N.
- Every tournament ends with a Siegerehrung phase — so the final phase is always the
  award-ceremony phase, and the certificate placement always comes from its avatar group
  positions.

This is a separate defect from the no-uploaded-template gate (Epic E67). Generating
certificates for this tournament end-to-end needs both fixed; they are technically
independent.

---

## Root Cause Analysis

Investigation (Discovery, 2026-05-17) — verified in the codebase:

1. `DefaultCertificateAssembler.getFinalPhase(tid)` returns the phase with the highest
   `sequenceNumber` — for this tournament, Phase 3, the Siegerehrung phase. **This is
   correct** (the operator confirmed the placement lives on the Siegerehrung phase) and is
   NOT part of the fix.
2. `DefaultCertificateAssembler.computePlacementOrder(tid, finalPhase)` loads that phase's
   `TeamAvatar`s, then ranks them by `TeamAvatarRating`. `TeamAvatarRating` is derived from
   **played matches**.
3. The Siegerehrung phase has `gameMode = "awardCeremony"` and is served by
   `AwardCeremonyMatchGenerator`, which generates **zero matches** by design. No matches →
   no `TeamAvatarRating` rows → `computePlacementOrder` hits its "no ratings" branch and
   returns `Collections.emptyList()`.
4. `CertificateRenderController` then takes its `placements.isEmpty()` branch and returns
   the false HTTP 400 "Es sind keine Spielergebnisse vorhanden".
5. The correct placement is already present: each team's final placement is the
   `groupPosition` of its TeamAvatar in the Siegerehrung phase (the DEC-9 structural
   identity `(groupNumber, groupPosition)`; single group → `groupPosition` = place).
   `computePlacementOrder` simply reads ratings instead of the avatar group positions.
6. `computePlacementOrder` and `getFinalPhase` are used only by
   `CertificateRenderController` (verified) — the fix's blast radius is the certificate
   render path.

## Acceptance Criteria

- [ ] **AC1 [reproduction]:** Given a completed tournament whose final phase is a
  Siegerehrung (`gameMode = "awardCeremony"`) phase whose `TeamAvatar`s have assigned teams
  and group positions, when the certificate placement is computed for that tournament
  (`CertificateAssembler.computePlacementOrder` for the tournament's final phase), then —
  against the pre-fix code — the result is an empty placement list, and consequently
  `GET /certificate/tournaments/{tid}/print` and `/print/{teamId}` return HTTP 400 "Es sind
  keine Spielergebnisse vorhanden". This is the RED reproduction (DEC-22).
- [ ] **AC2 [expected behavior]:** After the fix, the certificate placement for such a
  tournament is derived from the Siegerehrung phase's `TeamAvatar` group positions — each
  team's placement equals the `groupPosition` of its `TeamAvatar` in the Siegerehrung phase
  (single group: `groupPosition` 1..N → places 1..N). `computePlacementOrder` returns a
  non-empty, correctly-ordered placement list, and the render endpoints return HTTP 200 and
  render the certificates.
- [ ] **AC3 [expected behavior]:** In the all-teams certificate (`/print`), teams appear in
  ascending placement order (place 1, 2, 3, …) matching their Siegerehrung-phase
  `groupPosition`. The single-team certificate (`/print/{teamId}`) renders that team's
  certificate showing its Siegerehrung-phase placement.
- [ ] **AC4 [error-handling]:** The HTTP 400 "Es sind keine Spielergebnisse vorhanden" is
  preserved for the genuine not-ready case — a tournament whose final phase carries no
  placement data (no `TeamAvatar`s with an assigned team). The fix removes the false 400
  for completed tournaments; it does not remove the legitimate error for a tournament that
  has not been carried to a placement-bearing state. The existing `finalPhaseOpt.isEmpty()`
  guard (no phases at all) is likewise preserved.
- [ ] **AC5 [regression]:** Only the placement *source* changes. The certificate render
  output is otherwise unchanged — the SVG-vs-HTML branch selection, the all-teams ZIP
  packaging for SVG templates, single-vs-batch handling, and the certificate model
  variables are unaffected.
- [ ] **AC6 [testing]:** The fix is authored RED-first per DEC-22 — a test that reproduces
  the empty-placement / false-400 for a Siegerehrung-final-phase tournament fails against
  the pre-fix code and passes after the fix. The RED→GREEN cadence is recorded in the
  impl-report.
- [ ] **AC7 [testing]:** `mvn verify` for `vvwt-tm-web` is BUILD SUCCESS after the fix
  (DEC-54) — no regression in the certificate or tournament test suites.
- [ ] **AC8 [i18n]:** The rendered certificate continues to present its labels and content
  via the existing i18n mechanism (`tom_label_*` resolved via `MessageSource`,
  locale-resolved date). The fix introduces no hardcoded display strings and changes no
  certificate i18n behavior.
- [ ] **AC9 [security]:** The fix introduces no change to the `/certificate/**`
  authentication/authorization surface — no new endpoint, no `SecurityConfig` change. The
  certificate endpoints remain authenticated-only as today.
- [ ] **AC10 [governance]:** No new DEC is created. The fix is confined to the certificate
  module's placement computation (`DefaultCertificateAssembler.computePlacementOrder`,
  behind the `CertificateAssembler` public interface — DEC-35); `getFinalPhase` is correct
  and unchanged. If the rating-based code path or the `TeamAvatarRating` collaborator (a
  Repository read) becomes unused as a result, that orphan is removed in the same change
  per DEC-69 / DEC-70 (no test-only or orphan production code). `related_decs` cites the
  constraining DECs.

> All acceptance criteria must be verifiable. Vague criteria are invalid.
