# Story E31S02: Scoring Modulith module bootstrap — package-info + @ApplicationModule + bytecode-substantive boundary spike

## User Story

**As a** maintainer of the post-E31 Modulith module graph,
**I want** the `de.vvwt.tm.scoring` package declared as a Spring
Modulith module via a `package-info.java` carrying
`@ApplicationModule(allowedDependencies = {"tenant", "tournament"})`,
with a bytecode-substantive boundary-violation spike test that proves
`ApplicationModules.verify()` enforces the declared boundary in
production bytecode (not merely via unused imports),
**so that** E31S03 can author the `ScoringService` interface (no
`I`-prefix per DEC-35 naming canon) and `DefaultScoringService`
implementation inside a properly-declared
Modulith module from the first commit, and so that any future
import from a non-allowed module into `de.vvwt.tm.scoring.*` fails
build-time `verify()`.

---

## Context

Per Brief D-π and D-α, the scoring Modulith module must exist before
E31S03 can author functional code inside it. Per Brief D-ρ,
`de.vvwt.tm.domain` REMAINS undeclared (no package-info.java) — only
the new `de.vvwt.tm.scoring` package is declared in this story.

The bytecode-spike test is mandated by the Wave-1 E15 Pilot lesson
(retrospective §1) and by the E21S12 confirmation: the Java compiler
discards unused imports before bytecode is emitted, so a violation
spike using only an unused `import` statement silently passes
`verify()` vacuously. The spike MUST reference the foreign type in
bytecode — via class literal (`X.class`), field type (`X field;`), or
method parameter/return type (`void m(X arg)`). E21S12 codified this
pattern; E31S02 inherits it.

The scoring module is EMPTY of functional code at this story's commit
time. The `package-info.java` declaration is the only production code.
The bytecode-spike is in test code. The story is essentially a
governance act: making the boundary real before functional code
arrives in E31S03.

## Acceptance Criteria

### Module declaration

- [ ] AC-PKGINFO-EXISTS (governance — DEC-21 § Module layout):
  `vvwt-tm-web/src/main/java/de/vvwt/tm/scoring/package-info.java`
  exists and contains exactly
  `@ApplicationModule(allowedDependencies = {"tenant", "tournament"})`
  with the appropriate import (`org.springframework.modulith.ApplicationModule`)
  or fully-qualified annotation reference. No additional
  `allowedDependencies` entries (no `certificate`, `print`, `display`,
  `timer`, `slotopt-integration`, no `auth`).
- [ ] AC-NO-INTERNAL-ANNOTATION (governance):
  `vvwt-tm-web/src/main/java/de/vvwt/tm/scoring/internal/` (if it
  exists at this story's commit time as an empty directory or with
  placeholder files) does NOT receive its own `@ApplicationModule`
  annotation. Internal is a sub-package of the annotated root and
  inherits module membership per Modulith conventions.
- [ ] AC-EMPTY-FUNCTIONAL-CODE (governance — Brief D-π S-5):
  At this story's commit time, `vvwt-tm-web/src/main/java/de/vvwt/tm/scoring/`
  contains EXACTLY ONE file: `package-info.java`. The
  `de.vvwt.tm.scoring.internal/` sub-package is NOT created in S02
  (Java does not track empty directories; no `.gitkeep` placeholder
  files are introduced). The internal sub-package directory comes
  into existence in E31S03 when the first internal class
  (`DefaultScoringService.java`) is added. Test sources at
  `vvwt-tm-web/src/test/java/de/vvwt/tm/scoring/internal/` may
  contain the spike test class (per AC-SPIKE-TEST-CLASS) — test
  source tree is independent of production source tree per Java
  conventions.

### Modulith verify

- [ ] AC-MODULITH-VERIFY-GREEN (testing):
  `ApplicationModules.of(TournamentManagerApplication.class).verify()`
  passes with `de.vvwt.tm.scoring` declared as a module.
  `ApplicationModulesTest` (E13S01 / E21S12) remains green
  post-annotation. Tournament's `@ApplicationModule(allowedDependencies = {"tenant"})`
  is unaffected. Legacy `de.vvwt.tm.domain.*` and other undeclared
  packages continue to coexist as before (they are treated as
  application-root support per Modulith conventions; no false-positive
  cross-module violations are introduced by adding the scoring
  declaration).

### Bytecode-substantive boundary spike (the Pilot lesson encoded)

- [ ] AC-SPIKE-TEST-CLASS (testing — DEC-21 § C-14 Pilot lesson via
  E15S06 / E21S12 inheritance): A new test class
  `vvwt-tm-web/src/test/java/de/vvwt/tm/scoring/internal/ScoringBoundarySpikeTest.java`
  (or equivalent path) exists. The test class contains a method (or
  multiple methods) that intentionally REFERENCES a foreign type from
  a DISALLOWED module — for example, a class literal
  `de.vvwt.tm.tournament.internal.AuditLogEntry.class` or a field
  type declaration. The reference MUST survive Java's import-discard
  optimization — bytecode-retained via class literal, field type, or
  parameter/return type.
- [ ] AC-SPIKE-VERIFY-FAILS (testing — DEC-21 § C-14): When the
  spike file is uncommented (a normally-commented-out section
  containing the boundary violation), `ApplicationModules.verify()`
  must FAIL with a violation pointing at the spike file's foreign-
  type reference. This proves boundary enforcement is substantive,
  not vacuous. The spike file lives commented-out in the codebase
  with documentation (Javadoc at the top of the test class)
  explaining the C-14 lesson and how to manually verify the spike
  by uncommenting + running `mvn verify`.
- [ ] AC-SPIKE-VERIFY-EVIDENCE-IN-IMPL-REPORT (testing —
  governance): The story's impl-report MUST include a verbatim
  excerpt (≥10 lines) of the `mvn verify` failure output produced
  during the manual uncomment-then-run procedure. The excerpt
  demonstrates that `ApplicationModules.verify()` actually caught
  the violation and named the spike file's foreign-type reference.
  Without this evidence, AC-SPIKE-VERIFY-FAILS is unverified — a
  trust-me-governance anti-pattern. The procedure: (1) uncomment
  the violating block in the spike test, (2) run `mvn verify`,
  (3) capture the failure stack trace excerpt, (4) re-comment the
  block, (5) verify `mvn verify` is GREEN again, (6) paste the
  captured excerpt + the re-comment commit SHA into the
  impl-report.

### Regression gate

- [ ] AC-REGRESSION-GREEN (testing — error-handling): All pre-E31S02
  tests remain GREEN. `mvn verify` is green. No production code
  outside `package-info.java` is introduced by this story.
