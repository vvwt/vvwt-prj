# Story: Scoring-tablet match API — persist in-progress set scores and report the true set index, true current points, and tiebreak status

## User Story

**As a** referee scoring a match on the tablet,
**I want** the field page to know the true current set, the true current points (surviving a
reload), and whether the set is a tiebreak,
**so that** the header shows the correct set, the score is not lost when the page reloads, and
the tiebreak side-switch can be triggered.

---

## Context

This is the backend story of Epic E61. The scoring-tablet match API
(`GET /api/score/match`, returning the `de.vvwt.tm.scoring.ScoreEntryResult` DTO, resolved by
`DefaultScoreEntryService.resolveActiveMatch`) today reports a constant set index of 0 and
constant 0:0 points for every freshly loaded match, and exposes no tiebreak signal. In-progress
(partial) set scores are not persisted — `POST /api/score/partial` is fire-and-forget, so a
page reload (which happens after every submit) loses the live score.

Per the Discovery session of 2026-05-16 (user decision: persist in-progress scores
server-side), this story makes the match API report true match state: the current set, the
current points, and whether the open set is a tiebreak. This is required by the E61 header
(E61S01) and the team-position swap (E61S03).

---

## Acceptance Criteria

- [ ] AC1 (persistence): in-progress (partial) set scores submitted via the scoring-tablet
  partial-score endpoint are persisted, so the current points of the open set survive both a
  server restart and a tablet page reload.
- [ ] AC2 (API — set index): the scoring-tablet match API reports the true index of the current
  open set of the active match (the count of already-completed sets), not a constant 0.
- [ ] AC3 (API — points): the scoring-tablet match API reports the true current points of both
  teams in the open set, read from the persisted in-progress score, not a constant 0:0.
- [ ] AC4 (API — tiebreak): the scoring-tablet match API reports whether the current open set is
  a tiebreak — the deciding final set of a best-of-N match, reached because the teams are level
  on sets. For a match format with no deciding-set concept, this is reported as not-a-tiebreak.
- [ ] AC5 (error-handling): when no active match exists on the field, the API continues to
  return the existing no-match response unchanged.
- [ ] AC6 (governance — placement): the response remains a `de.vvwt.tm.scoring` public DTO and
  the REST controller remains in `de.vvwt.tm.web` (DEC-40); the API change is additive — every
  field the current tablet page already consumes is preserved with its current name and
  meaning.
- [ ] AC7 (governance — tenancy): persisting and reading the in-progress score, and resolving
  the set and match-format data, remain scoped to the device-token-resolved tenant context
  (DEC-20).
- [ ] AC8 (testing): the new behaviour is specified by failing-first tests per DEC-22 —
  covering (a) a multi-set match in progress: a set index greater than 0 and non-zero current
  points are reported and survive a simulated page reload; (b) a set that is a tiebreak versus
  one that is not.
- [ ] AC9 (governance): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS (DEC-54,
  DEC-71).

> All acceptance criteria must be verifiable.

## Notes

Persisting in-progress scores is an additive schema change; per DEC-25 (no production data) it
is applied within the Wave-2 reset posture — the schema design is Delivery's. The tiebreak
determination is computable from the match format (`Tournament` match-format value /
`MatchFormat`) plus the completed-set counts — `MatchFormat` already carries deciding-set and
tiebreak helpers. `resolveActiveMatch` reads `Phase.currentLapNumber`; DEC-65 governs that
field's semantics and lists this read site — the change must preserve DEC-65-correct
consumption. Per Brief D-9, E61S02 and E22S13 both touch `resolveActiveMatch`; this story's
`depends_on: [E22S13]` prevents a concurrent-delivery merge conflict. `mvn verify` is the build
gate per DEC-54 / DEC-71.
