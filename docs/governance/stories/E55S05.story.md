# Story E55S05: Cooperative cancel mechanism + DEC-49 D-11a Best-So-Far invariant preservation (M-4 IT)

## User Story

**As a** Tournament Operator,
**I want** the existing `POST /api/slotopt/tournaments/{tid}/cancel` endpoint to continue working under the new Saga-Orchestrator architecture — when I cancel an in-flight slot-opt job, the Best-So-Far permutation rank found so far MUST be applied to the matches, `phase.optimized` MUST be set to TRUE, and the job's status MUST advance to COMPLETED (not FAILED, not CANCELLED in a failure sense),
**so that** the operator-feel "work-not-lost" guaranteed by DEC-49 D-11a survives the architecture refactor — this is a pre-existing behavior that DEC-64 D-16 mandates as a hard regression-protected invariant.

---

## Context

DEC-49 D-11a codified Best-So-Far semantics on cancel (2026-04-28). DEC-64 D-16 re-affirms this as a hard regression-protected invariant for the refactor:

> When the operator cancels an in-flight slot-opt job:
> (a) the Best-So-Far permutation rank found BEFORE the cancel observation point MUST be applied to the phase's matches via SlotResultApplicator;
> (b) `phase.optimized` MUST be set to TRUE;
> (c) `phase_lifecycle_job.status` MUST transition to 'COMPLETED' (NOT 'FAILED', NOT 'CANCELLED' in a failure sense). `phase_lifecycle_job.cancelled=TRUE` flag remains as an audit signal;
> (d) Phase advances to PREPARED (or higher per the normal sequence — cancel does NOT regress backward).

This Story implements:

1. `DefaultCancelFlagRegistry` (interface from E55S01) — thread-safe in-memory mirror of `phase_lifecycle_job.cancelled=TRUE` for fast L3 permutation loop observation. `requestCancel(tournamentId)`, `isCancelled(tournamentId)`, `clear(tournamentId)`.
2. `SlotOptimizationCancelController` (existing, E27S02) update — when the operator clicks Cancel, the controller (a) updates `phase_lifecycle_job.cancelled=TRUE` for the currently-RUNNING row of the affected tournament, (b) calls `CancelFlagRegistry.requestCancel(tournamentId)` to update the in-memory mirror, (c) signals the L3 permutation loop via the existing `CancelableInProcessSlotOptimizationService` (per E27S02) so it observes the flag at its next polling point.
3. Orchestrator step-B continuation after cancel: when L3 returns Best-So-Far (per DEC-49 D-11a / DEC-64 D-16), the orchestrator continues its normal write-back path: applies the BSF result via `SlotResultApplicator`, sets `phase.optimized=TRUE`, advances `phase.status` per the normal sequence, sets `phase_lifecycle_job.status='COMPLETED'` (`cancelled=TRUE` audit flag retained).

**M-4 regression IT** is in this Story (not E55S07) because the invariant must be preserved on BOTH architectures — RED on neither, GREEN on both pre-E55 and post-E55 codebase. This is the regression protection: refactor must not change operator-visible cancel behavior.

DB durability: `phase_lifecycle_job.cancelled=TRUE` survives JVM restart. Recovery path (E55S07 IT) detects a claimed-but-cancelled row and dispatches directly to BSF apply + write-back (idempotent — if matches were already updated pre-crash, the second apply produces the same result).

DEC-49 D-11 per-tournament cancel scope unchanged.

## Acceptance Criteria

- [ ] **AC-IMPL-CANCEL-FLAG-REGISTRY**: `DefaultCancelFlagRegistry` (in `.internal`) implements `requestCancel(tournamentId)`, `isCancelled(tournamentId)`, `clear(tournamentId)`. Thread-safe (use `ConcurrentHashMap<UUID, Boolean>` or atomic flag holder). Lifecycle: flag set by Cancel handler; observed by L3 permutation loop via `CancelableInProcessSlotOptimizationService.shouldCancel()` (or whatever the existing E27S02 hook is); cleared by orchestrator after BSF apply completes successfully (so re-enqueue of next phase is not falsely cancelled).
- [ ] **AC-IMPL-CANCEL-HANDLER-WIRING**: `SlotOptimizationCancelController.cancel(tournamentId)` is updated to: (1) SET `phase_lifecycle_job.cancelled=TRUE` for the currently-RUNNING row of `tournamentId` (UPDATE with WHERE status='RUNNING'); (2) call `CancelFlagRegistry.requestCancel(tournamentId)`; (3) return the existing wire-contract response shape unchanged (DEC-64 D-13).
- [ ] **AC-IMPL-L3-CANCEL-OBSERVATION**: The orchestrator's call to `SlotOptimizationClient.optimize(phaseId)` (step-B) eventually reaches `CancelableInProcessSlotOptimizationService` which polls `CancelFlagRegistry.isCancelled(tournamentId)` at the existing L3 permutation polling points. On observed cancel, L3 returns the Best-So-Far permutation rank (per DEC-49 D-11a).
- [ ] **AC-IMPL-BSF-APPLY-ON-CANCEL**: orchestrator step-B, after L3 returns Best-So-Far (whether due to natural completion OR cancel-observed-mid-permutation), invokes `SlotResultApplicator` to apply the rank to the matches; sets `phase.optimized=TRUE`; advances `phase.status` per the normal sequence; sets `phase_lifecycle_job.status='COMPLETED'`. The `cancelled=TRUE` audit flag on the job row is RETAINED (not cleared).
- [ ] **AC-TEST-M-4-CANCEL-BSF-INVARIANT-RED** (testing): RED-first IT — set up a tournament with a roundRobin phase + 12 teams + lapCount > 6 (slow enough to allow cancel mid-permutation). Submit job. While L3 is running, invoke `POST /api/slotopt/tournaments/{tid}/cancel`. Wait for orchestrator step-B to complete. Assert post-state: `phase.optimized=TRUE`, `phase.status='PREPARED'`, `phase_lifecycle_job.status='COMPLETED'`, `phase_lifecycle_job.cancelled=TRUE`, matches all have `lap_number` and `field_number` non-null (BSF applied). Test fails before cancel mechanism integrates with BSF apply path.
- [ ] **AC-TEST-M-4-CANCEL-BSF-INVARIANT-GREEN-ON-PRE-E55** (testing): The SAME M-4 IT GREEN-passes on the pre-E55 codebase (verified by Delivery checking out the staging baseline before this Story, running the IT, observing GREEN, then proceeding with this Story's RED-first cycle). Documented in qa-report.md per the regression-protection rationale.
- [ ] **AC-TEST-CANCEL-PRE-PERMUTATION-RED** (testing): RED-first IT — cancel BEFORE the L3 permutation loop has evaluated any permutation. Per DEC-49 D-11a literal, the Best-So-Far is the trivial rank-0 result. Assert `phase.optimized=TRUE`, matches have lap/field assigned (the trivial assignment), `phase_lifecycle_job.cancelled=TRUE`, `status='COMPLETED'`.
- [ ] **AC-TEST-CANCEL-CLEAR-ON-COMPLETION** (testing): After orchestrator step-B completes successfully (cancel or normal), `CancelFlagRegistry.isCancelled(tournamentId)` returns FALSE for any subsequent job enqueued under the same tournament. Verified by an IT that cancels job1, lets it complete with BSF, enqueues job2, asserts job2 runs to natural completion (not cancelled).
- [ ] **AC-TEST-CANCEL-PERSISTS-OVER-RESTART** (testing): RED-first IT — submit job, cancel mid-execution, kill the worker thread (or simulate JVM restart by clearing the in-memory `CancelFlagRegistry` and reloading from DB). On restart, the recovery path (E55S07) detects `phase_lifecycle_job.cancelled=TRUE AND status='RUNNING'` and dispatches directly to BSF apply path (skipping L3 re-invocation since cancel was already observed pre-crash). Post-recovery: `phase.optimized=TRUE`, `status='COMPLETED'`.
- [ ] **AC-IMPL-REST-CONTRACT-PRESERVED**: `POST /api/slotopt/tournaments/{tid}/cancel` response shape, HTTP status codes (200 / 404 / 409 as before per E27S02), and error messages unchanged. Verified by a controller IT that asserts response JSON matches the pre-refactor schema.
- [ ] **AC-IMPL-DEC-49-D-11-PER-TOURNAMENT-SCOPE**: cancel for tournament A does NOT affect tournament B's in-flight job (worker per-tournament isolation per E55S03 + cancel-flag per-tournament per E55S05).
- [ ] **AC-TEST-DEC-49-D-11-ISOLATION-RED** (testing): RED-first IT — two tournaments running jobs concurrently; cancel A; assert B completes normally with `cancelled=FALSE`.
- [ ] **AC-ERROR-HANDLING-CANCEL-NO-RUNNING-JOB** (error-handling): cancel request when no RUNNING job exists for the tournament returns a defined response (existing E27S02 contract — likely 404 or 200-with-noop-body; preserved verbatim).
- [ ] **AC-ERROR-HANDLING-BSF-APPLY-FAILURE** (error-handling): If `SlotResultApplicator` throws during BSF apply (e.g., DB constraint violation), the step-B TX rolls back. Recovery picks up and re-runs step-B (which re-attempts BSF apply with the same Best-So-Far permutation — idempotent at the algorithmic level per DEC-49 D-11a determinism caveat). Document the edge-case explicitly in qa-report.md.
- [ ] **AC-SEC-CANCEL-AUTH-PRESERVED** (security): cancel endpoint authorization rules (admin-only via existing `SecurityConfig` filter chain) unchanged. Verified by a security IT that asserts unauthorized requests receive 401/403 with same response as pre-refactor.
