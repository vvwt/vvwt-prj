# Story E49S01: Tablet PIN out-of-band + inline-row field assignment + DEC-24 amendment + Devices.svelte rewrite + tablet name display

## User Story

**As a** tournament organizer (admin),
**I want** to assign each Scoring-Tablet to a court directly in its table row by typing the PIN that the tablet itself displays — and to never see any tablet's PIN in the admin UI —
**so that** I cannot be tricked into assigning a tablet I am not physically holding, the security claim is honest, and the workflow is faster than the current lookup-then-form approach.

---

## Context

Story E06S05 (2026-04-12) introduced a 4-digit PIN as a security feature for tablet-to-field assignment. The as-built UI shows the PIN as a column in the device list AND requires typing the same PIN in a separate lookup form on the same screen. The PIN is therefore not an out-of-band token (anyone with admin-UI access already sees it), and the lookup-then-assign workflow is cumbersome at tournament setup time when many tablets must be assigned in sequence.

Discovery 2026-05-07 (Brief `discovery-2026-05-07-e49-tablet-pin-out-of-band-and-inline-row-assignment`, human-validated v3 after Tier-2 cycles 1+2 with substantive findings on threat model, brute-force vector, schema-reuse cost, name-uniqueness scope) reframed the PIN's role: it is now a per-device, lifetime-stable, out-of-band proof-of-possession token displayed only on the registering tablet. The threat model is (a) operator confusion / wrong-tablet-pickup at assignment, and (b) third-party spoofing inducing the admin to assign a tablet they do not physically hold — NOT defense against admin-session compromise. A per-device fail-counter (N=10 wrong-PIN attempts before the device's assign endpoint locks; manual admin reset) is the sole brute-force defense; no global rate-limiting is added.

Field assignment moves inline into the device row (Option β chosen over Option α / PIN-filter-above-table — explicit human choice). To preserve row-identification when the PIN is no longer visible, a server-generated device name `Tablet-{4 random hex chars}` (reusing the existing `Device.deviceName` schema column already in use for DISPLAY devices) is shown both on the registering tablet and in the admin row. Admin can rename a Scoring-Tablet via a new endpoint scoped to `SCORING_TABLET` only (DISPLAY rename continues via the existing `/configure` endpoint — no dual-write).

This Story is atomic: backend, tablet Mustache, and admin Svelte must land together because removing `findDeviceByPin` and changing the assign contract simultaneously breaks the existing `Devices.svelte` lookup section, and a 2-story split would leave staging in a broken intermediate state.

## Acceptance Criteria

- [ ] **AC1 (registration response + tablet name display):** `POST /api/devices/register` for a SCORING_TABLET returns `{id, deviceToken, pin, deviceName}` — extended from the existing 3-field shape `{id, deviceToken, pin}` (NOT 2-field `{deviceToken, pin}` as Brief O-4 mis-stated; verified empirically against `DeviceRegisterResponse.java:16` which is `record (UUID id, String deviceToken, String pin)`). `id` is retained — no breaking change to existing clients. The server populates `device.deviceName` at registration with a generated value of format `Tablet-{4 random hex chars}` (uppercase hex, e.g. `Tablet-A3F2`); `DefaultDeviceService` exposes a new `generateUniqueDeviceName()` retry helper paired with a new `DeviceRepository.isNameTaken(String)` method; on persistence-time collision the generator retries up to 20 times then throws `IllegalStateException`. The `DeviceRegisterResponse` record signature changes from 3-arg `(UUID id, String deviceToken, String pin)` to 4-arg `(UUID id, String deviceToken, String pin, String deviceName)`; the `from(Device)` factory at line 24 is updated accordingly. The tablet registration screen `score/register.mustache` shows both the generated name and the PIN — a new `#device-name` block populated by the same `showPinAndPoll` flow that already populates `#pin-value`. Existing E21S06 register-response tests are updated to the new 4-arg shape.

- [ ] **AC2 (PIN never visible in admin UI):** The admin device-management view (`vvwt-tm-web/src/main/ui/src/routes/Devices.svelte`) does NOT display the PIN under any state — neither in the device-list table nor in any lookup or assignment form. The previous PIN column header and `<td>{device.pin}</td>` cell are removed; a name column displaying `device.deviceName` is added in its place. The previous PIN-lookup section (the lookup-form root element block in `Devices.svelte`, lines 632–681 of the as-built file at Brief authoring time — semantic anchor: the `.devices__lookup` `<section>` containing `pinInput`, `handlePinLookup`, and the `lookedUpDevice` assign sub-form) is removed entirely. Verified by Vitest UI test asserting no `device.pin` reference is rendered for any device row across every filter tab declared by `Devices.svelte` (currently `all`, `scoring`, `display`; the assertion holds regardless of future tab additions).

- [ ] **AC3 (PIN excluded from API response payloads):** `GET /api/devices` and any list/single-fetch endpoint MUST NOT include the `pin` field in the JSON response payload — the exclusion is server-side at the DTO/serialization layer (e.g., `DeviceSummaryResponse` does not contain a `pin` field). Verified by an integration test that asserts the parsed JSON of every list/single-fetch device endpoint contains no key named `pin`. UI-only hiding (still serializing the field) is rejected.

- [ ] **AC4 (inline-per-row assignment for SCORING_TABLET):** For an unassigned `SCORING_TABLET` row in the admin UI, the row contains an inline PIN input with HTML attribute `autocomplete="off"` AND visual character masking — implemented as either `type="password"` OR an explicit CSS character-replacement (`-webkit-text-security: disc` or `text-security` equivalent). A soft-keyboard-only hint such as `inputmode="numeric"` is NOT sufficient on its own — the typed PIN MUST NOT be visible on screen. The row also contains a field-number input and a "Feld zuweisen" button. Submitting calls `PUT /api/devices/{id}/assign` with body `{fieldNumber, pin}`. On success the row updates to display `device.assignedField` and a "Zuweisung aufheben" button. Existing field-conflict confirmation dialog (E06S05 AC4) is preserved when the chosen field is already occupied. The previous separate lookup→assign form is gone; assignment occurs entirely within the row.

- [ ] **AC5 (type-conditional `pin` body parameter on assign):** Server validates `PUT /api/devices/{id}/assign` per device type. For `SCORING_TABLET`: `pin` MUST be present in the body and MUST equal `device.pin`; absent → 400 RFC-7807 `application/problem+json` with `type=missing-pin-for-tablet`; mismatch → 400 with `type=pin-mismatch` (the supplied PIN value MUST NOT appear in the response body, headers, or any log line). For `DISPLAY`: `pin` MUST NOT be present in the body; presence → 400 with `type=unexpected-pin-for-display`. DISPLAY assign-flow is otherwise unchanged. **PIN is NOT validated on `PUT /api/devices/{id}/unassign` nor on `DELETE /api/devices/{id}`** — those endpoints retain their pre-E49 contracts (admin-authentication is sufficient per Brief T-3 threat model).

- [ ] **AC6 (per-device fail-counter + lock + reset):** A new `device.pin_fail_count` integer column (Flyway migration, default 0) tracks consecutive wrong-PIN attempts on `PUT /api/devices/{id}/assign` per device. On `pin-mismatch`, the counter is incremented atomically. On a successful assign for that device, the counter is reset to 0. When the counter reaches **N = 10**, subsequent assign calls for that device return 423 Locked (RFC-4918) with type `device-pin-locked` — without exposing the supplied PIN. A new endpoint `POST /api/devices/{id}/pin-lock/reset` (admin-authenticated, no body required) resets the counter to 0 and returns 204 No Content. The admin UI surfaces the locked state on the row (replacing the inline assign controls with a lock indicator + "Sperre aufheben" button calling the reset endpoint). **Counter retention semantics:** on `DELETE /api/devices/{id}` the counter row is removed atomically with the device row (hard-delete per Brief O-7); no orphan counters; soft-delete / tombstone is out of scope.

- [ ] **AC7 (`findDeviceByPin` removed end-to-end):** Remove the endpoint and all callers, exhaustive list:
  - Web: `DeviceController.findByPin` and any route binding referencing `pin` query parameter on the GET /api/devices route.
  - Service: `DeviceService.getDeviceByPin` (interface) + `DefaultDeviceService.getDeviceByPin` (impl).
  - Repository: `DeviceRepository.findByPin` (interface) + `DefaultDeviceRepository.findByPin` (impl).
  - Tests: `DeviceRepositoryIT.findByPin_*` integration tests, `DeviceControllerIT.findByPin*` integration tests, `DeviceControllerSliceTest` and `DeviceAdminControllerSliceTest` PIN-lookup test methods.
  - Frontend: `deviceStore.findDeviceByPin` (TypeScript), `deviceStore.test.ts` PIN-lookup test cases. The Svelte lookup-section block on `Devices.svelte` (the `.devices__lookup` `<section>`, lines 632–681 at Brief authoring time) is removed — see AC2 for the UI-side enforcement and rendering contract; AC7 covers the JavaScript/store-layer removal.
  - API artefacts: scan repo for OpenAPI / API-spec / generated-client artefacts referencing `findDeviceByPin` or the `pin` query parameter; remove if present, or assert in an AC-IMPL note that none exist.
  - `mvn verify` and `npm run build` MUST pass with zero remaining `findDeviceByPin` or PIN-lookup-by-query-param references. Verified by a final `grep -rIn "findDeviceByPin\|getDeviceByPin"` returning no source-code matches outside of the changelog/commit messages.

- [ ] **AC8 (rename endpoint scoped to SCORING_TABLET):** New endpoint `PUT /api/devices/{id}/rename` accepts body `{name}` and updates `device.deviceName` for `SCORING_TABLET` devices only. For `DISPLAY` devices the endpoint returns 400 RFC-7807 with `type=rename-not-supported-for-display` (DISPLAY rename continues via the existing `/configure` endpoint — no dual-write to `device.deviceName`). Server validates the new name is non-blank and ≤255 chars (matching the column constraint). Name uniqueness is NOT enforced (D-14 — name is a UX label, not a correctness identifier). The admin UI exposes a rename action on each `SCORING_TABLET` row (interaction shape — inline input or modal — at Delivery's discretion; AC focuses on the server contract).

- [ ] **AC9 (DEC-24 amendment applied):** `contexts/memory/decisions/DEC-24.md` is amended (delta — not superseded) with two new clauses:
  - **Clause E** — PIN is per-device, lifetime-stable, out-of-band proof-of-possession; valid for the entire device lifecycle until removal; NOT rotated on assign, unassign, rename, or inactivity.
  - **Clause F** — Registration contract input shape is unchanged; only the response is extended (`{deviceToken, pin, deviceName}` — no new request parameters).
  Frontmatter `last_updated_at` advances to `2026-05-08`. `contexts/memory/index.md` Decision Registry one-liner for DEC-24 is updated to reference the amendment. DEC-24 D2 (`device_token` remains the SOLE WebSocket-handshake credential) is reaffirmed in the amendment narrative — text unchanged.

- [ ] **AC10 (security — PIN never logged or echoed):** No PIN value (registration PIN nor supplied-on-assign PIN) appears in server logs, audit logs, error responses, or response headers. Verified by:
  - (i) Code-level grep: no `log.info`/`log.warn`/`log.error`/`logger.*` call site with the PIN value as an argument or interpolated into a format string.
  - (ii) Integration test: send a wrong-PIN assign request, capture the response body and a logback list-appender; assert the supplied PIN substring does not appear in either.
  - The mismatch error response uses only the type discriminator and a generic message — no PIN echo.

- [ ] **AC11 (testing — TDD per DEC-22):** All new server behavior is delivered RED-first per DEC-22 Iron Law — for each of: (a) PIN validation on assign (5 paths: missing-pin-tablet / pin-mismatch / unexpected-pin-display / valid-tablet / valid-display), (b) name generation + isNameTaken collision retry, (c) fail-counter increment / reset-on-success / lock-at-N=10 / reset-endpoint, (d) rename endpoint + DISPLAY-rejection, (e) type-conditional assign body, (f) list-PIN-omission, (g) registration response 4-field shape — the failing test commit precedes the production-code commit on the story branch. Per-step Red→Green→Refactor cycles, evidenced in Delivery's impl-report.

- [ ] **AC12 (DAO IT three-rule per DEC-26 / DEC-46):** New persistence tests follow the three rules — schema-from-migration, independent assertj-db verifier, JDBC read/write decoupling — for: `isNameTaken` (positive + negative), name-collision retry path, fail-counter persistence (increment / reset / lock-state), and the new `device.pin_fail_count` column migration. Tests live alongside existing `DeviceRepositoryIT` and follow the established `TenantDaoTestSupport` pattern.

- [ ] **AC13 (build gate — DEC-54):** `mvn verify` exit-zero is the canonical full-build validation gate (DEC-54). The frontend build is invoked via the existing `frontend-maven-plugin` binding in `vvwt-tm-web/pom.xml`. `mvn verify` MUST pass end-to-end before close-story; partial invocations (`mvn test` or `npm run build` standalone) are insufficient evidence per DEC-54.

- [ ] **AC14 (i18n):** All NEW admin UI strings — locked-state row label, "Sperre aufheben" button, "Feld zuweisen" inline button, "Zuweisung aufheben" inline button (text inherited from the existing button if present), inline PIN/field-number input placeholders and labels, error messages mapped from the new RFC-7807 problem-detail types (`missing-pin-for-tablet`, `pin-mismatch`, `unexpected-pin-for-display`, `device-pin-locked`, `rename-not-supported-for-display`) — are sourced from the translation layer established in E05S01. No hardcoded strings; English baseline per existing E05S01 i18n convention.

## Out of Scope

- DISPLAY configure modal (E07S03) — `configure()` endpoint stays DISPLAY-only with name+JSON; DISPLAY rename remains via configure. No dual-write to `device.deviceName`.
- Score-page (`/score/field`) extensions — the active scoring surface is not extended to show the device name.
- QR-code feature (E06S05 AC5) — unchanged.
- Real-time WebSocket DEVICE_REGISTERED / DEVICE_REMOVED updates (E06S05 AC6) — unchanged; the inline-row UX integrates with the existing subscription.
- Global rate-limiting, IP-based throttling, PIN-attempt audit logging beyond the per-device counter — explicitly excluded by the threat model (Brief D-11). May be revisited in a separate Story if admin-malice or session-bypass becomes a concern.
- PIN rotation on any event (Brief D-12).
- Admin-session-CSRF defense — assumed in place per existing E05S02; no new transport-security layer introduced.
- Soft-delete or tombstone for removed devices — `deleteById` remains a hard DELETE; PIN active-only uniqueness is the resulting (Brief-acknowledged) limitation.
- Schema-level unique index on `device_name` — explicitly NOT added (Brief D-14); name is a UX label, not a correctness identifier.

## Notes

**Atomic delivery rationale:** Backend, tablet Mustache, and admin Svelte ship in one PR because removing `findDeviceByPin` (AC7) and changing the assign contract (AC5) simultaneously breaks the existing Devices.svelte lookup section. A 2-story split (backend-then-frontend) would leave staging with a broken Devices view between the two PRs.

**Threat-model boundary:** PIN is NOT a defense against admin-session compromise (Brief D-2 explicitly rules this out). The fail-counter (AC6, N=10, manual reset) defends against the spoofing scenario where a third party induces the admin to type attacker-supplied PINs across the 7⁴=2401 keyspace. If admin-malice ever becomes in-scope, additional defenses (rate-limit, audit) belong in a separate Story.

**Active-only PIN uniqueness (Brief D-12, Story O-7):** `isPinTaken` checks only currently-existing devices because `deleteById` is a hard DELETE; a removed device's PIN may rarely (~1/2401 per registration) be re-issued to a future new device. Operator should treat the new PIN after re-registration as the assumption, not a guarantee. Brief acknowledges; no remediation in this Story.

**Name uniqueness NOT enforced (Brief D-14):** A TOCTOU race during concurrent registration or an admin manual rename to a duplicate produces a duplicate-name row. Recoverable via admin rename (AC8). PIN remains the correctness identifier — the duplicate-name UX degradation is acceptable.

**Brief gate trail:** Brief Tier-2 cycle-1 FAIL (4 HIGH / 6 MEDIUM / 5 LOW), cycle-2 FAIL (2 HIGH / 4 MEDIUM / 4 LOW), max-2-cycle escalation → human-validated v3 with: F-1 → per-device fail-counter (α, N=10, manual reset); F-2 → active-only PIN uniqueness (α, T-6 mitigation softened); F-3 → no unique index on name (D-14 added); F-4 → `/rename` scoped to SCORING_TABLET only (no dual-write); F-5 → DEC-24 Clause G dropped as redundant; F-6 → format ratified; F-7..F-10/F-12..F-14 → autonomous resolutions per Brief v3.
