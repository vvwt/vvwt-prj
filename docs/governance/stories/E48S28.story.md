# Story E48S28: Bug-Triage — match-correction submit must reject ONCHECK-producing inputs pre-write (4xx) instead of persisting a structurally unrecoverable Match.state

## User Story

**As a** Tournament Organizer (Admin),
**I want** the match-score-correction form to reject an incomplete or otherwise non-terminal-resolving submit BEFORE any database state is changed, with a clear operator-facing error,
**so that** a partial or empty correction never leaves a match stranded in `Match.state = ONCHECK` ("Prüfung") — a state from which the existing Korrigieren-button is intentionally hidden and the existing backend guard refuses correction, jointly producing a structural lock-in that blocks tournament progress.

---

## Context

### Bug provenance — in-the-wild incident 2026-05-30

While reproducing a Phase-2 Laufzettel display issue on the operator's PC, an operator entered set results via the correction form (`MatchCorrection.svelte` → `POST /api/matches/{matchId}/correction` → `DefaultMatchCorrectionService.correctMatchSets`). The screen "Spiele der Phase" then showed one match (Round 5, Field 2 of the test tournament "31. Frühjahrsturnier") with set scores rendered as `–` and status **Prüfung** — but no "Korrigieren" button next to it. The whole tournament was blocked. Manual H2 SQL intervention (resetting `match.state = 10` for the stuck row) restored progress. The `match.state = ONCHECK(35)` row was confirmed in committed state (the request had completed without throwing — `@Transactional` rollback boundary was unrelated to the bug).

### Root-cause walk (verified in-session 2026-05-30 against current `staging` HEAD)

1. The correction service aggregates `setsWon` + `setCount` over all `set_result` rows for the match and calls `MatchFormat.deriveMatchState(team1SetsWon, team2SetsWon, setCount)` (`DefaultMatchCorrectionService.java:411`).
2. `deriveMatchState` returns `MatchState.ONCHECK(35)` whenever neither team has reached `requiredToWin` and the match is not a finished standoff (`MatchFormat.java:172-219`). Empirical enumeration in-session: ONCHECK is returned for **every** "match not yet decided" tuple — `(0,0,0)` for every format, plus partial-non-winning tuples per format (`BEST_OF_3`: `(1,0,1)`, `(0,1,1)`, `(1,1,2)`; `BEST_OF_5`: 9 tuples; `BEST_OF_7`: 16 tuples; `FIXED_2_SETS`: `(0,0,0)`, `(1,0,1)`, `(0,1,1)`).
3. The derived state is written directly to `match.state` (`DefaultMatchCorrectionService.java:428-431`).
4. Subsequent correction attempts on the same match are rejected by Guard Step 3 (`DefaultMatchCorrectionService.java:233-244`) with `MatchStateGuardException` — the backend forbids correcting an `ONCHECK` match.
5. The frontend `MatchOverview.svelte:76-78` hides the "Korrigieren" button for `ONCHECK` matches (intentional mirror of the backend guard).
6. Net effect — a structural lock-in. The operator's only path forward is direct database editing (operationally unacceptable as a recurring workaround).

### Resolution shape (human-validated Discovery Session Brief v2 2026-05-30)

A **pre-write input guard** on the operator-correction path rejects any submit that would compute to `MatchState.ONCHECK` *before* any database write. The guard is **server-side only** (Brief D-1, T-1, T-2). Approach A (4xx pre-write reject) was chosen over Approach B (200 OK + post-derive substitution) per the human-validated Brief: semantic cleanness (no half-state persistence, no `match_outcome` upsert with a non-terminal `computedState`), fail-fast operator feedback, no `audit_log` spam from invalid submissions.

The fix is **scoped to the operator-correction path**. The live-scoring path (`DefaultScoreEntryService`) legitimately uses `ONCHECK` as a transient between-sets state (an `ACTIVE_STATES` member at `DefaultScoreEntryService.java:122-127`) and is explicitly out of scope.

### Scope-discipline anchors

- This story does **not** modify `MatchFormat.deriveMatchState` — it is correct for live-scoring use.
- This story does **not** modify the live-scoring path (`DefaultScoreEntryService`).
- This story does **not** modify the frontend "Korrigieren" button visibility rule — that rule remains correct *for newly authored matches* after the fix (the fix prevents new ONCHECK rows from being persisted via the correction path).
- This story does **not** include a data-migration / repair script for pre-existing stuck rows; the in-session in-the-wild row was unblocked manually and the system is pre-production under DEC-25 (no production data to migrate).
- This story does **not** add or modify the UX path for resuming live-scoring on a stranded ONCHECK match via score-tablet — that is a separate latent UX concern, not bundled.
- This story does **not** investigate or fix the Phase-2 Laufzettel display bug that the operator was originally reproducing.

### Empirical MatchFormat.deriveMatchState ONCHECK enumeration (in-session 2026-05-30)

### Asymmetric-error preference (DEC-47 Clause F lineage)

If Delivery faces invocation or parse ambiguity in interpreting a submitted `MatchCorrectionInput` (e.g., uncertain whether to reject or to coerce), the asymmetric-error preference is **false-FAIL ≫ false-PASS** — prefer rejecting an ambiguous submit over accepting it and leaving the system in a potentially locked state. Operator can always retry with a fully-formed correction.
