## User Story

**As a** developer running `mvn verify` on `vvwt-tm-web` against staging HEAD (or via NetBeans Clean & Build),
**I want** the test `DefaultDraftServiceApplyNoTeamAvatarsIT.apply_withParticipatingTeams_creates3PhasesAndStructuralAvatars` to pass deterministically by aligning its phase-status assertion with the post-quiescence equilibrium contract codified by DEC-55 D-3 + DEC-56 D-3,
**so that** `mvn verify` GREEN reflects the actual merged-on-staging behavior of the background-job pipeline (DEC-54 closure gate restored) without requiring `PASS_WITH_NOTES` waivers.

## Context

User reported on 2026-05-09 that `mvn verify` fails on `vvwt-tm-web` post-E53S04-merge with assertion failure at `DefaultDraftServiceApplyNoTeamAvatarsIT.java:324`:

```
[All 3 phases must have status PENDING after apply()]
expected: 3
 but was: 2
```

Empirical reproduction on staging HEAD `de380a29` (initially observed at `36bf620` per E53S04's qa-report Step 2): **5/5 deterministic FAIL** of `apply_withParticipatingTeams_creates3PhasesAndStructuralAvatars` via repeated `mvn -pl vvwt-tm-web -Dtest=DefaultDraftServiceApplyNoTeamAvatarsIT#apply_withParticipatingTeams_creates3PhasesAndStructuralAvatars test`. `pendingCount` distribution: {1, 2} (never 3, never 0); failure direction deterministic, count variable due to mid-quiescence observation timing.

### Root cause

The test's status-assertion at lines 317-324 expects `pendingCount==3` immediately after `draftService.apply(tournamentId, config)` returns:

```java
int pendingCount = jdbcTemplate.queryForObject(
    "SELECT COUNT(*) FROM phase WHERE tournament_id = ? AND status = 'PENDING'",
    Integer.class, tournamentId);
assertThat(pendingCount)
    .as("All 3 phases must have status PENDING after apply()")
    .isEqualTo(3);
```

This assertion was authored at E48S17 (when `apply()` had no async lifecycle wiring) and updated at E51S02 (DEC-55 D-1 avatar-shift) — **both pre-date E51S14**. E51S14 (commit `9f5fa9d`, "wire PhaseLifecycleService into MatchGenJobExecutor — PENDING→PREPARED on match-gen success") introduced an async lifecycle transition that retroactively invalidated the assertion. The test does NOT call `waitForPipelineQuiescent` before the status query — only in `tearDown` (line 169). The race window is the time between `apply()` returning and the status-COUNT-query running (~600ms test elapsed time): `MatchGenJobListener` (`@TransactionalEventListener(AFTER_COMMIT) @Async`) consumes events, `MatchGenJobExecutor` runs L1 (MatchGenerator) + L2 (RoundAssignmentService per DEC-56 D-3), and on success `PhaseLifecycleService` transitions phase PENDING→PREPARED. Phase 1 always wins this race within ~600ms; Phase 2 sometimes does.

### Equilibrium contract (post-quiescence, deterministic)

Per **DEC-56 D-3** ("L1+L2 are always mandatory; matches reference `avatar.getId()`, not `teamId`") + **DEC-55 D-3 step 1** (siegerehrung phases skip avatar-creation → no `MatchGenJobScheduledEvent` published → `last_job_state` stays NULL → `waitForPipelineQuiescent` does not block on siegerehrung) + **DEC-9** (TeamAvatar structural identity `(phaseId, groupNumber, groupPosition)` → matches reference `memberAvatar1Id`/`memberAvatar2Id`):

| Phase | gameMode | MatchGen runs? | Equilibrium status |
|---|---|---|---|
| Phase 1 | roundRobin | YES (avatar.id-based; teamId state irrelevant) | PREPARED |
| Phase 2 | roundRobin | YES (same mechanism) | PREPARED |
| Phase 3 | siegerehrung | NO (skipped per DEC-55 D-3 step 1) | PENDING |

Expected post-quiescence: `preparedCount=2, pendingCount=1, totalPhases=3`.

### Why this is a test-side fix only (production behavior is correct)

The async pipeline behavior is the intended DEC-55/DEC-56 contract. E51S14's PhaseLifecycleService wiring was correct per its own qa-report (verified). The test assertion is the only thing that needs to change. **No production code changes** are in scope of this Story.

### Why a new Story (not amend E51S14, E51S08, or E48S17)

E51S14 is `status: done` and merged. Lifecycle does not permit `done → in_progress` (per `base.rules.md` § Backlog State Lifecycle). E51S08 added `waitForPipelineQuiescent` to `tearDown` but not to the assertion sequence — it pre-dated E51S14's wiring. E48S17 authored the original assertion under pre-E51S14 production behavior. Bug-triage post-E51S14 contract-alignment is its own scope.
