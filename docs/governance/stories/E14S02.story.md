# Story E14S02: Per-tenant H2 file layout + registry persistence — tests first

## User Story

**As an** operator running the self-hosted TM application on a local machine,
**I want** each tenant's data stored as a dedicated H2 file under a predictable path, with a durable registry that survives restarts,
**so that** I can locate, back up, or move a tenant's database as a single file and the application recognises registered tenants on every subsequent start.

---

## Context

DEC-20 prescribes one H2 file per tenant under `${tm.data.dir}/tenants/{tenant-uuid}/db.mv.db` and requires a durable tenant registry. This story implements the file-layout component and the registry persistence, satisfying the `TenantRegistryPort` contract defined in E14S01.

Two registry persistence options are open per the Epic: (a) a separate H2 "registry" DB at `${tm.data.dir}/registry.mv.db`, or (b) a file-based registry (YAML/JSON) in the same directory. The story's AC pins the decision and records the rationale. Both choices must satisfy: survives restart, supports concurrent-start-safe initialisation, and is inspectable by an operator without special tooling.

Per DEC-22, registry write/read code is written test-first with real filesystem I/O (temp directories in tests); no characterization tests against an existing registry are permitted.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first): Git history shows a failing test for registry read/write operations before the implementation commits for those operations. A test-first commit precedes the implementation commit for each of: "register new tenant", "lookup by identifier", "enumerate all tenants". Characterization tests are forbidden per DEC-22.

- [ ] AC2 (data-isolation — file layout): Tenant DB files are created at `${tm.data.dir}/tenants/{tenant-uuid}/db.mv.db` (or the exact H2 variant selected; path finalized in the Delivery execution plan). Writing to tenant A's DataSource touches only tenant A's file; no shared file is written across tenants. An integration test confirms by inspecting the filesystem after two test tenants write distinct rows.

- [ ] AC3 (data-isolation — registry persistence choice): The registry persistence mechanism is selected (H2 registry DB vs file-based registry) and documented inline in the registry implementation's Javadoc with a one-paragraph rationale. The choice satisfies: (a) survives restart, (b) tolerates concurrent-start safely (no partial-write corruption on crash mid-init), (c) is human-inspectable.

- [ ] AC4 (error-handling — missing data dir): If `${tm.data.dir}` does not exist on first start, the registry creation path creates the directory. If the path exists but is not writable, the application fails fast with an actionable error message naming the path and the required permission. Tests cover both paths.

- [ ] AC5 (error-handling — corrupt registry): If the registry file/DB is present but unreadable (e.g., malformed), the application fails fast with a message that names the registry location and does NOT silently recreate it (avoid hidden data loss). A test simulates corruption by truncating the file or injecting invalid content.

- [ ] AC6 (error-handling — duplicate registration): `TenantRegistryPort.register(...)` with an already-registered identifier fails with a typed exception; no silent overwrite. A test asserts this.

- [ ] AC7 (governance — internal placement): All implementation classes (registry store, file-path helper) live under `de.vvwt.tm.tenant.internal`. No new types are added to `de.vvwt.tm.tenant` root package beyond AC-driven extensions to the interfaces from E14S01, if any.

- [ ] AC8 (testing — Modulith verify): `ApplicationModulesTest` continues to pass. No import from `de.vvwt.tm.tenant.internal` leaks into any other module's tests or production code.

- [ ] AC9 (governance — configuration surface): `${tm.data.dir}` has a documented default (platform-appropriate app-data directory per DEC-15 deployment context) and an `application.yml` override key. Both paths are tested.

- [ ] AC-PATH-LENGTH (error-handling — Windows path length safety): At tenant directory creation, if the total path length (`tm.data.dir` + `/tenants/` + tenant-UUID + `/db.mv.db`) exceeds 250 characters (conservative buffer below Windows default 260 MAX_PATH), the creation fails fast with an actionable error naming both the computed path and the length. A test verifies this with an artificially long `tm.data.dir`.

- [ ] AC-CONCURRENT-REGISTER (data-isolation — concurrent tenant registration safety): Two threads simultaneously calling `TenantRegistryPort.register(tenantId)` for DIFFERENT tenant IDs MUST both succeed without partial-write corruption. Two threads simultaneously calling `register(tenantId)` for the SAME tenant ID MUST result in exactly one success; the other receives a deterministic typed response (exception OR idempotent return — decision documented in Javadoc of `TenantRegistryPort`, tested here).

## Notes

The registry-persistence choice (H2 vs file) has a mild trade-off: H2 gives transactional semantics but adds a second H2 file to back up; YAML is easier to inspect and edit manually but offers no transactional guarantees. Delivery's Java context tends toward H2 for consistency; the rationale in AC3 should name the chosen trade-off explicitly rather than merely picking.

Temp-directory-based tests (JUnit `@TempDir`) are the right shape for this story. Avoid test pollution by not writing into the user's real `${tm.data.dir}` default during tests.
