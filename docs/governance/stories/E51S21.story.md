# Story E51S21: Fix — DEC-59 UI-surface gaps (Phase-1 stuck in PREPARED: PhaseList missing "Mannschaften zuordnen" action + activate-guard siegerehrung-OR-term client-mirror gap + PhaseOverviewResponse missing `optimized` field)

## User Story

**As the** Tournament Operator,
**I want** to be able to assign teams to a phase that is in PREPARED status (when the phase is the first or its predecessor is COMPLETED) via the existing drag&drop UI, and to see the slot-optimization status reliably (✅ when complete, ⏳ when running, "—" when not applicable),
**so that** after applying the Phasenplan I can actually proceed: confirm team assignments via the operator-confirmation workflow (DEC-59 Clause C), then start the phase — instead of being stuck on the Phasenübersicht with only a "Phase starten" button that the backend rejects.

---

## Context

DEC-59 (commit `ab727af`) and its operationalization Story E51S18 (PR #245, merged 2026-05-10) corrected the team-assignment workflow contract:

- **Clause B:** `team_avatar.team_id = NULL` universally at apply-time (Phase 1 carve-out removed).
- **Clause C:** `PREPARED → ASSIGNED` requires operator-confirmation (proposal → review → confirm); `commitTransition` now rejects non-PREPARED phases and non-COMPLETED predecessors with HTTP 409.
- **Clause F:** Activation-guard `ASSIGNED → ACTIVE` amended to `!tournament.optimize OR phase.optimized OR section.gameMode == 'siegerehrung'`.

E51S18 implemented Clauses A–F at the **Java backend** (`DefaultDraftService`, `DefaultPhaseTransitionService`, `DefaultPhaseLifecycleService`, `MatchGenJobExecutor`). DEC-59 § Implementation explicitly noted: *"UI-surface implementation for the Operator-Confirmation team-assignment workflow (Clause C) — likely already implemented partially via existing drag&drop; gaps surfaced in Story A's investigation. UI-implementation gap-fill may require a separate Story; deferred to Story A's qa-report scope-call."* E51S18's `impl-report.md` lists **zero Svelte file modifications** — the deferred UI gap-fill never happened.

### Reproduction (operator-reported, 2026-05-10)

After creating tournament `31. Frühjahrsturnier` and applying the Phasenplan:
- All 3 phases display status `Vorbereitet` (PREPARED) on Phasenübersicht (`PhaseList.svelte`).
- Only `"Phase starten"` button is offered as action — no entry-point to drag&drop team-assignment UI.
- Clicking `"Phase starten"` calls `POST /api/phases/{id}/start` which the backend (per DEC-55 D-4 `ALLOWED_TRANSITIONS`) rejects: PREPARED → ACTIVE is not a valid transition (only ASSIGNED → ACTIVE is). User is stuck.
- `Job` column displays "—" for all 3 phases including `roundRobin` phases where `tournament.optimize=true` (operator left default checkbox active) and slot-optimization has completed server-side (`phase.optimized=true`).

### Three independent root causes — bundled per user 2026-05-10

### Why ONE Story (not 3 split)

- All three are UI-side gaps left by E51S18 (Java-only change). DEC-59 § Implementation explicitly anticipated this gap-fill as "a separate Story".
- Logical cohesion: workflow restoration (Befund 1) is the user-visible restoration of the operator-confirmation flow; Befund 2 prevents siegerehrung being broken once the user reaches Phase 3; Befund 3 prevents the workflow from looking visually broken even when the backend pipeline is healthy.
- Deploy cohesion: a partial fix (e.g., Befund 1 only) leaves Befund 3's "—" rendering visible on the same screen — looks half-broken to the operator. Atomic delivery avoids intermediate broken states.
- Closure-gate convergence: all three fixes converge on a single `mvn verify` GREEN per DEC-54 (the frontend-build-bypass path closed by DEC-54 ensures the Vite build runs).

### Why a new Story (not amend E51S18)

- E51S18 is `status: done` and merged. Lifecycle does not permit `done → in_progress` per `base.rules.md` § Backlog State Lifecycle.
- DEC-59 § Implementation defined this UI gap-fill as a separate-Story scope.

### Testing — Frontend activate-guard siegerehrung mirror (Befund 2)

- [ ] **AC-TEST-PHASELIST-SIEGEREHRUNG-START-ENABLED-WITH-OPTIMIZE-TRUE-RED**: A RED-first vitest demonstrates that for a fixture `{ status: 'ASSIGNED', gameMode: 'siegerehrung', optimized: false }` with `tournament.optimize = true`, the `phases.startButton` is **enabled** (mirror of server-side DEC-59 Clause F). Baseline FAIL on staging HEAD because `activateGuardFails(phase)` evaluates `tournamentOptimize && (phase.optimized === false)` (JS precedence: `===` binds tighter than `&&`) → `true && (false === false)` → `true && true` → `true` → guard FAILS → button disabled. **Note on the latent-vs-active state of this bug:** today (pre-Befund-3) the wire-DTO omits `optimized`, so `phase.optimized` is `undefined` and `(undefined === false)` is `false` → guard passes → bug masked. Once Befund 3 lands and `optimized: false` arrives as an actual boolean for siegerehrung phases, the bug becomes operator-visible — therefore N-2 must ship in the same Story as the DTO fix. The RED test fixture sets `optimized: false` as a literal boolean to exercise the post-Befund-3 state directly.
- [ ] **AC-TEST-PHASELIST-SIEGEREHRUNG-START-ENABLED-WITH-OPTIMIZE-TRUE-GREEN**: After fix, `activateGuardFails` includes the `&& !isSiegerehrungPhase(phase)` (or equivalent — `gameMode != 'siegerehrung'`) term. Test passes. Use the GameMode enum constant from E51S20 if applicable; otherwise the literal `"siegerehrung"` is acceptable per DEC-59 Clause F's literal-form authorization.
- [ ] **AC-TEST-PHASELIST-NON-SIEGEREHRUNG-START-DISABLED-WITH-OPTIMIZE-TRUE-OPTIMIZED-FALSE**: Regression guard: for `{ status: 'ASSIGNED', gameMode: 'roundRobin', optimized: false }` with `tournament.optimize = true`, `phases.startButton` is **disabled** with tooltip `phases.activateGuardTooltip`. Existing behavior preserved.
