## Acceptance Criteria

- [ ] **AC1 (testing, DEC-22 Iron Law — anti-spoof):** Every test class in this story is committed to staging in its RED state BEFORE the corresponding production class is committed. The RED state is verified by TWO co-observations, not by commit-order alone (which is mechanically spoofable given the E08S06 DEC-28 incident history):
  - **(a) Commit-order:** `git log --oneline` on the story branch shows the test-class commit SHA preceding the controller/service-class commit SHA for each new test file.
  - **(b) Captured RED output with SHA match:** For at least the FIRST `@Test` method of each new test class, `impl-report.md` records: (i) the RED commit SHA (matching the commit in (a)); (ii) the verbatim test output, which MUST contain one of the following behavioural-failure markers — `org.opentest4j.AssertionFailedError`, `java.lang.AssertionError`, `org.springframework.test.web.servlet.ResultMatcher` status-mismatch string, or an equivalent assertion-level failure. Compile failures (`java.lang.Error`, `ClassNotFoundException`, `CompilationFailedException`) do NOT satisfy this AC — compile-RED is not behavioural-RED.
  - **(c) QA-review check:** `qa-report.md` cites the SHA in (b) and confirms the captured output matches one of the allowed behavioural-failure markers.

- [ ] **AC2 (testing, slice — ActivityType):** `ActivityTypeControllerTest` exists as `@WebMvcTest(ActivityTypeController.class)` with service collaborators declared via `@MockitoBean`. Covers all per-endpoint logic scenarios migrated from the behaviour reference (`archive/E08S06-pre-dec28`, `ActivityTypeControllerIT` 10/10 tests) to the slice layer under Approach C: CRUD mapping (`POST/GET/PUT/DELETE /api/tournaments/{tournamentId}/activity-types`), request validation (`@Valid` on POST/PUT body: `name` required non-blank, `assignmentRule` required and within the allowed V1 set, `capacityPerRound` nullable non-negative), HTTP status branches (201/200/204/400/404/409), security-decision via `@WithMockUser` + `SecurityMockMvcConfigurers.springSecurity()`, CSRF on POST/PUT/DELETE.

- [ ] **AC3 (testing, slice — Assignment Preview):** `ActivityAssignmentPreviewControllerTest` exists as `@WebMvcTest(ActivityAssignmentPreviewController.class)` with service collaborators via `@MockitoBean`. Covers all per-endpoint logic scenarios migrated from the behaviour reference (`ActivityAssignmentPreviewControllerIT` 4/4 tests): GET `/api/tournaments/{tournamentId}/activity-assignments` mapping, `phaseId` query parameter handling, response JSON shape `{phaseId, assignments:[{activityTypeName, entries:[{lapNumber, teams:[...]}]}], unassigned:[...]}`, HTTP status branches (200/400/404), security-decision via `@WithMockUser`.

- [ ] **AC4 (testing, IT minimalism per Brief D-3):**
  - `ActivityTypeEndpointIT` exists with **exactly 2 `@Test` methods**: (a) happy-path `POST /api/tournaments/{id}/activity-types` → 201 Created + DB verification via `AssertDbConnection.table("activity_types")` asserting the inserted row; (b) unauthenticated `POST` → 401 Unauthorized.
  - `ActivityAssignmentPreviewEndpointIT` exists with **exactly 2 `@Test` methods**: (a) happy-path `GET /api/tournaments/{id}/activity-assignments` → 200 OK + JSON shape assertion; (b) unauthenticated `GET` → 401.
  - No IT test class introduced by this story contains more than 2 `@Test` methods — the minimalist-IT discipline is grep-verifiable across the story's changed file set.

- [ ] **AC5 (testing, DEC-26 Rule 2 explicit composition):** Every IT write-path `@Test` method verifies DB state via an **independent verifier** — either `assertj-db` (`AssertDbConnection.table(...)`) OR direct JDBC via a fresh `JdbcTemplate` constructed from the DataSource (per DEC-26 Rule 2's "assertj-db or equivalent" clause). Never via a subsequent HTTP-GET call against the system under test, and never via any DAO read method:
  - **PASS predicate (either satisfies):** write-path `@Test` body contains `AssertDbConnection` **OR** direct `jdbcTemplate.queryForMap/queryForList/queryForObject(...)` inside an `assertThat(...)` assertion against the same DataSource.
  - **FAIL predicate (any of):** write-path `@Test` body contains (i) `mockMvc.perform(get(...))` / `restTemplate.getForEntity(...)` / any HTTP-GET invocation used for verification, OR (ii) a call to any DAO read method (pattern `<someDao>.(find|get|read|fetch|load)...(...)` returning asserted values). Both are DEC-26 Rule 2 violations because they use the system-under-test as its own verifier.
  - Grep-verifiable on the final committed test classes; `qa-report.md` cites the grep results for each write-path `@Test`.

- [ ] **AC6 (testing, infrastructure — TenantContext slice-stub per Brief D-10):** A new `TenantContextSliceTestSupport` (working name; final name documented in `impl-report.md`) exists as a test-scope utility at `vvwt-tm-web/src/test/java/de/vvwt/tm/infrastructure/testsupport/` (co-located with `TenantDaoTestSupport` per DEC-26 test-utility-convention precedent — NOTE: the existing `TenantContextTestSupport` lives at `de.vvwt.tm.tenant/`, a separate location oriented toward full-context ITs; the new slice-layer utility deliberately lives with the DEC-26 utilities at `infrastructure.testsupport/`). Provides the minimum API needed by the two slice test classes in AC2 + AC3 — no more. Design decision documented in `impl-report.md` (2–4 lines) covering:
  - **(a) Stub target:** which DEC-20 artefact is stubbed — `TenantContext` (the bearer of the current tenant identifier; stubbed via ThreadLocal seeding on the bearer's public-API entrypoint) vs. `TenantContextResolver` (the Spring-bean resolver; stubbed via `@MockitoBean` or equivalent). **Caveat on `TenantContextResolver`:** this class lives at `de.vvwt.tm.tenant.internal.*` per DEC-21 Modulith boundaries. Choosing to stub it crosses the `tenant.internal` boundary at test scope — an accepted trade-off for slice-test ergonomics that Delivery MUST document in `impl-report.md` if this option is selected. Stubbing `TenantContext` (public-API bearer) does not cross the boundary and is the lower-coupling option. These are different artefacts — Delivery names which is chosen and why.
  - **(b) DEC-20 invariant (MUST-hold):** the chosen stub MUST permit each slice-test method to set a caller-tenant identifier that the controller code sees via the production resolution path (not bypassed). The stub MUST NOT permit a slice-test to read tenant-B resources while holding tenant-A identity — cross-tenant isolation at slice layer is preserved by construction. AC9's cross-tenant security test is the behavioural verifier of this invariant.
  - **(c) Utility shape:** `final` class, private constructor (DEC-26 `TenantDaoTestSupport` precedent — no inheritance-based extension that would reintroduce shared-evaluator coupling).

- [ ] **AC7 (governance — Approach C conformance):** Both controller test pairs (slice + IT) conform to the convention section E20S01 adds to `.gaai/project/contexts/memory/patterns/conventions.md` § "REST Controller Integration Tests". - [ ] **AC8 (governance — IT-Annotation Empirical Evaluation per Brief D-5 / H-3):** `impl-report.md` contains a section **"IT-Annotation Empirical Evaluation"** comparing `@SpringBootTest(webEnvironment = RANDOM_PORT)` vs `@ApplicationModuleTest` on this story's controllers. The comparison reports for each annotation:
  - (a) **Cold-boot context-load time measurement:** run **exactly 3 cold-boot measurements per annotation** (fresh JVM process between runs — `mvn test -Dtest=XxxEndpointIT` invoked 3 times independently, not repeated inside one JVM). Capture min / median / max in seconds. Report all 3 raw timings + the median.
  - (b) **Cross-module bean-wiring outcome:** works out-of-the-box / requires `extraIncludes = {...}` (list the modules explicitly) / fails with the specific error message.
  - (c) **Ability to use `TestRestTemplate` (or `MockMvc` inside `@AutoConfigureMockMvc`)** — whether the chosen HTTP client works with the annotation.
  - (d) **Sample-size hedge (per Brief Q-3 Honest Hedging):** N=3 runs on 2 controllers is not a robust statistical sample; the empirical evaluation reports point-measurements from a specific machine at a specific time. The chosen annotation is defensible against the median-time + wiring-outcome evidence at this sample size; a future Track-3 epic may re-evaluate if the evidence proves misleading in practice.
  
  The section concludes with the annotation chosen for this story's two ITs + 2-line rationale anchored in the median of (a) and the concrete outcome of (b). Both annotations MUST be tried; the conclusion may prefer either.
