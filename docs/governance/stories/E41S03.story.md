# Story E41S03: Crypto integration (ResultSigner + DefaultWorkerKeyManager instantiation via worker-lib API; signed canonical bytes per delivered dispatcher DTOs)

## User Story

**As a** standalone-worker process responsible for signing optimization results before submission to the dispatcher,
**I want** a `ResultSigner` component that consumes the `WorkerKeyManager` API from `vvwt-slotopt-worker-lib` (instantiating `DefaultWorkerKeyManager` per Brief C-22) and produces signed canonical bytes per the delivered dispatcher DTO contracts (per Brief D-10),
**so that** result submissions to `POST /api/submit-result` carry valid signatures matching what the delivered `SubmitResultController` accepts.

---

## Context

Per Brief C-22: `WorkerKeyManager` + `DefaultWorkerKeyManager` (E37S03 done) provide D-4 hybrid keypair-mismatch mechanic. Standalone-worker INSTANTIATES the existing default impl from worker-lib; E41 does NOT author the mechanic. The `ResultSigner` in this story is a thin adapter on top of the worker-lib API.

Per Brief D-10: when E37S02 spec § (b)/(c)/(d) and DELIVERED dispatcher API source diverge, DELIVERED is authoritative. Per Brief O-6 (ii): SubmitResult `algorithm` field is on the request body per E37S09 delivered (spec § (b) signed-bytes layout omits it). Implementer reads delivered `SubmitResultRequest.java` source for canonical-bytes shape.

Per Brief C-21 + D-9: this story depends on E41S02 (`WorkerConfig` provides keyDir + signingAlgorithm). It does NOT depend on E40 stories — the crypto layer authors against worker-lib API only; HTTP integration with dispatcher endpoints is E41S04+ scope.

Per Brief D-6: V1 supports only Ed25519 signing. ResultSigner instantiates `DefaultWorkerKeyManager` configured for Ed25519; future Phase-2+ would add a `WorkerCapabilityProvider` consultation step here, but that's OOS for V1.

### Story-specific ACs

- [ ] **AC-RESULT-SIGNER-INTERFACE**: `de.vvwt.slotopt.standalone.crypto.ResultSigner` interface declared with method:
  ```java
  byte[] signResult(SubmitResultPayload payload) throws SigningException;
  ```
  where `SubmitResultPayload` is a record carrying the fields needed to compute canonical bytes per the delivered `SubmitResultRequest` DTO (e.g., `UUID jobId`, `UUID packetId`, `byte[] resultBytes`, `String algorithm` — exact field set derived by reading `vvwt-slotopt-dispatcher/src/main/java/de/vvwt/slotopt/dispatcher/result/SubmitResultRequest.java` per Brief D-10). Authored RED-first.
- [ ] **AC-DEFAULT-RESULT-SIGNER**: `de.vvwt.slotopt.standalone.crypto.internal.DefaultResultSigner` impl per DEC-35-by-analogy. Constructor receives a `WorkerKeyManager` instance (from `vvwt-slotopt-worker-lib`, instantiated as `DefaultWorkerKeyManager` per Brief C-22). The signing algorithm in V1 is the worker-lib's Ed25519-backed mechanism; the worker-lib WorkerKeyManager API is the boundary — `DefaultResultSigner` does NOT re-implement crypto.
- [ ] **AC-WORKERKEYMANAGER-INSTANTIATION**: A `WorkerKeyManager` instance (interface-typed) is obtained from `vvwt-slotopt-worker-lib` and used by `DefaultResultSigner`. Instantiation pattern is **delivery-time decision** per worker-lib public surface inspection:
  - **Path 1 (preferred per DEC-35-by-analogy)**: if vvwt-slotopt-worker-lib exposes a public factory (e.g., `WorkerKeyManagerFactory.create(Path keyDir)` in package root `de.vvwt.slotopt.worker.identity.*`), use it directly.
  - **Path 2 (fallback)**: if no public factory exists, the implementer reads the worker-lib public surface to determine the canonical instantiation pattern (DI mechanism, builder, or otherwise). Cross-module import of `de.vvwt.slotopt.worker.identity.internal.DefaultWorkerKeyManager` is FORBIDDEN per DEC-35-by-analogy (E35S04 sub-section establishes interface-in-root + Default*-in-`.internal` for non-Spring modules; cross-module consumers MUST use the public surface).
  - **Path 3 (escalation)**: if neither Path 1 nor Path 2 yields a viable pattern, implementer **stops and escalates** to Discovery — worker-lib's public surface needs a factory/exposition update before E41S03 can complete (worker-lib amendment is OOS for E41 — separate Discovery cycle would be required for worker-lib changes).
  Implementer documents the chosen path + rationale in impl-report. Verifiable: `DefaultResultSigner` source contains zero `import` statements with package suffix `.internal` referencing other modules.
- [ ] **AC-CANONICAL-BYTES-FROM-DELIVERED-DTO**: Canonical-bytes layout for SubmitResult signing matches the delivered `SubmitResultRequest` DTO field shape per Brief D-10 + O-6 (ii). Implementer reads `vvwt-slotopt-dispatcher/src/main/java/de/vvwt/slotopt/dispatcher/result/SubmitResultRequest.java` source. RED test fixture provides a known SubmitResultPayload + expected canonical bytes; signature verification round-trip with worker-lib WorkerKeyManager confirms a valid signature is produced.
- [ ] **AC-SIGNING-EXCEPTION** (error-handling category): `de.vvwt.slotopt.standalone.crypto.SigningException extends RuntimeException` with `(String message, Throwable cause)` constructor. Wraps any worker-lib WorkerKeyManager errors during signing (e.g., `IOException` reading keypair, `GeneralSecurityException` from JDK Signature). Authored RED-first.
- [ ] **AC-D-4-MECHANIC-INSTANTIATED-NOT-AUTHORED** (per Brief C-22): The hybrid keypair-mismatch mechanic from `DefaultWorkerKeyManager` (E37S03 delivered) is INSTANTIATED via the worker-lib API at startup. This story does NOT re-author the mechanic. Verifiable: `DefaultResultSigner` source contains zero references to file-naming, refuse-to-start, or keypair-rotation logic — those concerns live in worker-lib.
- [ ] **AC-V1-SINGLE-ALGORITHM-CHECK**: `DefaultResultSigner` validates that `WorkerConfig.signingAlgorithm == "Ed25519"` at construction time; mismatched algorithm → `IllegalStateException` with explicit "V1 supports only Ed25519" message. Defensive code per Brief Q-5. RED test asserts this.

## Notes

- The worker-lib `WorkerKeyManager` API is a STABLE boundary established by E35S02 + E37S03. This story consumes it; does not modify it.
- Canonical-bytes layout MUST match what the delivered `DefaultSubmitResultService.submit()` verifies (per E37S09 delivered code). Implementer reads both DTO source AND service-side verifier source to confirm field-ordering + canonicalization.
- V1 hardcoded `algorithm == "Ed25519"` check is defensive; it WILL be relaxed in Phase-2+ when ML-DSA-65 etc. land. The check exists to fail-fast at startup if WorkerConfig is misconfigured.
