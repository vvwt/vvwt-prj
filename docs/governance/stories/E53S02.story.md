# Story E53S02: Laufzettel content semantics — playing-vs-context + refereeing-team-pair-context + LaufzettelRow VO extension + PrintController ACTIVE-only phase filter

## User Story

**As a** participating team viewing my own Laufzettel (printed team-schedule),
**I want** the Aktivität column to clearly disambiguate when I am playing against a specific opponent versus when I am refereeing a match between two other teams, AND I want only the operationally-relevant phase displayed (not all phases of the tournament including those whose schedule is still pre-optimization),
**so that** I can read my schedule without ambiguity and trust that the displayed round-numbers + opponents are final.

---

## Context

User-observable symptoms (Discovery 2026-05-08, screenshot 2 in session brief):

- The team-schedule page (`/print/tournaments/{tid}/team-schedules` for all teams; `/team-schedules/{teamId}` for one team) shows the Aktivität column with only one team name (e.g. "Mannschaft 02") on rows. The team viewing their own Laufzettel cannot tell whether they have a match AGAINST that team or whether they are providing the referee for a match where that team is one side.
- The same page shows ALL phases of the tournament (e.g. "Phase 1" + "Phase 2" headers + their respective round tables), creating multi-phase clutter even when only one phase is operationally active.

User-stated complaint (verbatim 2026-05-08): "wird bei Aktivität nur ein Mannschaftsname angezeigt. Die Mannschaft sieht nicht, ob sie ein Spiel gegen diese Mannschaft hat oder das Schiedsgericht stellen muss. Außerdem werden mehrere Phasen ausgegeben."

### Root cause (verified empirically 2026-05-09)

**(a) Playing rows render only `{{opponentName}}`** without any "vs"-semantic prefix. `vvwt-prj/vvwt-tm-web/src/main/resources/templates/print/laufzettel.mustache:65` reads:

```
<td class="laufzettel-col-activity">{{opponentName}}</td>
```

**(b) Refereeing rows render only `{{msgReferee}}`** ("Schiedsgericht") with no opponent-pair information. `laufzettel.mustache:74` reads:

```
<td class="laufzettel-col-activity">{{msgReferee}}</td>
```

LaufzettelRow.java (the underlying VO for each row) is a Java record with components `{isPhaseHeader, phaseHeaderName, isBreak, breakLabel, breakTimeWindow, roundNumber, timeWindow, isPlaying, opponentName, fieldNumber, isRefereeing, isActivity, activityName, isFree}` (LaufzettelRow.java:49-63). The `refereeing()` factory at lines 156-172 explicitly passes `""` for `opponentName` (line 166). The VO carries no referee-side opponent data — the team-pair information for the refereed match is not in the VO. **The VO must be extended** to carry the two team names of the refereed match (e.g. add `String refereeMatchTeamA, String refereeMatchTeamB` fields, or equivalent shape).

**(c) PrintController passes ALL phases to LaufzettelAssembler** without status-filter. `PrintController.java:259-268` (singleTeamSchedule) and `:340-349` (allTeamSchedules) both pass the unfiltered `phases` list directly to `laufzettelAssembler.assemble(...)`. The assembler iterates all input phases and emits per-phase rows; the multi-phase output is the natural consequence.

### Why ACTIVE-only filter (not ASSIGNED, not PREPARED)

Per O-13 (Brief, user-stated 2026-05-09): the round-order within a phase changes via slot-optimization in the `[PREPARED-with-L2-RoundAssignment, optimize=true completion]` window (DEC-55 D-6 governs the optimizer + activation-guard). ASSIGNED-stage round-order is pre-optimization-final; output rendered in ASSIGNED stage produces technically-WRONG `Runde N` assignments. ACTIVE-stage is the only state guaranteed post-optimization-final per the activation-guard (`!tournament.optimize OR phase.optimized`).

PREPARED has match data (per Phase.java:60 "match-gen completed") but no team-avatar mapping (status PREPARED → ASSIGNED happens at the "assign" step). A team viewing a Laufzettel for a PREPARED phase would see match rows without knowing which team they are. PREPARED is correctly excluded.

ACTIVE-stage is also chronologically BEFORE the actual phase start (per O-14 Brief: chronological start = tournament-start-time + computed timing; gap typically hours), so the operator has time to print + distribute the Laufzettel after activation but before round 1 begins.

### Scope posture

This is a **producer-side fix at three layers** (per memory `feedback_discovery_cycle_resolution_scope_creep.md`):
1. Mustache template `laufzettel.mustache` (template surface for the new playing/refereeing semantics).
2. `LaufzettelRow` VO + `DefaultLaufzettelAssembler` (data layer for the new referee-team-pair fields).
3. `PrintController.singleTeamSchedule()` + `.allTeamSchedules()` (controller layer for the ACTIVE-status filter).

Discovery does NOT prescribe the exact i18n composition pattern for the playing/refereeing strings — Delivery picks (e.g., `"vs " + opponentName` vs. `i18n.format("laufzettel.playing.vs", opponentName)` vs. `"Schiedsgericht: " + teamA + " vs " + teamB` etc.).
