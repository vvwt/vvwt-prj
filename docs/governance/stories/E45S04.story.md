# Story E45S04: Java pre-Reset (tenant + display + timer + draft + infoportal contexts) — drop redundant `tenant_id` WHERE predicates from non-tournament-package DAOs/services; preserve INSERT/UPDATE `tenant_id`-passing temporarily until S05

## User Story

**As a** Tournament Manager developer preparing for the Wave-2 Big-Bang-Reset,
**I want** redundant `tenant_id` WHERE predicates and `tenantId` parameters removed from `tenant`-context bootstrap runners, `locations` queries, `display`/`timer`/`draft` cross-context tenantId references, AND `infoportal.InfoPortalStateDao` predicates,
**so that** the production code is fully aligned with the post-Reset schema BEFORE S05's atomic SQL Reset, while the system remains functional during the S04→S05 window.

---

## Context

S04 mirrors S03's pattern but for the non-tournament-package surfaces in Brief
O-6's audit set:

- **`tenant` context**: `DefaultTenantBootstrapRunner` + `TenantFileRegistry` +
  `TenantFileRegistryDataSourceResolver` + `DefaultLocationDisplayResolver` —
  these manage tenant registration and location-display resolution;
  `tenant_id` references in WHERE clauses for `tenants` / `locations` lookups.
- **`display` context**: `DefaultDisplayOverviewService` carries `tenantId`
  field references (per Brief audit `tenantId` grep hit at
  `display/internal/DefaultDisplayOverviewService.java`).
- **`timer` context**: `TimerDataResponse` carries `tenantId` field; the entity
  passes the tenant via DTO. S04 removes the field where it's a redundant
  passthrough.
- **`tournament.draft`** sub-package: any draft-config-specific DAO predicates
  not covered by S03's `DefaultDraftService` scope.
- **`infoportal.InfoPortalStateDao`**: DEC-50 newly authorizes `info_portal_state`
  tenant_id removal; S04 includes the predicate-removal here. (Brief D-NEW-DEC50
  + DEC-50 authoring — `InfoPortalStateDao` SELECT/UPSERT predicates lose
  `tenant_id` filters; INSERT/UPSERT-side `tenant_id` writes preserved until S05.)

Same DEC-22 + DEC-41 classification rule per surface as S03. Brief H-4 verified
that DAO ITs in these contexts also use per-tenant routing via
`TenantContextTestSupport.bindDefaultTenant()` (or equivalent for tenant-context
itself, which uses its own bootstrap-time DataSource construction in
`DefaultTenantBootstrapRunner`-tests).

## Acceptance Criteria

### Predicate-removal scope (production code, non-tournament-package)

- [ ] **AC-WHERE-PREDICATE-REMOVED-TENANT-CONTEXT [governance]:** In
  `de.vvwt.tm.tenant.internal.*`, `tenant_id` WHERE predicates removed from
  `TenantFileRegistry` / `TenantFileRegistryDataSourceResolver` / `DefaultTenantBootstrapRunner`
  SQL constants where `tenant_id` is a redundant predicate (specifically: queries
  on `locations` table that filter `WHERE tenant_id=?` while running inside
  `TenantContext.bindTenant(...)` scope). Bootstrap-time queries that run BEFORE
  any `TenantContext` is bound (e.g., the initial registry read on the flat
  DataSource) are EXCLUDED — those queries must continue to use `tenant_id` until
  S05 redesigns the bootstrap flow. Story-author classifies each query at
  delivery time; rationale in `impl-report.md`.
- [ ] **AC-DEFAULT-LOCATION-DISPLAY-RESOLVER-PREDICATE-REMOVED [governance]:** `DefaultLocationDisplayResolver` SQL constants drop `WHERE tenant_id=?` from per-tenant-context-resolved location queries. Method signature `tenantId` parameter dropped where the value was sourced solely from `TenantContext.current()`.
- [ ] **AC-WHERE-PREDICATE-REMOVED-DISPLAY [governance]:** `DefaultDisplayOverviewService` `tenantId`-field references removed where the field was used to filter queries inside per-tenant-context scope. The `tenantId` field on the service class itself (if present) is removed; if used in INSERT/UPDATE call paths, those references stay until S06.
- [ ] **AC-WHERE-PREDICATE-REMOVED-TIMER [governance]:** `TimerDataResponse` carries `tenantId` field per Brief audit. If the field is purely DTO-level passthrough (no behavioral predicate use), it stays in S04 (DTO field removal happens at S06 alongside the column drop). If it gates timer-side queries, predicate removed in S04 with surface classification per DEC-41.
- [ ] **AC-WHERE-PREDICATE-REMOVED-DRAFT [governance]:** Any `de.vvwt.tm.tournament.draft.*` SQL with `tenant_id` predicate not covered by S03's `DefaultDraftService` — e.g., draft-config-specific queries on the `draft_config` columns of `tournament` table — removed.
- [ ] **AC-WHERE-PREDICATE-REMOVED-INFOPORTAL [governance]:** `InfoPortalStateDao` SQL constants (SELECT_BY_TOURNAMENT, UPSERT, DELETE_BY_TOURNAMENT, etc.) drop `WHERE tenant_id=?` clauses; method signatures lose `tenantId` parameter where sourced from `TenantContext.current()`. Per DEC-50 authority. INSERT/UPSERT-side `tenant_id` writes preserved until S05.

## Notes

- **Bootstrap-time vs runtime-time predicates**: this is the subtle classification
  in S04. `tenantContext.current()` is null during early bootstrap; queries that
  fire before tenant binding (e.g., `TenantFileRegistry.findAll()` to enumerate
  tenant files at startup) cannot rely on per-tenant routing because no tenant
  is bound yet. S04 must NOT remove `tenant_id` predicates from these — they
  query the flat DataSource and need the column. S05 redesigns this path:
  post-Reset, the flat DataSource has no Flyway-applied schema, so bootstrap
  queries use either (a) a dedicated `tenants` table on a single dedicated
  registry DataSource, or (b) filesystem-driven tenant enumeration. Story-author
  documents the bootstrap-flow assumption in `impl-report.md`.
- **DTO field cleanup deferral**: if `TimerDataResponse` carries `tenantId` as
  pure DTO passthrough (gets serialized, never used as predicate), removing it
  is API-shape change with potential client impact. Defer to S06 alongside
  schema-driven field cleanup.
- **InfoPortalStateDao predicate-removal under DEC-50**: S04 cites DEC-50 in
  `related_decs`; DEC-50 was authored before E45 backlog registration so it is
  available to story-authoring.
- **DEC-23 / DEC-31 governance propagation**: applies post-QA.
