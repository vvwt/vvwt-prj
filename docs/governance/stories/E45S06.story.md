# Story E45S06: Post-Reset Java cleanup — drop `tenant_id` from INSERT/UPDATE statements + drop entity tenantId fields + adapt DAO ITs to per-module schema (DEC-26+DEC-46) + final ApplicationModules.verify() green; closes the DEC-21 §Deploy-pause window opened by S05

## User Story

**As a** Tournament Manager developer completing the Wave-2 Big-Bang-Reset Epic,
**I want** all Java INSERT/UPDATE statements stripped of their now-orphaned `tenant_id` references, all entity `tenantId` field declarations removed, and all DAO ITs re-pointed at the per-module schema paths under DEC-26 + DEC-46 governance,
**so that** the post-Reset system is fully functional (no runtime errors from Java-Schema mismatch), the full test suite is green, and the Epic closes with the system in DEC-20+DEC-25+DEC-39+DEC-50 end-state.

## Context

S05 dropped the `tenant_id` columns from the schema. Between S05 and S06 the
system runs in temporary inconsistency state — INSERT/UPDATE statements in S03/S04-
refactored DAOs still pass `tenant_id` to the now-non-existent column, producing
runtime errors on writes. DEC-21 §Deploy-pause line 148-151 + Brief C-11 explicitly
authorize this transient state given DEC-25's no-production-data invariant
(H-3 verified 2026-05-03).

S06 closes the deploy-pause window:

1. **INSERT/UPDATE column-removal**: every INSERT/UPDATE SQL constant in S03/S04-
   touched DAOs drops its `tenant_id` column reference and corresponding
   parameter binding. Local `tenantContext.current()` invocations that were
   preserved by S03/S04 (used solely for INSERT-side passing) are removed.
2. **Entity `tenantId` field removal**: domain entities that mapped a Java
   `tenantId` field to the schema column (Tournament, Phase, Match, Team,
   SetResult, MatchOutcome, RoundSnapshot, TeamAvatarRating, PhaseBreak,
   ActivityType — now in tournament.activity per S01 — and any service-layer
   classes carrying `tenantId` as a passthrough) lose their `tenantId` field +
   getter/setter + constructor parameter.
3. **DTO field cleanup**: `TimerDataResponse.tenantId` field removed (Brief T-NEW
   from S04 deferral). Any other DTOs carrying `tenantId` as pure passthrough
   removed.
4. **DAO IT schema-source path migration**: ITs that load schema via
   `ScriptUtils.executeSqlScript` against root migration paths (not yet
   redirected by S05's `TenantDaoTestSupport` rewrite) now point to the per-module
   paths.
5. **`InfoPortalStateDao` INSERT cleanup**: per DEC-50, post-S05 the
   `info_portal_state` table has PK `(location_id, tournament_id)`; INSERTs no
   longer pass `tenant_id`.
6. **Final invariants**: `ApplicationModules.verify()` green; full test suite
   green; commit-message-evidence per DEC-27.

S06 commit lands immediately after S05 — no production deploy, no human-in-the-
loop break (per DEC-21 §Deploy-pause).

## Routing-Key vs Column-Discriminator Classification (added cycle-1)

The cycle-0 story conflated two distinct uses of `tenantId` in Java:

1. **Column-discriminator passthrough** — `tenantId` value is read from / written to the
   `tenant_id` schema column. After DEC-39 D1 + DEC-50 dropped these columns at S05, these
   fields are **dead code**: the value has no schema-side anchor and no consumer beyond the
   redundant routing already provided by `AbstractRoutingDataSource`. **REMOVED at S06.**

2. **STOMP-routing-key carrier** — `tenantId` value is part of the **wire-protocol** for
   WebSocket topic derivation (Svelte SPA builds `/topic/display/{tenantId}/events` or
   `/topic/timer/{tenantId}/events` URL from the field). The schema column never gates this;
   the value is sourced from `TenantContext.current()` at the producing service. **PRESERVED**
   — these are not "tenant_id" the column-discriminator; they are tenant-routing-key as a
   wire-protocol-level identifier (analog to `tournamentId` in WebSocket topics).

### Preservation Allowlist (PRESERVED — STOMP-routing-keys)

| Field | Consumer | STOMP topic |
|---|---|---|
| `DisplayPhaseOverviewResponse.tenantId` | display Svelte SPA + timer Svelte SPA | `/topic/display/{tenantId}/events` |
| `TimerDataResponse.tenantId` | timer Svelte SPA | `/topic/timer/{tenantId}/events` (per timerWs.ts) |
| `PhaseStatusChangedEvent.tenantId` | DomainEventBridge → STOMP | `/topic/display/{tenantId}/events` |
| `MatchResultChangedEvent.tenantId` | DomainEventBridge → STOMP | `/topic/display/{tenantId}/events` |
| `LapAdvancedEvent.tenantId` | DomainEventBridge → STOMP | `/topic/display/{tenantId}/events` |

These five fields are EXPLICITLY OUT of S06's removal scope. Source-flow: producing service
invokes `tenantContext.current()` at publish/build time and passes the value to the
event constructor / response builder. No `entity.getTenantId()` calls remain (entities lose
their `tenantId` field in S06 — see Entity field cleanup below).

### Removal Set (REMOVED — column-discriminator passthroughs)

| Class | Removal scope |
|---|---|
| `Tournament`, `Phase`, `Team`, `TeamAvatar`, `TeamAvatarRating`, `Match`, `SetResult`, `MatchOutcome`, `RoundSnapshot`, `PhaseBreak`, `Device` (entities in `de.vvwt.tm.tournament.*`) | `tenantId` field + getter/setter + Spring Data JDBC `@Column("tenant_id")` annotation |
| `ActivityType` in `de.vvwt.tm.tournament.activity` | same |
| `AuditLogEntry` in `de.vvwt.tm.tournament.*` | same |
| `DefaultDisplayOverviewService` | internal `tenantId` field + setter |
| `DefaultDeviceService.setTenantId(...)` setter callers | call removed; setter deleted with entity field |
| `InfoPortalStateRecord` | `tenantId` field |

Note: `MatchResultChangedEvent` and `LapAdvancedEvent` remain in `de.vvwt.tm.tournament.events`
package — these events are in the PRESERVATION allowlist above (NOT removed despite being
listed in cycle-0 story body).

### Event-publisher source-flow updates (events keep tenantId; producers source from TenantContext)

- [ ] **AC-EVENT-PRODUCER-TENANT-CONTEXT-SOURCE [governance]:** All services that publish `MatchResultChangedEvent`, `LapAdvancedEvent`, or `PhaseStatusChangedEvent` source the `tenantId` constructor parameter from `tenantContext.current()` at publish-time (replacing any current `entity.getTenantId()` source). This is necessary because the entity-side `tenantId` field is dropped under AC-ENTITY-TENANT-ID-FIELD-REMOVED. `DomainEventBridge` itself remains UNCHANGED (still calls `event.getTenantId()` to derive the STOMP topic). Verified by `grep -rn 'new MatchResultChangedEvent\|new LapAdvancedEvent\|new PhaseStatusChangedEvent' vvwt-tm-web/src/main/java/` — every constructor call passes `tenantContext.current()` (or a logically equivalent source like a method parameter that was itself sourced from TenantContext).
- [ ] **AC-DOMAIN-EVENT-BRIDGE-UNCHANGED [error-handling]:** `DomainEventBridge.java` is NOT modified by S06 — it continues to call `event.getTenantId()` and `displayTopic(...)`. Forward-compatibility note: if DEC-37's "async event-queue evolutionary option" is ever activated, events already carry `tenantId` in payload — no breaking change required at that future Discovery.
