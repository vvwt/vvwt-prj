# Story E48S14: Bug-Fix — plannedStartTime missing in Tournament-CREATE Multi-Layer

## User Story

**As a** Tournament Organizer,
**I want** the start time I enter when creating a new tournament to be persisted on the very first save,
**so that** I do not have to re-enter it after navigating away from the form and back.

---

## Context

Per Brief D-3 / O-1 / O-2 / O-3 (`discovery-2026-05-06-tournament-form-bugs`): the `plannedStartTime` field is silently dropped from the Tournament-CREATE flow at all four layers — frontend payload, TypeScript interface, Java DTO record, and Java service. Reproduction (User 2026-05-06): "Ich habe ein neues Turnier angelegt und die Start-Zeit eingetragen. Beim Klick auf den Zurück-Pfeil [von Teams] kam ich wieder in das Turnier und die Start-Zeit war leer. Nachdem ich es nochmal eingetragen UND GESPEICHERT habe, blieb die Startzeit gespeichert" — confirms CREATE-only scope.

Empirical layer-by-layer evidence:
- **Svelte CREATE payload** (`vvwt-tm-web/src/main/ui/src/routes/TournamentForm.svelte:125-135`): the `req: TournamentCreateRequest` object literal omits `plannedStartTime`.
- **TS interface** (`vvwt-tm-web/src/main/ui/src/stores/tournamentStore.ts:50-59`): `TournamentCreateRequest` declares `description, appointment, teamCount, fieldCount, matchFormat, scoringRuleId, setValidationRuleId, matchGeneratorId` — no `plannedStartTime`.
- **Java DTO record** (`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/dto/TournamentCreateRequest.java:24-55`): record components mirror the TS interface, without `plannedStartTime`.
- **Java service** (`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/DefaultTournamentService.java:341`): `tournament.setPlannedStartTime(plannedStartTime)` is called in the UPDATE method body (line 307+) — the CREATE method body needs an analogous setter call (Delivery verifies).

The UPDATE path is correct on all four layers (`TournamentForm.svelte:113-124` includes `plannedStartTime`; `TournamentUpdateRequest.java:52` declares it; `DefaultTournamentService` setter at line 341 handles it; TS interface `TournamentUpdateRequest` at `tournamentStore.ts:71` declares it). The fix mirrors the UPDATE pattern into CREATE atomically across all four layers.

Per Brief T-1: Frontend-only fix (sending the field to a backend that ignores it) was rejected because backend MUST validate and persist — data integrity is non-negotiable.
