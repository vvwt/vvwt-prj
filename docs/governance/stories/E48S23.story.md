# Story E48S23: Reset-Phasenplan affordance on Phasen-Übersicht — surface E48S13 reset-plan endpoint via PhaseList.svelte (PLANNED-only visibility)

## User Story

**As a** Tournament Organizer who has just applied a Phasenplan and landed on the Phasen-Übersicht,
**I want** a "Phasenplan zurücksetzen"-button visible directly on this page,
**so that** I can revert a misconfigured tournament back to DRAFT (preserving the saved draft for further editing) without having to remember that the same affordance also lives on the DraftConfig editor route — which I would not naturally re-enter after a successful Apply.

---

## Context

This Story closes the post-Apply discoverability gap left open by E48S13 (PR #207, merged 2026-05-06). E48S13 placed the Reset-Plan button on `DraftConfig.svelte:556` — visible only when `tournamentStatus === 'PLANNED'`. The intended user benefit was "operator returns to edit-context" — but observation O-5 in the Discovery Brief shows the user never re-enters the DraftConfig editor: after Apply, the success view at `DraftConfig.svelte:392-398` renders only an `applySuccess` message + a "Zurück" button (`pop()`), routing the user back to the prior route — typically the Tournaments listing. From there, the "Phasen" navigation goes to PhaseList (the read-only Phasen-Übersicht overview, E48S05) — and PhaseList has no Reset-Plan affordance.

E48S13's own backlog notes flagged this as out-of-scope: *"Phases-overview Reset-Plan entry (T-4 follow-up)"*. This Story IS that follow-up.

Per User-decision B-β=b (Brief T-2), the Reset-Plan button surfaces on **PhaseList** — NOT on the Tournaments listing (which already carries 10+ buttons for PLANNED state). The button reuses the existing E48S13 backend endpoint POST `/api/tournaments/{id}/reset-plan`, the existing `tournamentStore.resetPlan` client (`tournamentStore.ts:230`), and the existing i18n keys at `de.json:182-184` (`draft.resetPlanButton`, `draft.resetPlanConfirm`, `draft.resetPlanError`) — no new backend, no new client function, no new i18n keys.

PhaseList currently has no `tournamentStatus` state — it loads phases via `listPhases()` only. The Story extends PhaseList to also fetch the parent tournament via the existing `tournamentStore.getTournament(id)` (`tournamentStore.ts:136`) so that the button's PLANNED-only visibility predicate can evaluate.

This is a **purely additive FE-only change**: zero backend modification, zero new dependencies, zero existing test breakage. The handler pattern mirrors `DraftConfig.svelte:354-376` line-for-line (typed `apiError.messageKey` extraction with i18n fallback to `draft.error.resetPlanFailed`).

- [ ] **AC-IMPL-RESET-PLAN-HANDLER-MIRRORS-DRAFTCONFIG**: the click handler in `PhaseList.svelte` mirrors `DraftConfig.svelte:354-376` shape:

  - sets a local `resettingPlan` boolean for in-flight UI state;
  - awaits `resetPlan(tournamentId)` from `tournamentStore`;
  - on success: refreshes phases (calls existing `loadPhases()`) AND refetches tournament status (so button hides because status is now DRAFT);
  - on failure: extracts `apiError.messageKey`, renders i18n-resolved error or fallback `draft.error.resetPlanFailed`;
  - `finally`: resets `resettingPlan = false`.
