# Story E18S02: Activate Spotless + google-java-format (AOSP) — project-wide formatting + unused-import removal

## User Story

**As a** maintainer collaborating with multiple Claude Code sessions (potentially multi-model over time),
**I want** every `.java` file in `vvwt-prj` formatted to a single enforced style (Google Java Format AOSP) with zero unused imports,
**so that** code review focuses on semantics rather than style drift, multi-agent code drift is prevented at the build layer, and the 97-unused-import backlog (including the originally-reported `TenantFileRegistryDataSourceResolver.java:6` `SmartDataSource` case) is closed in one atomic reformat.

---

## Context

The codebase contains 97 unused imports (heuristic-measured) across 62 files in 4 modules, and no formatting enforcement. Authorship is spread across multiple Claude Code sessions; without build-time formatting enforcement, style drift is an expected long-tail defect. DEC-30 selects Spotless + google-java-format (AOSP style) and specifies the exact parent-POM configuration, execution phase, and version pins.

Per DEC-22 TDD Iron Law: unused-import removal is deletion, and formatter reflow is non-semantic normalisation; neither is "new production code". No new failing test is required. Existing tests MUST remain green as non-regression evidence — a reformat that breaks a test indicates either a Spotless/google-java-format defect or a subtle edge case (e.g., a test depending on source-file line numbers) that halts the Story.

The first-run `mvn spotless:apply` touches hundreds of files across all 5 modules. This is ONE atomic commit per DEC-30 § Decision #4 — not spread across days — to avoid partial-state where some files are AOSP-formatted and others aren't, and to keep reformat-review cost bounded.

---

## Acceptance Criteria

- [ ] **AC1 (governance — DEC-30 configuration):** Parent POM `de.vvwt:vvwt-prj` gains a `spotless-maven-plugin` configuration inside `<build><pluginManagement><plugins>` and is activated in `<build><plugins>`. The configuration matches DEC-30 § Decision #1 exactly: `<java><googleJavaFormat><version>${google-java-format.version}</version><style>AOSP</style><reflowLongStrings>true</reflowLongStrings></googleJavaFormat><removeUnusedImports/><importOrder/></java>`. Plugin version `${spotless-maven-plugin.version}` = 2.44.x; google-java-format version `${google-java-format.version}` = 1.19.x. Both properties declared in parent POM `<properties>`. Execution `spotless-check` binds to phase `verify` with goal `check`.

- [ ] **AC2 (build — one atomic reformat commit):** Story delivers exactly ONE commit containing the Spotless-apply output — `mvn spotless:apply` run from `vvwt-prj/` root, covering all 5 modules. Commit message format: `chore(E18S02): spotless:apply + remove unused imports [staging]`. The plugin-configuration change (AC1) may live in the same commit or a prior commit within the story branch (Delivery decides; the atomic constraint applies to the reformat content itself — it must not be split).

- [ ] **AC3 (build — spotless check green):** After the reformat commit, `mvn spotless:check` on a fresh checkout of `staging` passes with zero formatting violations. `mvn verify` also passes end-to-end. Evidence: command transcript in the impl-report.

- [ ] **AC4 (governance — original-report closure):** `TenantFileRegistryDataSourceResolver.java` no longer imports `org.springframework.jdbc.datasource.SmartDataSource`. Command evidence: `grep -n "SmartDataSource" vvwt-prj/vvwt-tm-web/src/main/java/de/vvwt/tm/tenant/internal/TenantFileRegistryDataSourceResolver.java` returns zero matches. Traceable closure of the user-reported symptom that triggered the Discovery session.

- [ ] **AC5 (build — unused-import count reported):** After `spotless:apply`, the authoritative removed-import count is measured (e.g., `git diff HEAD~1 -- '*.java' | grep -cE '^-import '` on the reformat commit) and reported in the impl-report alongside the heuristic-measured 97. Acceptable delta: ±15. If the delta is larger (<82 or >112), the impl-report explains the deviation (static imports, Javadoc-referenced symbols, heuristic edge cases).

- [ ] **AC6 (build — forward enforcement is live):** Introduce a deliberate probe — e.g., add `import java.util.UUID;` to any `.java` file that doesn't use `UUID`. `mvn spotless:check` MUST fail with `BUILD FAILURE` (not merely warn). Revert the probe. Evidence: inline terminal transcript in the impl-report OR a probe-then-revert commit pair on the story branch.

- [ ] **AC7 (testing — existing suite green per DEC-22):** All existing tests across the 5 modules pass after the reformat commit. Evidence: `mvn verify` green on fresh checkout of `staging` after merge. The reformat is a non-semantic transformation by construction; any test failure indicates a defect in Spotless/google-java-format or an edge case (e.g., a test depending on source-file layout) and must be reported in the impl-report — not silently fixed by altering the reformat.

- [ ] **AC8 (governance — documentation):** `patterns/conventions.md` "Code Quality" section (introduced by E18S01 or by this Story if E18S01 has not merged yet) gains a "Formatting" subsection that: (a) names Spotless + google-java-format (AOSP) as the active formatting stack; (b) names `mvn spotless:apply` as the canonical local fix command developers run before committing; (c) states that `mvn verify` enforces via `spotless:check`; (d) explicitly states AOSP is chosen over GOOGLE to preserve 4-space indentation; (e) points to DEC-30.

- [ ] **AC9 (governance — no Spotless scope creep):** Spotless configuration contains ONLY `googleJavaFormat` + `removeUnusedImports` + `importOrder`. No license-header rule, no trailing-whitespace rule, no tab-to-space beyond what google-java-format handles implicitly, no custom rule set. Narrow start per DEC-30 § Decision #6. Any addition is a DEC-30 amendment, not an inline config tweak.

## Out of Scope

- Serial-keyset javac warnings (DEC-29 territory, deferred via `-Xlint:-serial`).
- `-Xlint:all` javac activation (Story E18S01).
- GOOGLE style (2-space indent) — rejected in DEC-30 rationale.
- License headers, custom trailing-whitespace / tab-to-space rules, custom import-order variants — deferred per DEC-30 narrow-start.
- Per-module `.java` includes/excludes — if any file must be excluded, it's a DEC-30 amendment, not an inline Spotless config tweak.
- Editor/IDE config files (`.editorconfig`, IntelliJ code style XML) — developers use preferred editors; `spotless:apply` is the canonical normalizer.
- CI pipeline wiring (DEC-21/DEC-22 no-CI fallback).
- Behavioural code changes while reformatting — `spotless:apply` output is deterministic and non-semantic; any apparent behavioural change is a defect.

## Notes

- The ~97 heuristic count is a floor. Actual Spotless removal may differ due to edge cases: static imports where the simple name coincides with a local symbol (heuristic-over-counts as used, Spotless correctly identifies as unused); Javadoc `@link` references (heuristic counts as used, Spotless correctly preserves the import). Empirically this codebase appears to have a low edge-case rate; ±15 variance is expected.
- **Reformat commit is intentionally massive** per DEC-30 § Decision #4. Reviewers focus on (a) the plugin configuration (AC1), (b) AC4 (the original-report closure), (c) AC5 (count sanity), and (d) AC6 (forward-enforcement probe). Line-by-line review of the reformat diff is not expected — `spotless:apply` output is deterministic for a pinned google-java-format version and re-runnable for audit.
- `spotless:apply` is deterministic: re-running it against a formatted codebase produces zero changes. This is the reproducibility guarantee that makes the large commit reviewable.
- **Branch coordination:** user confirmed no open WIP at Brief validation (2026-04-19). If late-breaking WIP appears between Story creation and Delivery, Delivery documents the conflict-resolution strategy (rebase WIP branches post-E18S02, or merge-then-reformat) in the impl-report. Do not silently reformat WIP branches as part of this Story.
- If `mvn spotless:apply` reveals that google-java-format 1.19.x has a bug (e.g., miscompiles a file, produces invalid Java), halt and escalate to Discovery before attempting workarounds. Pinning to an older google-java-format version would be a DEC-30 amendment.
