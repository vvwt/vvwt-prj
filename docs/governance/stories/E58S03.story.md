# Story: Team-sort registry — TeamSortCalculator strategy + AbstractAssignmentProposalCalculator base

## User Story

**As a** tournament organizer,
**I want** the team-sort orders to be selected through the same registry mechanism as match generators and distributors,
**so that** a new sort order can be added as a self-contained class without editing a core branch.

---

## Context

Team sorting today has no registry: `DefaultPhaseTransitionService.computeProposals` branches inline on
`DraftSection.sortType` (a plain `String` — `team_number` / `placement_group` / `group_placement`) when
computing the Phase-2+ team-assignment proposal from the previous phase's ratings. DEC-73 (D-3) extracts this
into a `TeamSortCalculator` strategy interface plus a registry, with an `AbstractAssignmentProposalCalculator`
base for shared proposal-calculation helpers.

This story is behaviour-preserving for the DEC-59 operator-confirmation team-assignment workflow: the same
proposal is computed; only the dispatch mechanism changes.

---

## Acceptance Criteria

- [ ] AC1 (governance): a `TeamSortCalculator` strategy interface exists — a registry-key accessor plus an operation that produces a sorted team list from the participating teams and the optional previous-phase ratings — placed in the bounded-context public package per the DEC-35 layout.
- [ ] AC2 (governance): a `TeamSortCalculator` registry exists, dispatching by string key; the registry and the strategy interface satisfy the DEC-58/DEC-72 interface mandate and the E57S04 build-time guard passes.
- [ ] AC3 (governance): an `AbstractAssignmentProposalCalculator` base type provides the shared proposal-calculation helper(s), placed per the DEC-35 layout.
- [ ] AC4 (testing): three `TeamSortCalculator` implementations exist, one per current sort mode (`team_number`, `placement_group`, `group_placement`); each is registered under its key and resolvable from the registry. Verified by tests authored failing-first per DEC-22.
- [ ] AC5 (testing): the inline `sortType` branching in `DefaultPhaseTransitionService.computeProposals` is replaced by registry dispatch; for all three modes, the observable Phase-2+ proposal output is identical to the current behaviour. The equivalence is verified by fresh RED-first tests that re-specify the proposal semantics — not by a characterization test (forbidden by DEC-22).
- [ ] AC6 (governance): `DraftSection.sortType` is validated as a registry-membership check against the `TeamSortCalculator` registry, fail-fast in the `DraftConfig` / `DraftSection` validation path (replacing today's hardcoded string-set check); an unregistered `sortType` key is rejected with an operator-actionable error at draft save/apply. Verified by test.
- [ ] AC7 (testing): Delivery first verifies, at delivery HEAD, whether any existing `TeamAvatarRatingRepository` method already performs a by-phase rating lookup. If one exists, it is used and no new method is added. If none exists, `TeamAvatarRatingRepository` gains a `findByPhaseId(UUID)` read method, and it has a named production (non-test) callsite — the proposal-computation code path that loads the previous phase's ratings and supplies them to `TeamSortCalculator` (per DEC-69, a public repository read method MUST have a production callsite and MUST NOT be test-only). The by-phase lookup that is added or reused is covered by a DAO integration test following the DEC-46 three rules: schema loaded from the production migration; written state verified independently via assertj-db; read-path fixtures inserted via direct JDBC, never via the DAO's own write methods.
- [ ] AC8 (testing): TDD per DEC-22 — every new class and method has a failing test authored before the production code.
- [ ] AC9 (governance): `mvn verify` is BUILD SUCCESS for `vvwt-tm-web` (DEC-54); no new compiler warnings or unused imports (DEC-29 / DEC-30).
- [ ] AC10 (governance): the DEC-59 operator-confirmation team-assignment workflow is behaviour-unchanged — the `TeamSortCalculator`-driven proposal computation produces the same proposal; `teamId` is written only by the operator-confirmation handler, not by any `TeamSortCalculator` implementation or the proposal-computation path. Verified by test.

> All acceptance criteria must be verifiable.
