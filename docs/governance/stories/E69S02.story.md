# Story: Operator runbook for building, flashing, and verifying a venue display Pi

## User Story

**As a** tournament operator preparing the venue,
**I want** a single document that walks me from a freshly-cloned
`vvwt-prj` checkout to a Raspberry Pi 4 mounted on a venue monitor
showing the TM Display registration page,
**so that** I can deploy any number of display devices without having
to read FullPageOS upstream docs, RaspiOS docs, and project source code
to figure out the sequence.

---

## Context

E69S01 ships the build-script and Maven module that produce a flashable
FullPageOS-based image. E69S02 ships the **operator-facing instructions**
that turn the build script into a deployment workflow: image build, SD
flash, WiFi-credential provisioning (the operator chooses between two
paths), boot verification, and the watchdog / splash-on-no-network
attestation protocols defined by the Brief.

The Brief (D-6, T-4, S-9; Mustache-score-tablet precedent — memory
`project_scoring_tablet_test_surface.md`) is clear that actual image
build / SD flash / on-device boot tests are **operator-runbook steps**,
not delivery acceptance criteria. The verification surface for this
story is therefore the runbook's **completeness and correctness as a
written document** (markdown lints, link checks, content-anchored
greps in bats tests) — not whether an actual Pi boots and shows the
register page. The latter is the operator's job at venue setup; the
runbook makes that job routine.

The runbook documents two WiFi-provisioning paths that the operator
chooses between at flash time (Brief D-5, T-9, H-3):

1. **RaspiOS Imager (`rpi-imager`) headless-config** — credentials are
   injected into the rootfs at flash time and never appear on the FAT32
   partition. License Apache-2.0, AGPL-forward-compatible per the FSF
   matrix (Brief O-9).
2. **`/boot/firmware/wpa_supplicant.conf`** — operator writes the file
   directly on the FAT32 partition after flashing. Plaintext credentials
   are readable by anyone with the SD card in hand. Operator-supervised
   physical security is the trust assumption.

The watchdog / splash-on-no-network attestation protocol (Brief D-7-a,
S-2) walks the operator through three observable scenarios at
provisioning time — `pkill chromium-browser`, ethernet unplug, and a
TM server 5xx — and records the upstream FullPageOS behaviour for the
pinned tag (`0.14.0`). If a scenario reveals a gap, the runbook
explicitly instructs the operator to **stop and escalate to a new
story** (Brief D-7-b for watchdog, S-2 for splash) — never to author
fixes inline.

The runbook is **English** (Brief C-8, Q-5 — base.rules § Language
Rule, even though the operator is German-speaking). Operator-facing
language consistency is a project-wide governance rule, not a
preference.

## Acceptance Criteria

- [ ] **AC1 [runbook coverage — Build]:** `vvwt-prj/pi-display/README.md`
  contains a **Build** section that walks an operator from a fresh
  `vvwt-prj` clone to a working `.img` file. The section names
  (a) the upstream prerequisites (Docker or Linux + qemu — per
  upstream FullPageOS README), (b) the exact `build-image.sh`
  invocation including the recommended args (e.g.
  `./build-image.sh --server-url=https://your-tm-host/`),
  (c) the expected output `.img` path and approximate size, and
  (d) the SHA256 / how to verify the build matches.
- [ ] **AC2 [runbook coverage — SD Flash]:** A **Flash** section
  documents (a) the recommended tool (`rpi-imager`; Apache-2.0,
  AGPL-forward-compatible), (b) the operator-choice between the two
  WiFi-provisioning paths described in the Context section above,
  with the security posture of each spelled out, (c) for path 1, the
  exact `rpi-imager` headless-config field names to set (WiFi SSID,
  password, country code; **never** committing them to the repo);
  (d) for path 2, the exact `/boot/firmware/wpa_supplicant.conf` file
  template with placeholder values (and an explicit note that the
  file is plaintext-readable from any computer holding the SD).
- [ ] **AC3 [runbook coverage — Boot Verification]:** A **Boot &
  Verify** section documents the expected boot sequence on first
  power-on: (a) Pi joins WiFi within ~30 s; (b) Chromium opens
  fullscreen at the URL from `/boot/fullpageos.txt`; (c) if that URL
  resolves to the TM server's `/display/register` route, the page
  shows the `DisplayRegisterPage.svelte` token; (d) operator opens
  the TM admin Devices page and finds the pending display under the
  display-devices filter; (e) operator configures the device per the
  existing E07 admin flow. The expected screenshot or text content
  for each step is described in words sufficient for the operator to
  decide pass/fail without reading source.
- [ ] **AC4 [runbook coverage — Watchdog Attestation Protocol —
  Brief D-7-a]:** A **Watchdog Attestation** section walks the
  operator through three scenarios on a freshly-provisioned Pi:
  (i) `pkill chromium-browser` from SSH on the Pi and observe
  systemd respawn within ~5 s; (ii) unplug the network cable (or
  block WiFi at the router) and observe the upstream FullPageOS
  splash / fallback within ~30 s; (iii) point the kiosk URL at a TM
  test server returning HTTP 5xx and observe the chromium-side
  behaviour. For each scenario the runbook records (a) the expected
  upstream-FullPageOS outcome at tag `0.14.0`, (b) the actual outcome
  field for the operator to fill in, (c) the explicit escalation
  instruction: **if outcome ≠ expected, stop and open a new story
  per Brief D-7-b — do not author systemd drop-ins inline**.
- [ ] **AC5 [runbook coverage — Splash-on-No-Network Attestation —
  Brief S-2]:** A **Splash Attestation** section similarly walks the
  operator through verifying that upstream FullPageOS displays a
  visible splash (not a blank screen) when the server is unreachable.
  The same escalation contract applies: if a visible splash is
  absent, **stop and open a new story per Brief S-2 — do not author
  an HTML fallback page inline**.
- [ ] **AC6 [runbook coverage — Known Limitations]:** A **Known
  Limitations** section explicitly records: (a) Pi-3 rendering
  performance is not validated this pass (Brief D-3, T-5); (b)
  FullPageOS release cadence is irregular (tags typically 1–2+
  years apart historically — Brief O-7) and tag bumps are separate
  stories per Brief D-9; (c) `wpa_supplicant.conf` on FAT32 is
  plaintext-readable; (d) Pi-side identity is anonymous — the
  server-side device-token is the sole means of distinguishing
  displays.
- [ ] **AC7 [runbook coverage — License Attestation]:** A
  **Licensing** section records (a) `vvwt-prj` license:
  AGPL-3.0-or-later per DEC-75 (with copyright holder per DEC-75
  §D3); (b) FullPageOS upstream: GPL-3.0, AGPL-forward-compatible
  per the FSF matrix; (c) `rpi-imager`: Apache-2.0, AGPL-forward-
  compatible; (d) the transitive RaspiOS Bookworm / chromium-browser
  / systemd / openbox dependencies as a list with their SPDX
  identifiers and the AGPL-forward-compatibility statement.
- [ ] **AC8 [SPDX header — DEC-75 §D6]:** `pi-display/README.md`
  carries an SPDX comment header
  `<!-- SPDX-License-Identifier: AGPL-3.0-or-later -->` (or
  equivalent markdown-safe form). A bats test under
  `pi-display/src/test/sh/` greps for the header on the file and
  fails if it is missing.
- [ ] **AC9 [testing — content-anchored greps — DEC-22 RED-first]:**
  Bats tests under `vvwt-prj/pi-display/src/test/sh/readme.bats`
  (or equivalent) author the RED state for runbook completeness:
  each section (Build, Flash, Boot & Verify, Watchdog Attestation,
  Splash Attestation, Known Limitations, Licensing) is asserted
  present via a grep for its anchor heading; AC8's SPDX header is
  asserted; the two escalation instructions (Brief D-7-b and
  Brief S-2) are asserted present as literal grep targets. Each
  test fails against an empty or partial `README.md` and passes
  after the document is authored.
- [ ] **AC10 [governance — `mvn verify` end-to-end]:** A
  whole-reactor `mvn verify` from the project root continues to
  BUILD SUCCESS and the integration-test phase log shows the bats
  invocation passing both AC9's `readme.bats` and E69S01's
  `build-image.bats`. The DEC-54 gate covers both stories'
  shell-test surfaces uniformly via the `exec-maven-plugin`
  binding E69S01 established.
- [ ] **AC11 [error-handling — escalation contract is the only
  remediation path]:** The runbook contains **no instructions** to
  author systemd drop-ins, HTML fallback pages, or any other
  in-runbook code changes. Both escalation instructions (AC4-c,
  AC5) point to the new-story protocol per the Brief. A bats
  assertion enforces the absence of forbidden literal strings
  (e.g. `systemctl edit`, `nano /etc/systemd`) inside the runbook
  body, treating their presence as a regression.

## Out of Scope

- **Authoring new systemd drop-ins** or **HTML fallback pages** if
  upstream FullPageOS gaps emerge during operator attestation — both
  escalate to new stories per Brief D-7-b and S-2.
- **FullPageOS tag bumps** beyond `0.14.0` — separate stories per
  Brief D-9.
- **A first-boot WiFi AP setup wizard on the Pi** — Future-Work
  (Brief S-6).
- **Auto-update / remote management** — Future-Work (Brief S-7).
- **German translation** of the runbook — base.rules § Language Rule
  + Brief C-8 + Q-5 require English for governance artefacts.
- **Pi-3 rendering-performance validation** — explicitly listed as a
  Known Limitation (AC6), not as a fix target.

## Notes

`README.md` is a markdown document; the bats test surface is content-
anchored grep rather than markdown rendering — Delivery may opt to
add a markdownlint binding as a tightening if the upstream churn or
copy-edits show drift, but the RED-first contract here is the
grep-able section anchors named in AC9, not styling.

Operationalizes Brief D-6 (operator-runbook scope), D-7 (watchdog
upstream verify + escalation), D-9 (tag-bump protocol), S-2 (splash
escalation), S-9 (runbook DOC-only), S-10 (SPDX header), C-7
(WiFi-creds posture documentation), C-8 + Q-5 (English).

Brief Q-1 (CRLF tolerance) is exercised end-to-end here: AC2's
`wpa_supplicant.conf` template note explicitly tells the operator
that LF and CRLF line endings both work — covers the FAT32-edit-from-
Windows-Notepad case the project's operator base actually hits.
