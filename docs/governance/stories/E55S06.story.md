# Story E55S06: Migration — relocate apply-orchestration to phaselifecycle + remove obsolete Spring event-driven beans + cascade re-wiring (Option C — DDD-clean dependency direction)

## User Story

**As a** Tournament Manager developer (Delivery Agent),
**I want** the apply-orchestration entry-point relocated from tournament to phaselifecycle (controllers in `web` call phaselifecycle's new `DraftApplicationOrchestrator`, which calls tournament's existing `DefaultDraftService.apply()` for phase+avatar persistence and then enqueues job-rows itself), AND the obsolete event-driven beans (`SlotOptJobScheduler`, `SlotOptFifoDispatcher`, `SlotOptInvocationListener`, `MatchGenJobListener`, `MatchGenJobExecutor`'s `@Async` public surface, `JobQueueRecoveryService`) removed, AND the auto-invalidation cascade (DEC-55 D-7) re-wired to enqueue job-rows instead of re-publishing events,
**so that** the slot-opt + match-gen pipeline runs ONLY via the new Saga-Orchestrator path; no Spring `@TransactionalEventListener(AFTER_COMMIT) + @Async + @Transactional(REQUIRES_NEW)` survives in the pipeline; the Modulith dependency direction `phaselifecycle → tournament` is preserved (no cycle); DEC-64 D-1/D-5/D-7/D-11/D-12 are operationally realized.

## Context

### 2026-05-12 refinement (after first attempt failed) — architectural defect resolved

The first authoring of this Story (2026-05-11) implicitly assumed tournament's `DefaultDraftService.apply()` could directly call `phaseLifecycleJobRepository.enqueueJob(...)`. The Delivery Planning Sub-Agent (2026-05-12) caught the defect:

```
tournament/package-info.java: @ApplicationModule(allowedDependencies = {"tenant"})
phaselifecycle/package-info.java: allowedDependencies = {"tournament", "slotopt", "tenant"}
```

`tournament` CANNOT import `phaselifecycle` (one-way dependency by Modulith contract; DEC-21 mandates `ApplicationModules.verify()` green). The original AC formulation violated DEC-21 boundary semantics.

The Delivery `claude -p` subprocess died after generating the execution plan (no impl-report/qa-report on disk, no commits on `story/E55S06` branch — verified via daemon's DEC-51 Clause G post-exit-gate that wrote `chore(E55S06): failed [daemon-post-exit-gate]` correctly per DEC-47 evidence-gate). User-validated 2026-05-12 to fix the Discovery defect via Option C (relocate apply-orchestration to phaselifecycle), the DDD-cleanest of the three options surfaced (A=direct-JdbcTemplate-cross-module, B=hexagonal-port-in-tournament, C=relocate-orchestration-entry-point).

### Option C architecture

- **Web controllers** (already in `de.vvwt.tm.web` module per DEC-40, which has access to phaselifecycle by virtue of being the primary-adapter module) call `phaselifecycle`'s new `DraftApplicationOrchestrator.applyDraft(tournamentId, config)` instead of `tournament.DraftService.apply(...)` directly.
- **`phaselifecycle.DraftApplicationOrchestrator`** (new interface in module-root) — entry-point for the apply-and-orchestrate workflow:
  1. Calls `tournament.DefaultDraftService.apply(tournamentId, config)` — existing service, allowed direction `phaselifecycle → tournament` per phaselifecycle's `allowedDependencies = {"tournament", ...}`. Returns the created phase IDs.
  2. For each created phase ID, calls own `phaseLifecycleJobRepository.enqueueJob(...)` to insert a job row.
  3. (Optionally) triggers an immediate drain via `JobDrainService.drainNext(tournamentId)` so the worker doesn't wait for the next poll cycle.
- **`tournament.DefaultDraftService.apply()`** is retained but **stripped of the event-publication step (d3)** — replaces `eventPublisher.publishEvent(new MatchGenJobScheduledEvent(...))` with a NO-OP (or removes the loop entirely). The remainder of `apply()` (phase persistence step (d), avatar persistence step (d2) per DEC-55 D-1, draft_json step (e), `markPlanned` step (f) per DEC-35) is preserved unchanged. The method's return value (List<UUID> of created phase IDs) is preserved — the new orchestrator consumes it.

### Bean removals (unchanged from initial scope)

DEC-64 D-5 lists the Spring events to REMOVE:
- `MatchGenJobScheduledEvent` — no longer published anywhere.
- `SlotOptJobScheduledEvent` — no longer published anywhere.
- `OptimizePhaseRequestedEvent` — no longer published anywhere.
- `SlotOptJobCompletedEvent` — no longer published anywhere.

Bean classes to DELETE:
- `SlotOptJobScheduler` (event listener for SlotOptJobScheduledEvent + SlotOptJobCompletedEvent).
- `SlotOptFifoDispatcher` (publisher of OptimizePhaseRequestedEvent).
- `SlotOptInvocationListener` (event listener for OptimizePhaseRequestedEvent).
- `MatchGenJobListener` (event listener for MatchGenJobScheduledEvent).
- `MatchGenJobExecutor` — `@Async` public surface removed; internal compute logic moves into a helper invoked by the new orchestrator OR deleted entirely if no callers remain (Delivery picks).
- `JobQueueRecoveryService` (event listener for ApplicationReadyEvent per DEC-55 D-8) — superseded by orchestrator's built-in recovery path (DEC-64 D-7).

### Auto-invalidation cascade (DEC-55 D-7 preserved with re-wired enqueue)

The auto-invalidation cascade for `PhaseInputsChangedEvent` (or its current equivalent in `DraftController.apply()` re-apply path) continues to delete dependent rows (FK CASCADE per DEC-55 D-7) and re-trigger preparation — but the re-trigger uses `phaseLifecycleJobRepository.enqueueJob(...)` rather than `eventPublisher.publishEvent(new MatchGenJobScheduledEvent(...))`. The re-wire happens inside `DraftApplicationOrchestrator` (or a dedicated cascade-invocation helper inside phaselifecycle), invoked by the same upstream trigger.

`PhaseInputsChangedEvent` (if used) is PRESERVED as a domain event for informational purposes (UI broadcast / audit). It does NOT drive the orchestrator workflow.

### Surviving events

- `PhaseStatusChangedEvent` — PRESERVED. Published by `PhaseLifecycleService.transition()` for STOMP UI broadcast (DEC-55 D-9 + DEC-64 D-13). DomainEventBridge forwarder retained.
- `PhaseInputsChangedEvent` (if used in current code) — PRESERVED as informational. Does NOT drive workflow.

### Backward-compat: `SlotOptimizationJobRegistry.getHandle()`

`SlotOptimizationJobRegistry` (E27S02) becomes obsolete as a `ConcurrentHashMap<UUID, JobHandle>` queue substrate, but its `getHandle(tournamentId)` consumer API is reimplemented to read from the DB queue (`SELECT … FROM phase_lifecycle_job WHERE tournament_id=? AND status='RUNNING' ORDER BY sequence ASC LIMIT 1`). Cancel controller + status-polling endpoint preserve their wire contracts per DEC-64 D-6 + D-13.

## Acceptance Criteria

### Apply-orchestration relocation (Option C core)

- [ ] **AC-IMPL-DRAFT-APPLICATION-ORCHESTRATOR-INTERFACE**: New public interface `de.vvwt.tm.phaselifecycle.DraftApplicationOrchestrator` declared in phaselifecycle module-root with method `List<UUID> applyDraft(UUID tournamentId, DraftConfig config)`. Default implementation `de.vvwt.tm.phaselifecycle.internal.DefaultDraftApplicationOrchestrator` with `@Service` annotation + Spring DI of `tournament`-owned `DraftService` (via the existing public interface) and `phaselifecycle`-owned `PhaseLifecycleJobRepository` + `JobDrainService`.
- [ ] **AC-IMPL-DRAFT-APPLICATION-ORCHESTRATOR-WORKFLOW**: `DefaultDraftApplicationOrchestrator.applyDraft(tournamentId, config)` executes in a single `@Transactional` boundary:
  1. Calls `tournament.DraftService.apply(tournamentId, config)` — existing service, returns `List<UUID>` of created phase IDs (allowed direction `phaselifecycle → tournament`).
  2. For each `(phaseId, draftSection)` pair: invokes `phaseLifecycleJobRepository.enqueueJob(new PhaseLifecycleJob(..., section.getGameMode(), sequence))` to insert a PENDING row.
  3. Triggers an immediate drain hint via `jobDrainService.drainNext(tournamentId)` (best-effort; if the worker is idle, this primes it; if it's busy, the new row will be picked at the next tick).
  4. Returns the list of phase IDs to the caller (controller).
- [ ] **AC-IMPL-CONTROLLER-REWIRED-TO-PHASELIFECYCLE**: `de.vvwt.tm.web.draft.DraftController` (or whichever web-module controller currently invokes `DraftService.apply()`) is updated to inject + invoke `DraftApplicationOrchestrator.applyDraft(...)` instead of `DraftService.apply(...)` directly. The controller's REST contract (request body, response shape, HTTP status codes) is UNCHANGED (DEC-64 D-13 wire-contract preservation).
- [ ] **AC-IMPL-DRAFTSERVICE-APPLY-EVENTS-STRIPPED**: `tournament.DefaultDraftService.apply()` retains all current steps (a/b/c/d/d2/e/f per DEC-55 D-1 + E48S22 markPlanned) EXCEPT step (d3) — the `eventPublisher.publishEvent(new MatchGenJobScheduledEvent(...))` for-loop is REMOVED. The method's return value (`List<UUID>` of created phase IDs) is preserved. The `ApplicationEventPublisher` field is REMOVED if no other event publications remain in the class.
- [ ] **AC-TEST-CONTROLLER-CALLS-PHASELIFECYCLE-RED** (testing): RED-first IT — invokes `POST /api/tournaments/{tid}/draft/apply` (or current equivalent); asserts (a) `DraftApplicationOrchestrator.applyDraft(...)` is invoked once, (b) `tournament.DraftService.apply(...)` is invoked once (inside the orchestrator), (c) post-state has `phase_lifecycle_job` PENDING rows for each phase, (d) `MatchGenJobScheduledEvent` is NOT published (Mockito spy or `ApplicationEventPublisher` verification). Test fails before controller re-wiring lands.
- [ ] **AC-TEST-ORCHESTRATOR-APPLY-ENQUEUES-N-JOBS-RED** (testing): RED-first IT directly invoking `DraftApplicationOrchestrator.applyDraft(...)` with a 3-phase DraftConfig; asserts (a) 3 rows in `phase_lifecycle_job` with `status='PENDING'`, (b) sequences 1, 2, 3 mapped correctly, (c) `game_mode` column carries each section's gameMode, (d) `MatchGenJobScheduledEvent` is NOT published. Test fails before orchestrator wiring lands.

### Auto-invalidation cascade re-wiring

- [ ] **AC-IMPL-AUTO-INVALIDATION-CASCADE-RE-WIRED**: DEC-55 D-7 auto-invalidation cascade (triggered by re-apply of DraftConfig with changed phases) re-wires its re-trigger path: instead of `eventPublisher.publishEvent(new MatchGenJobScheduledEvent(...))` per invalidated phase, it calls `phaseLifecycleJobRepository.enqueueJob(...)` per invalidated phase (or invokes `DraftApplicationOrchestrator` for re-apply, which performs the enqueue uniformly). The deletion-of-dependent-rows logic (matches, avatars, ratings) + FK CASCADE behavior remain unchanged.
- [ ] **AC-TEST-AUTO-INVALIDATION-CASCADE-RED** (testing): RED-first IT — apply a 3-phase DraftConfig, wait for all jobs to complete; then re-apply with a changed phase 2 gameMode; assert (a) phases 2 and 3 are invalidated (matches+avatars deleted via FK CASCADE), (b) 2 new `phase_lifecycle_job` rows are enqueued for phases 2 and 3 with `status='PENDING'`, (c) `MatchGenJobScheduledEvent` is NOT published, (d) the orchestrator picks up the new rows and completes them.
