# Story: `vvwt-prj/pi-display/` module + FullPageOS overlay build script bound to `mvn verify`

## User Story

**As a** tournament operator,
**I want** a repeatable shell-script build that produces a flashable
FullPageOS-based kiosk image whose Chromium opens at the TM Display
registration URL,
**so that** I can prepare any number of venue display Pis from one signed
recipe without hand-crafting a custom image each time.

---

## Context

The Display Overview SPA lifecycle on the server side is already complete
(Epic E07: `DisplayViewController.java:89` exposes `GET /display/register`
as a public path, `DisplayRegisterPage.svelte` runs the
CHECKING → REGISTERING → WAITING state machine, the admin Devices page
configures pending displays). What is missing on the Pi side is a turnkey
image whose Pi boots, joins WiFi, and opens Chromium fullscreen at the TM
server's `/display/register` URL.

The Discovery Session Brief (`discovery-2026-05-25-raspberry-pi-display-
kiosk-provisioning`, human-validated 2026-05-25 after two review cycles)
chose FullPageOS (https://github.com/guysoft/FullPageOS, GPL-3.0, pinned
to release tag `0.14.0`) as the image base over four steel-manned
alternatives — pi-gen-from-scratch, Anthias, `rpi-imager`-headless, and
Buildroot/Yocto. The choice reduces project-authored kiosk-stack code by
60–80 %: FullPageOS ships Chromium-autostart via an openbox session,
`/boot/fullpageos.txt` as the kiosk-URL config path, and a connection-loss
splash. The project owns only the configuration overlay, the build wrapper,
and the operator runbook (the runbook is split out into story E69S02).

This story creates the Maven module that holds those artefacts and binds
their shell-test suite to the canonical `mvn verify` build gate. Per the
Brief's F-6+F-7 structural resolution (user-direction 2026-05-25), the
module enters the Maven reactor with `packaging=pom` and uses
`exec-maven-plugin` to invoke `shellcheck` and `bats-core` during the
`integration-test` phase — so DEC-54 (`mvn verify` exit-zero canonical
gate) applies to the pi-display surface automatically. No qa-review skill
amendment and no DEC-67 carve-out is invoked. DEC-22 (RED-first Iron Law)
applies to the shell scripts: every behaviour must be authored with a
failing bats test first.

`build-image.sh` is a wrapper, not a re-implementation: it clones the
upstream FullPageOS repository at the pinned tag and applies a
project-local stage that bakes the kiosk URL default (defaulting to
empty — operator fills it post-flash by editing the FAT32 `/boot`
partition) and an optional `vvwt-display` branding configuration file
into the resulting `.img`. Image building requires the operator to run
`build-image.sh` on a Linux host with Docker/qemu set up per the upstream
FullPageOS README — this is documented in the runbook (E69S02), not in
this story's ACs.

The test surface for this story is shell-level only: shellcheck
cleanliness, CLI surface (e.g. `--help` exits zero with usage), tag-pin
enforcement (refuses to build against any FullPageOS ref other than the
pinned tag without an explicit override flag), and a fixture-based
`--dry-run` mode that exercises the overlay logic without actually
fetching or building anything. Actual image build, SD flash, and on-Pi
boot are operator-runbook steps (E69S02) — the Mustache-score-tablet
precedent (memory `project_scoring_tablet_test_surface.md`) is the
governing pattern.

## Acceptance Criteria

- [ ] **AC1 [module-foundation]:** `vvwt-prj/pi-display/` exists as a new
  top-level folder containing a `pom.xml` with `packaging=pom` (no
  `src/main/java`, no Java compilation). The parent POM
  (`vvwt-prj/pom.xml`) lists `pi-display` in its `<modules>` element so
  the reactor includes it. `mvn -pl pi-display -am verify` and the
  whole-reactor `mvn verify` both BUILD SUCCESS.
- [ ] **AC2 [build-gate-binding — DEC-54]:** The `pi-display/pom.xml`
  binds `shellcheck` and `bats-core` invocations to the Maven
  `integration-test` phase via the `exec-maven-plugin` (or equivalent
  Apache-2.0/MIT-licensed Maven plugin). A failing bats assertion
  produces a non-zero exit from `mvn verify` (DEC-54 §"Verdict semantics"
  binary-on-exit invariant preserved). A failing `shellcheck` finding
  on any authored shell script under `vvwt-prj/pi-display/` likewise
  fails the phase.
- [ ] **AC3 [build-image.sh shell shape — DEC-22 RED-first]:**
  `vvwt-prj/pi-display/build-image.sh` exists and exposes a CLI with at
  minimum: `--help` (prints usage, exits zero), `--dry-run` (exercises
  the overlay logic against a checked-in fixture without fetching
  FullPageOS or producing an `.img`), and `--server-url` (optional;
  when supplied, is baked as the default kiosk URL into
  `/boot/fullpageos.txt` in the resulting image; when omitted, the file
  is created empty for the operator to fill post-flash). The script
  pins FullPageOS to tag `0.14.0` and refuses any other ref unless an
  explicit `--fullpageos-tag` override flag is supplied (the override
  is intended for tag-bump stories, not casual operator use).
- [ ] **AC4 [tests — DEC-22 RED-first]:** Bats tests live under
  `vvwt-prj/pi-display/src/test/sh/build-image.bats` (or equivalent
  bats convention) and cover at minimum: (a) `shellcheck` against
  `build-image.sh` and any other authored shell file in the module
  emits zero findings; (b) `build-image.sh --help` exits zero and the
  output contains the literal strings `--server-url` and `--dry-run`;
  (c) `build-image.sh --dry-run` (with no other args) exits zero and
  produces the overlay-fixture artefacts (e.g. a temp-dir with
  `boot/fullpageos.txt` and `boot/firmware/vvwt-display/branding.conf`)
  matching expected content; (d) `build-image.sh --dry-run
  --server-url=https://tm.example.test/` produces a temp-dir where
  `boot/fullpageos.txt` contains exactly `https://tm.example.test/`;
  (e) tag-pin enforcement: invoking `build-image.sh
  --fullpageos-tag=devel` is rejected non-zero unless a separate
  override-confirmation flag is also supplied. Each test fails against
  the pre-story code and passes after.
- [ ] **AC5 [security — WiFi-creds posture documented]:** The
  module's `README.md` (full operator runbook is E69S02) contains a
  stub `Security Notes` section documenting that
  (i) WiFi credentials placed in `/boot/firmware/wpa_supplicant.conf`
  live in plaintext on a FAT32 partition that any computer can read by
  inserting the SD card — operator-supervised physical security is the
  trust assumption; (ii) the alternative is the RaspiOS Imager
  headless-config path, which injects credentials into the rootfs
  (not the FAT32 partition) at flash time. Both paths are summarized;
  the full procedural detail is in E69S02. No credentials of any kind
  are committed under `pi-display/`.
- [ ] **AC6 [SPDX licensing — DEC-75 §D6]:** Every authored shell file
  under `vvwt-prj/pi-display/` and the `pi-display/pom.xml` carries a
  comment header containing
  `SPDX-License-Identifier: AGPL-3.0-or-later`. The bats test suite
  asserts this header is present on `build-image.sh` (a grep
  assertion); the assertion fails on a stripped header. The
  attestation that FullPageOS GPL-3.0 is AGPL-forward-compatible per
  the FSF compatibility matrix is recorded inline as a comment in
  `build-image.sh` near the upstream-clone block.
- [ ] **AC7 [error-handling — explicit failure modes]:** The script
  exits non-zero with an actionable English message in each of these
  cases (bats-tested per AC4 where automatable; runbook-attested in
  E69S02 where the failure mode requires real network / disk): (i)
  invoked without `--dry-run` on a host that lacks the upstream
  FullPageOS build prerequisites (the script does a pre-flight check
  for the required tools and fails fast); (ii) `--server-url`
  argument is not a syntactically valid URL (validated via a simple
  regex / `printf`-and-grep, not via a network call); (iii)
  `--fullpageos-tag` is set to a value that does not exist upstream
  (only checked when not in `--dry-run`).
- [ ] **AC8 [governance — reactor and `mvn verify` end-to-end check]:**
  After this story merges to `staging`, a clean checkout +
  `mvn verify` from the project root completes BUILD SUCCESS and the
  Maven log shows the `exec-maven-plugin` invocation that ran the bats
  suite (a content-anchored grep on the log for the literal string
  `bats` or the equivalent plugin marker). DEC-54 surfaces the gate
  uniformly across the reactor; the verify in `qa-review` discovers
  no separate harness because there is none — the canonical `mvn
  verify` is the single source of truth.
- [ ] **AC9 [governance — RED-first attestation per DEC-22]:** The
  impl-report records, for each behaviour added in AC3/AC4/AC6/AC7,
  the commit hash at which the bats test was added (RED) and the
  commit hash at which the corresponding `build-image.sh` change
  turned it green. Reconstruction-in-place is the canonical Maven
  pattern; here the same discipline applies to shell-script
  authoring — the script does not preexist this story.

## Out of Scope

- **Operator runbook contents** — image-build invocation steps, SD-flash
  procedure, WiFi-options walkthrough, boot verification, watchdog
  attestation protocol, splash-on-no-network attestation, known-
  limitations section. All these belong to E69S02 (`pi-display/README.md`
  full content). This story ships only the stub `Security Notes` section
  required by AC5.
- **Actual FullPageOS image building / SD-flashing / on-device boot
  testing** — operator-runbook steps (E69S02), Mustache-score-tablet
  precedent (memory `project_scoring_tablet_test_surface.md`).
- **In-story authoring of new systemd drop-ins** if the runbook
  attestation later reveals an upstream FullPageOS watchdog gap —
  escalated to a separate story (Brief D-7-b).
- **In-story authoring of an HTML fallback page** if the runbook
  attestation later reveals an upstream FullPageOS splash-on-no-network
  gap — escalated to a separate story (Brief S-2).
- **FullPageOS tag bumps** beyond `0.14.0` — separate stories (Brief
  D-9), each carrying their own runbook re-execution as the regression-
  safety equivalent.
- **Server-side changes in `vvwt-tm-web`** — already shipped by E07.

## Notes

The pinned FullPageOS tag (`0.14.0`) and the AGPL forward-compatibility
attestation are recorded in `build-image.sh` as comments (not in a
separate manifest file) — Delivery may choose to refactor the
attestation into a dedicated `LICENSE-ATTESTATION.md` if the inline
comment grows beyond ~10 lines, but for V1 inline is sufficient.

Brief Q-1 (operator-friendly UTF-8 LF with CRLF tolerance) applies to
the `/boot` text files the build script emits — the bats tests under
AC4 verify the line endings of the emitted fixture files are LF; CRLF
tolerance is exercised by the runbook (E69S02), not here.

Brief D-9 establishes the project convention that tag bumps are
separate stories (not DEC-67 carve-out — see Brief F-2 resolution).
The `--fullpageos-tag` override flag in AC3/AC4 is therefore intended
for the tag-bump story itself, not for casual operator use; this is
not enforced in code but is documented inline in the script.

This story's RED-first pattern (`bats` test first, `build-image.sh`
change second) is the natural fit for shell-script authoring under
DEC-22. Reconstruction-in-place (the project's canonical migration
strategy) does not apply because there is no preexisting code — this is
greenfield authoring.

Operationalizes Brief D-2 (module foundation), D-4 (FullPageOS choice),
D-5 (config delivery via `/boot/fullpageos.txt` + optional branding
file), D-9 (tag pin to `0.14.0`), C-3 (RED-first), C-4 (DEC-54 gate),
C-6 (Maven module status), C-9 (recommendation validation discharged),
S-10 (SPDX headers), Q-1 (line endings).
