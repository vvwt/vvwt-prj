# Story E21S05: Match + SetResult + AuditLog Aggregates — reconstruction-in-place with TDD

## User Story

**As a** maintainer of the `tournament` bounded context,
**I want** the `Match` entity, `SetResult` entity, `AuditLogEntry` entity, the four match/set enums (`MatchState`, `MatchFormat`, `MatchOutcome` enum, `SetState`), the `SetResultInput` value object, and the seven repositories (`MatchRepository` + `MatchCrudRepository` + `MatchOutcomeRepository` + `MatchOutcomeCrudRepository` + `SetResultRepository` + `AuditLogRepository` + `AuditLogCrudRepository`) reconstructed under `de.vvwt.tm.tournament.*` / `.tournament.internal.*` with a failing test preceding every implementation,
**so that** the central tournament scoring-substrate aggregates sit cleanly on the new Modulith boundary and the scoring, display, print, and slotopt contexts can target `tournament::api` from day one.

---

## Context

Epic E21 reconstructs the `tournament` hub first among Track-3 contexts (Brief D-10 Approach C). This story delivers the **match + scoring-substrate cluster** — the most cross-context-referenced slice of the tournament domain. The `Match` entity alone has 16 importers across slotopt, scoring, display, print, and timer contexts (inventory line 173 — the highest import count of any single tournament entity). `MatchState`, `MatchFormat`, and `MatchOutcome` are boundary-API enums because cross-context code uses them in method signatures and field types — moving them later (rather than now) would force every consumer to import from `.domain.*` longer than necessary.

Per Session Brief D-4 (aggregate-oriented DDD decomposition), the match cluster includes: match + outcome + set + set-input + audit log. Per D-8 and inventory:
- `Match` (line 173) — `tournament-core` in inventory, but elevated to boundary-API during refinement given its 16 importers and cross-context role (slotopt, display, print all consume `Match` directly).
- `SetResult` (line 182) — boundary-API candidate (consumed by `display/DisplayOverviewService`); elevated in refinement.
- `MatchState`, `MatchFormat`, `MatchOutcome` enum, `SetResult`'s state enum — all boundary-API per inventory lines 174–176 and 184. `SetState` (line 184) is inventory-classified `tournament-core` because grep found no cross-context imports, but refinement elevates it to boundary-API on Brief D-4 consistency grounds: `SetResult` is boundary-API and a consumer that reads `SetResult.state` transitively needs `SetState` on the class path.
- `SetResultInput` (line 183) — boundary-API value object consumed by `scoring/ScoreEntryService`.
- `AuditLogEntry` (line 167) — tournament-core, INTERNAL audit-log entity; append-only (E03S04 history). Not part of the public API surface.
- Repositories: `MatchRepository` (line 294, 12 importers — boundary-API), `MatchOutcomeRepository` (line 293 — boundary-API candidate; elevated in refinement), `SetResultRepository` (line 301 — elevated to boundary-API for consistency with `SetResult`), `AuditLogRepository` + `AuditLogCrudRepository` (lines 286–287 — internal). CrudRepository twins are internal.

Per DEC-22, RED-first TDD per class. Per DEC-26, DAO tests use `TenantDaoTestSupport.applyTournamentSchema()` (delivered by E21S02) — no helper modification in this story. The helper loads V1–V16 including V3 (match table), V4 (team_avatar), V5 (set_result + team_avatar_rating), V9 (audit_log), etc. — all the tables this story's ITs touch.

No REST controller in this story: scoring owns the scoring REST surface (`ScoreController` at `infrastructure.score.*`, stays legacy until E22); `Match` data is exposed via `TournamentController` (S02) or a later dedicated controller. Consumer-context code (scoring, display, slotopt cascades) is NOT edited here — S13 atomic cutover handles mechanical rewire per DEC-32.
