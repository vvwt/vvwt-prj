# Story E55S03: Per-tournament Worker Registry + ExecutorService lifecycle

## User Story

**As a** Tournament Manager developer (Delivery Agent),
**I want** `DefaultWorkerRegistry` implemented per the interface from E55S01 — lazy-creating one `Executors.newSingleThreadExecutor()` per tournament, with idle-timeout shutdown and graceful JVM-shutdown handling,
**so that** subsequent E55S04 orchestrator drain logic can submit job-execution tasks to the correct per-tournament worker, achieving FIFO within a tournament and parallelism across tournaments per DEC-64 D-3, without leaking thread-pool resources on tournament inactivity.

---

## Context

DEC-64 D-3 mandates per-tournament single-thread workers via `ConcurrentHashMap<UUID, ExecutorService>` registry. Lifecycle:

- Lazy-create on first enqueue (first call to `getOrCreate(tournamentId)`).
- Idle-timeout shutdown: a worker with an empty pending-jobs queue for ≥ 5 minutes (configurable via `tm.phaselifecycle.worker-idle-timeout-seconds`, default 300) receives `shutdown()` and is removed from the registry. Restart on next enqueue.
- JVM-shutdown: `@PreDestroy` hook calls `shutdownAll()` which iterates the registry and invokes `shutdown()` followed by `awaitTermination(30, SECONDS)` (configurable via `tm.phaselifecycle.worker-shutdown-timeout-seconds`, default 30). Incomplete jobs are reclaimed by the next JVM instance per DEC-64 D-7 restart-recovery.

The registry is purely an in-memory bookkeeping device — it does NOT persist worker state. The PERSISTENCE substrate for jobs is the `phase_lifecycle_job` table (E55S02). On JVM restart, the orchestrator's recovery path (E55S04 + E55S07 IT) reads RUNNING-but-stale-claimed rows and resets them to PENDING for fresh claim.

Idle-timeout is a hygiene concern, not a correctness concern. A worker that idles longer than the timeout simply gets recreated on the next enqueue with no semantic difference.

## Acceptance Criteria

- [ ] **AC-IMPL-WORKER-REGISTRY-LAZY-CREATE**: `DefaultWorkerRegistry.getOrCreate(tournamentId)` returns an `ExecutorService` for the tournament. First call creates a new `Executors.newSingleThreadExecutor()` and stores it in `ConcurrentHashMap<UUID, ExecutorService>`. Subsequent calls return the existing instance. Thread-safe under concurrent calls (use `ConcurrentHashMap.computeIfAbsent` or equivalent).
- [ ] **AC-TEST-LAZY-CREATE-IDENTITY-RED** (testing): RED-first unit test — two `getOrCreate(tournamentA)` calls return the same `ExecutorService` instance (reference equality). A `getOrCreate(tournamentB)` for a different tournament returns a DIFFERENT instance.
- [ ] **AC-TEST-CONCURRENT-CREATE-SINGLE-INSTANCE-RED** (testing): RED-first unit test — 10 threads call `getOrCreate(sameTournamentId)` in parallel; only one `ExecutorService` instance is created (verified by holding a `Set<ExecutorService>` of all returned instances and asserting size==1).
- [ ] **AC-TEST-PARALLEL-TOURNAMENT-EXECUTION-RED** (testing): RED-first IT — two distinct tournaments submit blocking tasks (each sleeps 200ms). Total elapsed time is < 350ms (would be ≥ 400ms if serialized). Verifies cross-tournament parallelism.
- [ ] **AC-TEST-FIFO-WITHIN-TOURNAMENT-RED** (testing): RED-first IT — one tournament submits 5 tasks each writing a sequence number to a shared list. The list ordering matches submission order. Verifies single-thread FIFO within a tournament.
- [ ] **AC-IMPL-IDLE-TIMEOUT-SHUTDOWN**: A worker idle for ≥ `tm.phaselifecycle.worker-idle-timeout-seconds` (default 300) is shut down via `shutdown()` and removed from the registry. Implementation may use a scheduled poller, `ScheduledExecutorService`, or last-used timestamp tracking — Delivery picks.
- [ ] **AC-TEST-IDLE-TIMEOUT-SHUTDOWN-RED** (testing): RED-first IT (with reduced timeout via `@TestPropertySource(properties = "tm.phaselifecycle.worker-idle-timeout-seconds=1")`) — submit a quick task; wait 2 seconds; verify the worker has been removed from the registry; subsequent `getOrCreate()` for the same tournament creates a NEW `ExecutorService` instance (reference inequality with the prior one).
- [ ] **AC-IMPL-JVM-SHUTDOWN-AWAIT-TERMINATION**: `DefaultWorkerRegistry.shutdownAll()` (called via `@PreDestroy`) iterates the registry, calls `shutdown()` on each ExecutorService, awaits up to `tm.phaselifecycle.worker-shutdown-timeout-seconds` (default 30) via `awaitTermination`. If a worker fails to terminate, logs WARN with the tournamentId.
- [ ] **AC-TEST-JVM-SHUTDOWN-AWAIT-TERMINATION-RED** (testing): RED-first IT — submit a long-running task; call `shutdownAll()`; verify the task is awaited within the timeout; verify post-shutdown `getOrCreate()` is rejected (RejectedExecutionException) or transparently re-creates per Delivery's contract choice.
- [ ] **AC-IMPL-WORKER-NAMED-THREADS**: Each `ExecutorService` uses a `ThreadFactory` that names threads `phaselifecycle-{shortTournamentId}-{threadNum}` (e.g., `phaselifecycle-abc123de-0`). Aids debugging + log correlation.
- [ ] **AC-ERROR-HANDLING-TASK-EXCEPTION-LOGGED** (error-handling): A submitted task that throws an uncaught exception is logged at ERROR with the tournament context. Verified by submitting a `throw new RuntimeException("test-failure")` task and asserting the log contains the expected ERROR entry + the worker is still alive for the next submission.
- [ ] **AC-ERROR-HANDLING-SHUTDOWN-DURING-EXECUTION** (error-handling): If `shutdownAll()` is called while a worker has an in-flight task, the in-flight task completes (or hits `awaitTermination` timeout). DEC-37 Clause B's transactions inside the task are NOT affected — the task is allowed to commit/rollback naturally.
- [ ] **AC-SEC-NO-NEW-AUTH-SURFACE** (security): No REST endpoint, no auth surface. Worker threads inherit the tenant context of the submitting thread via the existing `TenantContextResolver` mechanism — verified by an IT that submits a tenant-context-using task and asserts the binding is correct.
- [ ] **AC-IMPL-TENANT-CONTEXT-PROPAGATION**: Submitted tasks run with the tenant context of the submitter. Delivery uses Spring's `TaskDecorator` mechanism or the existing tenant-context-propagation infrastructure (per the `TenantContextResolver`); verified by an IT.
- [ ] **AC-TEST-TENANT-CONTEXT-PROPAGATION-RED** (testing): RED-first IT — submit a task that reads `TenantContext.current()`; assert the returned tenantId matches the submitting thread's tenant. Test fails until the TaskDecorator is wired correctly.
- [ ] **AC-GOVERNANCE-DEC-22-Q-1A-RED-FIRST** (governance): All testing-category ACs committed RED-first per DEC-22 Pattern B.
- [ ] **AC-GOVERNANCE-DEC-44-IT-FRAMEWORK** (governance): ITs use `@SpringBootTest(NONE, classes=TournamentManagerApplication.class)`.
- [ ] **AC-GOVERNANCE-DEC-54-MVN-VERIFY** (governance): `mvn verify` BUILD SUCCESS.
- [ ] **AC-GOVERNANCE-DEC-29-DEC-30-CLEAN** (governance).
- [ ] **AC-GOVERNANCE-COMMIT-MESSAGE-FORMAT** (governance): `chore(E55S03): ...` + close-commit.
