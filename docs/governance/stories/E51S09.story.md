# Story E51S09: L1 group-aware Match-Generation — RoundRobinMatchGenerator partitions per groupNumber

## User Story

**As a** Tournament Operator,
**I want** Phase 1 (12 teams in 2 groups of 6, gameMode=roundRobin) to generate exactly 30 matches (2×15) — one round-robin per group — instead of 66 (one round-robin across all 12 teams),
**so that** Group A teams play only Group A teams (and Group B only Group B), and the Phasenübersicht "Spiele (fertig / gesamt)" column shows the correct expected count.

---

## Context

**Empirically verified mechanism (Brief O-1 + O-3 + O-4):** `RoundRobinMatchGenerator.generate()` (`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/RoundRobinMatchGenerator.java:85-156`) does NOT partition by `avatar.getGroupNumber()`. `generatePairs()` (line 165-196) iterates over the FULL avatar list and produces N×(N-1)/2 pairs. For 12 avatars: 66 pairs. `PhasePreparationService.generateMatches()` (`vvwt-tm-web/.../PhasePreparationService.java:143-148`) loads ALL phase avatars in one repository call and passes them to the generator — no per-group iteration.

**Symptom:** operator screenshot 2026-05-08 shows Phase 1 = "0/66" and Phase 2 = "0/66" (matches Bug 1). Expected per operator: Phase 1 = "0/30", Phase 2 = "0/18". The query at `DefaultPhaseQueryService.SELECT_MATCH_COUNTS` is phase-scoped (groups by `phase_id`); the displayed "66" reflects actual DB row count per phase.

**Fix at L1 layer (Brief D-1 + S-1):** `RoundRobinMatchGenerator.generate()` partitions input avatars by `groupNumber`, runs the existing circle-method per group, concatenates the per-group match-lists. Total matches = sum over groups of `(N_g × (N_g-1) / 2)`. For 2 groups of 6 → 2×15 = 30. For 3 groups of 4 → 3×6 = 18. SiegerehrungMatchGenerator unchanged (already returns empty).

This story is the L1 layer of the Layered Decomposition (Brief D-1). L2 (Round-Assignment) consumes L1 output but is OUT OF SCOPE for this story (Story 10).
