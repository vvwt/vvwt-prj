# Story E51S02: Avatar-Erzeugung-Verschiebung — `DefaultDraftService.apply()` persists structural avatars at DraftConfig-Apply

## User Story

**As a** Tournament Operator,
**I want** every TeamAvatar slot for every phase of my tournament to exist in the database immediately after I click Apply on the DraftConfig — even before any team is assigned to a slot,
**so that** the background job pipeline (Match-Gen, Slot-Opt) can run upfront against the structural avatars (DEC-9 identity), not waiting for Phase-N completion.

---

## Context

DEC-55 D-1 mandates that avatars are persisted at DraftConfig-Apply time as structural placeholders with `(phaseId, groupNumber, groupPosition)` populated and `teamId` nullable. Today, `DefaultDraftService.apply()` (verified via `DefaultDraftService.java:98+179` Javadoc *"TeamAvatar creation is deferred to the phase transition"*) only creates Phase records — the avatar persistence is deferred to `DefaultPhaseTransitionService.commitTransition()` line 160.

Avatars must be persisted upfront because the Match-Gen background job (E51S03) needs `List<TeamAvatar>` as input to invoke `RoundRobinMatchGenerator.generate(phase, avatars)` — verified that the generator uses `avatar.getId()` (not `teamId`) to populate match pairs (`RoundRobinMatchGenerator.java:173`).

For Phase 1, `teamId` MAY be populated immediately at apply-time using the existing `computePhase1Proposals()` algorithm (which derives team IDs from `participate=true Tournament.Teams` sorted by `teamNumber` per `DefaultPhaseTransitionService.java:209-258`). For Phase 2+, `teamId` stays NULL until the operator's drag&drop commit at phase-transition-time.

Number of avatars per phase = `groupCount × maxPositionPerGroup` derived from the `DraftSection` (per existing `computeProposals` round-robin distribution: `targetGroup = (i % groupCount) + 1`, `targetPosition = (i / groupCount) + 1` — for Phase 2+ the structural shape is identical to Phase 1's, since DEC-9 identity does not depend on Phase-N rating points).

Per `DraftSection.java`, the position count for Phase 2+ is determined either by the explicit `positionCount` field (if set in DraftConfig) or, for `placement_group` / `group_placement` algorithms, by deriving from the participating-team count divided by `groupCount` and rounding up. Delivery's investigation determines the exact computation; the AC envelope requires that **all structurally-required avatar slots exist after apply** — re-running the apply for the same DraftConfig produces the same number of avatars (idempotent) per AC.

## Acceptance Criteria

- [ ] **AC-TEST-DRAFT-APPLY-PERSISTS-PHASE-1-AVATARS-RED** (testing): RED-first integration test — given a Tournament with two phases (Phase 1 + Phase 2) declared in DraftConfig + N participating teams (`participate=true`) + `groupCount` declared on Phase 1, when `POST /api/draft/apply` is invoked, then exactly `N` TeamAvatar records are persisted for Phase 1 with structural identity `(phaseId, groupNumber, groupPosition)` per `computePhase1Proposals()` distribution AND `teamId` populated to the participating team's UUID. Test fails before fix because `DefaultDraftService.apply()` does not create avatars.
- [ ] **AC-TEST-DRAFT-APPLY-PERSISTS-PHASE-2-PLUS-STRUCTURAL-AVATARS-RED** (testing): RED-first — same fixture as AC1 but asserts Phase 2 avatars: exactly the structurally-required number of avatars exist for Phase 2 (count = `groupCount × maxPositionPerGroup` per the existing structural distribution rules) with `(phaseId, groupNumber, groupPosition)` populated AND `teamId IS NULL`. Test fails before fix.
- [ ] **AC-TEST-DRAFT-APPLY-DEC-9-IDENTITY-INVARIANT-RED** (testing): RED-first — given any apply, the persisted avatars have unique `(phaseId, groupNumber, groupPosition)` triples (no two avatars share the same triple within the same phase). DEC-9 structural-identity invariant. Test fails before fix because no avatars are persisted.
- [ ] **AC-TEST-DRAFT-APPLY-IDEMPOTENT-GREEN** (testing): regression — re-applying the same DraftConfig produces the same set of avatars (idempotent at the structural level — no duplicates, no orphan rows). The exact semantics (delete-and-recreate vs. upsert vs. no-op-if-equivalent) is at Delivery's discretion as long as the post-state matches AC1 + AC2 deterministically. The chosen semantics is documented in the impl-report.
- [ ] **AC-TEST-DRAFT-APPLY-NON-PARTICIPATING-EXCLUDED-PHASE-1-RED** (testing): RED-first — given a tournament with M total teams (M ≥ N) where exactly N have `participate=true`, when `apply()` runs, Phase 1 has exactly N avatars (the M-N non-participating teams produce no Phase 1 avatar). Test fails before fix.
- [ ] **AC-IMPL-AVATAR-PERSISTENCE-AT-APPLY**: `DefaultDraftService.apply()` is extended to invoke the new avatar-persistence logic for every phase declared in the draft. The transactional boundary is preserved (DEC-37 Clause B per-tournament pessimistic row-lock — `tournamentRepository.findByIdForUpdate(tournamentId)` is the first read in the apply transaction; avatar persistence runs inside the same TX).
- [ ] **AC-IMPL-DEC-9-STRUCTURAL-IDENTITY**: persisted avatars have `(phaseId, groupNumber, groupPosition)` populated. teamId is populated for Phase 1 from `computePhase1Proposals()`-equivalent logic; teamId is NULL for Phase 2+. The exact code structure (a new `AvatarFactory` class, an inline loop, a service method) is at Delivery's discretion.
- [ ] **AC-IMPL-NO-MATCH-GEN-IN-APPLY**: `apply()` does NOT invoke `phasePreparationService.generateMatches(...)`. Match-Gen runs in the background per E51S03 — out of scope here. Verified by inspecting the apply call graph.
- [ ] **AC-IMPL-NO-EVENT-PUBLICATION-IN-S02**: `apply()` does NOT publish `MatchGenJobScheduledEvent` in this story. Event publication wires into the apply path in E51S03 (the consuming story). E51S02 is foundational data-model only.
- [ ] **AC-ERROR-HANDLING-EMPTY-PARTICIPATING-TEAMS** (error-handling): given a tournament with zero `participate=true` teams, the apply rejects with HTTP 4xx (operator-actionable) before any avatar is persisted. No partial persistence (no Phase 2+ avatars without Phase 1 avatars). The exact HTTP status code follows the existing `DefaultDraftService.apply()` precondition error pattern — Delivery preserves whatever the existing apply rejection contract is.
- [ ] **AC-ERROR-HANDLING-DRAFT-VALIDATION-PRECONDITIONS** (error-handling): given any DraftSection with invalid groupCount (≤ 0) or invalid sequence numbering, the apply rejects per the existing draft-validation contract; the new avatar persistence does NOT run. Verified by IT injecting an invalid draft and asserting no avatar rows after the rejection.
- [ ] **AC-ERROR-HANDLING-NO-PARTIAL-PERSISTENCE-ON-FAILURE** (error-handling): if avatar persistence for any phase fails mid-loop (e.g., DB error), the entire transaction rolls back. No orphan avatars. Verified by an IT that injects a stub `TeamAvatarRepository.save()` failure and asserts pre-fix DB state is restored.
- [ ] **AC-SECURITY-APPLY-AUTH-UNCHANGED** (security): the apply endpoint authentication and authorization posture is unchanged from the pre-E51 contract — admin-only via Spring Security. No new auth surface. Verified by a security IT that issues an unauthenticated apply and expects 401/403.
