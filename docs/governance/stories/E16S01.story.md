# Story E16S01: `TenantDaoTestSupport` — TDD-first test infrastructure for DAO integration tests

## User Story

**As a** maintainer writing DAO integration tests in `vvwt-tm-web`,
**I want** a small, final test-support utility that makes schema-loading, independent persistence verification, and read-path fixture insertion trivial,
**so that** every new DAO test satisfies DEC-26's three rules by default — without anyone having to remember them — and the DAO under test is never the evaluator of its own write path.

---

## Context

DEC-26 (governance, 2026-04-19) codifies three rules for DAO integration tests in `vvwt-tm-web`:

1. Schema MUST be loaded from the production Flyway migration via Spring `ScriptUtils`.
2. Persistence MUST be verified by an independent instrument (assertj-db 3.0.2 `AssertDbConnection`) — never by the DAO's own read methods.
3. Read-path tests MUST use direct-JDBC fixture insertion, never the DAO's write methods.

The root principle is generator/evaluator separation at the data-access boundary — a DAO must not be both the subject of a test and the instrument of its verification (Base-Rule 5 applied at the DB layer).

Conventions and rules alone are insufficient — they require discipline at every test authoring. E16S01 delivers the Poka-Yoke lever: a test utility that makes the three rules the default, not a discipline to remember. The utility is developed test-first from scratch against a new `TenantDaoTestSupportTest`, with RED-before-GREEN per method per DEC-22.

The utility lives in `vvwt-tm-web/src/test/java/` (test-scope only — must never be imported from production code). Location and package chosen by Delivery within test-classpath boundaries.

---

## Acceptance Criteria

- [ ] **AC1 (testing — test-first per DEC-22):** Git history shows a failing test in `TenantDaoTestSupportTest` committed BEFORE the corresponding method in `TenantDaoTestSupport`, for each of the four public methods (`freshDataSource`, `applyMigration`, `assertDbOf`, `insertDirectly`). Spot-check: four RED-then-GREEN commit pairs. Characterization tests (tests written against already-working code) are explicitly forbidden per DEC-22 and the Review Sub-Agent's cycle-1 finding.

- [ ] **AC2 (testing — real H2, no mocks):** The utility is tested against a real in-memory H2 DataSource. `DataSource`, `Connection`, `Statement`, `ResultSet` — none are mocked. `TenantDaoTestSupportTest` uses `TenantDaoTestSupport.freshDataSource()` itself once the method exists (self-referential in the normal test-support pattern, but with an explicit bootstrap test — see AC3).

- [ ] **AC3 (testing — bootstrap independence):** The first test (for `freshDataSource`) does NOT depend on any other method in `TenantDaoTestSupport`. It constructs the expected `DataSource` shape from first principles (`JdbcDataSource` + unique URL assertion + open-connection smoke test) so that a bug in `applyMigration` or `insertDirectly` cannot mask a bug in `freshDataSource`. No `@BeforeEach` in `TenantDaoTestSupportTest` may invoke other `TenantDaoTestSupport` methods while the `freshDataSource` test is being set up — the bootstrap test runs against a hand-rolled DataSource wiring (explicit in the `@Test` method body), not against a `TenantDaoTestSupport`-produced one.

- [ ] **AC4 (governance — DEC-26 Rule 1, schema-from-migration):** `applyMigration(DataSource ds, String classpathResource)` delegates to `org.springframework.jdbc.datasource.init.ScriptUtils.executeSqlScript(Connection, Resource)` with a `new ClassPathResource(classpathResource)`. A test verifies that the method successfully applies `db/migration/auth/V1__admin_credentials.sql` (the canonical production migration, already present in `vvwt-tm-web/src/main/resources/`) to a fresh DataSource. A second test verifies that a bogus classpath resource throws with a descriptive message containing the resource name.

- [ ] **AC5 (governance — DEC-26 Rule 2, independent persistence verifier):** `assertDbOf(DataSource ds)` returns an `org.assertj.db.type.AssertDbConnection` built via `AssertDbConnectionFactory.of(ds).create()`. A test verifies that the returned connection can build a `Table` handle for a table that exists in the DataSource and that `hasNumberOfRows(N)` assertions work as expected on a seeded DataSource.

- [ ] **AC6 (governance — DEC-26 Rule 3, read/write decoupling):** `insertDirectly(DataSource ds, String table, Map<String, Object> cols)` inserts a single row via direct JDBC (PreparedStatement with parameterised values from the map, no SQL string concatenation of values), auto-commit. A test verifies that (a) the row appears in the DB when queried via `assertDbOf`, (b) SQL injection via a crafted key or value is prevented (keys are treated as identifiers with a whitelist or quoted-identifier strategy; values are parameterised), (c) unknown columns produce a descriptive error, (d) empty map throws `IllegalArgumentException`.

- [ ] **AC7 (governance — final / sealed, no DAO-specific inheritance):** `TenantDaoTestSupport` is declared `final` with a private constructor. All four methods are `static`. A test (or a static-analysis assertion, e.g., an `ApplicationModulesTest`-style test) verifies: the class has no public constructor and has no non-final subclass anywhere in `vvwt-tm-web/src/test/java`.

- [ ] **AC8 (governance — test-scope only):** The class lives in `src/test/java/` and is NOT importable from `src/main/java/`. A test verifies that no `main/java` class references `TenantDaoTestSupport` (a simple classpath scan or a dedicated `ArchUnit`-style rule; if ArchUnit is not on the classpath, a regex-based file scan across `src/main/java` is acceptable — no match is the expected result).

- [ ] **AC9 (testing — reference MarkerDao demonstrates three-rule compliance):** A throwaway `MarkerDao` + `MarkerDaoTest` pair (both in `src/test/java` — `MarkerDao` is a test-scope class, not production code) demonstrates that a DAO test built on `TenantDaoTestSupport` satisfies all three DEC-26 rules end-to-end. The test:
  - Loads schema via `TenantDaoTestSupport.applyMigration` (Rule 1)
  - Verifies MarkerDao's insert via `TenantDaoTestSupport.assertDbOf(...).table("marker")` (Rule 2 — no call to MarkerDao's own read method in the insert test)
  - For the find test, seeds the row via `TenantDaoTestSupport.insertDirectly` (Rule 3 — no call to MarkerDao's write method)
  The `MarkerDao` implementation may be minimal (single insert, single findAll). Its schema is a new test-only SQL resource, e.g., `src/test/resources/db/migration/testsupport/marker_schema.sql`, clearly labelled as test-only so it is not confused with production migrations.

- [ ] **AC10 (testing — Modulith verify remains green):** `ApplicationModulesTest` passes after this story lands. Test-scope classes do not normally affect Modulith verification, but the AC is stated explicitly to prevent regressions from future adjustments (e.g., a Delivery choice to move the utility into a shared test-support package that accidentally shadows a production module).

- [ ] **AC11 (build quality — per `tdd.rules.md` Build Quality Gate):** `mvn verify` completes with zero warnings in Maven output (no `[WARNING]`, no deprecation warnings, no unchecked warnings). The new code must be clean against the project's existing compiler-warning gates.

- [ ] **AC12 (dependency wiring — if not already present):** If assertj-db is not yet on the parent-POM `dependencyManagement` and the `vvwt-tm-web/pom.xml` test-scope, Delivery adds both per DEC-10 (version in parent, no pin in child module). Note: the session refactor of `AdminCredentialsDaoTest` already introduced `<assertj-db.version>3.0.2</assertj-db.version>` — if that commit lands before E16S01 starts, this AC is already satisfied; Delivery verifies and moves on.

## Out of Scope

- Migration of `AdminCredentialsDaoTest` onto `TenantDaoTestSupport` — the existing test already satisfies DEC-26's three rules via inline helpers; migration is cosmetic and explicitly NOT part of this story (per DEC-26 § TenantDaoTestSupport contract).
- Retrofit of any other tests — no other TDD-reconstructed DAOs exist (audit 2026-04-19).
- Transaction-boundary control (commit vs. rollback semantics) on `insertDirectly` — initial API is auto-commit only; extension via later story AC if required.
- Multi-table FK fixtures — initial API is single-table; extension via later story AC if required.
- Reset-between-tests helpers (table-level truncate/delete) — `freshDataSource()` produces a new DB per call, so per-test isolation is guaranteed by construction; no explicit reset needed. Future DAO tests with a different lifecycle requirement extend the API.
- Any production-code changes to DAOs or DAO contracts.
- Extraction of the utility into a separate Maven test-support submodule.

## Notes

- **Package choice is a Delivery decision** within test-classpath. Suggested: `de.vvwt.tm.infrastructure.testsupport` (aligns with `de.vvwt.tm.infrastructure.web` pattern already used for test helpers). Alternatively `de.vvwt.tm.testsupport` at root level. Delivery picks the less-disruptive option and documents in the impl report.
- **The `MarkerDao` reference test (AC9)** may be tempting to skip because it looks like ceremony. It is not — it is the acceptance proof that the utility closes the generator/evaluator loop end-to-end. Without AC9, E16S01 delivers a utility whose surface looks correct but whose semantics are untested at the "real DAO + real schema + real verification" layer. AC9 is small (~50 lines total across MarkerDao + MarkerDaoTest) and earns its keep.
- **Future DAO stories that need richer fixture support** (multi-table FKs, transaction boundaries) MUST add the required capabilities via explicit AC in their own story — not via ad-hoc workarounds in test bodies or via subclassing `TenantDaoTestSupport` (forbidden by AC7). The utility's minimal API is deliberate; growth is story-gated and API-review-visible.
- **The session refactor of `AdminCredentialsDaoTest`** (2026-04-19, uncommitted at story-creation time) is committed as a direct post-hoc improvement to E15S02 per DEC-26's "E15S02 post-hoc cleanup" clause — it is NOT framed as an E16 story payload. Delivery of E16S01 must not take a dependency on that commit having landed; if it has, great (AC12 becomes a verification); if not, E16S01 adds the parent-POM property + dependency management entry itself.
