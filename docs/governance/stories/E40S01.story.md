# Story E40S01: Extend SignatureVerifier interface with DEC-43 D1 metadata methods (displayName, deprecationDate, parameters); explicit override in DefaultEd25519Verifier

## User Story

**As a** maintainer of the slot-opt dispatcher closing the DEC-43 D1 compliance gap,
**I want** the `SignatureVerifier` interface extended with three new metadata methods (`displayName()`, `deprecationDate()`, `parameters()`) and the existing `DefaultEd25519Verifier` extended via explicit-override (per Brief T-4 recommendation),
**so that** subsequent E40 stories (S02 announcement endpoint + S03 deprecation enforcement) can consume per-verifier algorithm metadata, and any future verifier impl (Phase-2+ ML-DSA, SLH-DSA, Falcon, hybrid) is forced at compile-time to author its own metadata explicitly.

---

## Context

Per Brief D-5: SignatureVerifier interface gains three new methods authored ADDITIVELY:
- `String displayName()` — human-readable name (e.g., `"Ed25519"`)
- `LocalDate deprecationDate()` — ISO-8601 date or null per DEC-43 D1 schema; null = not deprecated; non-null = deprecated for new registrations after `deprecationDate.atTime(23:59:59Z)` per DEC-43 § Boundary semantics
- `Map<String, Object> parameters()` — algorithm-specific parameter set or null (V1 Ed25519 returns null)

Per Brief T-4: explicit-override in `DefaultEd25519Verifier` chosen over Java 8+ default-method-in-interface. Rationale: per-impl metadata authorship is forced at compile-time; future impls cannot silently expose null metadata where the algorithm may genuinely be deprecated.

E37-shipped `SignatureVerifier` interface (per Brief O-4) currently has 4 methods: `algorithmId()`, `minPublicKeyBytes()`, `maxPublicKeyBytes()`, `verify(...)`. The 3 new methods are additive — V1 has only one impl (`DefaultEd25519Verifier` per Brief H-2), so binary-compat risk is theoretical until Phase-2+ adds new impls.

This story is foundational for E40 — both E40S02 (announcement service) and E40S03 (deprecation enforcement) consume the metadata methods. They cannot start until S01 closes.

## Notes

- **Interface evolution risk** (per Brief H-2): adding three abstract methods to an interface is binary-incompatible with any unknown impl. V1 has only one impl (DefaultEd25519Verifier); the explicit-override choice (T-4) means future impls (e.g., a Phase-2+ ML-DSA verifier) MUST author metadata explicitly — preventing silent-null-where-actually-deprecated bugs.
- **Backward-compat invariant**: existing `algorithmId() = "Ed25519"` PascalCase return value MUST be preserved (per Brief T-3 / D-4) — otherwise existing E37-registered worker_id rows (with `algorithm` column persisted as `"Ed25519"`) would no longer resolve via `SignatureVerifierRegistry.lookup("Ed25519")`.
- **Date type choice** for `deprecationDate()`: `java.time.LocalDate` (ISO-8601 calendar date with no time-of-day component). DEC-43 § Boundary semantics interprets `deprecation_date` as UTC end-of-day; the time-of-day evaluation happens at enforcement boundary (E40S03) using server clock, not on the type itself.
- **`parameters()` Map shape**: V1 Ed25519 returns null. Phase-2+ ML-DSA-65 might return e.g., `Map.of("parameter_set", "ML-DSA-65")`. The Map keys/values are algorithm-specific and not constrained by DEC-43 D1 beyond the wire-format-as-JSON requirement (Map<String, Object> serializes naturally via Jackson).
