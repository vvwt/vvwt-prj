# Story: A scoring tablet's between-match polling spends as little battery as possible while still auto-advancing to the next round

## User Story

**As a** referee using a scoring tablet over a full-day tournament,
**I want** the tablet's between-match polling to spend as little battery
as possible while still picking up the next round automatically,
**so that** an aged tablet can finish the tournament on a single charge.

---

## Context

E65S05 (PR #346, merged 2026-05-18) added a constant 5-second polling
loop to the scoring-tablet field page so that a tablet whose field has
finished its current-round match auto-advances when the tournament
advances. That loop currently runs unchanged through every idle period
of a tournament — between rounds, between phases, during longer phase
pauses — without any client-side power-management safeguards
(no `document.hidden` / `visibilitychange` guard, no backoff, no
idle-timeout, no Wake-Lock). On aged tablets with reduced battery
capacity, the operator's concern is that polling cumulatively shortens
runtime to the point a 6–10-hour tournament can no longer be played on
one charge.

The Discovery session of 2026-05-27 chose **defensive hardening without
measurement** — the energy risk is designed out preemptively rather
than confirmed empirically first (Brief T-1 — the saving cannot be
quantified inside this story; Brief H-1 stays UNVERIFIED). E65S05's
auto-advance value is preserved at a relaxed latency bound: the tablet
must still show the next-round match without a manual reload, just not
within "a few seconds" any more (Brief D-3, T-2).

The mechanism stays polling — DEC-19 §52 explicitly permits both
WebSocket and short-interval HTTP polling on the scoring tablet; the
choice to keep polling is operator preference for a self-contained
client-only change with a smaller blast radius (Brief T-3), not a
DEC-19 constraint.

Specific numeric values (the new poll interval, the idle-timeout
threshold, whether backoff is constant or exponential) are Delivery's
to choose within this story's behavioural bounds (per memory
`feedback_ac_behavioural_what_not_test_how`).

## Acceptance Criteria

- [ ] AC1 (relaxed auto-advance latency): When the tournament advances
  to the next round while a scoring tablet is in the no-match /
  waiting state on its field, the tablet shows the field's next-round
  match within **at most 60 seconds**, without a manual reload. The
  E65S05 auto-advance value is preserved at this relaxed latency bound.

- [ ] AC2 (visibility-aware polling): While the field page is not
  visible to the operator — the document is hidden (screen locked,
  browser backgrounded, tab in background) — the page performs **no
  polling network requests**. As soon as the page becomes visible
  again, polling resumes; if a match for the field has become
  available during the hidden period, the tablet shows it within
  AC1's latency bound after the page becomes visible.

- [ ] AC3 (idle-timeout with manual resume): After an extended
  continuous no-match / waiting state, the tablet **stops polling**
  and shows a clearly labelled "tap to refresh" control. When the
  operator activates that control, the tablet performs a fresh match
  lookup; if a match for the field is now available it is shown,
  otherwise the waiting state is re-entered and polling resumes per
  AC1. The threshold value is Delivery's choice — long enough that
  it does not interrupt normal between-round waits, and short enough
  to protect battery during phase pauses of an hour or more.

- [ ] AC4 (no regression — auto-advance still primary): When the
  tournament advances to the next round before AC3's idle-timeout has
  fired, the tablet still leaves its no-match / waiting state
  automatically (AC1) — AC3's manual-tap path is the recovery surface
  AFTER the idle timeout fires, not the primary auto-advance path.
  When a match is being scored, polling is not active (E65S05's
  `stopPolling()`-on-`renderMatch()` behaviour preserved).

- [ ] AC5 (no regression — error recovery): A transient network error
  during polling does not strand the tablet permanently. Once
  connectivity returns, the mechanism this story introduces resumes
  the lookup and the tablet shows the correct current match for its
  field within AC1's latency bound, without a manual reload. The
  offline retry queue stays out of scope (consistent with E65S05 AC5).

- [ ] AC6 (governance — DEC-19): The field page remains Mustache +
  inline vanilla ES5 JavaScript only — no Svelte or other framework,
  no ES2015+ syntax, no bundler. Feature detection for the Page
  Visibility API and any vendor-prefixed fallback (e.g.,
  `webkitHidden` / `webkitvisibilitychange` for iOS 9 Safari) is
  permitted and required where applicable.

- [ ] AC7 (governance — testing): First-party ES5 logic changed by
  this story is authored test-first per DEC-22 to the extent the
  project's existing automated test surface for this Mustache + ES5
  page supports it — that surface is rendered-HTML /
  template-structure inspection in the existing `ScoreFieldLayoutIT`
  / `ScoreFieldSwapIT` pattern, NOT runtime-JavaScript execution. The
  runtime behaviours introduced by this story (visibility-driven
  polling pause, idle-timeout + manual resume, relaxed auto-advance
  latency bound) are, where not reachable by that automated surface,
  verified by the implementer and explicitly recorded in the
  impl-report, which states exactly what is automated and what is
  attested. Delivery may extend the test surface but is not required to.

- [ ] AC8 (governance — build gate): `mvn verify` from the `vvwt-prj`
  root is BUILD SUCCESS (DEC-54, DEC-71).

> All acceptance criteria must be verifiable.

## Out of Scope

- Push-based architecture redesign — no WebSocket, no SSE, no
  long-poll. DEC-19 permits both polling and WebSocket; this story
  keeps polling per Brief T-3.
- Empirical energy measurement — no telemetry, no on-device counters
  reported to the server, no power-profiling harness. Brief T-1
  accepts that the actual saving cannot be quantified inside this
  story.
- E65S05's offline retry queue (already out of scope in E65S05 AC5).
- The Display overview (E65S04 surface), the admin SPA, the Timer
  SPA, and the `score/register` / `score/hello` scoring-tablet pages
  — only `score/field` changes.
- The `/api/score/match` server-side endpoint and its response
  semantics — unchanged.
- Other polling surfaces in the codebase (e.g.,
  `vvwt-tm-web/src/main/resources/static/score/spike/spike-utils.js`).
- Screen-management from JavaScript — Wake Lock API is not available
  in iOS 9 Safari; no JS-side dimming control.

## Notes

Brief H-1 ("5-s-fixed polling materially shortens battery life on
aged tablets") is UNVERIFIED — the operator chose preemptive defensive
hardening over measurement (Brief T-1). The saving this story produces
cannot be quantified from inside the story. The acceptance criteria
are structural: visibility-pause (AC2), idle-timeout-with-manual-resume
(AC3), and a relaxed auto-advance latency bound (AC1) each address a
different idle-state class (foreground-active vs. background/locked vs.
extended-pause), per Brief T-5 / T-6.

Brief Q-1 — "Tablet must survive a 6–10 h tournament on one
(degraded-capacity, aged) charge" — is the operator's felt objective
but is NOT a measured AC in this story. Brief Q-3's risk-asymmetry
preference (design-out over post-incident retro) is the rationale for
shipping this defensive change before any failure has been observed.

Per memory `feedback_ac_behavioural_what_not_test_how`, the ACs state
behavioural WHAT (visibility-aware, idle-bounded, ≤ 60-s latency).
Specific numeric values (new poll interval, idle-timeout threshold,
backoff curve if any) are Delivery's choice within those bounds. Per
memory `project_scoring_tablet_test_surface` the automated test
surface for this Mustache + ES5 page is rendered-HTML inspection only;
AC7 follows E65S05's impl-report attestation pattern for runtime
behaviours.
