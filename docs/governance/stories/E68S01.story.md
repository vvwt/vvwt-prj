# Story: The organizer name is an editable field on the tournament form

## User Story

**As a** tournament organizer,
**I want** to enter and change the organizer name on the tournament itself,
**so that** the certificate shows the organizer I chose instead of an
auto-filled default I was never asked about.

---

## Context

The certificate prints an organizer subtitle (`{{tom_organizer}}`) directly
under the tournament name. Its value is `tournament.organizer` — a column that
story E46S01 populates **once, at tournament creation**, by snapshotting the
organization's name (the tenant `display_name`, which on a fresh install is the
bootstrap default *"ToM Tournament Manager (LAN)"*). The column is deliberately
**write-once**: E46S01 excluded it from the tournament update path, and the
tournament create/edit form (`TournamentForm.svelte`) has no organizer field at
all — so the operator currently has no way to set or correct it.

This story makes the organizer a normal, editable field on the tournament
create and edit forms. This **intentionally reverses** E46S01's write-once
handling: `tournament.organizer` becomes a normal mutable column, and the
tournament update path is extended to carry it.

Because the certificate is a printed award handed to participants, an organizer
value is always wanted on it — the field is **required** (non-blank), exactly
as the existing required fields on the same form (e.g. the tournament
description). It is pre-filled with a sensible default so the operator never
has to type from scratch, but it cannot be saved blank.

The tournament create/edit form is reachable for **DRAFT** tournaments only
(the edit affordance is gated on `status === 'DRAFT'`). Correcting the
organizer on a tournament that has progressed past DRAFT — including a
completed tournament whose certificates are being printed — is handled by the
certificate-generation override (story E68S02), not by this story.

## Acceptance Criteria

- [ ] **AC1 [create]:** The tournament **create** form presents an organizer
  field, pre-filled with the organization's current name (the tenant display
  name). The operator may keep or change the pre-filled value. On save, the
  value held in the field is stored as the new tournament's `organizer`. A
  tournament created with the field left at its pre-filled default therefore
  carries the organization's name as its organizer — preserving today's
  outcome (no regression).
- [ ] **AC2 [edit]:** The tournament **edit** form (reachable for DRAFT
  tournaments) presents the organizer field pre-filled with the tournament's
  currently stored `organizer`. The operator may change it; saving the form
  persists the new value through the tournament update path — which previously
  did not carry the `organizer` column.
- [ ] **AC3 [end-to-end — certificate reflects the value]:** A test confirms
  end-to-end that a tournament saved with an operator-chosen organizer (via
  create or via edit) renders that organizer as the certificate subtitle. The
  certificate already binds `{{tom_organizer}}` to `tournament.organizer`
  (delivered by E46S03) — no change to certificate-rendering code is in this
  story's scope; this AC verifies the persisted value reaches the certificate.
- [ ] **AC4 [existing data unchanged]:** Tournaments created before this story
  keep their stored `organizer` value unchanged. There is no backfill, no
  migration, and no re-derivation of existing tournaments' organizer.
- [ ] **AC5 [error-handling]:** The organizer field is **required**. Submitting
  the create or edit form with a blank or whitespace-only organizer is rejected
  with a localized validation message and the tournament is not saved —
  consistent with how the other required fields on `TournamentForm.svelte`
  (e.g. the tournament description) behave. This guarantees every tournament
  saved through the form carries a non-blank organizer, so the certificate
  subtitle is never empty (Brief Q-1 — certificates are printed awards).
- [ ] **AC6 [i18n]:** The organizer field's label and any helper or validation
  text are rendered through the project's German-first i18n mechanism
  (`$_(key, { default })` with a German default string), consistent with the
  other fields on `TournamentForm.svelte`. No hardcoded display string is
  introduced.
- [ ] **AC7 [testing — TDD/RED-first]:** The new behavior is authored RED-first
  per DEC-22. Tests cover: (a) the organizer persisted on create; (b) the
  organizer persisted on edit via the newly-extended update path; (c) a blank /
  whitespace-only organizer rejected by form validation on both create and
  edit; (d) the end-to-end check of AC3 — a tournament saved with a custom
  organizer renders it as the certificate subtitle. Each fails against the
  pre-story code and passes after. Any pre-existing test that asserts
  `tournament.organizer` is excluded from the tournament update is
  intentionally updated to the new behavior — the write-once immutability is
  deliberately reversed by this story, so the legacy assertion is not a
  trustworthy oracle (DEC-22 reconstruction intent). The RED→GREEN cadence is
  recorded in the impl-report.
- [ ] **AC8 [testing — build gate]:** `mvn verify` for `vvwt-tm-web` is BUILD
  SUCCESS after the story (DEC-54) — no regression in the tournament
  create/edit or certificate test suites, frontend build included.
- [ ] **AC9 [governance]:** No new DEC is created. The organizer write path is
  extended within the existing `tournament` module, following the DEC-35
  package-layout rule (service/repository implementations in `.internal` behind
  their public interface) and with the REST surface in the `de.vvwt.tm.web`
  controller module (DEC-40). No database schema change is made — the
  `organizer` column already exists in the V1 baseline (DEC-52). If E46S01's
  intra-DB snapshot logic becomes wholly or partly unused as a result of this
  change, the orphaned production code — method, constructor, or field — is
  removed in the same change (DEC-70; and, if the orphan is a Repository/DAO
  read method, DEC-69). `related_decs` cites the constraining DECs.

> All acceptance criteria must be verifiable. Vague criteria are invalid.

## Out of Scope

- The venue / location label — not added to the tournament form. Persistent
  venue editing is deferred with location management; the venue is corrected
  only via the certificate override (E68S02).
- Editing the organizer of non-DRAFT tournaments — the tournament form is
  reachable for DRAFT tournaments only; non-DRAFT and completed tournaments are
  corrected via the certificate override (E68S02).
- A Settings / Configuration page, and editing the tenant `display_name`
  itself.
- Certificate-rendering code — unchanged; it already binds `{{tom_organizer}}`
  to `tournament.organizer`.
- Re-snapshotting or backfilling existing tournaments' organizer values.

- **DEC-69 / DEC-70** — no test-only or orphan production code; applies if the

## Notes

- This story defines the behavioral outcome. Delivery chooses the
  implementation — including how the create form obtains the organization's
  name for the pre-fill (a small read endpoint, an existing one, or a
  server-side default applied when the create request omits the field), and
  whether E46S01's intra-DB snapshot SELECT is kept or removed (subject to
  DEC-69 / DEC-70 if it becomes orphaned).
- If E46S01's snapshot SELECT is retained, it may serve **only** as the
  create-form pre-fill / create-time default for the organizer. It must not
  act as a render-time fallback: the certificate subtitle is the stored
  `tournament.organizer` value as persisted (the form guarantees it is
  non-blank — AC5). There is no render-time re-derivation of the organizer.
- E46S01 deliberately excluded `organizer` from the tournament UPDATE SQL.
  Delivery should expect to update E46S01-era tests that assert that exclusion
  — the reversal is intentional and in scope (AC7).
