# Story E71S03: Multi-candidate upload with automatic best-shot suggestion (offline)

## User Story

**As an** operator with several candidate shots of a team,
**I want** the app to rank my candidates and suggest the best one (everyone looking, eyes open, smiling, well framed) — which I can always override —
**so that** I no longer eyeball and compare near-identical photos by hand.

---

## Context

Operators take 3–7 candidate shots per team in quick succession (same background, varying
poses). The photos are uniformly sharp/well-exposed, so the discriminator is **group facial
expression** (eyes open, smiling, looking at the camera) and **framing/completeness**, not
technical quality. This story adds, to the Team-Photos screen, a multi-candidate step that
scores candidates in-browser and pre-selects the best — always overridable — then hands the
chosen photo to the E71S01 crop step.

Scoring uses **MediaPipe Face Landmarker** (Apache-2.0 SDK; model asset Apache-2.0 — verified in
Discovery against the official Blendshape V2 + FaceMesh model cards → AGPL-compatible per
DEC-75 D6, no carve-out). Its per-face blendshapes (`eyeBlink`, `mouthSmile`) and head pose map
directly onto the criterion; the group score aggregates across all detected faces plus an
in-frame/completeness check. Per reuse-search this is NEAR-HIT: the single-file upload
UI/store/endpoint are reused for the **final chosen image only** — candidates stay transient in
the browser, so there is **no server-side candidate storage and no multi-file endpoint** (YAGNI,
DEC-78). The scoring, the candidate-selection UI, and the offline asset bundling are net-new and
frontend-only.

Honest limitation (Brief O-8): MediaPipe is optimized for selfie/near-range faces; for group
photos with small/distant faces accuracy may degrade — hence the suggestion is never a silent
auto-pick and manual override is mandatory.

---

## Acceptance Criteria

- [ ] **AC1 (multi-candidate upload + gallery):** Given the Team-Photos screen, when the operator
  selects multiple candidate images (typical 3–7) for a team, then all selected candidates are
  shown as a gallery in the browser (none yet persisted to the server).
- [ ] **AC2 (automatic best-shot suggestion, overridable):** Given uploaded candidates, when
  scoring completes, then the candidates are ranked by a group score combining per-face
  eye-open, smile, and looking-at-camera signals plus a framing/completeness check, and the
  top-ranked candidate is **pre-selected as a suggestion**; the operator can select any other
  candidate instead (manual override always available — never a silent auto-commit).
- [ ] **AC3 (hand-off to crop + save):** Given the operator confirms a candidate, when they
  proceed, then exactly that one image enters the E71S01 crop+downscale step and only the final
  cropped image is saved via the existing endpoint; the other candidates are discarded
  (not persisted).
- [ ] **AC4 (fully offline — self-bundled assets):** Given the machine has no internet access,
  when the operator runs the best-shot step, then the MediaPipe WASM runtime and the model asset
  load from the application's own bundled static assets (same origin) with **no runtime fetch to
  any external CDN** (DEC-16/DEC-15). The bundled model asset's Apache-2.0 provenance is recorded
  in the impl-report (DEC-75 D6); no proprietary or AGPL-incompatible dependency is introduced
  (DEC-3).
- [ ] **AC5 (error-handling / degraded states):** Given a candidate where no face is detected, or
  fewer than the expected candidates, or the model fails to load, then the operator is not
  blocked: they can still manually select a candidate and proceed to crop (graceful degradation
  to manual selection), with a localized message where appropriate. Performance is kept
  acceptable by analysing downscaled copies of the candidates.
- [ ] **AC6 (testing — deterministic RED-first; runtime attested):** The deterministic
  group-score aggregation/ranking (given fixed per-face signal inputs) is covered by RED-first
  automated unit tests (DEC-22). Runtime MediaPipe inference + canvas behaviour (no automated
  browser oracle) is verified via the impl-report and MUST NOT be claimed as automated coverage.
  `mvn verify` is BUILD SUCCESS (DEC-54).
- [ ] **AC7 (i18n):** All new UI text (multi-upload, candidate gallery, suggestion/ranking labels,
  degraded-state messages) is provided through the frontend i18n layer, German-first per the TM
  convention — no hardcoded user-facing strings.

## Out of Scope

- Face-compositing / merging faces across frames (one real photo is selected).
- Server-side candidate storage, a multi-file backend endpoint, or any backend change.
- The crop/downscale itself (E71S01) and the per-template ratio (E71S02).
- Server-side (Java) scoring — only the documented evolutionary fallback, not this story.

---

## Dependencies

- **E71S01** — the chosen candidate is handed to E71S01's crop+downscale+save flow.
