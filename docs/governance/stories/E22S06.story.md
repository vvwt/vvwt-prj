# Story E22S06: TDD-reconstruct `ScoreEntryService` (public interface + `scoring.internal` impl) with scoring-public DTOs

## User Story

**As a** maintainer of the `de.vvwt.tm.scoring` Modulith module,
**I want** `ScoreEntryService` reconstructed as a **public interface**
at `de.vvwt.tm.scoring.ScoreEntryService` + `DefaultScoreEntryService`
(`@Service`) implementation at `de.vvwt.tm.scoring.internal.*` via
RED-first TDD, with its **method signatures preserved verbatim from
legacy** (`getMatchForField(int fieldNumber, String deviceToken) →
Optional<ScoreEntryResult>`, `handlePartialScore(PartialScoreInput
request) → void`, `submitSetResult(SetSubmitInput request) → void`)
and its 3 scoring DTO records (`PartialScoreInput`, `SetSubmitInput`,
`ScoreEntryResult`) placed in **`de.vvwt.tm.scoring.*` public root**
(Q-11 transitive-exposure rule — they are the return / parameter
types of a public interface method),
**so that** scoring remains a pure-domain module (no REST-DTO
coupling — the scoring DTOs are domain records, not Jackson wire
formats), E22S09's future `ScoreApiController` can consume the public
interface + public DTOs across module boundaries per DEC-21 without
an interface-extraction refactor at S09 pickup, and the deviceToken-
based authN for scoring-tablet flows is asserted by RED-first service
tests.

---

## Context

Per D-8 (Brief v3), `ScoreEntryService` is pure domain orchestration
(deviceToken auth + submit orchestration + cascade delegation to
`ScoringService`); it belongs in the scoring module, not in
`infrastructure.score.*` (its legacy location, kept there by E31's
hybrid-retrofit boundary). Per Q-11 transitive-exposure rule + DEC-35
"service interfaces in public for every service consumed by another
module", the web-module controller in E22S09 WILL consume
`ScoreEntryService` across module boundaries — so it is authored from
the start as a **public interface** in `scoring.*` root, with the
concrete impl (`DefaultScoreEntryService`) in `scoring.internal.*`
per DEC-35 naming canon.

**DTO placement resolution (Q-11 transitive-exposure rule):** The
public interface's method signatures take `PartialScoreInput` +
`SetSubmitInput` (parameters) and return `Optional<ScoreEntryResult>`
(return type). Per Q-11, types transitively exposed by public API MUST
be in the public package. Therefore these 3 DTOs are placed in
`de.vvwt.tm.scoring.*` public root (NOT `scoring.internal.*`).
This is the corrected Brief v3 DTO placement — the web controller
(E22S09) consumes these scoring-public DTOs directly and does NOT
need a separate DTO conversion layer unless the HTTP wire format
requires field omission / aliasing (DEC-40 Clause B(a)/(d)).

**Method-name fidelity to legacy (reviewer-caught coordination
invariant):** Legacy `ScoreEntryService.java` (on-disk, verified)
exposes 3 methods:
`Optional<MatchScoreResponse> getMatchForField(int fieldNumber,
String deviceToken)`, `void handlePartialScore(PartialScoreRequest
request)`, `void submitSetResult(SetSubmitRequest request)`. The
reconstructed interface preserves these exact method names + parameter
shapes (with DTO types renamed to `PartialScoreInput` /
`SetSubmitInput` / `ScoreEntryResult` since those are the new scoring-
public record types). Return-type `void` on the 2 submit methods is
preserved — the legacy controller returns HTTP 204 No Content for
both; E22S09's reconstructed controller continues the pattern.

The legacy `infrastructure.score.dto.*` classes remain untouched
through this story (deleted at E22S11 cutover).

Classification: Q-1a TDD RED-first per C-2. Cascade delegation per
DEC-37 Clause B preserved via injection of `ScoringService` interface
(E31S03). DeviceToken authN preserved from legacy.

### Error-handling

- [ ] **AC-VALIDATION-FAILURE-PATH**: On `submitSetResult(...)` with a
  set that `SetValidationRule.isSetClosed(...)` rejects, the service
  throws `ValidationException` with a message containing the failing
  set's coordinates. RED-first test required.
- [ ] **AC-NULL-GUARDS**: All 3 methods throw `IllegalArgumentException`
  on null arguments (`matchId`, `deviceToken`, `input`). RED-first
  test coverage.
- [ ] **AC-CASCADE-DELEGATION-PRESERVED (C-7)**: `submitSetResult(...)`
  delegates to `ScoringService.registerMatchResult(...)` — which
  (per E31S03) holds the per-tournament row-lock via
  `TournamentRepository.findByIdForUpdate(...)`. This story MUST NOT
  re-implement or bypass the cascade lock; it MUST NOT call
  `TournamentRepository.findByIdForUpdate(...)` directly. Impl-report
  cites the delegation line and attests no direct lock acquisition.

### Security

- [ ] **AC-SECURITY-DEVICE-TOKEN (SUBSTANTIVE)**: All 3 public methods
  MUST validate the `deviceToken` parameter via
  `DeviceRepository.findByToken(deviceToken)` (or equivalent lookup)
  BEFORE any business logic runs. Invalid / unknown token →
  `UnauthorizedException`. Token valid but not assigned to the match's
  device → `ForbiddenException`. RED-first test per failure mode
  (AC-TEST-COVERAGE-MATRIX includes these cases).
- [ ] **AC-SECURITY-TENANT-ISOLATION**: The device-token lookup MUST
  resolve within the current tenant scope (per DEC-14 tenant
  isolation); cross-tenant device tokens MUST NOT authorize a submit.
  RED-first test with a cross-tenant token asserts `UnauthorizedException`
  (or equivalent isolation-violation response).
- [ ] **AC-NO-RAW-INPUT-PERSISTENCE**: User-supplied input fields (set
  scores, elapsed minutes) are validated via the `SetValidationRule`
  path before persistence; no raw input is written to any repo without
  validation. Impl-report attests the validation sequencing.

## Notes

- **Interface-at-authoring decision (Brief Q-11)**: This story
  authors the public interface directly (not post-hoc extraction).
  Per D-8 + Q-11 transitive-exposure + E22S09's known consumer
  requirement, the interface is known at authoring time; skipping
  the refactor saves a Q-1b roundtrip at S09 pickup.
- **DTO architecture decision (Brief v3 recommended resolution)** —
  scoring-internal DTOs in this story, wire-format DTOs in E22S09,
  conversion in the controller. Keeps scoring a pure-domain module
  with no REST coupling. This decision is documented in the impl-
  report per Q-5 (implementation-level decision, not a standalone
  DEC).
- **Legacy REST controller** — `de.vvwt.tm.infrastructure.score.ScoreApiController`
  still targets the legacy `infrastructure.score.ScoreEntryService` +
  legacy DTOs through this story. E22S09 migrates the controller.
  No wiring or routing change in this story.
- **Commit-message template (Q-4):** `feat(E22S06): TDD-reconstruct
  ScoreEntryService (interface + Default impl) in scoring module`.
- **DeviceRepository interface type** — if `DeviceRepository` is still
  a concrete class in E22S06's pickup, delivery must escalate per
  DEC-36 to confirm the mock-type strategy (prefer interface mock; if
  none exists, same-package white-box test may use the concrete class
  — document choice in impl-report).
- **Cross-tenant isolation** — `DeviceRepository.findByToken(...)` MUST
  be the tenant-scoped variant (per DEC-14). If the legacy impl used
  a non-tenant-scoped lookup, that is a latent bug; escalate per
  base-rule "if in doubt, stop and ask" before coding.
