# Story E22S12: Add jakarta-validation annotations to scoring-public DTOs `PartialScoreInput` + `SetSubmitInput` (E22S06 follow-up — unblocks E22S09)

## User Story

**As a** maintainer of the `de.vvwt.tm.scoring` Modulith public API,
**I want** the 2 scoring-public request records (`PartialScoreInput`,
`SetSubmitInput`) decorated with the exact jakarta-validation
annotations carried by their legacy counterparts
(`PartialScoreRequest` → `@NotNull UUID matchId`, `@Min(0) int setIndex`,
`@Min(0) @Max(99) int team1Points`, `@Min(0) @Max(99) int team2Points`,
`@NotBlank String deviceToken`; `SetSubmitRequest` → identical set),
**so that** E22S09's `@Valid`-annotated controller binding rejects
invalid payloads at the Jackson boundary (HTTP 400 with legacy-parity
error shape), E22S06's Javadoc-documented invariants become runtime-
enforced (not merely descriptive), and the E22S09 AC-DTO-VALIDATION-
BOUNDARY-VERIFIED grep-gate passes so E22S09 can resume Delivery.

---

## Context

E22S06 delivered the 2 scoring-public records at
`de.vvwt.tm.scoring.PartialScoreInput` + `de.vvwt.tm.scoring.SetSubmitInput`
per its AC-PUBLIC-DTOS-CREATED. The field shapes match legacy verbatim
(confirmed on-disk). However the jakarta-validation annotations
(`@NotNull`, `@Min`, `@Max`, `@NotBlank`) that legacy
`PartialScoreRequest` + `SetSubmitRequest` carried were NOT copied
onto the new records — only the Javadoc invariants
("(NOT NULL)", "(0–99)", "(NOT BLANK)") were preserved.

Delivery of E22S09 picked up this gap via the STOP-gate
AC-DTO-VALIDATION-BOUNDARY-VERIFIED (which greps for
`@(Min|Max|NotBlank|NotNull)` on the 2 scoring-public record files
and expects >0 hits per file). Grep returned 0 → Delivery STOPPED
and escalated per E22S09's explicit "do NOT re-declare annotations
on web-internal DTOs" clause. E22S09 is currently `escalated` in
the backlog; E22S11 (atomic cutover) waits on E22S09.

**Classification**: Q-1b pure mechanical refactor under DEC-22
§refactor-clause. The annotations are declarative metadata
equivalent to the already-documented Javadoc invariants. No behavior
is introduced that was not documented by E22S06; this story makes
the documented behavior runtime-enforced by Jakarta Bean Validation
(the standard mechanism that legacy already relied on).

No new RED-first test is required — existing `DefaultScoreEntryServiceTest`
behavior assertions remain GREEN. A downstream slice test in E22S09
(`ScoreApiControllerSliceTest`) will assert `@Valid`-triggered 400
responses against the annotations; that coverage is E22S09 scope,
not this story's.

### Error handling

- [ ] **AC-S12-NO-NEW-EXCEPTION-TYPE**: No new Java exception type is
  introduced. The annotations will cause `jakarta.validation.ConstraintViolationException`
  (or `MethodArgumentNotValidException` at the MVC binding layer) to
  fire at controller boundaries when invalid input arrives — these
  exceptions already exist in the Spring/Jakarta runtime and are
  already mapped by the existing `GlobalExceptionHandler` (HTTP 400).
  Impl-report attests: no new exception class authored in this story.
- [ ] **AC-S12-ERROR-RESPONSE-UNAFFECTED-THIS-STORY**: The error
  response shape for invalid payload bindings is unchanged by this
  story — the `GlobalExceptionHandler` already produces a 400
  response body for `MethodArgumentNotValidException`. Wire-format
  parity vs legacy is asserted in E22S09 (slice test), not here.

### Security

- [ ] **AC-S12-SECURITY-INPUT-VALIDATION-RESTORED (SUBSTANTIVE)**:
  The added annotations re-establish legacy input-validation
  guarantees at the Jakarta Bean Validation boundary:
  - `@NotBlank String deviceToken` — prevents empty / whitespace-only
    device tokens from reaching `DeviceRepository.findByToken(...)`
    (which would otherwise execute a DB query with a blank key and
    could return spurious results or pollute query logs).
  - `@NotNull UUID matchId` — prevents null-UUID from reaching
    `MatchRepository.findById(...)` (NPE or wrong-match lookup).
  - `@Min(0)` / `@Max(99)` on point fields — prevents out-of-range
    numeric values from reaching set-validation logic
    (`SetValidationRule.isSetClosed(...)`) which assumes non-negative
    bounded inputs.
  Without these annotations (the current as-delivered state of
  E22S06), invalid inputs would bypass the Jackson-boundary guard
  and surface as `NullPointerException` / `IllegalArgumentException`
  deeper in the call stack — producing HTTP 500 (server error) rather
  than HTTP 400 (client error), and leaking implementation-detail
  stack traces in error bodies.
