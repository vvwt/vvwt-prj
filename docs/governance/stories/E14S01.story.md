# Story E14S01: Define `tenant::api` interfaces (TenantContext, TenantDataSourceResolver, TenantRegistryPort) — tests first

## User Story

**As a** developer implementing a data-accessing bounded context (starting with `auth` in E15),
**I want** the `tenant::api` public surface defined as stable, documented Java interfaces under `de.vvwt.tm.tenant`,
**so that** every consuming module declares `allowedDependencies = "tenant"` against a contract that will not churn beneath it.

---

## Context

DEC-20 fixes DB-per-Tenant as the multi-tenancy strategy and assigns the `tenant` context the responsibility for DataSource routing, registry lookup, and per-tenant Flyway execution. Modulith (DEC-21) treats the root package `de.vvwt.tm.tenant` as the public API surface; `de.vvwt.tm.tenant.internal` is implementation hidden from other modules.

This story defines the three interfaces on that public surface — `TenantContext`, `TenantDataSourceResolver`, `TenantRegistryPort` — as empty contracts backed by red tests. No implementation is wired yet; E14S02/S03/S04/S05 deliver implementations behind each interface. Getting the contract stable here prevents thrash across the remaining E14 stories and across E15's dependencies.

Per DEC-22, every interface method must have a failing test first. For interfaces, "failing" means a test that exercises the contract (via a test double) and asserts the contract shape — for example, verifying the resolver returns a non-null DataSource, or that the context rejects nested set/clear mismatches.

---

## Acceptance Criteria

- [ ] AC1 (testing — test-first discipline): For each of the three interfaces, git history shows a commit containing the first failing test for that interface before the commit introducing the interface itself. Spot-check on all three confirms red-then-green ordering per DEC-22. Characterization tests are forbidden.

- [ ] AC2 (governance — package placement): `TenantContext`, `TenantDataSourceResolver`, and `TenantRegistryPort` live in root package `de.vvwt.tm.tenant` (public API), NOT in `de.vvwt.tm.tenant.internal`. A `package-info.java` in the root declares `@ApplicationModule(allowedDependencies = {})` per DEC-21.

- [ ] AC3 (data-isolation — contract coverage): The interface contracts explicitly address (via Javadoc and test) (a) tenant identifier type — UUID-based per DEC-17, (b) resolution semantics when no tenant is bound (MUST fail fast, not return a shared DataSource), (c) lookup-by-identifier returning empty for unknown tenants versus resolution failing — distinction documented on each method.

- [ ] AC4 (testing — Modulith verify still green): After the package and `package-info.java` are in place, `ApplicationModulesTest` (from E13S01) continues to pass. The new annotated module does not introduce unresolved dependencies.

- [ ] AC5 (error-handling — unbound context): `TenantContext` contract specifies and tests that `current()` when nothing is bound throws a well-defined `IllegalStateException` (or an application-specific subtype) — never returns null and never silently returns a default. A contract test verifies this; a future implementation bug cannot degrade the contract to "silent default".

- [ ] AC6 (error-handling — unknown tenant resolution): `TenantDataSourceResolver` contract documents behaviour for unknown tenant identifiers — fast-fail with a typed exception, not a lazily-failing DataSource. The contract test asserts the exception shape.

- [ ] AC7 (governance — no implementation leak): No class under `de.vvwt.tm.tenant.internal` is introduced by this story. `git diff` at merge shows only interfaces, `package-info.java`, tests, and a minimal test-only fake if needed (tests may reside under `src/test/java/de/vvwt/tm/tenant/`).

- [ ] AC8 (governance — documentation): Each of the three interfaces has Javadoc describing: intended consumer, thread-safety expectations, transactional semantics (particularly for the resolver). No "TBD" placeholders — contracts are final, not exploratory. The Javadoc explicitly enumerates propagation surfaces where `ThreadLocal`-based `TenantContext` does NOT automatically propagate: `@Async` method invocations, `CompletableFuture.supplyAsync` (default common pool), `@Scheduled` tasks, reactive Mono/Flux boundaries, and cross-thread `@Transactional(propagation=REQUIRES_NEW)` on a TaskExecutor. Each listed surface requires manual context-capture-and-restore (e.g., `TenantContext.capture()` + re-bind inside the async block). This is a Wave-1 documentation obligation, not a Wave-1 implementation obligation.

- [ ] AC-NESTED-BIND (governance — nested binding semantics fixed in interface contract): `TenantContext.current()` throws `IllegalStateException` if no tenant is bound. `TenantContext.bind(tenantId)` MUST support re-entrant/nested binding — an inner `bind` overrides the outer for the inner's scope only, and `close()` restores the outer. This is specified in the Javadoc of `TenantContext` and tested in AC1/AC4. Downstream stories (E14S03) consume this contract and DO NOT re-open it.

## Notes

The interface shape decided here flows directly into E15's `auth` context as its only `tenant` dependency. Any ambiguity in, for example, how the resolver signals "tenant not found" vs "tenant known but DataSource unavailable" will cost E15 cycle time. Resolve both in Javadoc now.

Contract tests may use a hand-rolled test double (not a mock) to exercise the contract without binding to any future implementation. Keep the double in `src/test/java` — it is not a fixture for other modules' tests.
