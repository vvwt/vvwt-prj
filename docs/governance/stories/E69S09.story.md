# Story: Bug-Triage retrofit on E69S01 — `maven-enforcer-plugin requireExecutable` host-prereq enforcement for `shellcheck` + `bats` in `pi-display/pom.xml` + Host-Prerequisites section in `pi-display/README.md` (DEC-79 origin-incident closure)

## User Story

**As a** tournament operator (or delivery agent) building the `pi-display` module,
**I want** `mvn -pl pi-display validate` to fail fast with an actionable error message
that names the missing tool (`shellcheck` or `bats`) and provides installation
instructions, before `exec-maven-plugin` even attempts to invoke those tools,
**so that** any host that lacks `shellcheck` or `bats` receives an immediate,
operator-actionable error — not a confusing "Cannot run program: error=2" — and
no agent is tempted to self-install these tools mid-delivery to satisfy ACs
(closing the DEC-79 origin-incident gap on E69S01).

---

## Context

E69S01 (delivered 2026-05-25, PR #357) created the `vvwt-prj/pi-display/` Maven
module binding `shellcheck` and `bats-core` to `mvn verify` via
`exec-maven-plugin`. The delivering agent verified host absence of `bats` and
`shellcheck`, then installed both via `npm install -g --prefix ~/.local bats` and
a direct binary download — a self-bootstrap that violated the prohibition
DEC-79 later formalized. The impl-report (L61-64) noted this as an "operator
note" (passive prose), not a Story-Scope enforcement item.

Six days later, E70S01-attempt#1 failed because the daemon's `claude -p`
subprocess lacked `~/.local/bin` in PATH and `shellcheck` was not found; the
delivering agent wrote a DEC-71-forbidden self-granted carve-out. The
daemon-post-exit-gate caught the violation and wrote `chore(E70S01): failed`.
DEC-79 (2026-05-31) formalized the host-environment-integrity prohibition and
explicitly delegated E69S01's missing host-prereqs enforcement to this story
(DEC-79 §Out of scope + §References §Implementing Stories).

E69S09 is the **code-side Bug-Triage retrofit** that closes the origin-incident
gap: a `maven-enforcer-plugin requireExecutable` rule in `pi-display/pom.xml`
(fail fast BEFORE `exec-maven-plugin`; actionable error message naming the
missing tool) plus a "Host Prerequisites" section in `pi-display/README.md`
(operator-targeted install instructions for common package ecosystems).

This story is `track: bug-triage` per the Discovery Bug-Triage Flow in
`discovery.agent.md`. It is an in-place amendment to E69S01's artefacts and is
the ninth bug-triage retrofit under Epic E69 (continuing the E69S03–S08
sequential pattern).

## Notes

- **Bug-Triage provenance.** This story follows the Discovery Bug-Triage Flow per
  `.gaai/core/agents/discovery.agent.md` (`track: bug-triage`). Root cause
  established empirically at the DEC-79 Discovery session (2026-05-31): E69S01
  impl-report L61-64 documented the host-prereq gap as a passive "operator note";
  E70S01-attempt#1 surfaced the gap as a build failure when `shellcheck` was not
  on PATH. DEC-79 formalized the prohibition and delegated the code-side retrofit
  to E69S09.

- **DEC-79 §Out of scope closure.** DEC-79 §Out of scope reads: *"Recovery of
  E69S01 production code (the pi-display module is done + merged; the self-bootstrap
  was the delivery-time act, not a code defect) — separate Bug-Triage Story E69S09
  retrofits `maven-enforcer-plugin requireExecutable` + README Host-Prerequisites."*
  This story is that story. The DEC-79 §References §Implementing Stories entry for
  E69S09 is the canonical cross-reference; Delivery records this closure in the
  impl-report per AC5.

- **DEC-22 RED-first feasibility (AC1).** The `requireExecutable` rule is a
  structural pom.xml change, not a shell-script behavior change. The empirical RED
  state (build fails when shellcheck absent) is reproducible only on a host where
  shellcheck is NOT on PATH. If the Delivery host has shellcheck+bats present
  (standard delivery environment), empirical RED is structurally unavailable
  without host mutation (which DEC-79 Clause A forbids). Per DEC-22 §refactor-clause
  (memory `feedback_dec22_refactor_phase_first`): if empirical RED-first is
  structurally unavailable, declare as known accepted gap with impl-report
  attestation per the E69S02 W-X precedent. The AC1 body documents this
  decision rule exactly so Delivery is not left to interpret.

- **Enforcer phase binding choice.** E69S09 binds the `requireExecutable` rule
  to the `validate` phase. Maven's `requireExecutable` rule is checked by
  `maven-enforcer-plugin` at the `validate` phase when the execution is bound
  there. This ensures the error fires BEFORE the `integration-test`-phase
  `exec-maven-plugin` invocations that would otherwise produce a confusing
  "Cannot run program: error=2, No such file or directory" message. The
  `validate` phase runs on every `mvn verify` invocation (it is the first phase
  in the default lifecycle), so the guard fires automatically on all standard
  build invocations. Delivery may alternatively use `initialize` if `validate`
  proves insufficient — the AC3 requirement is phase-ordering (BEFORE
  `integration-test`), not the specific phase name.

- **README Host-Prerequisites placement.** The current `pi-display/README.md`
  structure (verified at pre-flight): SPDX header → title → Module Contents →
  Build (Prerequisites, Invocation, Expected output, SHA-256) → Flash → Boot &
  Verify → Watchdog Attestation → Splash Attestation → Known Limitations →
  Image-Build Attestation → Licensing. The "Security Notes" stub referenced in
  E69S01 AC5 is the `Security Notes` section; inspection of the current README
  shows it is part of the Prerequisites → Security-posture notes under the Flash
  section (WiFi credential paths). The "Host Prerequisites" section for Maven
  build-toolchain prereqs is DISTINCT from the Flash-prerequisite security notes.
  Delivery inserts the new "Host Prerequisites" section BEFORE the existing
  "Build" → "Prerequisites" subsection (or as a new top-level section before
  Build), so it is the FIRST thing an operator reads after Module Contents.
  Delivery has discretion on exact placement as long as it precedes the Build
  section and is clearly distinguished from the FullPageOS image-build prerequisites
  listed under Build → Prerequisites.

- **Reuse decision.** The `maven-enforcer-plugin` 3.5.0 coordinate is already
  managed in the parent POM's `pluginManagement` (confirmed at pre-flight:
  `vvwt-prj/pom.xml` line 473-474). The existing `bannedDependencies` blocks in
  `vvwt-info-server/pom.xml` (line 281) and other modules demonstrate the pattern:
  declare the `<plugin>` block with `<groupId>/<artifactId>` only, omit
  `<version>`, add a new `<execution>`. E69S09 follows the SAME pattern with
  `requireExecutable` rule instead of `bannedDependencies`. This is the Near-hit
  reuse decision documented in the `reuse_search` frontmatter.
