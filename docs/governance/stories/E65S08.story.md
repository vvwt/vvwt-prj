# Story: The Display reflects phase-status changes automatically when the tournament transitions a phase

## User Story

**As a** spectator or operator watching the public Display overview,
**I want** the Display to reflect the new phase status automatically whenever a phase
transitions (prepared, started, completed, force-completed) — without a manual reload,
**so that** the Display stays truthful on devices that have no input peripherals and cannot
be reloaded by hand.

---

## Context

The Display is a Vite + Svelte SPA running on input-less venue screens. It subscribes to a
tenant-scoped STOMP topic (`vvwt-tm-web/src/main/ui-display/src/App.svelte:345` —
`/topic/display/{phaseData.tenantId}/events`) and already has a handler for the
phase-status-changed event that triggers a full reload of its phase data
(`App.svelte:222-224`, `EVENT_TYPE_PHASE_STATUS_CHANGED` → `fullReload()`).

Running a tournament on 2026-05-29 the operator observed that when a phase transitions
(prepared / started / completed / force-completed) the Display does NOT pick up the new
status until the device is reloaded by hand — which is impossible on the input-less Display
hardware. The defect is BLOCKER for tournament operations on those devices.

Per the Discovery session of 2026-05-29 the full publish-to-broadcast chain has been
inspected end to end at HEAD (Brief H-1 VERIFIED): `DefaultPhaseLifecycleService`
publishes `PhaseStatusChangedEvent` from five sites — lines 304, 364, 469, 548, 593 of
`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/DefaultPhaseLifecycleService.java`
— passing `null` as the `tenantId` constructor argument with the comment "resolved by
DomainEventBridge via TenantContext"; the bridge
(`vvwt-tm-web/src/main/java/de/vvwt/tm/tournament/internal/web/DomainEventBridge.java:169-188`
— `onPhaseStatusChanged`) however does NOT resolve it and forwards the literal
`event.getTenantId()` (`null`) to `displayTopic(...)`, so the broadcast lands on
`/topic/display/null/events` and the SPA's tenant-scoped subscription silently drops it.
The SPA's own handler is correct (per Brief O-6); only the broadcast never arrives.

Two further consumers of `PhaseStatusChangedEvent` are tenantId-blind today and are NOT
affected by this defect (Brief H-2 VERIFIED): `DefaultHostActivityProbe.onPhaseStatusChanged`
(`vvwt-tm-web/src/main/java/de/vvwt/tm/slotopt/internal/DefaultHostActivityProbe.java:59-78`,
`@EventListener` — reads only `getPreviousStatus`/`getNewStatus`/`getPhaseId`) and
`DefaultTournamentEventDeltaPublisher.onPhaseStatusChanged`
(`vvwt-tm-web/src/main/java/de/vvwt/tm/infoportal/internal/DefaultTournamentEventDeltaPublisher.java:144-152`,
`@ApplicationModuleListener` — explicit no-op reading only `getTournamentId`). The bridge is
the only listener that reads `getTenantId`.

Counterpart event types already publish the right value at the publish site —
`DefaultScoringService.java:527,548` (`MatchResultChangedEvent`, `LapAdvancedEvent`) and
`DefaultMatchCorrectionService.java:514` pass `tenantContext.current()` — and reach the
Display correctly. This story makes phase-status-change behave the same way for the Display
without disturbing the surrounding event architecture (Brief D-1, T-2).

Two publish paths must both work: the REST controller path
(`PhaseLifecycleController` — 4 endpoints `prepare`/`start`/`complete`/`forceComplete`, web
interceptor sets TenantContext on the HTTP thread) and the Saga-Orchestrator path
(`vvwt-tm-web/src/main/java/de/vvwt/tm/phaselifecycle/internal/DefaultOrchestratorStepAExecutor.java:152`
invokes `transition(phaseId, PREPARED, "match-gen-done")` from a worker thread where
`DefaultWorkerRegistry` explicitly propagates TenantContext to the worker — DEC-64).

This is a bug-triage story: Delivery investigates the defect at HEAD, picks the technical
fix, and authors a RED-first regression that covers both publish paths.

## Acceptance Criteria

- [ ] AC1 (reproduction): Given a tenant-scoped tournament that has at least one phase, when
  the phase transitions to a new status (prepared, started, completed, or force-completed —
  via the REST `PhaseLifecycleController` endpoints), then the Display overview currently
  does NOT reflect the new phase status without a manual reload — this is the defect.
- [ ] AC2 (root-cause investigation): Delivery investigates the defect at delivery HEAD.
  Per Brief H-1 the publish-to-broadcast chain has been confirmed end to end —
  `DefaultPhaseLifecycleService` (5 publish sites at lines 304, 364, 469, 548, 593) →
  `DomainEventBridge.onPhaseStatusChanged` (`DomainEventBridge.java:169-188`) →
  `displayTopic(event.getTenantId())` → SPA subscription
  `/topic/display/{phaseData.tenantId}/events` (`App.svelte:345`); the SPA's
  `EVENT_TYPE_PHASE_STATUS_CHANGED` handler is confirmed correct (`App.svelte:222-224`).
  Delivery pins the exact root cause and records it in the impl-report — including which
  point in the publish→broadcast chain was changed and why. Listeners that do not read
  `getTenantId` (`DefaultHostActivityProbe`, `DefaultTournamentEventDeltaPublisher` — per
  Brief H-2) are out of scope and must not be modified.
- [ ] AC3 (expected behaviour): After the fix, when a phase transitions (any of the four
  REST endpoints OR the Saga-Orchestrator's `transition(phaseId, PREPARED, "match-gen-done")`
  step), every connected Display overview for the tournament's tenant reflects the new phase
  status automatically — without a manual reload — within ≤10 s on a LAN (the Display
  latency envelope established in E50S01 echo behaviour).
- [ ] AC4 (no regression): The noPhase → active recovery flow (E50S01) and the
  round-advance handler (E65S04) continue to work; scoring (`MatchResultChangedEvent`,
  `LapAdvancedEvent`), match-correction propagation, and per-tournament Saga-Orchestrator
  serialisation per DEC-37 Clause B are unchanged.
- [ ] AC5 (error-handling / no-regression): The Display's existing resilience is preserved
  — if a live phase-status-changed broadcast is missed (transient WebSocket drop or
  reconnect), the Display still converges to the correct phase status on its next refresh or
  reconnection, and the fix introduces no new failure mode (no NullPointerException, no
  silent drop on a tenant-less or unauthenticated publish path).
- [ ] AC6 (testing — regression): A web-module integration test, authored failing-first per
  DEC-22 (RED), reproduces the defect at the broadcast surface — asserting that for each of
  the four transitions the STOMP destination receiving the `PhaseStatusChangedEvent`
  broadcast equals `/topic/display/{realTenantId}/events` (NOT `/topic/display/null/events`)
  — and passes after the fix. The IT runs under `@SpringBootTest(RANDOM_PORT, classes =
  TournamentManagerApplication.class)` per DEC-44 D1. Both publish paths from Brief S-1a are
  exercised: the REST `PhaseLifecycleController` path AND the Saga-Orchestrator path
  (`DefaultOrchestratorStepAExecutor:152`); if one path is shown to be structurally
  redundant for this assertion, the impl-report documents why. The existing test suite
  continues to pass; behaviour not reachable by the test surface is recorded in the
  impl-report.
- [ ] AC7 (governance — no test-only code): No production method, constructor, or field is
  introduced that exists solely to satisfy tests (DEC-70 — every member of a production
  class). Tests exercise the genuine production surface.
- [ ] AC8 (governance — build gate): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS
  (DEC-54, DEC-71). Any new source file carries the AGPL-3.0-or-later SPDX header that
  Spotless `licenseHeader` enforces at the verify phase (DEC-75, DEC-76).

> All acceptance criteria must be verifiable.

## Out of Scope

- The Display SPA's `handleWsEvent` dispatcher and its `EVENT_TYPE_PHASE_STATUS_CHANGED`
  handler (correct per Brief O-6).
- The WebSocket connect / reconnect flow and the noPhase → active recovery path
  (E50S01) — only no-regression is asserted.
- Other event types' `tenantId` handling (`MatchResultChangedEvent`, `LapAdvancedEvent`,
  partial-score propagation) — they already publish the right value.
- The admin SPA, the scoring-tablet SPA, the Timer SPA — only the public Display overview
  is affected.
- Any DEC amendment — the `tenantId` constructor parameter on
  `PhaseStatusChangedEvent` already exists; only the value being passed is wrong (Brief
  S-3, C-6).
- Any refactor of the event-publish API or of the event/listener architecture (Brief S-4).
- The `DefaultHostActivityProbe` and `DefaultTournamentEventDeltaPublisher` listeners —
  tenantId-blind today; the fix neither requires nor breaks them (Brief S-5 / H-2).
- A wider phase-status event-architecture rework (Brief D-1).

## Notes

Source: Discovery Session Brief `discovery-2026-05-29-display-phase-status-tenantid-defect`
(2026-05-29). Severity BLOCKER per Brief D-4 — operator-confirmed that Display devices have
no input peripherals and manual reload per phase transition requires physical intervention.

The Brief identifies two equivalent fix shapes (informational — Delivery picks the HOW; the
WHAT-only AC voice per Bug-Triage discipline is preserved):

- **T-1 (a)** — supply `tenantContext.current()` at all five publish sites in
  `DefaultPhaseLifecycleService`. Matches the established
  `DefaultScoringService` / `DefaultMatchCorrectionService` pattern (Brief O-4, Q-1).
  Trade-off: five publish-site edits + `TenantContext` injection into the service. This is
  the Discovery preference.
- **T-1 (b)** — resolve `tenantId` inside `DomainEventBridge.onPhaseStatusChanged` via an
  injected `TenantContext`. Single-listener edit, but encodes the publisher bug as a bridge
  contract (the bridge's other listeners already receive a real `event.getTenantId()`).
- **T-3** — a compile-time-enforced variant of (a) — making `tenantId` a non-null
  constructor invariant on `PhaseStatusChangedEvent`. Stricter form of (a) and still
  WHAT-only.

Per Brief C-5 the `TenantContext` is already set on the publish thread by either the web
`TenantContextResolver` (REST `PhaseLifecycleController`) or `DefaultWorkerRegistry`
propagation (Saga `DefaultOrchestratorStepAExecutor:152`, DEC-64), so option (a) and (T-3)
are operationally sound on both paths. Per Brief Q-3 / C-7 the DEC-37 Clause B
per-tournament lock semantics MUST stay unchanged — publishing happens after the
`@Transactional` boundary on both paths.

Per Brief S-1a the regression IT obligation in AC6 covers BOTH publish paths (REST and
Saga); if Delivery shows one path is structurally sufficient for the broadcast assertion,
that justification is recorded in the impl-report. The Display SPA is a Vite + Svelte SPA;
no SPA change is expected — but if one is, it must respect the existing
`EVENT_TYPE_PHASE_STATUS_CHANGED → fullReload()` contract (Brief O-6).
