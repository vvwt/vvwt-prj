# Story: Job-status lifecycle + `finalResult` / `bestSoFar` + usable cache-hit `submit-job` response

## User Story

**As a** consumer of the dispatcher,
**I want** to query a job's real lifecycle status and obtain its computed result — and to
receive a usable result when my submitted job is a cache hit,
**so that** a submitter can actually retrieve the optimization outcome instead of polling a
status that never changes and a cache hit that carries no payload.

---

## Context

Two read surfaces of the dispatcher are unusable for obtaining a result:

1. **The job-status endpoint** (`GET /api/job-status/{jobId}`) returns `job.getStatus()`
   verbatim — and because nothing transitioned the status, it was perpetually `RECEIVED`.
   After E60S01–S03 the status is real (`RECEIVED` / `DECOMPOSED` / `COMPLETED`), but the
   endpoint still exposes no result: its response is `{jobId, status, totalPackets,
   completedPackets}`. A consumer that polls until `COMPLETED` still has no way to read the
   computed optimum.

2. **The cache-hit `submit-job` response** — when a structurally-identical job is already
   cached, `DefaultJobService.submitJob` short-circuits and returns
   `SubmitJobResponse(syntheticJobId, null, true)`: a `cacheHit` flag, a *synthetic* job id
   that no `JobRecord` backs (so it is not queryable via the job-status endpoint), and no
   result payload. The submitter is told "cache hit" and given nothing to read.

This story makes both surfaces yield the result. The job-status endpoint reports the real
lifecycle status and is extended with `finalResult` (the aggregated global optimum, present
once the job is `COMPLETED`) and `bestSoFar` (the best result among the job's completed
packets while the job is in progress). The cache-hit `submit-job` response is made usable —
the cached job optimum becomes retrievable by the submitter (carried inline in the response,
or via a queryable `COMPLETED` job — Delivery's design choice).

This is the surface the separate, later TM-integration epic consumes for its Leg-2 result
round-trip and Leg-2-cancel best-so-far — so the response shape and the endpoint path must
be the delivered ones, deliberately chosen, not the stale `E37.slotopt-contract.md` shapes.

## Acceptance Criteria

### Testing

- [ ] **AC-TEST-JOB-STATUS-REPORTS-LIFECYCLE** — RED-first (DEC-22): the job-status endpoint
  reports the real lifecycle — `RECEIVED` before decomposition, `DECOMPOSED` while packets
  are in flight, `COMPLETED` after finalization. The test fails on pre-E60 `HEAD` (always
  `RECEIVED`).
- [ ] **AC-TEST-JOB-STATUS-FINAL-RESULT** — for a `COMPLETED` job the job-status response
  exposes `finalResult` carrying the aggregated global optimum (`bestRank` + `bestScore`);
  for a job not yet `COMPLETED` `finalResult` is null/absent.
- [ ] **AC-TEST-JOB-STATUS-BEST-SO-FAR** — for an in-progress job (some packets
  `RESULT_RECEIVED`, some not) the response exposes `bestSoFar` — the best result among the
  job's completed packets, computed from the E60S02 per-packet retention store; `bestSoFar`
  is null/absent when no packet of the job has completed yet.
- [ ] **AC-TEST-CACHE-HIT-RESPONSE-USABLE** — when `submit-job` hits the result-cache
  short-circuit, the submitter can obtain the cached job optimum from the response: either
  the optimum is carried inline in the `submit-job` response, or the response yields a
  reference (e.g. a real, queryable job id) from which the optimum is retrievable. The test
  asserts the cached `bestRank` / `bestScore` is reachable — it is not on pre-E60 `HEAD`.
- [ ] **AC-TEST-SUITE-GREEN** — `mvn verify` is BUILD SUCCESS for `vvwt-slotopt-dispatcher`
  (DEC-54); the existing E37/E40 suite remains GREEN.

### Error Handling

- [ ] **AC-ERR-UNKNOWN-JOB-404** — a job-status query for an unknown `jobId` returns the
  existing HTTP 404 behaviour, unchanged by this story.
- [ ] **AC-ERR-BEST-SO-FAR-NO-COMPLETED-PACKETS** — `bestSoFar` for a job with zero
  completed packets is a defined null/absent value in a successful (HTTP 200) response, not
  an error.
- [ ] **AC-ERR-CACHE-HIT-RESPONSE-CONSISTENT** — whatever retrieval path the cache-hit
  `submit-job` response offers (inline payload or a queryable reference) resolves
  consistently to the cached job optimum; the submitter is never handed a reference that
  does not resolve.

## Out of Scope

- Job finalization, aggregation, the cache write — E60S03 (this story reads their outputs).
- Per-packet result retention — E60S02 (this story reads that store for `bestSoFar`).
- The `E37.slotopt-contract.md` granular packet-count breakdown and any packet-failure
  status.
- All TM-side consumption of these surfaces — the separate later TM-integration epic.

---

## Dependencies

- **E60S03** — hard dependency: `finalResult` requires job finalization + aggregation, and
  `bestSoFar` aggregates the per-packet retention store (E60S02, on which E60S03 already
  depends). E60S04 cannot be delivered before E60S03.

## Notes

`bestSoFar` is computed from the E60S02 per-packet retention store — **not** from the result
cache, which holds nothing for a job until finalization (wiring `bestSoFar` to the cache
would return null until `COMPLETED`, defeating its purpose). Related Session Brief items:
D-6, O-10 (the four spec-vs-code drift axes), C-11 (the binding spec→code mapping), S-5,
S-11, S-12.
