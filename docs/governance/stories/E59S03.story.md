# Story: AGPL §13 in-application source-code offer in every web UI

## User Story

**As a** user interacting with a vvwt-prj web UI over the network,
**I want** a visible, reachable way to obtain the application's source code,
**so that** my AGPL §13 right to the Corresponding Source is honoured — and so every
operator who runs a modified deployment inherits a §13-compliant baseline.

---

## Context

AGPL-3.0 §13 requires that anyone running a modified version of the program, with which
users interact over a network, prominently offer those users the Corresponding Source.
DEC-75 licensed vvwt-prj under AGPL-3.0-or-later. To make every deployment §13-compliant by
default, each network-interactive UI must itself present a source-code offer.

vvwt-prj has five network-interactive UIs: the TM Admin SPA, the TM Display SPA, the TM
Timer SPA, the Infoportal SPA (all Svelte per DEC-2), and the Mustache-rendered
Scoring-Tablet UI (DEC-19). The Display SPA and the Scoring Tablet are space-constrained —
their live views must not lose layout space — so the offer is placed on a secondary surface
there. "Prominently" is a judgement, not a bright line; the secondary-surface placement is a
deliberate, operator-confirmed trade-off, and the offer must remain genuinely discoverable.

This is the third story of Epic E59. It depends on E59S02 so the UI files it creates or
edits are already under the active DEC-76 license-header enforcement.

---

## Acceptance Criteria

- [ ] AC1 (governance): each of the five network-interactive UIs presents an AGPL §13
  source-code offer — a visible, reachable element linking to the Corresponding Source at
  `https://github.com/vvwt/vvwt-prj`. The set of network-interactive UIs is confirmed by a
  fresh inspection of the repository at delivery time.
- [ ] AC2 (governance): in the TM Admin SPA, the Infoportal SPA, and the TM Timer SPA the
  offer is a persistent, visible footer link (e.g. labelled "Source code").
- [ ] AC3 (governance): in the TM Display SPA the offer sits on a secondary surface (e.g. an
  info panel/overlay reachable from the live view) so that the live overview view loses no
  layout space. The entry point to that surface is a persistently-rendered, deliberately
  identifiable control on the live view — an icon alone qualifies only if it carries an
  accessible label / tooltip naming its purpose; an unlabelled or easily-missed element does
  NOT satisfy this AC (Brief Q-3 / O-5: the §13 offer must stay genuinely discoverable, not
  buried). The impl-report records the chosen entry point and why it is discoverable.
- [ ] AC4 (governance): in the Scoring-Tablet UI the offer is a plain static link placed on
  an existing non-live setup/info screen (the `register` / `hello` template), NOT on the
  live `field` scoring screen, implemented with no new JavaScript — consistent with DEC-19
  (Mustache + ES5 only; no framework, no bundled asset on the tablet).
- [ ] AC5 (governance): in every UI the offer's label/text makes clear it links to the
  application's source code and that the application is licensed under AGPL-3.0-or-later.
  The offer text is in English.
- [ ] AC6 (governance): the print-output templates (`templates/print/*`) are NOT given a §13
  link — they are not network-interactive UIs and are out of §13 scope.
- [ ] AC7 (testing): any behaviour introduced (e.g. an info-panel open/close toggle on the
  Display SPA) is covered by a test authored failing-first per DEC-22; a purely static link
  (the footer links, the tablet link) introduces no behaviour and needs no test. Delivery
  records the per-UI static-vs-behavioural classification in the impl-report.
- [ ] AC8 (governance): `mvn verify` from the `vvwt-prj` root is BUILD SUCCESS (DEC-54),
  covering the Java build and every frontend sub-build. Any source file E59S03 newly adds
  carries the DEC-76 SPDX license header — the Spotless `licenseHeader` enforcement (active
  after E59S02, on which this story depends) is part of this gate.

> All acceptance criteria must be verifiable.

## Out of Scope

- The repo-root `LICENSE` file (E59S01) and the per-file headers (E59S02).
- A §13 link in the print-output templates (AC6).
- Any redesign of the UIs beyond adding the source-code offer.
- The exact visual/pixel design of the offer and its entry point — Delivery decides within
  AC2–AC4.
- Changing the license — settled by DEC-75.

## Notes

E59S03 adds the AGPL §13 in-application source-code offer. Most of it is static
presentational markup (footer links, a tablet link) — no behaviour, no test (DEC-22). The
only candidate behaviour is a TM-Display-SPA info-panel toggle; AC7 routes that to
failing-first TDD. Per DEC-75 §Impact, the offer is built into the canonical app so every
downstream deployment inherits a §13-compliant baseline. The tablet placement (AC4) strictly
respects DEC-19 — Mustache + ES5, no new JavaScript, no bundled asset. The §13 link target
is a static external URL — no REST endpoint is added. `depends_on` E59S02 so any new file
E59S03 creates carries a DEC-76 header (the enforcement is active by then). Per DEC-13 the
work is delivered on a `story/E59S03` branch off `staging`; AI never pushes or merges to
`vvwt-prj/main`. The exact pixel placement is a Delivery decision — Discovery defines the
requirement and the space constraint, not the layout.
