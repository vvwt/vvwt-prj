# Story E41S07 (Bug-Triage): Fix — `vvwt-slotopt-standalone-worker` algorithm-deprecation-date tests are timezone-fragile: fixtures built from `LocalDate.now()` (JVM default zone) are not past the validator's UTC-authoritative DEC-48 boundary during the local-date-ahead-of-UTC window

## User Story

**As a** developer maintaining `vvwt-prj` — and the GAAI Delivery pipeline that gates every story on `mvn verify` (DEC-54 / DEC-71),
**I want** the `vvwt-slotopt-standalone-worker` algorithm-deprecation-date tests to pass deterministically regardless of the wall-clock instant and JVM default timezone at which the suite runs,
**so that** `mvn verify` exits zero at any time of day and the delivery pipeline stops escalating every story on a test flake it does not cause.

---

## Context

Five stories escalated within a single ~80-minute window on 2026-05-16 — `E60S02`, `E61S01`,
`E22S13`, `E16S04`, `E62S01` — every one with the identical blocker: *"pre-existing `mvn verify`
failure in `vvwt-slotopt-standalone-worker` blocks QA PASS per DEC-71."* Under DEC-71 a non-zero
`mvn verify` exit is an **unconditional** qa-report FAIL with no pre-existing-failure allowance, so
a single broken test in this module fails QA for every story in the pipeline, regardless of what
that story touches.

The `E60S02` delivery agent attributed the failure to *"hardcoded DEC-43 algorithm deprecation
dates that have now passed."* That attribution is **incorrect** — the tests use no hardcoded dates.
The real defect is a timezone-boundary fragility.

**Empirical reproduction (triage, 2026-05-16T23:55Z, `staging` HEAD `dee35094`).** Running the two
escalation-named test classes on staging HEAD reproduced exactly the four reported failures:

| Test | Failure |
|---|---|
| `AlgorithmValidationTest.validate_algorithm_past_deprecation_throws` | "Expecting code to raise a throwable" — no exception thrown |
| `AlgorithmValidationTest.validate_deprecation_boundary_semantics_dec48` | "Expecting code to raise a throwable" — no exception thrown |
| `AlgorithmValidationTest.recommended_migration_excludes_chosen_and_deprecated` | a past-dated algorithm was returned as a migration target instead of excluded |
| `DefaultBootstrapServiceTest.exit_78_on_algorithm_deprecated_past_deadline` | `NullPointerException` downstream — validation did not fail-fast, so the bootstrap flow continued to a null-mock `registerKey` response |

`Tests run: 19, Failures: 4` in `vvwt-slotopt-standalone-worker`.

**The mechanism.** The failing tests build deprecation-date fixtures from `LocalDate.now()` — the
JVM **default** timezone (the daemon host runs CEST, UTC+2): `PAST_DATE = LocalDate.now().minusDays(1)`,
and `today.minusDays(1)` in the boundary test. The production `AlgorithmValidator` evaluates the
deprecation boundary in **UTC**, exactly per DEC-48: an algorithm is past its deadline when
`!Instant.now().isBefore(deprecationDate.plusDays(1).atStartOfDay(ZoneOffset.UTC).toInstant())`.

Each day, during the window from local midnight to UTC midnight (00:00–02:00 CEST), the JVM
default-zone date is one calendar day **ahead** of the UTC date. Inside that window
`LocalDate.now().minusDays(1)` yields a date whose UTC end-of-day boundary
(`+1 day @ 00:00Z`) is still in the **future** relative to `Instant.now()`. The validator therefore
classifies a fixture intended as "past-deprecation" as **not yet past** — it does not fail-fast, the
warning/migration logic runs instead, and every assertion that expects rejection inverts. The
`DefaultBootstrapServiceTest` `NullPointerException` is a downstream symptom of the same skipped
fail-fast.

The daemon ran all five escalated stories' `started_at` between 22:06Z and 23:28Z on 2026-05-16 —
i.e. 00:06–01:28 CEST on 2026-05-17 — squarely inside that window. Outside the window (the other
~22 h/day) these tests pass, which is why Epic E41 originally passed QA: the tests have been
**latently flaky since E41S04 / E41S06 shipped (2026-04-28)** and only surface when QA runs in the
window.

This is a defect in **test code**. The production `AlgorithmValidator` is correct: DEC-48 makes the
deprecation boundary UTC end-of-day with the server clock authoritative, and the validator
implements precisely that. The fix is to make the tests' fixture dates unambiguous with respect to
that UTC boundary — not to change deprecation policy.

The rest of the codebase already handles this correctly and is **out of scope**: triage confirmed
`vvwt-slotopt-dispatcher` (`AnnouncedAlgorithmTest`, `DeprecatedAlgorithmExceptionTest` — fixed
absolute `LocalDate.of(...)` dates; `DefaultKeyRegistrationServiceTest` — injected `Clock.fixed(...)`,
the E40S03 precedent), `vvwt-info-server` (`RegistrationServiceTest` — injected `Clock`), and
`vvwt-info-dto` all build deprecation fixtures deterministically. `vvwt-slotopt-standalone-worker`
is the lone outlier.

## Root Cause Analysis

- **Root cause:** the `vvwt-slotopt-standalone-worker` algorithm-deprecation-date tests construct
  "past" / "boundary" deprecation-date fixtures from `LocalDate.now()`, evaluated in the JVM
  **default** timezone. The production `AlgorithmValidator` evaluates the DEC-48 deprecation
  boundary in **UTC** (`deprecationDate.plusDays(1).atStartOfDay(ZoneOffset.UTC)` vs `Instant.now()`).
  When the JVM default zone is east of UTC, a "yesterday" fixture in default-zone terms is not yet
  past the UTC end-of-day boundary during the daily local-midnight-to-UTC-midnight window — so the
  validator does not reject it and the rejection-expecting assertions invert. The defect is a
  zone/clock mismatch between test fixtures and production boundary math; it is **not** a hardcoded
  expired date (the `E60S02` escalation's stated cause is wrong).
- **Originating change:** the affected tests were authored under Epic E41's Q-1a TDD — chiefly
  E41S04 (`AlgorithmValidationTest`, `DefaultBootstrapServiceTest`) and E41S06 (the
  `Deprecation*IT` integration tests). The fragility shipped with them on 2026-04-28; it is not a
  regression from any later story.
- **Why it surfaces only now:** the failure is wall-clock-windowed (~2 h/day in CEST). The Delivery
  Daemon happened to run a batch of stories' QA inside that window on 2026-05-16/17; all of them
  hit the same module's flake.
- **Blast radius:** every `mvn verify` run inside the window exits non-zero. Because DEC-54 / DEC-71
  make `mvn verify` exit-zero the unconditional closure gate, the **entire Delivery pipeline** is
  blocked during that window. Five stories (`E60S02`, `E61S01`, `E22S13`, `E16S04`, `E62S01`) have
  already escalated on it, and it recurs daily until fixed.
- **Why no production change is required:** `AlgorithmValidator` correctly implements DEC-48 — UTC
  end-of-day boundary, server clock authoritative. The fix belongs in the test fixtures. Delivery
  may, at its discretion, alter production code if it judges a different HOW cleaner, but it must
  not introduce a production seam that exists solely for tests (DEC-70) — see
  `AC-GOV-NO-TEST-ONLY-SEAM`.

### Fix

- [ ] **AC-FIX-DETERMINISTIC-DEPRECATION-TESTS**: After the fix, every test in
  `vvwt-slotopt-standalone-worker` that exercises algorithm-deprecation-date logic passes
  deterministically — its pass/fail no longer depends on the wall-clock instant or the JVM default
  timezone at which the suite runs. A fixture's "past" / "future" / "boundary" deprecation date is
  unambiguous with respect to the boundary the production code evaluates.
- [ ] **AC-FIX-ALIGNED-TO-DEC48**: The corrected tests are aligned to the DEC-48 boundary semantics
  the production `AlgorithmValidator` implements — the deprecation boundary is
  `deprecationDate.plusDays(1).atStartOfDay(ZoneOffset.UTC)` compared against a UTC instant. A
  "past-deprecation" fixture is one whose boundary is genuinely before the instant the validator
  compares against; a "future" fixture is genuinely after; a "boundary" fixture exercises the
  today-is-`deprecation_date`-accepted / day-after-rejected edge per DEC-48. (HOW — UTC-anchored
  fixture dates, a widened day offset, a fixed clock, or otherwise — is a Delivery decision.)
- [ ] **AC-FIX-MODULE-WIDE-AUDIT**: Delivery audits every test in `vvwt-slotopt-standalone-worker`
  (unit and integration, all packages) that constructs or asserts an algorithm `deprecation_date`,

  the tests named in Context (e.g. the deprecation integration tests are in the same suite and must
  be audited). The audit, the full set of files changed, and the reason any audited test was left
  unchanged are recorded in the impl-report.
- [ ] **AC-FIX-NO-PRODUCTION-BEHAVIOUR-CHANGE**: The observable behaviour of `AlgorithmValidator`
  (and `DefaultBootstrapService`'s use of it) is unchanged — it still rejects an algorithm past its
  DEC-48 UTC end-of-day boundary, still warns (not fail-fast) on a future `deprecation_date`, and
  still derives recommended-migration targets exactly as before. If the fix touches production code
  at all, the production deprecation-boundary evaluation remains UTC-authoritative against the real
  system clock and the DEC-48 semantics are preserved unchanged.
