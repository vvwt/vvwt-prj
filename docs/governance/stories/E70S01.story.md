# Story E70S01: Activate PMD CPD for Java token-duplication detection in vvwt-prj `mvn verify`

## User Story

**As an** operator + every Delivery agent,
**I want** Java code duplication to fail the build mechanically when token-similar code blocks exceed a tuned threshold,
**so that** the print-schedule-class drift pattern (two production paths computing the same thing redundantly) is detected at build time instead of being discovered after a production incident.

---

## Context

DEC-78 establishes the Clean Code Principles Governance ruleset; the framework rule `clean-code.rules.md` classifies DRY-lexical as **hard-gated**. This Story operationalizes the hard-gated DRY-lexical surface for Java code in vvwt-prj by wiring **PMD CPD** (Copy-Paste Detector) into `mvn verify` (DEC-54) via the existing `maven-pmd-plugin` plugin family, with parent-POM inheritance per DEC-29 / DEC-30 / DEC-76 precedent.

The activation produces (i) a parent-POM `<plugin>` declaration with `<execution>` binding to the `verify` phase + `<configuration>` naming the `cpd-check` goal + threshold, (ii) a rule-set / threshold-config (PMD CPD's `--minimumTokens` flag value, justified empirically in `impl-report.md`), (iii) a baseline-suppression file capturing pre-existing duplicates (default posture per DEC-78 Clause E — suppress-with-tracking), and (iv) a per-Story injected-violation fixture (DEC-22 RED-first artefact — fails against unmodified codebase, GREENs once gate is configured).

Per DEC-78 Clause C, the pure pom.xml `<plugin>` addition is DEC-67 carve-out (non-authoring build-descriptor coordinate); the rule-set config + fixture test are DEC-22 RED-first.

## Acceptance Criteria

- [ ] **AC1 (governance / DEC-67 classification)**: The pom.xml `<plugin>` declaration for `maven-pmd-plugin` (with `<execution>` binding `cpd-check` goal to phase `verify` + `<configuration>` naming `minimumTokens`) is added in vvwt-prj's parent POM at `vvwt-prj/pom.xml` (the Maven multi-module parent per DEC-10 + DEC-29/DEC-30/DEC-76 inheritance precedent) — per-module overrides in submodule POMs are forbidden except where explicitly justified in `impl-report.md`. Citation: DEC-67 (non-authoring carve-out per DEC-78 Clause C broader reading).
- [ ] **AC2 (build-gate / mvn verify binding)**: After this Story merges, `mvn verify` invoked from `vvwt-prj/` exercises PMD CPD on Java sources across all Maven submodules. A novel intra-file Java token duplication exceeding `minimumTokens` (≥1 block, both sides in `src/main/java`) produces non-zero `mvn verify` exit per DEC-54 § 2026-05-15 Amendment.
- [ ] **AC3 (testing / DEC-22 RED-first injected-violation fixture)**: A RED-first regression fixture under `.gaai/core/scripts/tests/clean-code/` (or vvwt-prj/`{module}/src/test/java/...`) — name suggestion `CleanCodeCpdJavaActivationIT` — exists. The fixture authors a synthetic Java file with a deliberately duplicated `≥minimumTokens` block, invokes the configured PMD CPD goal, and asserts the goal's verdict is FAIL (non-zero exit OR PMD violation count ≥ 1 on the synthetic block). The fixture was authored RED (verified non-zero exit) BEFORE the plugin configuration was added.
- [ ] **AC4 (testing / suppress-with-tracking baseline)**: A baseline-suppression file (`.gaai/project/cpd-baseline.xml` or PMD-conventional path) captures all pre-existing PMD CPD findings present at first activation. The baseline file is committed alongside the plugin configuration. After activation, `mvn verify` is BUILD SUCCESS on the unmodified codebase (suppressions in force).
- [ ] **AC5 (testing / mvn verify GREEN)**: `mvn verify` invoked from vvwt-prj root after the activation is BUILD SUCCESS, exit code zero, with PMD CPD effectively skipping the baselined pre-existing duplicates and only reporting NEW violations.
- [ ] **AC6 (governance / impl-report)**: The story's `impl-report.md` documents (a) the chosen `minimumTokens` threshold value + empirical justification (number of findings at the chosen threshold vs ±25%), (b) the suppression-baseline file size (number of suppressed findings), (c) first-empirical observation per H-1 (DEC-78 §Hypotheses), and (d) `mvn verify` exit code zero per DEC-54 / DEC-71. Citations: DEC-78, DEC-22, DEC-54, DEC-67.

## Notes

**Tool choice rationale**: PMD CPD is the Java-native token-duplication detector with first-class Maven binding (`maven-pmd-plugin` `cpd-check`), AST-aware tokenization (more precise than byte-CPD), and parent-POM-inheritance compatibility. Steel-manned alternatives (Simian, raw byte-CPD, SonarQube) were rejected per DEC-78 §T-3 (Simian = shareware → DEC-3 violation; byte-CPD = no Maven binding; SonarQube = proprietary service per DEC-3 + no-CI per DEC-54).

**Threshold tuning**: Industry conventional default is `--minimumTokens=100`. Empirical tuning at activation may justify a tighter (more findings, higher recall) or looser (fewer false-positives, esp. on DTO builders / fluent chains / standard boilerplate) value. The chosen value is documented in `impl-report.md` per AC6 with the number of findings at the chosen threshold + the number at ±25% as comparison.

**Anti-dogma**: Per `clean-code.rules.md` §Application Discipline Clause 2 (Rule of Three), two similar Java code blocks are NOT a DRY violation. The CPD threshold should be set such that only ≥3-occurrence-class duplications fire — false-FAIL on intentional symmetry (e.g., test fixtures with deliberately mirrored Given/When/Then) is mitigated by the suppression baseline (AC4).

**Asymmetric-error preference**: Per DEC-47 Clause F / DEC-71 — when in doubt on threshold, prefer slightly stricter (more sensitive). The suppression baseline absorbs false-positives without weakening the gate against new violations.
