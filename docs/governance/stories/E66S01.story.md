# Story: Decouple team-sort from team-distribution and unify the phase-transition proposal computation

## User Story

**As a** tournament organizer,
**I want** the team-assignment proposal for a phase to first rank the teams and then spread that ranking across the groups by the configured distribution mode,
**so that** the proposal reflects both the team ranking I chose and the distribution I chose — for every phase, not just the first.

---

## Context

When the operator opens the phase-transition ("Phasenwechsel") screen for a Phase-2+
transition, the proposal does not reflect the configured distribution mode. The cause is in
`DefaultPhaseTransitionService`: the Phase-1 path (`computePhase1Proposals`) correctly
composes a fixed `team_number` sort with `DraftSection.distributionMode` via a
`Team2AvatarDistributor`; but the Phase-2+ path (`computeProposals`) reads only `sortType`
and **ignores `DraftSection.distributionMode` entirely** — each of the three
`TeamSortCalculator` implementations hardcodes its own distribution. The two calculators
that rank by results (`PlacementGroupSortCalculator`, `GroupPlacementSortCalculator`) also
sort by **points only**, with no set-, ball-, or position tie-break. This conflation is
legacy behaviour that E58S03 preserved 1:1 from the original switch-case.

DEC-77 settles the model: a `TeamSortCalculator` produces a flat ranked list of teams; a
`Team2AvatarDistributor` spreads that list across the groups; the two compose for **every**
phase. The two proposal functions collapse into one. This story is the backend foundation
of Epic E66 — the editable controls (E66S02), the ranking-basis display (E66S03) and the
Display-standings alignment (E66S04) all build on it. It changes no UI.

## Acceptance Criteria

- [ ] AC1 (testing): TDD per DEC-22 — failing tests are authored before the production
  change. The sort (flat ranking) and the distribution (group spread) are tested as
  separate units, and their composition is tested; this is a backend story — no Svelte
  component mount is involved.
- [ ] AC2: a `TeamSortCalculator` produces a **flat ordered list** of the teams entering
  the next phase — it assigns no `(groupNumber, groupPosition)`. A `Team2AvatarDistributor`
  consumes a flat ordered list and produces the `(groupNumber, groupPosition)` placement.
  The phase-transition proposal is the composition `distribute(sort(...))`.
- [ ] AC3: the composed sort-then-distribute pipeline runs for **every** phase — the
  initial (no-predecessor) transition and every later transition. For a Phase-2+
  transition the proposal reflects `DraftSection.distributionMode` (`sequential` vs
  `round_robin`), which the Phase-2+ path currently ignores — the same flat ranking spread
  `sequential` and spread `round_robin` produces two different, mode-appropriate proposals.
- [ ] AC4: the three `sortType` flat-sort orders behave per DEC-77 D-2 — `team_number`
  ranks by team registration number ascending; `placement_group` ranks placement-first
  then source group (rank-major: rank-1 of every source group, then rank-2 of every source
  group, …); `group_placement` ranks source-group-first then placement (group-major: all
  of source group 1 in placement order, then all of source group 2, …). Throughout AC4,
  "placement" / "rank" means the placement comparator order defined in AC5.
- [ ] AC5: the placement/rank order is points descending → set ratio (`setQuotient`)
  descending → ball ratio (`ballQuotient`) descending → source-phase group position
  (`TeamAvatar.groupPosition`) ascending; a team flagged `TeamAvatarRating.withoutAssessment`
  ranks below every assessed team. Teams that tie on points are ordered deterministically
  by the lower tie-breakers — never left in an arbitrary order.
- [ ] AC6: there is exactly one proposal-computation function, `computeProposals`;
  `computePhase1Proposals` no longer exists. The no-predecessor case is handled inside the
  single function — teams are taken from the registered participating tournament teams and
  `sortType` is forced to `team_number` (the placement-based sorts require a played
  predecessor phase with ratings; this invariant is preserved). At delivery, the codebase
  is audited so that no caller of a removed `computePhase1Proposals` remains.
- [ ] AC7 (governance): no `TeamSortCalculator` and no `Team2AvatarDistributor` writes
  `teamId` — `teamId` is written exclusively by the operator-confirmation handler
  (DEC-59 Clause C); the distributor emits structural `(groupNumber, groupPosition)`
  coordinates only (DEC-9). Any self-created Spring component added or changed by this
  story carries a public interface in the bounded-context root package per DEC-35 / DEC-58.
- [ ] AC8 (governance): the individual `team_number` order and the `sequential` /
  `round_robin` spread algorithms, and the Phase-1 proposal for an unchanged configuration,
  are behaviour-preserved; the deliberate behavioural changes — Phase-2+ now honouring
  `distributionMode`, and the placement comparator replacing the points-only ordering —
  are the ones DEC-77 mandates and are not regressions. The transition-proposal REST
  endpoint output shape is unchanged. `mvn verify` is BUILD SUCCESS for `vvwt-tm-web`,
  including the frontend build via `frontend-maven-plugin` (DEC-54).

> All acceptance criteria must be verifiable.

## Out of Scope

- The phase-transition page's editable sort / distribution controls (E66S02) and the
  ranking-basis display (E66S03) — this story changes no UI.
- The Display overview standings (E66S04).
- Changing the set of `sortType` keys (three retained) or `distributionMode` keys (two
  retained), or adding any new sort or distribution algorithm (DEC-77 §Scope).
- Any migration of persisted `draft_json` values (DEC-25 no-production-data posture).

## Dependencies

- None as a hard prerequisite — the `TeamSortCalculator` and `Team2AvatarDistributor`
  registries this story rebuilds were delivered by Epic E58 (`done`). Independently
  deliverable.
- DEC-77 — the governing decision (sort/distribution decoupling, the placement comparator,
  the unified `computeProposals`).
- DEC-59 — the operator-confirmation workflow; `teamId` is written only at confirmation.
- DEC-9 / DEC-56 — TeamAvatar structural identity; matches reference avatar slots, not
  teams — so the decoupling does not affect generated matches.

## Notes

This is a deliberate, DEC-77-mandated behavioural change for Phase-2+ transitions, not a
behaviour-preserving refactor — the legacy conflation is the defect being corrected.
Delivery decides the exact strategy signatures (e.g. how the flat list is typed so one
distributor serves both the registered-team and previous-phase-avatar input sources) and
the testable seams; the ACs state the behaviour, not the mechanism. The placement
comparator introduced here is the single shared implementation that E66S04 reuses for the
Display overview standings (DEC-77 D-6) — it must be reachable for that reuse.
