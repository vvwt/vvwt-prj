# Epic E27: Wave-2 Track 3 — `slotopt-integration` Bounded-Context Completion (Pattern C Strict-Additive)

## Purpose

Complete the `slotopt-integration` bounded context per DEC-21 (Spring Modulith) — the last Wave-2 epic per DEC-45 D2 trajectory (E25 + E26 + E27). This epic operationalizes the user-stated routing policy (2026-04-28) for slot-optimization compute placement, codifies it via the new **DEC-49 amendment to DEC-4 V1**, and unblocks E01S10 (TM HTTP-submitter pattern, blocked since 2026-04-11 awaiting TM-module bootstrap).

User outcome: a tournament organizer can launch slot-optimization on any phase regardless of internet connectivity. For ≤10 rounds the optimization runs locally in-process (existing E04S03 path, byte-equivalent). For >10 rounds, if the configured dispatcher is reachable the optimization is offloaded via HTTP (distributed compute, faster); if unreachable, optimization runs locally with a cancelable timeout — the admin sees a clear "in-progress, no dispatcher" status and can cancel at any time, receiving the best-so-far permutation found at cancellation. The existing N≤10 behavior is preserved unchanged; the existing 11 Snapshot-Driven mapper+applicator tests stay green against their (untouched) subjects.

This epic resumes per-epic Discovery 2026-04-28 with Pattern C STRICT-ADDITIVE strategy (substantively chosen over Wave-2 D-7γ Reconstruction-in-place per DEC-22 § Decision item 5). Pre-conditions:

- DEC-44 + DEC-45 active and propagated.
- E25 (display) + E26 (timer) Wave-2 epics done; E27 unblocks the final Wave-2 web `allowedDependencies` extension.
- Per audit 2026-04-28: existing `de.vvwt.tm.slotopt.*` (6 classes, ~600 LOC, 11 Snapshot-Driven tests on `PhaseToRawPhaseDefMapper` + `SlotResultApplicator` only; `DirectSlotOptimizationClient` + `FallbackSlotOptimizationClient` are untested) was authored by E04S01–S04 (done 2026-04-12, **before DEC-22 was created 2026-04-18**) — per DEC-22 § Decision item 5 the reconstruction-vs-not choice is "a separate Wave-2 Epic scope decision". This epic substantively decides "not": Pattern C strict-additive preserves the working algorithm + non-trivial invariants; greenfield work concentrates on the actual gap (routing + cancelable in-process + dispatcher HTTP + admin-cancel + DEC-43 D3 warning surface).
- Per audit 2026-04-28: `DirectSlotOptimizationClient.java:184-193` throws `UnsupportedOperationException` for N>exhaustiveMaxN with explicit comment "E04S04 not yet implemented" — E04S04 backlog status `done` does NOT reflect on-disk reality. The N>10 in-process compute substrate is **greenfield code**, not a repurpose; this is materialized via Leg 3 (E27S02) under DEC-22 Iron Law.

## Scope

**Strategy:** Pattern C STRICT-ADDITIVE per Brief D-1 + Q-5. Zero modification of existing classes in `de.vvwt.tm.slotopt.*` (`SlotOptimizationClient`, `DirectSlotOptimizationClient`, `FallbackSlotOptimizationClient`, `PhaseToRawPhaseDefMapper`, `SlotResultApplicator`, `MappingResult`). **Architecture (codified by DEC-49):**

`RoutingSlotOptimizationClient` is a NEW `@Primary @Service` bean implementing `SlotOptimizationClient`. It injects `DirectSlotOptimizationClient` **as concrete class** (not via interface) to avoid autowiring-resolution cycle. Three routing legs:

| Leg | Trigger | Path | Provenance |
|---|---|---|---|
| **Leg 1** | N ≤ `tm.slotopt.exhaustive-max-n` (default 10) | Delegate to existing `DirectSlotOptimizationClient` (in-process exhaustive) | DEC-4 V1 amendment (existing) |
| **Leg 2** | N > threshold AND `tm.slotopt.dispatcher.url` is non-null AND reachable | Submit job to dispatcher via HTTP (E01S10 pattern; DEC-11 boundary; DEC-43 wire format) | DEC-49 D-3 (NEW) |
| **Leg 3** | N > threshold AND (URL null OR unreachable) | NEW in-process cancelable timeout compute via `vvwt-slotopt-worker-lib`'s `PacketSolver`; admin cancels → returns Best-So-Far | DEC-49 D-3 (NEW; greenfield code) |

`FallbackSlotOptimizationClient` stays disabled (its `@ConditionalOnMissingBean` evaluates to false because two `SlotOptimizationClient` beans now exist: Routing + Direct).

**Threshold semantic (per Brief D-13):** N = rowCount = number of rounds in the optimization schedule. `PacketSolver` evaluates N! permutations of round orderings; therefore round count is the natural complexity threshold. The existing config property `tm.slotopt.exhaustive-max-n` (default 10) is preserved as-is; DEC-49 references it verbatim.

**Modulith bounded-context registration:** `de.vvwt.tm.slotopt/package-info.java` declares `@ApplicationModule(allowedDependencies = {"tournament"})`. The exact set is empirically verified at E27S01 RED-first compile-attempt per E26S01 OMIT-IF-UNUSED precedent. `web/package-info.java` `allowedDependencies` extends with `"slotopt"` when E27S02 introduces the admin-cancel REST controller (DEC-40 Trigger-α already-fired since E24S06; DEC-45 D2 §E27 unconditional FIRM pre-approval covers this addition).
